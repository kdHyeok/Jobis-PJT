# 공고 중복 판별과 운영자 최종 승인

- 날짜: 2026-07-31
- 상태: 결정됨 · 1차 구현 완료
- 범위: 공용 공고 카탈로그, 공고 분석 재사용, 대체 공고 추천, 운영자 기능

## 배경

동일한 이스트게임즈 공고를 여러 사용자가 분석한 결과, 공용
`posting_catalog`에 같은 공고가 여러 건 등록됐다. 공고 원문이 같아도 AI가
회사명, 직무명, 경력 표현을 조금씩 다르게 만들었고, 현재 지문이 이 값을
포함하기 때문에 서로 다른 공고로 식별됐다.

그 결과 대체 공고 추천에서 사실상 같은 이스트게임즈 공고가 여러 카드로
노출됐다. 이 문제는 화면의 단순 중복이 아니라 공용 공고의 정체성 모델과
검토 절차가 부족해서 발생했다.

## 결정

공고 중복 처리는 규칙, AI 에이전트, 운영자의 역할을 분리한다.

### 1. 정확 중복은 백엔드가 즉시 판별한다

다음 값은 AI를 호출하지 않고 정규화된 값과 해시로 비교한다.

- 채용 플랫폼과 플랫폼 공고 ID
- 정규화한 원본 URL
- 공고 원문 해시

정확히 일치하는 공고는 같은 대표 공고에 연결한다. 자동 연결 내역도 감사
기록에 남겨 운영자가 확인하거나 되돌릴 수 있어야 한다.

### 2. 애매한 유사 공고는 AI가 판정안을 만든다

백엔드가 먼저 유사 공고 후보를 좁히고, AI 에이전트는 후보끼리만 비교한다.
AI의 구조화된 판정 값은 다음 네 가지다.

- `SAME_POSTING`: 동일한 공고
- `SAME_RECRUITMENT_VARIANT`: 같은 모집 공고의 직무·경력 변형
- `DIFFERENT_POSTING`: 별개의 공고
- `UNKNOWN`: 근거가 부족해 판정할 수 없음

AI는 판정, 신뢰도, 근거, 주요 차이를 제공한다. AI에게 공고 병합이나 삭제
권한은 주지 않는다.

### 3. 운영자가 최종 판정한다

AI의 판정안은 운영자 페이지의 중복 검토 대기열에 등록한다. 운영자는 다음
작업 중 하나를 선택한다.

- 동일 공고로 연결
- 같은 모집의 변형으로 연결
- 별개 공고로 유지
- 판정 보류

운영자 화면에는 두 공고 원문과 정규화 정보, 요구 조건 차이, AI의 근거와
신뢰도, 연결된 사용자·분석·로드맵 수, 판정의 예상 영향을 함께 표시한다.
모든 판정은 운영자, 시각, 변경 전후 값이 남아야 하며 취소할 수 있어야 한다.

### 4. 공고 원본, 관측, 변형, 사용자 평가를 분리한다

논리적으로 다음 책임을 분리한다. 실제 테이블 이름은 구현 시 확정한다.

- 대표 공고: 서비스 전체에서 공유하는 정규화된 공고
- 공고 관측: 각 사용자가 입력한 URL, 원문, 수집 시각과 출처
- 모집 변형: 프론트엔드·백엔드, 신입·경력처럼 한 모집 안의 선택지
- 분석 버전: 모델과 프롬프트 버전에 따른 공통 분석 기록
- 사용자 평가: 사용자의 역량과 비교한 준비도, 공백, 로드맵 제안
- 중복 검토 건: AI 판정안과 운영자 최종 결정

공용 공고를 연결하더라도 사용자의 원문, 대화, 평가, 로드맵 진행 상태는
삭제하거나 다른 사용자에게 공개하지 않는다.

### 5. 사용자 요청을 운영자 검토로 막지 않는다

운영자 판정과 애매한 중복 판정은 사용자 분석의 핵심 요청 경로 밖에서
비동기로 실행한다.

사용자 흐름은 다음과 같다.

1. 공고 입력
2. URL·원문 해시로 정확 중복 조회
3. 공통 분석을 재사용하거나 새 분석 시작
4. 사용자별 역량 비교와 결과 제공
5. 별도 백그라운드 작업으로 유사 후보 판정 및 운영자 검토 등록

사용자는 AI의 유사 중복 판정이나 운영자 결정을 기다리지 않는다. 정확히
같은 공고가 이미 분석됐다면 공통 분석을 재사용하므로 오히려 더 빨라져야
한다.

### 6. 대체 공고는 대표 공고 기준으로 한 번만 보여준다

정확히 같은 원문 해시의 공고는 운영자 판단 전에도 하나의 카드로 표시한다.
애매한 변형은 대표 카드 아래에 “유사한 직무 변형”으로 묶어 펼칠 수 있다.
추천 조회는 개별 카탈로그 행 ID가 아니라 대표 공고 또는 표시 그룹을 기준으로
중복을 제거한다.

운영자 판정 후에도 사용자의 기존 로드맵을 자동으로 재작성하지 않는다.
대표 공고 연결만 갱신하고 로드맵 변경은 사용자가 다음 초안을 만들고 적용할
때 반영한다.

## 현재 구현

- 플랫폼 공고 ID와 정규화 원문 SHA-256으로 정확 중복을 먼저 연결한다.
- 동일 원문·동일 추가 답변은 사용자 무관 공통 분석을 재사용하고 사용자별
  적합도와 백엔드 준비도는 다시 계산한다.
- 유사한 카탈로그 후보는 검토 대기열에 쌓이며 운영자 화면에서 병합·분리·
  보류하고 병합을 되돌릴 수 있다.
- 추천은 출처 ID와 원문 지문으로 중복을 제거하고 마감·비검증·병합 공고를
  제외한다.
- 공고 관측과 사용자 원문은 사용자별 RLS 영역에 남고 대표 카탈로그 연결만
  공용으로 관리한다.
- 후보에 대한 AI의 `SAME_POSTING | SAME_RECRUITMENT_VARIANT |
  DIFFERENT_POSTING | UNKNOWN` 사전 판정은 후속 고도화 범위다. 현재 1차 후보는
  규칙 기반 유사도와 근거로 운영자에게 제시한다.

## 수용 기준

- 동일한 URL 또는 원문을 여러 계정에서 등록해도 추천에는 한 번만 표시된다.
- 같은 모집의 프론트엔드·백엔드, 신입·경력 변형은 삭제되지 않고 대표 공고
  아래에 구분되어 남는다.
- 애매한 후보는 AI 판정 근거와 함께 운영자 대기열에 나타난다.
- AI가 단독으로 공고를 병합하거나 삭제할 수 없다.
- 운영자 판정은 감사 기록과 되돌리기를 지원한다.
- 중복 판정과 운영자 검토 때문에 사용자의 최초 분석 응답 시간이 늘어나지
  않는다.
- 이미 분석한 동일 공고는 공통 분석을 재사용하고 사용자별 비교만 다시
  수행한다.
