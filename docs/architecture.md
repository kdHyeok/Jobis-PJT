# JOBISS 아키텍처

## 실행 구조와 신뢰 경계

```text
Browser
  └─ HTTPS ─> Vue/Nginx
                └─ /api ─> Spring Boot
                              ├─ transaction-scoped RLS ─> PostgreSQL
                              └─ authenticated internal HTTP ─> AI server
                                                                  └─ Claude
```

- 인증은 HttpOnly `jobiss_access` 쿠키, 변경 요청 보호는 CSRF 토큰을 사용합니다.
- 브라우저가 보낸 `userId`는 소유권 판단에 사용하지 않습니다.
- Spring Security가 인증한 UUID만 `app.current_user_id`에 트랜잭션 로컬 값으로 설정합니다.
- PostgreSQL 정책은 앱 역할에도 `FORCE ROW LEVEL SECURITY`로 적용됩니다.
- AI 서버는 DB 자격 증명을 갖지 않고 내부 공유 비밀 헤더가 있어야 호출할 수 있습니다.
- 외부 입력의 프롬프트 명령은 데이터로 취급하며 AI 출력은 엄격한 JSON 계약으로 검증합니다.

## 핵심 데이터 흐름

### 자유 대화

사용자와 AI 메시지는 `conversations`, `conversation_messages`에 저장됩니다. 사용자 메시지는 먼저 저장되어 화면에 즉시 표시되고, `chat_reply_job_queue`의 워커가 답변을 생성합니다. 공고가 없어도 대화할 수 있으며 AI가 실패해도 사용자 메시지는 보존되고 해당 답변 작업을 재시도할 수 있습니다.

### 커리어 저장소

1. 사용자가 이력서·프로젝트 설명·경력 자료의 원문을 등록합니다.
2. `career_source_queue`에 파편화 작업을 넣고 즉시 응답합니다.
3. AI가 기술·프로젝트·경력·교육·자격·성과·링크 조각을 제안합니다.
4. 제안은 `SUGGESTED` 상태로 보관되며 사용자가 수정·선택한 조각만 `CONFIRMED`가 됩니다.
5. 확정된 조각만 이후 대화와 공고 분석의 사용자 근거로 전달됩니다.

조각은 검색·정렬·수정·병합·보관·복원·삭제할 수 있고, 원본 자료 분석 실패는 최대 횟수 안에서 재시도할 수 있습니다.

### 공고 분석

1. 공고 원문과 대화 연결을 저장합니다.
2. `analysis_job_queue`에 작업을 넣고 즉시 응답합니다.
3. 워커가 권한 제한 함수로 작업 하나를 점유합니다.
4. 해당 사용자의 RLS 문맥에서 표준 역량과 확정된 커리어 조각을 읽습니다.
5. AI가 먼저 결과를 크게 바꾸는 모호함이 있는지만 작은 구조화 응답으로 판단합니다.
6. 확인이 필요하면 질문 하나를 저장하고 큐에서 작업을 제거합니다. 사용자가 답하면 같은 작업을 다시 큐에 넣습니다.
7. 질문이 없거나 답변으로 해소되면 AI가 표준 역량, 공고 조건, 회사 맞춤 프로젝트 자료를 반환합니다.
8. 서버가 역량을 `canonicalKey + 범위 + 수준`으로 정규화하고, 검증된 필수 역량 충족률과 경력 조건으로 지원 판단을 확정합니다.
9. 검증 가능한 역량은 공용 `competency_catalog`에 축적하고 사용자 진행 상태는 `user_competencies`에 분리합니다. 공고 원문은 비공개로 유지하고 회사·직무·경력·정규화된 요구 역량만 추천 카탈로그에 게시합니다.
10. 승인하면 공고를 목표 목록에 추가하고 서버가 새 로드맵 초안을 계산합니다. 현재 공개 로드맵은 아직 유지됩니다.
11. 사용자가 로드맵 화면에서 변경점을 확인하고 적용하면 새 버전이 공개됩니다.

작업은 `QUEUED → RUNNING → WAITING_FOR_INPUT → QUEUED` 흐름을 최대 세 번 반복할 수 있고, 최종적으로 `SUCCEEDED | FAILED`가 됩니다. 질문은 한 번에 하나만 제공하며 답변 이력을 저장해 같은 질문을 반복하지 않습니다. 실패 작업은 최대 횟수 안에서 재시도할 수 있습니다.

### 로드맵 생성

1. 활성 목표 공고들의 검증 가능한 필수·우대·업무 역량을 서버가 읽습니다.
2. 분석 결과의 `primaryTrack`과 구조화된 경력 조건으로 공고를 주 직무와 경력
   단계에 배치합니다.
3. 같은 표준 역량은 회사 수와 필수·우대 차이에 관계없이 하나의 노드로 합치고,
   공고별 관계만 별도 메타데이터로 유지합니다.
4. 경력 제한이 없는 같은 직무의 회사들은 같은 단계에 나란히 배치합니다.
5. 신입 기회 뒤에는 `관련 직무 취업` 합류점을 두고, 경력직 공고가 요구하는
   최소 개월 수를 경력 관문으로 연결합니다.
6. 경력직 공고에만 필요한 기술은 해당 경력 관문 뒤에 배치합니다.
7. 각 회사의 기술 준비 뒤에는 도메인과 필수·우대 사항을 반영한 회사 맞춤
   프로젝트와 지원 기회를 둡니다.
8. 초안의 추가·유지·제거 항목을 미리 보여준 뒤 사용자가 적용해야 공개 버전으로
   승격합니다.

로드맵 배치가 바뀌어도 진행 상태는 `user_competencies`의 표준 역량에 남습니다. 예를 들어 A사의 Kafka 분기를 완료한 뒤 Redis를 요구하는 B사를 추가하면, 최신 초안에서 Kafka는 완료 상태를 유지하고 Redis만 새 미완료 분기로 나타납니다.

책임감·몰입도·원활한 소통처럼 객관적 완료 기준이 없는 조건은 분석 결과에만
보존하고 로드맵과 준비도에서는 제외합니다. 코드 리뷰 기록, 테스트 결과, 기술
문서처럼 산출물로 확인 가능한 실천은 포함합니다. `COMMON`은 가입 시 제공되는
프로그래밍 기초·Git/터미널·CS 기초에만 사용합니다. 표준 역량의 기술 분류와 화면
경로 배치는 별개입니다. 예를 들어 CI/CD의 분류는 `DEVOPS`로 유지하더라도 백엔드
공고가 요구했다면 통합 로드맵에서는 `BACKEND` 섹션에 놓습니다. 이후 DevOps
공고에서도 같은 표준 역량을 재사용할 수 있으며 완료 상태도 공유됩니다.

### 역량 검증과 프로젝트 증빙

- 가입 시 제공되는 프로그래밍·Git/터미널·CS 기초는 사용자가 자기 확인합니다.
- 일반 기술 노드는 사용자가 시작할 때 개인 검증 세션을 만듭니다. 공용 역량의 같은 평가 기준을 사용하되 목표 회사·직무·도메인에 맞춘 문제를 냅니다.
- 최소 `개념`, `코드 판단`, `상황 적용`을 포함한 3문항을 평가하고 부족하면 최대 5문항까지 후속 질문을 냅니다.
- 백엔드는 평균 75점 이상, 개별 문항 60점 이상, 세 필수 문제 유형 충족을 모두 확인해야 요구 수준을 인증합니다.
- 인증 수준은 사용자 역량에 남아 다른 공고에서도 재사용되며 더 높은 수준을 요구하는 공고에서는 추가 검증합니다.
- Git 저장소·배포 URL·문서는 기술마다 받지 않고 회사 맞춤 프로젝트, 자격, 실제 경험처럼 결과물 증거가 필요한 노드에서만 받습니다.
- 프로젝트 증빙은 `evidence_verification_queue`에서 비동기로 처리합니다. 링크 내용은 실제로 읽었다고 가정하지 않고 사용자가 함께 제출한 설명만 평가합니다.

### 실제 대체 공고

분석 완료 공고의 원문과 사용자 소유권은 공개하지 않습니다. 정규화된 회사·직무·경력 조건과 공용 역량 연결만 `posting_catalog`에 저장합니다. 추천은 같은 주 직무의 실제 카탈로그 공고를 대상으로 필수 역량 충족률 70%, 우대 역량 20%, 경력 조건 10%를 계산합니다. AI가 존재하지 않는 공고를 생성하거나 후보 순위를 결정하지 않습니다.

## 로드맵 불변 조건

- AI는 로드맵 구조를 직접 생성하지 않고 역량·조건·프로젝트 자료만 제안합니다.
- 표준 역량 정체성은 이름만이 아니라 `canonicalKey + level + 정규화된 scopeDefinition`입니다.
- 공고별 필수·우대·업무 조건은 최신 분석 결과로 교체됩니다.
- 공개 버전은 사용자마다 하나이며 초안을 적용할 때 이전 공개 버전은 보관됩니다.
- 새 초안을 만들거나 적용해도 표준 역량과 완료 상태는 삭제하거나 초기화하지 않습니다.
- 우대 조건은 준비도에 표시하되 지원 기회 잠금을 해제하는 필수 조건으로 사용하지 않습니다.
- 회사 맞춤 프로젝트는 기술 역량과 별개의 결과물 노드이며 해당 공고의 지원 기회 바로 앞에 위치합니다.
- 같은 표준 역량은 통합 로드맵에서 한 번만 나타나며 공고별 필수·우대 관계를
  노드 메타데이터로 보존합니다.
- 경력직 기회는 같은 직무의 관련 취업 합류점과 최소 경력 관문 뒤에 위치합니다.
- 회사 자체를 경력 전제조건으로 사용하지 않으며 실제 관련 직무 경력을 조건으로
  사용합니다.

## 보안과 운영

- PostgreSQL 마이그레이션 역할과 앱 역할을 분리합니다.
- 로그인은 IP+이메일, 가입은 IP 기준으로 제한합니다.
- AI 사용량은 DB에 사용자별 시간 단위로 기록해 서버가 여러 대여도 동일하게 제한합니다.
- 대화 답변, 공고 분석, 커리어 파편화, 증빙 검증, 역량 검증은 서로 구분된 사용량 한도를 가집니다.
- 운영 프로필은 강한 JWT/AI 비밀값, Secure 쿠키와 명시적 비로컬 CORS 도메인이 없으면 기동하지 않습니다.
- 각 HTTP 응답은 `X-Request-ID`를 반환하고 로그에도 같은 ID를 남깁니다.
- 헬스체크는 API 프로세스뿐 아니라 DB 연결도 확인합니다.
