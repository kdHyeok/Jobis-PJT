## 1. DB — 마이그레이션 7개

### V20 `chat_reply_agent_events` (신규 테이블)

대화 한 턴의 **에이전트 진행 타임라인**. `chat_reply_jobs.stage`/`stage_message` 는 한 칸이라
덮어쓰면 마지막 단계만 남는다 — 대화창이 담당별 말풍선을 순서대로 그리려면 순서가 남아야 한다.
공고 분석 쪽 `analysis_agent_events` 와 같은 구조다.

- `(chat_reply_job_id, sequence)` 유니크, `sequence`는 1~10000
- RLS `ENABLE` + `FORCE`, 소유자 정책
- **진행 기록 실패는 대화를 죽이지 않는다** — 워커가 로그만 남기고 넘어간다

### V21 · V25 좀비 작업 회수 (`claim_analysis_job` 교체)

워커나 서버가 실행 도중 죽으면 분석 작업이 `RUNNING` 인 채로 남고, 락이 만료돼도 **아무도 다시
집지 않았다.** 게다가 `findActiveAnalysis` 가 그 좀비를 "진행 중"으로 보고 새 요청을 붙여서, 같은
공고로 재시도하면 영원히 "분석 중"이 됐다(실측 08-04: 좀비 5건).

- V21: 락 만료된 `RUNNING` 도 회수 대상에 넣는다
- V25: 재시도 상한(3회)까지 쓴 좀비는 `FAILED` 로 닫는다 — 재시도도 회수도 못 하는 채로 화면에
  "분석 중"으로 남는 것보다 실패를 실패라고 말하는 편이 정직하다

### V22 `user_goal_profiles` 칼럼 추가

```sql
ADD COLUMN chat_preferences jsonb,
ADD COLUMN chat_facts       jsonb;
```

대화로 수집한 선호·지속 사실이 지금까지 `sessions.sqlite3` 에만 있었다 — 세션이 지워지면 사라졌다.

### V23 에이전트 자산의 집 (신규 테이블 6 + 칼럼 3) ★ 가장 큰 변경

| 테이블 | 담는 것 |
|---|---|
| `ai_user_profiles` | 사용자 프로필(사용자당 1행, upsert) |
| `posting_recommendations` | 추천 공고 묶음(append) |
| `coverletter_drafts` | 자소서 초안(append) |
| `interview_sessions` | 면접 진행 상태(대화당 1행, upsert) |
| `application_plans` | 지원 계획(append) |
| **`agent_session_state`** | **세션 자산 전체 블롭 — 진실의 출처(D152)** |

칼럼 추가: `analysis_jobs.engine_result jsonb`,
`user_goal_profiles.preparation_period_weeks`·`available_hours_per_week`.

전부 RLS `ENABLE`+`FORCE`, `user_id = app_current_user_id()` 소유자 정책.

**`agent_session_state` 를 이해하는 것이 이 브랜치의 핵심이다.** 매 턴 응답의
`collected.outputs.sessionState` 로 세션 **전체**가 나가고, 백엔드가 그것을 통째로 upsert 했다가
다음 요청의 `career.sessionState` 로 되돌려 준다. 번역기가 없다 — AI 가 준 모양 그대로 담는다.
그래서 **AI 세션 파일을 지워도 대화가 이어진다.**

### V24 상태 카드의 빈 본문 허용

```sql
CHECK (char_length(content) <= 100000
       AND (kind = 'ANALYSIS_STATUS' OR char_length(content) >= 1))
```

상태 카드(`kind='ANALYSIS_STATUS'`)는 **의도적으로 본문이 없다** — 이 턴에 말하는 주체는
에이전트이고 그 행은 카드가 붙을 자리만 잡는다. 그런데 V2 의 `content >= 1` 제약이 그 insert 를
거부해 `complete()`/`fail()` 트랜잭션이 통째로 굴러떨어졌고, 분석 작업이 전부 FAILED → 지도 자동
생성까지 막혔다. **일반 메시지의 빈 본문은 여전히 막는다.**

### V26 AI 서버가 잠깐 사라진 턴을 되살린다 (08-04 오전)

지연을 받는 3인자 `requeue_chat_reply_job(uuid, uuid, integer)` 신설. 기존 2인자는 그대로 둔다
(사람이 누르는 재시도는 즉시가 맞다). 상세는 §2 `ChatReplyWorker`.

### 1-4. 롤백·운영 주의

- **적용은 Flyway 자동**(`spring.flyway.enabled=true`). 기동 로그에
  `Successfully applied ... now at version v26` 확인.
- **되돌리기**: 신규 테이블 7개는 아무도 참조하지 않으므로 `DROP TABLE` 로 떨어진다.
  V22·V23 의 추가 칼럼도 `DROP COLUMN` 가능(기존 코드가 읽지 않는다).
  V24 만 주의 — 되돌리면 상태 카드 insert 가 다시 깨진다.
- **함수 교체(V21·V25·V26)는 `CREATE OR REPLACE`** 라 이전 정의를 다시 실행하면 원복된다.
- 개발 DB 는 도커 컨테이너 `jobiss-pg` **:5436** 이다(문서의 옛 55432 아님).
  `application.yml` 기본값이 아직 55432 라 **`DB_URL` 을 넘겨야 한다**:
  `DB_URL=jdbc:postgresql://localhost:5436/jobiss`.

## 2. 백엔드

### `conversation/ChatReplyWorker.java` — 가장 많이 바뀐 파일 (+606줄)

1. **진행 단계 기록**(`recordChatProgress`) — AI 스트림의 각 단계를 `chat_reply_agent_events`
   에 순서대로 적는다. 실패해도 대화를 죽이지 않는다(창문이지 대화가 아니다).
2. **대화가 확보한 자산 적재**(`ingestCollected`) — 채팅에 붙인 공고 URL 을 AI 가 수집·파싱해도
   그 사실이 우리 쪽으로 돌아오지 않아 채용공고 페이지에도 커리어지도에도 안 나타났다. 이제
   공고는 첨부 경로와 **같은** `JobPostingService.create` 를 부른다(중복 지문·사용량 제한·분석
   큐잉이 전부 그 안에 있다).
3. **산출물 적재**(`ingestOutputs`) — 판정·로드맵·초안·면접·세션 블롭을 §1 의 테이블에.
   각 항목은 **그 턴에 만들어졌을 때만** 온다(매 턴 전량이면 append 테이블에 같은 행이 쌓인다).
4. **적재 실패가 대화를 죽이지 않는다** — 답변은 이미 저장돼 있고 경고만 남긴다.
5. **전송 실패 재시도(08-04 오전, D164)** — `ResourceAccessException`(AI 서버에 못 닿음)이면
   최종 실패로 닫지 않고 15초 뒤 재시도로 되돌린다. 큐가 원래 3회를 허용하는데
   (`attempt_count < 3`) 워커가 그 예산을 한 번도 쓰지 않고 있었다. AI 가 스스로 낸 오류
   (`AiServiceException`)는 되돌리지 않는다 — 다시 걸어도 같은 답이고 매번 LLM 비용을 쓴다.

### `conversation/ChatReplyJobService.java`

조회 응답에 `progressSteps` 추가(저장된 이벤트를 `jsonb_agg`). **AI 가 만든 화자 키·문구를
백엔드가 다시 해석하지 않는다** — 그대로 통과시킨다(분석 작업의 `progressEvents` 와 같은 규약).

### `conversation/ConversationService.java`

- 공고 첨부도 답변 작업을 만든다(전에는 첨부가 AI 대화를 타지 않았다)
- **백엔드가 대화 문구를 쓰지 않는다**(D149) — 말은 에이전트가 한다

### `analysis/AnalysisWorker.java` · `roadmap/RoadmapService.java`

- 적합도 분석 뒤 **커리어지도를 자동 생성**(D146). 재료가 없으면 시도 자체를 막는다
- 대화가 만든 지도 재료는 기존 **공유 분석 재사용 경로**로 적재한다(D147) — 적재 SQL 을 복제하지
  않는다. writer 가 둘이 되면 두 경로의 지도가 갈린다
- 트랙 없는 공고도 지도에 오른다(D155)

### `career/repository/DocumentText.java` (신설)

업로드 파일(base64) → 텍스트. **새 의존성 없음** — docx 는 ZIP 안의 `word/document.xml` 이라
표준 `java.util.zip` 으로 푼다(Apache POI 를 들이지 않았다). 형식은 **파일명 확장자**로 가른다
(브라우저 MIME 은 docx 를 `application/octet-stream` 으로 준다). 실패는 400 `INVALID_FILE`.

### `analysis/AiAnalysisClient.java`

`/v1/chat/stream`(NDJSON) 을 먼저 시도하고 404/405 면 단건 `/v1/chat` 으로 폴백. 스트림이 아닌
본문이 와도 대화가 깨지지 않는다 — **스트림은 편의이고 대화는 기능이다.**

## 4. AI ↔ 백엔드 계약 (`analysis/AiContracts.java`, +173줄)

요청 `career` 가 넓어졌다 — AI 가 세션 파일 없이도 대화를 이어가게 하는 재료다:

```
+ List<StoredResume>  resumes       (id, title, sourceType, rawText, createdAt)
+ List<StoredPosting> postings      (id, sourceType, sourceUrl, rawText, parsedData, createdAt)
+ JsonNode            preferences   + List<String> facts
+ JsonNode            sessionState  ← agent_session_state.state 블롭 (진실의 출처)
+ JsonNode            interview
```

응답에 `collected` 가 생겼다 — 이 턴에 확보한 것을 우리 테이블로 되돌리는 통로다:

```
collected.posting / collected.resume / collected.preferences / collected.facts
collected.outputs = { analysis, roadmap, judgmentSummary, profile, recommendations,
                      coverletter, interview, applicationPlan,
                      preparationPeriodWeeks, availableHoursPerWeek,
                      competencyProposal, jobContext, sessionState }
```

그 밖에 `progress`(진행 단계), `replySources`(담당별 발화), `degradedReason`(폴백 사유).
**폴백은 이유를 삼키지 않는다** — 기본 문구가 나온 이유가 응답에 남는다.

   `orchestrator/attachment_kind.py:_heuristic` 의 신호 어휘가 서술체("~했습니다")를 노려서,
