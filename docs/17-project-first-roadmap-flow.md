# 프로젝트 중심 로드맵 생성 흐름

작성일: 2026-08-05

## 결정

공고 문장을 기술 노드로 바로 바꾸지 않는다. 사용자가 선택한 직무에 맞는 회사 특화 프로젝트를
먼저 만들고, 프로젝트의 구체적인 과제가 요구하는 승인 원자 역량을 Capability Graph에서 찾는다.
그래프의 선수 관계를 확장해 준비 경로를 만든 뒤에만 사용자별 이력과 검증 상태를 진행 상태로
덧씌운다.

## 실행 순서

1. 확인된 공고 원문을 직무별로 구조화한다.
2. 서로 다른 직무가 둘 이상이면 하나를 임의로 고르지 않고 사용자에게 선택을 요청한다.
3. 선택된 직무의 업무·필수·우대·도메인을 결합해 회사 특화 프로젝트 한 건과 수행 과제를 만든다.
4. 각 과제가 실제로 입증하는 승인 원자 역량만 선택한다.
5. 선택한 원자 역량에서 Capability Graph의 승인된 선수 관계를 역방향으로 확장한다.
6. 경력·자격은 학습 노드가 아니라 별도 관문으로 유지한다.
7. 사용자 역량 ID와 검증 근거를 마지막에 대조해 `CLAIMED`, `EVIDENCED`, `VERIFIED`를 표시한다.
8. 결과는 초안이며 사용자가 적용하기 전에는 커리어 지도를 변경하지 않는다.

## 제거한 중복 호출

- 공고의 모든 요건과 전체 역량 사전을 다시 LLM에 보내던 선행 정규화 호출을 제거했다.
- 프로젝트 과제가 확정한 `requirementId ↔ canonicalKey` 연결을 결정적으로 컴파일한다.
- 같은 연결을 적합도 단계에서 다시 추론하지 않고 사용자 역량 ID로 결정적으로 대조한다.
- 통합 분석의 주요 LLM 호출은 공고 구조화와 회사 특화 프로젝트 설계로 제한한다.

## 직무와 사용자 상태 경계

- `웹 개발자`처럼 넓은 제목을 근거 없이 풀스택으로 확정하지 않는다.
- 프론트엔드와 백엔드 모집 근거가 함께 있으면 확인 화면에 두 경로를 보존한다.
- 사용자 이력은 프로젝트 내용이나 공개 선수 관계를 바꿀 수 없다.
- 사용자 이력은 자신의 노드 진행 상태에만 영향을 준다.
- 확인되지 않은 경력·자격·역량은 완료로 추정하지 않는다.

## 실측

- 현재 Capability Graph: 승인 원자 역량 69개.
- Sonnet 프로젝트 설계 실측: 약 66초, 회사 프로젝트 1건과 과제 8건 생성.
- 이스트게임즈 통합 웹 공고 구조화 실측: 프론트엔드와 백엔드 2개 포지션 보존.
- Haiku 구조화는 약 113초 뒤 경력 계약을 위반해 기본 모델로 채택하지 않았다.
- Claude CLI는 프로세스 시작과 큰 JSON Schema 처리 비용이 있어 일반 웹 API보다 느리다.

## 알려진 후속 과제

- 공고 구조화의 p50/p95를 여러 공고로 측정하고, 검증된 구조화 체크포인트를 재사용한다.
- 자유 서술형 커리어 조각을 원자 역량으로 연결할 때는 사용자 확인이 있는 이관 후보를 만든다.
- Capability Graph에 없는 직무·기술은 비슷한 역량으로 강제 연결하지 않고 검토 대상으로 남긴다.
