# 00. 현재 시스템 기준선

- 기준일: 2026-08-04
- 기준 폴더: `C:\jobiss-service-real-agent-lab`
- 목적: 기존 팀 작업을 보존하고 새 구현에서 기능을 빠뜨리지 않기 위한 기준선
- 상태: 읽기 전용 분석 완료

## 1. 시스템의 실제 계층

현재 서비스는 하나의 AI가 아니라 다음 네 계층이 합쳐진 결과다.

```text
사용자 입력(URL·이미지·원문·대화)
  → 공고 수집 계층(Jina·HTML·iframe·VLM/OCR)
  → AI팀 코어(플래너·에이전트·분석 그래프·세션)
  → v2bridge(서비스 JSON 변환·직무/기술/로드맵 재분류)
  → Spring 백엔드(저장·RLS·큐·판정·로드맵 버전)
  → Vue 프론트엔드(대화·공고·진행 상태·미리보기)
```

AI Python 소스는 현재 93개 파일이고, 테스트 소스는 50개다. 주요 영역은 다음과 같다.

- `agents`: 에이전트 역할과 실행 구현
- `orchestrator`: 의도 분류, 실행 계획, 관찰, 세션 갱신
- `graph`: 공고 파싱, 프로필 조립, 적합도 계산 그래프
- `feat_url`: URL·HTML·이미지 공고 수집
- `contracts`: 공고·이력서·적합도 도메인 모델
- `eval`: 플래너·일관성 평가 하네스
- `v2bridge`: 실제 AI와 JOBIS 서비스 계약 사이의 변환
- `webbridge`, `prototype`: 과거 또는 별도 연결 경로

현재 결과는 AI팀 코어의 출력만이 아니다. 특히 `v2bridge`가 코어 결과를 JOBIS의
역량·로드맵 모델로 다시 분류하므로, 같은 의미를 두 계층이 서로 다르게 해석할 수 있다.

## 2. 유지해야 할 현재 기능

### 대화와 오케스트레이션

- 자유 대화와 의도 자동 분류
- 공고 분석, 적합도 분석, 이력서 진단, 추천 등 필요한 에이전트 선택
- 전제조건이 없는 에이전트 실행 차단
- 실행 후 남은 계획 재검토
- 사용자 동의가 필요한 무거운 작업 구분
- 사용자 사실과 세션 자산 누적
- 실제 실행 trace와 경고 수집

### 공고 수집

- URL 원문 수집
- 일반 HTML과 iframe 대응
- 이미지형 공고 VLM 처리
- 긴 이미지 타일 분할
- 붙여넣기 원문 처리
- 수집 실패 경고와 대체 입력 안내

### 분석

- 공고의 직무·경력·필수·우대요건 구조화
- 사용자의 이력서·확정된 커리어 자료와 비교
- 정보 없음과 미충족 구분
- 추가 질문 후 같은 분석 재개
- 분석 결과의 구조화 검증과 일부 복구
- 동일 입력 분석 재사용 기반

### 서비스 통합

- Spring이 사용자 데이터와 RLS의 정본 역할
- 사용자 메시지를 먼저 저장하고 AI 실패 시에도 보존
- 백그라운드 분석 큐와 재시도
- 실제 AI trace를 NDJSON 진행 이벤트로 전달
- AI 제안을 저장한 뒤 사용자의 승인으로 실행
- 로드맵 초안과 공개 버전 분리
- 공용 공고 카탈로그와 사용자별 평가 분리
- 운영자 중복 검토와 되돌리기 기반

### 역량 학습과 검증

- 공용 역량 정의와 사용자별 진행 상태 분리
- 개념·코드·상황 적용 문제
- 회사 맥락을 활용한 문제 개인화
- 현재 기술 범위와 미래 확장 문제 분리 원칙
- 재도전, 통과 항목 이월, 이의제기 기반
- 저장소·결과물 증거를 필요한 노드에서만 요구

## 3. 팀 AI의 핵심 설계 철학

AI팀의 `AGENTS.md`는 다음 세 계층을 명시한다.

1. 읽기: LLM이 비정형 정보를 정형 필드로 추출한다.
2. 판단: 결정론적 코드가 매칭·계산·검색·검증·분기를 수행한다.
3. 말하기: LLM이 정형 결정을 자연어로 표현한다.

이 구조는 다음 문제를 방지하려는 시도였다.

- 같은 입력의 결과가 매번 바뀌는 문제
- LLM이 없는 사실이나 근거를 만드는 문제
- 표현을 고치다가 계산 결과가 바뀌는 문제
- 에이전트가 임의로 세션을 변경하는 문제
- 모르는 정보를 미충족으로 단정하는 문제

이 철학은 계산·권한·저장·무결성 영역에서는 유지해야 한다. 그러나 직무·경력·복합
요건 해석처럼 문맥에 따라 달라지는 의미 판단까지 폐쇄형 규칙이 최종 결정하면 실제
공고를 왜곡한다.

## 4. 확인된 구조적 문제

### 4.1 단일 포지션 계약

현재 `NormalizedJobPosting`은 공고당 하나의 `roleCategory`, 하나의 경력 범위와
평평한 요구사항 목록을 가진다. 여러 직무가 서로 다른 경력과 요건을 가진 공고를
손실 없이 표현할 수 없다.

### 4.2 직무의 키워드 확정

코어는 제목 별칭과 본문 빈도로 직무를 선택한다. `v2bridge`는 구조화 결과가 나오기
전에 전체 원문에서 프론트엔드·백엔드 등의 표시를 찾는다. 그 결과 다음 문장도 복수
채용으로 오인할 수 있다.

```text
백엔드 개발자를 모집합니다. 프론트엔드 개발자와 협업합니다.
```

### 4.3 경력 숫자 오인

숫자 경력 표현을 신입 표현보다 먼저 채택할 수 있다. OCR이 잘못 읽은 `19년`, 회사
업력, 팀원의 경력, 서비스 운영 연수 등이 요구 경력으로 전달될 수 있다.

### 4.4 추출 텍스트를 원본 근거로 간주

현재 경력 근거 문자열이 추출 텍스트에 존재하는지는 확인하지만, 추출 텍스트 자체가
원본 이미지와 같은지는 검증하지 않는다. OCR/VLM 오류가 자기 자신을 근거로 통과한다.

### 4.5 중복 taxonomy

코어와 `v2bridge`가 각각 직무와 기술 taxonomy를 가진다. 한 계층의 올바른 판정이 다음
계층에서 다시 바뀔 수 있고, 규칙의 최종 소유자가 불명확하다.

### 4.6 공고 요건과 학습 노드의 직접 연결

복합 공고 문장을 기술·업무·도메인 등으로 휴리스틱 분류하고 바로 로드맵 후보로 바꾼다.
따라서 기술과 정성적 표현이 한 노드 이름에 섞이거나, 회사 업무가 학습 기술처럼 나타날
수 있다.

### 4.7 적합도와 검증 완료의 혼합

이력서에 기술 이름이 있으면 근거가 약해도 충족으로 볼 수 있다. JOBIS가 요구하는
사용자 주장, 이력서 근거, 실제 검증 완료를 하나의 상태로 표현하기에는 부족하다.

### 4.8 테스트의 의미 정확성 공백

현재 테스트는 실행 순서, 계약, 결정론적 재현성을 잘 검증한다. 하지만 다음과 같은 실제
공고 문맥의 부정 사례와 이미지 의미 정확성은 충분히 고정하지 못했다.

- 협업 대상 언급과 모집 직무 구분
- 업력·서비스 운영 연수와 요구 경력 구분
- 복수 직무별 경력과 요건
- OCR 분할 중복과 오인식
- 사전에 없는 신규 기술
- 정성적 요건과 학습 가능한 역량 구분

## 5. 현재 기준선의 강점과 한계

### 강점

- 에이전트 실행 기반이 체계적이다.
- 계약과 상태를 구조화하려는 원칙이 강하다.
- 권한과 저장을 AI에서 분리했다.
- 오류와 경고를 관찰할 수 있다.
- 실제 서비스에 필요한 RLS, 큐, 버전, 운영자 흐름이 존재한다.
- 팀이 실패와 측정 결과를 문서에 기록했다.

### 한계

- 결정론을 의미 정확성보다 우선한 구간이 있다.
- 여러 실제 직무를 표현하기 전에 하나로 압축한다.
- 수집 결과의 사용자 확인이 채팅 자동 분석 경로에서는 빠진다.
- 새 서비스 계약에 맞추기 위해 만든 변환 계층이 두 번째 판정 엔진이 됐다.
- 테스트가 현재 구현을 안정화하지만 실제 공고의 정답성을 충분히 보장하지 않는다.

## 6. 기준선 보존 규칙

- `C:\jobiss-service-real-agent-lab`은 새 v3 구현 중 직접 수정하지 않는다.
- 기존 실행 결과와 trace는 비교 자료로만 사용한다.
- 기존 테스트 기대값을 새 구현에 그대로 복사하지 않는다.
- 기존 결과가 정확한 사례와 잘못된 사례를 구분해 기록한다.
- 재사용할 모듈은 공개 입력·출력과 부작용을 확인한 뒤 가져온다.
- 새 버전이 통합 수용 기준을 통과할 때까지 기존 버전을 삭제하지 않는다.
