# JOBIS 페이지별 UI·UX 리뷰

## 문서 목적

실제 사용자 여정을 따라 페이지를 하나씩 확인하고 다음 관점의 문제와 개선 우선순위를
기록한다.

- 첫 방문 사용자와 재방문 사용자
- 제품 가치와 기능 전달
- UI 완성도와 시각적 일관성
- 반응형과 접근성
- 오류·빈 상태·권한 등 예외 상황
- 실제 백엔드·AI 기능과 화면 설명의 일치 여부
- 공개 서비스 출시 준비도

리뷰는 별도의 수정 허락이 없는 한 코드 변경 없이 진행한다.

## 리뷰 순서

1. 랜딩
2. 로그인·회원가입
3. 홈
4. 대화
5. 커리어 저장소
6. 커리어 자료 검토
7. 채용 공고 목록
8. 새 공고 분석
9. 채용 공고 상세
10. 커리어 지도
11. 활동 내역
12. 설정
13. 운영 검토함

## 1. 랜딩 페이지

- 경로: `/`
- 구현: `frontend/src/views/LandingView.vue`
- 스타일: `frontend/src/styles/base.css`의 `Landing` 영역
- 확인 화면: 데스크톱 1280×720, 모바일 390×844
- 확인 결과: 두 화면 모두 가로 오버플로 없음

### 종합 평가

첫인상과 시각적 완성도는 좋지만, 제품을 이해시키는 랜딩 페이지보다는 잘 만든 서비스
표지에 가깝다. 핵심 가치 문장은 명확하지만 JOBIS에서 실제로 얻게 되는 커리어 지도의
모습과 작동 과정이 보이지 않는다.

### 잘된 점

- `공고마다 다시 시작하지 않는 나만의 커리어 지도`가 서비스의 차별점을 정확히 전달한다.
- 초록·주황·노랑 색상과 눌리는 버튼 효과가 앱 내부 디자인 시스템과 일관된다.
- `대화 → 누적 지도 → 증거 검증` 설명이 실제 서비스 기능과 일치한다.
- 정보량이 과하지 않고 주요 CTA가 분명하다.
- `main`, `header`, `section`, `article`, `h1`, `h2` 등 시맨틱 구조가 적절하다.
- 키보드 포커스 표시가 있으며 모바일 주요 버튼 높이가 50px라 조작하기 좋다.
- 한국어 문서 설정과 기본 description 메타 태그가 존재한다.

### 주요 문제

#### P0. 실제 제품 결과가 보이지 않음

커리어 지도는 일반 사용자에게 익숙하지 않은 개념이지만 현재는 문장으로만 설명한다.
사용자는 다음 내용을 직접 상상해야 한다.

- 공고를 넣으면 무엇이 생성되는가
- 여러 회사가 어떻게 하나의 지도로 합쳐지는가
- 완료한 기술은 어떻게 표시되는가
- 회사별 필수·우대사항은 어떻게 구분되는가

실제 커리어 지도 축소 미리보기, `공고 입력 → 기술 추출 → 지도 분기` 애니메이션,
두 회사의 요구사항이 하나로 합쳐지는 예시 중 하나가 필요하다.

#### P0. 모바일 제목 줄바꿈이 깨짐

390px 화면에서 제목 마지막 글자 `도`가 한 줄을 단독으로 차지한다. 보조 CTA인
`어떻게 작동하나요?`도 두 줄로 갈라진다. 강제 `<br>`, 큰 글꼴과 강한 음수 자간의
조합을 모바일 구간에서 다시 조정해야 한다.

#### P1. 작동 방식 CTA의 기대와 결과가 다름

`어떻게 작동하나요?`는 자세한 흐름이나 데모를 기대하게 하지만, 실제로는 이미 일부
보이는 카드 세 개로만 이동한다. 다음과 같은 실제 흐름 설명이 필요하다.

1. 공고 URL 입력
2. AI가 필수·우대 역량 분리
3. 기존 커리어 자료와 비교
4. 하나의 누적 지도에 반영
5. 학습·검증 후 단계 완료

#### P1. 신뢰 정보 부족

이력서, 프로젝트 경험, GitHub·GitLab 저장소, 지원 대상 회사와 AI 역량 판단을 다루지만
다음 정보가 공개 화면에 없다.

- 자료 저장·삭제 방식
- 저장소 연결이 읽기 전용인지 여부
- AI 판단을 사용자가 검토할 수 있는지 여부
- 개인정보처리방침과 이용약관
- 문의 경로

#### P1. 핵심 사용자가 선명하지 않음

취업 준비 서비스인 것은 알 수 있지만 개발자 중심인지, 신입과 경력자가 모두 사용할 수
있는지, 공고가 없는 사람도 시작할 수 있는지가 한 문장으로 정리되지 않았다. 대표 사용자
사례를 추가하면 이해가 빨라진다.

예: `백엔드 취업을 준비하는 신입 개발자가 여러 회사의 요구사항을 하나의 성장 경로로 관리합니다.`

#### P2. 로그인 사용자의 CTA가 동일함

로그인 사용자가 `/`에 접근해도 `시작하기`가 표시된다. 클릭하면 라우터가 홈으로 보내므로
기능은 동작하지만 `내 커리어 지도 계속하기` 또는 `대시보드로 이동`이 더 자연스럽다.

#### P2. 공개 서비스 메타 정보 부족

- 파비콘 없음
- Open Graph 이미지·제목·설명 없음
- 공유 미리보기 없음
- 푸터와 약관 링크 없음
- 문서 제목이 `JOBIS`뿐이라 검색 결과에서 서비스 성격이 드러나지 않음
- 기능 카드 본문이 12px로 작아 긴 문장에는 불리함

### 권장 우선순위

1. 모바일 제목과 보조 CTA 줄바꿈 해결
2. 실제 커리어 지도 또는 서비스 결과 미리보기 추가
3. `어떻게 작동하나요?` 영역을 실제 5단계 흐름으로 확장
4. 개인정보·저장소 접근·AI 검토 정책 표시
5. 로그인 사용자의 CTA 변경
6. 파비콘·Open Graph·푸터·약관 보완

### 유지할 방향

현재 색상, 버튼 효과, 간결한 히어로 구성과 핵심 가치 문장은 유지할 가치가 있다. 전면
재디자인보다는 실제 제품을 보여주는 구간과 신뢰 구간을 추가하는 것이 우선이다.

## 2. 로그인·회원가입 페이지

- 경로: `/login`
- 구현: `frontend/src/views/LoginView.vue`
- 연관 기능: Spring Security 인증, HttpOnly 인증 쿠키, 회원가입 시 공통 기반 노드 생성
- 확인 화면: 데스크톱 1280×720, 모바일 390×844
- 확인 결과: 두 화면 모두 가로 오버플로는 없고 폼 입력과 모드 전환은 정상 동작함

### 종합 평가

시각적 완성도와 인증 구현의 기본기는 좋다. 데스크톱에서는 서비스 가치 설명과 인증 폼을
분리한 구성이 자연스럽고, 회원가입 직후 공통 기반 세 단계를 만드는 백엔드 동작도 화면의
안내와 일치한다. 다만 비밀번호 복구와 약관·개인정보 안내가 없어 실제 공개 서비스의 계정
진입점으로는 아직 부족하다. 현재 수준은 내부 테스트나 시연에는 적합하지만 출시 가능한
인증 화면으로 보기는 어렵다.

### 잘된 점

- 데스크톱의 좌측 스토리와 미니 로드맵이 로그인 전에도 JOBIS의 정체성을 전달한다.
- 로그인과 회원가입을 한 경로에서 전환하므로 사용자가 다른 페이지를 찾아다닐 필요가 없다.
- `form`, `label`, `required`, 이메일 입력 타입과 `autocomplete`가 적용되어 기본 접근성과
  브라우저 자동 완성 지원이 갖춰져 있다.
- 요청 중 버튼을 비활성화하고 `확인 중…`을 표시해 중복 제출을 줄인다.
- 세션 만료와 API 오류를 `role="alert"` 영역으로 알려 보조 기술에서도 오류를 인지할 수 있다.
- 백엔드는 BCrypt 비밀번호 해시, 일반화된 로그인 실패 메시지, 로그인·가입 속도 제한,
  HttpOnly·SameSite 쿠키와 CSRF 방어를 사용한다.
- 회원가입과 함께 프로그래밍 기초, Git·터미널, CS 기초 노드를 생성하므로 가입 후 빈 화면에
  도착하지 않는다.

### 주요 문제

#### P0. 비밀번호 복구 경로가 없음

비밀번호를 잊은 사용자가 계정을 되찾을 방법이 화면과 백엔드 모두에 없다. 실제 서비스에서
지원 문의나 새 계정 생성을 유발하는 출시 차단 문제다. 이메일 기반 재설정 요청, 만료되는
일회용 토큰, 새 비밀번호 설정 화면과 모든 기존 세션 무효화 흐름이 필요하다.

#### P0. 가입 동의와 개인정보 안내가 없음

JOBIS는 이력서, 프로젝트 경험, 저장소 정보와 지원 대상 공고를 다루지만 계정 생성 전에
이용약관과 개인정보처리방침을 확인할 수 없다. 최소한 필수 동의, 정책 링크, 수집 목적과
삭제 방법을 보여줘야 한다. 이메일 소유 확인도 없으므로 계정 오입력과 자동 가입 방지를 위한
인증 메일 도입 여부를 함께 결정해야 한다.

#### P1. 980px 이하에서 서비스 맥락과 이동 경로가 모두 사라짐

반응형 구간에서 `.login-story` 전체를 숨기므로 모바일뿐 아니라 태블릿에서도 JOBIS 로고,
핵심 가치, 미니 로드맵, 첫 로그인 안내와 홈으로 돌아가는 링크가 모두 사라진다. 390×844
화면에서는 인증 카드만 중앙에 있고 아래쪽에 큰 빈 공간이 남는다. 좌측 영역을 모두 숨기기보다
모바일용 로고·한 줄 가치 문장·홈 링크만 남기는 압축 헤더가 필요하다.

#### P1. 화면 문구가 사용자보다 개발 상태를 설명함

`목업 계정 없이 실제 사용자 데이터로 시작합니다.`는 구현 과정에서 의미가 있는 문장이지,
가입을 고민하는 사용자가 얻는 가치를 설명하지 않는다. `공고와 경험을 내 계정에 안전하게
저장하고 어디서든 이어보세요.`처럼 효용과 신뢰를 전달하는 문구가 더 적합하다.

#### P1. 회원가입의 비밀번호 경험이 부족함

12자 길이 제한은 있지만 비밀번호 확인, 표시·숨기기, Caps Lock 안내, 조건 충족 상태나 강도
피드백이 없다. 오타가 있어도 곧바로 계정이 만들어져 이후에는 복구 기능도 사용할 수 없다.
비밀번호 확인 필드와 표시 버튼을 우선 제공하고, 오류는 필드 가까이에 구체적으로 표시해야 한다.

#### P1. 로그인과 회원가입 전환 시 이전 오류가 남음

모드 전환 버튼은 `mode`만 변경한다. 만료 오류나 로그인 실패 오류가 표시된 상태에서 회원가입으로
전환하면 관계없는 오류가 그대로 남아 새 폼의 오류처럼 보인다. 모드 전환 시 오류를 지우고,
비밀번호처럼 민감한 값의 유지 여부도 명시적으로 정해야 한다.

#### P1. 가입 직후 생성되는 지도의 의미를 설명하지 않음

백엔드는 가입과 동시에 공통 기반 세 단계를 만들지만 화면에서는 좌측 가이드 한 문장만 제공하고,
980px 이하에서는 그 안내마저 사라진다. 가입 버튼 아래 또는 첫 진입 온보딩에서 `기초 세 단계가
준비되고, 공고를 분석할수록 지도가 확장된다`는 결과를 짧게 알려주는 편이 좋다.

#### P2. 보조 문구가 지나치게 작음

모바일 실측 기준 보조 설명과 라벨은 11px, 비밀번호 도움말은 9px이다. 높은 정보 밀도가 필요한
화면도 아닌 만큼 라벨과 도움말을 적어도 12~14px 범위로 올려야 장시간 사용과 저시력 접근성이
좋아진다.

#### P2. 로그인 후 이동 경로를 제한하지 않음

`redirect` 쿼리 문자열을 그대로 라우터에 전달한다. Vue Router가 외부 주소를 일반적인 브라우저
이동처럼 처리하지 않더라도 존재하지 않는 경로나 의도하지 않은 화면으로 보낼 수 있다. 허용된
내부 경로인지 검사하고, 유효하지 않으면 `/app`으로 보내는 방어가 필요하다.

### 권장 우선순위

1. 비밀번호 재설정과 계정 복구 흐름 추가
2. 이용약관·개인정보처리방침 링크와 가입 동의 제공
3. 모바일·태블릿용 브랜드 헤더와 홈 이동 경로 유지
4. 비밀번호 확인·표시 버튼·필드별 오류 피드백 보완
5. 개발자 관점 문구를 사용자 가치 문구로 교체하고 가입 결과 설명
6. 모드 전환 오류 초기화와 리다이렉트 경로 검증
7. 9~11px 보조 문구의 가독성 개선

### 유지할 방향

데스크톱 분할 구성, 색상과 눌리는 버튼 효과, 미니 로드맵, 한 화면 안의 로그인·회원가입 전환은
유지할 가치가 있다. 전면 재디자인보다 계정 복구와 신뢰 정보, 모바일에서 사라지는 서비스 맥락을
보완하는 것이 우선이다.

## 3. 홈 페이지

- 경로: `/app`
- 구현: `frontend/src/views/HomeView.vue`
- 공통 화면: `frontend/src/components/AppShell.vue`
- 연관 API: 커리어 그래프, 공고, 분석 작업, 커리어 자료, 알림
- 확인 방식: 화면 코드·반응형 스타일·라우터·API 계약 검토, 비로그인 접근 차단 확인
- 제한 사항: 검토용 브라우저에 로그인 세션이 없어 실제 사용자 데이터가 채워진 렌더링은 확인하지 못함

### 종합 평가

홈이 해야 할 정보 구조는 잘 잡혀 있다. 다음 단계, 전체 진행률, 백그라운드 작업, 빠른 시작과
최근 알림을 한 화면에 모아 로그인 직후 사용자가 무엇을 할지 찾기 쉽다. 고정 사이드바와 화면
내부 스크롤 구조도 이전에 문제였던 페이지 전체 스크롤을 해결하는 방향이다.

그러나 현재 홈은 실제 커리어 지도 화면과 다른 데이터 계약을 사용한다. 이 때문에 가장 중요한
`다음 단계`와 진행률이 지도에서 보이는 여정과 달라질 수 있고, `단계 열기`도 선택한 단계를
실제로 열지 못한다. 시각적 개선보다 홈과 로드맵의 기준을 하나로 통일하는 것이 먼저다.

### 잘된 점

- 인사말 아래에 다음 퀘스트를 가장 크게 배치해 홈의 우선 행동이 선명하다.
- AI 대화, 이력서 등록, 공고 분석, 지도 보기를 빠른 시작으로 제공해 주요 기능 접근이 쉽다.
- 분석 작업과 커리어 파편화를 `백그라운드에서 진행 중` 영역에 함께 표시한다.
- 추가 답변이 필요한 작업은 일반 실행 중 상태와 구분하여 해당 공고로 이동시킨다.
- 최근 알림과 전체 활동 내역을 연결해 백그라운드 결과를 다시 찾을 수 있다.
- 사이드바는 접은 상태를 브라우저에 기억하고, 계정 영역은 화면 아래에 고정된다.
- 820px 이하에서는 상단 헤더와 하단 내비게이션으로 전환되어 본문 폭을 확보한다.
- 인증되지 않은 `/app` 접근은 로그인 페이지로 이동시키고 원래 경로를 보존한다.
- 모든 API를 병렬로 요청하므로 정상 상황의 초기 로딩 시간을 줄이려는 방향은 적절하다.

### 주요 문제

#### P0. 홈과 커리어 지도 화면이 서로 다른 데이터를 사용함

홈은 `/api/career-map`의 원시 `CareerMap` 노드를 사용하지만 실제 커리어 지도 화면은
`/api/roadmap`의 `RoadmapWorkspace`를 사용한다. 로드맵에서는 공통 기반, 직무 구간, 프로젝트,
회사 기회가 다시 묶이고 초안 여부도 구분되므로 두 화면의 노드 ID, 제목, 순서와 상태가 같다고
볼 수 없다.

현재 홈의 다음 단계는 원시 노드를 `rank`로 정렬한 뒤 처음 만나는 미완료 노드를 고른다.
선행 조건, 잠금 상태, 필수·우대 여부, 현재 목표 회사, 선택한 직무 분기와 진행 중 상태를 고려하지
않아 여러 갈래가 생기면 사실상 임의의 노드를 추천할 수 있다. 진행률 역시 회사 기회와 완료할 수
없는 노드를 포함한 전체 노드 수를 분모로 사용하므로 사용자가 이해하는 학습 진척도와 달라질 수
있다.

홈 전용 요약 API 또는 `RoadmapWorkspace`를 기준으로 다음 항목을 서버에서 일관되게 계산해야 한다.

- 지금 실제로 열려 있는 필수 단계
- 현재 목표 공고와 가장 관련 있는 다음 단계
- 완료 가능한 역량 기준 진행률
- 필수·우대·보너스 진행률의 분리
- 적용된 지도와 아직 검토 중인 초안의 구분

#### P0. `단계 열기`가 선택한 단계를 열지 못함

홈은 `map?node={careerNodeId}`로 이동하지만 `CareerMapView`는 `node` 쿼리를 읽지 않고
`posting` 쿼리만 처리한다. 더구나 홈의 ID는 원시 커리어 노드 ID이고 지도 화면의 주 단위는
로드맵 노드다. 사용자는 `단계 열기`를 눌러 상세 과제나 검증 화면이 열릴 것으로 기대하지만 실제로는
지도 전체로만 이동한다.

홈과 지도 사이에 `roadmapNodeId` 또는 `careerNodeId + competencyId` 중 하나의 명확한 딥링크
계약을 정하고, 지도 진입 후 해당 노드를 중앙에 배치하고 상세 패널까지 열어야 한다.

#### P1. 진행률 원의 모양이 실제 비율과 관계없음

진행률 원은 숫자로 `완료/전체`를 보여주지만 CSS에서는 원의 위쪽 테두리만 항상 초록색이다.
0%, 30%, 100% 모두 같은 모양이어서 시각 정보가 숫자와 충돌한다. `conic-gradient` 또는 실제
progress 컴포넌트로 비율을 반영하고 `aria-valuenow`, `aria-valuemax`도 제공해야 한다.

#### P1. 한 API 실패가 홈 전체를 실패시킴

커리어 지도, 공고, 분석 작업, 커리어 자료, 알림 중 하나만 실패해도 `Promise.all` 전체가 예외로
끝난다. 그 뒤 화면은 오류를 표시하면서 동시에 `첫 성장 경로를 만들어 보세요`, `0/0` 같은 빈
상태를 보여 실제로 데이터가 없는 것처럼 오해시킨다.

핵심 영역과 보조 영역을 나누고 `Promise.allSettled` 또는 개별 상태를 사용해 다음 단계와 진행률은
살리되 실패한 최근 알림만 재시도할 수 있게 해야 한다. 전체 실패라면 정상 빈 상태와 구분되는
전용 오류 화면과 다시 불러오기 버튼이 필요하다.

#### P1. 백그라운드 작업 완료 후 홈 정보가 자동으로 갱신되지 않음

알림은 15초마다 갱신되지만 홈의 작업 목록, 지도 진행률과 공고 수는 화면 최초 진입 때 한 번만
불러온다. 홈에 머무는 동안 분석이 완료되어도 작업이 계속 실행 중인 것처럼 남거나 이전 진행률이
보일 수 있다. 작업 완료 알림을 받았을 때 관련 홈 데이터도 다시 불러오거나, 작업 영역에 제한된
폴링과 마지막 갱신 시각·수동 새로고침을 제공해야 한다.

#### P1. 현재 목표가 홈에 보이지 않음

서비스가 공고와 최종 목표에 맞춰 다음 경로를 정하는데 홈에는 목표 직무, 회사, 경력 조건이나
최종 목표가 나타나지 않는다. 따라서 사용자는 `왜 이 단계가 다음인지` 확인할 근거가 없다.
다음 퀘스트 카드에 `네이버 백엔드 지원 준비 · 필수 역량`처럼 추천 근거를 붙이고, 목표가 없으면
목표 설정 또는 첫 공고 등록을 우선 행동으로 안내하는 편이 좋다.

#### P1. 상단의 AI 상태가 실제 상태와 무관함

`AI 작업은 다른 화면에서도 계속됩니다` 옆 초록 점은 AI 서버 상태나 현재 작업 존재 여부를
확인하지 않고 항상 표시된다. AI 연결이 끊겼을 때도 정상 상태처럼 보일 수 있다. 단순 안내라면
상태등을 제거하고, 상태 표시라면 실제 가용성·실행 작업 수·입력 대기 여부와 연결해야 한다.

#### P2. 모바일 내비게이션이 아이콘만 남음

560px 이하에서는 여섯 메뉴의 글자를 `font-size: 0`으로 숨긴다. 익숙해지기 전에는 보관함,
공고, 지도와 활동 아이콘을 구분하기 어렵다. 핵심 메뉴를 4~5개로 줄이고 나머지를 `더보기`에
넣거나, 선택 항목만이라도 짧은 라벨을 유지하는 방식이 더 이해하기 쉽다. 운영자 계정은 메뉴가
하나 더 생기지만 그리드는 여전히 여섯 칸으로 고정되어 별도 확인이 필요하다.

#### P2. 작은 보조 문구와 상태 접근성

작업 종류는 8px, 작업 메시지는 9px, 빠른 시작 설명과 진행률 설명은 10px이다. 핵심 행동을
설명하는 문구이므로 12px 이상이 적절하다. 로딩 영역과 홈 오류에는 `aria-live` 또는
`role="status"`·`role="alert"`가 없고 진행률 원도 보조 기술용 진행 상태를 제공하지 않는다.

#### P2. 알림 작업 실패에 사용자 피드백이 없음

알림 하나 열기와 모두 읽음 처리에는 화면 수준의 오류 처리가 없다. 읽음 API는 성공했지만 이동이
실패하거나, 모두 읽음 요청이 실패하면 사용자에게 상태가 전달되지 않는다. 알림 팝오버의 Esc 닫기,
바깥 클릭, 초점 이동과 복원도 함께 보완해야 한다.

### 권장 우선순위

1. 홈 데이터를 `RoadmapWorkspace` 또는 홈 전용 요약 API로 통일
2. `단계 열기` 딥링크 계약을 정하고 지도 노드 상세까지 실제로 열기
3. 역량·필수 조건 기준으로 다음 단계와 진행률 계산 규칙 재정의
4. 부분 실패, 다시 불러오기와 백그라운드 완료 자동 갱신 구현
5. 진행률 원을 실제 비율과 동기화
6. 현재 목표와 다음 단계 추천 이유 표시
7. AI 상태 문구를 실제 작업 상태와 연결하거나 상태 표현 제거
8. 모바일 메뉴와 8~10px 보조 문구의 가독성·접근성 개선

### 유지할 방향

홈의 정보 순서와 카드 구성은 전면 교체할 필요가 없다. `오늘의 여정 → 다음 퀘스트 → 진행 중 작업
→ 빠른 시작 → 최근 변화`의 흐름, 고정 사이드바, 하단 모바일 내비게이션의 방향은 좋다. 화면의
외형보다 홈과 실제 로드맵이 같은 사실을 말하도록 데이터 계약과 이동 동작을 바로잡는 것이 먼저다.

## 4. 대화

- 경로: /app/chat
- 주요 구현: ChatView.vue, 대화·비동기 응답·공고 분석 API

### 한줄 평가

낙관적 메시지 표시, 백그라운드 작업, 추가 질문, 에이전트 실행 과정까지 현재 프로젝트의 핵심 경험은
가장 많이 구현된 화면이다. 다만 대화가 길어지거나 여러 대화를 빠르게 오갈 때 데이터가 뒤섞이거나
최신 메시지가 보이지 않을 수 있어, 출시 전에는 장기 사용 안정성을 먼저 보완해야 한다.

### 잘된 점

- 사용자가 보낸 메시지를 AI 응답 전에 즉시 표시한다.
- 대화 영역 안에서만 스크롤되며, 사용자가 과거 메시지를 읽는 중에는 강제로 아래로 이동시키지 않는다.
- 새 메시지가 도착하면 하단 이동 버튼을 제공하고, 처음 열 때는 최신 대화로 이동한다.
- 공고 분석 작업과 일반 AI 답변 작업을 백그라운드 상태로 추적하며 취소·재시도·추가 질문·승인과
  반려까지 한 화면에서 이어갈 수 있다.
- 에이전트 실행 과정, 산출물, 출처, 확인 요청을 구분해 보여 주는 방향은 서비스 신뢰 형성에 유리하다.
- 대화 삭제 시 연동된 공고와 분석 결과는 유지된다고 안내하여 파괴 범위를 설명한다.

### P0. 긴 대화에서 최신 메시지가 사라질 수 있음

백엔드는 대화 메시지를 오래된 순서로 정렬한 뒤 최대 200개만 반환한다. 메시지가 200개를 넘으면
최신 200개가 아니라 최초 200개가 돌아오므로 사용자가 방금 나눈 대화를 다시 열었을 때 최근 내용이
보이지 않을 수 있다. 최신 200개를 조회한 뒤 시간순으로 재정렬하고, 그 이전 기록은 더 불러오기나
커서 페이지네이션으로 제공해야 한다.

대화 목록도 최대 50개로 제한되지만 화면에는 더 불러오기, 검색, 제한 안내가 없다. 장기 사용자를
고려하면 대화 목록과 메시지 모두 커서 기반 조회가 필요하다.

### P1. 대화를 빠르게 전환하면 이전 응답이 새 화면을 덮을 수 있음

대화를 여는 요청에 취소나 요청 식별자가 없다. A 대화를 연 직후 B 대화를 열었는데 A 응답이 늦게
도착하면 현재 선택은 B인데 메시지는 A인 상태가 될 수 있다. 선택 시퀀스 번호나 AbortController를
사용해 마지막 요청만 반영해야 한다.

### P1. 폴링이 한 번의 부가 요청 실패로 완전히 멈출 수 있음

작업 상태 조회 이후 대화 재조회나 자동 액션 실행에서 예외가 발생하면 다음 폴링 예약까지 도달하지
못할 수 있다. 일시적인 네트워크 오류 한 번으로 진행 상태가 영원히 멈춘 것처럼 보이게 된다.
폴링 전체를 try/finally로 감싸고, 실패 횟수·재시도 간격·수동 새로고침을 제공해야 한다.

### P1. 대화별 문맥 선택이 분리되지 않음

수동 에이전트 모드와 선택한 공고·자료가 다른 대화로 이동해도 남는다. 사용자는 새 대화에서 이전
대화의 자료를 의도치 않게 첨부할 수 있다. 대화별 초안으로 저장하거나 대화 전환 시 초기화하고,
전송 버튼 근처에 실제로 함께 전송되는 문맥을 항상 표시해야 한다.

### P1. 보관 기능과 실제 목록의 의미가 불완전함

백엔드에는 대화 보관 기능이 있지만 UI는 영구 삭제만 제공한다. 보관된 대화도 목록 조회에서 별도로
구분되지 않아, 백엔드에서 보관된 대화를 열고 메시지를 보내면 갑자기 실패할 가능성이 있다.
보관함·복원·영구 삭제를 분리하고 목록 API도 상태를 명시적으로 필터링해야 한다.

### P2. 입력과 접근성

- 공고 URL을 일반 채팅에 입력할 때와 공고 첨부 창을 사용할 때 필요한 입력이 서로 다르다.
- 긴 입력을 위한 자동 높이 조절이 없어 작성 경험이 답답할 수 있다.
- 모달의 초점 고정·Esc 닫기·닫은 뒤 초점 복원과 오류 영역의 role=alert가 부족하다.
- 내부 판단, 에이전트 이름 같은 용어는 기본 화면에서 최소화하고 자세히 보기에 두는 편이 좋다.
- 대화와 에이전트 자산을 한 번에 불러와 하나가 실패하면 전체 화면을 오류로 만드는 결합도 완화해야 한다.

### 권장 우선순위

1. 최신 메시지 200개 조회와 과거 기록 페이지네이션
2. 대화 전환 요청 경합 방지
3. 실패해도 계속 살아 있는 폴링과 수동 복구
4. 대화별 에이전트 모드·첨부 문맥 격리
5. 검색·이름 변경·보관함과 삭제 정책 정리
6. 모달·오류·키보드 접근성 보완

## 5. 커리어 저장소

- 경로: /app/storage
- 주요 구현: StorageView.vue, 커리어 조각·원본 자료 API

### 한줄 평가

검색·정렬·수정·보관·복원·삭제·병합과 원본 분석 재시도까지 예전 프로젝트에서 부족했던 관리 기능은
상당 부분 갖췄다. 그러나 원본 이력서와 자료를 사용자가 삭제할 수 없고, 자료가 많아지면 100개 이후
조각이 보이지 않는다는 점은 데이터 소유권과 실제 사용성 측면에서 큰 문제다.

### 잘된 점

- 조각 검색, 종류 필터, 정렬 기준과 방향, 보관함을 제공한다.
- 조각 수정·보관·복원·삭제와 여러 조각 병합을 지원한다.
- 원본 자료의 대기·분석 중·검토 필요·확정·실패 상태를 구분한다.
- 텍스트·파일·URL 입력을 지원하고 AI 추출 결과를 저장 전에 검토하게 한다.
- 실패한 자료의 재시도와 AI 진단을 제공한다.

### P0. 원본 자료 삭제 기능이 화면에 없음

백엔드와 API 클라이언트에는 원본 자료 삭제 기능이 있지만 저장소와 검토 화면 어디에서도 사용할 수
없다. 이력서 원문은 민감정보가 많은 데이터이므로 조각만 삭제하고 원문은 남는 구조는 사용자 기대와
맞지 않는다. 삭제 범위와 파생 조각 처리 방식을 설명한 원본 삭제 기능이 반드시 필요하다.

### P1. 조각 100개 이후가 조용히 사라짐

조각 목록은 한 번에 100개만 요청하며 페이지 이동이나 더 불러오기가 없다. 전체 개수는 존재하지만
사용자는 101번째 이후 조각에 접근할 수 없다. 서버 페이지네이션과 검색 결과 개수를 화면에 연결해야 한다.

### P1. 분석 중 3초마다 전체 저장소가 로딩될 수 있음

원본 자료가 처리 중이면 주기적으로 전체 load를 호출하며, 이 과정에서 공통 loading 상태가 켜진다.
조각 목록까지 반복해서 스피너로 바뀌거나 깜박일 수 있다. 원본 상태만 조용히 갱신하거나 항목 단위로
상태를 업데이트해야 한다.

### P1. URL 자료가 실제 URL 가져오기가 아님

URL과 함께 원문을 직접 붙여 넣어야 하므로 사용자가 기대하는 링크 수집 기능과 다르다. 대화 화면의
URL 수집 흐름과 통일해 URL을 가져오고 미리 보여 준 뒤, 가져오기 실패 시에만 직접 붙여 넣기를
요청하는 편이 자연스럽다.

### P1. 병합이 내부 데이터 구조를 사용자에게 노출함

서로 다른 종류의 조각도 호환성 확인 없이 병합할 수 있고, canonicalKey 같은 내부 식별자를 사용자가
수정할 수 있다. 잘못 병합하면 이후 공고 매칭까지 오염될 수 있다. 병합 전 미리보기, 허용 가능한
종류 제한, 대표값 선택과 되돌리기가 필요하며 내부 키는 숨겨야 한다.

### P2. 상태와 오류 표현

- 검색 결과가 0개일 때 저장된 자료가 없다는 빈 상태와 검색 결과 없음이 구분되지 않는다.
- 파일 업로드·편집 오류가 열린 모달이나 서랍 뒤에 렌더링되어 메시지를 보기 어렵다.
- 원본 자료가 많아질 때 검색·필터가 없고 가로 목록이 길어진다.
- 조각과 원본을 Promise.all로 묶어 한 API 실패가 전체 저장소 실패로 보인다.
- 모달과 서랍의 초점 이동·Esc·레이블 연결이 부족하다.

### 권장 우선순위

1. 원본 자료 삭제와 파생 데이터 처리 정책
2. 조각 페이지네이션 또는 무한 스크롤
3. 분석 상태만 부분 갱신하여 화면 깜박임 제거
4. URL 자동 수집과 미리보기
5. 안전한 병합 미리보기·되돌리기와 내부 키 숨김
6. 검색 결과·오류·모달 접근성 개선

## 6. 커리어 자료 검토

- 경로: /app/storage/sources/:sourceId
- 주요 구현: CareerSourceReviewView.vue

### 한줄 평가

원문과 추출 조각을 나란히 검토하고 수정·제외한 뒤 저장하는 핵심 흐름은 올바르다. 다만 AI가
제안한 모든 항목이 기본 선택되어 있어 검토보다 일괄 수락을 유도하고, AI가 놓친 조각을 직접 추가할
방법이 없다는 점이 품질을 제한한다.

### 잘된 점

- 원문과 추출 결과를 함께 보여 주어 근거를 확인할 수 있다.
- 제안 조각의 수정과 제외, 선택 저장을 지원한다.
- 처리 중·실패·재시도·확정 상태를 구분한다.
- 최초 로딩 이후 폴링에서는 화면 전체를 교체하지 않아 읽던 위치를 비교적 잘 보존한다.

### P0. 원본 삭제·취소·민감정보 제거가 없음

잘못 올린 이력서나 개인정보가 포함된 자료를 화면에서 삭제할 수 없다. 원본 삭제, 분석 취소,
민감정보 마스킹 또는 원문 교체가 필요하다.

### P1. 모든 AI 제안이 기본 선택됨

모든 SUGGESTED 조각을 자동 선택하면 사용자는 검토자라기보다 확인 버튼을 누르는 역할이 된다.
신뢰도가 낮거나 중복 가능성이 있는 항목은 선택하지 않고, 변경점과 추출 근거를 보여 주어 의식적인
승인을 유도하는 편이 안전하다.

### P1. 누락된 조각을 직접 추가할 수 없음

AI가 경험 하나를 놓치면 사용자는 기존 제안을 고치는 것 외에 새 조각을 만들 수 없다. 검토 화면에서
직접 조각 추가와 원문 범위 연결을 제공해야 저장소가 완성된다.

### P1. 폴링 오류 뒤 자동 복구가 멈출 수 있음

한 번 load가 실패하면 다음 폴링 예약까지 도달하지 못해 계속 처리 중인 것처럼 남을 수 있다.
try/finally 기반 재시도와 수동 새로고침이 필요하다.

### P2. 검토 상태 표현

- 확정된 결과도 비활성 체크박스로 보여 주어 결과인지 선택 불가 상태인지 구분하기 어렵다.
- 편집 오류가 모달 뒤에 표시된다.
- 재시도 3회 제한에 도달한 뒤 사용자가 취할 수 있는 다음 행동이 없다.
- 긴 원문과 조각의 작은 글씨는 장시간 검토에 부담을 준다.

### 권장 우선순위

1. 원본 삭제·분석 취소·민감정보 처리
2. 직접 조각 추가
3. 기본 선택 정책과 신뢰도·근거 표시 개선
4. 실패 후 살아 있는 폴링과 복구 수단
5. 확정 결과용 상태 컴포넌트와 편집 오류 위치 개선

## 7. 채용 공고 목록

- 경로: /app/postings
- 주요 구현: PostingsView.vue

### 한줄 평가

검색·상태·정렬·보관 필터와 서버 페이지네이션을 갖춘 목록 자체는 좋다. 그러나 코드에 작성된
수정·보관·삭제 서랍이 실제로는 절대 열리지 않아 핵심 관리 기능이 죽어 있고, 분석 상태가 화면에
자동 갱신되지 않는다.

### 잘된 점

- 검색, 분석 상태, 정렬, 보관 여부를 조합할 수 있다.
- 서버 페이지네이션을 사용해 저장 공고가 늘어나는 상황을 고려했다.
- 분석 대기·추가 질문·분석 중·실패·취소와 모집 마감 상태를 구분한다.

### P0. 공고 관리 서랍이 실제로 열리지 않음

카드 클릭 함수는 선택 공고를 설정하지 않고 곧바로 상세 경로로 이동한다. 따라서 같은 파일 안에
존재하는 수정·보관·삭제·취소·재시도 서랍은 도달할 수 없는 죽은 UI다. 상세 화면에는 재시도와
진행 중 취소가 일부 존재하지만 수정·보관·삭제는 제공되지 않는다. 관리 기능을 상세 화면으로 옮기거나
명확한 더보기 버튼으로 서랍을 열고, 사용하지 않는 중복 코드는 제거해야 한다.

### P1. 목록에 머물면 분석 상태가 낡음

새 공고의 분석을 시작한 뒤 목록에 머물러도 폴링이나 이벤트 갱신이 없다. 사용자는 직접 새로고침하거나
다른 페이지에 다녀와야 완료 상태를 본다. 실행 중 항목만 가볍게 폴링하거나 공통 작업 상태 저장소와
연결해야 한다.

### P1. 빠른 필터 변경에서 오래된 응답이 덮을 수 있음

검색어·필터·페이지를 빠르게 바꿀 때 요청 취소나 순번 비교가 없다. 먼저 시작한 느린 응답이 나중
조건의 결과를 덮을 수 있으므로 마지막 요청만 반영해야 한다.

### P2. 빈 상태와 유지보수

- 저장 공고가 전혀 없는 상태와 필터 결과가 없는 상태를 구분해야 한다.
- 실제 상세와 죽은 서랍에 유사한 표시·액션이 중복되어 이후 수정이 서로 달라질 위험이 크다.
- 상태 변경을 위한 수동 새로고침 버튼도 없다.

### 권장 우선순위

1. 관리 액션을 상세 또는 명시적 더보기 메뉴로 복구
2. 진행 중 공고 상태 자동 갱신
3. 목록 요청 경합 방지
4. 빈 상태 분리와 죽은 중복 코드 제거

## 8. 새 공고 분석

- 경로: /app/postings/new
- 주요 구현: NewPostingView.vue

### 한줄 평가

공고 저장 후 백그라운드에서 분석하고 중복 공고는 기존 결과로 안내하는 흐름이 분명하다. 반면 URL
하나만으로 시작할 수 없고, 긴 공고 원문을 작성하던 중 이탈하면 모두 잃는다는 점이 실제 수집 경험을
무겁게 만든다.

### 잘된 점

- 공고 추가와 AI 분석이 어떤 순서로 진행되는지 설명한다.
- 10만 자 카운터와 원문 입력 공간이 충분하다.
- 같은 공고를 재사용했을 때 기존 공고로 이동하며 이유를 안내한다.
- 저장 직후 다른 화면을 사용해도 백그라운드에서 처리된다는 기대를 만든다.

### P1. URL만으로 공고를 가져올 수 없음

URL과 전체 원문을 모두 요구한다. 대화에서는 URL을 수집할 수 있으므로 같은 서비스 안에서 능력과
사용법이 다르게 느껴진다. URL 가져오기 → 원문 미리보기 → 부족할 때 직접 붙여 넣기 순서로 통일하는
것이 좋다.

### P1. 잘못된 URL이 서버까지 전달될 수 있음

입력은 type=url이지만 제출이 form submit이 아닌 버튼 클릭으로 구현되어 브라우저 기본 URL 검증이
확실히 실행되지 않는다. 백엔드도 길이만 확인하고 http/https 형식을 검증하지 않는다. 서버에서 허용
스킴과 정규화 규칙을 검사하고, 화면에서도 즉시 오류를 보여 줘야 한다.

### P1. 긴 원문 초안 보호가 없음

자동 저장이나 페이지 이탈 경고가 없어 새로고침·뒤로 가기·로그인 만료로 입력 전체를 잃을 수 있다.
로컬 임시 저장과 제출 성공 후 삭제, 이탈 확인을 제공해야 한다.

### P2. 입력 안내와 접근성

- 입력 방식 전환 버튼에 tab 역할과 aria-selected가 없다.
- 오류 영역에 role=alert가 없다.
- 지원하는 채용 사이트, 가져오지 못하는 경우, 개인정보를 넣지 말라는 안내가 부족하다.

### 권장 우선순위

1. URL 자동 수집과 원문 미리보기
2. 서버 측 URL 검증
3. 작성 중 초안 자동 저장과 이탈 경고
4. 입력 탭·오류 접근성 및 도움말 보완

## 9. 채용 공고 상세

- 경로: /app/postings/:postingId
- 주요 구현: PostingDetailView.vue

### 한줄 평가

공고 해설, 추가 질문, 분석 단계, 지원 판정, 목표 프로젝트, 대체 공고와 지도 반영까지 서비스의 핵심
결정을 한곳에 잘 모았다. 그러나 공고 조건과 내 커리어를 연결한다는 제목과 달리 실제 보유 근거와
진행 상태를 보여 주지 않아 가장 중요한 비교 결과가 반쪽이다.

### 잘된 점

- 중복 공고 재사용, 모집 마감, 원문 링크와 AI 대화 진입을 제공한다.
- 동적으로 달라지는 분석 단계, 대기 순서, 추가 질문과 답변 이력, 정보 없음 확정을 표현한다.
- 분석 취소·재시도와 구조화 데이터 오류를 사용자에게 설명한다.
- 즉시 지원·보강 후 지원·대체 경로 판정과 이유, 필수·우대 조건, 목표 프로젝트, 대체 공고를 구분한다.
- 로드맵에서 제외되는 정성 항목을 따로 보여 주고 변경안을 검토한 뒤 승인·반려하게 한다.
- 마감된 공고를 새 목표로 추가하지 않도록 막는다.

### P0. 내 역량과의 실제 비교 상태가 없음

공고 조건 행에는 단계와 요구 수준만 나오고 사용자의 현재 수준, 완료·진행 중·미시작, 검증 근거,
부족한 차이를 표시하지 않는다. 사용자는 왜 보강 후 지원인지 이유 문장을 읽어 추론해야 한다.
각 조건을 필수 여부, 요구 수준, 현재 검증 수준, 근거, 차이, 다음 행동으로 구성해야 한다.

### P1. 공고 수정·보관·삭제가 없음

목록에 있던 관리 서랍은 열리지 않고 상세에도 수정·보관·삭제가 없다. 잘못 저장한 원문이나 마감
공고를 사용자가 정리할 수 있도록 상세의 더보기 메뉴로 제공해야 한다.

### P1. 대체 공고 오류가 빈 결과처럼 보임

대체 공고 조회 실패를 조용히 무시하여 정말 추천이 없는 것과 서버 오류를 구분할 수 없다. 다시
불러오기와 오류 상태를 분리해야 한다. 저장된 대체 공고라면 외부 링크뿐 아니라 내부 상세로도 이동해야 한다.

### P1. 많은 조건이 한 번에 펼쳐짐

요구 조건이 수십 개면 중복 문장까지 그대로 노출되어 판정과 목표 프로젝트가 아래로 밀린다. 필수
미충족을 먼저 보여 주고, 충족·우대·원문 추출은 접어서 볼 수 있게 그룹화해야 한다. 책임 업무도
요약 개수만 세지 말고 별도 섹션에서 확인할 수 있어야 한다.

### P2. 상태 복구와 설명

- 상태 조회가 한 번 실패한 뒤 폴링이 멈출 수 있다.
- 공고 구조화 결과가 없을 때 이유와 다시 시도 CTA가 없다.
- 재시도 한도에 도달한 뒤 운영 문의나 원문 수정 같은 다음 행동이 없다.
- 마감 사유를 title 속성에만 의존하면 모바일에서 확인하기 어렵다.
- 지원 판정에 대한 재평가 또는 이의 제기 경로가 없다.

### 권장 우선순위

1. 조건별 현재 수준·근거·차이·다음 행동 표시
2. 공고 수정·보관·삭제
3. 필수 미충족 중심의 조건 그룹화와 중복 제거
4. 대체 공고 오류·내부 이동 개선
5. 폴링 복구, 재평가와 재시도 한도 이후 경로

## 10. 커리어 지도

- 경로: /app/map
- 주요 구현: CareerMapView.vue, JourneyMap.vue, roadmap/journey.ts

### 한줄 평가

현재 지도와 초안을 나눠 검토·적용하고, 확대·축소·이동·직무 섹션·회사 분기를 제공하는 현재 방향은
지금까지 합의한 서비스 개념에 가장 가깝다. 다만 직무가 여러 개가 되면 공통 기초가 직무마다 복제되는
구조여서 하나의 통합 여정이라는 핵심 개념이 다시 깨진다.

### 잘된 점

- 현재 지도와 새 초안을 구분하고 변경 개수와 적용 확인을 제공한다.
- 응답 오류가 나도 실제 적용 여부를 다시 조회해 조정하려는 복구 로직이 있다.
- 목표 필터, 목표 제거, 지도 초기화와 최신화를 제공한다.
- 여정 보기와 상세 관계 보기를 나누고, 확대·축소·드래그·화면 맞춤을 제공한다.
- 공통 기초, 직무별 역량, 회사 프로젝트와 지원 기회를 시각적으로 구분한다.
- 노드 상세에서 기초 자기 확인, 학습 가이드, AI 검증 문제, 프로젝트 증거 제출, 판정 이의 제기를 잇는다.
- 문제 수와 평균 점수, 유지되는 검증 결과를 보여 주는 방향이 좋다.

### P0. 공통 기초가 직무마다 복제됨

JourneyMap은 직무 트랙을 순회할 때마다 동일한 foundations를 다시 렌더링한다. 백엔드·프론트엔드·보안
목표가 함께 생기면 하나의 프로그래밍 기초에서 여러 분야로 갈라지는 것이 아니라, 분야마다 프로그래밍
기초가 반복된다. 접기 상태도 전역 불리언 하나라 한 트랙에서 열면 모든 복제본이 같이 열린다.

공통 기초는 지도 왼쪽에 한 번만 두고 완료 후 직무 트랙으로 분기해야 한다. 공통 기술도 같은 정규화된
역량을 참조하도록 하되, 회사별 요구 수준과 검증 범위는 연결 관계에 별도로 보존해야 한다.

### P0. 경력 관문 판별이 노드 ID 문자열에 의존함

경력 단계 판단이 career:로 시작하는 ID 규칙에 기대고 있다. AI나 백엔드가 다른 ID를 만들면 경력
노드가 일반 기술로 잘못 배치된다. 노드 종류, stage, requirement metadata 같은 명시적 필드로 판단해야 한다.

### P1. 진행률에 지원 기회가 포함될 수 있음

여정 전체 완료 수에 회사 지원 기회까지 포함되면 사용자가 직접 완료할 수 없는 노드 때문에 100%에
도달하지 못할 수 있다. 학습 진행률, 프로젝트 준비도, 지원 가능 회사 수를 별도 지표로 나누는 편이 정확하다.

### P1. 상세 관계 보기는 데이터 증가에 취약함

모든 노드와 연결을 DOM·SVG로 한 번에 렌더링하고 최대 rank에 따라 캔버스를 크게 만든다. 공고와
직무가 늘면 화면이 지나치게 넓고 느려진다. 분야·회사 클러스터 접기, 화면 내 렌더링, 미니맵과 검색,
현재 목표 중심 보기 같은 규모 대응이 필요하다.

### P1. 초안 검토 정보가 부족함

변경 목록은 앞의 6개만 보여 주고 나머지 개수나 전체 보기로 연결되지 않는다. 사용자는 어떤 노드가
왜 합쳐지고 제거됐는지 확인하지 못한 채 적용할 수 있다. 전체 diff, 변경 이유, 영향받는 회사,
적용 후 미리보기와 버전 되돌리기를 제공해야 한다.

또한 기존 초안이 있는 상태에서 최신화를 누르면 검토 중 초안을 교체할 수 있으므로 확인이 필요하다.

### P1. 검증과 학습 작업의 복구 경험

- 역량 선택 시 최근 검증과 학습 가이드를 Promise.all로 묶어 하나만 실패해도 둘 다 보이지 않는다.
- 문제 표시는 항상 현재 문제/5처럼 보여 3~5문제 가변 계약과 맞지 않을 수 있다.
- 진행 중 검증을 포기하거나 처음부터 다시 시작할 방법이 없다.
- 증거 검증 실패 이유와 재시도 기능이 UI에 없지만 API에는 재시도 기능이 존재한다.
- 프로젝트 URL은 서버에서 GitHub·GitLab 형식과 접근 가능 여부를 검증해야 한다.

### P2. 지도 탐색과 표현

- 초안이 있으면 매번 초안 미리보기로 강제되어 현재 지도를 보던 맥락이 바뀔 수 있다.
- 직무와 단계 코드가 영문 대문자 enum 그대로 보이는 부분이 있다.
- 목표 회사가 많아지면 검색과 회사 그룹 접기가 필요하다.
- 서랍과 확인 창은 Esc는 지원하지만 초점 고정과 닫은 뒤 복원이 부족하다.
- 직무 섹션 순서가 데이터 삽입 순서에 좌우될 수 있어 같은 지도도 갱신 때 위치가 달라질 수 있다.

### 권장 우선순위

1. 하나의 공통 기초에서 여러 직무로 갈라지는 통합 여정 모델
2. 노드 ID가 아닌 명시적 타입 기반 배치
3. 학습 진행률·프로젝트 준비도·지원 가능성을 별도 표시
4. 전체 초안 diff, 변경 이유와 버전 되돌리기
5. 대규모 그래프 클러스터링·검색·미니맵
6. 검증 중단·재시작, 증거 실패 이유·재시도
7. 초안 보기 상태와 직무 순서 안정화

## 11. 활동 내역

- 경로: /app/activity
- 주요 구현: ActivityView.vue

### 한줄 평가

백그라운드 공고 분석과 알림을 한곳에 모은 기본 틀은 있지만 현재는 읽음 처리용 목록에 가깝다.
알림을 눌러도 결과 화면으로 이동하지 않고, 공고 분석 이외의 장기 작업은 보여 주지 않아 활동 허브라는
목적을 충분히 수행하지 못한다.

### 잘된 점

- 진행 중 분석을 상단에 따로 보여 준다.
- 수동 새로고침과 모두 읽음을 제공한다.
- 알림을 시간순으로 확인할 수 있다.

### P0. 알림을 눌러도 결과로 이동하지 않음

사이드바 알림은 공고·자료·지도 등 관련 화면으로 이동하지만 활동 내역의 항목 클릭은 읽음 처리만 한다.
사용자는 완료 알림을 보고도 어디서 결과를 볼지 다시 찾아야 한다. 알림 payload를 공통 라우팅 함수로
연결해 두 화면이 같은 행동을 해야 한다.

### P1. 일부 작업만 진행 상태로 보임

진행 중 목록은 공고 분석 작업만 보여 준다. 커리어 자료 분석, 증거 검증, 비동기 채팅 답변, 로드맵
생성처럼 실제로 오래 걸리는 작업도 같은 작업 모델로 보여 줘야 한다.

### P1. 자동 갱신과 과거 기록이 부족함

화면에 머무르는 동안 폴링이나 이벤트 갱신이 없고 최신 알림 30개만 조회한다. 더 불러오기와 날짜
그룹, 안 읽음·작업 종류 필터가 필요하다.

### P1. 부분 실패가 전체 실패로 보임

알림·작업·공고를 Promise.all로 묶어 하나가 실패하면 모든 내용이 보이지 않는다. 읽음과 모두 읽음도
실패 피드백이 없다. 패널별 오류와 재시도를 제공해야 한다.

### P2. 사용자 언어와 가독성

- ANALYSIS_COMPLETED 같은 내부 enum을 그대로 보여 준다.
- 종류·본문·시간의 8~9px 보조 글자는 중요한 활동을 읽기에 너무 작다.
- 알림 삭제, 읽은 항목 정리, 기간 필터가 없다.

### 권장 우선순위

1. 알림에서 실제 결과 화면으로 이동
2. 모든 백그라운드 작업을 공통 상태로 표시
3. 자동 갱신, 페이지네이션과 필터
4. 패널별 오류·읽음 실패 피드백
5. 상태명 현지화와 글자 크기 조정

## 12. 설정

- 경로: /app/settings
- 주요 구현: SettingsView.vue

### 한줄 평가

현재 목표·최종 목표와 GitHub·GitLab 연결을 한곳에 모으고 권한 경계를 설명한 점은 좋다. 그러나
비밀번호 변경, 계정 탈퇴, 데이터 내보내기와 전체 삭제 같은 기본 계정·개인정보 기능이 없어 출시
가능한 설정 화면으로 보기 어렵다.

### 잘된 점

- 현재 지원 목표와 장기 최종 목표의 차이를 설명한다.
- 목표가 AI 문제 생성과 피드백에 어떻게 쓰이는지 알려 준다.
- GitHub App과 GitLab OAuth 연결, 읽기 전용 접근과 토큰 암호화를 설명한다.
- 연결 해제 후에도 이미 검증된 스냅샷은 유지된다는 정책을 사전에 알린다.
- 프로필, RLS, AI 변경 승인 원칙을 설명한다.

### P0. 계정과 개인정보 자기 결정 기능이 없음

계정 탈퇴, 내 데이터 내보내기, 커리어 자료 전체 삭제, 원본 자료 삭제가 없다. 이름·이메일 수정과
비밀번호 변경·재설정도 제공되지 않는다. 최소한 계정 정보, 보안, 연결 서비스, 데이터 관리,
위험 작업 영역으로 나누어 제공해야 한다.

### P1. 현재 목표의 자격 조건이 화면과 데이터에서 보장되지 않음

안내문은 경력·자격증 같은 실질 자격을 충족하는 공고만 현재 목표로 선택하라고 하지만 선택 목록은
활성 공고라면 모두 허용한다. 사용자의 자격 충족 여부를 판단해 추천·경고하거나, 단순히 사용자의
선택임을 분명히 해야 한다.

### P1. 독립 기능이 한 번의 실패로 함께 막힘

목표, 공고, 저장소 연결 상태를 Promise.all로 불러와 저장소 제공자 장애가 목표 설정까지 막을 수
있다. 오류 문구도 목표 정보를 불러오지 못했다고 뭉뚱그려진다. 섹션별 로딩과 오류로 분리해야 한다.

### P1. 저장소 연결 상태가 충분하지 않음

연결 계정만 표시하고 선택 저장소, 마지막 동기화, 권한 상태, 재인증 필요 여부를 보여 주지 않는다.
연결 이동 전에 저장하지 않은 목표 변경이 있다면 이탈 경고도 필요하다. 연결 해제 후 유지된 검증
스냅샷을 사용자가 별도로 지울 방법도 제공해야 한다.

### P2. 피드백과 개인화

- 저장 성공과 오류가 스크린리더에 전달되는 live region이 아니다.
- 현재 목표가 홈 화면에는 충분히 노출되지 않아 설정 결과가 핵심 경험과 연결되지 않는다.
- 테마, 글자 크기, 움직임 감소 같은 접근성 환경설정은 향후 고려할 수 있다.

### 권장 우선순위

1. 계정 보안·탈퇴·데이터 내보내기와 삭제
2. 현재 목표 선택 가능 조건과 경고 규칙 명확화
3. 설정 섹션별 로딩·오류 분리
4. 저장소 권한·동기화·재인증 상태와 스냅샷 삭제
5. 홈과 목표 연결, 상태 접근성 개선

## 13. 운영 검토함

- 경로: /app/operator
- 주요 구현: OperatorView.vue, OperatorService

### 한줄 평가

중복 공고 합치기와 AI 검증 이의 제기를 사람이 최종 판정한다는 운영 모델은 적절하고 백엔드 권한도
검사한다. 그러나 운영자가 판단에 필요한 원문과 차이를 거의 볼 수 없으며, 브라우저 prompt 취소가
빈 사유의 실제 처리로 이어질 수 있는 치명적인 조작 문제가 있다.

### 잘된 점

- 운영자 역할을 라우트와 백엔드에서 모두 검사한다.
- 중복 후보를 왼쪽 유지·오른쪽 유지·별도 유지·보류로 결정할 수 있다.
- 검증 이의 제기를 승인·반려할 수 있다.
- 백엔드에 감사 기록과 롤백 API가 존재해 운영 안전성을 확장할 기반이 있다.

### P0. 중복 공고를 판단할 근거가 부족함

회사명, 직무명, 유사도와 AI 제안만 보여 주고 URL, 수집일, 마감일, 원문, 정규화된 요구 조건의
공통점과 차이를 보여 주지 않는다. 운영자는 이름만 보고 어느 쪽을 대표로 남길지 결정해야 한다.
두 공고의 필드별 비교, 출처, 변경 영향과 연결된 사용자 수가 필요하다.

### P0. 검증 이의 제기를 공정하게 볼 자료가 없음

역량명, 목표 수준, 평균 점수, 이메일과 사용자 이의 내용만 보여 준다. 실제 문제, 답변, 문제별 점수와
피드백, 목표 공고, 제출 증거가 없어 승인과 반려를 합리적으로 결정할 수 없다. 최소한 평가 세션
전체와 판정 기준을 읽기 전용으로 제공해야 한다.

### P0. prompt 취소가 빈 사유 처리로 이어질 수 있음

처리 사유를 window.prompt로 받고 null을 빈 문자열로 바꾼 뒤 그대로 API를 호출한다. 운영자가
취소를 눌러도 승인·반려·병합이 실행될 수 있다. 명시적 확인 모달, 필수 사유 검증, 취소 시 즉시
반환이 필요하다.

### P1. 감사와 협업 기능이 UI에 없음

- 최종 처리 전 영향 범위와 확인 단계가 없다.
- 감사 이력과 롤백 API가 있지만 화면에서 조회하거나 되돌릴 수 없다.
- 검색·상태 필터·페이지네이션·처리 이력이 없다.
- 담당자 할당이나 잠금, 마지막 갱신 시각이 없어 여러 운영자가 같은 항목을 동시에 처리할 수 있다.
- 두 검토 큐를 Promise.all로 묶어 한쪽 장애가 전체 화면을 가린다.

### P2. 운영 화면 가독성

브라우저 prompt 대신 사유 템플릿과 자유 입력을 갖춘 검토 모달이 필요하다. 모바일에서 3열 비교는
지나치게 좁으므로 세로 비교나 운영 화면의 최소 폭 정책도 정해야 한다. 이메일은 업무상 필요 범위만
노출하고 불필요하면 일부 마스킹하는 편이 좋다.

### 권장 우선순위

1. prompt 취소 시 처리되는 버그 수정과 필수 확인 모달
2. 중복 공고 필드별 비교·출처·영향 범위
3. 검증 문제·답변·점수·증거와 판정 기준
4. 감사 이력·롤백 UI
5. 검색·필터·페이지네이션·담당자 잠금
6. 모바일 비교 레이아웃과 개인정보 최소 노출

## 전체 화면을 함께 봤을 때의 결론

### 서비스의 강점

이 프로젝트는 단순한 공고 요약 서비스가 아니다. 대화로 사용자의 자료와 목표를 모으고, 공고를
분석해 준비도를 판정하고, 여러 회사의 요구를 하나의 커리어 지도에 합치며, 학습과 증거 검증을 거쳐
지원 가능한 상태로 이끄는 웹앱이다. 현재 구현은 이 핵심 흐름을 실제로 연결했고, 특히 비동기 AI
작업과 사람의 승인, 운영자 검토까지 고려한 점이 강하다.

### 가장 큰 구조적 문제 7가지

1. 같은 사실을 홈의 career-map과 지도의 roadmap이 서로 다르게 해석한다.
2. 대화 50개·메시지 200개·조각 100개·알림 30개처럼 숨겨진 조회 제한 뒤의 데이터에 접근할 수 없다.
3. 원본 자료 삭제, 증거 재시도, 대화 보관, 공고 관리, 운영 롤백처럼 백엔드에 있지만 화면에서
   사용할 수 없는 기능이 적지 않다.
4. 폴링이 한 번 실패하면 멈추거나, 전체 load로 화면이 깜박이는 등 백그라운드 작업 상태 관리가
   페이지마다 다르다.
5. 독립적인 패널을 Promise.all로 묶어 부분 장애가 전체 페이지 장애처럼 보인다.
6. 여러 직무가 생길 때 공통 기초가 반복되어 하나의 통합 로드맵이라는 개념이 깨진다.
7. 계정 탈퇴·데이터 내보내기·원본 삭제와 운영 감사 화면이 부족해 서비스 신뢰와 데이터 소유권이
   완성되지 않았다.

### 출시 전 P0 권장 목록

1. 긴 대화가 최신 메시지를 잃는 조회 오류 수정
2. 원본 커리어 자료 삭제와 계정·데이터 삭제 정책 구현
3. 공고 수정·보관·삭제 UI 복구
4. 조건별 사용자 보유 수준·근거·부족분 표시
5. 공통 기초 한 번에서 직무별로 분기하는 통합 지도 구조
6. 운영 검토함의 근거 자료와 prompt 취소 처리 버그 수정
7. 홈과 지도 데이터 계약 통일 및 단계 딥링크 완성

### 그다음 P1 권장 묶음

1. 공통 백그라운드 작업 저장소와 실패해도 복구되는 폴링
2. 모든 목록의 페이지네이션·검색·필터와 오래된 요청 경합 방지
3. URL 자동 수집과 서버 측 http/https 검증
4. 부분 실패가 가능한 섹션별 로딩·오류·재시도
5. 로드맵 전체 diff·변경 이유·버전 되돌리기
6. 활동 알림에서 실제 결과 화면으로 이동
7. 모달 초점 관리, 상태 live region, 최소 12px 이상의 핵심 보조 문구

### 디자인을 유지해도 되는 부분

현재의 듀오링고 계열 버튼 깊이감, 부드러운 카드, 연한 배경과 직무별 색, 접을 수 있는 사이드바,
대화의 실행 과정 접기, 여정 보기와 상세 관계 보기의 분리는 유지할 가치가 있다. 지금 필요한 것은
새로운 시각 스타일이 아니라 화면이 약속한 행동을 실제 데이터와 정확히 연결하고, 오래 사용해도
망가지지 않게 만드는 작업이다.

### 검토 방법에 대한 주석

이번 검토는 각 Vue 화면, 공통 레이아웃, API 클라이언트와 관련 Spring 백엔드 조회·상태 계약을 함께
읽어 실제 동작과 경우의 수를 확인했다. 별도 로그인 세션이 없는 브라우저에서는 인증 후 개인 데이터가
채워진 최종 렌더링을 다시 재현하지 못했으므로, 시각적인 실데이터 배치보다 기능 계약·상태 전이·오류
복구와 장기 사용 시나리오를 중심으로 판단했다.
