## 2. 정의서 최초 작성 — 3계층 아키텍처 정립 (선행 작업)

`docs/agent-derivation-and-tools.md`를 신규 작성. 요청("각 에이전트에 RAG를 어디에 쓰고 무슨 툴이 필요한지 전부 정의하되, LLM은 마지막에 알고리즘이 도출한 답을 사람 말투로 바꾸는 역할만")을 실제 설계로 확정했다. **이 정의서가 §3 이하 RAG 경계 재정의의 출발점.**

### 2.1 3계층 아키텍처 (핵심 골격)

LLM을 "쓴다/안 쓴다"가 아니라 **역할을 3개로 분리** → "파서는 LLM 되는데 갭 분석은 왜 안 되냐"는 혼선을 제거.

| 계층 | 하는 일 | LLM |
|---|---|---|
| **읽기(Read)** | 비정형 텍스트 → 정형 필드 추출 | 허용(추출만) — parse, profile |
| **판단(Decide)** | 매칭·계산·검색·검증 = 결정 | **금지** — 몸통 전부 |
| **말하기(Speak)** | 정형 결정 → 자연어 | 허용(표현만) — assemble |

→ LLM 호출은 **입구(읽기)·출구(말하기) 두 곳에만** 몰리고, 시스템의 몸통(판단)은 데이터가 돌린다.

### 2.2 전 9노드 도출방법·툴·RAG 표 확정

`parse_job_posting`부터 `assemble_output`까지 9노드 각각에 **"무엇이 답을 정하나 / 필요한 툴 / RAG 여부 / LLM 역할"** 4항목을 표로 명세.
- 핵심: `analyze_gap`의 충족/미충족 판정을 **`gap_matcher`(taxonomy 동의어 + 임베딩 cosine + severity 룰)**로 이관하고 LLM은 `reason` 문장만 쓰게 함.
- `plan_roadmap`은 무엇을/언제/얼마나를 DB+스케줄러가 결정, `verify_result`는 자기검증을 룰 검증으로 전환.

### 2.3 툴 카탈로그 초안

계층별 툴 목록·상태(기존/신규)·담당 노드를 정리하고 신규 구현 우선순위를 매김(**`skill_taxonomy` + `gap_matcher` 최우선**).

> 이 정의서 위에서 §3(RAG 경계 재정의)가 진행됐다 — RAG hook을 3곳→2곳으로 좁히고, 로드맵 학습자료 RAG를 자격증 정형 DB로 교체.

## 3. RAG 적용 경계 재정의 (핵심 결정)

노드별로 "정형 DB / 벡터 RAG / 웹검색 / 자격증 DB" 중 무엇이 맞는지 다시 따졌고, 다음으로 확정했다.

### 2.1 RAG(벡터 검색)는 2곳뿐으로 축소

| hook | 노드 | 결정 | 근거 |
|---|---|---|---|
| ① `fetch_company_context` | `analyze_gap` | **유지** (RAG) | 기업 인재상·기술문화는 비정형·회사마다 달라 정형 불가. **판정 전 재료 공급**일 뿐, 판정 결정권은 노드 |
| ② `search` | `find_alternatives` | **유지** (RAG) | 유사 공고는 비정형+의미유사검색+자체 데이터 축적 → 진짜 벡터 RAG가 맞는 유일 케이스 |

### 2.2 hook ③ (학습자료 RAG) **폐기** → 자격증 정형 DB

- 원래 `plan_roadmap`에 `learning_resource_search`(벡터 RAG)로 강의·아티클을 보강하려 했으나 폐기.
- **이유**: 강의는 무한·휘발성(최신성이 핵심 가치) → 벡터 DB 스냅샷과 상충, 재색인 유지보수 부담. IT 자격증은 정반대로 **유한·안정·완전 정형·스킬 매핑 명확**.
- **대체**: `cert_db`(자격증 정형 DB) + `skill_to_cert`(매핑) + `project_template_db`(자격증 없는 경험형 gap 보완).
- **덤**: `doneCriteria`가 "자격증 취득"으로 진짜 측정 가능해지고, `prepHours` 실측으로 예산 재적합 정확, 시험일정으로 역산 배치 가능.
- IT 솔루션 도메인으로 스코프를 좁혔기에 성립하는 설계.

### 2.3 희소·신규 기업은 웹검색 폴백

- hook ① 코퍼스에 없는 회사는 미리 색인 불가 → **어댑터 내부 웹검색 폴백**으로 흡수. 계약(`fetch_company_context`)·노드는 불변.

### 2.4 RAG를 안 쓰는 판단 기준 (문서 §5에 명문화)

> - 비정형 + 의미유사검색 + 자체 데이터 축적 → **RAG** (공고·기업지식)
> - 유한 + 안정 + 정형 → **정형 DB** (자격증)
> - 최신 + 희소 → **웹검색** (희소 기업, RAG 어댑터 내부 폴백)

## 4. `find_alternatives` 대체 경로 검색 흐름 정의

"사용자 gap이 목표 공고와 크게 벌어질 때, **징검다리 하위 직업군을 거쳐** 실현 가능한 경로를 찾는다"로 흐름을 확정하고, 오케스트레이터/RAG 담당의 역할을 분리했다.

```text
[오케스트레이터 — RAG 앞단]
① gap 차이 판정 → 대체경로 트리거
② 목표 직업군 확인 (roleCategory)
③ 하위/징검다리 직업군 도출 (career_graph)
④ 하위 직업군 기반 query 조립

[RAG 담당 — search() 내부]
⑤(a) 내부 공고 코퍼스 벡터 검색
⑤(b) 부족 시 웹검색 폴백  (warnings 에 web_fallback 표기, url 필수)
```

- **오케스트레이터가 ①~④까지 풀어 `query`에 실어 넘긴다.** RAG 담당은 ⑤(벡터→웹폴백)만 구현.
- 둘 다 실패 → `items=[]`+`no_result` → 경로 '유형'만 제안(허구 방지).

## 5. `career_graph` 신규 스캐폴딩 (③ 도출부 구현)

`src/jobis_ai/career_graph.py` 신규 — 목표 직군 → 하위/징검다리 직군을 도출하는 **순수 내부 정형 DB**(LLM/RAG/임베딩 미사용, 결정론).

- **`_SENIORITY_LADDER`**: `intern < junior < mid < senior < lead`.
- **`_ROLE_GRAPH`**: 대표 IT 직군 12종 + 각 직군의 `feeders`(징검다리 직군). 예: `backend.feeders=(fullstack,)`, `data_engineer.feeders=(backend, data_analyst)`.
- **`_ROLE_ALIASES`**: 파서 미표준화 원문(`web-backend`·`백엔드`·`서버개발`) 흡수.
- **`derive_sub_roles(role_category, seniority, max_roles=6)`**: 두 종류 도출 —
  - `lower_seniority`(같은 직군 낮은 연차: senior→mid/junior/intern),
  - `stepping_stone`(인접 피더 직군의 진입 연차: backend←fullstack junior).
- **`get_career_graph()`**: `lru_cache` 접근자. 운영 전환 시 여기만 외부 DB 구현체로 교체하면 노드 불변(`rag.py` 패턴 동일).

### 5.1 노드 배선 (`nodes.py`)

- `find_alternatives`가 RAG 검색 **앞단에서** `derive_sub_roles()` 호출 → `_build_alternative_query(posting, gap, sub_roles)`로 하위 직군 라벨을 쿼리에 실음 → `rag.search(query)`.
- `_build_alternative_query`는 `sub_roles=None` 기본값으로 **하위 호환**(기존 테스트 불변).
- LLM 입력에 `subRoleCandidates` 추가 + 프롬프트에 "relation(lower_seniority/stepping_stone)을 type에 반영" 규칙 추가.

### 5.2 테스트

- `tests/test_career_graph.py` 7건: 낮은 연차 도출, 징검다리 피더, 별칭 정규화, 미상 직군 graceful, junior 경계, max_roles 캡, 쿼리 변환.

## 9. 후속 작업 — 9노드 전면 전환 (같은 날 이어서)

§2의 3계층 설계를 **실제 코드로 전부 이관**했다. 툴 12종 신규 구현 + 9노드 배선.
설계 의도·근거는 `docs/agent-derivation-and-tools.md` §4~5가 정본이므로 여기선 결과만 적는다.

**핵심 성과: 판단 계층 5개 노드가 LLM을 호출하지 않는다.** LLM은 입구(parse/profile)·출구(assemble) 3곳에만 남았다(§4.1 검증표).

### 9.1 읽기 계층
- `skill_taxonomy`(표준화+동의어+**implies 함의**), `role_taxonomy`(직군·연차 룰 분류), `rule_extractor`(정규식 1차 추출) 신규.
- `parse_job_posting`: 하이브리드 추출(룰 우선 → 잔여 비정형만 LLM). **LLM 스키마에서 `roleCategory`/`seniority` 제거** — 프롬프트로 부탁하는 것보다 스키마에서 빼는 게 확실하다.
- `build_user_profile`: `skillEvidence`(스킬↔근거 매핑)를 **룰로** 생성 → 존재하지 않는 근거 인용이 구조적으로 불가능.
- `career_graph`가 자체 보유하던 role 별칭·연차 사다리를 걷어내고 `role_taxonomy`로 단일화(사전 이중화 제거).

### 9.2 판단 계층
- **`gap_matcher`** 신규(설계 1순위). 충족/미충족·severity·scoreBasis를 전부 계산. `analyze_gap`은 LLM 미호출.
- `sufficiency_rules` 신규. "정보가 충분한가"만 판단(≠"사람이 충분한가").
- `embed` 어댑터 계약 개방(`similarity()`는 `0.0`이 아니라 **`None`**="모른다").

### 9.3 로드맵 (hook ③ 폐기의 실제 대체)
- `cert_db`(국내 IT 자격증 시드) + `skill_to_cert` + `project_template_db` + `roadmap_scheduler` 신규.
- "invented roadmap" 제거. `plan_roadmap`은 LLM 미호출. `doneCriteria`가 "SQLD 최종 합격"이라 진짜 측정 가능.

### 9.4 검증·말하기
- `verify_rules` 4종 모듈화 + **gap↔roadmap requirementId 교차 검증 신규**(설계에만 있고 미구현이었음).
- `nl_render` 신규. 스키마에 `summary` 하나만 둬서 판정 불가. 출력도 금지표현 검사를 통과해야 채택.

### 9.5 계약 변경
- 내부: `NormalizedUserProfile.skillEvidence`, `Gap.missingSkills`, `GraphState.sufficiency`.
- **외부(백엔드): `AnalyzeResponse.summary` 추가** — 기본값 `""`인 추가 필드라 무시해도 되지만 **백엔드 팀에 공유 필요**(§11-1).

### 9.6 대체 경로
- `find_alternatives` LLM 제거. RAG 미연결이면 경로 '유형'만 내고 회사명·`sourceJobPostingId`·`reducedGaps`를 **비운다**(실공고 없이 추측하면 그게 허구).

## 10. 이번 세션에서 잡힌 실제 결함 (기록용)

돌려 보고서야 드러난 것들. 손으로 만든 샘플이나 코드 리뷰만으로는 못 잡았을 종류다.

1. **`■ 자격 요건 (필수)` 헤더 미인식** — 페르소나 공고(`tests/docs/user1`)로 돌려서 발견. 도형 불릿·접미 괄호를 정규식이 못 받아 섹션 분리가 통째로 실패 → 전문이 LLM으로 넘어가 required/preferred를 위치가 아니라 추측으로 나누고 있었다. `■`는 국내 공고에서 매우 흔하다.
2. **`companyName: "<UNKNOWN>"`** — LLM이 "값 없음"을 자리표시자로 채움. 그대로 두면 `fetch_company_context("<UNKNOWN>")`으로 RAG 호출. → `_clean_field` + 회사명 없으면 RAG 미호출.
3. **`reason`↔`status` 모순** — "다 확인됨"이라며 `partially_met`. 근거 있는 보유와 주장만 있는 보유를 뭉갠 탓.
4. **`find_alternatives`가 `roleCategory` 없으면 포기** — 기존 테스트가 잡음. 직무명이 "백엔드 개발자"인데 직군 미상이라며 빈 결과. → `role_taxonomy` 재분류.
5. **eval 모듈 파손(자체 유발)** — `_FORBIDDEN_EXPRESSIONS`/`_iter_text_fields`를 `verify_rules`로 옮기며 참조를 안 고쳐 2개 모듈이 collection 단계에서 사망. 임시 스크립트만 돌리고 pytest를 안 돌려서 늦게 발견.
6. **"테스트가 없다"는 잘못된 판단** — `tests/`는 처음부터 있었는데 확인 없이 단정하고 문서에도 적었다. 바로잡음.
7. **MySQL≠RDBMS 오판** — "MySQL 등 RDBMS 설계 및 SQL"에서 RDBMS·SQL을 별도 증명 요구. → `implies` 함의 관계 도입.
8. **근거 충분한 사용자에게 질문 퍼붓기** — 스킬 하나 근거 없다고 분석 차단. → `blocking` 구분.
