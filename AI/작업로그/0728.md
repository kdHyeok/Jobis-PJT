# AI 에이전트 구현 작업 로그 (0728)

이 문서는 0728 에 진행한 작업을 정리한다. 오전은 ① 멀티에이전트 개선방안 전면 반영,
② 팀원 프로토타입(Agent_Test 1.0.0)의 우수 구조 이식이었고, 오후는 **실서버로 직접
대화해 결함을 찾고 구조를 개편**하는 작업이었다: ③ 실사용 E2E 검증에서 나온 결함 3건
수정, ④ 팀원 설계와의 냉정한 대조 평가, ⑤ 그 평가에 따른 개편 1·2단계(인자 통로 ·
첫 자기 루프 에이전트), ⑥ 다중 턴을 원천 차단하던 백엔드 세션 버그 수정.

> **핵심 성과**: "멀티에이전트라 부를 당위성"을 로그로 검증하고, 부족한 부분을 실제로
> 메웠다. 실측 궤적으로 확인한 것 — 플래너가 맥락(지시어·자산 상태)을 읽고 고른다(동적
> 라우팅 O), 그러나 다중 시퀀스 순서는 LLM 이 아니라 검증기의 생산자 삽입이었고 관찰
> 루프는 8턴 중 1회만 발동해 아무것도 바꾸지 않으면서 턴당 11.5초를 썼다. 이 격차를
> **인자 통로(LLM 이 무엇으로 실행할지도 정함)** 와 **자기 루프 에이전트(interview_prep)**
> 로 메웠다. 겸해서 대화 절반이 두 번째 턴부터 맥락을 잃던 치명적 버그를 찾아 고쳤다.
> 테스트 **247 → 308건**.

## 2. 실사용 E2E 검증 — 로그가 아니면 못 찾았을 결함들

브릿지·백엔드·MySQL 을 띄우고 실제 대화를 돌려 답변 산출 로그를 읽었다. 단위 테스트가
전부 통과하는 상태에서 다음이 나왔다.

### 2-1. 공고 추천에 **영구히** 도달 못 하던 문제

"자바 스프링 백엔드 신입 공고 추천해줘"를 두 턴 연속 요청했는데 추천이 한 번도 나오지
않고, `career_chat` 이 *"공고 데이터가 없어서 특정 회사를 짚기 어렵다"* 며 다른 플랫폼을
안내했다 — **실공고 2053건이 적재된 상태에서.** 원인이 두 겹이었다:

1. `job_recommend` 의 전제가 `("resume",)` 뿐이었다. `resume` 는 사용자 첨부라 생산자가
   없어 자동 삽입으로도 못 채운다 → 이력서 없는 사용자에게 이 에이전트는 영구 실행 불가.
   플래너 프롬프트에도 매 턴 "실행 불가"로 실려 나갔다.
2. 전제를 풀어도 빈 프로필로 매칭을 돌리면 전 후보가 "일치 0"으로 탈락해 추천이 통째로
   사라졌다.

**수정**: `AgentSpec.preconditions_any`("이 중 하나라도") 도입 → `job_recommend` =
이력서 **또는** 선호. 선호는 생산자(`preference_intake`)가 있으므로 빈 세션에서도
`preference_intake → job_recommend` 로 목표가 살아남는다. 이력서가 없으면 프로필을 만들지
않고(빈 프로필로 LLM 만 쓰는 낭비) 선호 기준으로 추천하며, **역량 일치를 계산하지 않았음을
명시**한다(0개를 "일치 0"으로 말하지 않는다).

### 2-2. 후속 질문 하나가 실행 큐를 죽이던 문제

오케스트레이터가 `followUpQuestions` 가 있으면 **무조건** break 했다. 그래서 선호 파악이
(추천에 필요 없는) 공고 URL 을 물으면서 바로 실행 가능한 `job_recommend` 까지 함께 죽었다.
→ 남은 큐에 지금 그대로 돌 수 있는 단계가 있으면 계속한다(`_queue_can_run_now`). 질문은
어차피 같은 답변에 실려 나가므로 사용자가 잃는 것이 없다. 뒤 단계의 전제를 물은 경우는
기존대로 멈춘다.

### 2-3. 신입에게 "경력 8년" 공고를 추천하던 문제

검색·랭킹 어디에도 연차 조건이 없어서 "신입"이라고 말해도 키워드만 맞으면 그대로 나갔다.
크롤링 데이터의 `experience` 표기(1743건에 93종)를 결정론 파서로 해석했다:

| 표기 | 요구 최소 연차 | 실데이터 |
|---|---|---|
| `신입` · `경력무관` · `신입·경력` · `신입-경력 3년` | 0 (신입 가능) | 314건 |
| `경력 3년` · `경력 3-8년` | 3 (범위는 **하한**) | — |
| `경력` (연차 미표기) | 1 (경력자 채용) | 856건 |
| 빈 값 · 해석 불가 | None → 거르지 않음 | 0건 |

작업 중 **자기 버그 2개**를 잡았다: ① `경력 3-8년` 을 상한 8로 읽어(`\d+년` 정규식이 년에
붙은 숫자를 집었다) 3년차를 잘못 걸러냈다 → 하한을 읽도록 수정. ② 정형 필드는 `경력` 인데
제목에만 `경력7년이상` 인 공고가 5년차에게 통과했다 → 제목의 명시 연차로 보강(`경력` 이
숫자에 붙은 패턴만 인정해 `창립 20년`·`2026년` 오탐 차단. 실데이터 22건 보강, 오탐 0).

실측: "저는 신입이에요…" → 추천 3건 전부 경력무관/신입·경력, 27건 제외를 답변에 명시.
"저는 경력 5년이에요…" → 5건 추천, `경력 7년 이상` 1건만 제외(과도 필터 아님).

## 3. 팀원 프로토타입과의 냉정한 대조 — "멀티에이전트" 당위성 점검

`Agent_Test`(팀원, LangGraph + `bind_tools` ReAct)와 우리 오케스트레이터를 같은 기준으로
비교하고, 실제 판단 궤적을 계측해 확인했다.

**동적 라우팅은 근거 있음.** 발화→에이전트 대응표가 코드에 없고(grep 0건), 플래너가 맥락을
읽고 고른다. 특히 `"아까 그거 말고 딴 데 없어?"` → `job_recommend`(대화 이력 없이는 불가),
`"이 공고 나한테 맞을까?"`(이력서 없음) → 원안 `fit_analysis` 확신 **0.3** → 검증기가
빼고 대화로 후퇴. 키워드 테이블로는 못 하는 판단이다. 팀원의 D9(입구 라우팅=LLM 동적,
결정적 분기는 별도)와 철학이 같다.

**멀티에이전트라 부르기엔 약했음.** 계측이 보여준 것:

- 한 턴에 둘 이상 돈 사례는 전부 **검증기의 생산자 자동 삽입**이었다. 실측:
  `PLANNER 원안=['job_recommend']` → `DISPATCH 확정=['preference_intake','job_recommend']`.
  LLM 이 다중 시퀀스를 계획한 경우는 8턴 중 0건.
- 관찰 루프가 실행을 바꾼 사례 0건. 턴 1 시간 분해(총 45.2초):
  플래너 7.5s → `preference_intake` 11.4s → **관찰#1 14.7s(continue)** →
  `job_recommend` **0.055s** → **관찰#2 11.5s(finish, 큐 비어 있음)**.
  실제 일은 55ms 이고 26.2초(58%)가 아무것도 바꾸지 않은 제어 호출이었다.
  게다가 `continue` 는 `trace.emit` 전에 빠져나가 **로그에 흔적조차 없었다.**
- LLM 자유도가 팀원보다 좁았다: 팀원은 `load_posting(url)`·`search_postings(job_name)`
  처럼 **인자까지** LLM 이 정하는데, 우리는 에이전트 이름만 고르고 인자는 세션에서 왔다.
- 에이전트 간 통신·독립 루프 없음(팀원 것도 동일 — 팀원은 "Agent + tools"라 부른다).

이 대조로 개편 순서를 정했다: **인자 통로 → 자기 루프 에이전트 → (추후) 자소서 전환 ·
Tool/Agent 분리 · 문서 갱신.**

## 4. 관찰 낭비 제거 + 판단 궤적 기록

- **남은 예정이 없으면 관찰하지 않는다.** 큐가 비면 continue/finish 가 결과가 같아
  관찰이 할 수 있는 일은 `call` 하나뿐인데 실측 효과가 0이었다. *대가*: 턴 마지막에
  관찰이 스스로 한 단계를 덧붙이는 길은 포기한다(시퀀스 **중간** call 은 유지 —
  기존 테스트를 중간 위치로 옮겨 능력 자체는 계속 검증한다).
- **아무것도 바꾸지 않은 continue 도 기록한다.** 남기지 않으면 "결과를 보고 다시 정했다"를
  사후에 증명할 수 없다 — 이 구조의 핵심 주장이 관측 불가였다.
- `dispatch` 이벤트에 `planChanged` 를 실어 **LLM 판단인지 생산자 삽입인지 로그로 구분.**
- trace 는 턴이 끝나면 사라지므로(SSE 중계·패널 조립용) **로그로도** 남긴다. uvicorn 이
  루트 로거를 설정하지 않아 INFO 가 전부 버려지고 있었다 → 브릿지에 `basicConfig` 추가.

실서버 로그(이제 항상 남는다):

```
planner:  원안=['job_recommend'] 확신=0.85 인자={'job_recommend': {'job_name': '데이터 엔지니어'}}
dispatch: 확정=['job_recommend']
agent:    job_recommend 완료 질문=[] 갱신=['recommendations']
observe:  skipped (남은 예정 없음) after=job_recommend
```

## 5. 개편 1단계 — LLM 이 인자까지 정한다

`AgentSpec.params`(이름, 설명)를 선언하면 플래너 manifest 에 실려 LLM 이 값을 채운다.
에이전트 이름 환각은 `Literal` 이, **인자 이름 환각은 검증기**(`validate_agent_args`)가
선언과 대조해 막는다. 에이전트별 동적 스키마는 피했다 — 공급자별 지원이 갈려 하네스가
약해지므로 평평한 목록으로 받고 검증은 코드가 한다.

`AgentSpec.params_satisfy` 로 **인자가 전제를 대신할 수 있음**을 선언한다: 발화에 직군이
있으면 그것이 곧 사용자가 밝힌 선호이므로 선호 수집 생산자를 끼우지 않는다.

실측: `"데이터 엔지니어 공고 찾아줘"` → 인자 `job_name='데이터 엔지니어'`,
`dispatch=['job_recommend']`(생산자 삽입 없음), **4.7초**(이전 경로 ~30초).
→ LLM 판단만으로 목표에 도달하는 경로가 생겼다(§3 의 첫 번째 약점 완화).

## 6. 개편 2단계 — 첫 자기 루프 에이전트(interview_prep)

**`agents/agent_loop.py`(재사용 계약)** — 역할 분담을 코드로 갈랐다:

- **도구** = 결정론 파이썬 함수. 정확해야 하는 것(소재 순위·근거 조회·답변 점검).
- **에이전트** = LLM. 자유도가 필요한 것(무엇을 쓸지·물을지·어떻게 말할지).
  **근거는 도구가 준 것만** 쓸 수 있다.
- **하네스** = 도구 이름 `Literal` 제한, 스텝 상한, 금지표현 검증, 스텝마다 trace + 로그.

**interview_prep**: 템플릿 한 방 → 질문 → 답변 → 점검 → **꼬리 질문**이 여러 턴 이어진다.
상태는 세션 자산 `interview`(asked/answers/usedTopics)로 보존돼 다음 턴이 이어받는다.
소재 선택은 **합리적 조건의 결정론 점수**이고 LLM 이 순위를 바꿀 수 없다:

| 조건 | 가중 | 왜 |
|---|---|---|
| 사용자 프로젝트에 실제로 등장 | +3 | 경험으로 답할 수 있다 = 연습 가치 최상 |
| 공고의 **필수** 요건 | +2 | 면접에서 확실히 다뤄진다 |
| 격차 심각도 high / medium | +2 / +1 | 위험한 격차 먼저 |
| 이력서에 기재만 되고 근거 없음 | +2 | 면접에서 찔리는 지점 |

실 LLM 궤적:

```
1턴: pick_material → "React,TS / 고른 이유: 프로젝트('MindConnect')에 실제로 등장 + 공고 필수 요건"
     → find_evidence → record_question
     면접관: "MindConnect 에서 React·TS 로 드래그앤드롭 UI 를 직접 구현하셨다는데,
              가장 어려웠던 기술적 문제와 해결 방법을 말씀해 주시겠어요?"
2턴: check_answer(결정론: React 언급 O, 수치 X, 역할서술 X)
     면접관: "React 언급은 있었지만 구체적 구현 방식·역할·수치가 없었어요.
              → 라이브러리 사용 여부와 상태 관리 방식은 어떻게 하셨나요?"   ← 꼬리 질문
     상태: 질문 2개 / 답변 1개
```

**루프 신뢰성 — 실측으로 드러난 자기 결함 2건 수정**

- 금지표현 1회로 기능이 폴백되던 문제: 목록에 `반드시`·`무조건` 같은 **코칭 문장의 일상어**가
  있어서 답변 점검 턴이 매번 템플릿으로 떨어졌다 → 위반 낱말을 알려주고 **한 번 다시 쓰게**
  한다. 계속 걸리면 그때 폴백(이유 기록).
- 실패 이유를 삼키던 문제: 루프가 `None` 을 돌려주면 호출부가 폴백을 만들며 warnings 를
  잃어 "왜 템플릿 답변이 나왔는지" 흔적이 없었다(진단에 시간을 썼다) → 항상 outcome 을
  돌려주고(reply 가 비면 실패) 폴백이 이유를 싣는다. 폴백도 이번 턴 도구 진행분(점검한
  답변·다룬 주제)을 보존한다.

## 7. 대화 세션 맥락 유실 (backend V7) — 다중 턴을 원천 차단하던 버그

면접 에이전트를 실서버로 검증하다 발견했다. 같은 대화(id 33)가 턴마다 다른 세션 키를
냈다: `conv-33-1785258705` → `conv-33-1785258706`. 두 번째 턴의 자산이 `['last_message']`
뿐 — 이력서·공고가 사라졌다.

**원인**: `Conversation.sessionId()` 가 `"conv-{id}-{createdAt 초}"` 를 매 요청 계산했다.
`@CreationTimestamp` 는 나노초까지 메모리에 담지만 `created_at` 컬럼은 `DATETIME`(소수점
없음)이라 MySQL 이 저장 시 **반올림**한다 → 대화를 만든 첫 요청(메모리 `08:11:45.6` → 45)과
이후 요청(DB 재조회 `08:11:46` → 46)의 키가 어긋난다. 즉 **소수점 .5 이상에 생성된 대화
(약 절반)가 두 번째 턴부터 맥락을 통째로 잃었다.** 에이전트가 이어서 판단할 수 없었고,
다중 턴 상태를 쓰는 새 에이전트는 아예 성립할 수 없었다.

**수정**: 시각 파생을 버리고 생성 시 한 번 정해 `session_id` 컬럼에 저장(V7).
계산하지 않으므로 흔들릴 수 없다. 실측: 같은 대화의 두 턴이 `conv-0e116184…` 로 동일,
2턴에서 `resume`·`history` 자산이 보인다.

> 교훈: 값을 **파생**하면 파생 입력의 정밀도까지 계약이 된다. 키처럼 안정성이 본질인
> 값은 계산하지 말고 저장한다.

## 8. 방향 정정 · 문서

- **공고 URL 입력**: 프로토타입은 URL → 크롤링 DB 키 조회였고 0728 오전에 그대로 이식했지만,
  제품 방향은 다르다 — 사용자가 특정 공고를 가리킨 것이므로 DB 스냅샷이 아니라 **그 URL 의
  현재 내용을 수집·파싱**한다(마감·수정 반영). 공고 DB 는 검색·추천 경로에만 쓴다.
- **대안 공고 노출**: 중·하 등급이면 그래프가 이미 `find_alternatives` 를 돌리고 있었는데
  (`route_after_roadmap`) 결과가 답변에 실리지 않아 계산만 하고 버려졌다. `AlternativeJob.url`
  을 추가하고 답변에 싣는다(실측: 등급 하 0.32 턴에서 실공고 3건이 URL 과 함께).
- **README**: 실행 방법을 4단계로 재작성(203→135줄). LLM 은 `claude_code`(무과금·느림)와
  GMS(`openai`, 과금·빠름·토큰 스트리밍) 중 택일로 안내. `develop` 머지로 백엔드 설정이
  환경변수 필수로 바뀐 것(`backend/.env` + `local` 프로필)도 반영 — 실제로 그대로 따라가다
  `Could not resolve placeholder 'JWT_SECRET'` 기동 실패를 재현해 잡았다.

## 9. 남은 것 (개편 3~5단계)

1. **`coverletter_draft` 를 같은 틀로 전환** — 초안 → 자기비판 → 근거 보강 → 재작성 루프.

   사실상 도구다. 지금은 `AgentSpec` 하나로 뭉뚱그려 결정론이라 정확해야 할 것과 자유도가
   필요한 것이 같은 취급을 받는다.
3. **문서 갱신** — `_docs/agent/멀티에이전트_구현_평가_및_개선방안.md` 의 "엄밀히는 지능형
   라우터 + 파이프라인" 판정을 2단계 결과에 맞게 다시 쓴다.
