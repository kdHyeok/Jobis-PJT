# AI 에이전트 구현 작업 로그 (0720)

이 문서는 `check_profile_completeness` 결측 필드 정리부터 시작해, `gap_matcher`의 비교
항목을 `techStack`/`domainKeywords`/`seniority`까지 확장하고, 판정 정책(기재만 된 스킬
인정)을 바꾸고, **SSAFY GMS(API 게이트웨이)로 LLM·임베딩을 실제 연결**한 뒤, 그 실측
데이터를 근거로 도메인 키워드·서술형 요구사항 2차 매칭을 **임베딩에서 LLM 구조화 출력으로
교체**하기까지의 작업 내역을 정리한다.

> **핵심 성과**: `gap_matcher`가 실제 GMS(OpenAI 호환) LLM/임베딩과 연결됐고, 비교 대상이
> 요구사항 문장뿐 아니라 `techStack`/`domainKeywords`/`seniority`까지 넓어졌다. 단, 실측
> 결과 임베딩이 "짧은 텍스트 간 주제 관련성" 판정에 못 미더워, **`analyze_gap`(판단 계층)이
> 이 태스크 한정으로 LLM을 호출하게 됐다** — §0 3계층 원칙("판단 계층 LLM 금지")의 의도적·
> 국소적 예외다. 상세 근거는 `docs/troubleshooting.md` 2026-07-20 항목.
>
> **이어서 작업할 사람은 §10(다음에 이어서 할 일)부터 읽으면 된다.**

## 2. `check_profile_completeness` — projectType 선택지 정리

- `profile_completeness.py`의 `projectType` 결측 질문 선택지를 4개(`팀 프로젝트`/`개인 프로젝트`/`부트캠프 프로젝트`/`사이드 프로젝트`) → **2개**(`팀 프로젝트`/`개인 프로젝트`)로 축소. 사이드 프로젝트는 개인으로 흡수.
- 부트캠프는 애초에 `projects`가 아니라 별도 `bootcamp` 리스트(`BootcampEntry`)로 관리되고 있어 `projectType`에 있는 게 중복이었음 — 제거가 스키마와도 더 맞음.
- `graph/nodes.py`의 프로필 추출 LLM 프롬프트(§ `projectType(팀 프로젝트/개인 프로젝트/부트캠프 프로젝트 등)`) 예시도 동일하게 2개로 동기화.

## 3. `gap_matcher` 비교 항목 확장 — techStack / domainKeywords / seniority

기존엔 `gap_matcher.match()`가 공고의 `requiredRequirements`/`preferredRequirements`(자유
서술 문장)만 비교 대상으로 받았다. `techStack`/`domainKeywords`/`seniority`는 추출은 되는데
비교엔 안 쓰이는 죽은 데이터였음 — 이걸 비교 대상에 포함시켰다.

### 3.1 `_build_comparison_requirements` 신설 (`graph/nodes.py`)

공고의 이질적인 데이터(문장 목록/키워드 목록/사다리 값 하나)를 `gap_matcher`가 먹을 수 있는
공통 형태(`{requirementId, text, type, kind?}`)로 변환하는 접수처. `check_sufficiency`와
`analyze_gap` 둘 다 이 함수 하나를 공유해 두 노드의 판단 기준이 어긋나지 않게 했다.

- **`_tech_stack_requirements`**: techStack 항목 → `kind` 없는(=1차 정확매칭 경로) 합성
  요구사항, `type="preferred"`. 이미 요구사항 문장에 언급된 기술은 `skill_taxonomy.find_in_text()`로
  대조해 중복 제외(같은 스킬 두 번 판정 방지).
- **`_domain_keyword_requirements`**: domainKeywords → `kind="domain_keyword"`,
  `type="preferred"`.
- **`_seniority_requirement`**: `posting.seniority`가 있을 때만 `kind="seniority"`,
  `type="required"` 합성 요구사항 1건. `roleCategory`도 같이 실어서 연차 계산 시 무관 경력을
  걸러낼 기준으로 씀.

### 3.2 `experience_estimator.py` 신규 — 사용자 경력 개월수 추정

`gap_matcher`가 연차(seniority)를 비교하려면 사용자 쪽 "총 경력 개월수"가 필요한데, 기존엔
이걸 계산하는 로직이 아예 없었다. 순수 룰(LLM 미사용)로 신규 작성:

1. `experiences` 항목의 `role`/`summary`에 "3년 2개월" 같은 **명시적 문구**가 있으면 그대로 사용
2. 없으면 `period`를 날짜 구간("2022.03 - 2023.08", "2022.03 ~ 현재" 등)으로 파싱해 계산
3. 둘 다 실패하면 그 항목은 결측 — **결측이 하나라도 있으면 총 연차는 `None`**(0이 아님, "모른다"와 "없다"를 구분)
4. **직군 관련성 필터**: `role_taxonomy.classify_role()`로 각 경력의 직군을 재분류해, 공고
   직군과 **같은 직군만** 합산 대상으로 삼는다. 다르거나 못 정하면 **둘 다 제외**(보수적).
   예: 백엔드 공고에 미술학원 강사 경력이 섞여 있어도 정확히 제외됨(실측 확인).

### 3.3 `gap_matcher`에 3차/4차 매칭 경로 추가

- **3차 도메인 키워드**: 처음엔 "포함 매칭(룰)만" → 이후 §7에서 LLM 폴백으로 확장(아래 참고).
- **4차 연차 사다리**: `_match_seniority` — `experience_estimator`로 관련 경력 개월수 추정 →
  `role_taxonomy.seniority_from_years()`로 사다리 위치 환산 → 공고 요구 사다리 위치와 비교
  (`met`/`partially_met`/`not_met`). 연차를 못 정하면 `not_met`이 아니라 `uncertain`.

## 4. 판정 정책 변경 — "이력서에 기재만 된 스킬"도 met 인정

기존 설계는 "이력서 기술스택 나열은 주장일 뿐 증명이 아니므로 met을 주지 않는다"였는데,
**팀 결정으로 뒤집었다**: 사용자가 자기 이력서에 직접 적은 스킬은 근거 문장이 없어도
"쓸 수 있다"고 인정한다.

- `_match_by_skills`: met 판정 기준을 `evidenced_ratio`(근거 있는 것만)에서
  `matched_ratio`(근거 있음 + 기재만 됨 합산)로 변경.
- **`confidence`는 여전히 차등**: 근거 있는 스킬=만점, 기재만 된 스킬=절반 가중치. 판정은
  통과시키되 신뢰도 차이는 남긴다.
- `_reason_for_skills`: met이어도 "근거로 확인됨"과 "기재된 보유 스킬로 인정(근거 없음)"을
  문장에서 항상 구분해서 서술(판정-설명 모순 방지).
- `sufficiency_rules._unevidenced_claimed_skills`: 기존엔 `partially_met`만 후보로 봤는데,
  이제 `met`도 포함하도록 확장(판정은 통과했어도 근거 보강 질문은 비블로킹으로 계속 던짐).

## 5. `skill_taxonomy` — 사전에 없는 스킬명 임베딩 유사도 폴백

"비슷한 스킬명을 동일 취급하는 걸 LLM으로 하자"는 요청에 **하이브리드로 절충**: 사전(룰)이
여전히 먼저(무료·즉시·결정론), 사전에 없는 표기만 임베딩 유사도로 보조 판단.

- `resolve()` → 사전 조회 실패 시 `_resolve_by_embedding()` 호출. 표준 스킬명 전체와
  코사인 유사도 비교, **0.85 이상**(gap_matcher의 0.75보다 엄격 — "관련"이 아니라 "동일"이라고
  단정하는 자리라서)일 때만 인정.
- **버그 예방**: `get_skill_taxonomy()`가 `lru_cache`로 프로세스당 1개 인스턴스라, `__init__`에서
  embedder를 한 번 잡아두면 나중에 provider를 바꿔도 낡은 embedder를 계속 쓰게 된다
  (`gap_matcher.get_gap_matcher()`가 캐시를 안 거는 것과 같은 이유). `_resolve_by_embedding`
  안에서 매번 `get_embedder()`를 새로 호출하도록 설계.
- mock 임베더로 매칭/비매칭 양쪽 경로 검증 완료. **실제 GMS 데이터로는 아직 검증 안 함**(§10 참고).

## 6. RAG hook① 재분류 — 기업 맥락은 RAG가 아니라 크롤링 정형 DB

과거 팀 논의를 반영: `fetch_company_context`(기업 인재상·기술문화·후기)는 벡터 RAG로
구현하지 않기로 결정됨 — 이런 콘텐츠를 실제로 공개하는 회사는 사실상 대기업뿐이라 대상이
유한·식별 가능해서, 크롤링 + 정형 DB로 미리 채워두고 조회하는 방식이 맞다는 판단.

- `docs/agent-derivation-and-tools.md` §1/§2/§3.5/§4/§4.3 전체 갱신: "RAG는 2곳" →
  "**1곳**(hook②만)", hook①을 "RAG를 안 쓰기로 결정한 것" 표로 이동.
- **코드는 안 바뀜** — `RagAdapter.fetch_company_context` 계약(`rag.py`)과 hook 이름은
  그대로 두고, 구현체만 나중에 크롤링+정형DB 어댑터로 교체하면 되는 구조라서.
- 팀 결정 사항이라 memory에도 별도 기록(`rag_hook1_company_context_plan`).

## 7. GMS(SSAFY API 게이트웨이) 연동 — LLM/임베딩 실제 호출

**2026-07-20부터 이 프로젝트의 LLM·임베딩 호출은 GMS 경유로 통일.** `GMS_KEY` 하나로 챗(LLM)과
임베딩 둘 다 인증.

### 7.1 설정/코드 배선

- `config.py`: `Settings`에 `gms_key`/`llm_base_url`/`llm_model`/`embed_base_url`/`embed_model`
  필드 추가. `has_llm_key`/`has_embed_key`를 provider별로 분기.
- `llm.py`: `LLM_PROVIDER="openai"` 분기 추가 — `ChatOpenAI(base_url=..., api_key=GMS_KEY)`.
  기존 `run_structured`/`nl_render` 등은 LangChain 표준 인터페이스만 쓰므로 **코드 변경 없이**
  그대로 이 provider로 동작.
- `embed.py`: `EMBED_PROVIDER="openai"` 분기 추가 — `embed_impl/gms_openai.py`의
  `GmsOpenAIEmbedder` 연결.
- `pyproject.toml`: `langchain-openai`, `openai` 의존성 추가, venv에 설치.
- `.env`/`.env.example`: `GMS_KEY`, `LLM_PROVIDER=openai`, `LLM_BASE_URL`, `LLM_MODEL=gpt-5-nano`,
  `EMBED_PROVIDER=openai`, `EMBED_BASE_URL`, `EMBED_MODEL` 추가. 엔드포인트는 전부
  `https://gms.ssafy.io/gmsapi/...`로 시작(하드코딩 없이 환경변수로만 읽음).

### 7.2 `embed_impl/gms_openai.py` — 구현 중 실제로 잡은 버그

1차로 표준 라이브러리 `urllib`로 직접 구현했는데, **실제 GMS 응답에서
`http.client.IncompleteRead`가 발생**했고 이게 이 모듈의 "절대 예외를 던지지 않는다" 규칙을
깨는(잡히지 않는) 버그였다. 원인 조사 대신, 이미 `langchain-openai`의 의존성으로 설치돼
있던 공식 `openai` SDK(httpx 기반, 전송 계층이 훨씬 견고함)로 교체해 해결.

### 7.3 실측 검증

- 임베딩: `client.embeddings.create(...)` 실제 호출 성공, 1536차원 벡터 확인.
- LLM: `ChatOpenAI` 인스턴스 생성·`base_url`/`model` 배선 확인, 미설정 시 에러 메시지도
  provider별로 정확히 분기됨을 확인.

## 8. 임베딩 실측 → 신뢰도 부족 확인 → LLM 구조화 출력 폴백으로 전환

GMS 임베딩이 실제로 붙은 김에 `domain_keyword`/서술형 요구사항 2차 매칭을 임베딩으로
구현하려 했으나, **실측 결과 신뢰할 수 없다고 확인**됐다. 상세 데이터·조사 과정은
`docs/troubleshooting.md` 2026-07-20 항목에 전문 기록. 요지만 적으면:

```
0.271  [관련]  '이벤트 드리븐 아키텍처 설계 경험' <-> 'Kafka 비동기 메시지 처리'
0.364  [무관]  '이벤트 드리븐 아키텍처 설계 경험' <-> 'React 프론트엔드 UI 개발'   ← 무관이 더 높음
```

- `text-embedding-3-small`/`-large` 둘 다, 키워드 확장(짧은 단어 → 짧은 문장)을 해봐도 같은
  역전 패턴 재현. 모델 크기·쿼리 길이 문제가 아니라 **이 태스크 자체가 범용 임베딩에 약함**으로 결론.

### 8.1 `semantic_judge.py` 신규 — §0 원칙의 의도적·국소적 예외

- `judge_domain_relevance(topic, evidence_texts) -> list[int] | None`
- **구조화 출력**(관련 문장의 인덱스 배열만) — 자유 서술 금지, 이유를 지어내지 못하게 막음.
- 기존 읽기 계층 인프라(`structured.run_structured`) 재사용 — 새 LLM 호출 경로를 안 만듦.
- LLM 미설정/실패 → 예외 대신 `None`("모른다") 반환.
- 모듈 상단에 "왜 이 한 곳만 §0 예외인지"(실측 근거)와 "이 패턴을 다른 판단 노드로 넓히지
  말 것"을 명시.

### 8.2 `gap_matcher.py` 리팩터링

- `_match_by_embedding`, `_EMBED_MET`/`_EMBED_PARTIAL`, `self._embedder`(및 `get_embedder`
  import) **전부 삭제** — gap_matcher는 더 이상 임베딩을 쓰지 않는다.
- **`_llm_semantic_match(topic, evidences)`** 신설 — 2차(서술형 요구사항)와 3차(도메인 키워드
  포함 매칭 실패 시 폴백)가 공유하는 헬퍼. 이진 판정만 가능(met/not_met, LLM은 등급을 안 매김).
- `Match.method`에 `"llm_semantic"`/`"undecidable"` 추가해 추적성 유지.

### 8.3 실측 재검증 (같은 Kafka/React 케이스)

```
'이벤트 드리븐 아키텍처 설계 경험' → met, matched=[ev-2(Kafka)]   — ev-1(React)은 정확히 제외
'블록체인 스마트 컨트랙트 개발 경험' → not_met                    — 무관한 요구사항은 정확히 걸러짐
```

## 9. 부수적으로 잡은 버그 — 테스트가 실제 GMS API를 호출하고 있었음

GMS 연결(`.env`에 실제 `GMS_KEY` + `EMBED_PROVIDER=openai`) 이후 `pytest`가 3초 → 33초로
느려짐. `tests/conftest.py`가 `get_llm`만 미설정으로 강제하고 있었고 **임베딩은 아무도 막고
있지 않아서**, 기존 임베딩 관련 테스트가 전부 진짜 네트워크 호출을 하며 결과도 실제 점수
기준으로 달라져 있었다(`NullEmbedder` 가정 assertion이 깨짐).

- **해결**: `conftest.py`에 `force_null_embedder` 픽스처 추가 — `jobis_ai.skill_taxonomy.get_embedder`를
  `NullEmbedder`로 강제 패치(`from x import y` 바인딩이라 원본 모듈 하나만 패치해선 안 먹힘,
  참조하는 모듈에서 직접 패치해야 함). `gap_matcher`는 §8.2에서 임베딩 자체를 제거해 별도 패치
  불필요해짐 — `force_mock_llm`이 `semantic_judge`까지 같이 막아준다.
- **교훈**: 외부 API를 하나 연결할 때마다 "테스트가 그걸 진짜로 호출하지 않는지"를 반드시
  같이 확인해야 한다.
