# 2026-08-01 — 정리 도구를 대화형 담당으로 승격 · 봉인 · 대체군 · 평가 판별력 · 답변 품질 측정 (D97~D108)

## 발단 (실측 1건 + 감사 1건 + 외부 리뷰 1건)

1. **로그 실측**: 공고를 정리한 뒤 사용자가 "이 공고 기준으로 어떤 스택을 공부하고 어떤
   프로젝트를 하면 좋을까"를 물었다. 어휘 11종에 그 질문의 담당이 없어 플래너가
   `fit_analysis`→`application_plan` 을 골랐고, 이력서가 얇아 5개를 되묻고 `analysis` 를
   못 내 `application_plan` 이 전제 붕괴로 빠졌다(`요청 미완수 — application_plan`).
   **공고만으로 답할 수 있는 질문에 사용자 정보를 요구했다.**
   → 라우팅 결함이 아니라 **어휘의 빈칸**이었다. 플래너는 가진 것 중 최선을 골랐다.
2. **감사 문서 주장(D-9 회귀)**: 짧은 발화가 저장 이력서를 파괴하는 경로가 다시 열렸다.
3. **외부 리뷰**: 출력 두 개를 보고 파싱·추론·평가 전반을 지적.

## 오늘 내린 결정 (상세는 docs/decisions.md)

- **D97** `posting_analysis`·`resume_diagnosis` 를 도구 → **대화형 담당**으로 승격.
  근거는 원문·파싱 사실에 봉인(§2-5), 표현에만 자율성. LLM 없으면 승격 전과 동일 폴백.
- **D98** 짧은 텍스트는 저장된 이력서를 교체하지 못한다. 가드를 **입구가 아니라 합류점**에.
- **D99** 대체 가능한 기술은 **요구사항 하나로 센다** — 부푼 분모가 등급을 왜곡했다.
- **D100** 실 대화 검증에서 나온 3건 — 요청 문장 보존 · 이력서 판별 · 턴 계획 통보.
  셋 다 "지시가 안 지켜진 것"처럼 보였지만 실제로는 **에이전트에게 사실이 도달하지 않았다.**
- **D101** 평가 케이스는 **판별력을 검증한 뒤에** 센다 — 승격 전 선언을 주입해 되돌려 돌린다.
- **D103** 답변 품질은 **지표 두 개로** 잰다 — 하나는 서식에, 하나는 내용에 걸린다.
- **D104** 제안은 **커버하는 요구사항 ID 를 대야 기록된다** — 도구가 거부한다.
- **D105** 요구 연차 **상한을 보존한다**(판정에는 아직 쓰지 않는다).
- **D106** 제네릭 점수 평가셋을 공고 8개로 — **노이즈 바닥을 쓸 수 있게** 만들었다.
- **D107** 평가셋을 **실공고**로 + 지표 대칭(`_content_only`) + 하네스 진행 인쇄.
  **가설 하나가 틀렸다** — 실공고 기준선이 합성보다 *높다*(서식 상용구).
- **D108** 기준선은 **파서가 뽑은 요구사항**이고 답변 쪽 근거와 **대칭**이어야 한다.
  "비정형 칸을 추가해야 하나"의 답은 **아니다** — 있는 칸(`jobTitle`·`domainKeywords`)을 안 썼다.
  (D102 는 다른 사람의 결정 — URL 은 열어 본 뒤에 공고가 된다.)

## 축별로

### 승격 (D97)

| | 전 | 후 |
|---|---|---|
| `posting_analysis` | 도구 — 요건 요약만, 대화 못 함 | 에이전트 — 공고 질문 전담(학습 순서·프로젝트 제안 포함) |
| `resume_diagnosis` | 도구 — 항목화 사실만 | 에이전트 — **강점 서술**·보강 방향·원문 확인 |

- 루프의 근거는 도구가 준다: `read_posting` / `read_resume`(원문 키워드 검색, 공용 헬퍼
  `_common.grep_source_lines`). **못 찾으면 못 찾았다고 돌려준다** — 빈 관찰을 주면 LLM 이
  그 자리를 사전지식으로 채운다.
- 새 어휘 0개. 사용자 제안(`posting_prep` 신설안을 접었다)이 §3-1 과 맞았다.

**한 번 틀리고 고친 것 — 같은 목록이 두 번 나갔다.** 첫 구현은 결정론 요약 표를 앞에 붙이고
루프가 뒤를 이어 쓰게 했는데, 실측에서 루프가 같은 요건을 611자로 다시 정리한 뒤 제안을
붙였다. goal_system 에 "다시 나열하지 말라"고 적어 뒀지만 안 지켜졌다 —
**한 문장의 생산자가 둘이면 프롬프트로 못 막는다**(§2-2). 표를 폴백 경로에만 남겼다.

**같이 잡은 버그**: 한 턴에 공고 2개를 냈을 때(D94) 루프가 두 번째를 몰랐다 —
`posting_library` 는 턴 끝에 반영되므로 같은 턴의 `extraPostings` 를 직접 얹었다.

### 화이트보드 — 대부분 **안 만들었다** (D97 §3~4)

계획은 "정리 산출물을 자산으로 승격"이었는데 코드를 보니 `ASSET_KEYS` 에 `profile`
(skillEvidence 포함)·`posting_summary`·`posting_library`·`analysis`·`last_message` 가 전부
있고 저장된다. 승격한 두 루프의 "정리"는 그 자산의 **파생 뷰**라 따로 저장하면 출처가 갈린다.

- `produces=("posting_summary", …)` 선언 → **안 했다.** 그 자산을 `preconditions` 로 필요로
  하는 에이전트가 없어서, 선언하면 검증기 자동 삽입·`redundant` 드롭만 바뀐다(라우팅 변경 +
  재측정 비용, 기능 이득 0).
- `resumeSummary` 별도 저장 → 안 했다. `profile` 에서 결정론으로 파생된다.

**대신 실제 결핍은 하류의 *읽기* 쪽이었다.** `coverletter_draft` 의 facts 에 회사명·직무가
아예 없어 **어느 회사에 내는 자소서인지 모르고** 초안을 썼다. `application_plan` 은 읽으려
했지만 `session["job_posting"].get("company")` 로 찾아 늘 빈 값이었다(그 자산은
`{sourceType, value}` 원천이라 회사명 칸이 없다). 공용 읽기 함수
(`_common.posting_identity`, 출처 `posting_summary` → `analysis`)로 합쳤고 `interview_prep`
도 같은 입력을 받는다. 없으면 빈 문자열로 두고 언급하지 않는다(회사명 추측 금지).

> **교훈**: "자산을 공유하게 만들자"는 과제가 실제로는 "이미 있는 자산을 읽지 않는다"였다.
> 저장 계층을 늘리기 전에 소비자가 무엇을 읽는지 grep 하는 것이 순서다.

### 사고 경로 봉인 (D98) — 감사 판정은 정정했다

**코드 사실 2건은 맞다**: `resolve_kind` 는 40자 미만이면 claimed kind 를 그대로 돌려주고,
`_apply_attachments` 는 그걸 믿어 `stage({"resume": …, "profile": None, "analysis": None})`
로 **조건 없이 교체**했다. 자료 요청 슬롯이 열린 동안의 "네" 한 줄이 이력서와 파생 자산을
지운다.

**판정("최우선·경로 열림")은 과대평가**: v2 계약에 `attachments` 필드가 없고(백엔드는
messages + CareerSummary 만 보낸다), v2bridge 가 첨부를 합성하는 `promote_pasted_posting`
은 `len(text) >= _POSTING_MIN_CHARS` 게이트를 통과해야 한다. 열린 입구는 webbridge
`/chat` 하나이고 이 브랜치에서 띄우지 않는다. **지금 터질 사고가 아니라 입구가 하나 생기면
터지는 결함.**

**그래도 고친 이유는 심각도가 아니라 위치다.** 방어가 입구 두 곳에 흩어진 길이 상수로
우연히 성립하고 있었다. 모든 입구가 합류하는 `_apply_attachments` 에 한 줄이 입구마다의
검사보다 작다. `MIN_ASSET_CHARS` 를 공개해 "판정을 포기하는 경계"와 "믿지 않는 경계"가 같은
값을 보게 했다. 되돌린 텍스트는 **버리지 않고 발화로** 합친다 — 버리면 동의가 사라진다.
짝으로 `posting_analysis` 의 이력서 요청 카드에 `hasResume` 게이트(있는 것을 다시 청하지
않는다 = 슬롯을 열지 않는다).

### 대체군 (D99)

`skill_taxonomy._ALTERNATE_GROUPS`(5군) + `_tech_stack_requirements` 가 같은 군을
`anyOf: True` 요구사항 **하나**로 묶고, `gap_matcher._match_by_skills(any_of=True)` 는 하나만
충족돼도 met + **나머지를 missing 으로 세지 않는다**(분모도 1).

문제는 표시 숫자가 아니었다 — 항목마다 만든 합성 요구사항이 `_score_basis.techSkill` 의
**분모**가 되고, pgvector 만 아는 지원자가 벡터DB 자리에서 1/5 로 깎여(met 경계 0.8)
`overall_fit` 의 등급이 낮아지고, 낮은 등급은 `observe_rules ① 약한 판정` 을 발동시켜
사용자가 **청한** 자소서·면접을 큐에서 뺀다. 잘못된 산수 하나가 요청 거절까지 이어진다.

표준화와 다른 연산임을 코드 주석에 못 박았다 — 키를 합치지 않는다(pgvector ≠ Pinecone).
군에서 하나만 요구됐으면 묶지 않는다(대체가 아니라 지목). Kafka~RabbitMQ,
Kubernetes~ECS 는 제외했다(§3-1 — 갈리는 판단을 사전에 못 박지 않는다).

### 외부 리뷰 — 받은 것과 안 받은 것

**받음**: OR→AND 평면화(D99), HTML 노이즈 화이트리스트 부재(진단 정확 — `skill_taxonomy` 는
표준화만 하고 "이 토큰이 이 직무의 스킬인가"를 묻는 계층이 없다), 연차 상한 소실
(`grep maxYears src/` → **0건**, `minYears` 15곳), 제안 스키마 고정(소요 기간 제외),
**제네릭 점수**(출력 간 유사도 — 가장 좋은 아이디어).

**안 받음**: "우선순위 = 필수여부 × 갭 크기 ÷ 학습 비용", 제안마다 "예상 소요" 필드 —
학습 비용·소요 기간은 데이터가 없고, LLM 이 지어낸 값을 공식에 넣으면 **감이 결정론처럼
보이는 점수**가 된다(§2-1). "프롬프트에 근거 명시를 강제하라"도 안 받았다 — §2-2·§3-1 이
실측으로 부정한 방법이다(구조적 버전은 리뷰의 다른 문단이 말한 필수 스키마 필드).

**사실이 틀린 항목**: "갭 매트릭스를 만들라"(=`fit_analysis`+`gap_matcher`, 이미 있음),
"6워커로 나누라"(=현 구조), "아마 한 번의 호출로 전부 처리"(로그가 반박 — 한 턴에
`attachment_kind×1, agent_planner×1, parse_job_posting×1, posting_analysis×1`, 티어 분리).
출력 두 개만 보고 내부를 추정한 결과다.

### 실 대화 검증 (D100) — §3-7 "단위 테스트만으로는 부족하다"

`/v1/chat` 으로 실 모델을 태워 3건을 확인했다. **단위 테스트가 못 잡은 결함 셋이 나왔다.**

| # | 증상 | 진짜 원인 | 수정 |
|---|---|---|---|
| ① | 공고 + "뭘 공부할까" → **요약만** 돌아옴 | `promote_pasted_posting` 이 발화를 비워 **질문이 첨부 속으로 삼켜졌다** | `_trailing_request` — 꼬리 요청 문장을 발화로 남긴다 |
| ② | 이력서 + "강점 정리해줘" → **career_chat** 이 답함 | 평범한 이력서가 판별 안 돼 자산 승격 실패. 플래너는 `resume_diagnosis` 를 정확히 골랐다(0.95) | 서술체 신호 추가(`재직중`·`담당했`…) |
| ③ | "적합도는 제가 못 해요" **직후** 등급이 나옴 | 에이전트가 **이번 턴 계획을 모른다** | `_planThisTurn` + `others_this_turn()` |

①에서 **처음에 goal_system 을 고쳤다가 되돌렸다** — 프롬프트가 안 지켜진 것으로 오진했다.
`facts` 를 먼저 찍어봤어야 했다. ②는 **D68 이 막으려던 사고(career_chat 이 이력서 원문 위에서
즉흥 조언)가 다른 입구로 재현된 것**이고, 그 답에 근거 없는 시장 주장이 섞여 있었다.

> **교훈**: ①②③ 모두 "지시가 안 지켜진 것"처럼 보였지만 실제로는 **에이전트가 그 사실을
> 갖고 있지 않았다.** 없는 사실은 지시로 메울 수 없다 — §2-2 의 대우(對偶)다.
> **프롬프트를 의심하기 전에 facts 를 찍어본다.**

수정 후 실측 결과:
- ① 학습 순서 + 프로젝트 3안이 나오고, 택일 관계를 유지("중 하나"), 근거는 공고에서만
  ("공고에 '상담' 키워드 있음")
- ② `resume_diagnosis/agent_llm` 이 답하고, 이름만 있는 스킬을 **"결함이 아니라 보강 여지"**
  로 말한다(§2-1 지시 준수). 근거 없는 시장 주장 사라짐
- ③ "적합도 분석은 **다른 담당이 이어서 답해드릴게요**" 로 매끄럽게 넘김
- **D99 가 판정 경로에서 동작**: "총 14개 요구사항"(묶기 전이면 22+),
  "Airflow·Dagster·Prefect **중 하나 이상** 운영 경험 충족"

### 평가 판별력 (D101) — 새 케이스가 무언가를 **잡을 수 있는지** 먼저 확인했다

승격 케이스 4건을 추가하고 3/3 통과를 받았다. 그대로 두면 "승격이 검증됐다"의 근거가 됐을
것이다. 승격 전 description 을 주입해 다시 돌리니 **4건 모두 여전히 통과** — 판별력이 0 이었다.

원인은 **자산 설정**이었다. 원래 실패 턴의 자산은 `[... job_posting, resume]` — **이력서가
있었다.** 나는 `["job_posting"]` 만으로 케이스를 만들었고, 공고만 있는 상황은 애초에 라우팅이
맞던 쪽이다. 갈림길은 이력서가 있을 때다(그때 플래너가 무거운 판정으로 끌려간다).

| 케이스 | 자산 | 승격 전(주입) | 승격 후 |
|---|---|---|---|
| `posting-study-plan` | resume+job_posting | **ASK 3/3**(fit_analysis 동의 게이트) | posting_analysis 3/3 |
| `posting-study-plan-with-analysis` | +analysis | **application_plan 3/3** | posting_analysis 3/3 |
| `posting-detail-question` | job_posting | posting_analysis 3/3 | posting_analysis 3/3 (판별력 없음) |
| `resume-strengths-with-posting` | resume+job_posting | resume_diagnosis 3/3 | resume_diagnosis 3/3 (판별력 없음) |

판별력 없는 두 건은 지우지 않고 `note` 에 **없다고 적었다** — 다음에 description 을 좁히는
사람이 그 라우팅을 깨지 않게 잠가 두는 값이지만, 승격의 근거로 세면 안 된다.

> **이 실패가 드러낸 더 큰 것**: `posting-detail-question` 이 승격 전에도 통과했다는 사실은
> **승격이 바꾼 큰 부분이 라우팅이 아니라 답의 내용**임을 뜻한다. 같은 담당에게 갔어도 전에는
> 요약만 냈다. 그 차이는 플래너 하네스가 **원리적으로 못 잰다** — 답변 품질 하네스가 따로
> 필요하다. 그게 다음 작업(제네릭 점수)인 이유다.

# 같은 날 · 두 번째 갈래 — URL 공고 검증 · 구조 리뷰 (D102)

구조를 읽어 나가며 나온 질문들에서 결함 하나와 설계 판단 둘이 나왔다.

## 1. 고친 것 — URL 을 열어 보지도 않고 공고로 확정했다 (D102, `9a790d4`)

**발단**: "URL 을 공고로 못박는 건 위험하지 않나" 라는 질문. 확인해 보니 그대로였다 —
`detect_posting_urls` 는 정규식 `findall` 이 전부고 **내용을 한 글자도 보지 않는다**(D62 가
"URL 은 공고 전용"으로 정한 결과). 위키·기사·회사 소개 링크도 공고 자산이 된다.

**진짜 피해는 오판이 아니라 파괴였다.** `chat.py` 가 URL 을 스테이징할 때
`analysis: None`·`posting_summary: None` 을 함께 건다 — **페이지를 열어보기도 전에 기존
적합도 분석이 날아간다.** 공고가 아닌 링크였으면 아무 이득 없이 자산만 잃는다.

**고친 자리는 `_common.ensure_posting_text`** — 검출 시점에는 주소밖에 없어 판단할 재료가
없고, 본문을 손에 쥐는 첫 지점이 여기다. 그리고 `posting_fetch` 뿐 아니라
`posting_analysis`·`fit_analysis` 도 이 함수로 수집하므로 **한 곳이면 세 소비자가 다 덮인다**
(호출부마다 가드를 다는 것보다 작은 diff이고, 빠뜨릴 호출부도 없다).

**새 배관은 만들지 않았다** — 승격 거부가 기존 수집 실패 경로를 그대로 탄다
(`fetched=False` → render → followUp 카드 → 관찰 규칙 `preconditions_broken`).
다만 **문구는 갈랐다**: "못 읽었다"고 말하면 사용자는 같은 링크로 재시도하고 같은 결과를 받는다.

**문턱은 일부러 느슨하다**(공고 어휘 하나만 맞아도 통과). 진짜 공고를 거절하는 쪽이 훨씬
아프기 때문이다 — 주 흐름이 통째로 막힌다. 정밀 판별은 뒤의 `posting_analysis` 가 LLM 으로 한다.

플래너 manifest 불변 → 재측정 대상 아님. `tests/test_posting_fetch.py` 4건.

## 2. 고친 것 — `_common` 요약이 파일을 잘못 소개하고 있었다 (`479975a`)

"이 파일은 이력서 에이전트 헬퍼만 모은 것인가"라는 질문이 나왔는데, 첫 줄 docstring 이
헬퍼 2개(`ensure_profile`·`agent_arg`)만 적고 있었다. 실제로는 7개고 **공고 쪽이 더 많다**.
나머지 5개가 나중에 붙으면서 요약이 안 따라간 것.

들어오는 기준(자산 종류가 아니라 **"둘 이상이 같은 계산을 따로 구현했나"**)과 세 갈래
분류를 적었다 — 다음 사람이 여기에 무엇을 넣을지 판단할 수 있게.

## 3. 판단 — 에이전트 로스터를 합쳐야 하나 (권고, 미실행)

플래너 노출 10종이 많은 것 아니냐는 물음. **개수는 문제가 아니다** — 자산 그래프로 자른
분해라 대부분 경계가 분명하다. 다만 둘을 봤다.

- **합칠 만함: `roadmap_manager` → `application_plan`.** `fit_analysis` 가 `analysis`·`roadmap`
  을 **동시에** 내므로 판정 직후 `application_plan`·`roadmap_manager`·`interview_prep` 셋이
  한꺼번에 실행 가능해진다. 앞의 둘은 "이제 뭐 해야 해?"라는 발화로 구분이 안 된다.
  게다가 `roadmap_manager` 는 조회만 하는 스텁(`수정·진척은 후속`)이라 어휘 한 칸 값을 못 한다.
- **합치면 안 됨: `career_chat` ↔ `preference_intake`.** 경계는 얇지만
  `preference_intake.produces=("preferences",)` 가 `job_recommend` 전제의 자동 삽입 근거다.
  합치면 `career_chat` 이 preferences 생산자가 되어 빈 전제마다 자동 삽입 후보로 튄다 —
  어휘 하나 줄이려고 실행 그래프를 망가뜨리는 거래.

**진짜 비용은 개수가 아니라 설명문의 부정 서술이다.** 10개 중 4개
(`posting_analysis`·`career_chat`·`preference_intake`·`resume_diagnosis`)에 "여기가 아니다"·
"~는 안 함"이 있고, 그것들이 말하는 규칙은 거의 하나다 — "기능 요청인데 자료가 부족해도
대화로 도망가지 마라". 이미 플래너 규칙 4에 있는 것이 스펙 3곳에 다르게 반복돼 있다.
LLM 에게 부정 지시는 약한 신호이고, 4벌이 미묘하게 다르면 서로 간섭한다.

**손대는 순서**: ① `roadmap_manager` 병합 → 재측정, ② 부정 서술 정리는 **한 스펙씩** →
매번 재측정. 한 번에 다 하면 어느 변경이 점수를 움직였는지 못 가린다.
근거는 이미 있다 — D97 에서 역할 문장 하나를 지웠다가 `fit-missing-posting-degrade` 가
1.00 → 0.67 로 깨졌다.

## 4. 판단 — 오케스트레이터 대신 에이전트끼리 소통하는 방식은 어떤가 (팀 질문)

**결론: 지금 구조를 유지하고, 필요하면 `delegate` 화이트리스트만 넓힌다.**

이 저장소는 **이미 A2A 를 하고 있다** — `delegate_tool`. 다만 붙은 가드가 곧 자율 A2A 에서
터지는 것들의 목록이다: 읽기 전용(상태 전이는 오케스트레이터만) · 세션 사본 전달 ·
화이트리스트 · `heavy` 금지(동의 게이트 우회 차단) · 깊이 1 · 거부도 trace(성공률의 분모).
**실제로 쓸모 있었던 A2A 는 "물어보기"뿐이었고 "협업해서 진행하기"는 전부 막아 뒀다.**

오케스트레이터를 유지해야 하는 이유(이 프로젝트 기준):

1. **측정 가능성** — 결정 지점이 하나라서 52케이스×3회로 잰다. 협상 결과로 답이 나오면
   "무엇을 틀렸나"의 단위가 사라지고 AGENTS.md §3 재측정 규율이 통째로 성립 안 한다.
2. **동의 게이트** — A2A 에서는 아무 에이전트나 수십 초짜리를 촉발할 수 있다.
3. **비용·지연** — 오케스트레이터는 LLM 한 번으로 N단계를 짠다. A2A 는 홉마다 호출.
4. **결정론이어야 할 것** — `posting_fetch` 삽입·전제 그래프는 협상이 아니라 계산이다.

**가장 강한 근거는 `others_this_turn` 이다.** `resume_diagnosis` 가 "적합도는 제가 못 해요"
한 직후 `fit_analysis` 가 등급을 낸 사고의 원인은 에이전트가 **이번 턴 계획을 몰랐던 것**이고,
해결은 계획을 구조로 주입한 것이었다. **주입할 계획이 존재했기에 고칠 수 있었다** —
자율 A2A 에는 전역 계획이 없어 각자 추측하고, 그 추측은 프롬프트로 못 고친다.

다시 생각할 조건: 작업이 열려 있고(단계 수를 미리 못 셈), 실패가 싸고, 사용자가 기다려 주는
종류(리서치 에이전트). 취업 지원 대화는 정확히 그 반대다.

### ③ 인프라 — RAG 서버가 아예 뜨지 않았다 (`8716eb9`)

예외가 매번 달라(`10053` → `ConnectionTimeout` → `AdminShutdown`) **두 번 오진했다.** 셋 다

## 이 하루의 교훈 넷

1. **없는 사실은 지시로 메울 수 없다**(D100). 프롬프트를 의심하기 전에 `facts` 를 찍어본다.
2. **케이스가 무언가를 잡을 수 있는지 확인하라**(D101). §3-5 의 짝이다 — 없으면 통과율만
   올리는 케이스를 계속 추가한다.
3. **관찰 가능성은 감시 쪽이 아니라 도구가 만든다**(D107). 30초 하트비트가 "0줄"을 스무 번
   보고했다 — 출력 없는 도구는 감시해도 침묵이다.
4. **재측정 없이 원인을 나눌 수 있게 설계해 둔다**(D108). 답변을 저장하고 지표를 순수 함수로
   두면 함께 넣은 변경도 사후에 갈린다. 실제로 세 번 그렇게 갈랐다(비율 가드·라벨 제거·기준선 확장).
