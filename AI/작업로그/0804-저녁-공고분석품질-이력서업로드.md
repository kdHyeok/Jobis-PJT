## 2. 고친 것 (D157)

- `NormalizedJobPosting` · `_JobPostingRead` 에 **`responsibilities`·`conditions`·
  `hiringProcess`·`teamContext`** 신설. `conditions` 는 "라벨: 값" 자유 목록이다 — 공고마다
  항목이 달라 칸을 늘리는 대신 목록으로 받는다.
- `_JOB_PARSER_SYSTEM`: 섹션 제약(`requiredSection` 에서만)은 **요건 칸에만** 적용하고 새 칸은
  `fullText` 전체에서 읽으라고 명시. 담당업무와 요건을 섞지 말라는 규칙도 추가.
- `_normalize_job_schema`: 새 목록 중복 제거 + **자리표시자 조건 줄 폐기**
  ("근무지: 미기재"). `_PLACEHOLDER_VALUES` 에 `미기재`·`기재 없음`·`해당 없음` 추가.
- `tool_render.posting_facts`: 새 칸을 루프 근거로 노출.
- `posting_analysis._GOAL_SYSTEM`: firstLook 을 6절 순서로 재작성
  (① 어떤 자리 → ② **하는 일** → ③ 필수 → ④ 우대 → ⑤ 채용 조건·전형 → ⑥ 읽어야 할 신호).
  **하는 일을 요건보다 앞에** 뒀다. ⑥ 은 근거 원문 표현을 그 줄에 인용할 수 있을 때만 쓴다.

검증: `tests/test_nodes_and_rag.py::test_normalize_drops_placeholder_conditions`.

## 3. 동의 게이트가 공고 정리를 삼키고 있었다 (D158)

되묻기를 넣으려다 발견했다. 게이트가 걸리면 `Dispatch(())` 로 **계획 전체**를 막아서, 공고를
붙인 턴에 적합도 분석이 게이트에 걸리면 공고 정리까지 사라지고 질문만 나갔다.

→ 게이트 턴에도 `submission_review_inserts(dispatch.pending, stored_kinds)` 로 **이번 턴
제출물의 정리 단계만** 실행하고, 질문은 그 뒤에 붙인다.

**시도했다가 되돌린 것**: `validate_plan` 에서 "지금 돌 수 있는 것"을 골라 실행 — (ㄱ) 계획의
나머지는 미루는 것의 산출을 기대하고 배치된 것이라 자소서가 판정 없이 써졌고, (ㄴ) 정리 단계는
애초에 `validate_plan` 의 계획에 없다(제출 kind 를 아는 곳은 오케스트레이터뿐).

기대값을 고친 테스트 2건(`dispatched == []` 를 못 박고 있었다) — 근거는 §3-5 대로 적었다.

## 4. 판정 전 이력서 확인 되묻기 (D159)

**이 서비스의 이력서는 대화 중에 들어온다**(저장 경로가 채팅이다). 저장소에 있는 것이 이 공고를
위해 낸 것이라는 보장이 없다 → 판정 전에 **공고당 한 번** 묻는다.

- 묻는 조건: 판정 예정 ∧ 활성 이력서 origin 이 `career_summary` ∧ `resumeAskedFor` ≠ 이 공고.
- `pasted`·`uploaded` 는 안 묻는다 — 사용자가 이 대화에서 직접 준 것이다.
  처음엔 "이번 턴 제출"로 걸렀는데 **직전 턴에 붙여넣은 이력서에도 되물었다.**
- 배관은 D158 을 그대로 탄다(새 흐름 없음). 동의 게이트 **앞**에 둔다 — 더 구체적이고 답이
  동의까지 겸한다.
- 필드는 **`confirm_resume`**(`resume` 아님). `/analyze` 는 `field="resume"` 를 "자료 없음"으로
  읽어 분석을 `CAREER_DATA_REQUIRED` 로 끝낸다 — 자료가 있는데 어느 것을 쓸지 묻는 여기서는
  거짓말이 된다. 선택지 2개를 함께 내야 `mapping.build_question` 이 왼쪽 패널 질문을 만든다.
  "다른 이력서를 올릴게요"를 고르면 그 분석은 자료 요청으로 끝난다.
- 새 세션 키 `resumeAskedFor` — `ASSET_KEYS` + `persistence_map` 양쪽에 선언.

검증: `test_resume_confirm_gate_asks_once_per_posting`,
`test_resume_confirm_gate_stays_silent_for_a_resume_from_this_chat`.

## 5. 이력서 파일 업로드 (md·docx) — 프론트·백·DB

사용자 요청: 채팅 왼쪽이 공고만 받는데 이력서도 받아야 한다.

**AI 는 추가 작업 0이었다** — `extract.py` 가 이미 `.docx`·`.md`·`.txt`·`.pdf` 를 뽑고
`_apply_attachments` 가 `kind:"resume"` 를 받는다. 계약 변경 없음.

**DB 도 변경 0** — `career_sources.raw_text` 가 이미 추출 텍스트를 담는다. 마이그레이션 없음.

막힌 곳은 하나였다: 브라우저가 `file.text()` 로 md·txt 는 읽지만 **docx 는 ZIP 컨테이너**라
바이트를 문자로 읽으면 깨진다(저장소 화면이 실제로 그렇게 등록하고 있었다).

- **백엔드** `DocumentText.java` 신설 — docx = ZIP 안의 `word/document.xml` 이므로
  `java.util.zip`(표준 라이브러리)으로 풀고 태그를 지운다. **Apache POI 를 들이지 않았다.**
  단락·줄바꿈·탭을 먼저 공백 문자로 바꾼 뒤 태그를 지운다(순서를 뒤집으면 모든 단락이 한 줄로
  붙어 하류 파서가 항목 경계를 잃는다). 실패는 `ApiException` 400 — 잘못된 파일에 500 을
  주면 사용자가 고칠 수 없다.
- `CreateSourceRequest` 에 `fileBase64`·`fileName` 추가. `rawText` 의 `@NotBlank` 를 떼고
  `@AssertTrue hasContent()` 로 바꿨다 — 그대로 두면 docx 업로드가 400 으로 막힌다.
- **프론트** `resumeFile.ts` 신설(두 화면이 같은 규칙을 보게). docx 만 base64, 나머지는 텍스트.
  `StorageView` 는 이걸 쓰도록 갈고 accept 에 `.docx` 추가, `ChatView` 컴포저에 이력서 첨부
  버튼(등록은 `POST /api/career-sources`). 추출은 비동기라 "저장소에서 조각을 고르세요"까지
  알린다 — 끝난 척하지 않는다.

검증: `DocumentTextTest`(docx 를 테스트에서 zip 으로 만들어 검증 — 바이너리 픽스처는 리뷰에서
안 보인다), `npm run build`(vue-tsc 포함) 통과.

## 8. 발단 — 같은 이력서를 외부 LLM 과 비교했다 (공고 쪽 1절과 같은 방법)

대상: 주니어 백엔드/AI 이력서 1건(Django·DRF·RAG·OCR 프로젝트 2건).

| 상대가 낸 것 | 우리 | 원인 |
|---|---|---|
| "두 프로젝트에 기간·팀 규모·역할 비중이 없다" | 없음 | **facts 에 안 실렸다** |
| "숫자가 딱 하나다 — 나머지는 '대폭 단축'" | 없음 | 같음 |
| "'이해도 보유'는 안 해봤다로 읽힌다" | 없음 | 관찰 자체가 없었다 |
| Redis 에 `Distributed Lock` 을 적었는데 본문엔 캐싱만 | `unverifiedSkills` 로 스킬 이름까지만 | 괄호 수식어를 안 봤다 |
| 문장 고쳐쓰기 예시 | 없음 | 프롬프트에 없었다 |
| 지원 전략·시장 위치 | 없음 | **의도적으로 안 받았다**(다른 담당 몫) |

**원인은 프롬프트가 아니었다.** `tool_render.resume_facts` 가 프로젝트를 **제목 문자열**로
평평하게 만들어서 `period`·`teamSize`·`role`·`achievements` 가 루프에 **도달조차 안 했다**.
D157 과 같은 모양인데 그쪽은 스키마에 칸이 없었고 이쪽은 **칸은 있는데 전달 경로에서 잘렸다.**

상대가 **틀린** 것도 받지 않았다 — 고쳐쓰기 예시의 "p95 850ms → 210ms"는 이력서에 없는
**지어낸 숫자**다. 우리는 `p95 ___ms → ___ms` 로 빈칸을 남긴다.

## 9. 고친 것

- **신설 `resume_observations.py`** — 결정론 관찰기(§1 판단 계층). `observe(profile, text)` 가
  다섯 가지를 낸다: 프로젝트별 맥락 세 칸 + `missingContext`(빈 칸의 **이름**),
  `quantifiedClaims`/`unquantifiedClaims`(측정값 유무로 가른 성과 문장, 원문 그대로),
  `selfAssessedLines`, `skillQualifiers`(괄호 수식어 + 서술에 나오는지).
  **무엇이 결함인지는 정하지 않는다**(§2-1) — 말할 것은 루프가 고른다.
- `resume_diagnosis._parse`: `data["observations"]` 신설(우측 패널로도 나간다) → 루프 facts 로.
- `resume_diagnosis._GOAL_SYSTEM`: facts 다섯 필드의 뜻을 **좁게** 정의하고(§3-1 규칙 추가보다
  어휘 좁히기), 하는 일에 넷 추가 — ① **정형 항목화는 언제나 한다**(디테일이 대체하지 않는다),
  ② 항목화 뒤에 디테일을 **원문 인용과 함께** 짚는다, ③ 고쳐쓰기 예시는 수치를 지어내지 말고
  **빈칸으로**, ④ 재작성 요청엔 추측 대신 **되묻는다**(기간·팀 규모·담당 범위).
- `v2bridge.mapping.fragments_from_profile`: PROJECT·EXPERIENCE 조각을 서술(`description`)과
  정형 칸(`detail`)으로 갈랐다. `_narrative`·`_detail` 헬퍼 신설. 버려지던
  `achievements`·`role`·`teamSize`·`techStack` 이 저장소로 간다.
- 프론트 `components/CareerFragmentBody.vue` 신설 — 두 화면(`StorageView`·
  `CareerSourceReviewView`)이 `<p>{{ description }}</p>` 를 각자 그리고 있어 `detail` 을
  아무도 안 보여줬다. `white-space: pre-line`(성과 줄바꿈 살리기) + 라벨 화이트리스트 칩.

  봐야 한다 — 아직 안 돌렸다"** 고 남겨 둔 그 미측정분이고, 이 실행이 그 측정이다.
