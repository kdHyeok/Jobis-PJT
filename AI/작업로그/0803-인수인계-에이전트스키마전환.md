## 0. 다음에 할 일 — 결정은 끝났고 실행만 남았다

사용자 결정: **에이전트 자산 모델을 PostgreSQL 의 진실의 출처로 삼는다(ⓐ). 번역하지 않는다.**

| | 역할 | writer |
|---|---|---|
| **에이전트 자산(PG `agent_session_state.state`)** | **진실의 출처** — `ASSET_KEYS` 를 번역 없이 그대로 | AI 하나 |
| 도메인 테이블(`job_postings`·`career_sources`·`user_competencies`·`roadmap_*`) | **읽기용 투영** — 공고 페이지·커리어지도·로드맵 생성이 읽는다 | 백엔드 하나(자산에서 파생) |

같은 사실이 두 곳에 있지만 **방향이 한쪽(자산 → 투영)이고 테이블마다 writer 가 하나**라 갈리지
않는다. 반대했던 ⓐ는 "양방향으로 서로 덮어쓰는" 형태였고 이건 그게 아니다.

**전송은 지금 계약을 그대로 쓴다 — AI 는 PG 에 직접 붙지 않는다.** 요청에 자산이 오고 응답으로
나가고, 백엔드가 `agent_session_state`(V23 에 이미 있다)에 저장한다. RLS·마이그레이션은 백엔드.

### 순서
1. **자산 블롭 왕복** — 요청 `career.sessionState` 를 `ASSET_KEYS` **전체**로 넓히고,
   응답 `collected.outputs.session_state` 도 전체를 싣는다.
   지금은 `_SESSION_STATE_KEYS = ("pendingRequest", "unsupported_requests")` 두 개뿐이다
   (`v2bridge/service.py`). 도메인 자산까지 포함하도록 넓히는 것이 이 단계다.
2. **번역기 3개 삭제** — `v2bridge/service.py` 의 `_seed_resumes` · `_seed_postings` ·
   `_seed_profile`. 자산을 그대로 복원하므로 번역할 것이 없다. **오늘 회귀의 원인이 여기서
   구조적으로 사라진다**(§2 참고).
3. **투영은 지금 것 유지** — `collected`(공고·이력서) 적재와 `competencyProposal` →
   지도 재료 → 자동 생성(D146·D147)은 **손대지 않는다.** 로드맵 생성은 계속 동작해야 한다.
4. **검증** — `pytest -q`(현재 763건) + 백엔드 `gradlew test` + 실경로 1회.
   실경로는 §4 의 "확인 순서"를 그대로.

### 주의
- `persistence_map.py` + `tests/test_persistence_map.py` 가 **자산마다 목적지 선언을 강제**한다.
  1단계로 목적지가 바뀌는 자산은 그 선언도 함께 고쳐야 회귀가 통과한다(그게 유실 방지 장치다).
- `test_conversation_survives_without_a_session_file` 이 "파일 없이 대화가 서는가"를 잰다.
  1·2단계 뒤에도 이게 통과해야 한다.

## 2. 오늘 얻은 함정 — 다음 사람이 같은 데 빠지지 않게

1. **자산을 복원하는 층이 에이전트의 "이번 턴에 무엇이 새로 왔나"를 흐리면 에이전트의 단계별
   행동이 무너진다**(D151). `firstLook`·D71(정리 단계 삽입)·확신 문턱 면제가 그 신호 위에 선다.
   실측: 공고를 처음 붙인 턴인데 요건 정리가 사라졌다. **복원은 값만 주고 판단 신호는 건드리지
   않는다.** → ⓐ 로 가면 번역이 없어져 이 문제가 구조적으로 사라진다.
2. **증상에 규칙을 더하지 말 것.** "제출 턴에는 판정을 미룬다"는 규칙을 넣었다가 되돌렸다 —
   플래너 판단을 덮어쓰고 명시로 청한 판정까지 막아 회귀 5건이 깨졌다.
3. **`model_dump()` + `json.dumps` 는 Decimal·UUID·datetime 에서 죽는다.** 직렬화는
   `model_dump_json` 으로 pydantic 에 맡긴다. 실측: 판정을 다 끝낸 턴의 답변과 로드맵이 통째로
   유실됐다(`Object of type Decimal is not JSON serializable`).
4. **백엔드 nullable 컬럼을 계약에서 non-null 로 선언하면 요청 전체가 422** 다.
   `career_sources.title`·`job_postings.parsed_data` 로 실제로 겪었다. 받는 쪽은 넉넉하게.
5. **사유를 살리는 일은 저장까지가 아니라 화면까지다**(D149). 코드를 갈라 DB 에 남겼는데 그
   다음 겹에서 고정 문구가 덮었다.

## 5. 도커 postgres — 지금 도는 것은 `jobiss-pg` :5436 (08-04 확인)

**compose 로 띄우지 않는다.** 손으로 만든 컨테이너 `jobiss-pg` 하나가 돌고, 데이터는
compose 가 쓰던 볼륨 `s15p11c202-rag_jobiss_postgres_data` 를 그대로 물고 있다. 역할·비밀번호는
그 볼륨 안에 이미 있으므로 재기동에 `POSTGRES_*` 를 다시 줄 필요가 없다.

```powershell
$env:PATH = 'C:\Program Files\Docker\Docker\resources\bin;' + $env:PATH
docker start jobiss-pg          # 이미 있는 컨테이너를 다시 켤 때 (RestartPolicy 없음 — 재부팅 후 수동)
docker ps --format "{{.Names}} | {{.Ports}} | {{.Status}}"
```

없어졌다면 같은 볼륨으로 다시 만든다:

```powershell
docker run -d --name jobiss-pg -p 5436:5432 `
  -v s15p11c202-rag_jobiss_postgres_data:/var/lib/postgresql/data postgres:17-alpine
```

psql 접속(호스트에 psql 이 없어도 된다 — 컨테이너 것을 쓴다):

```powershell
docker exec jobiss-pg psql -U jobiss_migrator -d jobiss -P pager=off -c "select 1"
```

- **백엔드는 `DB_URL` 을 반드시 넘겨야 한다.** `application.yml` 의 기본값은 아직
  `jdbc:postgresql://localhost:55432/jobiss` 라 그냥 띄우면 5436 을 못 찾는다 →
  `DB_URL=jdbc:postgresql://localhost:5436/jobiss`.
- 안 쓰는 옛 경로 둘: compose 포트 오버라이드(`compose.pgport.yaml`, 55432)와
  `scripts/start-local-postgres.ps1`(네이티브 설치, 55432). **둘 다 지금 안 돈다** —
  55432 는 listen 조차 하지 않는다(08-04 실측). 도커 것 하나만 본다.
- 콘솔 인코딩 때문에 한글 리터럴이 든 SQL 은 `PGCLIENTENCODING=UTF8` 로도 깨질 수 있다 —
  그럴 때는 파이썬으로 `subprocess` 를 써서 UTF-8 로 받는다.
