## 3. LLM 플래너 전환 (`docs/llm-planner-design.md`)

**팀 결정**: "이력서 있고 공고 없으면 이 에이전트" 식 룰 확정 대신, 오케스트레이터가
LLM 에게 "이러한 에이전트들이 있다"를 알려주고 LLM 이 직접 호출 대상을 고르게 한다.

### 3.1 구조 — 선택은 LLM, 확정은 코드

```
발화 + 세션 자산 상태 + 에이전트 목록(레지스트리에서 동적 생성)
   → planner.py [LLM]  : agents 선택. 스키마가 Literal[6개 이름]이라 환각 호출 불가능
   → validate_plan [코드]: 전제조건 검사·전제 에이전트 자동 삽입·불가 시 되묻기
   → 실행 (기존 루프 무변경)
플래너 실패·미설정 → 기존 경로(키워드 의도분류 + 대응표)로 폴백 — 표는 삭제하지 않음
```

- `AgentSpec.produces` 신설 — 각 에이전트가 세션에 만드는 자산 선언. 검증기가
  "analysis 결측 → 생산자 fit_analysis 를 앞에 삽입"을 하드코딩 없이 추론(⊕ 합성의 일반화).
- 기존 테스트 190건이 **무수정 통과** — conftest 가 LLM 을 차단하므로 폴백 경로의
  회귀 테스트로 그대로 작동.

### 3.2 평가셋 실측 (`evals/planner_dataset.json` 41케이스)

| 경로 | 시퀀스 정확도 | 되묻기 일치율 |
|---|---|---|
| 플래너(실 LLM) | **100% (41/41)** | 100% |
| 폴백(키워드+대응표) | 78.0% | 82.9% |

- 되묻기 기대 케이스(인사·잡담·자산 결측 등 9건)에서 실행 유출 0건.
- "합격 가능성 몇 퍼센트야?" 같은 즉석 판단 유도 발화도 판단 없이 fit_analysis 로 위임.
- 러너: `python -m jobis_ai.eval.planner_harness` (`--fallback` 으로 폴백 경로 측정).
- 회고 §3.3·§6-1 과 `agent-structure-current.md` 를 측정 근거와 함께 갱신.

## 4. 관찰 UI — 에이전트가 하는 일을 전부 본다 (`docs/prototype-ui.md`)

이력서·공고 원문과 자연어 메시지를 **직접 입력**하면 전 과정이 타임라인으로 보이는
프로토타입 UI. 모든 실행은 SQLite(`prototype_runs.sqlite3`, gitignore)에 저장돼 재열람 가능.

### 4.1 트레이스 계측 — "하네스가 아니라 창문"

`jobis_ai/trace.py`: contextvar 기반 레코더. **비활성이면 모든 emit 이 no-op** 이라
운영 경로 무영향(계측 추가 후에도 기존 테스트 전부 통과가 증거). 이벤트 8종:

| kind | 내용 | 계측 위치 |
|---|---|---|
| planner / fallback / dispatch | 에이전트 선택·폴백·확정 시퀀스 | `chat.py` |
| agent_start / agent_end | 전제조건·산출물·세션 저장 키 | `chat.py` |
| node | 그래프 노드별 상태 갱신·소요시간 | `service.py` (LangGraph stream) |
| llm_call | **모든 LLM 호출** — 시스템 프롬프트·입력 원문·구조화 출력·재시도 | `structured.py` (단일 통로) |
| judgment | 요구사항별 판정 방법·상태·매칭/결측 스킬·근거·사유 | `gap_matcher.py` |
| score | 카테고리 점수·가중치·분모 제외·임계값·등급 | `gap_matcher.py` |

### 4.2 실기동 검증 (실 LLM)

샘플 이력서+공고 입력 → 21개 이벤트 / ~18초: 플래너(1.7s) → 공고 파싱 LLM(2.6s) →
프로필 추출 LLM(4.7s) → 의미판정 배치(1.2s) → 판정 8건(exact4·llm_semantic2·keyword1·
seniority1) → 점수 0.6/등급 중 → 로드맵·대안·검증(0~2ms, 결정론) → nl_render(6.4s).
판정 계층이 실제 0ms 대라는 것이 화면에서 확인된다.

## 6. (추가) 부분 자산의 우아한 대응 — posting_analysis 강등 실행

"공고만 있고 이력서 없이 분석 요청 → 되묻기만 하고 끝"이 UX 로 나쁘다는 피드백에서 출발.
오케스트레이터가 **가진 자산으로 할 수 있는 일을 먼저 하고, 그 결과를 들고 다음 입력을
자연스럽게 요청**하도록 바꿨다 (graceful degradation).

- **신규 에이전트 `posting_analysis`** (`agents/posting_analysis.py`) — 공고만으로
  `parse_job_posting` 노드를 재사용해 요구 연차·기술 스택·필수/우대를 정리해 답하고,
  "작성해두신 이력서가 있나요?"로 연결(followUpQuestions). 판정은 하지 않는다.
- **강등 룰 `_degrade_fit_analysis`** (`router.py`, 순수 결정론) — 적합도 분석 요청 시:
  공고만 있음 → posting_analysis / 이력서만 있음 → resume_diagnosis 먼저 + 공고 자연 요청 /
  둘 다 없음 → 기존대로 되묻기. `validate_plan`(플래너 경로)과 `route`(폴백 경로) 양쪽 적용.
- 플래너 매니페스트에도 등록 — LLM 이 "이 공고 분석해줘"(공고만 보유)에서
  posting_analysis 를 직접 고르는 것을 실측 확인.
- **평가셋 41→43케이스로 확장**(강등 2 + 직접 선택 1), 실 LLM 재측정 **43/43 (100%) 유지**.
  회귀 테스트 228→**232건** 통과.

## 7. (추가) 파싱 A/B 실험 — "전부 LLM에 맡기면 더 정확한가?"

"파싱을 전부 LLM 에게 맡기는 게 더 정확하지 않냐"는 제안을 실측으로 검증했다.
공고 6건(헤더형·산문형·불릿·혼합) × 3회 반복 × 2변형 = LLM 36콜.
스크립트 `scripts/ab_parse_experiment.py`, 데이터 `evals/ab_parse_dataset.json`,
결과 `evals/ab_parse_results.json`.

| 지표 | 하이브리드(현행) | LLM-only |
|---|---|---|
| 요구사항 F1 | **0.971** | 0.958 |
| techStack F1 | 0.947 | **0.954** |
| 환각 스택 | 0 | 0 |
| 연차 정확도 | 1.0 | 1.0 |
| **재현성**(3회 완전 동일) | **5/6 (0.833)** | 4/6 (0.667) |

**결론 — 정확도는 동률(잡음 범위), 재현성은 하이브리드 우위. 현행 유지.**

- LLM-only 가 "더 정확"하다는 가설은 기각 — 추출은 어차피 두 변형 다 LLM 이 하므로
  정확도 차이가 날 구조가 아니다. 산문형 공고에서 LLM-only 는 두 요구사항을 한 문장으로
  뭉쳐(granularity 손실, F1 0.75) 하류 요구사항별 판정이 거칠어진다.
- 재현성이 실질 차이: 헤더 있는 공고에서 하이브리드는 룰이 섹션·스택·연차를 고정해
  3회 모두 동일 출력. LLM-only 는 같은 입력에도 출력이 흔들린다(6건 중 2건) —
  같은 공고에 fitGrade 가 실행마다 달라질 수 있다는 뜻.
- 실험 과정의 교훈 2건: ① 초기 정답 라벨의 조사·띄어쓰기("HTML 과")가 토큰 매칭과
  어긋나 하이브리드 F1 이 0.08 로 왜곡됐었다 — 측정 도구의 한국어 토큰화 한계 확인,
  라벨 수정 후 재측정. ② **taxonomy 커버리지 공백 발견 → 즉시 보강**: Android·iOS·
  Flutter·React Native·Dart 가 skill_taxonomy(72개)에 없었다. 5종 추가 후 모바일 케이스
  techStack F1 0.75 → **1.0**. 상세는 `docs/troubleshooting.md` 07-24 항목.

## 8. (추가) LLM 호출 지점 전수 정리 + 모델 티어 분리

토큰 비용 절감 요청으로 GMS 호출 7지점을 전수 정리하고 2티어로 분리했다.
`get_llm(tier)` / `run_structured(..., tier=)` 신설, `LLM_MODEL_LIGHT`(기본 gpt-5-nano) 설정 추가.

| 호출 지점 | 일 | 티어 | 근거 |
|---|---|---|---|
| parse_job_posting | 공고 추출 | **default(고급)** | 긴 비정형 입력, 판정 엔진의 입력 품질 |
| build_user_profile | 이력서 추출 | **default** | 가장 긴 입력, evidence 가 판정 근거 |
| coverletter_draft | 자소서 생성 | **default** | 사용자에게 나가는 생성문 |
| agent_planner | 에이전트 선택 | **default** | ⚠️ 경량 실측서 정확도 100→48.8% 붕괴(과잉선택·오되묻기) — 되돌림 |
| nl_render | 요약 문장 | **default** | ⚠️ 경량이 오히려 느리고(6.4→15.6s) 문체 붕괴, 입력 짧아 절약 미미 — 되돌림 |
| domain_keyword_judge | 의미판정 배치 | **light(경량)** | 이진 센서(문장 번호만), 해석은 코드. 실측 정상 |
| intent_classifier | 폴백 라벨 분류 | **light** | 7라벨, 플래너 실패 시에만 호출 |

**교훈**: "단순해 보이는 업무 = 경량 가능"이 아니었다 — 스키마 제한·검증기가 있어도
판단 품질 차이는 못 막는다(플래너). 티어 배정은 감이 아니라 **지점별 실측**으로 확정했고,
결과적으로 경량화 가능 지점은 입력이 큰 의미판정 배치(토큰 절약 실익 최대)와 폴백 분류뿐.

## 10. (추가) 선호 수집 대화 — "정형 워크플로우가 아니라 주고받는 대화"

"이력서 없는데 공고 추천받고 싶어"에 "이력서 주세요"로 닫아버리는 것은 워크플로우지
에이전트가 아니라는 피드백. **오케스트레이터는 맥락으로 에이전트를 고르고, 정보 요구는
에이전트가 대화로 한다**는 구조로 구현했다.

- **신규 에이전트 `preference_intake`** (전제조건 없음·항상 실행 가능) — 원하는
  직군·회사·도메인을 대화로 수집해 세션 `preferences` 자산에 누적. 직군은
  role_taxonomy 룰(결정론), 회사·도메인은 LLM 읽기(경량 티어). LLM 이 직군을
  도메인으로도 중복 분류하는 것은 룰이 정리.
- **분기점은 결정론**: 선호 차원 2개 이상, 또는 1개 이상 + 되묻기 2턴 소진(무한
  질문 루프 방지). 넘으면 "○○ 직군, △△ 도메인에 관심이 있으시군요. 준비해두신
  이력서가 있으신가요?"로 자연 전환.
- 라우터: job_recommend + 이력서 없음 → 되묻기 대신 preference_intake 강등(플래너·폴백
  양쪽). 플래너에는 세션의 선호 수집 진행 상태를 맥락으로 주입 — 후속 발화("백엔드
  쪽이요")도 preference_intake 로 이어진다. 대화형 단독 실행은 "~로 이해했어요"
  라우팅 문구 생략(기계적 반복 제거).
- 세션 자산 2종 추가: `preferences`(누적 선호), `last_message`(발화 원문 — 대화형
  에이전트의 입력).
- **실측(실 LLM 3턴)**: "이력서 없는데 추천받고 싶어" → 열린 질문 → "백엔드 쪽으로
  가고 싶어요" → "백엔드 직군 쪽이시군요. 관심 도메인이나 회사가 있나요?" →
  "핀테크나 커머스요" → "백엔드 직군, 핀테크·커머스 도메인에 관심이 있으시군요.
  준비해두신 이력서가 있으신가요?" — 의도한 흐름 그대로.
- 플래너 평가셋 45케이스로 확장. 44/45 에서 유일한 불일치가 "취업 너무 어렵다"(하소연)에
  되묻기 대신 대화를 연 것 — 새 철학에선 이게 정답이라 라벨을 갱신(vent-opens-dialog).
  회귀 테스트 **236건** 통과.

## 11. (추가) 플래너 이해 확인 문장(ack) — 첫 응답부터 자연어로

단계 실행에서 계획 수립 직후 응답이 비어 있고 메타 정보만 떠서("intent=preference_intake
· confidence=0.97 …") 대화 느낌이 끊긴다는 피드백. **플래너가 "요청을 어떻게 이해했고
무엇을 하려는지" 한 문장(ack)을 함께 내도록** 스키마를 확장했다.

- `AgentPlan.ack` 필드 추가 — **표현 채널이지 판단 채널이 아니다**. 프롬프트 규칙으로
  적합도·합격 가능성 등 판단·예측·조언 금지.
- `safe_ack()` 검증 (planner.py) — 금지표현(`FORBIDDEN_EXPRESSIONS`)이 섞이면 문장을
  버리고 결정론 문구("~로 이해했어요")로 폴백. **표현 계층도 검증을 면제받지 않는다** —
  nl_render 와 동일 패턴.
- chat.handle_chat / stepper.start 양쪽에서 검증 통과한 ack 가 기계적 라우팅 문구를 대체.
  LLM 미설정·실패 시 기존 결정론 note 그대로 — 폴백 경로 무영향(테스트 236건 무수정 통과).
- 트레이스 `planner` 이벤트에 ack 기록 — UI 에서 확인 가능.
- **실측**: "나 공고 추천 받고싶어" 단계 실행 시작 → 즉시 "공고 추천을 원하시는군요.
  아직 이력서가 없으니 어떤 공고를 찾으시는지부터 파악해볼게요." (계획 수립 단계에서
  이미 자연어 응답, 다음 단계에서 preference_intake 의 열린 질문이 이어짐).

## 12. (추가) 대화 품질 2건 — 표현의 LLM 화 + 진로 대화 에이전트

### 12.1 preference_intake 응답을 LLM 표현으로 (고정 템플릿 탈피)

"공고 추천해줘"에 매번 같은 고정 문구가 나오는 것이 부자연스럽다는 피드백.
**무엇을 물을지는 룰이 정하고(askFor: preferences/domain_or_company/resume),
어떻게 말할지는 LLM 이 쓴다** — 직전 발화·수집된 선호를 facts 로 주고 렌더링,
금지표현 검증 실패·LLM 미설정 시 기존 템플릿 폴백 (nl_render 패턴).
ack 와 에이전트 질문이 겹치는 중복도 제거(대화형 단독 실행은 ack 생략).

실측: "공고 추천해줘" → "좋아요, 공고 추천해드릴게요. 어느 분야나 직군, 혹은 보고
싶은 회사가 있을까요?" / "백엔드요" → "좋아요, 백엔드 공고로 볼게요. 관심 있는
도메인이나 특정 회사가 있으면 같이 알려주세요." / "토스 같은 핀테크 가고 싶어요" →
"토스 같은 핀테크 쪽 백엔드 공고로 보면 되겠네요. 혹시 지금 준비해둔 이력서가
있으실까요?" — 턴마다 상황에 맞는 문장.

### 12.2 신규 에이전트 career_chat — 기능과 관련 적은 발화의 대화 상대

"바로 기능 에이전트를 호출하는 게 아니라, 기능과 관련이 적은 질문은 진로 대화를
나누는 에이전트가 받아야 한다"는 피드백. `agents/career_chat.py` 신설:

- 진로 고민·하소연·인사·일반 질문을 공감/담백한 답으로 받아주고, 대화 흐름상
  자연스러울 때만 기능을 부드럽게 안내. 표현 계층이라 적합도·합격 단정은 프롬프트
  금지 + 금지표현 검증, LLM 미설정 시 결정론 기능 안내 폴백.
- 플래너 규칙: "기능과 직접 관련이 적은 발화는 career_chat — 빈 agents 되묻기는
  최후의 수단". ASK_UNCLEAR 가 사실상 대화로 대체됨.
- 평가셋 46케이스(진로 대화 5케이스 추가) **46/46 (100%)**. 회귀 테스트 **237건** 통과.
- 실측 4턴: 인사 → 공감 → 포트폴리오 질문 답변 → "그럼 공고 추천해줘"에서
  preference_intake 로 자연 전환 — 잡담과 기능 사이를 오케스트레이터가 맥락으로 오간다.
