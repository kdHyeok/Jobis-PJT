# 2026-08-03 (저녁) — 대화 자산의 백엔드 적재 + 커리어지도 로드맵 복구 계획

사용자가 정한 구조(이 세션에서 확정):

1. **데이터를 사용자에게서 얻는 창구는 에이전트와의 대화다.**
2. **대화로 얻은 자산은 AI 세션에만 있으면 안 되고 백엔드의 알맞은 테이블에 적재된다.**
   예: 채팅에 URL 을 넣고 공고를 분석하면 사이드바 **채용공고 페이지에 그 내용이 전부** 있어야 한다.
3. **적합도 분석까지가 채팅·에이전트의 영역이고, 로드맵은 커리어지도에서 그린다.**
   채팅은 "로드맵이 다 그려지면 커리어지도에서 확인해 보세요" 까지만 말한다.
4. 로드맵 재료는 **적합도 분석까지 오면서 쌓인 데이터**로 만들고, 공고·이력서만으로 부족한
   자리는 LLM 이 읽어서 메운다(= 지금의 `mapping.build_competency_proposal` + `enrich`).

**AI 세션은 진실의 출처가 아니라 캐시다.** 이 문서의 대부분은 그 한 문장의 결과다.

---

## 1. 실측 — 지금 무엇이 어긋나 있나

### 1-1. 커리어지도 로드맵은 한 번도 생성된 적이 없다

PostgreSQL(55432) 실측:

| 테이블 | 행 수 |
|---|---|
| `analysis_jobs` | FAILED 2 · RUNNING(15:20 이후 멈춤) 1 · **COMPLETED 0** |
| `posting_competency_requirements` · `posting_target_projects` · `roadmap_targets` · `roadmap_versions` | **전부 0** |
| `user_competencies` · `career_nodes` | 6 · 6 (커리어 추출분 — 공고 로드맵과 무관) |

`RoadmapService.buildSnapshot` 이 이 테이블에서 지도를 그리므로 여정 보기·상세 관계 보기
둘 다 그릴 것이 없다.

### 1-2. 구멍 두 개가 겹쳐 있다

**구멍 ①  채팅 메시지로 붙인 공고는 백엔드에 등록되지 않는다.**
채팅 세션 `v2-chat-c1470d00` 의 공고는 잡코리아 `GI_Read/49590699` 인데 `job_postings` 에
없다(있는 것은 `49657175`·`49692518`·텍스트 1건). `ConversationService.send` 는
`command.posting()`(공고 첨부 UI)이 있을 때만 `JobPostingService.create` 를 부르고,
`ChatRequest` 는 `role`·`content` 만 싣는다. **AI 는 메시지 본문의 URL 을 공고 자산으로
승격해 수집·판정까지 다 했지만, 그 사실이 백엔드로 돌아갈 칸이 계약에 없다.**

**구멍 ②  첨부로 들어온 공고 3건은 전부 실패했다.** 사유는 백엔드 `safeMessage` 가 일반
문구로 덮어 `analysis_jobs.error_message` 에는 안 남았지만, `analysis_agent_events` 의
스트림 이벤트에 AI 의 원문 사유가 남아 있었다:

- **A. `sourceType=TEXT` 인데 `raw_text` 가 URL 하나**(124자). `service.py:120` 의
  `is_url_only` 는 `source_type=="URL"` 을 요구하므로 주소 문자열을 공고 원문으로 파싱 →
  요건 0건 → `fitGrade=판정불가`·`overallScore=None` → `_decide_status` 가 `UNDETERMINED`
  → `verdict_from_plan` 이 `VerdictUndetermined` → 503.
- **B. 필수요건에 기술이 없는 공고**는 로드맵을 못 만든다. 요건 13건을 정상 판정했는데
  구성이 `학력: 대졸이상`(required) · `요구 연차`(required, eligible=false) · 나머지 전부
  `preferred`(`_tech_stack_requirements` 가 techStack 을 preferred 로 매김, `nodes.py:160`)
  였다. `provable` 은 `roadmap_eligible ∧ REQUIRED` 를 요구(`mapping.py:367`)해서 ∅ →
  proposal None → 503 `공고에서 로드맵에 올릴 역량을 찾지 못했어요 (트랙=AI, 요건=13건)`.
  **판정 관점(techStack = 있으면 좋은 신호)과 지도 관점(REQUIRED = 본선 경로)의 충돌이다.**
- **C. AI 는 성공했는데 잡이 멈췄다.** 세션 `v2-analysis-32700782` 은 적합도 0.66/중 +
  로드맵까지 냈지만 잡은 `RUNNING` 으로 멈춰 있다. `claim_analysis_job` 은
  `status='QUEUED'` 만 집으므로 락(15분)이 만료돼도 회수되지 않는다. **백엔드 몫.**

### 1-3. 공고 원문의 수명 — 구조적으로 성공 경로에만 남는다

1. URL 공고는 백엔드가 `job_postings.raw_text` 에 **주소를 자리표시로** 넣는다(NOT NULL).
2. AI 는 잡마다 `store.clear(v2-analysis-{jobId})` 로 세션을 백지로 시작(`service.py:113`).
3. `posting_fetch` 가 수집한 원문은 **세션 자산에만** 들어간다(`_common.py:427`).
   세션 밖 캐시는 없다 — `postings_db` 는 크롤 데이터 읽기 전용, `posting_library` 도 세션 자산.
4. 원문이 백엔드로 돌아가는 유일한 길은 `JobContext.sourceText` → `AnalysisWorker` 의
   `raw_text` 되메우기(`AnalysisWorker.java:615`)이고 그것은 **`complete()` 안에만** 있다.
5. 그래서 실패하면 수집본이 세션과 함께 사라지고 재시도는 다시 주소만 받아 재수집한다.
   `attempt_count < 3` 이므로 세 번 긁고 영구 실패, `raw_text` 는 영영 주소로 남는다 —
   DB 의 두 공고가 정확히 그 상태다.
6. 게다가 채팅 세션(`v2-chat-{convId}`)이 같은 공고를 따로 수집한다. 같은 공고를 두 번 긁고,
   그 사이 페이지가 바뀌면 두 판정이 서로 다른 원문 위에 선다.

같은 이유로 **이중 판정**이 있다: `fit_analysis` 가 채팅 세션과 분석 잡 세션에서 각각 돌아
같은 공고·이력서에 대한 판정이 두 벌 존재하고, 지도는 그중 분석 잡 쪽만 본다.

## 2. 자산 → 백엔드 테이블 대응표

AI 세션이 갖는 자산(`orchestrator/session.py:ASSET_KEYS`)과 적재할 자리:

| AI 세션 자산 | 백엔드 테이블 | 기존 적재 경로 | 상태 |
|---|---|---|---|
| `job_posting`(원문·URL) + `posting_summary`(파싱) | `job_postings`(raw_text·parsed_data·company_name·role_title·experience_text·closes_at·lifecycle_status) + `job_requirements` | `JobPostingService.create` (첨부 UI 전용) | **칸 없음 → ①** |
| `resume` · `resume_library` | `career_sources` → 워커가 `career_fragments` 로 분해 | 커리어 저장소 업로드 | **칸 없음** |
| `analysis`(적합도) | `analysis_jobs.result_data` | 분석 잡 경로 | 분석 잡만 |
| 로드맵 재료 | `user_competencies` · `posting_competency_requirements` · `posting_target_projects` · `roadmap_targets` | `AnalysisWorker` | 분석 잡만 |
| `history` | `conversation_messages` | 백엔드가 직접 씀 | 적재됨 |
| `preferences` · `user_facts` | 마땅한 테이블 없음(`user_goal_profiles` 는 `final_goal_text` · `current_goal_posting_id` 뿐) | — | **후순위** |
| `recommendations` · `coverletter` · `interview` | 대응 테이블 없음 | — | **후순위** |

**후순위 항목은 새 테이블이 필요하다** — 이 계획에서는 손대지 않고, 필요해질 때 백엔드와
함께 정한다. 지금 막는 것은 공고·이력서·로드맵 세 줄이다.

## 3. AI 파트 계획 (순서대로)

### P1. `sourceType` 을 믿지 않는다 — 본문이 URL 하나면 URL 자산으로
`service.py:120` 의 `is_url_only` 를 본문 내용으로 판정한다. 판별기는
`orchestrator/attachment_kind` 에 이미 있으므로 재사용한다(같은 규칙 두 벌 금지 — 이 저장소가
세 번 대가를 치른 실수). → **원인 A 해소.** 테스트 1건(`sourceType=TEXT` + 본문이 URL).

### P2. `provable` 완화 — 필수에 기술이 없으면 우대에서 증명 대상을 잡는다
`mapping.build_competency_proposal` 의 `provable` 이 비면 **`roadmap_eligible` 한
`PREFERRED`** 로 `targetProject.requiredCompetencyRefs` 를 채운다.
`CompetencyProposal.validate_references` 는 relation 을 보지 않으므로 계약상 안전하고,
지도에는 우대 퀘스트(optional 노드)로 그려진다. **왜 우대만인지는 warning 으로 올린다**(§2-6).
로드맵이 통째로 안 생기는 것보다 우대 퀘스트라도 있는 것이 낫다. → **원인 B 해소.**
테스트 2건(실측 13건 구성을 픽스처로: 필수=학력·연차, 기술=전부 우대).

### P3. 실패 사유를 살린다
그래도 못 만들면 `AI_PROVIDER_UNAVAILABLE` 이 아니라 전용 코드로 낸다. 백엔드
`safeMessage` 는 `INVALID_AI_RESPONSE`·`AI_PROVIDER_UNAVAILABLE` 만 일반 문구로 덮고
나머지는 예외 메시지를 그대로 저장하므로, 코드를 바꾸면 AI 의 사유가 화면까지 간다.
`claim_analysis_job` 은 QUEUED 만 집으니 재시도 폭주 위험도 없다.

### P4. 채팅은 로드맵을 읊지 않는다
`tool_render.render_roadmap_manager` 가 항목을 나열하고 "항목 수정이나 진척 체크 기능은
준비 중"을 붙이는 것을 **"커리어지도에서 확인해 보세요"** 로 바꾸고 `OPEN_MAP` 을 붙인다.
`mapping._MAP_PRODUCERS` 에 `fit_analysis` 를 추가한다. 이것은 새 정책이 아니라 이미 적어
둔 정책의 이행이다 — `chat_actions` 주석(`mapping.py:859`)이 "`OPEN_MAP` 은 로드맵을 채팅으로
읊지 않기 위한 유일한 레버"라고 못 박아 뒀는데 렌더러가 그것을 어기고 있었다.

### P5. 대화에서 확보한 자산을 응답에 싣는다 (구멍 ① 의 AI 쪽 절반)
`ChatResponse` 에 **추가만 하는** 칸 하나:

```
class CollectedPosting(ContractModel):
    source_type: Literal["URL", "TEXT"]
    source_url: str | None
    raw_text: str                 # URL 이면 우리가 수집한 본문(주소가 아니다)
    parsed_data: dict             # posting_summary 그대로
    company_name / role_title / experience_type / closes_at / lifecycle_status

class CollectedResume(ContractModel):
    source_type / title / raw_text / summary

class CollectedAssets(ContractModel):
    posting: CollectedPosting | None = None
    resume: CollectedResume | None = None
```

`ChatResponse.collected: CollectedAssets | None`. 채팅 턴에서 공고·이력서 자산이 **새로
확보됐을 때만** 싣는다(매 턴 같은 원문을 다시 보내지 않는다 — 판단 기준은 자산 승격 사실).

**백엔드가 이 칸을 읽지 않아도 아무 일도 일어나지 않는다**(Spring Boot 의 Jackson 은 모르는
필드를 무시한다). 그래서 승인 대기 없이 AI 파트를 먼저 끝낼 수 있다.

### P6. 검증
1. 저장된 세 공고의 세션 자산으로 결정론 부분 재현(LLM 0원) — P1·P2 가 세 건 모두에서
   `competencyProposal` 을 내는지.
2. 실 모델 1회 풀 경로(§3-7) — `roadmap_targets` 에 행이 생기고 상세 관계 보기가 그려지는지.
3. `pytest -q` 회귀.

## 4. 백엔드·프론트에 필요한 것 (승인 없이는 손대지 않는다)

1. **`ChatResponse.collected` 소비** — `posting` 이 오면 첨부 경로가 쓰는
   `JobPostingService.create` 를 그대로 부른다(공고 등록 + 분석 잡 생성 + 중복 지문 처리가
   전부 그 안에 있다). `resume` 는 `career_sources` 로 넣는다. **프론트는 안 건드려도 된다**
   — 사이드바 공고 페이지·커리어 저장소는 이미 그 테이블을 읽는다.
2. **RUNNING 잡 회수**(원인 C) — 락 만료 잡을 QUEUED 로 되돌리는 회수기.
3. **`safeMessage` 가 AI 사유를 덮는 문제** — 사용자에게 보일 문구와 별개로 원문 사유를
   `error_message` 에 남긴다(P3 는 그 우회일 뿐 근본 수정이 아니다).

## 5. 안 하기로 한 것 (근거와 함께)

- **공고 원문 캐시를 세션 밖에 두는 일(중간에 검토했던 S1)은 지금 하지 않는다.**
  §1-3 의 유실을 막는 정공법으로 보였지만, P5 가 들어오면 **원문은 등록 시점에
  `job_postings.raw_text` 에 박힌다** — 진실의 출처가 하나 생기는데 그 앞에 캐시를 또 두면
  같은 사실이 두 곳에 있게 된다. 남는 노출은 "첨부 경로로 들어온 공고의 분석이 실패했고
  그 사이 공고 페이지가 닫힌" 경우뿐이고, P1·P2 가 실패 자체를 없앤다. 필요해지면 그때.
- **`ChatResponse` 에 `competencyProposal` 을 싣는 것은 하지 않는다.** 지도 재료를 내는 길이
  두 개가 되고 둘이 어긋나면 지도가 쪼개진다. 로드맵은 분석 잡 한 경로에서만 만든다
  (사용자 구조 3번과 같은 방향).
- **채팅의 `fit_analysis` 를 없애지 않는다.** 적합도 분석까지는 채팅의 영역이라고 정해졌다.
  이중 판정은 P5 로 공고가 등록되면 같은 원문을 보게 되므로 입력이 갈리는 문제는 사라진다.
  판정 결과 자체의 공유(채팅이 분석 잡 결과를 재사용)는 다음 순서로 남긴다.
