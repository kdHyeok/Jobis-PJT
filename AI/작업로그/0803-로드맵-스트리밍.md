## 1. 에이전트 자율성 — 도구·가드·대체안

### 1-1. 기준선 실측 (`evals/loop_baseline_0803.json`)

자기 루프 4케이스 × 5회, claude_code/sonnet, `EMBED_PROVIDER=null`.

|---|---|---|---|---|

| `interview_prep` | 0.80 | 2.8 | 3 | 3.8 |

않다). 계획 단계에서 "도구가 늘면 5가 모자랄 것"이라 적었는데 실측이 아니라고 답했다.

부수 관측 셋(이번 범위 밖, 다음 후보):

- `preference_intake` 5회 중 1회는 도구 없이 답한다(불변식 위반).
- `coverletter_emphasis` 에 `coverletter_check_unresolved` 5/5 + 재시도 5.

### 1-2. 바깥 세계 도구 (`_common.search_postings_tool`)

루프 하네스는 전부터 있었는데 등록된 도구가 **전부 세션 내부 데이터**였다
(`resume_diagnosis` 1개, `posting_analysis` 2개). 고를 것이 없으면 루프는 돌지 않는다 —
**자율성의 병목은 루프 구조가 아니라 도구 목록이었다.**

RAG 검색을 ToolSpec 으로 열고 `posting_analysis` 에 연결. 관찰은 사실만, 실패는 예외 대신
관찰 문자열, RAG 경고(`rag_http_failed`)는 삼키지 않고 올린다(D90 의 짝).

`fetch_posting` 도구는 **만들지 않았다** — `chat.py` 가 URL 공고를 이미 결정론으로 큐 맨 앞에
끼우고(D64), 임의 URL 을 LLM 이 가져오게 하면 §2-7 을 우회한다.

### 1-3. 위임 가드 통합 (`agent_loop.call_agent_readonly`)

계획은 "`application_plan` 을 루프로 승격"이었으나 **접근을 바꿨다** — 그러면 결정론 판정
경로에 LLM 도구 선택이 들어와 §1 을 위반한다.

대신 진짜 문제를 고쳤다: 위임 가드가 **두 벌이었고 어긋나 있었다.**
`application_plan._related_postings` 에는 `heavy` 검사도 중첩 위임 차단도 없었다 —
`job_recommend` 가 언젠가 heavy 가 되면 그 경로만 동의 게이트(§2-7)를 우회한다.
이제 두 호출자가 한 함수를 지난다. `_related_postings` 42줄 → 20줄.

회귀 1건 발생 → 원인은 공유 함수에 넣은 render 폴백. 문장이 필요한 루프의 관심사인데
`application_plan` 은 `.data` 만 쓴다 → `render_reply` 옵트인으로 분리.

### 1-4. 실패 자리에 대체 단계 1회

`Observation.dropped` 추가 — 전에는 무엇이 빠졌는지가 note **문장 안에만** 있어서 호출부가
코드로 알 수 없었다. 그게 "뺐다까지만 하고 대신 뭘 할까는 아무도 안 묻던" 구조적 원인이다.

`observe()` 는 **순수 함수로 남기고** LLM 호출은 `chat.py` 가 한다(`planner.replacement_for`).
자율은 고르기까지: 후보는 코드가 만들고(등록 ∧ `runnable_now` ∧ heavy 아님 ∧ 미실행),
고른 뒤 후보 밖이면 버리고 `replacement_out_of_candidates` 로 센다. 예산 턴당 1회.

## 2. 로드맵 계약 — v2bridge 가 `competencyProposal` 을 낸다

### 2-0. `ai-server/` 원복

세션 초반에 `ai-server/app/{models,prompts}.py` 를 고쳤다가 되돌렸다. **그건 백엔드 팀원이
자기 AI 답변을 시험하려고 세운 서버**이지 우리 계약 정본이 아니다.

`v2bridge/models.py` docstring 의 "계약 정본은 `ai-server/app/models.py`" 표기도 고쳤다.
**정본은 백엔드 코드다** — `AiContracts.java`, `RoadmapService`, V10/V12 CHECK,
`frontend/src/types.ts`. ai-server 는 참고 구현으로만 쓴다(동기화 의무 없음).

### 2-1. 계약 모델 이식 (`v2bridge/models.py`)

`AnalyzedCompetency`(+검증자) · `AnalyzedRequirement` · `TargetProjectBrief` ·
`CompetencyProposal`(ref 유일·키 유일·참조 무결성·`(ref,relation)` 중복 금지·정성 역량으로
targetProject 증명 금지) · `CareerTrack` · `ExperienceRequirement` · `SharedPostingAnalysis`
· `JobContext` 확장(`primaryTrack`·`experienceRequirement`·`closesAt`·`lifecycleStatus`).

**계획에 없던 발견 — 요청 쪽 구멍 2개.** `extra="forbid"` 라 백엔드가 보내는 필드가 없으면
**요청 전체가 422 로 거부된다**(무시가 아니다). `AnalysisRequest.sharedAnalysis` 와
`CareerSnapshot.goals` 가 빠져 있었다. 둘 다 추가. 응답 쪽 누락과 대칭이 아니라 더 위험하다.

### 2-2. 결정론 매핑 (`mapping.build_competency_proposal`)

앵커는 `skill_taxonomy`. 처음 `resolve(title)` 로 짰다가 전부 실패 — `resolve` 는 기술
**이름**을 받는데 요건 **문장**을 넘겼다. 문장용은 `find_in_text` 이고, 그걸 쓰니 문서 규칙 10
("복합 문장은 역량을 분리하되 sourceText 공유")도 따라왔다.

stage·domain 은 taxonomy 카테고리에서 결정론으로 나온다(문서 규칙 8·9 그대로):

| category | stage | domain |
|---|---|---|
| language / framework / testing | LANGUAGE / FRAMEWORK / QUALITY | **주 직무 레인** |
| database / data | DATA | DATA |
| devops / cloud | OPERATIONS | DEVOPS / CLOUD |

- `track_from_posting` — `roleCategory` → 10종 트랙. **모르면 None**(짐작해 BACKEND 로 채우지
  않는다 §2-1).
- 한글 산문 요건은 `slug()` 가 빈 문자열을 내므로 뺀다. `roadmapEligible=false` 로 남겨도
  카탈로그·준비도 분모 어디에도 안 쓰여 이득이 없다. **몇 건 뺐는지는 로그로 센다**(§2-6).
- 만들 수 없으면 **None** — 빈 과제를 지어내지 않는다.

### 2-3. LLM 분류 (`v2bridge/enrich.py`)

결정론이 못 채운 자리(사전 밖 요건의 단계·분야, 요구 수준, 검증 가능 여부, 트랙, 회사 맞춤
과제)를 **읽어서** 채운다. §1 의 *읽기* 계층이다.

**자율의 경계를 스키마로 그었다** — `CompetencyClassification` 에 `canonicalKey` 도 `title` 도
`sourceText` 도 **칸이 없다**. LLM 이 키를 지으면 같은 기술이 공고마다 다른 키를 받아
`user_competencies` 가 쪼개진다(예외도 경고도 없는 조용한 고장). `TargetProjectDraft` 에도
`requiredCompetencyRefs` 가 없다 — 증명 대상은 "필수 ∧ 검증 가능"이라는 **계산**이다.

트랙은 결정론이 먼저다 — `roleCategory` 가 표준 표기면 그게 사실이고 LLM 은 못 읽었을 때만.

### 2-4. 계약 조임

`COMPLETED` → `competencyProposal` **필수**. 없으면 `EngineFailed` 로 먼저 알린다.
없는 채로 COMPLETED 를 내보내는 것은 **성공을 가장한 실패**다(워커가 FAILED 로 끝내는데
원인이 응답 어디에도 안 남는다). 1단계에 심어둔 tripwire 테스트가 여기서 깨졌고 그걸
뒤집는 걸로 조였다.

### 2-5. 실 모델 검증에서 잡은 버그 — 경력 관문이 통째로 안 생겼다

`experienceRequirement` 가 **null** 이었다. 문서 §1-2 가 "`REQUIRED` 만 경력 관문을 만든다"
고 했으니 이대로면 지도에 `실무 경력 N년` 노드가 영영 안 생긴다.

원인: 정규화된 공고는 파서가 이미 `minYears`/`maxYears` 로 정형화해 주는데, 크롤링 행용인
`posting_floor_years(experience, …)` 를 불렀다. 정규화 공고에 `experience` 칸은 **없다**.
"같은 규칙을 두 곳에 두지 않는다"(D115)를 지키려다 **엉뚱한 계산기를 재사용**했다 —
재사용의 조건은 같은 규칙이 아니라 **같은 입력 모양**인데 그걸 확인 안 했다.

단위 테스트가 못 잡은 이유: 픽스처를 파서 실물이 아니라 상상대로(`experience: "경력 3년"`)
만들었다. 픽스처를 실물 모양으로 교체.

실 모델 1회(HTTP 200, 131초) 결과: `primaryTrack=BACKEND`, 역량 9건, 키 전부
`skill.<taxonomy-key>`(LLM 이 이름을 짓지 않았다), 정성 요건 걸러짐, `requiredLevel` 이
실제로 갈림(MySQL·REST API·AWS 4, 나머지 3), 검증 방법이 정형 문구가 아님
("쿼리 튜닝 전후 실행계획(EXPLAIN) 비교 결과").

## 3. 분석 진행 스트리밍

`docs/분석-진행-스트리밍-설계.md` §5 그대로 4곳: `models.py`(이벤트 스키마) ·
`stream.py`(신규 매퍼) · `service.analyze_events` · `app.py` 라우트.

**추가만 하는 변경이다** — 백엔드는 404/405 면 `/v1/analyses` 로 폴백하므로 스트림이 죽어도
분석은 안 깨진다. 시간 압박 속에서도 안전하게 넣을 수 있었던 이유.

지킨 불변식(백엔드가 검증하고 어기면 그 job 이 FAILED 로 끝난다):
`runId == analysisJobId`, sequence 1부터 엄격 증가·중복 없음, 첫 줄 RUN_STARTED,
마지막 줄 RESULT 또는 ERROR, RESULT 정확히 1건.

설계 결정 반영:
- **① 스테이지 1개 = 에이전트 1개.** 눈썹(`label`)=동작("공고 분석"), 제목(`role`)=담당
  ("공고 분석 담당"). 처음엔 둘 다 `agent_label` 이라 원 위에 같은 글자가 두 번 떴다.
- **② 툴 호출은 `STAGE_UPDATED.message`** — `도구 read_posting(전형, 복리후생) 호출 — <관찰 80자>`.
  인자(`arg`)도 싣는다(trace 에 있는데 안 쓰고 있었다).
- **③ RUN_STARTED 2단 발행** — 백본 4단계 → dispatch 확정 후 에이전트별 재발행.
- **④ 스테이지 12 상한** — 마지막 칸은 `RESULT_ASSEMBLY` 로 남기고 잘린 담당을 그 칸
  message 에 적는다(§2-6). **이벤트 예산 60건을 코드로 강제**(문서엔 목표만 있고 지키는
  곳이 없었다). 넘치면 진행 갱신만 멈추고 계획·결과·오류는 계속 낸다.
- **⑤ 색 6색 순환** — 7번째 스테이지부터 반복된다. 프론트 아이콘도 6종 순환이라 index 가
  맞물린 것이고, 색만 늘리면 아이콘과 어긋난다(늘리려면 프론트 아이콘 세트도 함께).

`OPEN_MAP` — `chat_actions(follow_ups, dispatched)` 로 인자를 하나 더 받아 `roadmap_manager`
또는 `application_plan` 이 돈 턴에 붙인다. **실행 사실로만 정한다** — 답변 문장을 뒤져
"로드맵을 만든 것 같다"고 추론하면 그건 재판정이다.

## 4. 게이트 정책 반전 — 분석이 절반 확률로 실패하던 원인

같은 입력 2회 중 1회가 `AI_PROVIDER_UNAVAILABLE`("왕복 상한 안에 판정에 이르지 못했어요").
**스트리밍을 붙인 덕분에 원인이 눈에 보였다** — `fit_analysis` 가 4번 반복되는 것이 그대로 찍혔다.

`sufficiency_rules` 가 두 군데서 막고 있었다. 둘 다 **경고로 남기고 진행**하도록 바꿨다:

1. **`undecidable_requirement`** — 옛 주석: *"사용자에게 직접 묻는 게 유일한 해결책"*. 두 번 틀렸다.
   - 유일하지 않다: `gap_matcher` 가 이미 LLM 으로 두 번 읽는다(배치 + 아래 3의 재시도).
     남은 uncertain 은 물어보기 전이라 모르는 게 아니라 **읽어도 모르는 것**이다.
   - 되물어도 못 묻는다: 이 질문에는 **선택지가 없어** v2 `NEEDS_INPUT`(선택지 2~4개 필수)로
     나갈 수 없다 → 서비스가 스스로 "정보 없음"으로 답하며 왕복 상한까지 반복 → 분석 전체 실패.
2. **`few_evidence`** — 근거 1건이면 정지. 이력서를 냈는데 지도가 통째로 안 나오는 경로였다.

**근거 0건은 여전히 막는다** — 신뢰도가 낮은 게 아니라 잴 것이 없는 것이다.
남은 uncertain 은 `_STATUS_SCORE` 가 분모에서 빼므로 미충족으로 둔갑하지 않는다(§2-1).

3. **배치 의미 판정 실패분 개별 재시도** (`gap_matcher._retry_missing_topics`).
   LLM 배치 호출 **하나가 서술형 요구사항 전부를 결정**하고 있었다. `semantic_judge` 주석이
   *"묶는 것은 호출이지 판단이 아니다"* 라고 적어뒀는데 실제로는 묶음이 실패하면 판단까지
   포기했다. 상한 8건, 첫 재시도가 실패하면 중단(공급자가 내려간 것이지 흔들림이 아니다).

   > 주의: 이번 503 의 직접 원인은 **아니었다**(로그상 배치는 성공). 그래도 단일 실패점이라
   > 방어는 남겼다. 원인을 배치 실패로 지목했던 중간 진단은 틀렸다.

§3-5 대로 옛 정책을 박아둔 테스트 2건은 지우지 않고 **뒤집은 근거를 적어** 반전 테스트로
교체했고, 여전히 막혀야 하는 경우(근거 0건)도 새로 박았다.

실 모델 재검증: **10 이벤트 · 150초 · COMPLETED**, 역량 9건, `experienceRequirement`
type=REQUIRED min=36.

## 5. 백엔드·프론트 (사용자가 팀원 허락을 받아 전달)

AI 는 진행 단계를 전부터 보내고 있었는데 **백엔드에서 버려지고 있었다.**

1. **`AiContracts.ChatResponse` 에 `progress` 신설** + `ProgressStep` 레코드.
   받을 칸이 없어 Jackson 이 조용히 버렸다.
2. **`AiAnalysisClient.chat(request, consumer)`** — `/v1/chat/stream` 소비, 404/405 면 단건 폴백.
   **결함 1건 발견**: 테스트가 `/v1/chat` 컨텍스트를 접두어로 매칭해 `/v1/chat/stream` 까지
   받아 단일 JSON 을 NDJSON 으로 읽다 대화가 통째로 죽었다. 프로덕션에서도 프록시가 스트림
   아닌 본문을 주면 같다 → **Content-Type 이 ndjson 이 아니면 폴백**. 스트림은 편의고 대화는 기능이다.
3. **`ChatReplyWorker.recordChatProgress`** — `chat_reply_jobs.stage/stage_message` 에 실시간 반영.
   마이그레이션·API·프론트 변경 없음(`ChatReplyJob` 에 이미 두 칸이 있고 프론트가 폴링 중).
   진행 기록이 실패해도 대화를 죽이지 않는다.
4. **URL 전용 공고 허용** — 대화창 좌측 공고 첨부에서 URL 만 넣으면 아무 일도 안 일어났다.
   - 프론트 `ChatView.vue`: 버튼 `:disabled` 와 함수 가드가 **따로** 있어 하나만 고치면 다른
     쪽이 막았다 → `canAttachPosting` computed 하나로 합침(오늘 세 번째 만난 "같은 규칙 두 벌").
   - 백엔드: `rawText` 의 `@NotBlank` 제거, `postingBody()` 가 URL 을 자리표시로 사용
     (`job_postings.raw_text` NOT NULL + AI 계약 최소 1자).
   - **AI**: `v2bridge.analyze` 가 `sourceType` 을 무시하고 항상 `text` 로 넘겨 **주소 문자열을
     공고 원문으로 파싱**하고 있었다(내용 0자). URL 자산으로 넘겨 `posting_fetch` 가 수집한다.
5. **입출력 조건을 AI 기준에 맞춤** — 프론트가 쓰던 20자는 근거 없는 숫자였다.
   AI 의 `attachment_kind.MIN_ASSET_CHARS = 40` 으로 프론트·백엔드 양쪽 정렬(주석에 출처 명기).
   20~39자는 UI 를 통과한 뒤 AI 가 자산으로 승격하지 않아 "저장은 됐는데 분석이 안 되는"
   공고가 됐다. URL 판별도 AI 와 같은 `startswith("http://"|"https://")` 로 통일.

## 6. 남은 것

- **`decisions.md` D 항목 미작성.** 오늘 결정이 여러 건이다(도구 노출 / 가드 통합 / 대체 1회 /
  상한 유지 / ai-server 는 정본이 아님 / 게이트 정책 반전 2건 / **외곽 오케스트레이터를
  ReAct 로 바꾸지 않는다**). 마지막 건은 "안 하기로 한 결정"이라 근거와 함께 남길 값어치가 크다.
- **`/v1/competency-assessments` 없음** → 역량 검증 화면이 통째로 죽어 있다(계약 문서 §4-8).
- **URL 전용 공고의 `raw_text` 가 주소다.** AI 가 수집한 원문은 `parsedData` 에 들어가지만
  채용공고 페이지의 "원문" 칸은 주소로 보인다. `AnalysisWorker` 가 분석 후 되메워야 한다.
- **채팅 진행은 현재 단계 1개만 보인다** — `stage_message` 를 덮어쓰므로 지나간 단계가 안 쌓인다.
  타임라인 전체(=휠)를 채팅에도 붙이려면 `chat_reply_jobs` 에 jsonb 컬럼(마이그레이션) 필요.
- **`loop_consistency` 하네스가 `posting_analysis` 를 안 돈다** — 도구를 붙인 그 에이전트가
  측정 대상이 아니다. 재는 방법이 없는 변경을 넣은 셈이라 케이스 추가가 다음 순서.
- **색 6색 순환** — 담당이 5개를 넘는 턴에서 색이 겹친다(프론트 아이콘 세트와 함께 늘려야 함).
- **`compose.yaml` 은 여전히 `ai-server` 를 띄운다** — 컨테이너 배포에는 이 작업이 반영되지 않는다.
  로컬 시연은 무관하지만 배포로 갈 거면 인프라·백엔드와 합의가 필요하다.
