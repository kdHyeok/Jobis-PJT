# 2026-08-03 (밤) — 에이전트를 무상태로: 자산의 집을 PostgreSQL 로

사용자가 정한 규칙(이 세션 확정):

> **PostgreSQL 은 처음부터 정한 DB다.** SQLite 는 에이전트가 잘 도는지 검증하려고 임의로
> 정한 것이고, **에이전트의 발화·대화부터 이력서·공고·파생 정보까지 전부 PostgreSQL 에
> 적재되는 게 맞다.** 삭제는 지양하고, 새 테이블·칼럼을 만드는 것은 괜찮다. 시간이 걸려도 된다.

## 0. 방향 — ⓐ 가 아니라 ⓑ

| | 계약의 성격 | `resume` 예 |
|---|---|---|
| 지금 | 에이전트 ↔ **저장소**(`ASSET_KEYS`: 키 → JSON, SQLite) | `assets['resume'] = {sourceType, value}` |
| **ⓐ (안 한다)** | 같은 저장소 계약을 엔진만 바꿔 옮김 | PG 에 `ai_sessions` 테이블 + 같은 JSON → `career_sources` 와 **같은 사실이 두 곳** |
| **ⓑ (한다)** | 에이전트 ↔ **백엔드** 메시지 계약 | 요청 `career.resumes[]` 로 받고, 새로 받은 것은 응답 `collected` 로 올려 백엔드가 적재. 세션은 **턴 동안만** |

ⓑ 의 핵심은 **에이전트가 저장소를 갖는 것을 그만두는 것**이다. 우리 자산 키가 PG 테이블이
되는 게 아니라, 백엔드에 **이미 있는 도메인 모델로 번역**된다 — 그래야 테이블마다 writer 가
하나로 유지되고 RLS·마이그레이션 소유가 백엔드 한 곳에 남는다. 오늘만 해도 `parsedData`·
`companyName` 을 계약에서 뺐다(`AnalysisWorker` 가 이미 그 열의 유일한 writer 다).

v2bridge docstring 이 이미 선언해 둔 것이기도 하다: **"매 요청이 문맥 전부다."** 지금 SQLite
파일이 턴을 넘어 살아 있는 이유는 백엔드가 안 보내주는 것이 있어서다.

## 1. 자산 → 목적지 (실제 스키마 대조 완료)

### 이미 PostgreSQL 에 있는 것
| 자산 | 목적지 | 비고 |
|---|---|---|
| `history` | `conversation_messages` | 백엔드가 씀. 세션 것은 사본 |
| `job_posting` · `posting_summary` | `job_postings.raw_text` · `.parsed_data` | D141(대화 적재) + `AnalysisWorker`(파싱) |
| `posting_library` | `job_postings` 여러 행 (`conversation_id` 로 묶임) | 요청으로 재구성 가능 |
| `resume` | `career_sources.raw_text` | D141 로 적재 시작 |
| `resume_library` | `career_sources` 여러 행 | `_label`→`title`, `_origin`→`source_type` 로 번역 |
| `preferences` · `user_facts` | `user_goal_profiles.chat_preferences` · `.chat_facts` | V22 |
| `last_message` · `userId` | (턴 입력) | 영속 대상 아님 |

### 칼럼을 새로 만들 것
| 자산 | 목적지 | 왜 새 칼럼인가 |
|---|---|---|
| `analysis`(엔진 형식) · `judgment_summary` · `roadmap` | `analysis_jobs.engine_result jsonb` (신규) | `result_data` 는 **v2 형식**(job·evaluation·competencyProposal)이다. 엔진 형식(fitGrade·gaps·roadmap)을 그 안에 섞으면 백엔드 파서가 읽는 계약이 흐려진다. 옆 칼럼이 정직하다 |
| `preparationPeriodWeeks` · `availableHoursPerWeek` | `user_goal_profiles` 2칼럼 | 이미 사용자별 목표 프로필의 집 |
| `profile`(정규화 프로필) | `career_sources.summary`? → **아니오**, `ai_user_profiles`(신규 1행/사용자) | 이력서 원문에서 파생한 캐시다. `career_fragments`/`career_nodes` 는 사용자가 확정한 커리어 모델이라 층이 다르다 — 파생 캐시를 거기 섞으면 확정본과 추정본이 뒤섞인다 |

### 테이블을 새로 만들 것
| 자산 | 신규 테이블 | 이유 |
|---|---|---|
| `recommendations` | `posting_recommendations` | 대화의 산출물이고 `posting_catalog`(크롤 카탈로그)와 다르다 — 그건 전체 공고 풀이고 이건 이 사용자에게 준 추천이다 |
| `coverletter` | `coverletter_drafts` | 산출물(초안). 항상 `draft_pending_review` |
| `interview` | `interview_sessions` | 여러 턴 상태(물은 질문·받은 답·쓴 주제). 대화 이력에서 재파싱하는 것보다 정직하다 |
| `application_plan` | `application_plans` | 목표 상태·지원 경로 판정 |
| `unsupported_requests` | (테이블 안 만든다) | 계측용이고 `scripts/harvest_sessions.py` 가 SQLite 를 읽는다. **이 스크립트가 SQLite 의 마지막 소비자** — 무상태 전환의 맨 마지막에 정리 |

### 턴 상태 — 영속시킬 것과 아닌 것을 가른다
| 자산 | 판단 |
|---|---|
| `pendingConsent` | 대화 이력에서 복원 가능(직전 assistant 메시지가 물은 것) → **영속 안 한다** |
| `pendingRequest` | `{agent, missing, turnsLeft}` — 남은 턴 카운터가 있어 이력에서 못 복원 → `conversation_messages.metadata` 에 실어 보낸다(백엔드가 이미 그 칼럼을 쓴다) |
| `analysis_key` | `analysis_jobs.engine_result` 와 함께 두면 파생 가능(공고·이력서 지문) → **영속 안 한다** |
| `_agentArgs`·`_submittedThisTurn`·`_stagedUpdates` | 턴 내부 — 애초에 저장 대상 아님 |

## 2. 슬라이스 (검증 가능한 단위로 자른다)

각 슬라이스는 **그 자체로 동작하고 회귀가 초록불**이어야 한다. SQLite 삭제는 맨 마지막이고,
그때까지 세션 저장소는 그대로 둔다 — 요청이 문맥을 온전히 주면 자연히 안 읽히게 된다.

1. **요청 계약 확장 — 이력서·라이브러리** (`ChatRequest.career`)
   백엔드는 `career_sources` 를 이미 갖고 있다. `resumes[]`(title·sourceType·rawText)를 보내면
   AI 는 세션의 `resume`·`resume_library` 를 요청에서 세운다.
2. **요청 계약 확장 — 선호·사실** (V22 로 적재한 것을 되돌려 받기)
   지금은 올려 보내기만 하고 받지 않아서, 다음 턴이 세션 파일에 의존한다.
3. **요청 계약 확장 — 공고 라이브러리** (`postings[]`, 이 대화의 공고들)
4. **판정 산출물 적재** (`analysis_jobs.engine_result` 신규 칼럼 + 응답 계약)
   교차 재사용(D143 이 못 한 것)이 여기서 자연히 풀린다 — 채팅과 분석 작업이 같은 판정을 본다.
4-b. **로드맵을 대화에서 만든다 (D142 뒤집기)** — 사용자 지시:
   *"로드맵 생성까지 에이전트 대화를 통한 자산과 LLM 으로 생성되게"*.
   `ChatResponse.collected` 에 지도 재료(`competencyProposal`)를 실어, 대화 턴이 **유일한
   생산자**가 된다. 백엔드는 `AnalysisWorker` 가 하던 적재(`user_competencies` ·
   `posting_competency_requirements` · `posting_target_projects` · `roadmap_targets`)를 채팅
   응답에서도 한다. D142 의 의도(생산자는 하나)는 유지하고 **생산자를 옮기는** 것이다 —
   오늘 D142 는 생산자를 분석 작업으로 골랐는데, 그 작업은 백엔드가 의도를 확정하는 고정
   파이프라인이라 루프가 돌지 못한다(D145 의 진단과 같은 뿌리).
   `/v1/analyses` 는 지우지 않는다(진행 휠·재분석 UI 가 쓴다) — 주 경로에서 안 타게만 한다.
5. **프로필 적재** (`ai_user_profiles`)
6. **산출물 테이블 4개** (`posting_recommendations`·`coverletter_drafts`·`interview_sessions`·`application_plans`)
7. **`pendingRequest` 를 메시지 메타데이터로**
8. **SQLite 를 턴 내부 캐시로 축소** — `SESSION_STORE=memory` 로 돌려도 대화가 이어지는지
   실측으로 확인한 뒤, 기본값을 memory 로 바꾼다. **파일 삭제는 그다음**이고
   `harvest_sessions.py` 를 먼저 옮긴다.

## 3. 지키는 규율

- **삭제 지양**: 기존 칼럼·테이블·엔드포인트를 지우지 않는다. 새 칼럼/테이블로 더한다.
- **writer 는 하나**: 이미 백엔드가 쓰는 열은 계약에 넣지 않는다(오늘의 `parsedData` 교훈).
- **추가만 하는 변경**: 요청·응답 계약은 새 필드를 optional 로 더한다 — 백엔드가 안 보내도
  안 읽어도 지금 동작이 깨지지 않는다.
- **각 슬라이스마다** AI 회귀 + 백엔드 `test` + 실경로 1회.
