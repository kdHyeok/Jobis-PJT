핵심 질문은 **"도구는 말을 하는가"** 다. 지금 `job_recommend` 는 검색·랭킹(결정론)도 하고

**한 일**
- `AgentSpec.kind`(`tool` | `agent`) + `AgentSpec.render` 선언. 구분 기준은 하나 —
  **말을 하는가.** 도구는 `entry` 에서 reply 를 비우고 데이터만 내고, 문장은
  `agents/tool_render.py`(표현 계층)가 만든다.
- 구분에서 따라 나오는 규칙을 코드로 강제: **도구 뒤에는 관찰(observe)을 걸지 않는다**
  (결정론이라 재선택 여지가 없다 — 값도 못 바꾸면서 LLM 비용만 낸다).
- `job_recommend`·`roadmap_manager` 를 도구로 전환. **문장 생성 코드를 그대로 옮겼다**
  → 출력이 한 글자도 바뀌지 않아 E2E 재검증 부담이 없었다(하루 추정이 몇 시간으로 줄어든 이유).
- 테스트가 규약을 강제한다: 도구는 reply 를 만들지 않는다 / 도구는 render 를 반드시 갖는다 /
  에이전트는 render 를 갖지 않는다 / 도구 뒤에 관찰이 걸리지 않는다.

**A-잔여** ✅ **완료 (2026-07-29)** — `fit_analysis` 를 도구로 내렸다.

### 질문 ② — **재정의됨: 동의 게이트를 플래너가 우회할 수 있다** (근본 원인 발견)

S5 의 불안정을 파고들다 표면 문제가 아니라 **결정론 결함**을 찾았다.

`router.validate_plan` 의 게이트 조건:
```python
requested = set(agents)                     # ← 플래너의 선택
inserted_heavy = [n for n in plan if n not in requested and registry[n].heavy]
```

게이트가 막으려는 것은 **"사용자가 청하지 않은 무거운 작업"** 인데, *"플래너가 고르지 않았다"* 를
그 **대용품**으로 쓰고 있다. 플래너도 전제를 추론해 넣으므로 대용품이 샌다 — 실측 S5:
플래너가 스스로 `[fit_analysis, coverletter_draft]` 를 골라 `fit_analysis` 가 requested 에
들어가고 **수십 초 파이프라인이 말없이 돌았다.**

**계획만으로는 구분할 수 없다** — 차이는 발화에만 있다:

| 발화 | 플래너 선택 | 게이트가 걸려야 하나 |
|---|---|---|
| "분석하고 면접 질문도 준비해줘" | `[fit_analysis, interview_prep]` | ❌ 사용자가 분석을 청했다 |
| "자소서 써줘" | `[fit_analysis, coverletter_draft]` | ✅ 플래너가 전제로 추론했다 |

**제안 해법 — 프롬프트 조건이 아니라 스키마로.** ①의 교훈대로 프롬프트에 일곱 번째 조건을
넣지 않는다. 플래너가 *"사용자가 청하지 않았지만 전제로 넣은 것"* 을 스스로 신고하게 한다:

```python
class AgentPlan(BaseModel):
    ...
    inferredPrerequisites: list[AgentName] = Field(default_factory=list, description=(
        "agents 에 넣었지만 **사용자가 청하지는 않은** 항목 — 요청을 수행하려면 전제로 필요해서 "
        "네가 판단해 넣은 것만. 사용자가 직접 요청한 것은 넣지 않는다."))
```

게이트는 `자동 삽입분 ∪ (신고분 ∩ heavy)` 에 걸린다. **판단은 LLM, 행동은 코드** — 이 저장소의
분업 그대로이고, 프롬프트 산문이 아니라 **필드**라 ①의 간섭 실패 모드를 피한다.

착수 전 계측 필요(GMS 크레딧) — 확인할 것 둘:
1. 플래너가 이 필드를 정확히 채우나 (위 표 두 발화가 갈리나)
2. 기존 46케이스 회귀 없나

`eval/consistency.py` S5 와 `router.validate_plan` 에 이 구멍을 주석으로 박아 뒀다.
**기대값을 고쳐 초록으로 만들지 않았다** — 구멍이 닫히기 전에 덮으면 그 사실이 사라진다.

> **→ 닫혔다 (D44 → D50).** 위 제안(`inferredPrerequisites` 신고)을 D44 로 넣었으나, 그것은
> **fail-open** 이었다 — 모델이 신고 칸을 비우면 게이트가 통과였고, 통과 경로 하나("동의하면
> 다음 턴에 플래너가 명시적으로 고를 것")는 아예 기록 없는 모델 기대였다. D50 에서 스키마를
> 긍정형(`requestedAgents`)으로 뒤집어 **모르면 묻게** 하고, 동의를 `session["pendingConsent"]`
> 에 적어 통과 조건 둘을 모두 코드가 확인한다. 남은 것은 **실 LLM `ask_accuracy` 재측정**뿐이다
> (D44 의 1.00 은 옛 스키마 기준).

### 로컬 모델로 바꾸는 법 — `.env` 만 고친다 (코드 변경 없음)

`llm.py` 의 `openai` 경로가 `base_url` 을 그대로 받으므로 **OpenAI 호환 서버**(vLLM · TGI ·
Ollama `/v1` · llama.cpp server)면 그대로 붙는다:

```bash
LLM_PROVIDER=openai
LLM_BASE_URL=http://<gpu-host>:8000/v1     # 로컬 서버
LLM_MODEL=<모델명>                          # 고급 티어 — 플래너·추출·생성
LLM_MODEL_LIGHT=<모델명>                    # 경량 티어 — 분류·이진판정
GMS_KEY=dummy                              # ★ 비어 있으면 LLMNotConfiguredError 로 막힌다
                                           #   (config.has_llm_key 가 bool(gms_key) 를 본다)
LLM_TEMPERATURE=0.3
LLM_MAX_TOKENS=4096
```

임베딩은 손댈 필요 없다 — `EMBED_PROVIDER=null` 기본이고 `gap_matcher` 는 07-20 부터
임베딩을 쓰지 않는다.

### ⚠️ 첫 번째로 확인할 것 — **function calling 지원 여부**

`structured.py` 는 구조화 출력을 이렇게 얻는다:

```python
method_kwargs = {"method": "function_calling"} if provider == "openai" else {}
structured_llm = llm.with_structured_output(schema, **method_kwargs)
```

즉 **OpenAI 스타일 tool calling 을 요구한다.** 로컬 서버가 `tools` 를 구현하지 않거나 모델이
못 하면 **모든** 구조화 호출이 3회 재시도 후 실패하고(`llm_call_failed`) 플래너가 `None` 을
내며 전 턴이 `career_chat` 으로 후퇴한다 — 그러면 "로컬 모델이 형편없다"로 **오진**하게 된다.

- 하네스가 이걸 구분해 준다: `llm_failed` 는 정확도와 **따로** 집계된다.
  `llm_failed` 가 크면 모델 품질이 아니라 **프로토콜 문제**다.
- 지원하지 않으면 `structured.py:run_structured` 의 `method_kwargs` 를
  `{"method": "json_schema"}` 또는 `{"method": "json_mode"}` 로 바꿔 시험한다
  (langchain-openai 가 셋 다 지원). **환경변수로 뽑아 두는 것이 좋다** — 예: `STRUCTURED_METHOD`.
- 가장 어려운 스키마는 **플래너**다(`AgentPlan`: `Literal` 에이전트 목록 + 중첩 `AgentArg` 배열).
  여기가 통과하면 나머지는 대개 통과한다.

### ⚠️ 두 번째 — 약한 모델의 알려진 실패 모드 (지표를 새로 넣어 뒀다)

`gpt-4.1-nano` 실측(07-28): **에이전트와 인자는 정확히 고르면서 `confidence` 를 0.00 으로
채웠다.** 임계값(0.6)에 걸려 전부 `career_chat` 으로 후퇴 → "라우팅을 못 한다"로 보인다.

그래서 하네스 출력에 **`paths` 분포 · `mean_confidence` · `fallback_rate`** 를 추가했다.
읽는 법:

| 증상 | 원인 | 처방 |
|---|---|---|
| `llm_failed` 높음 | 구조화 출력 프로토콜 | `method` 교체 (위) |
| `fallback_rate` 높고 `mean_confidence` ≈ 0 | 모델이 `confidence` 필드를 못 채운다 | `CONFIDENCE_THRESHOLD` 조정 또는 스키마 description 보강 |

| `unstable` 만 높음 | 흔들림 | 온도↓ — 단 GMS 에서는 효과 없었다(0.942→0.949) |

## [예약] 파일 업로드 통로 — 대화창 이력서 첨부 + 파일 원본 전달 (2026-08-02 계획, 실행은 저녁)

**결정된 것: 파일 전달은 (A) 공유 디렉토리 경로.** 백엔드가 저장하고 절대경로를 AI 에 넘긴다.
엔진 변경 0(`extract_text` 가 이미 `sourceType=file` 을 처리). 대신 **백엔드·AI 동일 호스트
전제**이므로 코드에 `# ponytail: 동일 호스트 전제. 호스트가 갈리면 presigned URL 로.` 를 남긴다.
(B) base64 는 100k 상한 충돌·페이로드 팽창으로, (C) 오브젝트 스토리지는 인프라 부재로 뺐다.

### 왜 — 엔진은 읽을 수 있는데 통로가 없다
`extract.py:73-95` 는 `.docx/.pdf/.txt/.md` + 이미지(Clova VLM)를 읽고, 엔진 대화 계약
`ChatAttachment` 도 `sourceType=file` 을 받는다. **막힌 것은 그 위 세 계층이 전부 텍스트 전용**
이라는 점이다:
- `POST /api/conversations/{id}/messages` → `posting{sourceType: TEXT|URL}` 뿐. **이력서 슬롯 없음**
- v2bridge `ChatRequest{conversation_id, display_name, messages, career}` → **첨부 필드 자체가 없다**
  (`promote_pasted_posting()` 이 발화 텍스트에서 추론할 뿐)
- `POST /api/career-sources` → `sourceType` 에 FILE 이 있는데 `rawText @NotBlank(20~100k)` 라
  바이트를 담을 자리가 없다. 프론트가 `file.text()` 로 읽어 문자열로 보낸다
- `ChatView.vue` 첨부 = 공고 전용, `<input type="file">` 없음

그래서 **D114 의 `uploaded` origin 분기는 지금 도달 불가능한 죽은 코드다.**

### 실행 순서 (아래 계층부터 — 그래야 위에서 테스트가 된다)
1. v2bridge `models.ChatRequest` 에 `attachments: list[ChatAttachment] = []`(하위호환) +
   `service.chat_events` 가 추론 결과와 합친다. **명시 첨부가 추론보다 우선.**
2. 백엔드 `POST /api/uploads`(multipart) → `{uploadId, fileName, contentType, size}`.
   **신뢰 경계 검증은 줄이지 않는다**: 확장자 allowlist(pdf docx txt md png jpg jpeg webp) +
   content sniffing(확장자만 믿지 않는다) + 10MB 상한 + **클라이언트 파일명을 경로로 쓰지 않는다**
   (UUID 저장, 원본명은 메타로만) + 사용자 스코프(RLS)
3. `SendMessageRequest` 에 `resume` 첨부 추가, `PostingAttachmentRequest` → `AssetAttachmentRequest`
   일반화(`sourceType` 에 FILE 추가). 백엔드 → AI 전달 경로는 `ChatReplyWorker` 경유 확인 필요
4. `ChatView.vue` 첨부 모달을 `공고 | 이력서` 2단으로, 이력서는 `붙여넣기 | 파일`.
   `attachPosting()` → `attachAsset(kind)` 일반화
5. `StorageView.vue` 의 `await file.text()` 제거, 같은 업로드 경로로 통일. `accept` 확장.
   `CreateSourceRequest.rawText @NotBlank` 완화(FILE 이면 uploadId 로 대체)
6. **실 브라우저 E2E 1회**(§3-7): PDF 이력서 업로드 → `origin=uploaded` 확인 →
   이력서 2건 비교 → D114 전체가 실경로에서 도는지

### 안 하기로 한 것
- 파일 보존·정리(TTL 삭제): 안 만든다. 저장 경로와 미삭제 사실만 `ponytail:` 로 남긴다
- 바이러스 스캔·OCR 품질 튜닝: 범위 밖
- **지름길(계약 안 늘리고 본문에 이력서를 붙여넣어 `detect_pasted_resume` 추론 승격)은 안 쓴다** —
  동작은 하지만 origin 이 영원히 `pasted` 이고 `content` 20,000자 제한에 걸려, D114 의 절반이
  죽은 채로 남는다

### 측정
AI 유닛(`test_v2bridge_contract`·`test_url_intake`) + 백엔드 테스트 + E2E 1회.
**프롬프트·manifest 를 안 건드리므로 플래너/consistency 재측정은 불필요.**
