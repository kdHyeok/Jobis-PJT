# 2026-07-29 — 개편 B·C단계 + A-잔여 (실측으로 잡은 결함 3건)

계획대로 **B단계(`coverletter_draft` → `agent_loop`)** 를 했다. `agent_loop` 계약의 두 번째
적용이고, 목적의 절반은 그 계약이 다른 일에도 맞는지 확인하는 것이었다. 맞았다 — 하네스는
한 줄도 고치지 않고 붙었고, **고친 곳은 계약이 아니라 계약과 모델 사이의 마찰 지점**이었다.

---

## 1. 무엇을 바꿨나

전에는 LLM 을 한 번 불러 3문단을 받아 그대로 내보냈다. 자소서 작성의 본질은 그게 아니다 —
쓰고 나서 "근거가 붙었나 / 공고 요건을 다뤘나 / 분량이 되나"를 확인해 고치는 일이 반복된다.
한 번 생성으로 끝나는 구조에는 그 반복이 일어날 자리가 없었다.

| | 도구(결정론) | 에이전트(LLM) |
|---|---|---|
| `find_evidence` | 이력서에서 확인된 사실을 준다 | |
| `save_draft` | 문단을 기록한다(**적어 보낸 문단만** 갱신) | 무엇을 어떻게 쓸지 |
| `check_draft` | 빈 문단·금지표현·근거 없는 기술·문단 분량·요건 커버리지·부족 역량 언급을 **센다** | 지적 중 무엇을 고칠지 |

**근거의 출처를 갈랐다**: 공고 쪽(요건·부족 역량)은 *과제*라 프롬프트에 싣고, 이력서 쪽은
*근거*라 `find_evidence` 만 준다. 없는 경험을 쓰는 길을 프롬프트 부탁이 아니라 구조로 막는다.

**화면에 나가는 본문은 검증 통과본으로 결정론 조립한다**(`_render_draft`). LLM 에게 본문을
reply 에 옮겨 적게 하면 검증 전 문장이 사용자에게 가고, 화면과 저장분이 갈라진다. LLM 은
"이번에 무엇을 고쳤는지" 안내만 쓴다. 검토 게이트(P5) 문장은 LLM 과 무관하게 **항상** 붙는다
— 규칙을 부탁으로 두지 않는다.

여러 턴 상태도 생겼다: 세션 자산 `coverletter` 를 이어받아 **지목된 문단만** 다시 쓴다.
`params=(("focus", …))` 로 "강점 문단만 다시 써줘" 가 플래너를 통해 전달된다. 전에는 reply 가
"수정하고 싶은 문단을 말씀해 주시면 다시 다듬어 드릴게요" 라고 약속만 하고 코드에는 그
통로가 없었다.

## 2. 실측 (GMS, `gpt-4.1-mini`)

단위 테스트만으로는 부족하다는 규율대로 실제 모델로 돌렸다. 1턴:

```
step1 find_evidence('React, TypeScript, Kafka') → 확인된 사실 1건
step2 save_draft            → 작성 1회 / 동기 189자, 강점 173자, 보완 122자
step3 check_draft           → 공고 요건 커버리지 3/3 | 분량 기준(3~5문장) 밖: 보완 계획 2문장
step4 save_draft(보완만)     → 작성 2회 / 보완 계획 171자          ← 자기비판 → 재작성
step5 reply
```

2턴("강점 문단이 밋밋해요, 수치를 넣어 다시"): 이전 초안을 이어받아 **강점 문단만** 재작성.
넣은 수치는 지어낸 것이 아니라 근거에 있던 값이었다 — "드래그앤드롭 렌더링 최적화로 노드
500개에서 프레임 드랍 제거". 2스텝으로 끝났다(쓸 도구가 적으면 적게 돈다).

## 3. 실측으로 드러난 결함 3건

### ① 모델이 `action` 칸에 도구 이름을 쓴다 → 턴이 통째로 실패 (하네스)

첫 실행이 이렇게 죽었다: `action="save_draft"`. 스키마는 `action ∈ {use_tool, reply}` 이고
도구 이름은 `tool` 칸이므로 Literal 이 막았고, **3회 재시도 끝에 자소서 턴 전체가 실패**했다.

두 칸에 나눠 담는 것은 우리 사정이지 모델이 자연스럽게 하는 표기가 아니다. 막아야 할 것은
**없는 도구**지 표기가 아니므로, `action` 의 허용값에 등록된 도구 이름을 더하고 하네스가
정규화한다. 환각 차단(등록된 이름만)은 그대로다.

> 교훈: 구조로 막을 때는 **무엇을 막는지** 분명히 해야 한다. 여기서 막을 것은 이름의
> 실재성이었는데, 실제로는 표기 형식까지 막고 있었다.

### ② 산출물에 붙은 수치가 산출물을 잰 값이 아니었다

`lastCheck` 에 루프 도중의 마지막 점검을 그대로 실었더니, 보완 문단을 3문장으로 고쳐 놓고도
저장분에는 **2문장(고치기 전 값)** 이 남았다. 점검 뒤에 재작성이 일어나고 검증이 문장을
지우므로, 도중값은 산출물을 설명하지 못한다. 점검을 순수 함수(`_check_report`)로 빼고
**내보내는 초안을 다시 재서** `check` 로 싣는다. 루프의 점검 도구와 최종 측정이 같은 자를 쓴다.

### ③ `interview` 자산을 세션이 저장할 수 없었다 (A/2단계 회귀)

`interview_prep` 은 `produces=("interview",)` 로 다중 턴 상태를 내는데 `ASSET_KEYS` 에
그 키가 없었다. 턴 끝 write-back 이 `KeyError` 로 터진다 — 즉 **면접 연습 턴은 실서버에서
매번 실패했다.** 재현 확인 후 키를 추가했고, 다시 어긋나지 않도록 테스트로 강제한다:
*모든 에이전트가 만든다고 선언한 자산은 세션 저장소가 받는 키여야 한다.*

> 교훈: 선언(`produces`)과 허용 목록(`ASSET_KEYS`)이 두 곳에 따로 있으면 조용히 갈라진다.
> 둘을 대조하는 테스트가 곧 단일 출처의 대용품이다.

부수적으로 하나 더: 2턴에서 루프가 `check_draft` 없이 바로 답한 적이 있다. 고칠 기회는
지났지만 묻히지는 않게, 최종 측정에 남은 지적이 있으면 `coverletter_check_unresolved`
경고로 싣는다.

## 4. A-잔여 — `fit_analysis` 를 도구로 내렸다

표현(등급 헤드·준비기간 가정 문구·대안 공고 블록·LLM 다음 행동 제안)을 전부
`tool_render.render_fit_analysis` 로 옮기고, `entry` 에는 "무엇을 계산했나"만 남겼다.
실측으로 답변 형태가 그대로인 것을 확인했다(등급/요약/대안 3건 URL/다음 행동 질문).

옮기는 과정에서 **계약 두 개를 손봐야 했다.** 둘 다 "규칙의 근거가 무엇인가"를 되물어서
나온 결론이다:

**① `render` 가 `(문장, 경고)` 를 낸다.** 다른 도구의 표현은 결정론이라 문장만 돌려주면
됐지만, 다음 행동 제안은 LLM 스트리밍이라 폴백할 수 있다. 문장만 돌려주는 계약에서는
"왜 기본 문구가 나왔는지"가 사라진다 — 0728·0729 에 두 번 대가를 치른 실수라 계약을 바꿨다.

**② `AgentSpec.observe` 예외를 뒀다.** A단계에서 "도구 뒤에는 관찰을 걸지 않는다"를 코드로
강제했는데, 그 근거는 *결정론이라 재선택 여지가 없다* 이지 *도구라서* 가 아니다.
`fit_analysis` 는 결과(등급·need_more_info)가 뒤에 예정된 자소서·면접의 타당성을 실제로
바꾸므로 근거가 성립하지 않는다. 그대로 뒀다면 **가장 재선택이 필요한 지점에서 관찰이
조용히 꺼졌을 것이다.**

> 교훈: 구분에서 규칙을 끌어낼 때는 규칙의 **근거**를 함께 적어야 한다. 근거를 적어 두면
> 근거가 성립하지 않는 항목을 나중에 알아볼 수 있다. `kind` 만 보고 분기하면 못 알아본다.

## 5. C단계 — 평가 문서 재평가

`_docs/agent/멀티에이전트_구현_평가_및_개선방안.md` 의 *"엄밀히는 지능형 라우터 +
파이프라인"* 판정을 다시 썼다. 1차 판정의 뼈대였던 근거가 뒤집혔기 때문이다.

07-28 계측: **"LLM 이 다중 시퀀스를 계획한 경우 8턴 중 0건"** (둘 이상 돈 것은 전부 검증기의
생산자 자동 삽입). 07-29 실측:

```
planner:  원안=['posting_analysis','resume_diagnosis','fit_analysis'] 확신=0.90
dispatch: 확정=['posting_analysis','resume_diagnosis','fit_analysis']   ← 삽입 0건
```

"공고를 정리하고 → 이력서를 진단하고 → 둘을 대조한다"는 순서는 코드 어디에도 없다.
1차 지적 §2·§3·§4 전 항목을 파일·줄 번호와 함께 표로 대조했고, 6개 우선순위는 전부 반영됨을
확인했다(팬아웃 병렬, 표현 계층 스트리밍, 플래너 프롬프트 정적화, 재시도 단일화,
세션 write-back, 동의 게이트).

**그래도 등급은 C→B 까지만 올렸다.** 증명하지 못한 것을 그대로 남겼다:
관찰이 실행을 바꾼 사례 **0건**(관측된 결정은 전부 continue/finish), 에이전트 간 통신 없음,
에이전트 시퀀스 병렬 없음. 그래서 새 우선순위 1번은 기능 추가가 아니라
**"관찰이 값을 하는지 계측"** 이다 — 값을 못 하면 걷어내는 것도 선택지로 적었다.

## 7. 오후 — ack 중복 · 시퀀스 병렬 · 에이전트 간 통신

### ① ack 중복 (사용자 눈에 보이던 결함)

면접 턴이 `"면접 연습을 시작하겠습니다. 면접 연습을 시작하겠습니다. 첫 질문입니다: …"` 로
나갔다. 플래너 ack 와 에이전트 첫 문장이 같은 말이었다. 전에는 대화형 에이전트 두 개만
예외 목록으로 막고 있었는데, 그 규칙의 **일반형**을 찾았다: ack 는 *계획을 설명하는 문장*
이다 → 설명할 계획이 하나뿐이고 그 에이전트가 스스로 말하면 싣지 않는다. 여럿을 돌리거나
검증기가 계획을 바꿨을 때만 싣는다. 라우팅 가시화는 ack 가 아니라 `intent` 가 맡는다
(프론트가 에이전트 이름을 칩으로 보여준다 — `ask.html` AGENT_KO).

### ② 시퀀스 병렬 (`chat.parallel_group`)

서로의 산출을 기다리지 않는 **연속 구간**을 동시에 돌린다. 독립 판정은 새 개념이 필요 없었다
— capability manifest 가 이미 답을 갖고 있다(앞이 `produces` 하는 자산을 뒤가 전제로 쓰면
순서가 있다). 실측: `posting_analysis ∥ resume_diagnosis ∥ fit_analysis` 순차 평균 21.3초 →
병렬 15.6초.

규율 셋을 코드에 박았다: **세션 사본**(남의 턴 중 변경을 보고 판단하지 않는다) · **결과는
큐 순서대로 합친다**(병렬이 답변 순서를 흔들면 안 된다) · **토큰 델타는 끈다**(프론트가 한
버퍼에 이어 붙여서 두 에이전트 토큰이 섞인다).

**선빌드 최적화는 넣었다가 뺐다.** 여러 멤버가 각자 프로필을 짓는 중복을 막으려 했는데,
브릿지 실측에서 `dispatch → parallel` 사이에 **8.3초**가 찍혔다. 전제에 resume 이 있다고
프로필을 쓰는 게 아니었다 — `fit_analysis` 는 그래프 안에서 따로 짓는다. 즉 대부분의 턴에서
헛돈이었다. 빼고 나니 그 간격이 0초가 됐다.

> 교훈: 최적화도 실측으로 확인해야 한다. "중복을 없앴으니 빨라졌겠지"가 임계 경로에
> 8초를 얹고 있었다. 단위 테스트는 이걸 절대 못 잡는다.

### ③ 에이전트 간 통신 (`agent_loop.delegate_tool`)

자기 루프 에이전트가 루프 안에서 다른 담당을 직접 부른다. 첫 소비자는
`coverletter_draft` → `resume_diagnosis`: 쓸 근거가 빈약할 때 *무엇이 왜 빈약한지*는
이력서 진단이 이미 세고 있으므로, 같은 계산을 두 번 구현하는 대신 물어본다.

**좁게 연 것이 설계의 핵심이다.** 읽기 전용(상대의 sessionUpdates 미적용 — 상태 전이는
오케스트레이터 독점) / 화이트리스트에 선언한 상대만 / `heavy` 금지(동의 게이트 우회 방지) /
전제 미충족이면 실행 안 함 / 중첩 금지 / 상대의 경고를 그대로 올림.

도구가 경고를 낼 자리가 없던 것도 이때 고쳤다 — `TOOL_WARNINGS_KEY` 표준 키로 담으면
하네스가 `LoopOutcome.warnings` 로 올린다. 남의 실패 이유를 삼키지 않기 위해서다.

예정돼 있으면 끊는다)을 **관찰 LLM 에 맡겨 뒀고 그 관찰은 한 번도 발동하지 않았다.**

등급 `하`·`판정불가` + 생성 단계 예정 → `application_plan` 으로 강제 교체. **"중" 은 넣지
않았다** — 0.4~0.7 은 사람마다 갈리는 구간이고, 갈리는 판단을 코드로 못 박는 것이 이 규칙이
피하려는 실수다. 그리고 규칙은 `fit_analysis` 가 **같은 턴에** 돈 경우만 걸려서, 등급을 본 뒤
"그래도 써줘" 하면 걸리지 않는다(사용자를 가두지 않는다).

실측이 잡은 결함 3건: **ack 가 하지 않은 일을 하겠다고 말했다**(`plan_changed` 는 dispatch
시점만 본다) · 조사 오류("설계**으로**") · **착지점이 값을 주지 않았다** —
`application_plan` 의 대화 응답이 `label — headline` 한 줄이라 산출물인 지원 경로 2~3개가
대화 채널에 도달하지 않았다(→ `render_plan_reply` 결정론 조립).

### ② §2-1 관찰 층 — LLM 을 걷어내고 규칙으로

프로토타입 루프의 세 성질(전체 히스토리 / 실제 행동 선택 / 답변 작성)을 `observe_after` 는
**셋 다 갖지 않았다** — 요약을 보고 제어 신호만 냈다. 즉 그 성질의 **열화 모방**이었고, 그
성질이 사는 곳은 `agent_loop` 다. 그래서 갈랐다:

- **오케스트레이션 관찰 → 결정론.** `orchestrator/observe_rules.py` 신설(규칙 2개).
  `observe_after`·`ObserveDecision`·`AgentSpec.observe`·`observes_after` 제거.
  근거는 프로토타입 자신에게도 있다 — D11: *"게이트까지 LLM 자유는 agent다움이 아니라
  설계 의도 위반 리스크"*. **툴 선택은 LLM, 분기는 조건엣지.**
- 교체하면서 **실측 결함이 닫혔다**: `runnable_now` 가 순차 실행 직전에 한 번도 검사되지 않아
  판정이 실패해도 자소서가 `analysis=None` 위에서 돌았다(재현 확인). 예전 판정은 "하나라도 돌
  수 있으면 계속" 이라 **못 도는 항목을 그대로 실행**했다.
- **`agent_loop` 는 넓혔다**: 채택 2→3(`preference_intake`), `max_steps` 3→5,
  **대화 이력을 매 스텝 입력에 추가**(프로토타입의 "전체 히스토리" 대응), 위임 소비자 1→2
  (`preference_intake → job_recommend` = "지금 조건으로 실공고가 있나" 미리보기).
- **`resume_diagnosis` 는 루프로 옮기지 않았다.** 프로필 읽기(결정론) → 조립(결정론) → 문장
  1회라 *다시 정할* 것이 없다. 공고 요건과 대조해 약점을 짚는 건 **판정이고 `fit_analysis`
  소관**이다. 여기 없는 건 루프가 아니라 표현 분리였다(→ ③). 판단 기준을 비교 문서에
  **"루프를 벌었는가"** 표로 남겼다(9개 에이전트 판정).

### ④ §2-3 재현성 — 기록된 100% 는 이미 죽은 숫자였다

`planner_harness` 에 `--runs N` + **정확도/안정성 분리 지표**를 넣고 46케이스 × 3회로 쟀다.

| 단계 | 정확도 | 안정성 |
|---|---|---|
| 최초 | 0.6739 | 0.9420 |
| temp 0 (실험) | 0.6884 | 0.9493 |
| 프롬프트 수정 | 0.7826 → 0.8188 | 0.9565 → **0.9855** |
| 데이터셋 갱신 | **0.9275** (되묻기 1.00) | 0.9783 |

네 가지가 나왔다:

1. **재현성은 문제가 아니었다** — 안정성 0.94. **온도를 0 으로 내려도 거의 안 변한다.**
   측정 전엔 유력한 손잡이로 보였던 "티어별 온도 분리" 가 **값이 없다**는 것이 확인됐다.
2. **100% 는 회귀가 아니라 죽은 숫자였다** — baseline 저장(07-27 16:24) **5시간 뒤**
   "제출 턴은 정리 먼저" 프롬프트 규칙이 들어왔고 재측정이 없었다.
   → **프롬프트 변경과 평가셋 재측정이 같은 커밋에 없으면 baseline 은 조용히 죽는다.**
3. **하네스가 프로덕션이 아닌 흐름을 재고 있었다** — 저신뢰 폴백(실제로는 `career_chat` 이
   돈다)을 "되묻기" 로 뭉개고, 동의 게이트를 빈 키로 기록했다. 둘 다 07-28 에 들어온 경로다.
4. **정확도/안정성 분리가 바로 값을 했다** — 실패 17건 중 flaky 는 3건뿐이고 나머지는
   프롬프트 과잉 적용 5건 + 데이터셋 낡음 6건이었다. "일관성 k/N" 하나로는 전부 "불일치" 로
   뭉쳐서 온도·프롬프트 경화를 헛되게 뒤졌을 것이다.

그리고 **프롬프트 수정 과정 자체가 교훈**이었다: `fit_analysis` 예외를 넣으면서 인사 조항을
같이 넣었는데 그 조항이 **기능 요청까지 끌어갔다**("면접 질문 뽑아줘" → career_chat).
총계는 올라갔으니(0.67→0.78) 통과시켰을 것이고, 케이스별 판정을 보고서야 "고친 것 8 / 깨뜨린
것 6" 이 드러났다. → **좁히는 문장과 넓히는 문장을 같은 커밋에 넣지 않는다.**

덤: 풀턴 S5 의 한 run 이 `['fit_analysis','application_plan']` 으로 나왔다 —
①에서 넣은 규칙이 **계측된 궤적에서 발동한 첫 기록**이다.
