# 2026-08-02 — 제네릭 점수의 **바닥**을 잡았다 · 자소서 근거 재료 확장 (D109~D110)

## 한 줄

"노이즈 바닥 안정화"를 하러 갔는데 **바닥이 흔들린 게 아니라 바닥을 재는 방법이 셋 다 틀렸다.**
셋을 고치고 문턱을 **runs=5 에서 0.0178** 로 확정했다.

## 무엇이 문제였나

08-01 이 남긴 처방은 "runs 를 늘려라"였다. 실행하니 **바닥이 더 나빠졌다**(0.0271 → 0.0375).
그 관측을 뜯어 원인 셋을 찾았다.

### ① 범위(max−min)를 문턱으로 썼다 — 표본이 늘면 커진다

범위는 극단값을 만날 기회가 늘어 n 과 함께 증가한다. **범위로는 "표본을 늘려 안정시켰다"를
원리적으로 보일 수 없다.** 같은 데이터를 SEM 으로 다시 재니 study-plan 은 0.0081 → **0.0041** 로
반이 됐다 — runs 를 늘린 효과가 실제로 있었고 범위가 그걸 가리고 있었다.

### ② 눈금자가 상수가 아니었다 — 기준선을 측정마다 LLM 으로 다시 파싱했다

①로도 `key-requirement` 평균이 +0.0019 → +0.0341 로 옮겨간 게 설명되지 않았다. 기준선을 꺼내 보니
**기준선 자체가 0.5271 → 0.5156 으로 움직였다.** delta 는 답변에서 기준선을 뺀 값이므로 **답변이
하나도 안 변해도 점수가 올라간다** — 이동분 +0.032 중 0.0115(3분의 1)가 기준선 몫이었다.

08-01 기록의 "기준선은 상수라 노이즈에 기여하지 않는다"는 **한 측정 안에서만** 맞았다. 전후 비교가
쓰는 것은 측정 **사이**다. 그 문장에 부분 뒤집힘 표시를 달았다(D108).

### ③ SEM 자체가 n=5 로는 못 믿을 추정치였다

①·②를 고치고 다시 재니(46분, 80회 실행) **미리 못박은 기준을 통과하지 못했다**: study-plan SEM 이
0.0041 → **0.0119**(3배), key-requirement 는 0.0072 → **0.0036**(반)으로 반대 방향으로 갈렸다.

세 측정의 측정내 변동을 합동 계산했다:

| 질문 | 측정별 σ (각 n=5) | 합동 σ (자유도 8) |
|---|---|---|
| study-plan | 0.0091 · 0.0267 | **0.0199** |
| key-requirement | 0.0160 · 0.0080 | **0.0126** |

n=5 에서 σ 추정의 90% 구간은 참값의 **×0.60~×2.37** 이다(χ², 자유도 4). 2.9배 차이는 노이즈 변화가
아니라 **추정 오차 안**이다. 그러므로 측정마다 SEM 을 문턱으로 쓰면 **문턱이 3배 흔들린다.**

## 무엇을 고쳤나

| 무엇 | 전 | 후 |
|---|---|---|
| 문턱 | 이 측정의 `range` → 이 측정의 `2×SEM` | **합동 σ 상수**: `2 × 0.0199 / √runs` (runs=5 → **0.0178**) |
| 기준선 | 측정마다 LLM 파싱 | 데이터셋 `baselineText` 에 **고정**, `--refresh-baseline` 로만 갱신 |
| 기준선 누락 | 조용히 빈 문자열 | **멈춘다**(빈 문자열끼리 비슷해 점수를 왜곡) |
| SEM·범위 | 문턱 | **진단용**(어느 회차가 튀었는지 볼 때) |

부수 효과로 측정마다 파싱 LLM 8회가 사라졌다.

# 같은 날 · 두 번째 갈래 — 자소서가 "이거 살려서 다시"를 못 받고 있었다 (D110)

## 발단 (사용자 질문 하나)

"제공한 자소서에서 사용자가 특정 스택이나 트러블슈팅을 강조해서 다시 써줘 하면 반영해서
다시 쓸 수 있도록 프롬프팅이나 툴이 있나?"

읽어 보니 **통로는 다 열려 있었다** — `userMessage` 원문이 프롬프트에 실리고, `focus` 인자도
있고, `currentDraft` 로 이전 턴 초안을 이어받고, `save_draft` 는 부분 갱신이다. 그런데 실제로는
안 됐다. 통로가 아니라 **재료와 검색**이 막고 있었다.

## 첫 안을 버렸다 — matcher 를 만들 뻔했다

처음 제안은 `_check_report` 에 "focus 를 반영했나"를 substring 으로 재는 검사를 넣는 것이었다.
사용자 지적: *"1하고 2는 범위를 상당히 늘려야 할 거 같은데? 지금은 너무 좁아서 에이전트 기능이
너무 좁아져. 사용자의 다양한 형태의 모호하거나 다양한 표현에도 사람처럼 대응할 수 있어야 해."*

맞는 지적이었다. 그 검사는 **지금 고치려는 문제(문자 대조의 한계)를 검사 쪽에 그대로 복제한다.**
taxonomy 를 "트러블슈팅"까지 넓히는 안도 같은 함정 — 어휘를 아무리 늘려도 "좀 더 임팩트 있게"는
못 잡는다. **의미 판단을 하는 엔진은 이미 있다(LLM). 좁은 것은 판단이 아니라 재료와 지시였다.**

## 고친 것 셋 (`agents/coverletter_draft.py`)

**① 재료** — `_collect_facts` 가 projects·experiences·certifications·awards 네 섹션, 20건만
봤다. `NormalizedUserProfile` 에 있는데 안 쓰던 것: **`evidenceMap`(이력서 원문 문장)**, education,
bootcamp, languages, `award.description`, `project.projectType/period/teamSize`,
`experience.employmentType`. `techStack[:5]` 잘림도 제거하고 상한 20 → 60. **검색을 고쳐도 없는
것은 못 찾는다** — 재료에 없는 게 진짜 원인이었다.

**② 검색** — `find_evidence` 의 인자를 **필터에서 정렬 힌트로 격하**. 문자 일치 0건이어도
`"확인되지 않습니다"` 로 끝내지 않고 전문을 함께 준다("다른 표현일 수 있으니 직접 읽어라, 정말
없으면 지어내지 마라"). 일부만 걸리면 그 목록이 전부가 아니라고 고지. `hits[:10]` 잘림도 제거.

**③ 지시** — `_GOAL_SYSTEM` 에 강조 요청 처리 한 문단. 문자로 찾지 말고 인자 없이 전문 읽고
직접 고를 것, 모호하면("좀 더 임팩트 있게") 가장 그럴듯하게 해석하고 무엇으로 해석했는지
마무리 안내에 적을 것, 근거가 정말 없으면 창작 금지 + 그 사실 고지.

`_check_report` 는 **안 건드렸다.** 셀 수 있는 것만 계속 센다.

## 측정 — 처음으로 이 표면을 쟀다

하네스(`eval/loop_consistency.py`)에 이 표면을 재는 케이스가 없었다. `coverletter_emphasis` 를
신설했다 — 근거를 `evidenceMap` 에만 두고 요청어와 한 글자도 안 겹치게:

- 근거 `"재고 동기화 중복 차감 장애를 추적해 낙관적 락으로 해결했습니다."`
- 발화 `"트러블슈팅 경험 살려서 강점 문단 다시 써줘"`
- 불변식 `save_draft` 호출 + 답변에 `락`·`중복 차감`·`동기화`·`장애` 중 하나

문자 대조로는 절대 못 맞추는 자리다. 통과하면 **의미로 골랐다**는 뜻이다.

**`loop_baseline.json` 과 비교하지 않았다** — openai/gpt-4.1-mini 로 잰 값이라 공급자가 다르다.
같은 공급자(claude_code/sonnet)로 대조군을 **다시 돌렸다**. `git stash` 는 병렬 세션 작업까지
쓸어가므로 안 쓰고 **파일 하나만 스왑**했다.

| 케이스 | 지표 | 대조군(HEAD `2103725`) | 실험군 |
|---|---|---|---|
| `coverletter_emphasis` | 불변식 위반 | **5/5** | **0/5** |
| | 안정성 / 스텝 / 콜 | 0.60 / 3.6 / 4.6 | **1.00 / 3.0 / 4.0** |
| `coverletter_draft` | 불변식 위반 | 0/5 | 0/5 |
| | 안정성 / 스텝 / 콜 | 0.60 / 4.2 / 6.0 | **0.80 / 3.2 / 4.4** |

**대조군이 실패한 방식이 궤적에 그대로 찍혔다:**

```
3/5  find_evidence>find_evidence>save_draft>check_draft
1/5  find_evidence>find_evidence>find_evidence>save_draft>check_draft
1/5  find_evidence                                    ← save_draft 없이 종료
```

2~3연타는 0건 받고 인자 비워 재호출한 것 — `_MAX_STEPS=7` 에서 **재작성 기회 하나와 맞바꾼
스텝**이다. 마지막 1/5 가 더 나쁘다: 저장을 못 한 채 끝났는데 `_has_draft` 가 이전 턴 초안으로
True 라, **재작성을 요청했는데 같은 초안이 그대로 다시 나갔다.** 사용자에겐 무시당한 것으로 보인다.

실험군 산출물(1회 실측, 강점 문단): *"재고관리 API 개발 중 재고 동기화 과정에서 중복 차감이
발생하는 장애를 겪었고, 원인을 추적해 낙관적 락(Optimistic Lock)을 적용해 문제를 해결했습니다.
(…) 주문 처리 지연 시간을 1.2초에서 0.4초로 개선하기도 했습니다."* 동기·보완 문단은 그대로 —
부분 수정 계약이 유지된다.

"이 세션에서 옛날에 말한 자료를 언급하며 질문·작성을 청하면 잘 하는가"를 훑다가 나왔다.
갈래가 셋으로 갈렸다.

| 대상 | 질문 | 작성 요청 |
|---|---|---|
| 공고 | ✅ `posting_library`(D86, 상한 5)를 `career_chat`·`posting_recall`·플래너가 전부 읽는다. 대화 이력 6개 제한과 무관 — 세션 자산이라 몇 턴 전이든 산다 | ❌ |
| 이력서 | ❌ `resume`/`profile` 슬롯 하나뿐, 라이브러리 없음 | ❌ |

작성이 안 되는 이유는 처음엔 "하류가 라이브러리를 안 본다"로 보였다. `coverletter_draft` 는
`posting_identity(session)` → `posting_summary` 하나만, `analysis` 도 활성 것 하나만 본다.

**그런데 진짜 원인은 그 앞이었다.** `fit_analysis.run` 이

```python
if len(targets) >= 2:
    return _run_multi(...)
```

라서, **지목이 하나면 반복 판정 경로에 들어가지도 못하고** 아래 단일 경로가 활성 공고를 그대로
판정했다. 지목이 통째로 사라진 것이다. D88 을 "여러 공고 비교" 기능으로만 만들면서 **하나
지목이 곧 대상 전환이라는 뜻**을 빠뜨렸다.

증상은 조용하다. 경고도 안 나고, 그럴듯한 자소서가 나오는데 **회사만 다르다.**

## 무엇을 고쳤나

`targets` 개수로 뜻을 갈랐다.

- **둘 이상 = 비교**(D88 그대로) — 활성 공고를 바꾸지 않는다. 무엇을 활성으로 삼을지 정할 수 없다.
- **하나 = 전환**(신설 `_switch_active`) — `job_posting` 원문과 `posting_summary` 를 라이브러리
  항목으로 갈아 끼우고, 그 다음은 **평소 단일 경로가 그대로 판정한다**(대안 공고·로드맵 포함).

전환을 무손실로 만들려고 라이브러리 항목에 원문(`_sourceText`)을 함께 저장했다. 원문이 없으면
`job_posting` 을 되돌릴 수 없어 재파싱이 돌고(D79 캐시 무효) 원문 grep 도구도 죽는다.
자리표시자로 때우는 쪽이 더 비쌌다.

라이브러리에 없는 이름이면 활성 공고로 판정하되 `fit_target_not_found` 를 남긴다 — 폴백이
이유를 삼키지 않는다(§2-6).

## 하류를 안 건드린 이유

`coverletter_draft`·`interview_prep` 이 라이브러리를 직접 보게 하는 것이 언뜻 자연스럽다.
**라이브러리 항목에는 gaps 가 없다.** gaps 는 활성 공고 기준으로만 계산되고, D88 이 `analysis`
승격을 활성으로 제한한 이유가 바로 그것이다. 공고만 갈아 끼우면 보완 문단이 엉뚱한 격차를
다룬다 — **지금보다 나쁘다.**

대상을 바꾸는 유일하게 일관된 방법은 활성 공고 자체를 바꾸는 것이고, 그러면 하류는 한 줄도
고칠 필요가 없다. 실제로 `coverletter_draft.py` 는 이번 변경에서 **손대지 않았다.**

## 곁가지 — 밑줄 키를 이름으로 걸러 내고 있었다

`_sourceHash` 를 빼는 코드가 네 군데에서 각각 `if k != "_sourceHash"` 였다. 밑줄 키가 하나 늘 때마다
네 곳을 고쳐야 하는 구조다(이번에 실제로 늘었다). `not k.startswith("_")` 로 바꿨다 —
같은 크기의 diff 인데 다음 번이 없다.

## 대가

라이브러리가 공고 원문을 최대 5벌 든다(공고 하나 수 KB). 밑줄 키는 소비자가 전부 필드를 골라
쓰므로(`posting_facts`·`job_items`) 화면·프롬프트로 새지 않는다 — 테스트로 고정했다.

## 안 한 것

**이력서 라이브러리.** `resume`/`profile` 은 여전히 슬롯 하나라 "처음에 올린 이력서로" 는
성립하지 않는다. 공고는 한 대화에서 여러 개를 훑는 것이 정상 사용이지만 이력서는 그렇지 않다.
여러 벌을 올리는 사용이 실제로 관측되면 그때 같은 방식(원문 포함 라이브러리)으로 넓힌다.

## 교훈

- **"기능이 있다"와 "그 기능에 닿는다"는 다르다.** D86 으로 지식을 남기고 D88 로 판정까지
  붙였는데, 가장 흔한 입력(하나 지목)이 분기 조건 하나에 걸려 통째로 무시됐다. 기능을 넓힐 때
  **경계값(1개)을 같이 적어야 한다.**
- **조용히 틀리는 것이 가장 비싸다.** 실패했으면 바로 알았을 텐데, 그럴듯한 자소서가 회사만
  바꿔 나갔다. 폴백에 이유를 남기는 규율(§2-6)이 여기에도 필요했다.
- **하류를 뚫고 싶을 때 상류를 본다.** 소비자 셋을 고치는 대신 생산자 하나를 고쳤다 —
  자소서 파일은 열지도 않았다.

# 같은 날 · 네 번째 갈래 — **예상 밖 상황을 예측하지 말고 센다** (D117)

## 발단 (사용자 질문 하나)

> "에이전트를 출시한 후 분명 만든이들도 예상치 못한 상황에 대한 질문이나 요청이 있을 텐데,
> 현재 범용 에이전트들은 이런 문제를 어떻게 해결해?"

일반론으로 답하고 나서 우리 코드에 같은 질문을 물었다. 구조는 이미 정석에 가까웠다 —
대응표 없음, 플래너 자율, 결정론 검증기, fail-closed 동의 게이트, 폴백이 이유를 남김.
그래서 "구조를 바꾸자"가 아니라 **그 구조에 뚫린 구멍**을 찾는 일이 됐고, 다섯을 추렸다.

## 순위를 데이터가 뒤집었다

착수 시점 순위는 코드만 읽고 매긴 것이었다. 1위는 "아무 링크나 저장된 분석을 파괴한다",
4위가 "career_chat 폴백". 재기 전에 **표본이 이미 있다는 걸 알아챘다** — `sessions.sqlite3`
에 133세션·275턴의 발화와 답변이 그대로 쌓여 있다. 코드 한 줄 안 고치고 오늘 볼 수 있다.

수확기를 짜서 돌리니 순위가 뒤집혔다:

| 신호 | 실측 | 착수 순위 → 실제 |
|---|---|---|
| `career_chat` 고정 안내문 | **7건 (2.5%)** | 4위 → **1위** |
| 범위 밖 거절 | 3건 (1.1%) | — |
| 미확인 호스트 URL | **0건** | 1위 → 3위 |

그리고 7건의 내용이 문제였다. **전부 정상 요청이다.**

```
U: 이 공고와 내 자료로 적합도를 분석해 주세요.
A: 이런 걸 도와드릴 수 있어요: 공고 적합도 분석, 이력서 기반 공고 추천, …

U: 응, 진단해줘                          ← 직전 턴에 "이력서를 받았어요" 까지 나간 뒤
A: 이런 걸 도와드릴 수 있어요: …

U: 요즘 취업 준비가 너무 힘들어. 위로해줘   ← career_chat 자기 홈그라운드
A: 이런 걸 도와드릴 수 있어요: …
```

범위 밖 질문이 메뉴를 받은 게 아니라 **핵심 기능 요청이 메뉴를 받았다.** 07-29 사고
("층이 죽었는데 답변은 그럴듯했다")와 같은 모양이다 — 첨부 확인 문구(결정론)는 정상으로
나가고 그 뒤에 메뉴가 붙은 케이스도 있었다.

## 이 코퍼스가 못 하는 것 (먼저 적어 둔다)

발화 121종 중 **합성 발화가 76건**("방금 드린 자료로 이어서 진행해 주세요")이고, 나머지도
로스터를 아는 사람이 쓴 QA 스크립트다. 진짜 범위 밖 질문은 **"오늘 날씨" 3건**뿐.

**이 데이터로는 OOD 빈도를 원리적으로 못 잰다** — 예상 못한 요청은 정의상 예상한 사람이
못 쓴다. 미확인 URL 0건도 "안전하다"가 아니라 "QA 스크립트는 사람인·잡코리아만 던진다"는
뜻이다. 실사용자 첫 주가 첫 측정 기회다.

## 고친 것 넷

### ① 폴백이 이유를 삼키던 마지막 자리 (`agents/career_chat.py`)

원인 셋의 관측 가능성이 달랐다:

| 원인 | 그때 남던 것 |
|---|---|
| `llm_not_configured` / `llm_call_failed` | ✅ warnings + `chat.py` 의 `log.error` |
| LLM 성공했는데 빈 문자열 | ❌ 무음 |
| **금지표현 강등** | ❌ **완전 무음** — 텍스트만 바꾸고 warnings 도 로그도 없었다 |

§2-6 을 어기는 마지막 구멍이었다. 경고 하나를 올린다.

**재작성 루프는 넣지 않았다.** `agent_loop` 이 이미 하는 것(금지표현 1회 재작성)을 여기에도
주는 게 다음 수순처럼 보였지만, **원인 분포를 모른 채 넣으면 원인이 인프라일 때 5줄이
아무것도 안 고친다.** 세는 것이 먼저다.

### ② 수확기 상설화 (`scripts/harvest_sessions.py`)

`eval/` 하네스 5종은 전부 사전 정의 케이스를 잰다 — 우리가 예상한 것만. 반대편이 하나도
없었다. 읽는 곳이 `sessions.sqlite3` 인 이유:

- 로그 → **stdout 전용**(`basicConfig`, 파일 핸들러 없음). 휘발한다.
- `warnings` → 응답과 함께 사라진다.
- `trace` → 턴 끝에 소멸한다.
- **발화와 답변이 함께 영속하는 곳은 세션 `history` 뿐이다.**

그래서 신호를 답변 **문구**로 잡을 수밖에 없고, 문구 지문은 문구가 바뀌면 **조용히 0을
보고**한다. 0 은 "괜찮다"로 읽히므로 그게 이 도구 최대의 실패다. `_assert_fingerprints_alive()`
가 소스를 검사해 없으면 죽고, **그 검사를 회귀 테스트로 묶었다** — 문구를 고치면 테스트가
먼저 깨진다. 임포트로 추적 가능한 상수(`career_chat._FALLBACK`)는 임포트하고, f-string 안이라
못 가져오는 것만 리터럴로 뒀다.

> **앞 제안을 스스로 정정한 자리**: 처음엔 "로그에 발화가 안 남아 회수 루프가 성립 안 한다,
> `log.info` 에 발화 80자를 붙이자"였다. 틀렸다 — `sessions.sqlite3` 에 이미 다 있다.
> 로그 수정은 필요 없고 수확기 하나면 된다.

### ③ 미확인 호스트 URL 가드 (`orchestrator/chat.py`)

`_URL_RE` 는 `https?://` 면 도메인 무제한으로 잡고, 곧바로
`_stage({"job_posting": …, "analysis": None, …})` 로 간다. 채용사이트 화이트리스트(D80)는
*스킴 없는 문장 속 주소*에만 걸려 있었다. 그래서 대화 중에 깃허브·포트폴리오 링크를 붙이면
**활성 공고가 바뀌고 수십 초짜리 판정이 말없이 사라진다.** D98 이 이력서 쪽에서 막은 파괴의
공고판이 없었던 것.

**조건을 "공고 보유"가 아니라 "분석 보유"로 좁혔다.** ① 분석이 없으면 교체는 되돌릴 수 있고
(다음 링크가 다시 덮는다), ② 회사 자체 채용페이지(`careers.*`)는 화이트리스트에 없어서 넓게
걸면 **정상 공고를 놓친다.** 화이트리스트는 판별 수단이지 공고의 정의가 아니다. 걸러낸 주소는
버리지 않는다 — 메시지 원문에 그대로 있어 플래너가 읽는다(D98 되돌리기 규약).

### ④ 로스터 밖 요청을 신고할 칸 (`orchestrator/planner.py`)

`blockedRequests: list[AgentName]` — **Literal 이라 등록된 에이전트로 표현되는 요청만**
신고할 수 있었다. "연봉 협상 어떻게 해요", "포트폴리오 봐주세요" 같은 로스터 밖 요청은
`career_chat` 이 즉흥으로 받고 턴이 끝나며 **시스템에 흔적이 0**이었다. D72 가 만든 회수
루프의 원료가 생산되지 않는 상태였다.

`unsupportedRequest`(자유 문자열)를 더했다. 규율 셋:

- **라우팅은 바꾸지 않는다.** 채워져도 계획은 그대로 돈다. 무엇이 오는지 모르는 채로 갈래를
  만들면 근거 없는 판단을 코드로 못 박게 된다.
- **세션에 남긴다**(`unsupported_requests`, 상한 20). ②에서 확인한 그대로 로그·warnings 는
  휘발하므로, 안 남기면 이 칸이 아무것도 생산하지 못한다. 수확기가 읽는 **유일하게 문구
  지문이 필요 없는 신호**다.
- **판단 원칙에 한 줄도 안 더했다.** §3-1 실측(규칙 추가 −0.022 / 선택지 정의 좁히기 +0.058)
  대로 스키마 description 만으로 지시한다.

## 안 한 것

- **`pendingRequest` 단일 슬롯 + break** — 한 발화에 두 기능을 청하면 하나만 기억되고,
  결측이 `resume`/`job_posting` 이 아니면 아예 안 기억된다. 신호 0건. 수확기가 빈도를 세기
  전에는 리스트로 바꿀 근거가 없다.
- **첨부 종류 2.5종** — 포트폴리오·경력기술서는 강제로 이력서/공고 중 하나가 된다. ③이 URL
  경로를 막고, 텍스트 경로는 `resolve_kind` 가 애매하면 claimed 유지라 사고 폭이 작다.
- **고용 차별성 질문**("나이가 많은데 될까요") — `FORBIDDEN_EXPRESSIONS` 는 합격 예측만 본다.
  예상 밖 질문 중 **유일하게 안전 리스크가 있는 종류**이고 처방(거절/일반론/근거 요구)이
  프로덕트 결정이라 코드로 정하지 않았다. **출시 전 한 번 정해야 한다.**
- **`career_chat` 재작성 루프** — ①의 이유. 원인 분포를 보고.

## 곁가지 — 커밋을 가르는 데 시간을 썼다

작업 트리에 **병렬 세션의 미커밋 작업이 15개 파일** 있었다(D113~D115). 통째로 `add` 하면
남의 진행 중 작업을 쓸어 담는다. 파일별 훅을 세어 보니 얽힌 것은 `session.py` 한 훅
(`resume_library`)과 `docs/*` 뿐이라, 그 둘만 **HEAD 판 + 내 것으로 blob 을 만들어
`update-index` 로 직접 올렸다.** 나머지는 통째로 stage.

그 과정에서 **`decisions.md` 에 `D115` 가 두 개**인 것을 발견했다(연차 필터 / 직군 선택).

## 교훈

- **예상 못한 것을 예상하려 하지 말고, 흡수한 것을 세는 자리를 만든다.** 구조는 이미 OOD 를
  흡수하게 생겼는데 흡수한 것을 세는 곳이 없었다. 계측이 처방보다 먼저다.
- **재기 전에 이미 있는 데이터를 찾는다.** 새 로깅을 제안했다가 `sessions.sqlite3` 에 다
  있다는 걸 알고 접었다. 275턴이 오늘 순위를 뒤집었다.
- **0 건은 "안전"이 아니라 "이 코퍼스가 못 재는 것"일 수 있다.** 미확인 URL 0건을 근거로
  가드를 버리지 않은 이유 — 표본을 만든 사람이 곧 시스템을 아는 사람이었다.
- **재측정은 "돌렸다"가 아니라 "무엇과 비교했나"다.** 이 세션에서 세 번 틀렸다 — ① 미커밋
  작업이 섞인 트리에서 쟀고(남의 `agents/__init__.py` 가 manifest 를 바꾸고 있었다) ② 직전
  *기록*의 숫자를 대조군으로 삼을 뻔했고(그 사이 어휘가 바뀌어 있었다) ③ 한 판이 1.0 이라
  "무회귀"로 쓸 뻔했다(둘째 판에서 갈렸다). 대조군은 기록이 아니라 **지금 돌린 부모 커밋**이다.
- **조용한 0 보고가 계측 도구의 가장 비싼 실패다.** 그래서 지문 검사를 테스트로 묶었다.
