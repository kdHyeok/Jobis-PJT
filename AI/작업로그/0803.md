# 2026-08-03 — 프로토타입 2.0.0 이식 4건 (D125~D128)

`feat/ai/prototype_2.0.0`(= `AI/Agent_Test` + 멀티턴·HTTP API 커밋 `44aea52`)을 분석해
본체에 없는 것 4건을 항목화하고 구현했다. 1.0.0 축은 기존 비교분석(07-29)이 이미 처리했으므로
**2.0.0 델타 기준**이다. 상세 결정은 `docs/decisions.md` D125~D128.

## 가져온 것

1. **추천 공고 지목(D125)** — 프로토타입의 posting registry(#번호 부여 → `select_posting`)에
   해당. 본체는 `job_recommend` 산출이 `recommendations` 자산에만 남아
   "추천해준 2번째 공고 분석해줘"가 성립하지 않았다.
   - `tool_render.render_job_recommend` 가 추천 목록에 **번호를 코드로** 매긴다.
   - `fit_analysis._match_recommendation` — 순번("2")·회사명·제목 부분 일치(결정론).
     순번은 **추천 목록에만** 해석한다(라이브러리와 번호 충돌 방지).
   - 매칭되면 URL 을 그 자리에서 수집(`ensure_posting_text` 재사용)해 활성 공고로 굳힌다.
   - manifest `fit_analysis.targets` 정의에 추천 목록·순번을 추가(§3-1 어휘만).
2. **지목 실패 시 되묻기(D126)** — 전에는 `fit_target_not_found`/`resume_target_not_found`
   경고만 남기고 **활성 자산으로 강행**했다(엉뚱한 공고 판정 경로, §2-1 위반).
   이제 판정하지 않고 후보 목록(기억하는 공고·이력서)과 함께 되묻는다.
   프로토타입 `select_posting` 의 "선택 가능한 번호: #1, #3" 관찰과 같은 규율.
   `switch_active_resume` 가 (세션, 갱신, 찾았는가) 3-튜플을 돌려주도록 계약 변경 —
   호출자 `fit_analysis`·`resume_diagnosis` 둘 다 되묻기로 갈아탐.
3. **런별 trace 파일 영속화(D127)** — `JOBIS_TRACE_DIR` 설정 시 `trace.recording()` 이
   끝날 때 이벤트를 JSON 파일 하나로 남긴다(opt-in, 중첩 레코더는 최상위 1회만,
   쓰기 실패는 삼킴). 프로토타입은 `traces/<시각>-<run_id>.json` 을 항상 남겨
   정상·실패·max_steps 케이스가 물증으로 남아 있었다 — 본체 trace 는 턴이 끝나면 소멸했다.
4. **세션 상태 조회(D128)** — `GET /v1/sessions/{conversation_id}` (v2bridge, 시크릿 필요).
   활성 이력서 라벨·이력서/공고 라이브러리·추천·판정 등급·턴 수를 읽기 전용으로 요약.
   프로토타입 `GET /session/{id}` 이식. 없는 세션은 404 가 아니라 빈 요약.
