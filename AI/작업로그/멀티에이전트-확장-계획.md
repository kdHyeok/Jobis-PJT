# 멀티에이전트 확장 계획 (2026-07-31)

> 다른 세션이 이 문서만 보고 작업할 수 있게 쓴 실행 계획이다.
> 배경: "지금 구현이 멀티에이전트로 적합한가"를 코드 기준으로 냉정하게 재평가한 결과,
> **격차 3개 중 1개(병렬)는 이미 구현돼 있었고**, 나머지 둘의 범위도 처음 짐작보다 좁다.
> 작업 전 `AGENTS.md`와 이 문서의 §5(하지 않기로 한 것)를 반드시 읽을 것.

## 0. 현황 — 계획의 전제가 되는 사실 (2026-07-31 코드 기준)

- 레지스트리(`src/jobis_ai/agents/__init__.py`)의 11개 항목 중:
  - **tool 6개** (`kind="tool"`, 말하지 않음, render 분리): posting_fetch(internal),
    fit_analysis, posting_analysis, job_recommend, resume_diagnosis, roadmap_manager.
    이들은 **의도적으로 결정론 도구다** — 에이전트화 대상이 아니다.
  - **agent 5개**: career_chat, preference_intake, interview_prep, coverletter_draft,
    application_plan.
  - agent 5개 중 **자기 루프(agent_loop) 3개**: coverletter_draft, interview_prep,
    preference_intake. 단발 LLM 호출 2개: career_chat, application_plan.
- **위임(delegate_tool) 경로 2개**: coverletter_draft → resume_diagnosis,
  preference_intake → job_recommend(`preview_postings`). 읽기 전용·깊이 1·heavy 금지·
  화이트리스트. 거부는 `delegate_refused` trace 로 분모까지 기록된다.
- **병렬 실행은 이미 있다**: `orchestrator/chat.py` 의 `parallel_group()`(±L198) +
  `_MAX_PARALLEL = 3` + ThreadPoolExecutor(±L550). 독립성 판정은 manifest 의
  `produces`/`preconditions` 겹침으로 결정론. 세션 사본 + `_stagedUpdates` 로 격리 후 병합.
- 재계획 판단자는 규칙(`observe_rules`)이다. 경량 LLM 관찰자는 실측 근거로 **기각**됐다
  (chat.py 모듈 docstring, ±L604 주석). 되살리지 말 것.

## P1. 위임 경로 확장 — 에이전트 간 통신 (원래 항목 2)

**목표**: 위임 인프라(agent_loop.delegate_tool)는 완성돼 있는데 소비자가 2곳뿐이다.
실제 중복 계산·근거 부재가 있는 자리에만 경로를 추가한다. "멀티에이전트답게 보이려고"
경로를 늘리지 않는다 — 아래 두 건은 각각 구체적 실익이 있다.

### P1-a. application_plan → job_recommend 위임

- **실익**: `application_plan` 의 routes 산출물에 "유사공고 병행" 경로가 있는데
  (`agents/application_plan.py` 모듈 docstring), 지금은 실제 공고 없이 경로 제목만 낸다.
  job_recommend 는 실공고 DB 추천을 이미 계산한다 — 같은 계산을 안 만들고 물어본다.
- **방법**: application_plan 은 현재 단발 호출이라 delegate_tool 을 쓸 수 없다
  (delegate_tool 은 agent_loop 의 ToolSpec 이다). 두 가지 중 **가벼운 쪽을 먼저 검토**:
  1. (권장 검토 순서 1) 루프 없이 `job_recommend.run(session)` 을 **읽기 전용으로 직접
     호출**해 결과를 routes 표현에만 쓴다. 오케스트레이터 규약(상태 전이는 오케스트레이터만)
     을 지키려면 sessionUpdates 는 버린다. delegate_tool 의 가드(전제 확인·trace)를 수동으로
     재현해야 하는 게 단점.
  2. (검토 순서 2) application_plan 을 agent_loop 로 전환하고 `delegate_tool(("job_recommend",))`
     를 도구로 준다. 단, §P2 의 판단 기준(재선택 동역학이 실제로 필요한가)을 통과해야 한다 —
     application_plan 의 판정은 룰이고 표현은 한 번이면 되므로, **루프 전환은 과할 가능성이
     높다.** 1안이 되면 1안으로 끝낸다.
- **가드 유지**: 읽기 전용(상대 sessionUpdates 미적용), heavy 금지(job_recommend 는
  heavy 아님 — OK), 전제 미충족 시 실행하지 않고 그 사실만 관찰로.
- **검증**: 기존 application_plan 테스트 + "유사공고 병행 경로에 실공고가 실리는가" 케이스
  추가. job_recommend 전제(resume 또는 preferences) 없는 세션에서 경로가 기존 문구로
  폴백하는지 확인.

### P1-b. interview_prep → resume_diagnosis 위임 (검토 후 결정)

- **가설**: 면접 꼬리 질문에서 "이력서의 어느 항목이 빈약한가"는 resume_diagnosis 가 이미
  세는 값이다. interview_prep 루프의 도구로 `delegate_tool(("resume_diagnosis",))` 를 주면
  빈약 항목을 파고드는 질문이 가능해진다.
- **먼저 할 일**: `agents/interview_prep.py` 의 기존 도구 목록을 읽고, 소재 선정 도구가
  이미 같은 정보를 쓰는지 확인한다. **겹치면 이 항목은 하지 않는다** — 근거를
  `docs/decisions.md` 에 "안 하기로 한 결정"으로 남긴다.
- **검증**: 위임 발생 시 `delegate_refused` 분모 집계가 깨지지 않는지(성공/거부 모두 trace),
  interview 진행 상태(`produces=("interview",)`)가 위임으로 오염되지 않는지.

### P1 공통 규칙

- **manifest(플래너 어휘)는 바뀌지 않는다** — 위임은 에이전트 내부 도구라 플래너 프롬프트에
  실리지 않으므로 평가셋 재측정 의무(AGENTS.md §3-1·§3-6)는 발동하지 않는다. 단
  에이전트 자체의 시스템 프롬프트를 고치면 **그 에이전트 평가 재측정과 같은 커밋**(§3-6).
- 깊이 1 제한·화이트리스트·읽기 전용은 그대로. 완화하지 않는다(§5).

## P2. 선택적 에이전트화 — 단발 agent 의 루프 전환 (원래 항목 1)

**대상은 2개뿐이고, 그중 1개는 아마 하지 않는 게 맞다.**
tool 6개는 대상이 아니다 — "재선택할 것이 없으므로 관찰도 걸지 않는다"는 레지스트리
docstring 의 규율이 정확하다. 전환 판단 기준은 하나: **결과를 보고 행동을 다시 고르는
동역학이 실제 대화에서 필요한가.** (preference_intake 전환 근거가 선례 —
"듣고 기록하고, 실공고가 나오는지 확인하고, 좁으면 넓히자고 다시 묻는 반복".)

### P2-a. career_chat — 조건부 전환

- **현황**: 단발 스트리밍 호출(`run_streaming_text`). 세션 상태(hasResume 등)를 컨텍스트로
  받아 말만 한다.
- **전환 실익이 있는 시나리오**: "포트폴리오가 중요한가요?" 류 정보성 질문에 사용자의
  실제 자산(이력서 진단 결과, 수집된 선호)을 근거로 답하기. 지금은 일반론만 말한다.
- **판단 기준 적용**: 도구가 "진단 결과 조회" 하나뿐이면 루프가 아니라 **컨텍스트 주입**
  (호출 전에 결정론으로 조회해 프롬프트에 넣기)으로 충분하다. **루프 전환은 도구가 2개
  이상이고 어떤 도구를 쓸지가 발화마다 갈릴 때만** 정당하다. 먼저 실측 대화 로그에서
  career_chat 이 받은 발화 유형을 세어 보고 결정할 것.
- **주의**: career_chat 은 현재 **토큰 스트리밍**이다(통짜 대기 제거가 목적이었음, 파일
  주석 참고). agent_loop 는 구조화 출력 기반이라 전환하면 스트리밍을 잃는다 — **첫 응답
  지연이 늘어나는 트레이드오프를 명시적으로 결정하고 `docs/decisions.md` 에 남길 것.**
  스트리밍 유지가 더 중요하면 전환하지 않는 것이 맞다.

### P2-b. application_plan — 전환하지 않기로 제안

- 판정은 룰(점수 경계·하드 제약 정규식), 표현은 LLM 한 번. 재선택 동역학이 없다.
- P1-a 를 1안(직접 호출)으로 해결하면 루프가 필요한 이유가 사라진다.
- 이 결론대로 가면 `docs/decisions.md` 에 "application_plan 은 루프 전환 안 함 — 판정이
  룰이라 재선택할 것이 없음"으로 append.

## P3. 병렬 실행 — 신규 구축이 아니라 실측·조정 (원래 항목 3)

**이미 구현돼 있다** (`chat.py` `parallel_group` + `_run_parallel`). 남은 일:

1. **실측 확인**: 병렬 그룹이 실제 대화에서 얼마나 잡히는가. 로그에서
   `parallel: … 동시 실행` 라인을 세어 빈도를 확인한다. 병렬 가능한 대표 시나리오
   (공고+이력서 동시 제출 → posting_analysis ∥ resume_diagnosis ∥ fit_analysis)가
   실제로 그룹으로 묶이는지 풀턴 테스트로 재현.
2. **상한 검토**: `_MAX_PARALLEL = 3` 은 과금·레이트리밋 방어다. 늘릴 필요가 실측으로
   증명되기 전에는 그대로 둔다.
3. **알려진 제약 확인 (버그 아님, 설계)**: internal 단계(posting_fetch)는 단독 실행
   (이중 fetch 방지), 같은 자산을 만드는 둘은 순차(순서 의존 제거). 이 제약이 실측에서
   병렬 기회를 과하게 죽이면 그때 논의 — 지금은 손대지 않는다.
4. **가능한 개선(선택)**: 병렬 구간의 지연 단축을 수치로 남기기 — 순차 대비 몇 초
   줄었는지 로그에 남기면 발표·문서 근거가 된다. `llm_usage` 집계가 이미 턴 단위로
   있으므로 그룹 실행 전후 타임스탬프만 추가하면 된다.

## 4. 작업 순서 제안

1. P3-1 (실측 확인 — 코드 변경 없음, 반나절)
2. P1-a 1안 (application_plan 이 job_recommend 결과를 읽기 전용으로 소비)
3. P2-b 결정 기록 (decisions.md append — P1-a 와 같은 PR 가능)
4. P1-b 검토 (interview_prep 도구 목록 읽고 겹침 판정 → 하거나, 안 하기로 기록)
5. P2-a 검토 (career_chat 발화 유형 실측 → 컨텍스트 주입 vs 루프 vs 현상 유지)

각 단계는 독립 커밋(하나의 커밋 = 하나의 논리적 변경). 작업 브랜치에서만.
프롬프트를 건드리는 커밋은 해당 평가 재측정을 같은 커밋에 포함(AGENTS.md §3-6).

## 5. 하지 않기로 한 것 (이 계획의 경계 — 뒤집으려면 새 실측 필요)

- **재계획 LLM 부활 금지**: 실측에서 call 0건, 자기 자리의 위험(전제 붕괴)조차 못 막았다
  (chat.py docstring·±L604). observe_rules(규칙) 유지.
- **위임 깊이 > 1, 쓰기 위임, heavy 위임 금지**: 재귀 폭주·동의 게이트 우회·상태 전이
  단일 주체(오케스트레이터) 규약 붕괴.
- **tool 6개의 에이전트화 금지**: 결정론이어야 하는 계산에 자유도를 주는 것 — 이 저장소가
  tool/agent 구분을 만든 이유 그 자체를 되돌리는 일이다.
- **에이전트별 사적 영속 상태 금지**: 상태는 세션(blackboard) 단일 출처 유지. 사적 상태는
  "왜 이랬나" 추적을 불가능하게 한다.
