# AGENTS.md — 이 코드베이스의 불변 규약

## §0 지위·우선순위

**코딩 중 지켜야 하는 규약의 단일 출처.** `CLAUDE.md` 가 자동 임포트한다.

- **수치·구조·현재 동작은 여기 없다.** 그건 낡기 때문이다(실측: "41케이스 100%" 가 프롬프트 변경
  5시간 뒤 죽은 숫자로 남아 있었다). 대신 §4 로 **코드에 물어본다.**
- 충돌 시 **코드 > 이 문서 > 그 밖의 문서**. 이 문서가 코드와 어긋나면 이 문서를 고친다.
- 문서 지도는 `CLAUDE.md` 에 있다. **이 규약이 왜 이렇게 됐는지**는
  `docs/decisions.md`(D1~, 뒤집힌 결정을 지우지 않는다)가 출처다.
- 새 결정을 내리면 `docs/decisions.md` 에 append 한다(§3-4 의 "근거를 함께 적는다"의 적용).

## §1 3계층 — 판단은 데이터가 하고, LLM 은 말만 한다

모든 코드는 셋 중 하나다. **어느 계층인지 모르겠으면 아직 설계가 안 된 것이다.**

| 계층 | 하는 일 | LLM |
|---|---|---|
| **읽기** | 비정형 → 정형 필드 추출 | ✅ 읽기만. 없는 사실 생성 금지 |
| **판단** | 매칭·계산·검색·검증·분기 | ❌ **금지.** 결정론이어야 신뢰성이 나온다 |
| **말하기** | 정형 결정 → 자연어 | ✅ 표현만. 판정을 바꿀 수 없다 |

의도적 예외는 **하나뿐**이다(`semantic_judge` — 서술형 요구의 이진 판정). 예외를 늘릴 때는
근거를 코드 주석에 적는다(§3).

## §2 금지형 — 어기면 되돌린다

1. **모른다 ≠ 아니다.** 판정 못 하면 `not_met` 이 아니라 `uncertain` 이다. 분모에서 빼고
   되묻는다. 모르는 걸 부족으로 세면 근거 없이 사람의 결함을 단정하고 그 위에 로드맵이 쌓인다.
2. **금지는 프롬프트가 아니라 구조로.** 줄 수 없는 답은 **스키마에서 필드를 빼고**, 하면 안 되는
   행동은 **툴을 주지 않는다.** "하지 마라"는 실측에서 지켜지지 않았다.
3. **도구는 말하지 않는다.** `kind="tool"` 의 `entry` 는 `reply` 를 비우고 데이터만 낸다.
   사용자향 문장은 표현 계층(`render(data, session)`)이 만든다. 문구를 고칠 때 계산 코드를
   건드리지 않는다.
4. **상태 전이는 오케스트레이터 독점.** 저장은 `AgentResult.sessionUpdates` 로만. 에이전트가
   세션을 직접 고치지 않는다. 에이전트 간 위임은 **읽기 전용**이다.
5. **근거는 도구만 준다.** 자기 루프의 LLM 은 판단하되 **없는 근거를 만들 수 없다.**
   도구가 주지 않은 사실·수치·회사명을 쓰면 안 된다.
6. **폴백은 이유를 삼키지 않는다.** 폴백할 때 `warnings` 를 반드시 올린다. 문장만 돌려주는
   계약은 "왜 기본 문구가 나왔는지"를 지운다 — 이 저장소가 세 번 대가를 치른 실수다.
7. **무거운 작업을 말없이 시작하지 않는다.** 사용자가 청하지 않은 무거운 파이프라인은 먼저 묻는다
   (동의 게이트). 플래너가 전제로 끼운 것은 `inferredPrerequisites` 로 **신고**하게 한다 —
   "끼워 넣지 마라"는 프롬프트 금지가 실측에서 안 먹혔다.
8. **최종 확정은 사람.** 제출·결제·전송 툴을 갖지 않는다. 생성물은 초안까지다.

## §3 하네스를 고치는 법 (실측으로 얻은 순서)

1. **규칙 추가보다 어휘 좁히기.** 같은 판단 영역의 규칙이 다섯 개를 넘으면 새 규칙은 기존 것을
   **흐린다.** 실증(2026-07-29, 같은 문제·같은 모델): 판단 원칙에 규칙 추가 → 정확도 **−0.022**
   + 무관한 케이스 4건 파손. 선택지(manifest)의 **정의**만 좁힘 → **+0.058**, 파손 0.
   *모델이 못 고르는 이유는 규칙을 몰라서가 아니라 선택지의 뜻이 넓어서다.*
2. **한 번에 하나만 고치고 매번 잰다.** 좁히는 문장과 넓히는 문장을 같은 커밋에 넣지 않는다 —
   총계가 서로를 가린다(실측: 총계는 올랐는데 케이스별로 6건이 깨져 있었다).
3. **총계가 아니라 케이스별 판정을 본다.** 그리고 **어떤 추정량으로 보는지도 확인한다** — 실측
   (2026-08-02): 같은 데이터가 범위(max−min)로는 "악화", SEM 으로는 "절반 개선"으로 읽혔다(범위는
   표본이 늘면 커진다). 추정치를 문턱으로 쓸 때는 **그 추정치의 오차**를 먼저 본다(n=5 의 σ 는
   ×0.6~×2.4 로 흔들린다). 정확도와 **안정성**을 갈라 센다. `stable-wrong`(일관되게
   틀림 = 명세·프롬프트 결함)과 `unstable`(flaky = 온도·경계 애매)은 처방이 다르다.
4. **규칙의 근거를 함께 적는다.** "도구라서" 가 아니라 "결정론이라 바꿀 게 없어서" 처럼. 근거를
   적어 두면 근거가 성립하지 않는 항목을 나중에 알아볼 수 있다.
5. **평가셋을 관측에 맞추지 않는다.** 기대값을 고칠 때는 *어느 결정이 그렇게 정했나*를 `note` 에
   적는다. 근거 없이 고치면 평가셋이 구현을 따라가는 **거울**이 된다. 고치지 않고 남기는 실패는
   `OPEN`·`KNOWN FAILURE` 로 표기한다.
6. **프롬프트를 고치면 평가셋을 같은 커밋에서 재측정한다.** 그러지 않으면 baseline 이 조용히
   죽는다(실측: 저장 5시간 뒤 프롬프트가 바뀌고 아무도 몰랐다).
7. **단위 테스트만으로는 부족하다.** 실 모델로 한 번 돌린다. 폴백이 그럴듯하면 결함이 안 보인다
   — 실측에서 자기 루프 층이 통째로 꺼진 채 "정상처럼" 답하고 있었다.

## §4 코드에 물어보는 법 (문서를 믿지 말고)

```bash
uv run --extra dev --extra prototype pytest -q          # 회귀 (LLM 없이 1초대·비용 0)
uv run --extra prototype python -m jobis_ai.explain     # 선언 표·관문 순서·관찰 규칙
uv run --extra prototype python -m jobis_ai.explain --assets resume,job_posting --plan coverletter_draft
```

`explain` 이 답하는 것: 에이전트별 전제·산출·무거움·인자 / 한 턴의 관문과 **실제 상수** /
실행 뒤 계획을 바꾸는 규칙 / 주어진 상태에서 무엇이 실행되고 **동의 게이트가 걸리는지**.

평가 하네스(실 LLM — 크레딧·시트를 쓴다. 큰 분기마다 한 번만):

```bash
python -m jobis_ai.eval.planner_harness evals/planner_dataset.json --runs 3   # 플래너 정확도·안정성
python -m jobis_ai.eval.consistency --runs 3                                   # 풀턴 궤적
python -m jobis_ai.eval.loop_consistency --runs 5                               # 자기 루프 궤적
```

## §5 CI (상세: `docs/ci.md`)

- 고칠 파일은 `ci-checks`뿐. `Jenkinsfile`은 Infra 소유 — MR + 리뷰.
- `--frozen`을 떼지 않는다. 의존성을 바꿨으면 락파일을 같은 커밋에서 갱신한다.
- 계약을 넓히면 `backend/` record도 같은 MR에서 — `extra="forbid"`라 한쪽만 넓히면 422다.
