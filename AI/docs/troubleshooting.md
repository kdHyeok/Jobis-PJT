# 트러블슈팅 · 교훈 기록

> 실제로 겪은 문제와 그 원인·해결을 기록한다. 설계 의도는 `agent-derivation-and-tools.md` /
> `agent-structure-current.md` 가 정본이고, 이 문서는 **"왜 이렇게 바뀌었는지"의 사건 기록**이다.
>
> 문서는 두 부분이다.
> - **1부 — 반복해서 확인된 원칙**: 여러 사건에서 같은 형태로 되풀이된 교훈. 새 코드를 쓰기 전에 읽는다.
> - **2부 — 사건 기록**: 날짜별 케이스 스터디. 1부의 각 원칙은 여기의 사건을 근거로 한다.
>
> 원칙에 붙은 `[→ 07-28 ②]` 표기는 2부의 해당 사건을 가리킨다.

# 1부 — 반복해서 확인된 원칙

## A. 측정하지 않은 것은 모르는 것이다

**A-1. 단위 테스트가 전부 통과해도 기능은 죽어 있을 수 있다.**
검증 재시도 루프는 라우터의 이중 가드 때문에 **한 번도 발동하지 않으면서** 겉보기로는 정상이었다
`[→ 07-15 ①]`. `interview_prep` 은 `produces` 선언한 자산 키가 세션 허용 목록에 없어서 실서버에서
**매번 실패**했다 `[→ 07-29 ③]`. 루프·재시도·다중 턴처럼 "여러 번 돌아야 성립하는" 기능은
**실제로 발동하는지**를 통합 테스트나 실기동으로 확인해야 한다. "예외가 안 났다"는 동작의 증거가 아니다.

**A-2. 실서버 로그가 아니면 못 찾는 결함이 따로 있다.**
공고 추천 영구 도달 불가, 후속 질문 하나가 실행 큐를 죽인 문제, 신입에게 경력 8년 공고 추천은
**단위 테스트 전부 통과 상태에서** 실대화 로그를 읽어야 나왔다 `[→ 07-28 ④⑤⑥]`. 릴리스 전
실기동 대화 한 번은 테스트 수십 건보다 값이 크다.

**A-3. 저장된 지표는 조용히 죽는다.**
플래너 정확도 100% 는 baseline 저장 **5시간 뒤** 프롬프트 규칙이 추가되면서 죽은 숫자가 됐고,
재측정하니 67% 였다 `[→ 07-29 ⑥]`.
→ **프롬프트·판정 로직 변경과 평가셋 재측정은 같은 커밋에 있어야 한다.** 아니면 baseline 은 사실이
아니라 유물이다.

**A-4. 평가 하네스가 있으면 문제를 숫자로 잡고 개선을 숫자로 증명할 수 있다.**
로드맵이 촉박한 제약에서 시간 예산을 초과하는 것(206h > 180h)은 하네스가 잡았고, 예산 재적합을
구현한 뒤 같은 평가셋에서 준수율 0.5 → 1.0 을 확인했다 `[→ 07-15 ④]`. 발견→수정→재측정 루프가
곧 산출물이다.

**A-5. 측정 도구 자체가 틀릴 수 있다.**
하이브리드 파싱 F1 이 0.08 로 나왔는데 실제 출력은 정답과 의미가 같았다 — 정답 라벨의 조사 띄어쓰기
("HTML 과")가 토큰 매칭을 깨뜨린 것이었다 `[→ 07-24 ①]`. 평가 하네스가 **프로덕션이 아닌 흐름**을
재고 있던 사례도 있다(저신뢰 폴백을 "되묻기"로 뭉갬) `[→ 07-29 ⑥]`.
지표가 상식과 크게 어긋나면 **먼저 채점기와 라벨을 의심한다.**

**A-6. 총계만 보면 개선과 퇴행이 상쇄돼 안 보인다.**
플래너 프롬프트를 고쳐 총 정확도 0.67 → 0.78 로 올렸는데, 케이스별로 보니 **고친 것 8 / 깨뜨린 것 6**
이었다 `[→ 07-29 ⑥]`. 그래서 두 가지가 규율이 됐다 — **케이스별 판정을 본다**, 그리고
**좁히는 문장과 넓히는 문장을 같은 커밋에 넣지 않는다**(원인을 가를 수 없어진다).

**A-7. 지표는 축을 갈라야 원인이 보인다.**
"일관성 k/N" 하나로 재면 실패가 전부 "불일치"로 뭉쳐 온도·프롬프트 경화를 헛되게 뒤졌을 것이다.
**정확도(맞았나)와 안정성(매번 같은가)을 분리**하니 실패 17건 중 flaky 는 3건뿐이고 나머지는
프롬프트 과잉 적용 5건 + 데이터셋 낡음 6건임이 바로 드러났다 `[→ 07-29 ⑥]`.

**A-8. 측정 전에 유력해 보이는 손잡이는 대개 값이 없다.**
"재현성이 문제일 것"이라 보고 온도 0 실험을 했는데 안정성 0.94 → 0.95, 거의 변화가 없었다
`[→ 07-29 ⑥]`. "단순한 업무 = 경량 모델 가능"도 실측에서 두 곳이 깨졌다 `[→ 07-24 ③]`.
"중복을 없앴으니 빨라졌겠지"라던 선빌드 최적화는 임계 경로에 **8.3초**를 얹고 있었다 `[→ 07-29 ⑤]`.
→ **아끼는 가설부터 재라.** 측정이 5분이면 추측할 이유가 없다.

## B. LLM 은 "부탁"이 아니라 "구조"로 다룬다

**B-1. 프롬프트로 부탁하는 것보다 스키마에서 빼는 게 확실하다.**
`roleCategory`/`seniority` 를 LLM 이 추측하지 않게 하려고 프롬프트 규칙을 쓰는 대신
**출력 스키마에서 필드를 제거**했다 `[→ 07-16 ⑤]`. 마찬가지로 `semantic_judge` 는 자유 서술 대신
**관련 문장의 인덱스 배열만** 반환하게 해서 이유를 지어낼 자리를 없앴다 `[→ 07-20]`.

**B-2. 스키마 필드의 `description` 은 문서가 아니라 지시문이다.**
`AgentPlan.confidence` 에 description 을 빼먹었더니 모델이 `0.0` 을 채웠고, **자기가 고른 계획이
임계값에서 잘려 나갔다** — 이력서를 냈는데 분석이 안 돌던 원인이다 `[→ 07-27 ①]`.

**B-3. LLM 은 "값 없음"을 그럴듯한 문자열로 채운다.**
회사명을 못 찾자 `companyName: "<UNKNOWN>"` 를 넣었고, 그 값으로 RAG 를 조회하려 했다
`[→ 07-16 ②]`. 추출 결과는 항상 자리표시자·빈 문자열을 씻어내고(`_clean_field`) 하류에서
**값의 존재 여부로 분기**해야 한다.

**B-4. 구조로 막을 때는 "무엇을 막는지" 분명히 해야 한다.**
`action ∈ {use_tool, reply}` 스키마가 모델이 `action="save_draft"` 로 쓴 것을 막아 **턴 전체를
실패시켰다** `[→ 07-29 ①]`. 막아야 할 것은 **없는 도구 이름**이었는데 실제로는 **표기 형식**까지
막고 있었다. 환각 차단(등록된 이름만)은 유지하고 표기는 하네스가 정규화한다.

**B-5. 표현 계층도 검증을 면제받지 않는다 — 단, 금지 목록에 일상어를 넣으면 기능이 죽는다.**
`ack`·`nl_render`·대화 응답 모두 금지표현 검사를 통과해야 채택된다. 반면 금지 목록에
`반드시`·`무조건` 같은 **코칭 문장의 일상어**가 있어서 면접 답변 점검 턴이 매번 템플릿으로 떨어졌다
`[→ 07-28 ⑦]`. 해결은 목록 완화가 아니라 **위반 낱말을 알려주고 한 번 다시 쓰게 하고, 계속 걸리면
그때 폴백(이유 기록)** 이다.

**B-6. 판단은 결정론, LLM 은 입구와 출구.**
3계층(읽기 / 판단 / 말하기)으로 역할을 갈라, LLM 호출을 **입구(추출)와 출구(표현)** 에만 두고
몸통(매칭·계산·검증)은 데이터와 룰이 돌린다 `[→ 07-16 ⑤]`. 이 구조의 실질 이득은
**LLM 없이 전 구간을 1초대에 검증할 수 있다**는 것이다(테스트 381건 / 1.2초 / API 비용 0원).
예외는 원칙을 인지한 상태로 **국소적으로만** 두고 근거를 코드에 적는다 `[→ 07-20]`.

**B-7. "전부 LLM 에 맡기면 더 정확하다"는 가설은 기각됐다.**
A/B 실험(공고 6건 × 3회 × 2변형): 요구사항 F1 은 동률(0.971 vs 0.958, 잡음 범위)인데
**재현성은 하이브리드 우위**(5/6 vs 4/6) `[→ 07-24 ②]`. LLM-only 는 같은 공고에 `fitGrade` 가
실행마다 달라질 수 있다는 뜻이다. 추출은 어차피 양쪽 다 LLM 이 하므로 정확도가 갈릴 구조가 아니고,
차이는 **룰이 고정해 주는 재현성**에서 나온다.

**B-8. 모델 티어는 업무의 겉보기 단순함이 아니라 지점별 실측으로 정한다.**
플래너를 경량으로 내리자 정확도 100% → 48.8% 로 붕괴했고, `nl_render` 는 경량이 **오히려 느리고**
(6.4s → 15.6s) 문체가 무너졌다 `[→ 07-24 ③]`. 스키마 제한과 결정론 검증기가 있어도
**"무엇을 고를지"의 품질은 모델에서 나온다.**

## C. 실패와 "모른다"를 정직하게 다룬다

**C-1. 가짜 폴백이 가장 위험하다.**
mock 폴백이 "키 없음(개발)"과 "호출 실패(실운영)"를 구분하지 못해, LLM 호출이 실패하면
**그럴듯한 가짜 결과가 진짜처럼** 나왔다 `[→ 07-15 ③]`. 이후 규칙: 키 없음이면 mock(개발 편의),
**호출 실패면 빈 결과 + `generation_failed` 경고**. 지어내지 않는다.

**C-2. `None`("모른다")과 `0.0`("없다/안 닮았다")은 다른 값이다.**
`similarity()` 가 실패 시 `0.0` 을 반환하면 그건 미충족 오판을 만든다 — 실패는 `None` 이다
`[→ 07-16 ⑥]`. 경력 개월수도 항목 하나라도 결측이면 총계를 `0` 이 아니라 `None` 으로 둔다.
등급 산출도 **계산된 카테고리만** 가중 평균하고 정규화한다 — 모르는 항목을 0점으로 깔지 않는다
`[→ 07-21 ②]`. 계산 근거가 없으면 등급을 단정하지 않고 `판정불가` 로 남긴다.

**C-3. 실패 이유를 삼키지 않는다.**
루프가 `None` 을 돌려주자 호출부가 폴백을 만들며 `warnings` 를 잃어 **"왜 템플릿 답변이 나왔는지"
흔적이 없었다** `[→ 07-28 ⑧]`. → 항상 `outcome` 을 돌려주고 폴백이 이유를 싣는다. 같은 대가를 두 번
치른 뒤(0728·0729) 표현 도구의 계약도 `문장` → `(문장, 경고)` 로 바꿨다 `[→ 07-29 ④]`.
위임(에이전트 간 호출)도 상대의 경고를 그대로 올린다.

**C-4. 아무것도 바꾸지 않은 결정도 기록한다.**
관찰 루프의 `continue` 가 `trace.emit` 전에 빠져나가 **로그에 흔적조차 없었다** — 이 구조의 핵심 주장
("결과를 보고 다시 정한다")이 관측 불가였다 `[→ 07-28 ②]`. 발동했지만 아무것도 바꾸지 않았다는
사실 자체가 데이터다.

**C-5. 실패를 전체 실패로 만들지 않는다.**
RAG 미연결·문서 추출 실패·URL 수집 실패는 예외가 아니라 **경고 + 빈 결과**로 흡수하고 나머지 근거로
진행한다. 단 빈 결과를 "0건"이라고 단정하지 않는다 — 이력서 없이 추천할 때는
**역량 일치를 계산하지 않았음을 명시**한다 `[→ 07-28 ④]`.

## D. 상태·계약: 파생하지 말고 단일 출처를 만든다

**D-1. 값을 파생하면 파생 입력의 정밀도까지 계약이 된다.**
`sessionId` 를 `"conv-{id}-{createdAt 초}"` 로 매 요청 계산했는데, `@CreationTimestamp` 는 나노초를
담고 `DATETIME` 컬럼은 소수점을 **반올림**한다 → **소수점 .5 이상에 생성된 대화(약 절반)가 두 번째
턴부터 맥락을 통째로 잃었다** `[→ 07-28 ①]`. 다중 턴 에이전트는 아예 성립할 수 없었다.
→ 키처럼 안정성이 본질인 값은 **계산하지 말고 생성 시 한 번 정해 저장**한다.

**D-2. 같은 사실이 두 곳에 선언되면 조용히 갈라진다.**
`AgentSpec.produces` 와 세션 `ASSET_KEYS` 가 따로 있어 면접 턴이 실서버에서 매번 `KeyError` 로
죽었다 `[→ 07-29 ③]`. 단일 출처가 어려우면 **둘을 대조하는 테스트가 그 대용품**이다:
*모든 에이전트가 만든다고 선언한 자산은 세션 저장소가 받는 키여야 한다.*
같은 이유로 `career_graph` 가 자체 보유하던 직군 별칭·연차 사다리를 걷어내고 `role_taxonomy` 로
단일화했다 `[→ 07-16 ⑤]`.

**D-3. 연속값을 조기에 버킷화하면 정보가 사라진다.**
룰이 정확히 뽑은 `minYears=2` 를 5칸 사다리(junior)로 뭉갠 뒤 버려서, **0년과 2년이 같은 칸에서
충돌해 "신입이 경력 2년 이상 공고를 충족"** 하는 오판이 났다 `[→ 07-27 ②]`.
→ 원값(`minYears`)과 원문 근거(`yearsEvidence`)를 보존하고, 숫자가 있으면 **숫자 대 숫자**로 비교하고
칸 비교는 키워드만 있는 공고의 폴백으로 강등한다. 표기도 **공고가 한 말 그대로** 쓴다
(공고에 없는 "신입" 같은 단어를 만들지 않는다).

**D-4. 같은 사실을 두 경로가 각각 판정하면 답변이 자기모순이 된다.**
순수 연차 줄이 텍스트 의미판정(충족)과 연차 룰(미충족) 양쪽에서 다르게 판정됐다 `[→ 07-27 ②]`.
→ 한 요건은 한 담당이 단독 판정한다.

**D-5. 계약을 넓힐 때는 기본값 있는 추가 필드로.**
`AnalyzeResponse.summary`·`fitGrade`·`overallScore` 는 기본값이 있어 기존 소비자를 깨지 않는다.
다만 **모르면 좋은 기능이 그냥 안 쓰인다** — 외부 계약을 건드렸으면 소비 팀에 공유하는 것까지가
작업이다 `[→ 07-16 ⑤]`.

**D-6. 산출물에 붙는 수치는 산출물을 다시 재서 붙인다.**
루프 도중의 마지막 점검값을 그대로 실었더니, 문단을 3문장으로 고쳐 놓고도 저장분에는
**2문장(고치기 전 값)** 이 남았다 `[→ 07-29 ②]`. 점검을 순수 함수로 빼고 **내보내는 산출물을 다시
재서** 싣는다 — 루프의 점검 도구와 최종 측정이 같은 자를 쓴다.

**D-7. 계산했는데 답변에 안 실리면 계산하지 않은 것과 같다.**
중·하 등급에서 `find_alternatives` 는 이미 돌고 있었는데 결과가 답변에 실리지 않아 버려졌다
`[→ 07-28 ⑨]`. `application_plan` 도 산출물인 지원 경로 2~3개가 대화 채널에 도달하지 않았다
`[→ 07-29 ⑦]`. 파이프라인 끝에 **사용자에게 도달하는지**까지 확인한다.

## E. 규칙과 구조: 근거를 함께 적는다

**E-1. 규칙을 만들 때는 규칙의 *근거*를 함께 적는다.**
"도구 뒤에는 관찰을 걸지 않는다"를 코드로 강제했는데, 그 근거는 *결정론이라 재선택 여지가 없다* 이지
*도구라서* 가 아니었다. `fit_analysis` 는 결과가 뒤 단계의 타당성을 실제로 바꾸므로 근거가 성립하지
않는다 — 그대로 뒀다면 **가장 재선택이 필요한 지점에서 관찰이 조용히 꺼졌을 것이다** `[→ 07-29 ④]`.
근거를 적어 두면 근거가 성립하지 않는 항목을 나중에 알아볼 수 있다. `kind` 만 보고 분기하면 못 알아본다.

**E-2. 되돌리기 쉬운데 되돌리면 원래 문제가 돌아오는 결정은 테스트로 묶는다.**
`uncertain` → `not_met` 으로 바꾸면 5건, `Spring Boot → Java` 함의를 추가하면 1건이 깨진다
(변이 주입으로 확인) `[→ 07-16 ⑤]`. 설계 원칙도 회귀 감시가 필요하다 —
`test_find_alternatives_never_calls_llm` 처럼 **"판단 계층에 LLM 을 추가하면 실패하는 테스트"** 를 둔다.

**E-3. (의도 × 자산) 대응표는 곱으로 커지고 문장이 조금만 달라져도 어긋난다.**
의도 7라벨 분류 + 대응표 + 자산별 강등 규칙을 전면 제거하고,
**추론은 자율(플래너) / 행동 집합·상태 전이는 하네스(스키마 Literal · 검증기 · 금지표현)** 로 갈랐다
`[→ 07-27 ③]`. 플래너에는 `agent_feasibility()` 로 **지금 무엇이 실행 가능한지**를 강제 주입해
그라운딩한다. 검증기는 **전제 확인·생산자 삽입·실행 불가 제거만** 하고 "무엇으로 대신할지"는 정하지 않는다.

**E-4. 생산자가 없는 전제는 영구 실행 불가를 만든다.**
`job_recommend` 의 전제가 `("resume",)` 뿐이었고 `resume` 는 사용자 첨부라 생산자가 없다 →
이력서 없는 사용자에게 이 에이전트는 **영구히** 실행되지 않았고, 실공고 2053건이 적재된 상태에서
"공고 데이터가 없다"는 답이 나갔다 `[→ 07-28 ④]`.
→ `preconditions_any`("이 중 하나라도")를 도입해 **생산자가 있는 대안 전제**를 열어 둔다.

**E-5. 갈리는 판단은 코드로 못 박지 않는다.**
등급이 낮은데 생성 단계가 예정되면 강제 분기하는 규칙에서 **"중"(0.4~0.7)은 넣지 않았다** —
사람마다 갈리는 구간을 코드로 확정하는 것이 이 규칙이 피하려는 실수다. 또 규칙은 판정이 **같은 턴에**
돈 경우만 걸려서, 등급을 본 뒤 "그래도 써줘" 하면 걸리지 않는다(사용자를 가두지 않는다) `[→ 07-29 ⑦]`.

**E-6. LLM 자유도를 넓힐 자리와 좁힐 자리는 다르다.**
넓힌 것: 에이전트 선택뿐 아니라 **인자까지** LLM 이 정한다(`AgentSpec.params`) — `"데이터 엔지니어 공고
찾아줘"` 가 30초 경로에서 4.7초 경로가 됐다 `[→ 07-28 ⑩]`. 좁힌 것: 오케스트레이션 관찰을 LLM 에서
**결정론 규칙**으로 되돌렸다 — 그 관찰은 8턴 중 실행을 바꾼 사례가 0건이면서 턴당 11.5초를 썼다
`[→ 07-28 ②]`. 기준은 *다시 정할 것이 있는가* 다: 도구는 결정론(정확해야 하는 것),
에이전트는 LLM(자유도가 필요한 것), 근거는 도구가 준 것만 쓴다.

**E-7. RAG 를 쓸지 말지는 데이터의 성질로 가른다.**
비정형 + 의미유사검색 + 자체 축적 → **벡터 RAG**(유사 공고) / 유한 + 안정 + 정형 →
**정형 DB**(자격증) / 최신 + 희소 → **웹검색**(희소 기업, 어댑터 내부 폴백) `[→ 07-16 ④]`.
강의 추천을 벡터 RAG 로 하려던 계획을 폐기한 이유는 **최신성이 핵심 가치인 데이터는 벡터 DB 스냅샷과
상충**하기 때문이다. 자격증 DB 로 바꾼 덤으로 `doneCriteria` 가 "SQLD 최종 합격"처럼 진짜 측정 가능해졌다.

**E-8. 사전(룰)이 먼저, 모델은 사전이 비었을 때만.**
표기 변형(대소문자·점·공백·하이픈)은 **정규화로 자동 흡수**하고 별칭에는 글자 구성 자체가 다른 표기만
등록한다 — 수동 나열은 빠뜨린 변형을 그냥 놓친다 `[→ 07-21 ①]`. 단 `C++`·`C#` 은 특수문자가 이름의
일부라 정규화에서 제외한다(지우면 `C`/`C++`/`C#` 이 뭉개진다).

**E-9. 커버리지가 곧 판정 품질이다.**
`skill_taxonomy` 에 Android·iOS·Flutter·React Native·Dart 가 없어서 모바일 공고 techStack F1 이
0.75 였고, 5종 추가로 1.0 이 됐다 `[→ 07-24 ①]`. "MySQL 등 RDBMS" 에서 RDBMS·SQL 을 별도로 증명하라고
요구하던 오판은 `implies`(함의 관계) 도입으로 해결했다 `[→ 07-16 ⑤]`.
**새 직군 케이스를 평가셋에 넣는 것이 곧 커버리지 점검이다.**

## F. 작업 위생

**F-1. 새 추출 규칙은 반드시 실데이터(페르소나 파일)로 검증한다.**
`■ 자격 요건 (필수)` 헤더를 정규식이 못 받아 **섹션 분리가 통째로 실패**하고 전문이 LLM 으로 넘어가
필수/우대를 위치가 아니라 추측으로 나누고 있었다 — `■` 는 국내 공고에서 매우 흔하다 `[→ 07-16 ①]`.
손으로 만든 샘플로는 안 나온다.

**F-2. 리팩터링 후에는 임시 스크립트가 아니라 전체 테스트를 돌린다.**
공용 상수를 다른 모듈로 옮기며 참조를 안 고쳐 2개 모듈이 **collection 단계에서 사망**했는데,
임시 스크립트만 돌려서 늦게 발견했다 `[→ 07-16 ③]`.

**F-3. 외부 API 를 하나 연결할 때마다 "테스트가 그걸 진짜로 호출하지 않는지" 확인한다.**
GMS 임베딩 연결 후 `pytest` 가 3초 → 33초가 됐다. `conftest.py` 가 `get_llm` 만 막고 **임베딩은
아무도 막지 않아서** 기존 테스트가 전부 실제 네트워크를 타고 있었다 `[→ 07-20]`.
`from x import y` 로 바인딩된 이름은 원본 모듈만 패치해선 안 먹힌다 — **참조하는 모듈에서 각각** 패치한다.

**F-4. `lru_cache` 로 잡아둔 인스턴스는 provider 교체를 무력화한다.**
`SkillTaxonomy.__init__` 에서 embedder 를 한 번 잡아두면 나중에 provider 를 바꿔도 낡은 embedder 를
계속 쓴다 → **호출 시점마다 `get_embedder()` 를 새로 부른다** `[→ 07-20 부수]`.

**F-5. 전송 계층은 직접 만들지 말고 공식 SDK 를 쓴다.**
`urllib` 로 직접 구현한 임베딩 클라이언트가 실제 GMS 응답에서 `http.client.IncompleteRead` 를 던져
"절대 예외를 던지지 않는다"는 모듈 규칙을 깼다. 원인 조사 대신 이미 설치돼 있던 공식 `openai`
SDK(httpx 기반)로 교체해 해결했다 `[→ 07-20 부수]`.

**F-6. 정규식은 반드시 반례로 검증한다.**
`\d+년` 이 `경력 3-8년` 에서 **상한 8** 을 집어 3년차를 잘못 걸러냈다(하한을 읽어야 한다).
제목의 `경력7년이상` 을 보강할 때는 `경력` 이 **숫자에 붙은 패턴만** 인정해 `창립 20년`·`2026년`
오탐을 차단했다(실데이터 22건 보강, 오탐 0) `[→ 07-28 ⑥]`.

**F-7. 로그가 안 보이면 코드가 아니라 로거 설정을 본다.**
uvicorn 이 루트 로거를 설정하지 않아 INFO 가 전부 버려지고 있었다 → 브릿지에 `basicConfig` 추가
`[→ 07-27 ④]`. trace 중첩 시 안쪽 레코더가 이벤트를 독점하던 버그도 같은 날 부모 체이닝으로 고쳤다.

**F-8. 테스트는 결정론·고속으로 만들어야 자주 돌린다.**
`conftest.py` 의 autouse 픽스처로 LLM·임베딩을 강제 미설정 처리해 **76초 → 1초**가 됐고, 그 뒤로
실제로 매번 돌리게 됐다 `[→ 07-15 ②]`. 현재 381건 / 1.2초 / API 비용 0원.
실 LLM 검증은 수동 스크립트(`tests/run_user1.py`, 평가 하네스)가 담당한다.

**F-9. 문서의 숫자는 갱신하지 않으면 셋 다 달라진다.**
테스트 수치가 README 133 / 회고 144 / 실코드 162 로 어긋나 있었다 `[→ 07-24 ④]`.
같은 사실을 여러 문서에 적으면 갱신 지점도 그만큼 늘어난다 — 시각화 문서 3종이 병존하게 된 것도 같은 부채다.

**F-10. 확인하지 않고 단정하지 않는다.**
"테스트가 없다"고 판단해 문서에까지 적었는데 `tests/` 는 처음부터 있었다 `[→ 07-16 ③]`.

# 2부 — 사건 기록

## 2026-07-15 — 오케스트레이션 골격에서 나온 결함 4건

### ① 재시도 루프가 한 번도 발동하지 않으면서 정상처럼 보였음

- **증상**: 검증기(`verify_result`)가 환각 근거를 잡아 재시도 신호를 내는데, 그래프가 실제로
  `analyze_gap` 으로 되돌아가는 일이 없었다. 예외도 안 나고 결과도 `completed` 라 겉보기 정상.
- **원인**: `route_verification` 이 `verify_result` 가 **이미 증가시킨** `retryCount` 를 다시 검사하는
  **이중 가드**. 첫 재시도조차 예산 초과로 판정됐다.
- **해결**: 재시도 예산 판단을 `verify_result` **한 곳으로** 모으고, 라우터는 `retrySignal` 만 따른다.
  `analyze_gap` 을 환각 유발 stub 으로 교체해 **1회 재시도 후 종료**(무한루프 없음)를 검증하는
  통합 테스트(`test_retry_loop.py`)를 추가했다. 
- **교훈**: 같은 조건을 두 곳에서 검사하면 한쪽이 다른 쪽의 부작용을 본다. 그리고 루프는
  "예외가 안 났다"가 아니라 **발동 자체**를 테스트해야 한다. → `A-1`

### ② 테스트가 실 LLM 을 호출해 76초가 걸렸음

- `tests/conftest.py` 에 autouse 픽스처로 `get_llm` 을 강제 미설정 → 모든 자동 테스트가
  결정론 mock 폴백 경로로 실행. **76초 → 1초.**
- 실 LLM 검증은 수동 스크립트(`tests/run_user1.py`)가 담당하도록 분리. → `F-8`

### ③ "가짜 폴백" — LLM 호출 실패 시 가짜 결과가 진짜처럼 나왔음

- **원인**: mock 폴백이 "키 없음(개발 중)"과 "호출 실패(실운영)"를 구분하지 못했다.
- **해결**: `structured.py` 에 최대 3회 재시도(일시적 오류 흡수) + `llm_unconfigured()` 헬퍼로 두 상황을
  구분. 5개 노드의 폴백을 분기 — 키 없음이면 mock, **호출 실패면 빈 결과 + `generation_failed` 경고.**
- 겸해서 오케스트레이터가 **다음 에이전트를 부르기 전에 직전 산출물을 검증**하고, 생성 실패면 다음으로
  넘어가지 않고 같은 에이전트에게 다시 지시하는 구조(`nodeFailed`/`retryCount[node]`, `MAX_GEN_RETRY=1`)를
  넣었다. 빈 답으로 그냥 진행하지 않는다. → `C-1`

### ④ 평가 하네스가 로드맵 예산 초과를 잡음 → 수정 → 재측정으로 증명

- baseline(실 LLM): 촉박한 제약(12주 × 15h = 180h)에서 Roadmap Planner 가 **206h** 를 계획.
  avg F1 1.0 / 근거성 1.0 / 금지표현 0 인데 **로드맵 준수율 0.5.**
- `_refit_roadmap_to_budget()`: 예산 초과 시 **우선순위 낮은 항목부터 제외**(최소 1개 유지, 단일 항목이
  초과하면 예산으로 캡, 제외 항목은 assumptions/warning 에 기록).
- 동일 평가셋 재측정: **준수율 0.5 → 1.0**, 다른 지표 회귀 없음. → `A-4`

### ⑤ 알려진 한계 — 잡코리아 URL 은 본문이 JS 렌더링

- `GI_Read` 공고는 stdlib fetch 로 본문을 못 가져온다. URL 경로는 회사명·제목만 잡고 필수요건은
  **잡코리아 공용 푸터를 오파싱**했다. 파서 로직 자체는 정상(`text` 소스타입으로 검증 완료).
- 당시 대응: 실사용 시 **본문 붙여넣기(`text`) 권장**. 완전 수집은 headless 브라우저 도입 과제로 남겼다.

## 2026-07-16 — 3계층 전환 중 돌려 보고서야 드러난 결함들

> 손으로 만든 샘플이나 코드 리뷰만으로는 못 잡았을 종류다.

### ① `■ 자격 요건 (필수)` 헤더 미인식 — 섹션 분리가 통째로 실패

페르소나 공고(`tests/docs/user1`)로 돌려서 발견. 도형 불릿·접미 괄호를 정규식이 못 받아
섹션 분리가 실패 → **전문이 LLM 으로 넘어가 required/preferred 를 위치가 아니라 추측으로 나누고 있었다.**
`■` 는 국내 공고에서 매우 흔하다. → `F-1`

## 2026-07-20 — 도메인 키워드 임베딩 매칭이 관련 없는 문장에 더 높은 점수를 줌 → LLM 폴백으로 전환

### 증상

`gap_matcher`의 3차 도메인 키워드 매칭(`domainKeywords` 비교)을 임베딩 유사도로 구현하려고
GMS(SSAFY API 게이트웨이) 경유 OpenAI 임베딩을 실제로 연결한 뒤 실측했더니, **관련 없는
문장이 관련 있는 문장보다 더 높은 유사도 점수**를 받는 역전이 반복 재현됨.

```
0.271  [관련]  '이벤트 드리븐 아키텍처 설계 경험' vs 'Kafka를 활용해 비동기 메시지 처리 파이프라인을 구축했습니다'
0.364  [무관]  '이벤트 드리븐 아키텍처 설계 경험' vs 'React로 프론트엔드 UI를 개발했습니다'   ← 무관이 더 높음
```

### 조사 과정

1. **1차 가설: 비교 대상이 너무 짧아서 그런가?** (단일 키워드 "커머스" vs 긴 문장)
   → 키워드를 짧은 문장으로 확장("커머스" → "커머스 도메인 경험")해서 재시도. **개선 안 됨**,
   같은 역전 패턴 재현.
2. **2차 가설: 모델이 작아서(`text-embedding-3-small`) 그런가?**
   → `text-embedding-3-large`로 교체(코드 변경 없이 `.env`의 `EMBED_MODEL`만 변경). **개선 안
   됨** — 오히려 관련 최소값(0.205)과 무관 최대값(0.358)의 격차가 더 벌어짐.
3. **결론**: 모델 크기·쿼리 길이 문제가 아니라, **짧은 도메인 키워드 vs 기술 문장을 코사인
   유사도로 세밀하게 구분하는 태스크 자체가 범용 임베딩(OpenAI `text-embedding-3-*`)에
   약하다**고 판단. 두 모델 다 "기술 문장처럼 생겼다"는 표면적 유사성에 끌려가는 것으로
   추정(둘 다 짧은 개발 경력 서술문이라 도메인이 달라도 벡터가 가까워짐).

### 해결

이 판정(도메인 키워드 관련성)에 한해 **LLM 구조화 출력으로 전환**. `src/jobis_ai/semantic_judge.py`
신규 작성:

- `judge_domain_relevance(topic, evidence_texts) -> list[int] | None`
- 자유 서술이 아니라 **관련 문장의 인덱스 배열만** 강제 반환(구조화 출력) — 이유를 지어내지
  못하게 막음
- 기존 읽기 계층 인프라(`structured.run_structured`) 그대로 재사용 — 새 LLM 호출 경로를
  따로 안 만듦
- LLM 미설정/실패 시 예외 대신 `None`("모른다") 반환 → `gap_matcher`가 `not_met`이 아니라
  `uncertain`으로 처리

`gap_matcher._match_domain_keyword`는 **1차 포함 매칭(룰)이 여전히 먼저**고, 그게 실패했을
때만 이 LLM 폴백을 탄다. `Match.method` 필드에 `"keyword"`/`"llm_semantic"`/`"undecidable"`을
남겨 어느 경로로 판정했는지 항상 추적 가능하게 함.

**재검증 결과** (같은 Kafka/React 케이스):
```
'이벤트 드리븐 아키텍처' → met, matched=[ev-2(Kafka)]   — ev-1(React)은 정확히 제외됨
'블록체인'               → not_met                       — 무관한 키워드는 정확히 걸러짐
```

### 왜 이게 `§0`("판단 계층에 LLM 금지") 원칙의 예외인가

이 프로젝트 전체는 "판단(Decide) 계층은 결정론이어야 한다"를 핵심 원칙으로 삼아왔다
(`agent-derivation-and-tools.md` §0). 이번 결정은 그 원칙을 **인지한 상태로, 국소적으로**
깬 것이다 — 근거는 추측이 아니라 위 실측(같은 모델을 두 번 바꿔봐도 재현되는 신호 부족)이다.
`semantic_judge.py` 상단 docstring에 이 예외의 범위와 이유를 명시해뒀다: **이 패턴을 다른
판단 노드로 함부로 넓히면 안 된다.**

### 부수적으로 발견한 버그: 테스트가 실제 GMS API를 호출하고 있었음

GMS 연결(`.env`의 `EMBED_PROVIDER=openai` + 실제 `GMS_KEY`) 이후 `pytest`가 3초 → **33초**로
느려짐. 원인: `tests/conftest.py`가 `get_llm`만 미설정으로 강제하고 있었고, **임베딩은 아무도
막고 있지 않아서** 기존 임베딩 관련 테스트(`test_gap_matcher.py`의 uncertain 판정 테스트 등)가
전부 진짜 네트워크 호출을 하고 있었다. 결과도 실제 임베딩 점수 기준으로 달라져서
`NullEmbedder` 가정하에 짠 assertion들이 깨짐.

**해결**: `conftest.py`에 `force_null_embedder` 픽스처 추가 — `jobis_ai.gap_matcher.get_embedder`
와 `jobis_ai.skill_taxonomy.get_embedder`를 `NullEmbedder`로 강제 패치. `from x import y` 형태로
이름을 각 모듈 네임스페이스에 바인딩해 쓰고 있어서, `jobis_ai.embed.get_embedder` 하나만
패치해선 안 먹혔다 — 각 모듈에서 참조하는 이름을 각각 패치해야 했다.

**교훈**: 외부 API를 하나 연결할 때마다, "테스트가 그걸 진짜로 호출하지 않는지"를 반드시
같이 확인해야 한다. LLM만 막고 임베딩을 빠뜨린 게 이번 사고 원인.

### 같은 날 부수 사건 2건

- **`lru_cache` 가 provider 교체를 무력화**: `get_skill_taxonomy()` 가 프로세스당 1개 인스턴스라
  `__init__` 에서 embedder 를 잡아두면 나중에 provider 를 바꿔도 낡은 embedder 를 계속 쓴다 →
  `_resolve_by_embedding` 안에서 **매번 `get_embedder()` 를 새로 호출**하도록 설계. → `F-4`
- **`urllib` 직접 구현 → `http.client.IncompleteRead`**: 실제 GMS 응답에서 잡히지 않는 예외가 발생해
  "절대 예외를 던지지 않는다"는 모듈 규칙을 깼다. 원인 조사 대신 이미 설치돼 있던 공식 `openai`
  SDK(httpx 기반)로 교체해 해결. → `F-5`

### 남은 것 / 후속 조치

- **`gap_matcher._match_by_embedding`(서술형 요구사항 2차 매칭)도 같은 패턴이라 신뢰도가 낮을 가능성이
  높다** → 이후 같은 방식(LLM 구조화 출력 폴백)으로 전환하고 임베딩 경로·임계값을 **전부 삭제**했다.
  `gap_matcher` 는 더 이상 임베딩을 쓰지 않는다.

## 2026-07-21 — 동의어를 손으로 나열하고 있었음 / 모르는 항목을 0점으로 깔고 있었음

### ① 표기 변형을 `aliases` 에 수동 나열 → 정규화로 흡수

- **증상**: `"React.js"` 와 `"ReactJS"` 가 서로 다른 dict 키라 둘 다 등록해야 둘 다 잡혔다.
  `node` 는 `("NodeJS","Node.JS","노드js","노드 js")` 처럼 같은 스킬의 표기 변형을 나열하고 있었고,
  **나열에서 빠진 변형(사용자가 "react js" 로 띄어 쓰면)은 그냥 놓쳤다.**
- **해결**: `_normalize_key()` — 소문자화에 더해 구분자(`.`, 공백, `-`, `_`)를 제거한 키로 조회.
  인덱스 생성과 조회 **양쪽**에서 같은 함수를 쓴다. 원문 스캔은 `_flexible()` — 별칭 안의 구분자를
  0개 이상 허용(`Node[.\s\-_]*js`)해서 등록 별칭 하나가 모든 변형을 잡는다.
- **주의**: `'+'`·`'#'` 은 구분자 집합에서 **제외**했다. `C++`·`C#` 은 특수문자가 이름의 일부라
  지우면 `C`/`C++`/`C#` 이 같은 키로 뭉개진다.
- **남긴 별칭 선택 기준**: **구분자를 품은 대표형**을 남긴다("노드 js" 를 남기면 유연 매칭이 "노드js"
  까지 커버한다. 반대로 붙여 쓴 형태만 남기면 띄어 쓴 변형을 못 잡는다). → `E-8`

### ② 종합 등급 — 계산되지 않은 카테고리를 0점으로 깔지 않음

- `roleRelevance`/`domainFit` 은 **무조건 `None`** 으로 하드코딩돼 있었다("근거 없음 — 지어내지 않는다").
  그런데 매칭 신호는 이미 `match()` 안에 있었고(`domain_keyword`·`seniority` 요구사항) 집계에서만
  안 쓰였다 → `Match.kind` 를 추가해 카테고리를 판정 결과까지 보존하고 집계에 연결했다.
- `overall_fit()` 은 **계산된 카테고리만** 골라 가중 평균하고 그 가중치 합으로 정규화한다.
  하나도 없으면 등급을 단정하지 않고 `(None, "판정불가")`. → `C-2`
- **합격 예측 금지 원칙 유지**: 등급 `상` 도 "합격 가능"이 아니라 "요구 역량 충족"으로만 말한다.
  LLM 에는 등급 라벨('상')을 넘기지 않고 **자연어 진단 문장만** 넘긴다(라벨을 그대로 읊으면 어색하다).

### ③ 발표 자료 작도 중 — 표와 대조하다 잡은 라벨 오류

흐름도의 `route_after_roadmap` 경로에 `적합도 상 · 대안 없음` 라벨을 달았는데, 이 엣지는
**plan_roadmap 을 거친 뒤**의 분기이므로 정의상 적합도 상이 될 수 없다(상이면 로드맵을 건너뛴다).
라우터 표의 서술과 대조하다 걸러 `대안 요청 없음 → 대안 생략` 으로 정정했다.
같은 날 카드 렌더링에서 `white-space:nowrap` 때문에 칩이 카드 밖으로 넘치는 것도 헤드리스 캡처로 잡았다.
**도식은 표와 교차 검증하고, 렌더링은 실제로 캡처해서 본다.**

## 2026-07-24 — 파싱 A/B 실험 중 발견: 평가 라벨 토큰화 왜곡 + skill_taxonomy 모바일 커버리지 공백

### ② 관찰 루프가 턴 시간의 58% 를 쓰면서 아무것도 바꾸지 않았고, 로그에 흔적조차 없었음

**실제 일은 55ms 이고 26.2초(58%)가 아무것도 바꾸지 않은 제어 호출이었다.**
게다가 `continue` 는 `trace.emit` **전에** 빠져나가 로그에 남지 않았다 —
"결과를 보고 다시 정한다"는 이 구조의 핵심 주장이 **관측 불가**였다.

  기존 테스트를 중간 위치로 옮겨 능력 자체는 계속 검증한다.
- **아무것도 바꾸지 않은 continue 도 기록한다.** `dispatch` 이벤트에 `planChanged` 를 실어
  **LLM 판단인지 생산자 삽입인지 로그로 구분**한다. trace 는 턴이 끝나면 사라지므로 로그로도 남긴다.

면접 답변 점검 턴이 매번 템플릿으로 떨어졌다. 금지표현 목록에 `반드시`·`무조건` 같은
**코칭 문장의 일상어**가 있어서다.
→ 목록을 완화하는 대신 **위반 낱말을 알려주고 한 번 다시 쓰게** 한다. 계속 걸리면 그때 폴백(이유 기록).
→ `B-5`

### ⑧ 실패 이유를 삼키고 있었음

루프가 `None` 을 돌려주면 호출부가 폴백을 만들며 `warnings` 를 잃어 **"왜 템플릿 답변이 나왔는지"
흔적이 없었다**(진단에 시간을 썼다). → 항상 `outcome` 을 돌려주고(reply 가 비면 실패) 폴백이 이유를
싣는다. 폴백도 이번 턴 도구 진행분(점검한 답변·다룬 주제)을 보존한다. → `C-3`

### ⑨ 계산해 놓고 답변에 싣지 않았음 / 방향 정정

- 중·하 등급이면 그래프가 이미 `find_alternatives` 를 돌리고 있었는데(`route_after_roadmap`)
  결과가 답변에 실리지 않아 **계산만 하고 버려졌다.** `AlternativeJob.url` 추가하고 답변에 싣는다
  (실측: 등급 하 0.32 턴에서 실공고 3건이 URL 과 함께). → `D-7`
- **공고 URL 입력 방향 정정**: 프로토타입은 URL → 크롤링 DB 키 조회였고 오전에 그대로 이식했지만,
  제품 방향은 다르다 — 사용자가 특정 공고를 가리킨 것이므로 DB 스냅샷이 아니라 **그 URL 의 현재 내용을
  수집·파싱**한다(마감·수정 반영). 공고 DB 는 검색·추천 경로에만 쓴다.
- README 재작성 중 **실제로 그대로 따라가다** `Could not resolve placeholder 'JWT_SECRET'` 기동 실패를
  재현해 잡았다. 실행 문서는 백지에서 따라가 봐야 검증된다.

### ⑩ 개편 — LLM 이 인자까지 정한다 / 도구·에이전트·하네스 3분할

- `AgentSpec.params` 선언 → 플래너 manifest 에 실려 LLM 이 값을 채운다. 에이전트 이름 환각은 `Literal`
  이, **인자 이름 환각은 검증기**(`validate_agent_args`)가 선언과 대조해 막는다. 에이전트별 동적 스키마는
  피했다 — 공급자별 지원이 갈려 하네스가 약해지므로 평평한 목록으로 받고 검증은 코드가 한다.
  `params_satisfy` 로 **인자가 전제를 대신할 수 있음**을 선언(발화에 직군이 있으면 그것이 곧 선호다).
  실측: `"데이터 엔지니어 공고 찾아줘"` → 생산자 삽입 없이 **4.7초**(이전 경로 ~30초).
- `agents/agent_loop.py` 재사용 계약 — **도구**=결정론 파이썬(정확해야 하는 것) /
  **에이전트**=LLM(자유도가 필요한 것, **근거는 도구가 준 것만**) /
  **하네스**=도구 이름 `Literal` 제한·스텝 상한·금지표현 검증·스텝마다 trace+로그.
  소재 선택은 결정론 점수라 LLM 이 순위를 바꿀 수 없다. → `E-6`

## 2026-07-29 — 두 번째 적용에서 드러난 계약의 마찰점

> `agent_loop` 계약을 `coverletter_draft` 에 두 번째로 적용했다. **하네스는 한 줄도 고치지 않고 붙었고,
> 고친 곳은 계약이 아니라 계약과 모델 사이의 마찰 지점이었다.**

### ① 모델이 `action` 칸에 도구 이름을 씀 → 턴이 통째로 실패

- **증상**: 첫 실행이 `action="save_draft"` 로 죽었다. 스키마는 `action ∈ {use_tool, reply}` 이고
  도구 이름은 `tool` 칸이므로 Literal 이 막았고, **3회 재시도 끝에 자소서 턴 전체가 실패**했다.
- **해결**: 두 칸에 나눠 담는 것은 우리 사정이지 모델이 자연스럽게 하는 표기가 아니다.
  `action` 의 허용값에 등록된 도구 이름을 더하고 하네스가 정규화한다. 환각 차단(등록된 이름만)은 그대로.
- **교훈**: 구조로 막을 때는 **무엇을 막는지** 분명히 해야 한다. 여기서 막을 것은 이름의 실재성이었는데
  실제로는 표기 형식까지 막고 있었다. → `B-4`

### ② 산출물에 붙은 수치가 산출물을 잰 값이 아니었음

`lastCheck` 에 루프 도중의 마지막 점검을 그대로 실었더니, 보완 문단을 3문장으로 고쳐 놓고도 저장분에는
**2문장(고치기 전 값)** 이 남았다. 점검 뒤에 재작성이 일어나고 검증이 문장을 지우므로 도중값은 산출물을
설명하지 못한다. → 점검을 순수 함수(`_check_report`)로 빼고 **내보내는 초안을 다시 재서** 싣는다.
루프의 점검 도구와 최종 측정이 같은 자를 쓴다. → `D-6`

### ③ `interview` 자산을 세션이 저장할 수 없었음 (2단계 회귀)

`interview_prep` 은 `produces=("interview",)` 로 다중 턴 상태를 내는데 `ASSET_KEYS` 에 그 키가 없었다.
턴 끝 write-back 이 `KeyError` 로 터진다 — 즉 **면접 연습 턴은 실서버에서 매번 실패했다.**
재현 확인 후 키를 추가하고, 다시 어긋나지 않도록 테스트로 강제했다:
*모든 에이전트가 만든다고 선언한 자산은 세션 저장소가 받는 키여야 한다.*

> 선언(`produces`)과 허용 목록(`ASSET_KEYS`)이 두 곳에 따로 있으면 조용히 갈라진다.
> 둘을 대조하는 테스트가 곧 단일 출처의 대용품이다. → `D-2`

부수적으로: 2턴에서 루프가 `check_draft` 없이 바로 답한 적이 있다. 고칠 기회는 지났지만 묻히지 않게
최종 측정에 남은 지적이 있으면 `coverletter_check_unresolved` 경고로 싣는다.

### ④ 계약 두 곳을 손봄 — 둘 다 "규칙의 근거가 무엇인가"에서 나왔다

- **`render` 가 `(문장, 경고)` 를 낸다.** 다른 도구의 표현은 결정론이라 문장만 돌려주면 됐지만,
  다음 행동 제안은 LLM 스트리밍이라 폴백할 수 있다. 문장만 돌려주는 계약에서는 "왜 기본 문구가
  나왔는지"가 사라진다 — **0728·0729 에 두 번 대가를 치른 실수**라 계약을 바꿨다. → `C-3`
- **`AgentSpec.observe` 예외를 뒀다.** "도구 뒤에는 관찰을 걸지 않는다"를 코드로 강제했는데, 그 근거는
  *결정론이라 재선택 여지가 없다* 이지 *도구라서* 가 아니다. `fit_analysis` 는 결과(등급·need_more_info)가
  뒤에 예정된 자소서·면접의 타당성을 실제로 바꾸므로 근거가 성립하지 않는다. 그대로 뒀다면
  **가장 재선택이 필요한 지점에서 관찰이 조용히 꺼졌을 것이다.**
  > 구분에서 규칙을 끌어낼 때는 규칙의 **근거**를 함께 적어야 한다. 근거를 적어 두면 근거가 성립하지
  > 않는 항목을 나중에 알아볼 수 있다. `kind` 만 보고 분기하면 못 알아본다. → `E-1`

### ⑤ 최적화가 임계 경로에 8.3초를 얹고 있었음

여러 멤버가 각자 프로필을 짓는 중복을 막으려 선빌드 최적화를 넣었는데, 브릿지 실측에서
`dispatch → parallel` 사이에 **8.3초**가 찍혔다. 전제에 resume 이 있다고 프로필을 쓰는 게 아니었다 —
`fit_analysis` 는 그래프 안에서 따로 짓는다. 즉 대부분의 턴에서 헛돈이었다. 빼고 나니 0초가 됐다.

> 최적화도 실측으로 확인해야 한다. "중복을 없앴으니 빨라졌겠지"가 임계 경로에 8초를 얹고 있었다.
> **단위 테스트는 이걸 절대 못 잡는다.** → `A-8`

(같은 날 시퀀스 병렬은 실측 이득이 있었다: 순차 21.3초 → 병렬 15.6초. 규율 셋을 코드에 박았다 —
**세션 사본**(남의 턴 중 변경을 보고 판단하지 않는다) · **결과는 큐 순서대로 합친다** ·
**토큰 델타는 끈다**(프론트가 한 버퍼에 이어 붙여 두 에이전트 토큰이 섞인다).)

### ⑥ 기록된 정확도 100% 는 이미 죽은 숫자였음

`planner_harness` 에 `--runs N` + **정확도/안정성 분리 지표**를 넣고 46케이스 × 3회로 다시 쟀다.

| 단계 | 정확도 | 안정성 |
|---|---|---|
| 최초 | 0.6739 | 0.9420 |
| temp 0 (실험) | 0.6884 | 0.9493 |
| 프롬프트 수정 | 0.7826 → 0.8188 | 0.9565 → **0.9855** |
| 데이터셋 갱신 | **0.9275** (되묻기 1.00) | 0.9783 |

네 가지가 나왔다:

1. **재현성은 문제가 아니었다** — 안정성 0.94. **온도를 0 으로 내려도 거의 안 변한다.**
   측정 전엔 유력한 손잡이로 보였던 "티어별 온도 분리"가 **값이 없다**는 것이 확인됐다.
2. **100% 는 회귀가 아니라 죽은 숫자였다** — baseline 저장(07-27 16:24) **5시간 뒤**
   "제출 턴은 정리 먼저" 프롬프트 규칙이 들어왔고 재측정이 없었다.
   → **프롬프트 변경과 평가셋 재측정이 같은 커밋에 없으면 baseline 은 조용히 죽는다.**
3. **하네스가 프로덕션이 아닌 흐름을 재고 있었다** — 저신뢰 폴백(실제로는 `career_chat` 이 돈다)을
   "되묻기"로 뭉개고, 동의 게이트를 빈 키로 기록했다. 둘 다 07-28 에 들어온 경로다.
4. **정확도/안정성 분리가 바로 값을 했다** — 실패 17건 중 flaky 는 3건뿐이고 나머지는 프롬프트 과잉
   적용 5건 + 데이터셋 낡음 6건이었다. "일관성 k/N" 하나로는 전부 "불일치"로 뭉쳐서 온도·프롬프트
   경화를 헛되게 뒤졌을 것이다.

그리고 **프롬프트 수정 과정 자체가 교훈**이었다: `fit_analysis` 예외를 넣으면서 인사 조항을 같이 넣었는데
그 조항이 **기능 요청까지 끌어갔다**("면접 질문 뽑아줘" → career_chat). 총계는 올라갔으니(0.67 → 0.78)
통과시켰을 것이고, 케이스별 판정을 보고서야 **"고친 것 8 / 깨뜨린 것 6"** 이 드러났다.
→ **좁히는 문장과 넓히는 문장을 같은 커밋에 넣지 않는다.** → `A-3`, `A-5`, `A-6`, `A-7`, `A-8`

### ⑦ 프로토타입 비교 — 작은 시스템이 옳게 한 것에 이름을 붙이면 큰 시스템의 공백이 보인다

팀원 프로토타입(`Agent_Test`)과 축별로 대조했다. **비교의 값은 등급표가 아니었다.**

- **결정적 강제 분기**: 프로토타입은 판정 직후 등급을 읽어 대체직군 검색을 **코드가 강제**한다.
  우리는 같은 성격의 규칙을 **관찰 LLM 에 맡겨 뒀고 그 관찰은 한 번도 발동하지 않았다.**
  → `observe_rules.weak_grade_transition` 신설. 등급 `하`·`판정불가` + 생성 단계 예정 →
  `application_plan` 으로 강제 교체. **"중"(0.4~0.7)은 넣지 않았다** — 사람마다 갈리는 구간을 코드로
  못 박는 것이 이 규칙이 피하려는 실수다. 규칙은 판정이 **같은 턴에** 돈 경우만 걸려서, 등급을 본 뒤
  "그래도 써줘" 하면 걸리지 않는다(사용자를 가두지 않는다). → `E-5`
  - 이 규칙에서 실측이 잡은 결함 3건: **ack 가 하지 않은 일을 하겠다고 말했다**(`plan_changed` 는
    dispatch 시점만 본다) · 조사 오류("설계**으로**") · **착지점이 값을 주지 않았다** —
    `application_plan` 의 대화 응답이 `label — headline` 한 줄이라 산출물인 지원 경로 2~3개가
    대화 채널에 도달하지 않았다(→ `render_plan_reply` 결정론 조립). → `D-7`
- **관찰 층에서 LLM 을 걷어냈다**: 프로토타입 루프의 세 성질(전체 히스토리 / 실제 행동 선택 / 답변 작성)을
  `observe_after` 는 **셋 다 갖지 않았다** — 요약을 보고 제어 신호만 냈다. 즉 그 성질의 **열화 모방**이었고,
  그 성질이 사는 곳은 `agent_loop` 다. 오케스트레이션 관찰은 결정론 규칙으로 내리고
  (`orchestrator/observe_rules.py`), `agent_loop` 는 넓혔다(대화 이력을 매 스텝 입력에 추가 등).
  **툴 선택은 LLM, 분기는 조건엣지.**
  - 교체하면서 **실측 결함이 닫혔다**: `runnable_now` 가 순차 실행 직전에 한 번도 검사되지 않아 판정이
    실패해도 자소서가 `analysis=None` 위에서 돌았다(재현 확인). 예전 판정은 "하나라도 돌 수 있으면 계속"
    이라 **못 도는 항목을 그대로 실행**했다.
- **루프로 옮기지 않은 것도 근거를 남겼다**: `resume_diagnosis` 는 읽기(결정론) → 조립(결정론) → 문장 1회라
  *다시 정할* 것이 없다. 공고 요건과 대조해 약점을 짚는 건 **판정이고 `fit_analysis` 소관**이다.
  여기 없는 건 루프가 아니라 표현 분리였다. 판단 기준을 **"루프를 벌었는가"** 표로 남겼다(9개 에이전트 판정).
- **에이전트 간 통신을 좁게 열었다**(`agent_loop.delegate_tool`): 읽기 전용(상대의 `sessionUpdates`
  미적용 — 상태 전이는 오케스트레이터 독점) / 화이트리스트에 선언한 상대만 / `heavy` 금지(동의 게이트
  우회 방지) / 전제 미충족이면 실행 안 함 / 중첩 금지 / **상대의 경고를 그대로 올림.**
  좁게 연 것이 설계의 핵심이다.

### ⑧ 증명하지 못한 것은 그대로 남겼다

평가 문서 등급을 C → **B 까지만** 올렸다. 관찰이 실행을 바꾼 사례 **0건**(관측된 결정은 전부
continue/finish), 에이전트 간 통신 없음, 시퀀스 병렬 없음 — 이후 뒤 두 개는 구현됐다.
그래서 새 우선순위 1번은 기능 추가가 아니라 **"관찰이 값을 하는지 계측"** 이다 —
값을 못 하면 걷어내는 것도 선택지로 적었다.

> 자기 시스템 평가에서 **증명하지 못한 항목을 증명된 것과 섞지 않는 것**이 다음 작업의 우선순위를
> 정확하게 만든다.

## 2026-07-31 — 실 RAG 연결 첫날: "실패"의 원인은 서버가 아니라 타임아웃이었다 (D95·D96)

### 증상

실 RAG(HttpRagAdapter) 연결 직후 첫 적합도 판정에서 대안 공고가 키워드 폴백으로 나갔다
(D90 문구 "실시간 검색 서버(RAG)가 연결되지 않아…" + 직무와 무관한 SM/SI 공고).
사용자가 "다시 시도"하자 정상 의미 검색으로 성공 — 재현되지 않는 실패였다.

### 진단 — 로그 대조로 확정하는 법

세 로그를 시간축으로 겹쳤다:
1. **대화 로그(DB)**: 16:39 답변에 폴백 문구, 16:40 재시도 답변에는 없음.
2. **RAG 서버 로그**: 연결 거부·오류 0건. `/search` 성공 200 이 **정확히 5건** —
   배포 검증 3건 + 재시도 1건 + **설명되지 않는 1건**.
3. **어댑터 코드**: 타임아웃 30초, 초과 시 URLError → 폴백.

설명되지 않는 200 1건이 답이다: **16:38 의 첫 호출은 서버에 도달해 결국 성공했지만,
클라이언트가 30초에 먼저 포기했다.** 서버 다운이 아니라 콜드 지연이다. 서버 실측
"warm 2.2초"는 짧은 쿼리 기준 — 격차 정보가 실린 장문 쿼리의 첫 리랭킹(모델 lazy 초기화
+ WSL 안 PostgreSQL 의 디스크→페이지 캐시)은 30초를 넘겼고, 재시도는 그 비용이 이미
지불된 상태라 빨랐다.

### 처방 (같은 날 적용)

- **D95**: 어댑터 타임아웃 30→90초. 10초 초과 검색은 지연·쿼리 길이를 WARNING 계측 —
  층별 기여도(모델 vs DB I/O)는 서버 내부 타이밍이 없어 추정이므로, 데이터를 쌓아
  RAG 팀 최적화 근거로 넘긴다.
- **D96(사용자 제안)**: 공고 파싱·이력서 정리 시점에 그 자산 기반 쿼리를 백그라운드로
  1회 쏘고 결과는 버리는 **선제 예열**. 예열이 데우는 곳은 전부 RAG 쪽 인프라(서버
  프로세스의 모델 상태, PostgreSQL shared_buffers, WSL OS 페이지 캐시)이고 우리 쪽엔
  아무것도 저장되지 않는다 — 독립 서비스라서 HTTP 요청이 곧 예열 방법이다.
  모델 서빙의 warmup·pg_prewarm·예측적 프리페치와 같은 계열의 정석이며, 예측 신호가
  사용자 자산이라 적중률이 사실상 100%다.

### 교훈

1. **간헐 실패는 "몇 번째 호출인가"부터 본다** — 콜드/웜 구분 없이 타임아웃을 정하면
   첫 사용자만 겪는 유령 장애가 된다.
2. **성공 카운트가 안 맞으면 그 차이가 원인이다** — 서버 로그의 200 개수와 클라이언트의
   성공 인식 개수가 다르면, 그 사이에 타임아웃이 있다.
3. **폴백 명시(D90)가 진단을 가능하게 했다** — 문구가 없었으면 사용자는 "결과가 이상하다"
   고만 느꼈고, 우리는 재현 안 되는 품질 불만을 쫓았을 것이다. 폴백은 이유를 삼키지
   않는다는 규약(§2-6)의 실증.

## 2026-08-01 RAG 서버가 아예 뜨지 않는다 — **에러 메시지 세 개가 모두 원인이 아니었다**

**증상**: `webapp.tool_server` 기동이 startup 단계에서 죽는다. 시도마다 다른 예외가 났다.

| 시도 | 예외 | 그때 세운 가설 |
|---|---|---|
| 1 | `psycopg.OperationalError: ... connection abort (10053)` + `SSL SYSCALL error` | WSL2 릴레이 위의 **SSL** 이 장시간 쿼리에서 끊긴다 |
| 2 | `psycopg.errors.ConnectionTimeout` | **릴레이가 유휴에 죽는다** (WSL IP 직접 접속으로 우회하자) |
| 3 | `psycopg.errors.AdminShutdown: terminating connection due to administrator command` | ← **여기서 진짜 원인이 보였다** |

**진짜 원인 둘**:

1. **WSL VM 이 유휴 60초(기본 `vmIdleTimeout`)로 자동 종료된다.** RAG 서버는 기동 시 임베딩·
   리랭커 모델을 로딩하는데 그 사이 DB 를 건드리지 않는다 → WSL 이 내려가고 → 열어 둔 커넥션이
   `AdminShutdown` 으로 끊긴다. 다음 시도에서는 WSL 자체가 없어 `ConnectionTimeout` 이 된다.
   1·2번 시도의 증상이 전부 이것의 다른 얼굴이었다.
2. **커넥션을 모델 로딩 *전에* 열고 로딩 후에 썼다**(`tool_server._warmup`). 몇 분짜리 유휴
   커넥션은 WSL 이 살아 있어도 릴레이가 끊는다(10053). **환경 문제가 아니라 코드 문제다** —
   어느 환경에서도 몇 분짜리 유휴 커넥션을 들고 있는 것은 결함이다.

**한 것**:

- `tool_server._warmup` 에서 `_ensure_conn()` 호출을 **모델 로딩 뒤로** 옮겼다(1줄).
  그 함수는 이미 죽은 커넥션 재연결 로직을 갖고 있었다 — 위치만 틀렸다.
- `%USERPROFILE%\.wslconfig` 에 `[wsl2] vmIdleTimeout=2000000000`.
  **`-1` 은 이 WSL 버전에서 먹지 않았다**(실측: 여전히 Stopped 로 내려갔다) — 밀리초 정수로 준다.
- 그래도 확실히 붙잡으려면 **앵커 프로세스**를 띄운다: `wsl.exe -u root -e sleep 100000` 을
  백그라운드로. WSL 에 붙은 프로세스가 있으면 내려가지 않는다. 세션마다 필요하다.

**결과**: warmup 25.5초, `{"status":"ok","warm":true}`, AI 의 추천 턴에서 `POST /search 200 OK`
— 폴백 문구("실시간 검색 서버가 연결되지 않아…")가 사라지고 실공고 5건이 URL 과 함께 나왔다.

**안 한 것 / 되돌린 것**:

- `sslmode=disable` + keepalives 를 DSN 에 넣었다 — SSL 은 원인이 아니었지만 로컬 루프백
  릴레이에서 해가 없고 유휴 보호가 되므로 남겼다.
- WSL postgres 를 `listen_addresses='*'` 로 넓히고 WSL IP 직접 접속을 시험했다 — **되긴 하지만
  DSN 에 IP 를 박아야 하고 WSL 재부팅마다 바뀐다.** WSL 이 상주하면 릴레이가 안 죽으니
  DSN 은 `127.0.0.1` 로 되돌렸다. 넓힌 바인딩은 폴백 경로로 남겨 뒀다(`pg_hba` 에
  `172.16.0.0/12` 한 줄).

**교훈**:

1. **예외 종류가 바뀌면 원인이 바뀐 게 아니라 관측 시점이 바뀐 것일 수 있다.** 같은 원인
   (WSL 종료)이 타이밍에 따라 `10053`·`ConnectionTimeout`·`AdminShutdown` 셋으로 나왔다.
   `AdminShutdown` 이 유일하게 원인을 직접 말해 주는 메시지였다.
2. **환경을 의심하기 전에 코드의 자원 수명을 본다.** 릴레이·SSL·IP 를 세 번 만졌는데 실제
   결함은 "커넥션을 몇 분 들고 있다" 한 줄이었다. 환경 우회는 그 결함을 가려 줄 뿐이다.
3. **`wsl.exe` 를 실행하는 것만으로 WSL 이 켜진다** — 그래서 진단용 `pg_isready` 가 매번
   증상을 지웠다. "확인했더니 되던데"가 반복되면 확인 행위가 상태를 바꾸는지 본다.
