# 2. build_user_profile — 프로필 빌더

## 흐름

1. **`extract_text`** — docx 텍스트 추출
   - 사용자가 docx 파일로 이력서를 입력하면 `extract_text` 툴 사용
   - 내부적으로 `.docx` 파일은 서드파티 라이브러리 `python-docx`(`pyproject.toml`에 `python-docx>=1.1`로 명시)를 씁니다.
   - `extract_text()`는 `sourceType`(text/file/url)을 보고 분기하는 공용 진입점이고, `sourceType: "file"`이면서 확장자가 `.docx`면 `_extract_docx()` 함수로 위임하는 구조입니다. LLM 호출 없는 순수 라이브러리 파싱입니다.

2. **`run_structured`** — LLM 항목 추출
   - 경력·프로젝트 등 이력서에서 추출해야 하는 필수 항목들을 추출합니다(LLM 사용).
   - 룰 기반으로 할 경우 파싱된 텍스트에서 추출 시 정확도가 떨어집니다.
   - 업계 전반의 전통 이력서 파서 벤더들(Affinda/RChilli/Textkernel 등)도 2023년 이후 LLM 구조화 출력 방식으로 이동했습니다 — 특정 대기업의 정확한 내부 구현까지 검증된 건 아니고 업계 방향성 차원입니다.

3. **`skill_taxonomy`** — 기술명 표준화
   - "이 사람이 이 스킬을 갖췄나"는 절대 판정하지 않습니다(그건 `gap_matcher`의 일). 표기가 제각각인 기술명을 하나의 표준형으로 모으고, 그 표준형들 사이의 포함 관계를 알려주는 사전 역할만 합니다(원문 직접 스캔 포함).
   - **표준화(normalize)**: 공고와 이력서는 같은 기술을 다르게 적습니다 — "ReactJS"/"React.js"/"리액트"가 전부 같은 기술인데 문자열이 다르면 `gap_matcher`의 정확 매칭이 다 빗나갑니다. `_SKILLS` 시드 데이터(70여 개 IT 스킬)에 `key`(내부 표준키)/`canonical`(표시명)/`aliases`(별칭들)를 등록해두고, 어떤 표기가 들어와도 `canonical`로 통일합니다.
   - **`implies`(함의 관계, `aliases`와 다른 개념)**: `aliases`는 같은 것의 다른 표기(ReactJS==React)입니다. `implies`는 다른 것인데 논리적으로 수반되는 관계입니다 — 예: MySQL → (RDBMS, SQL). "MySQL 인덱스 튜닝" 경험이 있으면 "RDBMS 설계"나 "SQL 활용"을 따로 증명하지 않아도 됩니다. 엄격히 수반되는 것만 등록합니다(예: Spring Boot → Java는 넣지 않음 — Spring Boot는 Kotlin으로도 쓰기 때문). `gap_matcher`가 서술형 요구사항을 이미 보유한 구체 기술 경험으로 충족 처리할 수 있게 해주는 핵심 확장입니다.

4. **`evidenceMap`** — 근거 문장 저장소
   - "이력서에서 나온 여러 주장(스킬 보유, 경험 등)이 진짜인지 나중에 검증할 수 있도록, 그 주장을 뒷받침하는 원문 문장 자체를 따로 목록화해서 인용 가능하게 만들어 둔 것"입니다.
   - **환각 원문 대조(`_filter_grounded_evidence`, 신규)**: LLM이 낸 `evidenceMap.text`가 실제로 원문(`resume_text`)에 있는 문장인지 공백 정규화 후 부분 문자열로 대조합니다. 없으면 환각으로 보고 제거하고 `hallucinated_evidence` 경고를 남깁니다. 완전 문자열 대조이지 퍼지 매칭이 아닙니다(프롬프트가 "그대로 인용"을 요구하므로 표기 차이까지 봐줄 이유가 없음). `verify_result.check_evidence_grounding`이 `matchedEvidenceIds` 참조 무결성(그 id가 `evidenceMap`에 실재하는가)을 검증하는 것과 같은 원리로, 이건 그보다 한 단계 앞선 "문장 자체가 원문에 실재하는가"를 막습니다.
   - **각 항목 id 룰 재부여(`_reassign_ids`)**: `education`/`experiences`/`projects`/`bootcamp`/`awards`/`certifications`/`languages`의 `id`, `evidenceMap`의 `evidenceId`를 LLM이 뭘 냈든 무시하고 등장 순서대로 `edu-1`/`exp-1`/`prj-1`/`boot-1`/`award-1`/`cert-1`/`lang-1`/`ev-1`... 재할당합니다. LLM이 중복 id를 내면 근거 인용이 서로 엉키기 때문입니다.

## 스키마 / 설계 결정

5. **프로필 스키마 타입 강제 (pydantic 하위 모델화)**
   - `education`/`experiences`/`projects`/`skills`/`certifications`/`languages`/`bootcamp`/`awards` 전부 자유 dict에서 pydantic 모델(`EducationEntry`/`ExperienceEntry`/`ProjectEntry`/`SkillEntry`/`BootcampEntry`/`AwardEntry`/`CertificationEntry`/`LanguageEntry`)로 타입을 강제했습니다. LLM이 필드명을 임의로 바꿔 낼 수 없게 구조적으로 막습니다.
   - **`experiences` vs `projects` 경계 확정**: `experiences`는 정규직/계약직/인턴/파견 등 고용관계가 있었던 재직 이력만 담습니다. 학교 수업/동아리/부트캠프/개인·팀 프로젝트는 고용관계가 아니므로 전부 `projects`로 넣습니다. 실제 페르소나 테스트(`tests/docs/결과.txt`)에서 같은 프로젝트가 `experiences`와 `projects` 양쪽에 중복 서술되는 문제가 발견돼 이렇게 경계를 나눴습니다.

6. **`portfolioLinks` 필드 제거** — 사용자 요청으로 받지 않기로 결정했습니다.

7. **`check_profile_completeness` (신규 노드)** — `build_user_profile` 직후, `check_sufficiency` 이전
   - docx에서 못 뽑은 enum 필드(`education.degree`/`status`, `experiences.employmentType`, `projects.projectType`)가 비어있으면 사용자에게 선택형(드롭다운) 질문을 생성합니다.
   - `school`/`company`/`summary` 같은 자유서술 필드나 `skills.level`은 대상에서 제외합니다(스킬 level은 룰 추출 스킬에서 의도적으로 비워두는 설계라, 결측 취급하면 매번 질문이 쏟아짐).
   - 엔트리 자체가 0건(예: 부트캠프 이력 없음)이면 묻지 않습니다 — "없다"와 "있는데 못 뽑았다"는 다르기 때문입니다.
   - **비블로킹 설계**: 이 결측 질문 때문에 전체 분석 파이프라인(`analyze_gap`/`roadmap`)을 멈추지 않습니다. `degree`/`employmentType` 등은 `gap_matcher`가 실제로 참조하는 값이 아니라서, 이것 때문에 분석을 막을 이유가 없습니다. `followUpQuestions`(블로킹, `check_sufficiency` 담당)와 분리된 `profileCompletionQuestions` 필드에 실려 최종 응답에만 곁들여집니다.

8. **`embed` 툴은 `build_user_profile`에서 사용하지 않음 (폐기 결정)**
   - 원래 설계엔 "embed로 유사 스킬 병합"이 있었으나 구현하지 않기로 했습니다.
   - `embed`는 지금 `gap_matcher`의 2차 유사도 매칭(서술형 요구사항 판정) 한 곳에서만 쓰입니다 — 현재 `NullEmbedder`라 미연결 상태입니다(`similarity()`가 `0.0`이 아닌 `None`을 반환 — "모른다"와 "안 닮았다"를 구분해 틀린 판정을 막는 설계).
