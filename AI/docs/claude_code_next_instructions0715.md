# Claude Code 작업 지시 참고사항

## 문서 목적
이 문서는 자비스 AI 에이전트 프로젝트의 다음 작업을 Claude Code에게 지시할 때 반드시 참고해야 할 구현 현황, 아키텍처 원칙, 작업 방식, 협업 분업 구조, 우선순위를 정리한 핸드오프 문서다.

## 팀 작업 구조
현재 이 프로젝트는 역할이 분리되어 병렬 진행 중이다.

- **RAG 담당 팀원**이 따로 있으며, RAG 스택은 앞으로도 상당히 고도화될 가능성이 크다.
- **나와 다른 팀원은 멀티에이전트 오케스트레이션에 중점**을 두고 작업 중이다.
- 따라서 현재 Claude Code에게 지시해야 할 핵심 범위는 RAG 자체를 새로 깊게 설계하는 것이 아니라, **향후 고도화된 RAG 스택이 자연스럽게 꽂힐 수 있는 멀티에이전트 오케스트라 구조를 견고하게 만드는 것**이다.

## 현재 구현 상태 요약
- 현재 코드는 **멀티에이전트 완성본**이 아니라, 전체 파이프라인이 돌아가기 위한 **스켈레톤과 공통 인프라**가 먼저 구현된 상태다.
- 설계 문서 기준으로는 LangGraph 오케스트레이터 + 역할별 LangChain 워커 에이전트 구조를 지향한다.
- 하지만 현재 src 범위에서는 실제 멀티에이전트 노드 구현보다, 다음과 같은 공통 계층이 먼저 구현되어 있다.
  - 환경 설정 로더 (`config.py`)
  - LLM 팩토리 (`llm.py`)
  - structured output 헬퍼 (`structured.py`)
  - 텍스트 추출 어댑터 (`extract.py`)
  - 요청/그래프 실행 진입점 (`service.py`)
  - 데모 실행기 (`run_demo.py`)
- 패키지 설명과 데모 코드 기준으로도 현재 단계는 “전체가 도는 뼈대”, “mock 데이터를 반환하는 스켈레톤” 성격이 강하다.

## 구현 평가 기준 정리
- 설계 완성도는 높다. 역할 분리, GraphState, 검증기, 재시도, 상태 흐름 설계는 상당히 잘 되어 있다.
- 반면 실제 코드 구현은 초기 단계다.
- 따라서 현재 상태를 과대평가하면 안 된다.
- 지금 코드는 “멀티에이전트 제품”이라기보다 **멀티에이전트 제품을 만들기 위한 기반 모듈이 깔린 상태**로 봐야 한다.
- 특히 LangGraph 핵심 노드, 상태 분기, retry 루프, verifier 재실행, 실제 워커 체인 연결은 아직 본격 구현 전 단계로 인식해야 한다.

## 이미 잘 깔려 있는 기반
다음 부분은 새 작업 시 최대한 재사용하고, 구조를 유지하는 방향으로 확장해야 한다.

### 1. 설정 계층
- `.env` / 환경변수 기반 설정 외부화 구조는 유지한다.
- 비밀값, 모델명, provider, temperature, model_version 같은 값은 코드에 하드코딩하지 않는다.
- 실행 환경 차이를 흡수하는 진입점으로 `config.py`를 계속 중심에 둔다.

### 2. LLM 추상화 계층
- 노드 내부에서는 provider별 구현 세부사항을 직접 다루지 않는다.
- `get_llm()` 추상화를 통해 모델을 주입받는 구조를 유지한다.
- 향후 Anthropic 외 provider 교체 가능성을 열어두는 방향으로 작업한다.

### 3. Structured Output 계층
- Pydantic 스키마 기반 structured output 호출 방식은 유지한다.
- 노드에서 provider별 structured output 차이를 직접 처리하지 않도록 한다.
- 실패 시 예외로 그래프를 죽이기보다 warning으로 흡수하고 상위에서 fallback할 수 있게 유지한다.

### 4. 입력 추출 계층
- `extract.py`는 단순 유틸이 아니라 공통 입력 어댑터다.
- text / file / url 입력을 한 인터페이스로 다루는 현재 구조를 유지한다.
- 실패 시 warning을 남기고 상위 노드에서 계속 진행하거나 폴백하도록 하는 철학을 깨지 않는다.

### 5. 서비스 진입점
- `service.py`의 역할은 AnalyzeRequest → GraphState → graph invoke → AnalyzeResponse 흐름이다.
- 이 진입점은 향후 FastAPI 백엔드와 연결될 핵심 인터페이스이므로, 변경하더라도 계약 형태를 최대한 안정적으로 유지한다.

## 작업 방식에 대한 가장 중요한 제약
현재 이 프로젝트는 **AI 백엔드 작업, 멀티에이전트 오케스트레이션 작업, RAG 작업이 병렬로 진행 중**이다.

즉, Claude Code는 단독으로 모든 것을 갈아엎는 방식으로 작업하면 안 된다.
다음 원칙을 반드시 지켜야 한다.

- 최종 목표는 **내가 마지막으로 작업 완료한 폴더를 기준으로**, 이후 백엔드 구현분과 RAG 구현분을 **그대로 조립해서 하나의 완성품으로 합치는 방식**이다.
- 따라서 현재 작업은 “전체 리포를 새로 재설계”하는 방식이 아니라, **조립 가능한 부품 단위로 안전하게 확장**해야 한다.
- 다른 병렬 작업 브랜치와 합쳐질 것을 전제로, 파일 구조/인터페이스/계약을 최대한 보존해야 한다.
- 임의의 대규모 리팩터링, 폴더 이동, 네이밍 전면 변경, 계약 스키마 파괴는 피해야 한다.
- 새 기능을 넣더라도, 나중에 백엔드 파트와 RAG 파트를 충돌 없이 합칠 수 있어야 한다.

## RAG 관련 작업 원칙
RAG는 별도 담당 팀원이 고도화하고 있으므로, Claude Code는 다음 원칙을 따른다.

### 1. RAG를 직접 완성하려 하지 말 것
- 현재 작업의 주역은 오케스트레이션이다.
- RAG 품질이나 검색 전략 자체를 이 브랜치에서 과도하게 설계·구현하려 하지 않는다.
- RAG 로직을 오케스트레이터 코드 내부에 강하게 박아 넣지 않는다.

### 2. RAG가 꽂힐 자리만 명확히 만들 것
- Gap Analyzer, Alternative Path Finder, company context fetch, insight fetch 같은 지점에서 **RAG adapter / interface / hook point**를 명확하게 만들어 둔다.
- 지금은 mock / placeholder / protocol 수준이어도 괜찮지만, 나중에 실제 고도화된 RAG 스택이 무리 없이 들어올 수 있어야 한다.

### 3. 오케스트레이터가 RAG를 호출하는 구조로 유지할 것
- 오케스트레이터와 워커 노드는 “언제 RAG가 필요한지 판단”하고, 실제 검색 엔진 구현은 외부 모듈/어댑터가 담당하게 한다.
- 즉, 오케스트레이션 계층은 제어와 상태 관리에 집중하고, RAG 내부 구현 세부사항과 결합하지 않는다.

### 4. RAG 실패도 시스템 전체 실패로 만들지 말 것
- 향후 RAG 연결 시 검색 실패, 빈 결과, timeout, low confidence가 발생할 수 있다.
- 이런 경우에도 warning/fallback/skip 가능한 구조로 설계한다.
- RAG가 없더라도 최소 분석 결과는 나오게 설계하는 것이 좋다.

## 병렬 작업 상황을 고려한 구현 원칙

### 1. 조립 우선
- 작업 결과는 “완결성”보다 “조립 가능성”이 우선이다.
- 각 모듈은 독립적으로 붙일 수 있어야 한다.
- 아직 연결되지 않은 부분은 mock / TODO / adapter interface 형태로 남겨도 되지만, 계약은 분명해야 한다.

### 2. 인터페이스 안정성 유지
- `AnalyzeRequest`, `AnalyzeResponse`, `GraphState`, 각 노드 입출력 스키마는 함부로 깨지 않는다.
- 필드 추가는 가능하더라도 기존 필드 의미를 바꾸지 않는다.
- 병합 시 충돌을 줄이기 위해 함수 시그니처와 데이터 계약을 안정적으로 유지한다.

### 3. 레이어 분리 유지
- 설정 / LLM / structured output / extractor / graph / service 레이어를 섞지 않는다.
- 한 파일에서 여러 계층의 책임을 동시에 처리하지 않는다.
- 나중에 RAG 파트가 들어왔을 때 꽂을 위치가 명확하도록 유지한다.

### 4. 예외보다 warning 중심
- 현재 구조의 장점은 실패를 warning으로 흡수하고 그래프 전체가 죽지 않게 만드는 점이다.
- 이 철학을 계속 유지한다.
- 외부 API, RAG 검색, 문서 추출, 파싱 실패는 가능한 한 상위에서 재시도/폴백 가능한 형태로 반환한다.

### 5. 작은 단위 구현
- 한 번에 전체 멀티에이전트를 완성하려 하지 않는다.
- 실제 동작 가능한 최소 노드부터 붙여 나간다.
- 특히 Job Posting Parser → 최소 Graph → 나머지 mock 대체 순으로 점진 확장한다.

## 다음 작업 우선순위

### 1순위: Job Posting Parser 실구현 고도화
가장 먼저 해야 할 일은 Job Posting Parser를 설계 문서 수준에 가깝게 실제 동작하도록 만드는 것이다.

목표 흐름:
1. input normalize
2. source type 분기 (`url | text | file`)
3. text extract
4. requirement parse with structured output
5. schema normalize
6. output validate
7. normalizedJobPosting 반환

구현 지침:
- 기존 `extract.py`, `structured.py`를 적극 재사용한다.
- parser 노드 내부에서 모든 걸 직접 구현하지 말고, 현재 깔린 어댑터 구조 위에서 조립한다.
- warnings를 누적해서 GraphState 또는 노드 결과에 반영한다.
- 추후 RAG/DB 연결 가능성을 고려해 normalization 단계는 분리해 둔다.

### 2순위: 최소 LangGraph 작동본 완성
다음 단계는 전체 멀티에이전트를 완성하는 것이 아니라, 최소 동작 그래프를 만드는 것이다.

권장 최소 흐름:
- parsejobposting (실제 구현)
- builduserprofile (임시 mock 가능)
- analyzegap (임시 mock 가능, 단 RAG hook point 고려)
- planroadmap (임시 mock 가능)
- assembleoutput

구현 지침:
- 우선 interrupt, retry loop, verifier full cycle까지 욕심내지 않는다.
- 최소 실행 가능 그래프를 먼저 안정화한다.
- 그래프 컴파일 및 invoke 경로를 `service.py`에서 그대로 사용할 수 있어야 한다.
- analyzegap 단계에는 나중에 RAG 모듈을 쉽게 주입할 수 있는 인터페이스를 남긴다.

### 3순위: GraphState / warnings / toolLog 정리
- 현재 공통 모듈들이 warning을 잘 흡수하고 있으므로, 이를 상태에 제대로 축적하는 흐름을 만든다.
- toolLog, warnings, sources가 각 노드에서 일관되게 append되도록 만든다.
- 이후 verifier, observability, UI 상태 출력, RAG 추적성으로 확장할 수 있게 한다.

### 4순위: mock → real 교체가 쉬운 구조 만들기
- User Profile Builder, Gap Analyzer, Roadmap Planner는 아직 mock 기반이어도 괜찮다.
- 대신 나중에 실제 체인으로 교체하기 쉬운 함수/노드 경계를 만들어 둔다.
- “지금은 mock이지만 나중에 내부만 바꾸면 된다” 수준의 안정된 추상화를 목표로 한다.
- 특히 Gap Analyzer는 이후 RAG 결합 지점이 많으므로 adapter 경계를 더 신경 써야 한다.

## Claude Code가 집중해야 할 핵심 범위
Claude Code는 아래 범위에 집중하는 것이 가장 적절하다.

- LangGraph 기반 오케스트레이터 흐름 정리
- 노드 간 상태 전달 구조 안정화
- warnings / sources / toolLog / retryCount 등 상태 축적 구조 정리
- 실제 구현된 parser 노드와 mock 노드의 공존 구조 설계
- 향후 고도화된 RAG 스택이 들어올 연결 포인트 확보

반대로 아래는 과도하게 깊게 들어가지 않는 것이 좋다.

- RAG 검색 품질 튜닝 자체
- 벡터 스토어 세부 설계 전면 주도
- 검색 파이프라인 내부 알고리즘 전면 구현
- 병렬 작업 중인 타 팀원의 전담 영역 침범

## 하지 말아야 할 것
- 병렬 작업 중인 백엔드/RAG 구조를 무시한 대규모 전면 리팩터링
- 폴더 구조를 전체적으로 뒤엎는 변경
- 공통 계약(Pydantic 모델, GraphState 키, service 인터페이스) 파괴
- provider 종속 코드를 여러 노드에 중복 삽입하는 방식
- extractor / structured output / graph 책임을 한 파일에 뭉개 넣는 방식
- RAG 로직을 오케스트레이터 내부에 강결합시키는 방식
- “한 번에 완성품 만들기” 식의 과도한 범위 확장

## Claude Code에게 원하는 작업 스타일
- 기존 설계를 존중하되, **지금 당장 붙일 수 있는 최소 구현**부터 완성한다.
- 이미 구현된 기반 모듈을 최대한 활용하고, 새 코드도 같은 철학으로 작성한다.
- 결과물은 나중에 백엔드 파트 및 RAG 파트와 쉽게 병합 가능해야 한다.
- 코드 추가 시 “이 부분은 이후 병렬 작업 브랜치와 어떻게 합쳐질지”를 항상 먼저 고려한다.
- 새 기능보다 **조립성, 안정성, 인터페이스 보존**을 우선한다.
- 오케스트레이션 중심 작업과 RAG 전담 작업의 경계를 명확히 인식한다.

## 권장 산출물 형태
다음 작업에서는 아래 결과물이 나오면 가장 좋다.

- Job Posting Parser 실제 노드 구현
- 최소 LangGraph builder / state 연결본
- warnings / toolLog 누적 흐름 반영
- mock 노드와 real 노드를 교체 가능한 구조 정리
- Gap Analyzer 등에서 RAG adapter/hook point 정의
- 기존 service 진입점과 호환되는 실행 가능 상태

## 최종 메모
이 프로젝트는 현재 “설계는 고도화되어 있고, 구현은 기반 모듈 중심으로 시작된 상태”다.
따라서 다음 작업의 핵심은 새로운 구조를 발명하는 것이 아니라, **이미 설계된 구조 위에 조립 가능한 실제 노드를 하나씩 붙여서 완성품 방향으로 전진시키는 것**이다.

특히 RAG는 전담 팀원이 별도로 고도화하고 있고, 현재 본 작업의 중심은 멀티에이전트 오케스트레이션이므로, 지금 만드는 코드는 RAG를 직접 대체하는 구조가 아니라 **고도화된 RAG가 나중에 자연스럽게 꽂히는 오케스트라 골격**이어야 한다.

작업 중 항상 “내가 마지막으로 완료한 폴더를 기준으로, 이후 다른 백엔드 구현분 및 RAG 구현분과 그대로 조립될 수 있는가?”를 체크 기준으로 삼아야 한다.
