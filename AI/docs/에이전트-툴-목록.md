# 에이전트·툴 목록 (코드 기준)

출처는 `src/jobis_ai/agents/__init__.py` 의 레지스트리(capability manifest)다.
`python -m jobis_ai.explain` 이 같은 표를 코드에서 뽑아 준다 — 숫자가 어긋나면 코드가 맞다.

**총계: 등록 항목 11개 = 에이전트 7 + 도구 4.** 그 위에 오케스트레이터 계층이 하나 있다.

구분 기준은 하나다 — **말을 하는가.**
에이전트는 LLM 으로 사용자향 문장을 만들고(금지표현 검증 통과 필수), 도구는 값만 내고
문장은 `tool_render.py` 가 만든다.

### 자기 루프 에이전트가 쓰는 툴

루프 툴의 공통점은 **판단하지 않는다**는 것이다 — 사실을 가져오거나(read·search·ask),
기록하거나(save·record), 검사한다(check). 근거는 툴만 만들고, LLM 은 고르고 말만 한다.
툴 이름은 `Literal` 로 제한돼 있어 없는 툴을 부를 수 없다(→ [§1-1](#1-1-툴이-llm-없는-순수-함수인-것은-아니다)).

한눈에 — **⚡** 는 프로세스 밖을 부르는 툴(→ [§1-1](#1-1-툴이-llm-없는-순수-함수인-것은-아니다)).

| 에이전트 | 툴 수 | 스텝 상한 | 툴 → 하는 일 |
|---|:---:|:---:|---|
| **`posting_analysis`**<br>공고 담당 | **3** | 5 | `read_posting` — 공고 원문에서 키워드 든 줄을 찾는다<br>`save_plan` — 프로젝트 제안 기록. **커버 요구사항 ID 를 못 대면 거부**<br>⚡`search_postings` — 비슷한 실공고를 RAG 로 검색(이 공고 **밖의** 사실용) |
| **`resume_diagnosis`**<br>이력서 담당 | **1**<br>(→ [왜](#1-2-툴-수가-일의-양이-아니다)) | 5 | `read_resume` — 이력서 원문에서 키워드 든 줄을 찾는다 |
| **`preference_intake`**<br>선호 수집 | **3** | 5 | `record_preference` — 선호를 라벨별로 기록 + **충분한지 룰로 판정**해 알려준다<br>⚡`preview_postings` — `job_recommend` 에 위임해 실제 공고가 있는지 미리 본다<br>`request_material` — 받을 자료(공고·이력서)를 표시한다 |

| `career_chat` | — | — | 루프 없음 — LLM 1회 호출, 실패 시 결정론 안내문 |

**합계 15개** = 순수 파이썬 함수 12 + 외부 호출 3(⚡).

한 줄로 읽는 각 루프의 성격:

```
posting_analysis   원문 읽기 → 제안 기록(근거 ID 검증) → 시장 검색
resume_diagnosis   원문 읽기
preference_intake  선호 기록(+충분성 판정) → 공고 미리보기 → 자료 요청
interview_prep     소재 고르기 → 근거 확인 → 답변 채점 → 질문 기록
coverletter_draft  근거 수집 → 초안 저장 → 자기 점검 → 다시 쓰기 (7스텝인 이유)
```

> 툴 수는 **루프 안에서 고를 수 있는 폭**이지 그 에이전트가 하는 일의 양이 아니다.
> `_common.py` 주석 — *"고를 것이 없으면 루프는 돌지 않는다. 자율성의 병목은 루프 구조가
> 아니라 도구 목록이었다."* 다만 `resume_diagnosis` 가 1개인 건 **근거가 이미 진입
> 파이프라인에서 다 만들어져 있기 때문**이다 → [§1-2](#1-2-툴-수가-일의-양이-아니다)

툴 하나하나가 실제로 무엇을 하는지 → [§1-3](#1-3-툴-하나하나가-실제로-하는-일)

### 1-1. 툴이 "LLM 없는 순수 함수"인 것은 아니다

15개 중 12개는 세션 데이터만 읽고 쓰는 순수 파이썬 함수다. 나머지 3개(⚡)는 프로세스 밖을 부른다:

| 툴 | 무엇을 부르나 | 그래서 |
|---|---|---|
| `search_postings` | RAG 서버 HTTP (`get_rag_adapter().search`) | 같은 입력이 같은 출력을 보장하지 않는다. 실패하면 키워드 폴백 — 폴백으로 찾은 결과인지를 `rag_http_failed`·`rag_not_connected` 경고로 올린다(D90) |
| `preview_postings` | `job_recommend` (→ 같은 RAG) | 위임 대상이 도구라 LLM 은 안 타지만 RAG 는 탄다 |
| `ask_agent` | `resume_diagnosis` 의 **자기 루프 전체** | 상대 에이전트의 LLM 호출이 통째로 일어난다 |

그러니 공통점은 "LLM 없음"이 아니라 **판단이 없음**이다. 위임 툴은 가드로 갇혀 있다
([`call_agent_readonly`](../src/jobis_ai/agents/agent_loop.py)): 선언 화이트리스트 → 중첩 금지(깊이 1)
→ 등록 여부 → `heavy` 금지(동의 게이트 우회 차단) → 전제 자산. 통과해도 **세션 사본**으로
실행하고 스테이징을 비운다 — 상태 전이는 오케스트레이터 독점(§2-4). 거부도 `delegate_refused`
로 trace 에 남는다(성공만 남기면 hand-off 성공률의 분모가 사라진다).

### 1-2. 툴 수가 일의 양이 아니다

위 표는 **루프 안에서 고를 수 있는 것**만 센다. 에이전트가 하는 일의 상당 부분은 루프가
시작되기 **전에** 결정론으로 끝나 있다. `resume_diagnosis` 가 툴 1개인 것도 할 일이 적어서가
아니라 **근거가 이미 다 만들어져 있어서**다:

| 단계 | 무엇을 하나 | 어디 | 계층 |
|---|---|---|---|
| 1. 이력서 지목 | `targets` 1개 = 활성 전환 / 2개 이상 = 비교 | `switch_active_resume` | 룰 |
| 2. **추출** | 이력서 원문 → 정규화 프로필 (항목 추출) | `ensure_profile` → `build_user_profile` | **LLM (읽기)** |
| 2-b. 증거 매핑 | "이 경험이 이 스킬을 증명한다" | `skill_taxonomy` + `skillEvidence` | 룰 |
| 3. **항목화** | 섹션별 개수 / 근거 있는 스킬 vs 기재만 된 스킬 / 빈 섹션 / 보완 질문 | `_parse` | 룰 |
| 4. **대화** | 그 사실만으로 "내 강점이 뭐야"·"이 프로젝트를 어떻게 써야 해" 에 답한다 | 자기 루프 | **LLM (말하기)** |
| 5. 폴백 | 루프가 검증 통과 문장을 못 만들면 승격 전과 똑같이 답한다 | `render_resume_diagnosis` | 룰 + LLM |

루프가 원문을 다시 뒤질 일은 "정리된 항목에 없는 서술"뿐이라 `read_resume` 하나면 된다.
파일 docstring 의 규율 그대로 — **자율성은 표현에, 근거는 도구에.**

`posting_analysis` 도 같은 모양이다(진입에서 `ensure_posting_text` → 파싱 → `facts.requirements`).
차이는 그쪽이 **공고 밖의 사실**을 물어볼 수 있어야 해서 `search_postings` 가 붙은 것.

> 부수 효과 하나: 이력서 항목화가 끝나면 스킬 상위 6개로 **RAG 캐시를 예열**한다(D96).
> 추천·대안 검색의 첫 쿼리 지연을 지금 백그라운드로 지불하고 결과는 버린다.

### 1-3. 툴 하나하나가 실제로 하는 일

#### `posting_analysis` — 공고 담당 (툴 3개)

- **`read_posting`** — 공고 원문에서 키워드가 든 줄을 grep 한다. 인자는 쉼표 구분 낱말, 비우면 앞부분. 파싱 요약에 안 잡힌 항목(전형·복리후생)을 확인하는 용도.
- **`save_plan`** — 프로젝트 제안 기록. **커버하는 요구사항 ID(`req-1`·`pref-3`)를 못 대면 거부한다.** 공고에 없는 ID 도 거부하고 무엇이 틀렸는지 관찰로 돌려준다. 외부 리뷰(2026-08-01)가 "제안이 아무 공고에나 나올 답"이라고 지적했을 때, 프롬프트로 근거를 강제하는 대신 **도구가 검증하게** 만든 자리다(§2-2). 예상 소요 기간 칸은 일부러 없다 — 데이터가 없어 지어내게 되니까.
- **⚡`search_postings`** — 비슷한 실공고를 RAG 로 검색. 이 공고 **밖의** 시장 사실이 필요할 때만(지금 공고 내용은 `read_posting` 담당). 빈 결과를 빈 관찰로 주지 않는다 — 그러면 LLM 이 그 자리를 사전지식으로 채운다(§2-5).

#### `resume_diagnosis` — 이력서 담당 (툴 1개)

- **`read_resume`** — 이력서 원문 grep. `read_posting` 과 같은 구현(`_common.py`), 대상만 다르다. 툴이 이것뿐인 이유는 [§1-2](#1-2-툴-수가-일의-양이-아니다) — 항목화가 진입에서 이미 끝나 있어, 루프가 원문을 다시 볼 일은 "정리된 항목에 없는 서술"뿐이다.

#### `preference_intake` — 선호 수집 (툴 3개)

- **`record_preference`** — 발화에서 읽은 선호를 라벨(`직군:`·`도메인:`·`회사:`·`지역:`·`기술:`·`경력:`)로 기록. 기록만 하는 게 아니라 **충분한지 판정까지 룰로 계산해 관찰로 돌려준다** ("선호 차원 3개, 충분한가: 예"). 직군 표현이 도메인·회사로 중복 분류되면 `role_taxonomy` 로 정리한다.
- **⚡`preview_postings`** — `job_recommend` 에 위임. "지금 조건으로 실제 공고가 있나"는 그쪽이 이미 계산하므로 같은 걸 두 번 구현하지 않는다.
- **`request_material`** — 받을 자료를 `공고`/`이력서` 로 표시. 실제 요청 문구·질문 카드는 코드가 만든다. 관찰에 "안내하세요" 같은 지시를 넣었더니 답변이 도구 동작을 서술해버려서("이력서를 요청드렸어요") 사실만 남겼다.

#### `interview_prep` — 면접 (툴 4개)

- **`pick_material`** — 다음에 물을 소재를 **점수로** 고른다: 사용자 프로젝트에 실제 등장 > 공고 필수 요건 > 격차 심각도 > 기재만 되고 근거 없음. 이미 다룬 주제는 제외, 동점이면 판정 엔진이 낸 순서를 지킨다(안정적 선택). 고른 이유까지 관찰에 실어 준다.
- **`find_evidence`** — 프로필의 `experiences`·`projects`·`skills` 에서 그 주제 근거를 찾는다. 없으면 **없다고 말한다** — "스킬 기재만 있고 경험 서술에는 없음"까지 구분해서.
- **`check_answer`** — 사용자 답변을 **센다**: taxonomy 로 잡히는 기술 용어 수 + 숫자 유무 + 역할 서술어(담당·구현·주도…) 유무. 신호가 임계 미만이면 "근거 부족". LLM 의 인상이 아니라 계수다.
- **`record_question`** — 이번 턴 질문을 `asked` 에 확정 기록. 다음 턴의 자기가 무엇을 물었는지 안다.

#### `coverletter_draft` — 자소서 (툴 4개, 스텝 상한 7)

- **`find_evidence`** — 초안의 **유일한** 근거 출처. 인자는 **필터가 아니라 정렬 힌트**다: 문자열로 0건이어도 전체를 함께 돌려준다. 이력서는 다른 말로 적혀 있기 때문("트러블슈팅" ↔ "장애 대응"), 어느 문장이 해당하는지 판단하는 건 substring 이 아니라 LLM 의 일이라서. 예전엔 "비우면 전부 볼 수 있다"고 안내만 했는데 그 한 스텝이 재작성 기회 하나와 맞바꿔졌다.
- **`save_draft`** — `동기:`·`강점:`·`보완:` 라벨 줄을 파싱해 기록. **적어 보낸 문단만 갱신**되고 나머지는 유지(부분 수정). 작성 횟수와 문단별 분량을 관찰로 준다.
- **`check_draft`** — 자기비판의 재료. 빈 문단 / 금지표현 / 근거 없는 스킬 언급 / 문단별 문장 수 / **공고 요건 커버리지** / 부족 역량 언급 여부를 센다. 커버리지는 기술 용어 대조라, 용어가 없는 서술형 요건은 **분모에서 뺀다** — 셀 수 없는 걸 센 척하지 않는다. 지적이 없어도 커버리지는 항상 앞에 붙인다(고쳤을 때 올라가는 걸 보라고).
- **⚡`ask_agent`** — `resume_diagnosis` 에게 물어본다. 근거가 빈약한 이유는 그쪽이 이미 세는 일이므로.

## 2. 도구 4개

말하지 않는다 — `entry` 는 데이터만 내고, 문장은 `tool_render.py` 의 짝이 만든다.

> **"말하지 않는다" ≠ "LLM 을 안 쓴다".** 계산(`entry`)과 표현(`render`)을 같은 함수에 두지
> 않는다는 뜻이고, 표현 쪽은 LLM 을 쓸 수 있다 (→ [§2-1](#21-render-도-llm-을-쓴다)).
> 아래 표의 LLM 칸은 **`entry` 기준**이다.

| 이름 | 하는 일 | 전제 자산 | 만드는 자산 | 받는 인자 | LLM (`entry`) |
|---|---|---|---|---|---|
| `fit_analysis` | 공고×이력서 적합도 판정. 판정 엔진(`build_graph`) 전체를 부르는 대화 진입 래퍼 — 판정 로직은 여기 한 줄도 없다 | resume, job_posting | analysis, roadmap | `targets`(공고 지목), `resumeTargets`(이력서 지목) | 엔진 내부 — **하이브리드**(아래) |
| `job_recommend` | 실공고 DB(RAG) 의미 검색 + 후보마다 `gap_matcher` 재매칭. 실공고가 없으면 **지어내지 않고 빈 결과** | resume **또는** preferences | recommendations | `job_name` | 없음 |
| `posting_fetch` | 공고 URL → 원문 텍스트 승격 (수집만, 파싱은 `posting_analysis` 의 일) | job_posting | — | — | 없음 |
| `roadmap_manager` | 세션에 저장된 로드맵 조회 | roadmap | — | — | 없음 |

- `fit_analysis` 는 **무거움(heavy)** — 검증기가 자동으로 끼울 때는 먼저 사용자에게 묻는다(동의 게이트).
- `posting_fetch` 는 **플래너에 안 보인다(internal)** — URL 이 미수집이면 오케스트레이터가 결정론으로 큐 맨 앞에 끼운다.
- `job_recommend` 만 전제가 "둘 중 하나"다 — 이력서면 역량 일치까지, 선호뿐이면 선호 기준으로 추천한다.

### 2-1. `render` 도 LLM 을 쓴다

표현 계층(`tool_render.py`)은 LLM 금지 구역이 아니다 — `AGENTS.md` §1 의 **말하기** 계층이라
원래 허용된다. 실제로 갈려 있는 건 이렇다:

| render | LLM | 무엇에 |
|---|---|---|
| `render_fit_analysis` | **쓴다** | 마무리 문장 + 다음 행동 제안 (`run_streaming_text` 2곳) |
| `render_job_recommend` · `render_roadmap_manager` · `render_posting_fetch` | 안 쓴다 | 순수 f-string 조립 |

**그래도 값을 못 바꾼다** — 시그니처가 막는다:

```python
render: Callable[[dict, dict], tuple[str, list[dict]]]   # (데이터, 세션) → (문장, 경고)
```

반환에 **데이터가 없다.** 표현 LLM 은 문장만 만들 수 있고 등급·점수·매칭 결과에 손댈 수 없다.
프롬프트 금지가 아니라 타입이 막는 것(`AGENTS.md` §2-2). 여기에 두 겹 더:

- 나온 문장은 금지표현·질문형 검사를 통과해야 하고, 실패하면 하드코딩 문구로 폴백한다.
- 폴백해도 `warnings` 를 함께 돌려준다 — 문장만 돌려주는 계약은 "왜 기본 문구가 나왔는지"를 지운다(§2-6).

`render` 가 세션을 **읽기 전용으로** 받는 것도 같은 이유다. 마무리 문장은 사용자가 방금 한 말에
이어져야 하는데, 그 맥락을 `data` 로 흘리면 프론트로 나가는 산출물 계약에 대화 이력이 섞인다.

### 2-2. `fit_analysis` 안의 등급 판정 — 하이브리드 (2026-08-04, `0f6736a`)

밖에서 보면 도구지만 안에서는 **LLM 이 제안하고 룰이 확정한다.** 전에는 등급이 점수식
(`overall_fit`) 하나로 나왔는데, 요구 문구가 달라 룰이 놓치는 자리(보유 스킬
Elasticsearch ↔ "검색 엔진 기반 서비스 개발 경험")를 메우려고 두 단계를 넣었다.

| 단계 | 누가 | 하는 일 | 코드 |
|---|---|---|---|
| 1. 사실 판정 | 룰 | 무엇을 갖췄나 (기존 그대로) | `gap_matcher.py` |
| 1.5. 재검증 | **LLM** | 룰이 미충족·판정불가로 본 것 중 근거로 뒤집을 수 있는 것을 찾아 **판정 기록 자체를 갱신** | `grade_judge.recheck` |
| 3. 등급 제안 | **LLM** | 검증 끝난 판정 결과만 보고 루브릭으로 상/중/하 | `grade_judge.judge` |
| 4. 등급 확정 | 룰 | LLM 제안을 하드 룰 G1~G6 의 허용 범위로 **클램프** | `grade_decision.decide_grade` |

LLM 을 판단 계층에 들인 대신 위험은 **구조로** 막는다 (`AGENTS.md` §2-2 의 적용):

- **상향 전용** — 하향은 스키마가 아예 허용하지 않는다. 룰이 met 이라 한 건 근거가 실존한다.
- **근거 인용 강제** — `evidenceIndexes` 나 `skillName` 없는 override 는 코드가 버린다. 지어낸 근거로 못 뒤집는다.
- **하드 룰 클램프** — G1(필수 미충족 2건↑ → 상 불가) · G3(필수 전부 met → 하 불가) · G5(필수 미충족 과반 → 하 확정) · G6(연차 격차 24개월↑ & 보유 < 요구의 절반 → 하 확정). LLM 이 무엇을 내든 넘을 수 없는 선이다.
- **추적** — 클램프 전 제안(`llmGrade`)과 발동한 규칙(`clampedBy`)을 결과에 남긴다.
- **3단계에 이력서 원문을 다시 주지 않는다** — 사실 재심은 1.5단계에서 끝났고, 입력을 넓히면 판단이 흔들린다(실측: 규칙 추가 −0.022 vs 어휘 좁히기 +0.058, `AGENTS.md` §3-1).
- **두 호출 다 실패해도 예외를 안 던진다** — 원 판정 유지 / 점수식 폴백 + warning.

> `AGENTS.md` §1 은 판단 계층의 LLM 을 금지하고 예외를 `semantic_judge` 하나로 적어 두었다.
> 이건 **두 번째 예외**다 — 근거는 `_fitgrade/design.md` §3~§4, `_fitgrade/CHANGELOG.md` 4번.

## 3. 오케스트레이터 (에이전트 수에 안 들어감)

한 턴이 지나가는 관문 순서다. 최종 통합 응답은 여기가 담당한다.

| 단계 | 어디 | 하는 일 |
|---|---|---|
| 1. 첨부 저장 | `chat._apply_attachments` | 내용으로 kind 재분류, 이력서가 바뀌면 파생 자산(analysis 등) 무효화 |
| 2. 플래너 | `planner.plan_agents` | LLM 이 manifest 에서 **이름과 인자**를 고른다. 확신 < 0.6 이면 `career_chat` 이 턴을 받는다 |
| 3. 검증기 | `router.validate_plan` | 전제 생산자 자동 삽입, 실행 불가 항목 제외, 미선언 인자 차단 |
| 4. 실행 | `chat.handle_chat` | 스텝 상한 5 / 동시 실행 상한 3, 독립 구간은 병렬 |
| 5. 관찰 | `observe_rules.observe` | **LLM 없음.** 판정 등급이 낮으면 자소서·면접을 빼고 `application_plan` 을 넣는다 / 전제 붕괴 항목 제외 |
| 6. 저장 | 턴 끝 write-back | 상태 전이는 `sessionUpdates` 로만 |

### 3-1. 오케스트레이터의 툴 — 플래너가 못 부르는 것들

**"오케스트레이터만 호출할 수 있는 것"도 결국 오케스트레이터의 툴이다.** 에이전트가 툴을
쥐고 루프를 돌듯, 오케스트레이터도 자기 툴을 쥐고 턴을 돈다. 차이는 **누가 고르느냐**뿐이다 —
에이전트의 툴은 LLM 이 고르고, 이것들은 **자산 상태가 고른다.**

| 툴 | 언제 발동 | 무엇을 하나 | 어디 |
|---|---|---|---|
| `posting_fetch` | URL 공고가 미수집 | 큐 맨 앞에 끼워 원문으로 승격 (D64) | `chat.py` |
| **정리 단계 삽입** | 판정이 예정된 턴에 자료가 **방금** 제출됨 | `posting_analysis`·`resume_diagnosis` 를 판정 **앞**에 끼운다 — 사용자는 판정만이 아니라 "무엇을 읽고 판정했는지"를 본다 (D71) | `submission_review_inserts` |
| 첨부 저장·재분류 | 첨부·붙여넣기 | 내용으로 kind 재판정, 이력서가 바뀌면 파생 자산 무효화 | `_apply_attachments` |
| 전제 생산자 삽입 | 전제 자산이 빔 | 그 자산의 생산자를 앞에 끼운다 | `router.validate_plan` |
| 동의 게이트 | 무거운 것이 **자동 삽입**됨 | 실행하지 않고 한 턴 묻는다 (명시 선택이면 그냥 실행) | `chat.py` |
| 재계획 | 판정 등급이 하·판정불가 | 자소서·면접을 빼고 `application_plan` 을 넣는다 | `observe_rules` |
| 미완수 요청 재큐 | 지난 턴 요청의 자료가 채워짐 | 이어서 실행 + 안내 한 줄. 못 채우면 수명(`turnsLeft`)을 줄이고 잊는다 | `pendingRequest` |
| 이력서 확인 질문 | 어느 이력서인지 모호 | 되묻는다. 동의 게이트와 **같은 배관** (D158·D159) | `resume_confirm_ask` |
| 병렬 배치 | 연속 구간이 서로 독립 | 같은 배치로 동시 실행 (동시 상한 3) | `parallel_group` |

공통점이 하나 있다 — **전부 플래너 어휘를 건드리지 않는 자리다.** manifest 에 넣으면 플래너
프롬프트가 바뀌어 평가셋 재측정이 필요해지는데(`AGENTS.md` §3-6), 이것들은 LLM 이 고를 판단이
아니라 자산 상태에서 따라 나오는 필연이다. 그래서 `posting_fetch` 는 레지스트리에 **등록은
돼 있되** `internal=True` 로 manifest 에서만 빠져 있다 — 등록의 이점(전제·산출 선언, 표현
계층)은 그대로 쓰고 플래너 어휘는 불변으로 둔다.

## 한 줄 결론

**에이전트 7 (말하는 것) + 도구 4 (계산하는 것) + 오케스트레이터 1층.** 자기 루프 에이전트
5개가 각자 1~4개 툴을 쥐고 돌고, 오케스트레이터도 플래너가 못 부르는 자기 툴 9개를 쥐고 돈다.
고르는 주체만 다르다 — 에이전트 툴은 LLM 이, 오케스트레이터 툴은 자산 상태가 고른다.
