## 1. 전체 3계층 구조

하나의 거대한 AI가 아니라, **신뢰성 계약이 다른 세 계층의 분업**이다.

```text
사용자 ↔ 자연어 대화 (v2bridge POST /v1/chat · /v1/chat/stream)
              │
┌─────────────▼──────────────────────────────────────────────┐
│  ① 대화 오케스트레이터  (orchestrator/)                          │
│     인테이크[결정론: URL 다중·이력서 붙여넣기·kind 재분류]            │
│     → 플래너[LLM 자율 판단, blockedRequests 신고]                │
│     → 검증기[결정론: 전제 생산자 삽입·동의 게이트]                   │
│     → 실행[병렬 ≤3 · 스텝 ≤5] → 관찰[결정론 규칙] → 저장           │
│     실행 불가 요청은 기억(pendingRequest)했다가 자료가 오면 재큐      │
└──┬──────────────────────────────────────────────────────────┘
   ▼  (agents/ 11종 = 도구형 4 + 대화형 7, 화이트보드(세션 자산)로 지식 공유)
 공고수집  적합도분석  공고추천  로드맵조회                   ← 도구형(말하지 않음)
 공고담당대화  이력서담당대화  진로대화  선호파악  면접준비  자소서초안  지원경로  ← 대화형
   │
   ▼
│  ② 판정 엔진  (graph/ 10노드, 결정론)                            │
│  parse → profile → completeness → sufficiency → gap            │
│  → roadmap → (alternatives) → verify → assemble                │
   │
   ▼
│  ③ 행동/생성 산출물 + 인간 게이트                                 │
│  초안까지만 — 최종 확정(제출)은 사용자. 제출 툴 자체가 없다          │
```

| 계층 | 신뢰성을 무엇으로 버나 | LLM |
|---|---|---|
| ① 오케스트레이터 | 추론은 자율, **행동 집합과 상태 전이는 하네스가 좁힌다**(등록된 에이전트만·전제 확인·가시화·기억) | 에이전트 선택만(판단 필드 없음) |
| ② 판정 엔진 | 틀리지 않음(결정론·회귀 테스트) | 입구(읽기)·출구(말하기)만 |
| ③ 행동/생성 | 제출 전 사람이 본다 | 근거제한 생성만 |

**한 줄**: **추론은 자율에 맡기고, 행동과 상태 전이는 하네스로 좁힌다.**
① 그라운딩 — 판단의 입력을 강제한다(세션 자산·최근 대화·지속 사실·실행 가능 여부·화이트보드).
② 액션 스페이스 제한 — 추론은 자유롭게, 실행 가능한 행동 집합은 좁게(레지스트리 등록 에이전트만).
③ 검증 — 자율 판단의 출력을 사후에 확인한다(스키마·전제 검사·금지표현·근거 대조).

## 2. 대화 오케스트레이터 (`orchestrator/`)

### 한 턴의 관문 (6단계 — `explain` 이 코드에서 파생해 주는 것)

| # | 관문 | 파일 | 성격 | 하는 일 |
|---|---|---|---|---|
| 1 | 인테이크 | `chat.py` (`_apply_attachments`·`detect_posting_urls`·`detect_pasted_resume`), `attachment_kind.py` | 결정론 | 첨부 kind 를 내용으로 재분류. 발화 속 **공고 URL 여러 개를 전부** 자산으로(D94, 스킴 없는 주소도 D80). 발화에 섞인 **이력서 원문도 신호 어휘 스코어로 승격**(D68·D69). 이력서 갱신 시 파생 자산(profile·analysis) 무효화 |
| 2 | 플래너 | `planner.py` | **LLM** | 발화+자산+지속 사실+에이전트 목록(레지스트리에서 동적 생성) → 호출할 에이전트·인자 선택. 선택지는 스키마 Literal 로 제한(환각 호출 구조적 불가). **지금 못 하는 요청은 `blockedRequests` 로 신고**(D72). 라우팅 판정은 **전용 티어(최상급 모델)** 분리(D74) |
| 3 | 검증기 | `router.py::validate_plan` | 결정론 | 전제 검사 + 전제 생산자 자동 삽입(`produces` 기반) + 실행 불가 제거. 무거운 생산자가 **자동 삽입**되면 **동의 게이트** — 실행 없이 한 턴 묻는다(애매하면 묻는 쪽) |
| 4 | 실행 | `chat.py::handle_chat` 루프 | — | 스텝 상한 5 · 동시 실행 상한 3. 서로 독립인 연속 구간은 병렬(`parallel_group`, 실측 최소 10초~최대 35초 단축) |
| 5 | 관찰 | `observe_rules.py` | 결정론 | 실행 결과를 보고 남은 계획 수정 — ① 약한 판정(하·판정불가)이면 자소서·면접을 빼고 지원 경로 설계로 교체 ② 전제 붕괴 항목 제거. **LLM 없음** |
| 6 | 저장 | `chat.py` write-back | 결정론 | 턴 끝에 한 번. 상태 전이는 `AgentResult.sessionUpdates` 로만(§2-4) |

### 턴을 넘는 기억 장치 (세션)

| 장치 | 무엇을 기억하나 | 근거 결정 |
|---|---|---|
| `pendingRequest` | 청했지만 자료 결측으로 못 한 요청(에이전트+결측 자산, 3턴 유효) — 자료가 오는 턴에 **결정론 재큐**로 완수. 되묻기 버튼도 구조로 보장 | D72 |
| `user_facts` | 발화 속 지속 사실(목표·제약·상황) 누적 — 다음 턴 플래너·대화의 그라운딩 | D82 |
| `posting_library` | 활성 공고가 바뀌어도 **정리했던 공고들을 잊지 않는다**. 조회(recall)도 라이브러리를 본다 | D86·D87 |
| `resume_library` | 여러 이력서를 보관·지목·비교 — 활성 이력서가 바뀌어도 이전 이력서를 잊지 않는다 | D119 |
| 화이트보드(세션 자산) | 도구가 만든 지식(공고 파싱·프로필)을 모든 에이전트·판정 그래프가 공유 — 재생산 금지 | D84 |
| 공고 파싱 캐시 | 이미 정리한 공고의 조회 질문은 재분석 없이 **물은 항목만 골라** 답한다 | D79·D81 |

**신뢰성 3규칙**: ① LLM은 선택만 한다(판단 필드 없는 스키마) ② 실행 가능 여부·순서 보정은
결정론 검증기가 확정 ③ 선택을 가시화하고(플래너 ack — 금지표현 검증 통과분만 + 진행 로그
D70·D93 + 문장별 화자 replySources D67), 확신이 낮거나 실행할 것이 없으면 **고정 문구로 끝내지
않고** 대화형 에이전트가 사용자의 말에 답하며 필요한 자료를 요청한다.

**대응표를 두지 않는 이유**: (발화 × 자산) 표는 문장 하나만 달라져도 무너지고, 에이전트가
늘어날 때마다 표가 곱으로 커진다. 무엇을 할지는 발화·상태·대화 이력을 함께 본 플래너가 매 턴
새로 정하고, 코드는 그 선택이 **지금 실행 가능한지만** 확인한다. LLM 이 없으면 흐름을 대신
정하는 대신 대화형 에이전트가 턴을 받는다(2026-07-27 `intent.py`·`route()` 제거).

**측정(2026-08-01, `evals/planner_dataset.json` 52케이스 × 3회)**: 시퀀스 정확도 **1.0**,
안정성 **1.0**, stable_wrong **0**, unstable **0**, blocked 신고 **1.0**. 승격(D97)이 노린
능력을 재는 케이스 4건을 넣고 **그 케이스에 판별력이 있는지까지 확인했다**(D101 — 승격 전
description 을 주입해 되돌려 돌린다. 2건은 승격 전 ASK/application_plan 으로 갈렸고, 2건은
판별력이 없어 `note` 에 그렇다고 적었다).
직전 07-31 은 0.965/0.986 이었다. 상세: `docs/eval-records/2026-08-01_planner-promoted-agents.md`.
**08-03 재측정**(D125 — `targets` 어휘에 추천 목록·순번 추가 후, 같은 52케이스 × 3회):
정확도 **1.0** · 안정성 **1.0** · stable_wrong **0** 유지(`evals/planner_baseline_rec_targets.json`).

*이전 측정(지우지 않는다 — 어떤 변경이 무엇을 흔들었는지가 다음 판단의 근거다)*:
07-31 은 0.965/0.986 — D72 신고 프롬프트를 넣은 비용(flaky 2건)과 이득(신고 정확도 1.0)을
갈라 기록했고, 그 2건은 08-01 승격 재측정에서 안정화됐다. 07-29 는 0.978/1.0.
07-24 의 "41/41 100%" 는 1회 측정 후 프롬프트가 바뀌어 **폐기**.
상세: `docs/eval-records/2026-07-31_planner-blocked-requests.md`.

**플래너 하네스가 못 재는 것**: 승격이 바꾼 큰 부분은 라우팅이 아니라 **답의 내용**이다
(같은 담당에게 갔어도 전에는 요약만 냈다). 그 차이는 이 하네스로 원리적으로 못 잰다 →
**`eval/generic_score` 를 따로 만들었다**(D103·D106~D109, §7 참고). 전후 비교 문턱은
**runs=5 에서 0.0178** 이다(D109 — 합동 σ 0.0199 에서 `2σ/√runs`). 측정마다 나오는 SEM·범위는
**문턱으로 쓰지 않는다**: 범위는 표본이 늘면 커지고, n=5 의 σ 추정은 참값의 ×0.6~×2.4 로 흔들린다.

**모든 호출은 오케스트레이터가 한다** — 에이전트끼리 서로의 상태를 바꿀 수 없고, 호출 경로는 항상 추적 가능하다.

## 3. 판정 엔진 (`graph/` 10노드)

모든 노드는 읽기/판단/말하기 중 하나다. **판단 노드는 LLM을 쓰지 않는다**
(유일한 의도적 예외: `semantic_judge` — 아래 §3.5).

| 노드 | 계층 | 답을 정하는 것 | LLM |
|---|---|---|---|
| `parse_job_posting` | 읽기 | 정규식(`rule_extractor`) 1차 → 잔여 비정형만 LLM → `skill/role_taxonomy` 표준화. 연차는 문서 선착 표기 우선(D85) | ✅ 잔여 추출만 |

**화이트보드 연동(D84)**: 그래프는 실행 전에 세션의 기존 지식(공고 파싱·프로필)을 받아
재생산하지 않고, 실행 후 새로 만든 지식을 세션 자산으로 승격한다 — `fit_analysis` 가
양방향 변환을 담당(`fit_analysis.py`).

### 3.5 스코어링 알고리즘 (핵심, `gap_matcher.py`)

**매칭 — 4단 캐스케이드** (정량은 룰, 정성만 LLM):

1. **정확/동의어 매칭(룰)** — `skill_taxonomy`로 표기 정규화(ReactJS/리액트→React) 후
   skillEvidence 대조. 함의 관계 `implies`(MySQL→RDBMS·SQL) 반영. 요구 기술의 80% 이상
   충족이면 met(4개 중 3개 증명을 미충족으로 찍는 건 과하다).
2. **LLM 의미판정(의도적 예외)** — 기술명이 안 뽑히는 서술형 요구만. **이력서 근거 문장
   안에서만, 관련 있냐 없냐 이진 판정만**(점수·등급 불가). N건을 1콜로 배치 + 캐시.
   (원래 임베딩 유사도였으나 실측 신뢰 불가로 교체 — troubleshooting 07-20.)
3. **도메인 키워드(룰→LLM 폴백)** — 포함 매칭 먼저, 실패 시 2번과 같은 의미판정.
4. **연차 사다리(룰)** — 관련 직군 경력만 개월 합산(`experience_estimator`) →
   intern~lead 사다리 위치 비교. 한 칸 아래면 partially_met.

**점수화 — 가중 평균 → 임계값 등급**:

- 상태 점수: met 1.0 / partially_met 0.5 / not_met 0.0. **uncertain 은 분모 제외.**
- 요구 종류 가중: required 1.0 / preferred 0.5.
- 카테고리 가중: techSkill 0.35 · projectExperience 0.25 · roleRelevance 0.15 ·
  domainFit 0.15 · certLanguage 0.10 — **계산된 카테고리만** 가중 평균(억지 숫자 금지,
  하나도 없으면 "판정불가").
- 등급 경계: **상 ≥ 0.7 / 중 ≥ 0.4 / 하 < 0.4.**

**가장 중요한 규칙 — 모른다 ≠ 아니다**: 판정 불가는 `uncertain`이며 gap 에 넣지 않고
`check_sufficiency`가 되묻기로 돌린다. 모든 판정에는 method(어떻게 판정했나)와 reason
(근거 문장, "근거로 확인됨/기재만 됨" 구분)이 남아 **점수 뒤 근거가 전부 추적된다.**

## 5. 신뢰성 장치 (계층 공통)

| 위험 | 방어 |
|---|---|
| LLM 즉석 판단 | 의도분류 스키마에 판단 필드 없음 / 읽기 스키마에서 판단 필드 제거 — **금지는 프롬프트가 아니라 구조로** |
| 근거 환각 | `evidenceMap` 원문 대조 제거 → id 룰 재부여 → skillEvidence 룰 구축 → verify 참조 무결성 — 문장이 판정까지 가는 동안 지어낼 기회 차단 |
| 자소서 환각 | evidenceMap 밖 서술 금지 + 원문 대조 + verify + 초안 게이트(사용자 검토 없이 완성본 없음) |
| 문항 답 창작 | 프로필 결측 문항은 생성 대신 되묻기 |
| 허구 공고 | 대안·추천은 RAG 실존 공고만. 검색 실패 시 경로 '유형'만 내고 confidence 0. **폴백 검색이면 그 사실을 말한다**(D90) |
| 요청 증발 | **요청 완수 보장(D72)** — 못 하는 요청은 신고(blockedRequests)→기억(pendingRequest)→재큐. 실행도 기억도 안 됐으면 경고로 못 박는다 |
| **로스터 밖 요청이 흔적 없이 사라짐** | `blockedRequests` 는 `list[AgentName]` 이라 **등록된 에이전트로 표현되는 요청만** 신고할 수 있었다 — "연봉 협상"·"포트폴리오 리뷰"처럼 로스터에 없는 요청은 신고할 칸 자체가 없어 `career_chat` 이 즉흥으로 받고 끝났다. `unsupportedRequest`(자유 문자열)로 **세기만 한다**(**D117**) — 라우팅은 바꾸지 않는다. 무엇이 오는지 모르는 채로 갈래를 만들면 근거 없는 판단을 코드로 못 박게 되므로, 첫 주 데이터를 보고 로스터 후보를 정한다. 세션(`unsupported_requests`)에 남긴다 — 로그는 stdout 전용이라 휘발한다 |
| **폴백이 이유를 삼킴** | `career_chat` 이 고정 안내문으로 강등할 때 `career_chat_fallback` 경고를 올린다(**D117**, §2-6 의 마지막 구멍). 실측 275턴에서 이 문구가 7건(2.5%) 나갔는데 **전부 정상 요청**이었고 원인 셋 중 어느 것인지 알 수 없었다 |
| 무거운 작업 무단 실행 | 동의 게이트 — 청하지 않은 무거운 생산자가 계획에 끼면 실행 없이 먼저 묻는다. 모르면 묻는 쪽이 기본값 |
| 오라우팅 | 라우팅 가시화(progress D70·D93 + replySources D67) + 저신뢰 되묻기 + 결정론 검증기 + 플래너 평가셋(**52케이스**: 정확도 1.0·안정성 1.0·신고 1.0, 08-01. 케이스 판별력 검증 D101) |
| **근거 없는 제안** | 프로젝트 제안은 `save_plan` 을 거쳐야 답변에 실리고, 도구가 **커버 요구사항 ID** 를 검증한다(**D104**). 빈 커버·공고에 없는 ID 는 기록되지 않는다. **연차 요건은 커버 목록에서 뺀다** — 프로젝트로 경력 연차를 채울 수는 없다 |
| **정보 손실(연차 상한)** | 범위 표기("경력 3~7년")의 상한을 파싱에서 버리지 않는다(**D105** `maxYears`). 판정에 쓰는 것은 별 결정으로 남겼다 |
| **지목 오해석 강행** | `targets`/`resumeTargets` 가 라이브러리·추천 어디에도 매칭되지 않으면(수집 실패·URL 없음 포함) **활성 자산으로 강행하지 않고** 기억하는 후보 목록과 함께 되묻는다(**D126**) — 전에는 경고만 남기고 활성 공고를 판정해 사용자는 그것이 지목한 공고의 판정인 줄 알았다 |
| **턴 사후 추적 불가** | trace 는 턴이 끝나면 소멸했다 — `JOBIS_TRACE_DIR` 설정 시 턴마다 이벤트 전체를 JSON 파일로 영속(**D127**, opt-in). "어제 그 턴에 왜 이 에이전트가 돌았나"의 물증 |
| **세션 내부 불가시** | `GET /v1/sessions/{id}` (v2bridge, 읽기 전용) — 활성 이력서·라이브러리·추천·판정 등급·턴 수 요약(**D128**). 전에는 sqlite 를 직접 열어야 했다 |
| 플래너 환각 선택 | 선택지를 스키마 Literal 로 제한 — 미등록 에이전트는 애초에 못 낸다. 인자도 선언된 이름만 통과 |
| 에이전트 폭주 | 스텝 상한 5 · 위임 읽기 전용 · **제출·결제·전송 툴 미보유** — 최종 행동은 사람만 가능 |
| LLM 사망 은폐 | 폴백 답변에는 warnings 필수(§2-6) + "이 응답은 결정론 폴백" 로그 한 줄 |
| **저장 자산 파괴** | 짧은 텍스트가 저장된 이력서를 교체하지 못한다(**D98**). **분석이 있을 때 채용사이트로 알아볼 수 없는 주소는 공고로 등록하지 않는다**(**D117** — 대화 중에 붙인 깃허브·포트폴리오 링크가 `analysis` 를 말없이 지우던 것. 조건이 "공고 보유"가 아니라 "분석 보유"인 이유는 §5 아래 표 밖 D117 참조). 걸러낸 주소는 버리지 않고 발화에 남아 플래너가 읽는다. 가드는 입구가 아니라 **모든 입구가 합류하는 `_apply_attachments`** 에 둔다 — 입구마다 검사하면 다음 입구를 만드는 사람이 그것을 다시 지켜야 한다. 되돌린 텍스트는 버리지 않고 발화로 합친다 |
| **부푼 분모로 등급 왜곡** | 택일 요구("A/B/C 중 하나")를 요구사항 하나로 센다(**D99**). 파서가 OR 관계를 잃고 평면화한 techStack 을 그대로 세면 그 수가 `techSkill` 분모가 되어 등급이 낮아지고, 낮은 등급이 관찰 규칙 ①을 발동시켜 **사용자가 청한 자소서·면접을 큐에서 뺀다** |
| **에이전트가 사실을 모른 채 답함** | 프롬프트로 못 고치는 종류다(**D100**) — 요청 문장이 첨부에 삼켜지거나(`_trailing_request` 로 보존), 이력서가 판별 안 돼 자산이 안 되거나(서술체 신호), 자기가 턴을 독점한다고 착각하면(`_planThisTurn` 통보) 지시가 아니라 **facts** 를 고쳐야 한다 |
