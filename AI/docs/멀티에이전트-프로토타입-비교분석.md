## 프로토타입이 더 나은 축

### 2-1. 툴 수준 ReAct 루프의 실효성 — ~~프로토타입 우세~~ → **재정의 후 처리 (2026-07-29)**

> 이 축은 1차 판정이 **두 가지를 뭉쳐서** 봤다. 아래 판정을 근거로 남기고, 절 끝의
> "재정의·처리"에서 그 둘을 갈라 각각 어떻게 했는지 적는다.


프로토타입은 `agent`(LLM `bind_tools`) ⇄ `tools` 를 **전체 메시지 히스토리로** 돌린다
(`agent/graph.py:85,165`). 매 관찰마다 LLM 이 다음 툴을 다시 고르고, 그 재선택이 실제로 일어난
기록이 있다:

- `test_logs/2026-07-27_task10-eval.md` E1 run3: 없는 URL → `load_posting` 실패 관찰 →
  그래도 `analyze_gap` 시도 → "조회된 공고 없음" 안전 처리. **관찰이 다음 행동을 결정했다.**
- S3: `['load_posting','analyze_gap']` 을 한 스텝에 함께 계획.

본체의 대응물은 두 층으로 갈려 있고, **바깥 층은 값을 증명하지 못했다.**

| 층 | 위치 | 상태 |
|---|---|---|
| 오케스트레이션 관찰 | `chat.py:467-506` `observe_after` — 요약 payload를 경량 모델에 되물어 `continue/finish/call` | **관찰이 실행을 바꾼 실측 0건.** 관측된 결정은 전부 continue·finish (`_docs/agent/멀티에이전트_구현_평가_및_개선방안.md` §0 "아직 증명하지 못한 것") |
| 에이전트 자기 루프 | `agents/agent_loop.py` (interview_prep, coverletter_draft) | **작동 확인됨.** 0729 실측: step3 `check_draft` → step4 `save_draft(보완만)` 재작성 |

즉 프로토타입의 루프는 **210줄로 실효가 확인**됐고, 본체는 같은 것을 두 층으로 나눠 짓고
바깥 층은 아직 비용만 낸다(0728 계측: 관찰 2회가 26.2초를 쓰고 아무것도 바꾸지 않아
도구 뒤·큐 소진 뒤에는 아예 걸지 않도록 잘라냈다 — `chat.py:467,475`).

**단, 비교 조건이 다르다는 것도 적는다.** 프로토타입은 툴 3개 중에서 고르고, 본체는
에이전트 10종 × 세션 자산 8종 × 다중 턴 맥락에서 고른다. 선택지가 3개면 히스토리 전체를
매 스텝 다시 넣는 것이 싸지만, 10종·수십 턴에서는 그 방식이 그대로 확장되지 않는다.
그래서 이 축의 교훈은 "본체가 프로토타입 방식으로 돌아가야 한다"가 아니라
**"바깥 층 관찰은 값을 증명하거나 걷어내야 한다"** 이다.

#### 재정의 — 뭉쳐 본 두 가지를 가른다

프로토타입 루프에는 세 성질이 있는데, 본체의 `observe_after` 는 **셋 다 없었다.**

| 성질 | 프로토타입 `agent⇄tools` | `observe_after` | `agent_loop` |
|---|---|---|---|
| LLM 이 보는 것 | **전체 메시지 히스토리** | 요약(reply 300자·dataKeys·warningCodes·producedAssets·askedUser) | facts + 관찰 + **대화 이력**(07-29 추가) |
| LLM 이 고르는 것 | **실제로 할 행동**(툴 호출) | `continue/finish/call` — **제어 신호** | **실제로 할 행동**(도구 호출) |
| 최종 답변 | **LLM 이 직접 쓴다** | 쓰지 않는다 | **LLM 이 직접 쓴다** |

즉 `observe_after` 는 그 성질의 **열화 모방**이었고, 그 성질이 실제로 사는 곳은
`agent_loop` 다. 그래서 둘로 갈라 처리했다.

**① 오케스트레이션 관찰(`observe_after`) → 규칙으로 교체.** `orchestrator/observe_rules.py`
신설(순수 함수, LLM 0회). 규칙 둘 — 약한 판정이면 생성 단계를 지원 경로 설계로 교체
(§2-2), 전제가 무너졌으면 그 단계를 제외(전부 빠지면 finish). `planner.observe_after`·
`ObserveDecision`·`AgentSpec.observe`·`observes_after` 제거. trace `observe` 이벤트 형태는
유지하고 **어느 규칙이 정했는지(`rule`)** 가 추가로 남는다.

프로토타입도 같은 분할을 했다는 점이 근거다 — `decisions.md` D11: *"A의 '게이트까지 LLM
자유'는 agent다움이 아니라 설계 의도 위반 리스크. B가 그 의도를 결정적으로 보장 = 더 충실."*
**툴 선택은 LLM, 분기는 조건엣지.** 이 자리는 그 조건엣지에 해당한다.

교체하면서 **실측 결함 하나가 닫혔다**: `runnable_now` 가 순차 실행 직전에 한 번도 검사되지
않아, 판정이 실패해 `analysis` 가 없어도 자소서가 그대로 돌았다(재현: `analysis=None` 위에서
초안 작성). 예전 판정은 "남은 것 중 하나라도 돌 수 있으면 계속"이라 **못 도는 항목을 그대로
실행**했다 — 관찰 LLM 이 앉아 있던 자리가 정확히 거기였는데 막지 못했다.

**② 에이전트 자기 루프(`agent_loop`) → 넓히고 깊게.** 본체의 에이전트다움을 지는 곳이라
얇은 것이 문제였다.

| | 전 | 후 |
|---|---|---|
| 채택 | 2/10 (interview_prep, coverletter_draft) | **3/10** (+ preference_intake) |
| 스텝 상한 | `DEFAULT_MAX_STEPS = 3` | **5** (coverletter 는 7 유지) |
| LLM 입력 | facts + 이번 턴 관찰 | **+ 최근 대화 이력**(매 스텝) — 프로토타입의 "전체 히스토리"에 해당 |
| 위임 소비자 | 1건 | **2건** (+ `preference_intake → job_recommend`) |

`preference_intake` 전환 실측(실 GMS `gpt-4.1-mini`, 2턴):

```
step1 record_preference('도메인: 커머스\n지역: 서울')
      → 선호 차원 2개, 충분한가: 예            ← 도구가 분기점(룰)을 관찰로 돌려준다
step2 request_material('이력서')                ← 그 관찰을 보고 행동을 바꿨다
step3 reply
```

도구가 낸 `충분한가` 를 보고 LLM 이 다음 행동을 정한다 — 프로토타입에서 `analyze_gap` 결과를
보고 다음 툴을 고르던 것과 같은 동역학이다. 새 도구 `preview_postings`(job_recommend 위임)는
"지금 조건으로 실공고가 몇 건인가"를 관찰로 주고, 0건이면 조건을 넓히자고 되묻게 한다 —
이 턴에서는 선호가 바로 충분해져 호출되지 않았다(미실측으로 남긴다).

**루프 궤적 안정성은 2026-07-29 에 측정했다**(`eval/loop_consistency.py`, 3케이스 × 5회,
Claude `sonnet`): `preference_intake` 0.80 / `interview_prep` 0.80 / `coverletter_draft` **0.40**,
불변식 위반 0건. **낮은 안정성이 여기서는 나쁜 것이 아니다** — 자소서의 세 궤적이 전부 정당하다
(점검 통과 2 / **점검→재작성** 2 / **위임** 1). 플래너와 같은 잣대로 읽으면 안 된다.

그 측정이 **두 가지를 처음 계측으로 확인했다**: 자기비판 재작성이 실제로 발동한다(2/5),
에이전트 간 위임이 실사용에서 발동한다(1/5 — 평가 문서 §2-2 가 "통로가 있다까지만"으로 남긴 것).
그리고 최대 궤적이 4스텝이라 **`max_steps` 3→5 상향이 사후 정당화됐다**(3이면 재작성·위임 궤적이 잘렸다).

측정 전에 **치명적 결함**도 잡혔다: `--tools ""` 가 없어 Claude CLI 에서 **자기 루프 층이 통째로
꺼져 있었다**(프롬프트의 "쓸 수 있는 도구:" 를 보고 Claude 가 자기 내장 도구를 쓰려 들다
`--max-turns 1` 에 걸려 실패 → 결정론 폴백). **답변이 그럴듯해서 겉으로는 정상처럼 보였다.**
상세: `eval-records/2026-07-29_planner-reproducibility.md` 후속 5.

실측이 잡은 계약 위반 1건: 내가 쓴 관찰 문구에 `"안내하세요"` 라는 **지시**가 들어가
답변이 도구 동작을 서술했다("이력서를 요청드렸어요"). `ToolSpec` 규약은 *관찰은 사실만
담고 판단·권유를 넣지 않는다* — 지시를 `goal_system` 으로 옮겼다.

**`resume_diagnosis` 는 전환하지 않았다.** 판단 근거는 §3 의 "루프를 벌었는가" 기준 참고.

### 2-2. 사용자 여정 수준의 결정적 강제 분기 — ~~프로토타입 우세~~ → **해소 (2026-07-29)**

> **이 축은 지적 직후 본체에 반영했다.** 아래 1차 판정을 근거로 남기고, 무엇을 어떻게 메웠는지는
> 절 끝의 "해소" 항목에 적는다.

이 축이 가장 뼈아팠다. 프로토타입은 제품의 핵심 규칙을 **코드가 강제**한다:

```python
# Agent_Test/agent/graph.py:165
def _route_after_tools(state):
    if state["tools_called"][-1] == "analyze_gap" and state.get("level") in ("중", "하"):
        return "auto_search"      # 대체직군 검색을 LLM 재량 없이 강제
    return "agent"
```

성공기준 2·3("중/하 → 검색" / "상 → 검색 안 함")이 조건엣지 하나로 판정되고,
`tests/checks.py` 가 LLM 없이 그 엣지를 직접 검사한다. 2026-07-27 수동 테스트에서
`level=상` 케이스가 처음 나와 "상 → search 없음"이 런타임으로 확인됐다.

(1:6). 같은 비율이면 우리는 2,500줄이고 매 세션 자동 로드할 수 없다. 그래서 **무엇을 넣을지**를
이 세션의 경험으로 정했다 — 문서가 실제로 낡은 것을 3건 잡았고(“41케이스 100%”·선언 필드
9→8개·죽은 baseline), 전부 **수치와 구조**였다. 반면 불변 규약과 포인터는 낡지 않는다.
게다가 §2-4 에서 만든 `jobis_ai.explain` 이 구조·상수를 **코드에서 파생**해 준다.

| | 내용 | 줄 |
|---|---|---|
| `AGENTS.md` (신규, 자동 로드) | §1 3계층 / §2 금지형 8개 / §3 하네스 수정 순서 / §4 코드에 물어보는 법 | 90 |
| `작업로그/지금상태.md` (신규, 자동 로드) | 브랜치·공급자·테스트·미커밋 여부·다음 후보 | 16 |
| `CLAUDE.md` (재편, 진입점) | 임포트 2개 + **문서 지도**(무엇을 알고 싶으면 어디로) + 권위 규칙 + 실제로 문제 됐던 Git 규칙 5줄 | 47 |
| `docs/git-conventions.md` (이관) | 기존 165줄 **내용 그대로** — 자리만 양보 | 169 |

**규약에 수치를 안 넣었다.** `AGENTS.md` §4 가 대신 명령을 적는다 — `pytest -q`(1초대·비용 0)와
`python -m jobis_ai.explain`. 그리고 §3 에는 이 세션에서 **실측으로 얻은 수정 순서**를 담았다
(규칙 추가 −0.022 vs 어휘 좁히기 +0.058 / 한 번에 하나만 / 총계 아니라 케이스별 / 평가셋을
관측에 맞추지 않는다 / 프롬프트 변경과 재측정은 같은 커밋).

**지도도 테스트가 지킨다**(`tests/test_docs_entrypoint.py` 5건): 임포트 경로가 실존하는지 ·
지도에 죽은 링크가 없는지 · **자동 로드 총량 상한**(130줄, 지금상태는 25줄) · 규약에
`explain`·`pytest` 와 핵심 금지형이 남아 있는지. 죽은 링크는 지도가 없는 것보다 나쁘고,
자동 로드가 커지는 문서는 낡는다.

> 남는 격차: 프로토타입은 `decisions.md` 에 **결정마다 왜·경위·교훈**을 시간순으로 잇고 뒤집힌
> 결정도 지우지 않는다(D1~D16). 우리는 그 역할이 `작업로그/<날짜>.md` + `docs/eval-records/` +
> `troubleshooting.md` 로 **흩어져 있다.** 지도가 있어 찾을 수는 있지만, "이 결정이 언제 왜
> 뒤집혔나"를 한 파일에서 훑는 경험은 아직 없다.

### 2-6. 호출 수 / 비용 — 프로토타입 유리, 단 **지연 실측 없음**

| | 턴당 LLM 호출 |
|---|---|
| 프로토타입 | 라우팅 1~2(cheap `gpt-4o-mini`) + 갭분석 2(mid 요건추출 + strong 폴백) ≈ **3~4콜** |
| 본체 | 플래너 1(고급) + 관찰 최대 n(경량) + 에이전트 내부 + 판정 그래프 노드 |

본체는 실측이 있다: 첫 분석 턴 ~81초(0723, `gpt-5.4`) → GMS `gpt-4.1-mini` 전환 후 **턴당 4~7초**,
독립 구간 병렬화로 21.3초 → 15.6초.
**재측정(07-29 밤, `claude_code`/sonnet, 독립 3개)**: 순차 47.8·48.0초 vs 병렬 13.3·37.6초
→ **최소 10초·최대 35초 단축**(D54). 순차는 안정적이고 병렬은 캐시 상태에 따라 갈린다.
**프로토타입은 지연 실측 기록이 전혀 없다** —
호출 수가 적으니 빠를 것이라는 추정은 가능하지만, 비교치로 쓸 수 없다. **미확정으로 남긴다.**

### 2-7. 판정(갭분석) 정확도 — 본체 압도적 우세

프로토타입 **자신의 측정 기록**이 가장 강한 증거다
(`prototype_1.0.0/test_logs/2026-07-27_1.0.1-baseline-observation.md`, 6프로필):

| 프로필 | 노림 | 관찰 | 판정 |
|---|---|---|---|
| 정민준/백엔드 | 상 | 중 | ✗ |
| 김도윤/부트캠프BE | 중 | 중(agent 상) | △ 판정 불안정 |
| 한유진/데이터 | 중 | 하 | ✗ |
| 오세훈/안드로이드 | 중/하 | **상 (score 1.00)** | ✗✗ **거짓 상** |
| 박지호/정보보안 | 하 | **상 (0.71)** | ✗✗ **거짓 상** |
| 이서현/프론트 | baseline | 상(0.81) | ✓ **6개 중 유일 정상** |

거짓 상의 기제가 로그에 그대로 남아 있다 — 오세훈의 `충족(필수)` 이 `[학력무관, 경력무관]`
**둘뿐**이고 부족 0건이라 score 1.00 → 상. 즉 **자격조건을 기술요건으로 오추출**해
트리비얼 충족으로 만점을 냈다(W1). 동시에 진짜 도메인 스킬(Linux·자료구조·알고리즘·OS·네트워크)은
`uncertain` 으로 빠져 분모에서 제외돼 신호가 소실됐다(W2).

원인은 구조적이다. `tools/analyze_gap.py` 의 판정 재료는 **LLM 1콜의 `_Requirements{required[], preferred[]}`**
가 전부다. 표기 정규화도, 함의 관계도, 카테고리 구분도, 연차 사다리도 없고, 무엇보다
**"판정 재료가 부실하다"를 감지하는 게이트가 없다** — `AGENTS.md §0` 이 "이력서 빈약 케이스 처리"를
*절대 안 할 것* 에 명시적으로 넣어 두었기 때문이다.

본체 `gap_matcher.py` 의 4단 캐스케이드는 그 결함들을 하나씩 겨냥한다:

| 프로토타입의 결함 | 본체의 대응 | 위치 |
|---|---|---|
| 표기 불일치(ReactJS/리액트) | `skill_taxonomy` 정규화 + `implies`(MySQL→RDBMS·SQL) | `gap_matcher.py` 1차 |
| 4개 중 3개 증명을 미충족 처리 | `_MET_EVIDENCE_RATIO = 0.8` | `gap_matcher.py:52,185` |
| 서술형 요건 → 통째 uncertain | `semantic_judge` 이진판정 N건 1콜 배치 + 캐시 | `gap_matcher.py:44,411` |
| 연차를 텍스트로만 봄 | `experience_estimator` 관련 직군 개월 합산 → intern~lead 사다리 | `gap_matcher.py` 4차 |
| 트리비얼 항목 위의 만점 | 카테고리 가중(techSkill .35 / projectExperience .25 / …) + **계산된 카테고리만** 정규화, 하나도 없으면 "판정불가" | `gap_matcher.py:75,588` |
| 재료 부실 감지 없음 | `check_sufficiency` 커버리지 게이트 → 되묻기 | `graph/nodes.py:856,896` |

그리고 **W3(판정 불안정 — 같은 입력에 agent 상 / 직접 중)** 은 프로토타입 결정 로그가 직접
*"'결정론 우선' 하이브리드의 결정론이 허상"* 이라고 인정한 항목이다. 본체의 판정 계층은
모델을 `gpt-5-nano` → `gpt-5.4` 로 갈아도 `fitGrade` 가 동일했다(0723 실측) — 판정에 LLM 이
없기 때문이다.

> **판정: 프로토타입은 6케이스 중 1건만 맞혔고, 그 원인(W1·W2)은 D16 으로 고치기로 정해졌으나
> 코드에 반영되지 않았다. 갭분석을 실제 사용자에게 쓰는 것은 지금도 위험하다.**

### 2-8. 'uncertain' 처리의 집행 장치 — 본체 우세

원칙은 **같다** — 둘 다 uncertain 을 점수 분모에서 뺀다
(`Agent_Test/tools/analyze_gap.py:27` `_STATUS_S` 주석 / `gap_matcher.py` `_STATUS_SCORE`).
차이는 그 다음이다:

| | uncertain 이 발생한 뒤 |
|---|---|
| 프로토타입 | 개수를 세어 `rationale` 문구에 싣고 끝. 자기 로그가 남긴 지적: *"캡처된 rationale 이 전부 '[중] 필수 N건 충족 …' 템플릿 — LLM 의 진짜 '왜'가 아니라 코드가 개수로 찍은 문자열"* |

같은 원칙을 프로토타입은 **선언**했고 본체는 **집행**한다.

### 2-9. 환각 방어 층수 — 본체 우세 (격차 큼)

### 2-10. 판정/표현 분리 — 본체 우세 (2026-07-29 완결)

본체는 *말을 하는가* 를 기준으로 `kind="tool"|"agent"` 를 갈랐다(`agents/__init__.py`).
도구의 `entry` 는 reply 를 비우고, 문장은 `tool_render` 가 만든다. 그리고 **그 규약을 테스트가
강제한다**: 도구는 reply 를 만들지 않는다 / 도구는 render 를 갖는다 / 에이전트는 render 를 갖지
않는다.

**07-29 에 `posting_analysis`·`resume_diagnosis` 까지 내려 5/10 이 도구가 됐다.** 옮기면서
계약 둘을 손봤는데, 둘 다 "규칙의 근거가 무엇인가"를 되물어 나온 결론이다:

- **`render(data, session)`** — 마무리 문장은 "사용자가 방금 한 말에 이어지게" 써야 하므로
  발화·대화 이력이 필요하다. 그것을 `data` 로 흘리면 **프론트로 나가는 산출물 계약에 대화
  이력이 섞인다** — 표현이 필요한 맥락은 표현 계층이 직접 읽는다(읽기 전용).
- **위임도 도구를 부를 때 render 를 거친다** — `delegate_tool` 은 상대의 `reply` 를 관찰로
  쓴다. 도구는 reply 를 비우므로, 이 처리가 없으면 도구로 내려간 상대를 부를 때마다 관찰이
  "문장을 내지 않았습니다"가 되어 **통로가 조용히 쓸모없어진다.** 스텁으로 reply 를 넣는
  기존 테스트는 이걸 못 잡아서, 실제 에이전트로 검사하는 테스트를 따로 넣었다.

부수 효과 하나가 **분리의 값을 그대로 보여준다.** 전에는 두 에이전트가 LLM 마무리 문장을
`followUpQuestions[0].question` 에도 그대로 실었다 — 대화 산문과 UI 질문 카드가 같은 문자열을
공유했다. 분리하면서 갈랐다: **카드 질문은 결정론**(안정적·항상 요점), **대화 마무리는 맥락
산문**(LLM). 같은 문자열로 묶어 두는 것이 곧 표현과 데이터 계약의 혼재였다.

실측(실 GMS `gpt-4.1-mini`)에서 답변 형태는 그대로였다 — 요구 연차·필수/우대·요구 기술·도메인
줄, 기재만 된 스킬 표시, 질문으로 끝나는 마무리.

프로토타입은 `_tools_node`(`agent/graph.py:85`) 안에서 판정 결과를 f-string 으로 조립해
그것이 곧 LLM 입력이자 사실상 표현 재료가 된다:

```python
summary = (f"공고 조회 OK — {res.company} | {res.title}\n경력:{res.experience} · …\n본문발췌: {excerpt}")
```

문구를 고치려면 판정·라우팅이 도는 노드를 건드려야 한다. 규모가 작을 때는 문제가 아니지만,
**분리 자체가 없다**는 것은 사실이다.

### 2-11. 다중 턴 상태·세션 영속 — 본체 우세 (결정적)

프로토타입은 **싱글턴이다**. 이건 결함이 아니라 명시적 결정이고(AGENTS §0 "멀티턴 누적 범위 밖",
D12 재확정), 흥미로운 것은 **직접 마찰을 겪고도 유지했다**는 점이다 — D12: *"대화형 직접
테스트(chat.py)에서 되묻기('네가 추천한 공고')·맥락 기억 불가 마찰을 겪었으나 … 싱글턴 유지"*.

본체: `SqliteSessionStore`(영속, WAL) + `ASSET_KEYS` 화이트리스트 + **write-back 규약**(턴 시작
1회 읽기 / 턴 끝 1회 쓰기) + `history` 30항 + 자산 무효화(이력서 갱신 시 profile·analysis 폐기,
`chat.py:96-107`) + `interview`·`coverletter` 가 턴을 이어받는 다중 턴 상태.

프로토타입 구조로는 "이 공고로 자소서 써줘 → 강점 문단만 다시" 같은 흐름이 **불가능하다.**
제품 요구를 기준으로 하면 이 축은 논쟁 대상이 아니다.

공통 상위(아이비티에스·앱메이드 → 오세훈·이서현 양쪽)"* ③ 안드로이드 검색에 Java SI 공고.

### 2-13. 실패 처리·재시도·관측성 — 본체 우세, 프로토타입에 **실제 결함 1건**

프로토타입의 `ToolError{error, source, detail}` 봉투 설계는 깔끔하고, 툴 계약에
"raise 금지"를 명문화했다(AGENTS §4.1). **그런데 LLM 호출 실패가 그 계약을 지키지 못한다:**

```python
# Agent_Test/tools/analyze_gap.py:88, 109 — try/except 없음
reqs = get_structured_llm("mid", _Requirements).invoke([...])
fb   = get_structured_llm("strong", _Fallback).invoke([...])
```

`llm/gateway.py` 에도 재시도가 없다. 즉 **일시적 네트워크·레이트리밋 오류 한 번이
`_tools_node` 를 통과해 `run_agent()` 전체를 예외로 죽인다** — docstring 의 "raise 안 함"과
어긋난다. `run_agent` 는 "raise 안 함"이라고 적었지만 그것을 보장하는 코드가 없다.

본체: `structured.py` 가 **재시도 단일 계층**(3회 백오프, 클라이언트는 `max_retries=0` 으로
중첩 차단 — `llm.py:608,636`) + `llm_not_configured` vs `llm_call_failed` **구분 후 정직한 폴백**
(키 없음이면 mock 허용, 호출 실패면 가짜 샘플 금지) + `_truncate` 가 자격/우대 섹션을 보존하고
잘랐다는 경고를 남김 + 위임 대상의 경고까지 올림(`TOOL_WARNINGS_KEY`) + 결정마다 trace + 로그 1줄.

관측성도 층이 다르다. 프로토타입은 `log.info` 한 줄 형식(`[run_id][step N] node=…`)으로
충분히 읽히지만, 본체는 trace 이벤트를 웹 SSE 로 중계해 **사용자 화면에 진행이 보인다**.

## 3. 종합

### 한 줄 판정

**프로토타입이 이긴 것은 "에이전트 루프의 형태"와 "규칙을 코드로 못 박는 규율"이고,
본체가 이긴 것은 "판정의 정확도"와 "제품으로서 서는 데 필요한 전부"다.**

프로토타입은 **좋은 설계 연습이고 실제로 본체에 부품을 공급했지만, 자기 측정이 6케이스 중
5케이스에서 갭분석을 틀렸고 그 원인을 고치기 전에 멈췄다.** 본체는 **판정을 결정론으로 굳혀
정확도를 벌었지만, 그 위에 올린 오케스트레이션 동역학(관찰·재계획) 일부가 아직 비용만 내고 있다.**

그 둘 중 **§2-2(결정적 강제 분기)와 §2-1(관찰 층)은 이 문서를 쓴 직후 처리했다** —
프로토타입의 조건엣지를 대화 수준으로 옮기고, 관찰 LLM 을 규칙으로 교체하고, 그 대신
진짜 ReAct 가 사는 `agent_loop` 를 넓혔다. 두 실측이 본체의 결함 5건을 추가로 잡았다.
**비교의 실제 값은 등급표가 아니라 이것이었다**: 작은 시스템이 옳게 한 것을 이름 붙여 놓으면
큰 시스템에서 무엇이 빠졌는지 바로 보인다.

### "루프를 벌었는가" 기준 (전환 판단의 잣대)

`agent_loop` 로 옮길지는 **LLM 에게 결과를 미리 알 수 없는 선택이 있는가**로 가른다.
없으면 루프는 스텝과 비용만 늘리고, 그건 `observe_after` 가 저지른 실수와 같은 것이다.
