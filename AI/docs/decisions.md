# 결정 로그 (decisions)

> **"무엇을 왜 정했나"를 시간순으로 잇는다.** 나중 세션·다음 사람이 이미 뒤집힌 결정을 되돌리지
> 않게 하는 것이 목적이다.
>
> 규약:
> - **새 결정은 맨 아래에 append.** 위에서 아래로 읽으면 "여기까지 어떻게 왔나"가 된다.
> - **뒤집힌 결정은 지우지 않는다.** `→ 이후 변경 (Dnn)` 으로 잇는다. 지우면 왜 그 길을 안
>   갔는지가 사라지고, 다음 사람이 같은 실수를 반복한다.
> - **한 항목은 짧게.** 결정·왜·(뒤집힘)·출처. 긴 서술은 출처 문서가 담는다.
> - 여기 있는 것은 **결정**이고, 그날 무엇을 했는지는 `작업로그/<날짜>.md`, 실측 문제·해결은
>   `docs/troubleshooting.md`, 평가 수치는 `docs/eval-records/` 가 출처다.
>
> 2026-07-29 신설 — 그전 결정은 `agent-structure-evolution.md`·`troubleshooting.md`·`작업로그/`
> 에 흩어져 있던 것을 모아 소급 정리했다(그래서 D1~D33 의 서술은 요약이고, 상세는 출처를 본다).

## 판정의 결정론화 (07-16 ~ 07-20)

### D6 (07-16) 모든 노드를 **읽기 / 판단 / 말하기** 셋 중 하나로 분류한다
판단 계층은 **LLM 금지**. **왜**: 결정론이어야 회귀 테스트로 신뢰성을 벌 수 있다.
→ 출처 `agent-structure-evolution.md` ② · `AGENTS.md` §1

### D7 (07-16) RAG 는 **2 hook** 만 — 학습자료 RAG 폐기
기업 맥락 + 공고 코퍼스만. **왜**: 강의는 무한·휘발성이라 벡터 DB 와 상충하고, IT 자격증은
유한·안정·정형이라 **DB 조회 한 방**이 맞다. → 이후 변경 (D11) → 출처 `작업로그/0716.md` §3

### D8 (07-16) `similarity()` 실패는 `0.0` 이 아니라 `None`
**왜**: 0.0 은 "관련 없다"는 주장이고 None 은 "모른다"는 고백이다. **"모른다 ≠ 아니다"의 첫
적용**이며 이후 `uncertain` 설계로 이어졌다. → 출처 `troubleshooting.md` 07-16 ⑥

### D9 (07-16) 대체 공고를 **지어내지 않는다**
LLM 추측 → `career_graph`(직군 전이) + RAG 실존 공고 + `gap_matcher` 재사용.
→ 출처 `작업로그/0716.md` §4

### D10 (07-20) 이력서에 **기재만 된 스킬**도 met 로 인정한다
단 `confidence` 는 근거 있는 쪽에 높게 주고, reason 에 "근거로 확인됨 / 기재만 됨"을 구분해
적는다. **왜**: 사용자가 직접 적은 것을 부정할 근거가 없다. → 출처 `작업로그/0720.md` §4

### D11 (07-20) RAG hook① 재분류 — 기업 맥락은 RAG 가 아니라 **크롤링 정형 DB**
D7 을 한 번 더 좁혔다. **왜**: 기업 정보는 정형이라 벡터 검색이 필요 없다.
→ 출처 `작업로그/0720.md` §6

### D12 (07-20) 임베딩 유사도 → **LLM 의미판정(이진)** 교체
실측에서 `text-embedding-3-small/-large` 둘 다 짧은 텍스트 간 주제 관련성을 신뢰할 수 없게
판정했다("React" 가 "Kafka" 보다 "이벤트 드리븐"에 더 가깝다고 나옴). **판단 계층 LLM 금지
(D6) 의 유일한 의도적 예외**이며, 점수·등급이 아니라 **이진 판정만** 허용한다.
→ 출처 `troubleshooting.md` 07-20

### D13 (07-20) GMS(SSAFY 게이트웨이) 연동 — 실 LLM·임베딩 호출
**왜**: mock 위에서만 돌면 D2 의 성적표가 무의미하다. → 출처 `작업로그/0720.md` §7

## 실데이터 보정 (07-21 ~ 07-22)

### D14 (07-21) 동의어를 손으로 나열하지 않는다 — 정규화로 흡수

계산된 카테고리만 가중 평균하고, 하나도 없으면 `(None, "판정불가")`. **왜**: 억지 숫자는
근거 없는 단정이다(D8 과 같은 뿌리). → 출처 `troubleshooting.md` 07-21 ②

### D16 (07-21) 종합 적합도 등급 경계 확정 — 상 ≥ 0.7 / 중 ≥ 0.4
카테고리 가중(techSkill .35 / projectExperience .25 / roleRelevance .15 / domainFit .15 /
certLanguage .10). **경계의 단일 출처는 `gap_matcher`** 이고 다른 곳에서 다시 정하지 않는다.
→ 출처 `agent-structure-current.md` §3.5

### D17 (07-21~22) **"에이전트냐 워크플로우냐"는 잘못된 질문이었다**
판정 결정론화(D6)를 되돌리지 않는다. 문제는 판정이 아니라 **판정 뒤의 행동**과 **의도를
해석하는 정문**을 짓지 않은 것이었다 → 3계층 분업(오케스트레이터 / 판정 / 인간 게이트).
→ 출처 `agent-structure-evolution.md` ④

### D18 (07-22) 최종 행동 금지는 **툴 미보유로 강제**한다
제출·결제·전송 툴을 아예 주지 않는다. **왜**: "하지 마라"를 프롬프트로 부탁하지 않는다
(스키마에서 필드를 빼던 전략의 행동판). → 출처 `agent-structure-evolution.md` ④

### D34 (07-29) 사용자 여정 수준의 **결정적 강제 분기**를 코드로 박는다
`observe_rules.weak_grade_transition` — 등급 `하`·`판정불가` + 생성 단계 예정이면
`application_plan` 으로 교체. 프로토타입 `_route_after_tools`(조건엣지)의 대화 수준 대응물.

같은 턴에 판정이 난 경우만 걸려 **사용자를 가두지 않는다.**

### D35 (07-29) 오케스트레이션 관찰을 **LLM 에서 규칙으로** 내린다
`planner.observe_after`·`ObserveDecision`·`AgentSpec.observe`(D31) 제거 →
`orchestrator/observe_rules.py`(결정론). **왜**: 관찰 LLM 은 플래너보다 정보가 적고(요약만
본다), 제어에 쓸 신호는 전부 열거 가능한 구조화 값이며, 실측에서 실행을 바꾼 사례가 0건이었고
**자기 자리의 위험조차 못 막았다**(판정 실패 후 자소서가 `analysis=None` 위에서 돌았다).
D27 을 흡수한다. 프로토타입도 같은 분할을 했다(D11 of `Agent_Test`: 툴 선택은 LLM, 분기는 엣지).

### D36 (07-29) `agent_loop` 를 넓히고 깊게 — 에이전트다움이 사는 곳
채택 2 → 3(`preference_intake`), `max_steps` 3 → 5, **대화 이력을 매 스텝 입력에 추가**,
위임 소비자 1 → 2. → 사후 정당화 (D47)

### D37 (07-29) **"루프를 벌었는가" 기준** — `resume_diagnosis` 는 옮기지 않는다
기준: *LLM 에게 결과를 미리 알 수 없는 선택이 있는가.* 없으면 루프는 스텝·비용만 늘리고,
그건 D35 가 걷어낸 실수와 같다. `resume_diagnosis` 는 읽기 1회 + 조립 + 문장 1회라 재선택할
것이 없다(공고 대조는 **판정이고 `fit_analysis` 소관**).

### D38 (07-29) 표현 분리 완결 — `render(data, **session**)`
`posting_analysis`·`resume_diagnosis` 도구화. 마무리 문장은 발화·대화 이력이 필요한데 그걸
`data` 로 흘리면 프론트 산출물 계약에 대화 이력이 섞인다(D30 확장). **위임도 도구를 부를 때
render 를 거친다** — 없으면 도구로 내려간 상대를 부를 때마다 관찰이 "문장을 내지 않았습니다"가
되어 통로가 조용히 쓸모없어진다.
덤: LLM 마무리 문장이 `followUpQuestions` 에도 같은 문자열로 실려 있던 것을 갈랐다 —
**카드 질문은 결정론, 대화 마무리는 맥락 산문.**

### D54 (07-29) 병렬 실행을 **남긴다** — 재측정으로 정당화 (D32 후속) + 냉정 비교 지적 2건 정정
비교 재분석에서 두 가지를 지적했는데 **코드를 재확인·실측하니 둘 다 틀렸다.** 지우지 않고
남긴다 — 다음 사람이 같은 결론으로 지우려 들지 않게.

1. **"병렬 실행은 투기적이다"(틀림)**. 세션 사본·contextvars 복사·토큰 뮤트·큐순서 병합이라는
   복잡도를 지고 얻는 것이 "데모 규모에서 수 초"라고 봤다. 재측정(claude_code/sonnet, 독립
   3개): 순차 **47.8 · 48.0초** vs 병렬 **13.3 · 37.6초** → **최소 10초, 최대 35초** 단축.
   순차는 안정적이고 병렬은 캐시 상태에 따라 갈린다. D32 의 21.3→15.6초보다 이득이 크다
   (그때보다 무거운 조합을 쟀다). 수치를 `_run_parallel` docstring 에 박았다 — 근거 없는
   복잡도는 지우는 것이 맞으므로, 근거는 코드 옆에 있어야 한다.
2. **"판정 경로가 4중 중복이다"(틀림)**. `gap_matcher` · `semantic_judge` ·
   `graph.nodes.analyze_gap` · 프로토타입 `analyze_gap` 을 같은 층으로 셌는데, 실제로는
   **계층 분리**다: `analyze_gap` 노드는 `gap_matcher.match()` 를 부르는 조립부이고
   (판정 코드 0줄), `semantic_judge` 는 `gap_matcher` 가 쓰는 하위 부품(D12 예외)이다.
   진짜 중복은 **경계 리터럴 하나**였고 D52 에서 닫았다. 프로토타입 쪽은 별 저장소다.

**교훈**: "중복처럼 보이는 것"과 "층이 나뉜 것"은 호출 방향을 봐야 갈린다. 파일 수와 줄 수만
세면 계층을 중복으로 오독한다 — 이 정정 두 건이 그 예다.

### D55 (07-29) hand-off 성공률은 **거부를 남겨서** 센다 + 위임 경로 수를 협업 지표로 쓰지 않는다
평가 리포트 §1-1 이 ○ 였던 이유는 통로가 부실해서가 아니라 **성공률의 분모가 없어서**였다.
`delegate_tool` 의 거부 6종이 전부 `return (관찰 문자열, {})` 로 끝나고 `trace.emit("delegate")`
는 성공 경로에만 있었다 — 즉 "시도했는데 가드에 걸렸다"가 어디에도 안 남았다. 분자만 있고
분모가 없으면 비율은 영구히 계산 불가다.

**한 것**: 거부마다 `delegate_refused` trace(사유 코드 `not_declared`·`nested`·`unregistered`·
`heavy`·`preconditions_missing`·`entry_failed`). 집계는 `loop_consistency` 가 `trace.recording()`
으로 받아 `hand-off 시도 N건 중 성공 M건` 을 인쇄한다. 사유는 **코드**로 남긴다 — 관찰 문장은
사용자 눈에 맞춰 고쳐지지만 집계는 안 깨져야 한다. 테스트 2건이 코드를 잠갔다.

**하지 않은 것**: 전역 카운터·새 메트릭 모듈. `trace` 가 이미 있고 레코더가 없으면 emit 은
no-op 이라 운영 경로 비용이 0이다. 도구 이름(`ask_agent`·`preview_postings`)이 아니라 trace
kind 로 세므로 위임 도구가 늘어도 집계는 그대로 맞는다.

**시도 0 이면 비율을 인쇄하지 않는다.** 0/0 을 0% 로 적으면 없는 실패를 만들어낸다 —
§2-1("모른다 ≠ 아니다")의 계측판 적용이다.

**같이 정정한 것 — "위임 경로가 2개뿐이라 멀티에이전트다움이 좁다"는 문장을 리포트에서 뺐다.**
10종 중 2종만 `delegate_tool` 을 선언한 것은 §1 설계의 귀결이다. 서로 부를 수 있게 하면 엣지가
N(N−1)=90 개로 늘고 엣지마다 전제·깊이·읽기전용·동의게이트를 따져야 한다. 이 구조는 그것을
**자산 그래프 18키로 압축**했다 — A 가 B 의 결과를 원하면 B 를 부르지 않고 `preconditions` 에
자산 이름을 적고 감독자가 B 를 끼운다. 직접 위임의 정당한 조건은 하나다: **상대의 결과가
세션에 저장할 자산이 아니라 내 루프 안의 다음 판단만 바꾸는 참고값일 때.** 실사용 2경로가
정확히 그 경우다(진단 결과는 자소서의 산출물이 아니고, 추천 0건은 다음 질문만 바꾼다).

**교훈**: 경로 수를 협업의 대리 지표로 쓰면 다음 사람이 **필요 없는 위임을 추가해 점수를
올리려 한다.** 지표는 "얼마나 많이 부르나"가 아니라 "부른 것이 성공하나"여야 한다.

### D56 (07-29) 조용한 폴백을 막는 것은 **신호를 만드는 것이 아니라 신호를 남기는 것**이다
07-29 사고("Claude CLI `--tools ""` 누락으로 자기 루프 층이 통째로 죽었는데 결정론 폴백이
정상처럼 답했다")를 다시 파 보니, 신호는 처음부터 **있었다.** `llm_call_failed` 경고가
`structured.py` 에서 정확히 올라오고 있었다. 문제는 그 경고가 **아무 데도 안 남았다**는 것이다:

- 경고 객체 → `ChatResponse.warnings` 에 실려 프론트로 감. 런타임 소비자 **0곳**(grep).
- trace → 레코더가 없으면 emit 은 no-op, 있어도 **턴 끝에 소멸**.
- 로그 → `src/` 전체의 `log.warning` + `log.error` 가 **2줄**뿐이었다. LLM 실패는 그 둘이 아니었다.

즉 §2-6("폴백은 이유를 삼키지 않는다")을 **경고 객체를 만드는 것까지만** 지키고 있었다.
계약은 지켰는데 아무도 안 읽으면 삼킨 것과 결과가 같다.

**한 것 — 두 줄.**
1. `structured.py` 재시도 소진 지점(`run_structured` + 스트리밍 쌍둥이) → `log.warning`.
   LLM 호출 지점 16개가 **전부 이 파일을 지나므로** 여기 한 줄이 전부를 덮는다. 호출부를
   16곳 고치지 않는다.
2. `chat.py` 턴 끝 → 경고에 `llm_call_failed` 가 있으면 `log.error`
   *"LLM 이 죽은 채 답변이 나갔다 — 이 응답은 결정론 폴백이다"*.

②가 ①과 중복처럼 보이지만 아니다. 사고의 증상은 "호출 하나가 실패"가 아니라 **"층이 죽었는데
답변은 그럴듯했다"** 였다. **답변이 나갔다는 사실과 LLM 이 죽었다는 사실이 같은 줄에 있어야**
로그를 훑는 사람이 알아본다. 재시도로 흡수된 실패는 ②에 오지 않는다(경고가 안 달린다) —
138콜 중 1건 흡수 같은 정상 동작이 ERROR 로 시끄러워지지 않는다.

**하지 않은 것**: 알림·헬스체크 엔드포인트·경고 집계 테이블. 로그 두 줄이면 사람이 알아본다.
`llm_failed(warnings)` 헬퍼도 안 만들었다 — 소비자가 한 곳이라 인라인 한 줄이 더 짧다
(`llm_unconfigured` 는 소비자가 있어서 남아 있는 것이다).

**고치지 못한 것 — 정직하게**: `claude_code` 간헐 `llm_call_failed` 의 **원인**은 여전히 모른다.
GMS 가 현 프로바이더라 재현되지 않고, 재현 못 하는 간헐 실패를 고치는 것은 추측이다.
고친 것은 "재발하면 조용히 재발하지 않는다"까지다.

**교훈**: "폴백이 이유를 삼키지 않는다"는 규약은 **이유가 도달하는 곳까지** 요구해야 한다.
경고 객체를 만드는 것은 규약의 절반이다. 다음에 경고 코드를 새로 만들 때 물어볼 것 —
**이 코드를 실제로 읽는 사람·코드가 어디 있나?**

### D57 (07-29) `claude_code` CLI 는 **E2E 하네스 전용** — 실서비스는 LLM API 고정
프로바이더 두 개의 **역할이 다르다.** 그동안 문서가 이 둘을 "지금 어느 쪽이냐"로만 적어서,
CLI 쪽 결함을 제품 결함처럼 쫓을 여지가 있었다(D56 이 실제로 그렇게 적혀 있었다).

| 프로바이더 | **LLM API 고정** | `claude_code` CLI (무과금) |

**따라서 하지 않는 것**: CLI 간헐 실패의 원인 추적, CLI 용 구조화 출력 보강. 재현 못 하는

("3케이스 × 5회 정상"으로 보였는데 자기 루프 층이 죽어 있었다). D56 의 두 줄은 제품 장애
알림이 아니라 **하네스 신뢰성 가드**로 읽어야 한다.

**남는 진짜 위험은 다른 것이다 — baseline provenance.** 평가 수치를 CLI(sonnet)로 재고 제품은
API 로 돌면, baseline 이 제품 성능을 대표하지 않는다. 그런데 `harness.py --save` 는 모델·날짜를

CLI 파싱 취약성보다 훨씬 비싼 문제다 — 평가 리포트 §5 요구항목 2번이 그것이고, 우선순위는

### D58 (07-29) 모델명의 단일 출처는 `Settings.active_model(tier)` — provenance 와 런타임이 갈라지지 못하게

### D59 (07-29) LLM 콜·토큰은 trace 가 아니라 **별도 수집기**(`llm_usage`)로 센다
평가 리포트 §5 우선순위 1번("이것 없이는 2-1·2-3 이 영구 미확정")의 구현. 결정은 셋이다.

**① 세는 곳은 trace 가 아니다.** trace 는 창문이다 — 레코더가 없으면 no-op 이고 이벤트는 턴
끝에 사라진다. 집계는 `llm_usage.py` 의 contextvar 수집기로 돈다: `chat.handle_chat` 이 턴마다
열어 턴 끝에 **로그 한 줄**(콜·재시도·실패·토큰·노드별)로 남기고, 평가 하네스는 run 마다 열어
파일로 저장한다. 중첩되면 부모에게도 전달한다(하네스가 턴 안의 콜을 놓치지 않게 —
`TraceRecorder._parent` 와 같은 규약). 호출 지점 16개가 전부 `structured.py` 를 지나므로
기록 코드는 그 파일 한 곳이다(D56 과 같은 논리).

**② 토큰은 콜백·청크에서 걷는다.** 구조화 출력은 파싱된 객체만 돌려줘 응답의 `usage_metadata`
가 사라진다 — LangChain 콜백(`on_llm_end`)이 파서 앞 모델 단계에서 걷는다. 스트리밍은
`stream_usage=True`(ChatOpenAI)로 마지막 청크에 합계가 실린다(GMS 실측 확인). 파싱 실패로
버린 시도의 토큰도 합계에 든다 — 실제로 태웠기 때문이다.

**③ 모른다 ≠ 0.** 토큰을 안 주는 공급자(claude_code CLI)의 콜은 추정하지 않고
`unmeteredCalls` 로 따로 센다. 합계가 전체가 아닐 수 있다는 사실 자체가 숫자로 남는다.

같은 단위로: `consistency`·`loop_consistency` 에 `--save`(meta 맨 앞, D58 규약) — 궤적·hand-off
수치가 콘솔에서 사라지던 §5-2 잔여를 닫았다. `agent_loop` 상한 도달은 trace(`action="limit"`)로
남겨 `loop_consistency` 가 도달 빈도를 센다(§5-4 의 첫 항목, "빈도를 보고 다시 조정한다"의 그 빈도).

**첫 실측 (GMS gpt-4.1-mini, evals/loop_baseline.json · consistency_baseline.json)**:

### D64 (07-30) 공고 URL 수집은 posting_fetch 도구 — 호출은 플래너가 아니라 오케스트레이터

**결정**: D62 의 "첫 소비자가 수집"(ensure_posting_text 지연 수집)을 **전용 도구로 승격**한다.
`posting_fetch`(kind=tool, `AgentSpec.internal=True`)가 URL 자산을 원문으로 승격하고,
오케스트레이터가 **결정론으로** URL 자산이 미수집 상태일 때 실행 큐 맨 앞에 끼운다.
플래너 manifest 에는 넣지 않는다(internal) — 자산 상태에서 따라 나오는 필연적 단계는 LLM 이
고를 판단이 아니고, manifest 를 건드리면 플래너 어휘가 바뀌어 재측정이 필요해진다(§3-1·§3-6).

**왜 뒤집었나**: 지연 수집은 동작했지만 실측 3공고를 돌리며 한계가 보였다 —
수집 실패가 파싱 단계 안에 숨어 "왜 분석이 비었나"를 로그에서 찾아야 했고, 실패 대응
(본문 붙여넣기 요청·앞으로의 캡쳐 VLM 경로)을 붙일 자리가 없었다. 수집이 제 단계를 가지면
진행 UI 에 "공고 수집"이 보이고, 실패 표현이 도구 하나의 render 로 떨어진다.

**따라 나온 규칙 둘**:
- 관찰 규칙 ③ `posting_fetch_failed` — 수집 실패 시 공고 소비 단계를 큐에서 뺀다.
  URL 자산은 세션에 존재하므로(주소 형태) 전제 붕괴 검사(②)가 못 잡는 구멍.
- internal 도구는 병렬 그룹에 넣지 않는다 — 세션 자산을 그 자리에서 바꾸는 단계라
  병렬 사본과 섞이면 뒤 멤버가 승격 전 자산으로 따로 수집한다(이중 fetch).

`ensure_posting_text` 는 소비자 쪽 안전망으로 남는다(멱등 — fetch 가 끝냈으면 no-op).

**출처**: `agents/posting_fetch.py` · `orchestrator/chat.py`(삽입) ·
`orchestrator/observe_rules.py`(규칙 ③) · `tests/test_url_intake.py` §④.
