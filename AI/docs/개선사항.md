# 개선사항 — 범용 멀티에이전트 대비 냉정 평가 (2026-08-02)

비교 대상: 범용 멀티에이전트 프레임워크가 표준으로 제공하는 능력
(LangGraph, AutoGen, CrewAI, Claude Agent SDK 류). 평가 기준은 "프레임워크를 쓰는가"가
아니라 **그 능력이 이 시스템에 있는가**다. 근거는 전부 코드 실측(파일:라인)이며,
문서 수치는 믿지 않았다(AGENTS.md §0).

## 한 줄 결론

**설계 규율(판단의 결정론화·평가 하네스·폴백 가시화)은 범용 프레임워크 사용자 평균을
분명히 상회하고, 런타임 인프라(체크포인트·컨텍스트 압축·네이티브 tool-calling)는 하회한다.**
상회하는 축은 도메인 특화의 이득이고, 하회하는 축은 대부분 "일부러 안 한 것"과
"아직 못 한 것"이 섞여 있다 — 이 문서는 그 둘을 가른다.

## 갭과 처방 (우선순위순)

### 1. 장애 격리 부재 — ✅ 구현함 (D122)

- **문제**: `chat.py::_execute` 의 `spec.entry(sess)` 무보호. 에이전트 하나의 예외가
  턴 전체를 죽였다. 병렬(`future.result()`)에선 나머지 멤버의 완료 결과까지 소실.
  범용 프레임워크는 노드 단위 에러 정책이 표준이다.
- **처방**: `_execute` 에서 격리 — `agent_crashed` 경고 + ERROR 스택 로그 + 사용자향
  안내 한 문장 + 빈 `AgentResult` 반환. 크래시 멤버의 산출 자산이 안 생기므로 후속
  의존 단계는 기존 관찰 규칙(`drop_unrunnable`)이 정리하고, 청한 기능이 안 돌았으면
  `request_not_fulfilled` 가 턴 끝에 센다 — **격리가 은폐가 되지 않는다**(§2-6).
- **검증**: `tests/test_improvements.py::test_agent_crash_is_isolated`. 전체 621건 통과.
  플래너 재측정 불필요 — 프롬프트·manifest 무변경(§3-6 조건 미해당).

### 2. 체크포인트·턴 내 재개 부재 — 보류 (다음작업 후보)

수십 초짜리 턴(fit_analysis 복수 판정)이 중간에 죽으면 진행분이 소실된다. 단, 이
시스템의 상태 전이는 턴 끝 write-back 하나라 **부분 저장 자체가 규약 위반**이 된다 —
체크포인트를 넣으려면 D 계열 결정으로 write-back 규약부터 다시 정해야 한다.
1번(장애 격리)이 "턴이 죽는" 최빈 원인을 막았으므로 시급도가 내려갔다.
비용(세션 규약 재설계) 대비 빈도(턴 사망은 이제 예외 아닌 인프라 장애뿐)로 보류.

### 3. 네이티브 tool-calling 미사용 — 유지 (의도적)

자기 루프의 툴 선택이 provider 네이티브 tool-calling 이 아니라 구조화 출력
(Literal 스키마)이다. 범용 대비 비표준이지만 근거가 있다: ① `claude_code` CLI
provider 는 네이티브 tool-calling 을 이 호출 경로로 노출하지 않고(내장 도구를 꺼야
동작한 실측 — `claude_code_llm.py`), ② 구조화 출력은 세 provider 에서 같은 코드로
돌며, ③ 루프 궤적을 `loop_consistency` 하네스가 이미 재고 있어 갈아타면 baseline 이
전부 죽는다. **provider 를 API 직결로 바꾸는 날 재검토** — 그 전엔 바꿀 이유가 비용뿐.

### 4. 컨텍스트 요약 압축 부재 — 안 함 (YAGNI)

6턴 밖 대화는 잘린다. 그러나 지속 사실은 `user_facts`(D82)가, 공고·이력서·판정은
라이브러리(D86·D119·D121)가 턴을 넘겨 받는다 — **도메인에서 잃으면 아픈 것은 이미
전부 구조화 기억으로 빠져 있다**. 남는 손실은 "6턴 전 잡담의 뉘앙스"뿐이고, 요약
압축은 읽기 계층 LLM 콜 +1/턴 이다. 실사용에서 "아까 말했잖아" 류 실패가 수확되면
(D117 수확기) 그때 넣는다.

### 5. 구조화 출력 스트리밍 부재 — 안 함

플래너·자기 루프 결정은 통짜 도착이다. 사용자 체감 지연은 표현 계층이 지배하고
그쪽은 이미 스트리밍한다(`run_streaming_text`). 결정 JSON 을 스트리밍해도 파싱 전엔
쓸 수 없다 — 이득 0.

### 고친 것 (D124): 저확신 계획은 버리되 잃지 않는다

- **문턱 완화(숫자 내리기)는 하지 않았다.** 측정이 근거다: 현 baseline
  (`planner_baseline_promoted_agents.json`, 52케이스×3회) 의 케이스별 최저 평균 확신이
  **0.793**, fallback_rate **0.0** — 문턱 0.6 은 평가셋에서 단 한 케이스도 자르지 않는다.
  숫자를 내리면 이득은 측정 불가하고 손해(정말 모르는 추측의 실행)만 생긴다.
- 고친 것은 **이항성**이다. 저확신 계획이 조용히 폐기돼 ① 사용자는 다시 말해야 했고
  ② 실사용 저확신 구간의 크기·적중률을 셀 흔적이 0이었다(문턱 조정 근거를 영영 못 만듦).
- 이제 저확신 턴은: career_chat 이 발화에 답하고(기존 유지) + 추측 계획을 **확인 버튼**
  (`confirm_plan`)으로 제시 + `pendingConsent` 를 심어 다음 턴 동의 한마디면 동의 게이트
  없이 바로 진행 + `low_confidence_plan` 경고로 **계수**(D117 원리 — 예측하지 말고 센다).
- 검증: 유닛 2건 신규, 전체 627건 통과. 프롬프트·문턱·manifest 무변경 — 재측정(§3-6)
  조건 미해당. 실사용 계수가 쌓이면 그 데이터로 문턱을 다시 논한다.

### 고친 것 (D123): 금지표현은 문장 단위로만 버린다

- `verify_rules.drop_forbidden_sentences()` — 결정론 순수 함수. 걸린 **문장**만 제거하고
  나머지를 살린다(목록 마커 "2." 는 문장 끝으로 안 본다). 남는 게 없을 때만 기존 폴백.
- 적용 지점은 **재작성 기회가 없는 두 곳**: `career_chat`(즉시 강등이던 곳),
  `agent_loop` 상한 도달 후 마지막 답변(전량 폐기이던 곳). 자기 루프 **중**의 검증은
  기존 재작성 1회를 유지한다 — 고칠 기회가 있으면 고치게 하는 쪽이 낫다.
- 판정 원칙은 그대로다: 금지표현이 든 문장은 여전히 사용자에게 나가지 않고, 제거 사실은
  `career_chat_softened` / `loop_reply_softened` 경고로 남는다(§2-6).
- 짧은 마무리 문장 생성부(tool_render·preference_intake 등)는 **손대지 않았다** — 한두
  문장짜리 출력이라 문장 제거가 곧 전량 제거이고, 각자 맥락 맞는 결정론 폴백이 이미 있다.
- 검증: 순수 함수 2건 + career_chat 행동 2건 신규, 전체 625건 통과. 프롬프트·manifest
  무변경 — 플래너 재측정 조건(§3-6) 미해당.
