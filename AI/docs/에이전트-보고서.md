# 1부. 개요 — 무엇을 만들었나

## 1-1. 한 줄로

**역할이 다른 에이전트 7명이 각자 판단하며 일하고, 팀장이 공용 도구 4개를 직접 부리는
자율 에이전트 팀이다.** 누구를 부를지도,
무엇을 볼지도, 언제 다시 쓸지도 **실행 중에 정해진다** — 정해진 순서를 적어 둔 코드가 없다.
다만 **수치·연차·기술 항목처럼 정형으로 대조되는 것은 알고리즘이 계산하고**, 담당자들은 그
계산 결과 위에서 자유롭게 움직인다.

비유하면 **팀장이 있는 하나의 팀**이다. 팀장이 일을 배분하지만, **어떻게 할지는 각자 정한다.**

| 팀에서 | 이 서비스 | 누가 정하나 |
|---|---|---|
| **팀장** — 요청을 듣고 누가 맡을지 정한다 | **플래너** | 상황을 보고 **LLM이 고른다.** 대응표 없음 |
| **팀 규칙** — 재료가 없으면 일을 못 시작한다. 큰 일은 먼저 확인받는다 | **오케스트레이터·검증기** | **알고리즘** — 실행 가능 여부는 취향이 아니라 사실 |
| **팀원 7명** — 자료를 보고, **더 볼 게 있으면 더 보고**, 결과를 낸다 | **에이전트 7명** | **담당이 스스로.** 어떤 도구를 쓸지·무엇으로 찾을지·다시 쓸지 |
| **팀장이 직접 돌리는 공용 장비 4대** — 수치는 감으로 안 매긴다 | **도구 4개**(적합도 분석·공고 수집·추천·로드맵 조회) | 정형 대조는 **알고리즘**, 문장으로만 쓰인 요건은 LLM |
| **공유 문서** — 조사한 건 적어 둔다. 남이 한 걸 다시 하지 않는다 | **세션 자산(화이트보드)** | 담당이 자기에게 필요한 것을 집어 간다 |
| **옆자리에 물어보기** | **담당 간 위임** | 필요하다고 **담당이 판단했을 때** (읽기 전용) |
| **모르면 되묻는다** — 넘겨짚고 진행하지 않는다 | **되묻기·동의 게이트** | 담당이 청하거나, 무거운 작업 전에 시스템이 확인 |
| **최종 제출은 본인이** | **초안까지만** | 지원·제출은 사용자 — **그 도구를 만들지 않았다** |

같은 요청을 두 번 넣으면 **거쳐 가는 경로가 달라질 수 있다.** 초안이 한 번에 요건을 다 담으면
그대로 나가고, 빠진 게 있으면 스스로 고쳐 쓰고, 근거가 얇으면 옆 담당에게 묻는다 — **셋 다
실측으로 관측된 궤적**이고, 어느 것도 사람이 코드에 적어 둔 분기가 아니다(§3-0).

## 1-2. 왜 쪼갰나

"이 공고에 지원할 만한지 봐줘"를 AI 하나에게 통째로 맡기면 공고 읽기 → 이력서 읽기 → 비교 →
점수 매기기 → 로드맵 → 답변 쓰기를 한 번에 한다. 문제는 둘이다.

1. **어디서 틀렸는지 알 수 없다.** 점수가 이상해도 공고를 잘못 읽은 건지, 비교를 잘못한 건지,
   말만 그렇게 한 건지 구분이 안 된다.
2. **같은 질문에 답이 매번 다르다.** 사람의 경력을 평가하는 일에서 이건 치명적이다.

그래서 담당자로 나누고 각자에게 **딱 두 가지**만 정했다 — *무엇이 있어야 시작하나(전제)*,
*끝나면 무엇이 남나(산출물)*. 이 둘만 정하면 **순서는 저절로 나온다.** "자소서 써줘"인데 분석
결과가 없으면, 자소서 담당의 전제가 *이력서 + 분석 결과*이므로 시스템이 "먼저 적합도 분석이
필요하다"를 계산해 낸다. **순서를 사람이 코드에 적어 둔 곳이 없다.**

## 1-3. 에이전트 7명과 팀장의 도구 4개

**이 시스템은 툴 콜링이 두 층이다.** 그리고 두 층 모두 **고르는 주체가 LLM**이다.

```
바깥 층 — 오케스트레이터의 툴 콜링
   플래너(LLM)가 고른다:  에이전트 7 + 도구 4  중에서, 순서까지
        │
        └─ 안쪽 층 — 에이전트의 툴 콜링
              담당(LLM)이 고른다:  read_resume · save_draft · ask_agent … 중에서, 매 스텝
```

그래서 **"도구형 에이전트"라는 것은 없다.** 넷은 에이전트가 아니라 **팀장이 직접 쓰는 도구**다 —
에이전트가 자기 루프에서 부르는 `read_resume` 과 성격이 같고, **부르는 주체가 팀장이냐
팀원이냐**만 다르다. 가르는 기준은 하나다: **자기 이름으로 말을 하는가.**

- **에이전트**는 사용자에게 **자기가 쓴 문장으로 답한다.** 답하기까지 무엇을 볼지 자기가 정한다.
- **도구**는 **말하지 않는다.** 값만 내고, 그 값을 문장으로 만드는 것은 표현 계층이다.

### 에이전트 7명

| 에이전트 | 하는 일 | 자기 루프 | 시작 조건 | 남기는 것 |
|---|---|:---:|---|---|
| 공고 담당 | 공고 질문을 원문 근거로 받는다 | ✅ | 공고 | — |
| 이력서 담당 | 이력서 질문을 이력서 근거로 받는다 | ✅ | 이력서 | — |
| 선호 파악 | 원하는 직군·지역을 모은다 | ✅ | (없음) | 선호 |
| 면접 준비 | 한 번에 한 질문씩, 답을 점검해 꼬리 질문 | ✅ | 분석 결과 | 면접 진행 |
| 자소서 초안 | 초안을 쓰고 **스스로 점검해 고친다** | ✅ | 이력서 + 분석 결과 | 자소서 초안 |
| 진로 대화 | 고민·일반 질문. 자료가 없으면 여기가 청한다 | — | (없음) | — |
| 지원 경로 설계 | 지원 경로 2~3개를 실제 공고와 함께 세운다 | — | 분석 결과 | 지원 경로 |

### 팀장이 직접 쓰는 도구 4개

| 도구 | 하는 일 | 시작 조건 | 남기는 것 |
|---|---|---|---|
| 공고 수집 | 주소·캡쳐 이미지에서 원문을 받아 온다 | 공고 | 공고 원문 |
| **적합도 분석** | 공고와 이력서를 대조해 등급과 근거를 낸다 | 이력서 + 공고 | 분석 결과, 로드맵 |
| 공고 추천 | 실제 공고 DB에서 의미 검색으로 찾는다 | 이력서 또는 선호 | 추천 목록 |
| 로드맵 조회 | 저장된 준비 로드맵을 보여준다 | 로드맵 | — |

넷 다 **정해진 공정을 돈다** — 같은 입력이면 같은 값이다. 그래서 팀장이 직접 부르고, 결과는
화이트보드에 남아 **에이전트들이 읽어 쓴다.** 적합도 분석이 도구인 것이 이 설계의 핵심이다:
등급은 **팀원이 각자 매기는 값이 아니라 팀이 공유하는 측정값**이어야 한다.

# 2부. 원리 — 어떻게 작동하나

## 2-1. 모든 코드는 셋 중 하나다

**기준은 "그 일이 정형으로 대조되는가"** 다.

| 계층 | 하는 일 | 누가 하나 |
|---|---|---|
| **읽기** | 비정형 글 → 정형 항목 뽑기 | **LLM** — 읽어서 옮긴다. 없는 사실은 만들지 않는다 |
| **판단** | 수치·연차·기술 항목의 매칭·계산·검색·검증·분기 | **알고리즘** — 정형끼리의 대조라 계산이 더 정확하고 같은 입력에 같은 값이 나온다 |
| | 기술명 없이 **문장으로만** 쓰인 요건의 해당 여부 | **LLM** — 정형화가 안 되는 자리다. 단 **"관련 있다 / 없다" 두 값**만 내고 점수는 못 매긴다 |
| **말하기** | 정형 결정 → 자연어 | **LLM** — 표현만. 판정값을 바꿀 수 없다 |

즉 판정 안에서도 갈린다. *"Java 3년 이상", "React 사용 경험", "학사 이상"* 은 항목과 수치라서
알고리즘이 대조하고, *"이벤트 드리븐 설계 경험", "주도적으로 문제를 정의해 본 경험"* 은
대조할 항목이 없어서 **LLM이 읽고 판정한다.** 도구 선택의 기준은 취향이 아니라 **입력의 형태**다.

## 2-2. 한 번의 대화가 지나는 여섯 관문

```
사용자: "이 공고 자소서 써줘"  (+ 이력서·공고 첨부)
   │
① 첨부 저장    붙여넣은 게 이력서인지 공고인지 내용을 보고 바로잡는다
② 플래너(LLM)  누가 이 일을 해야 하나? → "자소서 초안"      ← 선택은 LLM이 한다
③ 검증기(알고리즘) 자소서는 분석이 필요하다 → "적합도 분석"을 앞에 끼운다
               무거운 일이면 말없이 시작하지 않고 **먼저 묻는다**
④ 실행         순서대로. 서로 상관없는 일은 동시에 (최대 3개)
⑤ 관찰(알고리즘) 결과를 보고 남은 계획을 고친다
⑥ 저장         이번 턴에 생긴 것만 한 번에
```

**선택은 ②의 LLM이 하고, ③⑤는 자산의 유무·전제 충족 여부라는 정형 조건이라 알고리즘이 푼다.**
처음부터 이랬던 게 아니라 ③⑤도 LLM에게 맡겨 봤고, 실측에서 값을 못 해서 옮긴 것이다 —
그 근거가 3·4부다.

# 3부. 에이전트 심층 분석

여기서 "이게 진짜 에이전트인가"에 답한다.

## 3-0. 결론부터 — **이 시스템은 자율 에이전트다.** 코드로 확인되는 것

"에이전트"라는 말이 워낙 헐거워서, **무엇이 있으면 자율인가**를 먼저 못 박고 코드를 대조한다.
기준은 하나다 — **다음에 무엇을 할지를 실행 중에 LLM이 정하는가, 아니면 사람이 미리 적어
뒀는가.**

| 자율의 조건 | 이 시스템 | 코드 근거 |
|---|:---:|---|
| **다음 행동을 실행 중에 고른다** | ✅ | 매 스텝 `action ∈ (use_tool, reply, 도구이름…)` 을 LLM이 고른다 (`agent_loop.py:240-248`) |
| **행동의 인자를 스스로 만든다** | ✅ | `arg` 는 **자유 문자열**이다. *"찾을 낱말을 쉼표로 구분해 적는다"* — **검색어를 LLM이 직접 짓는다.** 값 목록에서 고르는 게 아니다 |
| **관찰이 다음 판단을 바꾼다** | ✅ | 도구는 `(관찰 문자열, 데이터)` 를 내고 **그 관찰이 다음 스텝의 입력**이 된다. 도구 주석이 *"사실만 담고 판단·권유를 넣지 않는다"* 로 못 박혀 있다 |
| **거절당하면 고쳐서 다시 한다** | ✅ | `save_plan` 은 **커버하는 요건 ID를 대야** 기록한다 — 못 대면 **거부 사유가 관찰로 돌아오고** 에이전트가 다시 시도한다 |
| **최종 답변을 스스로 쓴다** | ✅ | `reply` 가 비면 **실패로 친다**(호출부가 폴백). 정상 경로의 문장은 **전부 LLM이 쓴 것**이다 |
| **여러 턴에 걸쳐 상태를 갖는다** | ✅ | 작업 상태(`state`)가 세션에 보존되고, 매 스텝 **최근 대화 + 사용자 지속 사실**이 함께 실린다 (`agent_loop.py` 루프 본문) |
| **필요하면 남을 부른다** | ✅ | `ask_agent` — 옆 담당을 **읽기 전용으로** 호출. 실측 발동 기록 있음 |
| **자재가 없으면 스스로 청한다** | ✅ | `request_material` — 이력서가 필요하다고 **에이전트가 판단해서** 요청 |
| **바깥 층도 툴 콜링이다** | ✅ | 플래너(LLM)가 **에이전트 7 + 도구 4 중에서 순서까지 고른다.** 대응표가 없고, 빠진 전제는 전제·산출 선언에서 계산돼 채워진다 |
| 실행 중 계획이 바뀐다 | ✅ | 관찰 규칙이 결과를 보고 **남은 계획을 교체**한다(등급이 낮으면 자소서 대신 다른 큐로) |

### 워크플로우로 오해되는 두 가지, 그리고 왜 아닌가

**① "3계층이라 판정이 고정 아닌가."**
고정된 것은 **판정 공정**이지 **에이전트의 행동**이 아니다. 둘은 다른 층이다 — 적합도 등급을
내는 계산이 결정론인 것과, 이력서 담당이 *"어떤 낱말로 원문을 뒤질까"* 를 매번 새로 정하는 것은
**동시에 성립한다.** 오히려 앞이 있어야 뒤가 가능하다: **도구가 정확해야 그 위에서 자유로울 수
있다.** 도구가 흔들리면 에이전트는 자유로운 게 아니라 **아무 말이나 하게** 된다.

> **레일이 아니라 난간이다.** 상한(스텝 5·위임 깊이 1)과 검증은 **갈 수 있는 길을 정해 준 것이
> 아니라, 떨어지면 안 되는 곳에 세워 둔 것**이다. 그 안에서 몇 스텝을 어떤 순서로 밟을지는
> 매 실행마다 다르다 — 그래서 같은 입력에도 궤적이 갈리고(§3-5), 그 갈림이 전부 정당했다.

**② "순서가 정해져 있지 않나."**
**순서를 적어 둔 코드가 없다.** 담당은 *전제*와 *산출*만 선언하고, 결측 자산의 생산자를
시스템이 역으로 찾아 앞에 끼운다. 담당을 하나 더 넣어도 **아무 파일의 if 문도 늘지 않는다** —
실제로 2종을 추가했을 때 라우팅 정확도가 **1.0을 유지**했다(§5-6-1 #8).

### 자율성의 상한은 능력 제한이 아니라 **안전 경계**다

에이전트가 못 하는 일이 셋 있다. 셋 다 *할 수 없어서*가 아니라 **의도적으로 안 준 것**이다.

| 못 하는 것 | 왜 |
|---|---|
| 세션 상태를 직접 고치기 | 오케스트레이터가 독점한다 — 그래야 여러 담당이 동시에 돌아도 판이 안 꼬인다 |
| 무거운 파이프라인을 말없이 시작하기 | 사용자에게 먼저 묻는다(동의 게이트) |
| 지원·제출·결제 | **그 도구를 만들지 않았다.** 최종 확정은 사람 |

**이 셋을 뺀 나머지는 전부 에이전트가 정한다** — 무엇을 볼지, 무엇으로 검색할지, 다시 쓸지,
누구에게 물을지, 무엇을 되물을지, 어떤 문장으로 답할지.

### 자율성이 실측으로 남은 자리

말이 아니라 궤적으로 남아 있다. 아래는 전부 **사람이 코드에 적어 두지 않은 행동**이다.

| 관측된 행동 | 무엇이 자율인가 |
|---|---|
| `find_evidence → save_draft → check_draft → save_draft → check_draft` (6스텝) | **점검에서 지적받고 스스로 다시 썼다.** 재작성 여부를 코드가 정하지 않는다 |
| `record_preference` → *"충분한가: 예"* → `request_material('이력서')` | 규칙이 계산한 분기점을 **관찰로 받고 행동을 바꿨다** |
| `find_evidence → ask_agent → save_draft → check_draft` | 근거가 얇자 **옆 담당에게 물었다** |
| `pick_material → find_evidence → record_question` / `pick_material → record_question` | 같은 케이스에서 **스텝 수가 갈린다** — 볼 게 있으면 보고, 없으면 건너뛴다 |

§3-5가 보여주듯 자소서 담당의 궤적 안정성이 **0.40**까지 내려간 적이 있는데, 세 궤적이
**전부 정당했다.** 워크플로우라면 이 숫자는 1.0이어야 한다. **흔들린다는 사실 자체가 자율성의
증거**이고, 그래서 이 시스템은 자기 루프 층에 **정답을 두지 않고 안정성과 불변식만 잰다**(§5-5-4).

## 3-1. 누가 자기 루프를 갖는가 — 기준은 하나

에이전트 7명 중에서도 **자기 루프를 도는 것은 5명**이다. 그 선을 그은 기준은 **"루프를
벌었는가"** 다.

> **LLM에게 결과를 미리 알 수 없는 선택이 있는가.**
> 없으면 루프는 스텝과 비용만 늘린다.

이 기준을 실제로 적용한 결과다(코드 기준 — 루프를 도는 쪽은 `run_agent_loop` 를 부른다).

| 담당 | 루프? | 가진 도구 | 근거 |
|---|:---:|---|---|
| 면접 준비 | ✅ | `pick_material` · `find_evidence` · `check_answer` · `record_question` | 다음 꼬리 질문은 **방금 들은 답변**에 달려 있다 |
| 자소서 초안 | ✅ | `find_evidence` · `save_draft` · `check_draft` · **위임** | 쓰고 → 점검하고 → **지적된 곳을 고친다** (실측 4스텝) |
| 선호 파악 | ✅ | `record_preference` · `request_material` · `preview_postings` · **위임** | 기록의 "충분한가", 실공고 건수를 보고 다음 질문이 갈린다 |
| **공고 담당** | ✅ | `read_posting` · `save_plan` · `search_postings` | 사용자가 무엇을 물을지 미리 모른다 — **어떤 낱말로 원문을 뒤질지가 질문마다 다르다.** 제안을 남길 땐 `save_plan` 이 **커버하는 요건 ID를 대야** 받아 준다 |
| **이력서 담당** | ✅ | `read_resume` | 같은 이유 — 정리된 항목에 없는 서술("Kafka 어디에 썼지")은 **원문을 다시 뒤져야** 나오고, 그 키워드는 발화에서 온다 |
| 진로 대화 | ❌ | (없음) | 자료가 없을 때 받는 자리. 부를 도구가 없으니 고를 것도 없다 |
| 지원 경로 설계 | ❌ | (없음) | 목표 상태·경로는 **판정 결과의 함수**다 — 룰로 정하고 문구만 LLM |
| *(팀장의 도구 4개 — 적합도 분석 · 추천 · 공고 수집 · 로드맵 조회)* | — | (해당 없음) | 애초에 에이전트가 아니다. 정해진 공정을 돌고 **재선택 여지가 정의상 없다**(§1-3) |

**공고·이력서 담당은 원래 팀장의 도구였다가 에이전트로 승격됐다**(D97). 이 보고서가 한때 *"이력서
진단은 도구를 부른 뒤 다시 정할 것이 없다"* 고 적었던 자리이고, 뒤집힌 이유를 지우지 않고
적어 둔다 — **일이 바뀐 게 아니라 받는 요청이 바뀌었다.** "정리해 줘"만 받을 때는 추출 → 조립 →
문장 1회가 맞았지만, 사용자가 **자기 이력서와 공고에 대해 묻기 시작하자** 정리된 항목에 없는
것을 답해야 했다. 그때 필요한 것이 *원문을 어떤 낱말로 뒤질까*라는 **결과를 미리 알 수 없는
선택**이고, 그래서 루프를 벌었다.

> **거절했던 근거 자체는 지금도 유효하다.** 당시 거절 사유는 *"공고 요건과 대조해 약점을 짚는
> 것은 판정이고, 그건 적합도 분석의 일"* 이었다. 승격한 뒤에도 **그 선은 그대로다** — 새로 준
> 도구는 `read_posting`·`read_resume`(원문 조회)이지 판정 도구가 아니다. 같은 판정이 두 곳에서
> 나오면 언젠가 둘이 갈린다는 규칙은 안 건드렸다.

승격의 대가와 이득도 측정으로 갈렸다: 라우팅은 **1.0을 유지**했고(어휘를 정확히 만든 변경이라
깨지지 않았다 — §5-6-1 #8), 정작 승격이 바꾼 **답의 내용**은 플래너 하네스가 원리적으로 못 봐서
**그걸 재는 지표를 새로 만들어야 했다**(§5-4 · §5-6-4).

**"에이전트를 몇 개 만들었나"가 아니라 "루프가 값을 하는 자리가 어디인가"로 설계했고, 그 자리는
요청이 바뀌면 같이 옮겨 간다.**

## 3-2. 자기 루프 해부 — 에이전트다움이 실제로 사는 곳

자기 루프를 도는 에이전트는 매 스텝 이걸 본다: **확인된 사실 + 방금 도구가 돌려준 관찰 +
최근 대화 이력.**
그리고 **실제로 할 행동**(어느 도구를 부를지)을 고른다. 스텝 상한은 5(자소서만 7).

08-04 실측 궤적이다.

```
1  find_evidence()   → "이력서에서 확인된 사실 27건"
2  save_draft(…)     → "기록했습니다. 동기 450자, 강점 364자, 보완 310자"
3  check_draft()     → "공고 요건 3/4 다룸. 빠진 것: Java·Kotlin 상용 서비스 개발"
4  save_draft(…)     → "기록했습니다(작성 2회)"          ← 스스로 고쳤다
5  check_draft()     → "공고 요건 4/4"
6  답변 작성
```

**3번에서 지적받고 4번에서 고친 것을 사람이 코드에 적어 두지 않았다.** AI가 점검 도구를
부르기로 정하고, 결과를 보고 다시 쓰기로 정했다.

### 도구가 "분기점"을 관찰로 돌려준다

선호 파악 담당의 실측이 이 동역학을 가장 잘 보여준다.

```
step1 record_preference('도메인: 커머스 / 지역: 서울')
      → 도구: "선호 차원 2개, 충분한가: 예"      ← 규칙이 계산한 분기점을 관찰로 돌려준다
step2 request_material('이력서')                  ← 그 관찰을 보고 행동을 바꿨다
step3 답변
```

**판단은 규칙이 하고, 그 결과를 보고 무엇을 할지는 LLM이 고른다.** 3계층 원칙이 루프 안에서
작동하는 모습이 이것이다.

### 근거는 도구만 준다

AI는 **도구가 주지 않은 사실을 쓸 수 없다.** 자소서의 경험·수치는 `find_evidence`가 이력서에서
찾아 준 것만 쓴다. 없는 경력을 지어내는 일이 **구조적으로** 막힌다 — "지어내지 마세요"라고
부탁하는 게 아니라 **지어낼 재료를 안 준다.**

### 이력서·공고 담당의 루프 — **자율이 "무엇을 근거로 답할까"에서 산다**

이 둘은 원래 정리만 하고 끝나는 도구였다가 에이전트로 승격됐고(§3-1), 루프가 도는 방식이
자소서·면접과 다르다. **쓰고 고치는 루프가 아니라 찾아서 확인하는 루프**다.

**루프를 벌게 한 구조적 사실 하나** — 정형 추출은 **스키마에 있는 칸만** 채운다. 그런데 사용자가
묻는 것은 칸 밖에 있을 때가 많다.

| 물음 | 정형 추출로 답할 수 있나 | 그래서 |
|---|---|---|
| "이 공고 전형 절차가 어떻게 돼?" | 스키마에 칸이 없으면 **없는 정보다** | `read_posting("전형, 면접")` — 원문에서 그 줄을 찾는다 |
| "내가 Kafka를 어디에 썼다고 썼지?" | 프로필은 섹션별 정형 추출이라 **서술이 통째로 빠진다** | `read_resume("Kafka, 성과")` |
| "이 공고 기준으로 뭘 공부할까?" | 계산으로 나오는 값이 아니다 | 요건을 근거로 제안하고 `save_plan` 으로 기록 |

**여기서 자율인 것은 "검색어"다.** 도구 설명이 지시하는 것은 형식뿐이다 —
*"찾을 낱말을 쉼표로 구분해 적는다(예: Kafka, 성과). 원문 앞부분을 그냥 보려면 빈 문자열."*
**무슨 낱말로 찾을지는 발화에서 LLM이 만든다.** 값 목록에서 고르는 게 아니라 **짓는다.**
실행 화면의 진행 표시에도 그 인자가 그대로 나온다 — `도구 read_posting(전형, 복리후생) 호출`.

#### 도구가 거절하고, 에이전트가 고쳐서 다시 낸다

공고 담당의 `save_plan` 이 이 시스템에서 **거절을 가장 많이 하는 도구**다. 제안을 기록하려면
**그 제안이 커버하는 요구사항 ID를 대야 한다**. 못 대면 관찰로 이유가 돌아온다.

```
save_plan("프로젝트: 결제 시스템 클론 / 설명: … / 커버: (없음) / 완료: …")
   → 도구: "기록 거부 1건 — '결제 시스템 클론': 커버하는 요구사항 ID 가 없습니다.
            쓸 수 있는 ID: req-1, req-2, req-3, pref-1, pref-2."
save_plan("… / 커버: req-2, pref-1 / …")
   → 도구: "제안 1건을 기록했습니다: 결제 시스템 클론(커버 req-2, pref-1)"
```

거부 사유는 네 종류이고 **전부 값 검증**이다: 요구사항을 못 읽음 / 형식 불일치 / 커버 ID 없음 /
**이 공고에 없는 ID**. 마지막이 핵심이다 — *"어느 요건을 증명하는지 못 대는 제안은 그 공고에서
나온 제안이 아니다."* 그럴듯한 프로젝트 이름을 지어내도 **기록되지 않아 답변에 실리지 않는다.**

> **이것이 §3-0의 "거절당하면 고쳐서 다시 한다"가 사는 자리다.** 사람이 검수하는 게 아니라
> **환경이 거절하고 에이전트가 적응한다.** 그리고 거절 문구가 *"쓸 수 있는 ID: …"* 로 **다음
> 행동의 재료까지 돌려준다** — 도구는 판단·권유를 넣지 않고 사실만 준다는 규약 그대로다.

#### 도구를 안 부르는 것도 판단이다

이 둘은 **0스텝이 정상인 경우가 있다.** 정형 추출이 이미 채워 준 칸으로 답할 수 있으면 원문을
다시 뒤질 이유가 없다 — 판에 `profile` 이 있으면 재추출도 하지 않는다(§4-0-2). *"쓸 도구가
없으면 바로 reply"* 가 루프 규율에 명시돼 있다. **스텝 수가 적은 것이 게으른 게 아니라, 물음에
필요한 만큼만 도는 것이다.**

#### 그리고 이 둘은 판정하지 않는다

같은 이력서·공고를 다루지만 **등급을 매기는 것은 이 둘이 아니다** — 적합도 등급은 팀장의 도구
`fit_analysis` 가 정형 대조로 낸다(§3-6). 이력서 담당이 하는 것은 *"경험으로 뒷받침되는 강점은
이것이고, 이름만 적힌 스킬은 저것"* 까지다. **같은 판정이 두 곳에서 나오면 언젠가 둘이 갈린다** —
자율성을 넓힐 때도 이 선은 넘지 않았다.

> **미측정으로 남은 것** — 자기 루프 baseline(`loop_baseline_0803.json`)의 4케이스는
> 선호 파악·면접 준비·자소서(2종)이고, **승격된 이 두 담당의 궤적은 아직 하네스에 없다.**
> 위 진행은 도구가 실제로 돌려주는 관찰 문구를 코드에서 옮긴 것이지 **N회 반복 측정치가
> 아니다.** 재는 것이 다음 순서다(§5-5-8).

## 3-3. 관찰은 두 층이었고, 하나는 걷어냈다

**이 보고서에서 가장 중요한 구조 결정이다.**

처음에는 관찰(결과를 보고 다음을 정하는 일)이 두 층에 있었다.

| | 바깥 층 (오케스트레이션 관찰) | 안쪽 층 (에이전트 자기 루프) |
|---|---|---|
| LLM이 보는 것 | **요약**(답변 300자·데이터 키·경고 코드) | 사실 + 관찰 + **대화 이력** |
| LLM이 고르는 것 | `계속/종료/호출` — **제어 신호** | **실제로 할 행동**(도구 호출) |
| 최종 답변 | 쓰지 않는다 | **LLM이 직접 쓴다** |
| 실측 | **실행을 바꾼 적 0건.** 관찰 2회가 **26.2초**를 쓰고 아무것도 안 바꿈 | 재작성 2/5회, 위임 1/5회 발동 |

바깥 층은 진짜 에이전트 루프의 **열화 모방**이었다. 요약만 보고, 행동이 아니라 제어 신호를
고르고, 답변을 쓰지 않는다. **그래서 걷어내고 규칙으로 바꿨다.** 그 대신 진짜 루프가 사는
안쪽 층을 넓혔다(채택 2종 → 3종, 스텝 상한 3 → 5, 입력에 대화 이력 추가).

### 걷어내면서 실제 결함 하나가 닫혔다

관찰 LLM이 앉아 있던 자리에서 **"지금 실행 가능한가"를 아무도 검사하지 않고 있었다.** 판정이
실패해 분석 결과가 없는데도 자소서가 그대로 돌았다. 규칙으로 바꾸자 그 검사가 명시적으로
들어갔다.

> **요약만 보고 제어 신호만 고르는 자리에 LLM을 앉히면, 검사하는 것처럼 보이지만 검사하지
> 않는다.** 재료도 권한도 없는 자리였다는 뜻이다 — 이 프로젝트가 실측으로 가장 비싸게 배운 것이다.
> 같은 LLM이 재료(사실·관찰·이력)와 실제 행동을 쥔 안쪽 루프에서는 재작성과 위임을 해냈다.

## 3-4. 담당자끼리 물어볼 수 있다 — 단 읽기만

자소서 담당이 "쓸 근거가 왜 빈약한지"를 이력서 진단 담당에게 직접 물어본다. 같은 계산을 두 번
만들지 않기 위해서다. **단 읽기만 가능하다** — 남의 답을 참고할 수는 있어도 그 결과로 시스템
상태를 바꾸지는 못한다. 상태를 바꾸는 권한은 오케스트레이터가 독점한다.

## 3-5. "안정성이 낮다"가 나쁜 것이 아닌 경우

자기 루프의 궤적 안정성을 재 봤다(3케이스 × 5회).

| 담당 | 안정성 | 해석 |
|---|---|---|
| 선호 파악 | 0.80 | — |
| 면접 준비 | 0.80 | 상한 도달 1/5 |
| **자소서 초안** | **0.40** | **세 궤적이 전부 정당하다** — 점검 통과 2회 / 점검→재작성 2회 / 위임 1회 |

**플래너와 같은 잣대로 읽으면 안 된다.** 플래너의 흔들림은 결함이지만, 자소서 담당의 흔들림은
"초안 상태에 따라 다르게 대응했다"는 뜻이다. **같은 숫자가 자리에 따라 반대 의미를 갖는다** —
지표를 지표만 보고 읽지 않는 이유다.

이 측정이 두 가지를 처음으로 **계측으로** 확인했다: 자기비판 재작성이 실제로 발동한다(2/5),
담당 간 위임이 실사용에서 발동한다(1/5).

> ⚠️ **이 표는 07-29 측정치다. 08-03 최신 baseline 에서는 안정성 1.0 / 재작성 0-5 / 위임 0-5 로
> 바뀌었다** — 발동이 줄어든 것이 이 경우엔 **개선**이고, 그 인과는 A/B 로 갈렸다(§5-5-5).
> 옛 수치를 지우지 않는 이유는 "무엇이 그것을 바꿨나"가 곧 근거이기 때문이다.

### 그 측정 직전에 치명적 결함이 하나 잡혔다

설정 하나가 빠져서 **자기 루프 층이 통째로 꺼진 채 돌고 있었다.** LLM이 자기 내장 도구를 쓰려다
실패하고 계산 폴백으로 떨어지고 있었는데, **답변이 그럴듯해서 겉으로는 정상처럼 보였다.**

> 그래서 규약에 한 줄이 들어갔다: **단위 테스트만으로는 부족하다. 실 모델로 한 번 돌린다.**
> 폴백이 그럴듯하면 결함이 안 보인다.

## 3-6. 판정 엔진 — 정형은 알고리즘, 서술형은 LLM

적합도 분석은 **10단계 공정**이고, 요건의 형태에 따라 처리기가 갈린다. 핵심인 갭 분석은
**4단 캐스케이드**이며 그중 3단이 LLM 자리다.

| 단계 | 하는 일 | 누가 | 왜 필요했나 |
|---|---|---|---|
| 1. 표기 정규화 | "ReactJS"·"리액트"·"React"를 하나로. "MySQL을 안다"면 "SQL도 안다" | 알고리즘 | 표기가 다르면 있는 경력도 없는 것이 된다 |
| 2. 근거 대조 | 기술 항목 단위 대조 — 요구 기술의 **80% 이상** 확인되면 충족 | 알고리즘 | 4개 중 3개 증명을 미충족 처리하던 문제 |
| 3. **서술형 판정** | 기술명이 없어 항목으로 못 쪼개는 요건을 **LLM이 이진 판정**, N건을 1콜로 배치 | **LLM** | 통째로 "판정 불가"가 되어 신호가 사라지던 문제 |
| 4. 연차 사다리 | 관련 직군 경력만 개월로 합산 → 인턴~리드 위치 비교 | 알고리즘 | 연차를 텍스트로만 보던 문제 |
| 종합 | 카테고리 가중 평균, **계산된 카테고리만** 정규화. 하나도 없으면 "판정불가" | 알고리즘 | 하찮은 항목 위의 만점을 막는다 |

**1·2·4·종합이 알고리즘인 이유는 입력이 이미 정형이기 때문이다** — 기술명 목록, 개월 수,
카테고리별 비율은 대조와 산술로 답이 나오고 그 답은 재현된다. **3단이 LLM인 이유도 같은
기준이다** — "이벤트 드리븐 설계 경험"은 쪼갤 항목이 없어서 문장을 읽어야 한다. 다만 그 자리에도
울타리를 쳤다: **낼 수 있는 값이 "관련 있다 / 없다" 둘뿐이고 점수는 못 매긴다.** 서술형 요건이
등급의 소수점을 흔들지 않게 하려는 것이다.

그리고 그 앞뒤로 두 개의 문지기가 있다.

- **충분성 게이트** — 판정 재료가 부실하면 판정하지 않고 **되묻는다**
- **근거 실존 검증** — 근거가 전멸한 항목은 "충족"에서 **"판정 불가"로 강등**한다

> **모델을 갈아도 등급이 같다.** `gpt-5-nano` → `gpt-5.4`로 바꿔도 결과가 동일했다.
> 등급을 만드는 산술이 정형 항목 위에서 돌고, LLM이 맡은 서술형 판정은 이진값이라
> 모델이 달라져도 합계가 흔들릴 폭이 좁기 때문이다. **이게 이 구조의 존재 이유다.**

# 4부. 왜 이 구조를 택했나 — 대안과 비교

## 4-0. 왜 멀티에이전트여야 했나 — **대안이 실패한 자리로 증명한다**

> 멀티에이전트는 유행이라서 고른 구조가 아니다. **단일 에이전트로 같은 문제를 푼 코드가 옆에
> 있었고, 그것이 어디서 어떻게 무너지는지를 같은 데이터로 재 봤기 때문에** 고른 것이다.
> 이 절의 주장은 전부 이 보고서 안의 실측을 가리킨다.

### 4-0-1. 하나의 에이전트로는 성립하지 않았던 것 일곱

| | 멀티에이전트여서 가능한 것 | 단일 에이전트에서 무슨 일이 났나 | 근거 |
|:--:|---|---|---|
| **1** | **어디서 틀렸는지 지목할 수 있다** | 점수가 이상해도 공고를 잘못 읽은 건지, 대조를 잘못한 건지, 말만 그렇게 한 건지 구분이 안 된다 | §1-2 · §5-6 대장 31건이 **층을 지목**해서 고쳐졌다 |
| **2** | **책임이 갈려 있어 판정이 재현된다** | 판정 재료가 **한 콜의 결과에 실려 있으면** 정규화·연차·게이트가 놓일 자리가 없다 — 6프로필 중 5건이 기대와 어긋났다 | §4-4 |
| **3** | **순서를 사람이 적지 않는다** | 흐름을 대응표로 적으면 상황마다 표가 커진다 | §7-2 — 전제·산출 선언에서 순서가 **계산돼 나온다** |
| **4** | **독립 작업을 동시에 돌릴 수 있다** | 도구 호출을 for 루프로 순차 처리 | §5-3 — 47.8~48.0초 → **13.3~37.6초** |
| **5** | **줄 도구를 담당별로 다르게 준다** | 모든 도구가 한 컨텍스트에 놓인다 | §3-2 "근거는 도구만 준다" · 제출·결제 도구는 **만들지 않았다** |
| **6** | **무거운 일 앞에서 멈춰 물을 수 있다** | 멈출 경계 자체가 없다 | §5-6-1 #6 — 동의 게이트, `ask_accuracy` **1.0** |
| **7** | **층마다 따로 잴 수 있다** | 실패가 전부 "답이 이상하다" 한 줄로 뭉개진다 | §5-5 — 계획/풀턴/자기루프/판정 **네 하네스** |

**7번이 나머지 여섯을 떠받친다.** 이 보고서가 수치로 말할 수 있는 것 전부 — 정확도 0.85 → 1.0,
위반 5 → 0, 26.2초 절감 — 은 **잴 수 있는 경계가 있었기 때문에** 나왔다. 단일 루프에서는
"프롬프트를 고쳤더니 느낌이 나아졌다" 이상을 말할 방법이 없다. **구조를 나눈 것의 첫 배당은
성능이 아니라 관측 가능성이었고, 성능은 그 다음에 따라왔다.**

### 4-0-2. 담당끼리 말을 걸지 않는다 — **화이트보드(공유 상태) 아키텍처**

에이전트를 여럿 두면 보통 **에이전트끼리 서로를 직접 부르며** 메시지가 오간다(Point-to-Point).
이 방식의 문제는 규모다 — 담당이 N명이면 오갈 수 있는 통로가 최대 **N(N−1)** 개로 늘고,
**통로마다** "이건 보내도 되나 / 이 순서가 맞나 / 상대가 죽으면 어쩌나"를 따져야 한다.

이 시스템은 통로를 만드는 대신 **가운데에 판 하나**를 놓았다. 담당은 서로에게 말하지 않고
**화이트보드(세션 자산)에 적고, 필요한 담당이 거기서 집어 간다.**

| | Point-to-Point | **이 시스템 (화이트보드)** |
|---|---|---|
| 맥락 전달 | 담당 A → 담당 B 메시지 | 자산에 적고, 필요한 담당이 **전제**로 집는다 |
| 늘어나는 것 | 통로 N(N−1) | **자산 키**(현재 25종) — 담당이 늘어도 통로는 안 는다 |
| A가 B의 결과를 원할 때 | B를 호출 | **B를 부르지 않고 `preconditions` 에 자산 이름을 적는다** |
| 직접 위임 | 자유롭게 | **읽기 전용 · 깊이 1 · 화이트리스트 · 무거운 일 금지** (예외적 통로) |
| 상태 변경 | 각자 | **오케스트레이터 독점** (`sessionUpdates`) |

이 패턴이 주는 것 셋이 이 저장소에서 각각 무엇으로 나타나는지가 핵심이다.

| 화이트보드 패턴의 이득 | 이 시스템에서의 실체 |
|---|---|
| **낮은 결합도** — A는 B가 누구인지, 언제 도는지 알 필요가 없다 | 담당은 *전제*와 *산출*만 선언한다. 결측 자산의 **생산자를 시스템이 역으로 찾아 앞에 끼운다** — 대응표 하드코딩이 없고, 그래서 담당 2종을 추가했을 때(48 → 52케이스) 라우팅이 **1.0을 유지**했다(§5-6-1 #8) |
| **관찰 가능성·개입 지점** | 판 하나만 열면 지금 어디까지 왔는지 보인다. 진행 타임라인·화자 배지·실시간 스트리밍이 그 판을 그대로 비추고, **동의 게이트**가 사람이 끼어드는 자리다(무거운 일 앞에서 멈춰 묻는다 — `ask_accuracy` **1.0**) |
| **상태 변화가 트리거** | 못 한 요청을 3턴 기억했다가 **자산이 도착하는 턴에 자동 완수**(`pendingRequest`) · 이력서가 갱신되면 그로부터 파생된 자산을 **무효화** · 같은 입력이면 재판정하지 않는다(`analysis_key` 지문) |
| **같은 것을 두 번 만들지 않는다** | 담당이 일을 시작하기 전에 **판부터 본다.** 이력서 질문이 들어와도 `profile` 이 있으면 재추출하지 않고, 공고는 라이브러리·요약 캐시를 먼저 뒤지며, 면접·자소서는 `analysis` 를 **읽어 쓰지 판정을 다시 하지 않는다.** 같은 판정이 두 곳에서 나면 언젠가 둘이 갈리므로, 이건 성능 이득이자 **일관성 장치**다 |

**위임을 좁게 열어 둔 판단도 실측이 뒷받침했다.** 위임 발동이 많던 시절(4/5)의 정체는 자율성이
아니라 **근거 빈곤의 보상 행동**이었고, 재료를 넓히자 0/5로 사라지면서 **불변식 위반 5 → 0,
콜 −27%** 가 같이 왔다(§5-6-2). 통로를 넓게 열어 뒀다면 이 결함은 **"활발한 협업"으로 보였을
것이다.**

### 4-0-3. 옛 블랙보드와 무엇이 같고 무엇이 다른가

공유 상태 위에서 여러 전문가 모듈이 일하는 구조 자체는 오래된 **블랙보드 패턴**이다. LLM
시대에 다시 표준이 된 이유는 **판에 올라가는 것과 판 위에서 일하는 주체가 바뀌었기 때문**이다.

| 구분 | 과거 블랙보드 | 현대 LLM 화이트보드 | **이 시스템** |
|---|---|---|---|
| 저장 데이터 | 정형 규칙·심볼릭 데이터 | 프롬프트 컨텍스트·JSON 스키마·대화 이력 | **자산 25키**(원천·판정 결과·라이브러리·대화 이력·게이트 상태) |
| 일하는 주체 | 하드코딩된 규칙 모듈 | 역할과 도구를 받은 LLM 에이전트 | **에이전트 7명**(각자 다른 도구) + **팀장의 도구 4개** |
| 상태 제어 | 중앙 제어기 | Graph State · 라우터 에이전트 | **오케스트레이터 독점 + 결정론 검증기** |

LangGraph·AutoGen·CrewAI 계열이 이름만 다를 뿐 전부 이 변형이다. **이 저장소가 프레임워크를
따라간 것이 아니라, 같은 문제를 풀면 같은 형태로 수렴한다**는 편이 정확하다 — 실제로 이 구조는
"에이전트끼리 부르게 하면 엣지마다 가드를 따져야 한다"는 계산에서 나왔지 패턴 이름에서 나오지
않았다.

### 4-0-4. 이 패턴의 알려진 함정 둘 — 어떻게 막고 있나

화이트보드를 **"모든 출력을 계속 이어 붙이는 텍스트 판"** 으로 만들면 두 가지가 반드시 터진다.
이 저장소도 그 자리를 밟았고, 막은 방식이 코드에 남아 있다.

**① 컨텍스트 폭발** — 판이 커지면 토큰이 급증하고 모델이 가운데를 흘린다(Lost in the Middle).

| 방어 | 실제 값 |
|---|---|
| 대화 이력 상한 | `HISTORY_MAX_ITEMS = 30` — 오래된 턴부터 버린다 |
| 프롬프트에 넣는 창 | **최근 6개 · 항목당 300자**. 단 **답변만 4배**로 준다 — 사용자 발화는 대개 300자 밑이라 온전한데 답변(로드맵·공고 정리)은 400~800자라 앞머리만 남아 *"내 말은 기억하는데 자기 말은 못 기억"* 하는 증상이 났다 |
| 입력 절단 | 공고 원문 **16,000자** 상한(자격·우대 보존) + 절단 경고 |
| 라이브러리 상한 | 공고·이력서 각 **5건**, 미지원 요청 **20건** |
| 재계산 회피 | `analysis_key` 지문이 같으면 **판정을 다시 하지 않는다**(판정은 공고 × 이력서의 함수다) |

**② 경합·오염** — 여러 담당이 동시에 판을 고치면 결과가 꼬이거나 서로를 덮어쓴다.

| 방어 | 실제 규약 |
|---|---|
| 쓰기 창구 단일화 | 담당은 판을 **직접 못 고친다.** `sessionUpdates` 로 올리고 **턴 끝에 한 번** 반영 |
| 병렬 중 오염 | 병렬 담당에게는 **세션 사본**을 주고, **큐 순서로 병합**한다 |
| 키 화이트리스트 | 목록 밖의 키는 **저장하지 않는다.** `produces ⊆ ASSET_KEYS` 를 테스트가 강제 — 이 테스트가 없던 시절 `interview` 키 누락으로 면접 턴이 실서버에서 매번 실패했다 |
| 덮어쓰기 사고 | 이력서 슬롯 하나를 세 원천(붙여넣기·업로드·저장소)이 서로 덮던 문제를 **라이브러리 자산**으로 바꿔 닫았다 |
| 파생 자산 무효화 | 이력서가 바뀌면 그로부터 나온 프로필·분석을 **버린다** |

### 4-0-5. "스마트 화이트보드" 기준으로 지금 어디까지 왔나

최근의 발전 방향(구조화된 상태 / 메모리 압축 / 외부 메모리 연동)에 비추면 이 저장소의 좌표는
이렇다. **없는 칸을 있는 것처럼 적지 않는다.**

| 항목 | 상태 | 근거 |
|---|:---:|---|
| **구조화된 상태**(텍스트가 아닌 스키마) | ✅ | 자산 25키 각각이 타입을 가진 dict, 화이트리스트 검증. 백엔드와도 **블롭을 그대로 주고받는다** — 스키마를 번역하던 3개를 지웠다(*번역이 없으면 번역 버그도 없다*) |
| **필요한 담당만 필요한 속성을 읽는다** | ✅ | 담당은 **자기가 선언한 키를 지목해 집어 간다** — 이력서 담당은 `profile` 이 판에 있으면 **다시 추출하지 않고**(`resume_diagnosis.py:235`), 공고 담당은 `posting_library`·`posting_summary` 를 먼저 뒤진 뒤 없을 때만 파싱하며(`posting_analysis.py:51·98`), 면접·자소서 담당은 `analysis` 를 **읽어 쓰지 판정을 다시 하지 않는다**(`interview_prep.py:44` · `coverletter_draft.py:580`). 위임은 **읽기 전용** |
| **슬라이딩 윈도우** | ✅ | 이력 30항 보관 / 프롬프트에는 최근 6항·비대칭 절단 |
| **외부 메모리 연동(RAG)** | ✅ | 공고 **6,120건**은 벡터 검색 쪽에 두고, 판에는 **정리 결과와 참조만** 올린다 |
| **경량 LLM으로 중간 과정 압축** | ✅ | 매 턴 **경량 티어 1콜**이 발화에서 *이후에도 유효한 사실*만 뽑아 판에 누적한다(`user_facts`, 상한 20). 원문을 이어 붙이지 않고, **작업과 거리가 먼 것은 애초에 안 올린다** — 이번 턴에만 유효한 지시·인사말은 제외하고, **600자 넘는 발화는 붙여넣은 자료로 보고 건너뛴다** |

**압축 방식이 흔한 형태와 다르다.** 보통은 *쌓인 대화를 나중에 요약*하는데(append → summarize),
이 시스템은 **들어오는 순간 스키마로 승격**한다(extract → schema). 차이는 셋이다.

- 판에 올라가는 것이 **자유 텍스트가 아니라 짧은 사실 문장 목록**이라, 읽는 쪽이 파싱할 필요가
  없고 요약이 요약을 낳으며 뭉개지지 않는다.
- **압축 시점이 일정하다.** 판이 커진 다음 손대는 게 아니라 애초에 안 커진다.
- **뽑는 층이 판정을 안 한다.** 읽기 계층(§2-1) 그대로 — *"발화에 실제로 있는 것만, 추측·확장
  금지"*. 그리고 이 콜이 실패하거나 느리면 **기존 목록을 그대로 두고 턴을 진행한다**(타임아웃
  경고만 남긴다) — 압축은 강화(enrichment)이지 경로가 아니다.

이렇게 승격된 사실은 한 담당의 것이 아니다 — **플래너의 라우팅 근거**로도, 진로 대화의
컨텍스트로도, 자기 루프의 입력으로도 같은 자산이 쓰인다. *"9월까지 취업하고 싶다", "야간 근무는
어렵다"* 가 한 턴 지나면 사라져 담당들이 매번 백지에서 시작하던 것을 이 자산이 닫았다.

> **정리하면** — 화이트보드는 낡은 패턴이 아니라 **"구조화된 공유 상태"** 라는 형태로 다시
> 표준이 됐고, 이 시스템은 그 표준의 항목(스키마화 · 쓰기 창구 단일화 · 윈도우 · 외부 메모리 ·
> **경량 LLM 압축**)을 **전부 갖췄다.** 남은 것은 항목이 아니라 **증명**이다 — 이 장치들이 판을
> 실제로 가볍게 유지하는지는 토큰을 재야 말할 수 있고, 지금 프로바이더에서는 그 숫자가
> 없다(§5-5-7). **장치는 다 있고, 효과는 아직 미측정이다.**

### 4-0-6. 예상되는 반론 셋 — 실측으로 답한다

**① "모델이 좋아지면 하나로 다 되지 않나."**
같은 데이터로 재 봤다. 판정 재료를 한 콜에 몰아 준 구조는 **모델 문제가 아니라 재료 문제**로
무너졌다 — 자격 조건을 기술 요건으로 잘못 뽑아 `[학력무관, 경력무관]` 둘로 만점이 나왔고,
진짜 기술은 "판정 불가"로 분모에서 빠졌다(§4-4). 반대로 이 구조에서는 `gpt-5-nano` → `gpt-5.4`
로 갈아도 **등급이 같다**(§3-6). 모델을 올려서 얻는 것보다, **무엇을 주는가**를 고쳐서 얻은 것이
훨씬 컸다는 게 §5-6-8의 순위다.

**② "담당이 많으면 느리고 비싸지 않나."**
방향은 맞고 크기는 재 봤다. 턴당 **2.8콜**이고, 판정 계층은 **~0초**(정형 대조는 산술, 서술형은
N건 1콜 배치 + 캐시)다. 오히려 나눠 놓았기 때문에 **독립 담당을 병렬로 돌려 10~35초를 줄였고**,
값을 못 하던 관찰 층을 **26.2초째 잘라낼 수 있었다** — 한 덩어리였다면 그 26.2초가 어디서
쓰이는지 보이지도 않았다.

**③ "결국 사람이 순서를 정해 준 워크플로우 아닌가."**
아니다. **순서를 적어 둔 코드가 없다.** 담당마다 *전제*와 *산출*만 선언하고, 실행 순서는 그
선언에서 계산된다 — "자소서 써줘"에 분석이 없으면 시스템이 분석을 앞에 끼운다(§1-2). 그리고
**누구를 부를지는 LLM이 고르고**(52상황 정확도 1.0), 담당 안쪽에서는 **다음 도구를 LLM이
직접 고른다**(§3-2 — 점검받고 스스로 고쳐 쓰는 궤적이 실측으로 남아 있다). 고정된 것은
*실행 가능 여부*뿐이고, 그건 취향이 아니라 사실 문제다.

### 4-0-7. 그래서 당위성은 한 문장이다

> **문제가 이미 나뉘어 있었다.** 공고를 읽는 일, 이력서를 읽는 일, 둘을 대조해 등급을 내는 일,
> 그 결과로 글을 쓰는 일은 **입력도 다르고 실패 방식도 다르고 잘했다의 정의도 다르다.**
> 하나의 루프에 넣으면 그 차이가 사라지는 게 아니라 **보이지 않게 될 뿐**이라는 것을 초기
> 시제품 측정이 먼저 보여 줬다(6프로필 중 5건이 기대와 어긋났고, 어디서 어긋났는지는 한 콜
> 안에서 구분되지 않았다). 멀티에이전트는 이 시스템에 **얹은 구조가 아니라, 문제의 형태를
> 그대로 옮긴 구조**다.

단 이 구조는 공짜가 아니고, 그 대가는 §4-5에 숨기지 않고 적었다.

## 4-1. "에이전트냐 워크플로우냐"는 잘못된 질문이었다

프로젝트 초기에 이 논쟁을 했고, **질문 자체가 틀렸다**는 결론을 냈다.

둘은 배타적 선택지가 아니라 **계층마다 답이 다른 문제**다.

| 계층 | 답 | 왜 |
|---|---|---|
| 사용자 여정(어느 담당을 부르나) | **선택은 LLM, 실행 가능 여부는 코드** | 상황이 무한하니 표로 못 적는다. 하지만 실행 가능 여부는 사실 문제다 |
| 담당 안쪽(도구를 어떻게 쓰나) | **에이전트(자기 루프)** | 결과를 보고 다시 정할 것이 있다 |
| 판정 | **워크플로우(고정 공정)** — 정형 항목은 알고리즘, 서술형 요건은 LLM 이진 판정 | 같은 입력에 같은 값이 나와야 한다 |

**"LLM은 읽고·서술형을 판정하고·말한다. 수치와 항목의 대조는 알고리즘이 하고, 선택의 실행
가능 여부도 코드가 확정한다."**

## 4-2. 팀 시제품(단일 ReAct 루프)과 15개 축으로 비교했다

같은 문제를 훨씬 작은 구조(LLM ⇄ 도구 단일 루프, 210줄)로 푼 시제품이 있어서 **축별로 나란히
놓고 비교**했다. 결과를 그대로 옮긴다.

| 시제품이 앞선 축 | 본체가 앞선 축 |
|---|---|
| 읽기·변경 비용(줄 수) | 판정 정확도 |
| 호출 수·비용 구조 | uncertain 처리의 **집행** 장치 |
| ~~루프 실효성~~ → 재정의 후 처리 | 환각 방어 층수 |
| ~~결정적 강제 분기~~ → 이후 반영 | 판정/표현 분리 |
| ~~재현성 측정~~ → 이후 반영 | 다중 턴 상태·세션 영속 |
| ~~문서 단일 출처~~ → 이후 반영 | 검색·추천 품질 / 실패 처리·관측성 / 회귀 테스트 / 통합 표면 |

**비교의 진짜 값은 등급표가 아니었다.** 시제품이 앞선 6축 중 4축을 그 주에 **본체에 반영했다** —
작은 시스템이 옳게 한 것을 이름 붙여 놓으면 큰 시스템에서 무엇이 빠졌는지 바로 보인다.
관찰 층을 규칙으로 바꾼 것(§3-3)도 이 비교에서 나왔다. 규모가 다른 두 구조를 같은 표에 놓은
이유는 우열을 매기기 위해서가 아니라 **서로에게 없는 것을 찾기 위해서**다.

## 4-3. 그런데 왜 전면 ReAct로 가지 않았나

시제품의 루프는 210줄로 실효가 확인됐다 — **작동하는 설계였다.** 그대로 따라가지 않은 이유는
성능이 아니라 조건이 달라서다.

**① 비교 조건이 다르다.** 시제품은 **도구 3개 중에서** 고른다. 본체의 바깥 층은 **에이전트 7 +
도구 4 × 세션 자산 25종 × 여러 턴의 맥락**에서 고른다. 선택지가 3개면 매 스텝 히스토리 전체를 다시 넣는 게
싸지만, **선택지 11개·수십 턴에서는 그 방식이 그대로 확장되지 않는다.**

**② 자율성의 병목은 루프 구조가 아니라 도구 목록이었다.** 이게 핵심이다. 바깥 루프를 완전
자율(ReAct)로 바꿔 봐야 **AI가 고를 수 있는 것이 늘지 않는다.** 실제로 자율성이 늘어난 것은
루프를 바꿨을 때가 아니라 **도구를 하나 더 줬을 때**였다(선호 파악에 "지금 조건으로 공고가 몇
건인가"를 물어보는 도구를 준 순간 되묻기 행동이 생겼다).

그래서 **"바깥 오케스트레이터를 ReAct로 바꾸지 않는다"를 명시적 결정으로 남겼다**(D136).
구조를 바꿔도 이득이 없다는 근거와 함께 — 다음 사람이 같은 것을 다시 시도하지 않도록.

## 4-4. 왜 수치·항목 대조를 LLM 한 콜에 맡기지 않나 — 가장 강한 증거

**이 구조의 설계 근거는 시제품이 남긴 측정 기록에서 나왔다.** 판정 재료를 한 콜에 모아 주는
방식으로 6개 프로필을 돌려 본 결과이고, 이 데이터가 있었기 때문에 무엇을 만들어야 하는지가
분명해졌다.

| 프로필 | 기대 | 관측 |
|---|---|---|
| 백엔드 | 상 | 중 |
| 부트캠프 BE | 중 | 중(회차마다 갈림) |
| 데이터 | 중 | 하 |
| 안드로이드 | 중/하 | **상 (만점)** |
| 정보보안 | 하 | **상** |
| 프론트 | — | 상 (기대와 일치) |

**기대와 어긋난 것이 5건**이고, 그중 만점이 나온 두 건의 기제가 로그에 그대로 남아 있다 —
충족으로 집계된 필수 요건이 `[학력무관, 경력무관]` **둘뿐**이고 부족 0건이라 분모가 그 둘로
좁아져 만점이 됐다. 자격 조건이 기술 요건 자리로 들어갔기 때문이다. 동시에 실제 기술
(Linux·자료구조·알고리즘)은 "판정 불가"로 빠져 분모에서 제외돼 신호가 사라졌다.

**원인은 구현이 아니라 구조다.** 정형으로 대조할 수 있는 것까지 한 콜의 결과에 실려 있었고,
표기 정규화·함의 관계·카테고리 구분·연차 사다리가 놓일 자리가 없었으며, 무엇보다 *"판정 재료가
부실하다"* 를 감지하는 게이트가 아직 없었다. **LLM의 한계가 아니라 배치의 문제다** — 기술명
목록과 개월 수를 대조하는 일에는 산술이 맞는 도구인데 그 자리를 안 만든 상태였다.

§3-6의 4단 캐스케이드와 두 문지기는 **이 관측 하나하나를 겨냥해서** 만든 것이고, 그 안에서
LLM은 자기가 잘하는 자리(3단 서술형 판정)를 그대로 맡고 있다. **먼저 재 본 쪽이 없었다면 이
설계도 없었다.**

> 같은 기록에 재현성 관측도 함께 남아 있다 — 같은 입력에 등급이 갈렸고, *"'결정론 우선'
> 하이브리드에서 결정론이 실제로는 성립하지 않았다"* 는 것이 그 측정의 결론이었다. 지금 구조가
> 모델을 갈아도 등급이 같은 이유(§3-6)는 그 결론을 그대로 받아 만든 결과다.

# 5부. 성능을 어떻게 개선했나

## 5-1. 플래너 정확도 — 0.85에서 1.0까지

"누구를 부를지 고르는 정확도"의 실제 궤적이다. **각 단계에서 무엇을 했는지가 핵심이다.**

| 시점 | 무엇을 했나 | 정확도 | 안정성 | 일관되게 틀림 |
|---|---|---|---|---|
| 기준선 | 46케이스 × 3회 첫 측정 | 0.8478 | — | 3건 |
| ① | **평가셋 재캘리브레이션** — 근거 있는 2건만 갱신, 정책 위반은 갱신 거부 | 0.8985 | — | 1건 |
| ② | **어휘 좁히기** — 담당 설명의 정의를 좁힘(규칙 추가 아님) | **0.9783** | 0.9855 | **0건** |
| ③ | 프롬프트 규칙 5개 → 우선순위 사다리 1개로 합침 | +0.022 | +0.015 | — |
| ④ | 기능 추가(못 하는 요청 신고) — 케이스 46 → 48 | 0.9653 ▼ | 0.9861 | 1건 |
| ⑤ | 라우팅 모델을 최상급 티어로 | 0.9861 | 0.9861 | 0건 |

- **④에서 일부러 내렸다.** "못 하는 요청을 신고하는" 기능을 넣으면서 정확도가 0.9783 → 0.9653으로
  내려갔다. **비용과 이득을 알고 맞바꾼 것**이고, 그 기능의 정확도는 1.0이었다. 기록을 지우지
  않는다 — 어떤 변경이 무엇을 흔들었는지가 다음 판단의 근거다.
- **③의 폴백률 −40%** 는 정확도보다 중요할 수 있다. 폴백은 "플래너가 답을 못 내서 기본 담당이
  받은" 경우다.
- ②는 **GMS 기준선(0.9275)을 넘은 지점**이다. 모델을 바꿔서가 아니라 어휘를 좁혀서 넘었다.

## 5-2. 무엇이 올렸고 무엇이 내렸나 — A/B 실측

**같은 문제, 같은 모델, 두 가지 처방**을 실제로 재 봤다(2026-07-29).

| 처방 | 정확도 | 부작용 |
|---|---|---|
| 판단 원칙에 **규칙을 추가**한다 | **−0.022** | 무관한 케이스 **4건 파손** |
| 선택지의 **정의를 좁힌다** | **+0.058** | 파손 **0** |

**모델이 못 고르는 이유는 규칙을 몰라서가 아니라 선택지의 뜻이 넓어서였다.**

되돌린 시도도 남아 있다. 특정 케이스를 고치려고 프롬프트에 규칙을 넣었다가 **총계가 0.9275 →
0.9058로 내려가** 되돌렸다. 그 케이스는 지금도 "알려진 실패"로 표기해 두었다 — **고치지 못한
것을 고친 척하지 않는다.**

여기서 나온 작업 규칙 셋:

1. **한 번에 하나만 고치고 매번 잰다** — 좁히는 변경과 넓히는 변경을 같은 커밋에 넣으면 총계가
   서로를 가린다(실측: 총계는 올랐는데 케이스별로 6건이 깨져 있었다)
2. **총계가 아니라 케이스별로 본다** — **일관되게 틀림**(명세 결함)과 **흔들림**(온도·경계 애매)은
   처방이 다르다
3. **프롬프트를 고치면 평가셋을 같은 커밋에서 재측정한다** — 안 그러면 기준선이 조용히 죽는다
   (실측: 저장 5시간 뒤 프롬프트가 바뀌었는데 아무도 몰랐다)

## 5-4. 측정 방법 자체를 세 번 고쳤다

성능을 개선하려면 먼저 **제대로 재야 한다**. 그 과정에서 측정 방법을 세 번 고쳤다.

**① 지표를 갈랐다.** "일관성 k/N" 하나는 두 가지를 섞는다. 0/3이 *일관되게 틀린 것*인지
*무작위로 틀린 것*인지 구분되지 않는데 **원인과 처방이 다르다.** 같은 데이터에서 공짜로 갈라
냈다 — **정확도**(기대와 맞은 비율)와 **안정성**(최빈 결과의 비율).

**② 시험이 시험 구실을 하는지 검증했다.** 새 평가 케이스가 **고치기 전에도 통과**한다면 그
문제는 개선을 재는 게 아니라 결과를 베끼는 것이다. 그래서 **고치기 전 상태로 되돌려 같은 문제를
다시 풀렸다.** 처음 만든 4문제는 전부 "전에도 맞히는" 문제여서 실제 실패 사례에 맞춰 다시
만들었다.

**③ 통계를 한 번 틀렸다가 고쳤다.** 같은 데이터가 **범위(최대−최소)로는 "악화", 표준오차로는
"절반 개선"** 으로 읽혔다. 범위는 표본이 늘면 자동으로 커진다. **추정치를 판단 기준으로 쓸 때는
그 추정치의 오차부터 본다**로 규칙을 바꿨다.

### 답변 "내용"을 재는 지표도 만들었다

플래너 시험은 **누구를 부르는가**만 잰다. 담당 승격이 실제로 바꾼 것은 **답의 내용**인데 그건
원리적으로 못 본다. 그래서 지표를 새로 만들었다 — *"서로 다른 공고에 같은 답이 나오면 감점"*.

만들면서 **기준선을 한 번 틀렸다.** 처음엔 공고 전문끼리 비교했는데 도메인이 다른 공고끼리도
유사도가 0.615로 깔렸다. 원인은 모든 공고가 "채용/담당업무/자격요건/우대사항/전형절차" 뼈대를
공유한다는 것이었다. 부풀린 기준선을 빼자 지표가 **관대(−0.024) → 엄격(+0.051)** 으로 뒤집혔다.

그리고 지표를 **두 개** 뒀다. 하나만 쓰면 **표현만 바꿔서 점수를 올릴 수 있기 때문**이다
(실제로 그 취약점이 측정에 나왔다). 두 번째 지표는 "답변이 언급한 기술 중 그 공고에 없는 것의
비율"이다.

### 5-5-1. 지금의 정본 baseline 네 개

### 5-5-2. ① 계획 층 — 1.0 은 좋은 소식이자 **지표의 수명이 끝났다는 소식**

```
cases 52 · runs 3 · sequence_accuracy 1.0 · ask_accuracy 1.0 · mean_stability 1.0
stable_correct 52 / stable_wrong 0 / unstable 0 · blocked_accuracy 1.0
fallback_rate 0.0192 · mean_confidence 0.901
```

52케이스가 **전부** `stable-correct` 다. 이 데이터셋으로는 **더 이상 개선도 회귀도 잴 수 없다** —
어떤 변경을 넣어도 위쪽으로 움직일 칸이 없고, 아래쪽으로 한 칸만 움직여도 그게 유일한 신호다.
포화된 지표는 안심의 근거가 아니라 **교체 시점의 신호**다.

그래서 지금 판별력이 남아 있는 축은 **정확도가 아니라 부가 지표**다.

| 축 | 08-01 (`promoted_agents`) | 08-03 (`rec_targets`) | 읽는 법 |
|---|---|---|---|
| 정확도 | 1.0 | 1.0 | 포화 — 판별력 없음 |
| `fallback_rate` | **0.0** | **0.0192** | 156회 중 3회가 대화로 후퇴 |
| `mean_confidence` | 0.901 | 0.901 | 확신 자체는 안 죽었다 |

정확도가 같은데 폴백만 늘었다 = **플래너가 맞히긴 하는데 몇 번은 자신 없어 한다.** §5-2에서
`fallback_rate` 가 정확도보다 먼저 프롬프트 결함을 알려 준 적이 있으므로, 다음 프롬프트 변경
때 **가장 먼저 볼 값은 이 0.0192** 다.

> **대조군이 남아 있다는 것이 이 폴더의 값이다.** `planner_ab_confidence_default.json` 은 확신도
> 기본값을 잘못 잡았을 때의 기록이다 — 정확도 **0.3913**, 폴백률 **0.5652**, `mean_confidence`
> 0.393. 같은 코드가 **확신 하나 때문에** 어디까지 무너지는지가 파일로 남아 있다. 지우지 않는다.

| 시나리오 | 07-31 `..._multiturn` | 08-04 `..._resume_detail` | **08-04 `..._gate_predicate`** |

| S5 동의게이트 | `(없음)` 3/3 ✅ | `posting_analysis>resume_diagnosis` 3/3 ❌ | 같은 궤적 3/3 **✅** |
| S9 턴1 | `(없음)` 3/3 ✅ | 동일하게 3/3 ❌ | 3/3 **✅** (턴2 `fit_analysis>coverletter_draft`) |
| 이탈 합계 | 0 | **6** | **0** |
| 시나리오당 콜 | 4.63 | 5.85 | 5.6 |

**① 3/3 일관 실패였으므로 flaky 가 아니라 `stable-wrong` 성격이었다.** 그런데 궤적을 보면 원인이
"게이트가 뚫렸다"가 아니었다 — 뚫렸다면 턴1에 `fit_analysis` 가 돌았어야 하는데, 돈 것은
**경량 생산자 둘**(공고 정리·이력서 정리)이고 무거운 `fit_analysis` 는 S9 **턴2에서야** 돌았다.
**게이트는 지켰고, 깨진 것은 판정 술어**였다.

**② 귀속: 정책 변경이다(D158).** 게이트가 걸리면 `Dispatch(())` 로 **계획 전체**를 막고 있어서,
공고를 붙인 턴에 판정이 게이트에 걸리면 **공고 정리까지 사라지고 질문만** 나갔다. 그래서 게이트
턴에도 **이번 턴 제출물의 정리 단계만** 돌고 질문이 뒤에 붙게 바꿨다. 하네스가 본
`posting_analysis>resume_diagnosis` 는 **의도된 동작**이고, 옛 동작을 못 박고 있던 술어가
낡은 쪽이었다. 콜 +26%도 같은 변경의 대가다 — **정리 한 단계가 게이트 턴에 추가된 값**이다.

**③ 술어를 갱신했다 — 넓힌 것이 아니라 좁혔다.**

```python
d == []                    # 옛 술어: 게이트 턴에 아무 담당도 돌지 않을 것
"fit_analysis" not in d    # 새 술어: 무거운 판정이 묻기 전에 돌지 않을 것
```

이 케이스가 지키려는 것은 *"정리가 안 도는 것"* 이 아니라 **"무거운 판정이 묻기 전에 돌지 않는
것"** 이다. 새 술어는 07-29에 발견된 **게이트 우회 구멍을 그대로 감시한다** — 플래너가 자소서의
전제로 `fit_analysis` 를 스스로 끼워 실행하면 여전히 빨간불이 된다. **관측에 맞춰 넓힌 것이
아니라 결정(D158)이 정한 동작에 맞춘 것**이고, 그 근거를 코드 주석에 남겼다(§5-4 규율).

**④ 재측정: 이탈 0건**(`consistency_after_gate_predicate.json`, 9시나리오 × 3회,
`claude_code/sonnet` · `EMBED_PROVIDER=null`). 술어를 고친 커밋에서 바로 다시 쟀다 — 고치고
안 재면 baseline 이 조용히 죽는다는 것이 이 저장소가 가장 먼저 배운 것이다(§5-2).

> **이 한 사이클이 §5-5가 존재하는 이유다.** 지표가 빨간불을 켰고 → 궤적을 보고 원인이 표면과
> 다르다는 것을 알았고 → 결정 기록에서 귀속했고 → 감시 범위를 잃지 않게 술어를 좁혔고 →
> 다시 쟀다. **어느 단계도 "기대값을 관측에 맞춰 고친 것"이 아니다.**

### 5-5-4. ③ 자기 루프 층 — 유일하게 남은 불변식 위반 1건

`loop_baseline_0803.json` (4케이스 × 5회):

| 담당 | 안정성 | 궤적 | 스텝(평균/최대) | 콜 | 불변식 |
|---|---|---|---|---|---|
| 선호 파악 | 0.80 | `record_preference` ×4 / **도구 없음 ×1** | 0.8 / 1 | 1.8 | **위반 1** |
| 면접 준비 | 0.80 | `pick_material>find_evidence>record_question` ×4 | 2.8 / 3 | 3.8 | 0 |
| 자소서 초안 | **1.00** | `find_evidence>save_draft>check_draft` ×5 | 3.0 / 3 | 4.0 | 0 |
| 자소서 강조 | 1.00 | 동일 ×5 | 3.0 / 3 | 4.0 | 0 (경고 5/5) |

읽어야 할 것 셋이다.

1. **위반 1건이 현재 이 시스템의 유일한 빨간 불변식이다.** 선호 파악이 5회 중 1회 **도구를 하나도
   안 쓰고** 답했다. 불변식(`record_preference` 호출)은 취향이 아니라 계약이다 — 기록 없이 답하면
   다음 턴이 아무것도 물려받지 못한다. 상한 도달은 0이므로 잘린 게 아니라 **안 부른 것**이다.
2. **강조 요청은 5/5 전부 `coverletter_check_unresolved` 경고를 달고 나갔다.** 답변은 나왔지만
   점검이 지적한 것을 못 지운 채 나갔다는 뜻이다. 경고가 없었으면 이 사실은 안 보였다 —
   §6-5의 "폴백은 이유를 삼키지 않는다"가 지표에서 값을 하는 자리다.
3. **`handoff.attempts = 0`.** 위임이 한 번도 시도되지 않았다.

### 5-5-5. §3-5의 수치는 지금 baseline 과 다르다 — 그리고 그 차이가 결론이다

이 보고서 §3-3·§3-5는 *"재작성 2/5, 위임 1/5, 자소서 안정성 0.40"* 을 인용한다. **07-29 측정치다.**
08-03 최신 baseline 은 **안정성 1.0, 재작성 0/5, 위임 0/5** 다. 숫자만 보면 "발동하던 것이 안
발동한다"이지만, 그 사이에 **A/B 가 하나 돌아 있어서 원인을 말할 수 있다**
(`loop_coverletter_control_claude.json` vs `loop_coverletter_after_claude.json`, 08-02).

| | 대조군 (근거 4섹션·20건, 0건이면 "없습니다") | 처치군 (전 섹션·60건, 0건이면 전문 반환) |
|---|---|---|
| 불변식 위반 | **5** | **0** |
| 안정성 (초안/강조) | 0.60 / 0.60 | 0.80 / **1.00** |
| 위임 시도 | **4/5** (전부 성공) | **1/5** |
| `find_evidence` 반복 | 2~3회 반복 궤적 4건 | **0** |
| 평균 콜 | 6.0 / 4.6 | **4.4 / 4.0** |

**위임은 자율성의 증거가 아니라 근거 빈곤의 보상 행동이었다.** 재료를 못 찾은 LLM 이 옆 담당에게
물어보고, 같은 도구를 두세 번 다시 부르고, 그러다 스텝을 태우고 있었다. 재료를 넓히자 그 행동이
사라졌다 — 위임 4/5 → 1/5 → (08-03) 0/5, 콜 −27%, 위반 5 → 0.

> **그래서 이 지표들은 "높을수록 좋다"가 아니다.** 위임 발동률·재작성률·궤적 다양성은 **낮아지는
> 것이 개선인 경우가 있다.** §3-5가 "낮은 안정성이 나쁜 것이 아니다"를 말했다면, 여기는 그 반대편
> — **높은 발동률이 좋은 것이 아니다.** 판단 기준은 지표의 방향이 아니라 **왜 그 행동이 나왔나**다.
> 이 구분은 A/B 대조군 없이는 만들 수 없었다.

만들었다 — **원칙이 먼저 있고 측정이 따라간 게 아니라, 측정이 원칙을 만들었다.**

# 6부. 무엇이 터졌고 어떻게 고쳤나 — 사건 기록

이 시스템의 규칙은 대부분 **책이 아니라 사고에서** 나왔다. 대표 사건을 **증상 → 진짜 원인 →
처방** 으로 정리한다. 세 칸이 다른 것이 핵심이다 — **증상에서 원인으로 가는 길이 매번 반직관적**
이었다.

## 6-1. "정상처럼 보였는데 죽어 있던" 것들

| 증상 | 진짜 원인 | 처방 |
|---|---|---|
| 검증 재시도 루프가 잘 도는 줄 알았다 | 라우터의 **이중 가드** 때문에 **한 번도 발동한 적이 없었다** | 여러 번 돌아야 성립하는 기능은 **실제로 발동하는지**를 실기동으로 확인 |
| 면접 준비 담당이 테스트는 통과 | 선언한 산출물 키가 세션 허용 목록에 없어 **실서버에서 매번 실패** | 계약을 테스트로 못 박기 |
| 자기 루프가 도는 줄 알았다 | 설정 하나가 빠져 **층이 통째로 꺼진 채** 계산 폴백으로 답하고 있었다 | **실 모델로 한 번 돌린다**를 규약에 |
| 관찰이 "결과를 보고 다시 정한다"는데 로그가 없다 | 로그를 남기기 **전에** 함수를 빠져나가고 있었다 | **아무것도 안 바꾼 결정도 기록한다** |

> **"예외가 안 났다"는 동작의 증거가 아니다.** 이 네 건이 전부 단위 테스트 전 통과 상태였다.

## 6-2. 숫자가 거짓말한 순간들

| 증상 | 진짜 원인 | 처방 |
|---|---|---|
| 플래너 정확도 100%로 기록돼 있었다 | baseline 저장 **5시간 뒤** 프롬프트가 바뀌었다. 재측정하니 **67%** | **프롬프트 변경과 평가셋 재측정은 같은 커밋에** |
| 프롬프트를 고쳐 총계 0.67 → 0.78 | 케이스별로는 **고친 것 8 / 깨뜨린 것 6** | 총계 말고 **케이스별로 본다**. 좁히는 변경과 넓히는 변경을 같은 커밋에 넣지 않는다 |
| 파싱 정확도(F1)가 0.08로 나왔다 | 출력은 정답과 의미가 같았다. **정답 라벨의 띄어쓰기**("HTML 과")가 채점기를 깨뜨렸다 | 지표가 상식과 어긋나면 **먼저 채점기와 라벨을 의심** |
| 실패 17건을 "불일치"로 뭉쳐 보고 있었다 | 축이 하나였다 | **정확도와 안정성을 분리** → flaky는 3건뿐, 나머지는 프롬프트 과잉 5 + 데이터셋 낡음 6 |

> **측정하지 않은 것은 모르는 것이고, 측정 도구 자체도 틀릴 수 있다.**

## 6-3. LLM을 부탁으로 다루려다 실패한 것들

| 증상 | 진짜 원인 | 처방 |
|---|---|---|
| 이력서를 냈는데 분석이 안 돌았다 | 스키마 필드에 **설명을 빼먹어** 모델이 확신도를 `0.0`으로 채웠고, **자기가 고른 계획이 문턱에서 잘렸다** | **스키마의 description은 문서가 아니라 지시문이다** |
| 회사명을 못 찾자 그 값으로 검색을 돌렸다 | LLM이 "값 없음"을 **`<UNKNOWN>`이라는 그럴듯한 문자열**로 채웠다 | 자리표시자를 씻어내고 **값의 존재 여부로 분기** |
| 모델이 직군을 멋대로 추측했다 | 프롬프트로 부탁하고 있었다 | **출력 스키마에서 그 필드를 제거** |
| 면접 답변 점검이 매번 템플릿으로 떨어졌다 | 금지 낱말 목록에 `반드시`·`무조건` 같은 **코칭 일상어**가 있었다 | 목록을 푸는 게 아니라 **위반 낱말을 알려주고 다시 쓰게**, 계속 걸리면 그때 폴백(이유 기록) |
| 도구 이름 환각을 막으려 형식을 제한했다 | 표기 형식까지 막아 **턴 전체를 실패시켰다** | 막아야 할 것은 **없는 이름**이지 표기가 아니다 — 표기는 정규화 |

## 6-4. "실패"의 원인이 실패한 곳에 없던 사건 둘

**① RAG가 계속 실패한다 → 서버 문제가 아니었다.** 첫 장문 검색이 수십 초 걸리는데 타임아웃이
짧아 **정상 동작을 실패로 오판**하고 있었다. 타임아웃을 늘리고, 자산이 도착하는 순간 **미리 한 번
예열**하게 바꿨다.

**② RAG 서버가 아예 안 뜬다 → 에러 메시지 세 개가 모두 원인이 아니었다.** 화면에 찍힌 에러를
차례로 고쳤는데 전부 헛다리였다. **에러 메시지는 증상이지 원인이 아니다.**

## 6-5. 정직함을 지키느라 만든 규칙들

| 사건 | 규칙 |
|---|---|
| LLM 호출이 실패하자 **그럴듯한 가짜 결과가 진짜처럼** 나왔다 | 키가 없으면 mock(개발 편의), **호출이 실패하면 빈 결과 + 경고**. 지어내지 않는다 |
| 폴백이 경고를 잃어 **"왜 기본 문구가 나왔는지" 흔적이 없었다** (두 번 겪었다) | 표현 도구의 계약을 `문장` → **`(문장, 경고)`** 로 바꿨다. 위임도 상대의 경고를 그대로 올린다 |
| 유사도 계산 실패를 `0.0`으로 돌려줬다 | `0.0`은 "안 닮았다"는 **판정**이다. 실패는 **"모른다"** 여야 한다 |
| 신입이 "경력 2년 이상" 공고를 충족으로 나왔다 | 연속값(개월)을 **너무 일찍 구간으로 뭉갠** 탓. 원값을 끝까지 들고 간다 |

## 6-6. 전부를 관통하는 여섯 원칙

사건들에서 반복 확인된 것을 규약으로 굳혔다.

| | 원칙 | 대표 근거 |
|---|---|---|
| **A** | 측정하지 않은 것은 모르는 것이다 | baseline이 5시간 만에 죽었다 |
| **B** | LLM은 **부탁이 아니라 구조**로 다룬다 | 파싱을 "전부 LLM 한 콜"로 두는 안을 A/B로 기각 — 정확도는 동률(0.971 vs 0.958)인데 **재현성이 갈렸다**(5/6 vs 4/6) |
| **C** | 실패와 "모른다"를 정직하게 다룬다 | 가짜 폴백이 가장 위험하다 |
| **D** | 상태·계약은 파생하지 말고 **단일 출처**를 만든다 | 번역기 3개를 지운 이유 |
| **E** | 규칙에는 **근거를 함께 적는다** | "도구라서"가 아니라 "결정론이라 바꿀 게 없어서" |
| **F** | 작업 위생 — 한 번에 하나, 매번 잰다 | 총계가 케이스별 파손을 가렸다 |

## 7-2. 일마다 맞는 도구로 옮겨 온 역사

처음에는 여러 일을 한꺼번에 LLM 한 콜에 맡겼다가, **정형으로 표현되는 것부터** 하나씩 알고리즘
쪽으로 옮겼다. 옮긴 근거는 전부 실측이다.

| 원래 LLM 한 콜에 맡겼던 것 | 무슨 일이 생겼나 | 어떻게 바꿨나 |
|---|---|---|
| 흐름 판단 | 대응표가 상황마다 커졌다 | 자산 유무는 정형 조건이다 → **전제조건**에서 순서가 계산돼 나오게 |
| 관찰 | **실측 발동 0건**, 26.2초 낭비 | 결과 요약은 키 유무로 판별된다 → 규칙으로 |
| 동의 게이트 | 스스로 신고하게 했더니 **신고하지 않았다** | **스키마 필드**로 받아 코드가 판정 |
| 최종 행동(제출·결제) | 프롬프트로 막은 것이 지켜지지 않았다 | **그 도구를 만들지 않았다** |
| 답변에 넣지 말아야 할 칸 | 마찬가지 | **출력 형식에서 그 칸을 없앴다** |

> **부탁으로 되는 일과 구조로 해야 하는 일이 갈린다.** 옮긴 것은 전부 *정형으로 확정할 수
> 있어서 옮길 자리가 있던* 것이고, 문장을 읽어야 하는 일(요건 추출·서술형 판정·표현)은 그대로
> LLM이 맡고 있다.

## 7-3. "모른다"를 지켜 낸 결정들

유사도 계산 실패는 0점이 아니라 **값 없음**(0점은 "안 닮았다"는 판정이지 실패가 아니다) ·
계산되지 않은 항목을 0점으로 깔지 않는다 · 자료가 일부만 있어도 되묻고 끝내지 않는다 ·
대체 가능한 기술은 요구사항 하나로 센다(분모가 부풀면 등급이 왜곡된다).

## 7-4. 기억 — 대화가 이어지게 만든 장치

| 장치 | 왜 |
|---|---|
| **화이트보드** | 한 담당이 만든 지식을 다른 담당이 다시 만들지 않는다 |
| **공고 라이브러리** | 활성 공고가 바뀌어도 정리했던 공고를 잊지 않는다 |
| **이력서 라이브러리** | 슬롯 하나를 두고 세 원천이 서로를 덮어쓰던 문제 |
| **요청 기억·재개** | 못 한 요청을 3턴 기억했다가 자료가 오는 턴에 자동 완수 |

## 7-5. 현실의 입력 받아내기

**3단 사다리**(본문 리더 → 프레임 추출 → **캡쳐를 비전 AI로 텍스트화**)로 크롤링을 막은
사이트도 받는다 · 주소는 **열어 본 뒤에** 공고가 된다 · 공고 주소 + 이력서 + 요청이 한 메시지에
오면 **성분별로 분해** · 여러 개 동시 접수 · 공고에서 담당업무·조건·전형까지 읽는다
(**칸이 없어서 못 읽고 있었다** — 프롬프트가 아니라 출력 형식의 문제였다).

## 7-6. 서비스 결합 (8/03~8/04)

- **기억을 DB로**: 처음엔 AI의 말과 DB의 말을 **번역**했는데 그 번역이 버그를 만들었다.
  **번역을 없애고 통째로 주고받게** 바꿨다 — *번역이 없으면 번역 버그도 없다*
- **진행 상황 실시간 표시**: 담당의 발화가 완성되는 즉시 화면에 나온다
- **커리어지도 자동 생성**: 재료가 없으면 **시도조차 막는다**. 적재는 **기존 경로 하나를 그대로**
  쓴다 — 같은 것을 만드는 코드가 둘이 되면 언젠가 결과가 갈린다
- **말은 에이전트가 한다**: 백엔드가 사용자향 문장을 쓰지 않는다. 로드맵도 채팅에서 읊지 않는다
  (지도에 그려진 걸 다시 읊으면 지도를 열 이유가 없어진다)
- **실패해도 죽지 않게**: 담당 하나의 예외가 턴을 죽이지 않는다 · 버려진 작업을 회수한다 ·
  AI 서버가 잠깐 재시작돼도 대화를 되살린다

## 7-7. 안 하기로 한 결정도 남긴다

| 안 한 것 | 왜 |
|---|---|
| 바깥 오케스트레이터를 완전 자율(ReAct)로 | 병목은 루프 구조가 아니라 **도구 목록**이었다 |
| 티어별 온도 분리 | 재 봤더니 이득이 없었다 |
| 동의어 사전 손으로 나열 | 계속 지는 경주다. 정규화로 흡수 |
| 강조 재작성 전용 매칭기 | 근거를 넓게 주고 **LLM이 좁히게** 하는 편이 낫다 |
| 선빌드 최적화 | 넣었다가 뺐다 — 복잡도 대비 이득이 없었다 |
| **읽기 전용 위임을 표준 A2A 메시지로 확대** | **측정이 반대를 말한다** — 아래 |
| **내부 도구를 MCP로 표준화** | 이미 `ToolSpec` 하나로 통일돼 있고, 이 도구들은 세션 상태를 직접 만지는 결정론 함수다. 프로토콜 경계를 넣으면 **표준화 이득 없이 직렬화 비용만** 붙는다. 값이 있는 자리는 외부 경계(RAG·공고 수집)이고, **외부 소스가 두 번째로 붙는 날**이 도입 시점이다 |
| **메모리를 별도 저장소로 분리** | 스키마 분리는 이미 끝나 있다(자산 25키가 성격별로 갈려 있다). 저장소를 물리적으로 나누면 D152가 지운 **번역기가 돌아온다** — *번역이 없으면 번역 버그도 없다* |

> **A2A 확대를 안 하는 이유는 취향이 아니라 실측이다.** 위임 발동이 많던 시절(4/5)의 정체는
> 협업이 아니라 **근거 빈곤의 보상 행동**이었다 — 재료를 넓히자 `4/5 → 1/5 → 0/5` 로 사라지면서
> **불변식 위반 5 → 0, 콜 −27%** 가 같이 왔다(§5-6-2). 통로를 넓게 열어 뒀다면 이 결함은
> *"활발한 에이전트 간 협업"* 으로 보였을 것이다. 구조적으로도 표준 메시지 경로를 늘리면 엣지가
> N(N−1)로 돌아가고 **통로마다 가드**가 필요해진다(§4-0-2). 그리고 *"표준 메시지로 바꾸면
> 명확해진다"* 는 부분은 이미 그렇다 — `DelegateOutcome{result, refusal(사유 코드), message,
> warnings}`, 거부를 예외나 `None` 이 아니라 **코드**로 돌려주는 이유가 집계 분모였다.
>
> **다시 열 조건**: 위임이 근거 빈곤의 보상이 아니라 *"상대의 결과가 세션 자산이 아니라 내 루프
> 안의 다음 판단만 바꾸는 참고값"* 인 경로가 새로 생겼을 때. 그 전에는 블랙보드를 우회하는
> 두 번째 통로만 생긴다.

## 8-1. 아직 안 되는 것

- **승격된 공고·이력서 담당의 루프 궤적을 재는 케이스가 없다** — 자기 루프 baseline 4케이스가
  선호·면접·자소서(2종)뿐이라, 에이전트 7 중 2명은 측정 밖에 있다(§3-2)
- **선호 파악이 5회 중 1회 도구를 하나도 안 쓰고 답했다** — 기록 없이 답하면 다음 턴이
  아무것도 물려받지 못한다 (불변식 위반 1건, §5-5-4)
- **지금 프로바이더에서는 토큰을 못 잰다** — 콜 수만 유효하고 비용 환산은 없다 (§5-5-7)

- **개조식 이력서를 못 알아본다** — "~했습니다" 문체를 신호로 쓰는데 명사형("개발", "구축")으로
  쓴 이력서는 판정을 포기한다. 이때 이력서가 저장되지 않아 분석이 실패하는데,
  **답변 문장은 그럴듯하게 나오므로 겉으로는 안 보인다** (08-04 발견, 미수정)
- **추천 순위가 잘 안 갈린다** — 추천이 전부 동률로 나와 사실상 검색 점수순이 된다
- **대안 공고의 다양성** — 같은 회사 공고가 대안을 다 차지하거나 직군이 다른 공고가 섞인다
- **추천 품질은 아직 측정하지 않았다** — 지금 잰 것은 "누구를 부르나"와 "같은 답을 내나"이지
  **"좋은 답인가"가 아니다**

## 8-2. 이 프로젝트가 배운 것 다섯 줄

1. **LLM에게 재료와 권한이 없는 자리를 주면 일하는 것처럼 보이지만 일하지 않는다** — 요약만
   보던 관찰 층 실측 발동 0건, 재료를 쥔 안쪽 루프는 같은 모델로 재작성·위임을 해냈다
2. **금지는 프롬프트가 아니라 구조로** — 줄 수 없는 답은 형식에서 칸을 빼고, 하면 안 되는 행동은
   도구를 주지 않는다
3. **규칙 추가보다 어휘 좁히기** — 같은 문제에서 −0.022 vs +0.058
4. **총계가 아니라 케이스별로, 그리고 어떤 추정량으로 보는지까지** — 같은 데이터가 지표에 따라
   "악화"와 "개선"으로 갈렸다
5. **폴백이 그럴듯하면 결함이 안 보인다** — 자기 루프가 통째로 꺼진 채 "정상처럼" 답하고 있었다
