# 분석 진행 스트리밍 — AI가 백엔드에 보낼 JSON 설계

작성 2026-08-03. 목표: **어느 에이전트가 무슨 툴로 무엇을 하고 있는지**를 백엔드가 이미 구현한
진행 시각화(피자 휠)에 실어 보낸다. 백엔드·프론트는 완성 상태 → **AI 쪽 송신만 구현한다.**

권위: `backend/.../analysis/AiAnalysisClient.java`, `AnalysisWorker.recordProgress`,
`AnalysisJobService.get`, `frontend/src/components/AnalysisProgressWheel.vue`,
`ai-server/app/models.py`(AnalysisStreamEvent). 아래는 그 코드에서 읽어낸 사실이다.

---

## 1. 백엔드·프론트가 이미 하는 일 (우리가 맞춰야 하는 골격)

**① 호출** — `AiAnalysisClient.postAnalysisStream`
- `POST /v1/analyses/stream`, `Accept: application/x-ndjson`, 헤더 `X-JOBISS-AI-SECRET`
- 본문은 `/v1/analyses` 와 **동일한 AnalysisRequest**
- **404/405 면 `/v1/analyses` 로 자동 폴백** → 스트림을 나중에 붙여도 기존 분석은 안 깨진다
- 한 줄 = 한 이벤트(`BufferedReader.readLine`), 빈 줄은 무시, 줄 파싱 실패 = `INVALID_AI_RESPONSE`
- `type=ERROR` 를 만나면 즉시 `AiServiceException(errorCode, errorMessage)`
- `type=RESULT` 의 `result` 가 **최종 분석 응답**. 스트림이 RESULT 없이 끝나면 `EMPTY_AI_RESPONSE`

**② 저장** — `AnalysisWorker.recordProgress` (이벤트 1건 = DB 쓰기 1회)
- **검증 실패 = 분석 실패**: `runId != analysisJobId` 이거나 `sequence < 1 || > 10000` 이면
  `IllegalStateException` → 그 job 은 FAILED 로 끝난다. **runId 는 요청의 analysisJobId 그대로.**
- `type=RESULT` 는 **저장하지 않는다**(early return). 그래도 반드시 보내야 한다(①이 결과를 여기서 얻는다).
- 나머지는 `analysis_agent_events(analysis_job_id, sequence)` 에 upsert → **sequence 재사용 금지**
- `type=STAGE_UPDATED` 면 `analysis_jobs.stage = stage.id`, `stage_message = stage.message`
  (message 가 비면 기존 문구 유지) → 이벤트 목록을 안 읽는 화면에서도 현재 상태가 보인다
- 작업 시작 시 이전 이벤트는 전부 삭제(`loadRequest`) → 재시도는 항상 깨끗하다

**③ 노출** — `GET /api/analysis-jobs/{id}` → `progressEvents = jsonb_agg(event_data order by sequence)`
우리가 보낸 JSON이 **가공 없이** 프론트까지 간다.

**④ 렌더** — `AnalysisProgressWheel.vue`
- `stages` = 이벤트 중 **마지막** `RUN_STARTED`(stages 비어 있지 않은 것)의 `stages[]`
  → **RUN_STARTED 를 나중에 다시 보내 계획을 갱신할 수 있다.** 없으면 프론트 fallback 5단계
- `stageUpdates` = `STAGE_UPDATED` 를 `stage.id` 로 맵(같은 id 는 나중 sequence 가 이김)
- 현재 단계 = 뒤에서부터 `RUNNING|WAITING|FAILED` 인 첫 스테이지 → 없으면 `job.stage == stage.id`
- 화면 텍스트: 눈썹=`label`, 제목=`role`, 본문=현재 단계의 `STAGE_UPDATED.message`
  (없으면 `stage_message` → `RUN_STARTED` 의 `message`)
- 원 노드 색 = `color` 그대로, 아이콘은 **프론트가 index 순서로** 6종을 돌려 붙인다
- 완료 표시는 `status=COMPLETED` 인 단계, 전체 완료는 job status `SUCCEEDED`
- 폴링 **2.5초**(`PostingDetailView`·`ChatView`) → 이벤트가 실시간으로 밀리는 게 아니라 2.5초마다 모여 보인다

## 2. 보낼 이벤트 스키마 (제약 = 계약 검증 대상)

공통: `type` `runId` `sequence` `occurredAt` + 타입별 페이로드. 나머지 필드는 null/빈 배열.

| 필드 | 제약 |
|---|---|
| `type` | `RUN_STARTED` \| `STAGE_UPDATED` \| `RESULT` \| `ERROR` |
| `runId` | **요청 `analysisJobId` 와 동일한 UUID** |
| `sequence` | 1부터 **엄격 증가**, ≤10000, 중복 금지 |
| `occurredAt` | ISO8601 (UTC, `Z`) |
| `stages[]` | RUN_STARTED 에만. **1~12개** |
| `stages[].id` | `^[A-Za-z0-9][A-Za-z0-9._-]{1,79}$` — 이게 `analysis_jobs.stage` 에 그대로 저장된다 |
| `stages[].label` | 1~80자 (눈썹 문구) |
| `stages[].role` | 1~120자 (제목 — **에이전트 이름이 들어갈 자리**) |
| `stages[].message` | 1~500자 (그 단계 기본 설명) |
| `stages[].color` | `^#[0-9a-fA-F]{6}$` |
| `stage` | STAGE_UPDATED 에만. `{id, status, message?}` |
| `stage.status` | `PENDING` \| `RUNNING` \| `WAITING` \| `COMPLETED` \| `FAILED` |
| `stage.message` | ≤1000자 (**툴 호출·관찰이 들어갈 자리**) |
| `result` | RESULT 에만. `/v1/analyses` 응답 전문 |
| `errorCode` / `errorMessage` | ERROR 에만. ≤80 / ≤2000자 |

예시 (한 줄 = 한 이벤트, 개행이 경계):

## 3. 설계 결정 — "어느 에이전트가 무슨 툴" 을 이 스키마에 싣는 법

스키마에 에이전트·툴 필드는 없다. 사람이 읽는 자리는 `label`/`role`/`message` 뿐이므로 이렇게 나눈다.

**결정 ①: 스테이지 1개 = 에이전트(또는 판정 그래프 노드) 1개.**
`role` 에 에이전트 이름(`orchestrator.router.agent_label`), `label` 에 그 단계 요약,
`message` 에 그 에이전트가 무엇을 하는지. 원 위의 노드 하나가 에이전트 하나로 보인다.

**결정 ②: 툴 호출은 `STAGE_UPDATED.message` 로 흘린다.**
`도구 <tool> 호출 — <관찰 80자>` 형태. 화면은 **현재 단계의 최신 message 한 줄**만 보여주므로
툴 문구는 흐르는 정보다. 전체 툴 로그는 `progressEvents` 에 이미 다 담겨 프론트로 가고 있어서,
나중에 타임라인 UI 를 붙이면 추가 전송 없이 그대로 쓸 수 있다(프론트 몫).

**결정 ③: `RUN_STARTED` 를 두 번 보낸다(2단 발행).**
플래너가 돌기 전에는 실행할 에이전트를 모른다. 그래서
1) 첫 줄: 백본 계획(`CONTEXT_ASSEMBLY`, `PLANNING`, `CONTRACT_VALIDATION`, `RESULT_ASSEMBLY`)
2) 플래너·dispatch 확정 직후: **에이전트별 스테이지가 채워진 완전한 계획으로 RUN_STARTED 재발행**

프론트가 "마지막 RUN_STARTED" 를 쓰기 때문에 성립한다(§1-④). 이전 백본 id 로 보낸
STAGE_UPDATED 는 새 계획에 없는 id 라 무시될 뿐 화면을 깨지 않는다.

**결정 ④: 스테이지 상한 12를 코드로 지킨다.**
dispatch 순서로 앞에서 채우고, 넘치면 마지막 한 칸을 `RESULT_ASSEMBLY` 로 남긴다.
초과분 에이전트는 그 칸의 message 로 표기한다(계획을 잘랐다는 사실을 삼키지 않는다 — AGENTS.md §2-6).

**결정 ⑤: 색은 고정 팔레트 6색 순환** — `#1cb0f6 #ce82ff #ff9600 #2b70c9 #58cc02 #ffc800`.
프론트 아이콘도 6종 순환이라 index 가 맞물린다.

**결정 ⑥: `token` 이벤트는 스트림에 싣지 않는다.** 분석 경로엔 표현 스트리밍이 필요 없고
이벤트 수(=DB 쓰기)만 폭발한다. 이벤트 예산은 **한 분석당 60건 이하**를 목표로 한다.

> 더 작게 가는 대안: RUN_STARTED 1회(문서 기준 5단계 고정) + 에이전트·툴은 전부 message.
> 변경은 가장 작지만 원 노드 라벨이 에이전트가 아니라 고정 단계라, "어느 에이전트가"가
> 문장 안에만 남는다. 시각화 요구를 채우려면 결정 ①·③이 필요하다.

## 4. trace 이벤트 → 스트림 이벤트 매핑

jobis_ai 는 이미 필요한 계측을 다 갖고 있다(`trace.py`, `mapping.ProgressMapper`).
새 판단은 만들지 않고 **옮겨 적기만** 한다.

| trace kind (detail) | 스트림 이벤트 | 문구 |
|---|---|---|
| (스트림 시작) | `RUN_STARTED` #1 | 백본 4단계 |
| `planner` (selectedAgents, confidence) | `STAGE_UPDATED` `PLANNING/RUNNING` | `선택: <라벨…> · 확신 0.82` |
| `fallback` | `STAGE_UPDATED` `PLANNING/RUNNING` | `플래너 불가 — 대화형 에이전트가 턴을 받음` |
| `dispatch` (agents) | **`RUN_STARTED` #2 재발행** + `PLANNING/COMPLETED` | 에이전트별 스테이지 확정 |
| `consent_gate` (ask) | `STAGE_UPDATED` `.../WAITING` | `실행 전 확인: <ask>` |
| `url_intake`·`resume_intake` | `CONTEXT_ASSEMBLY/RUNNING` | `자료 접수 — <label>` |
| `agent_start` (agent, sessionAssets) | `AGENT_<NAME>/RUNNING` | `실행 중 · 입력: 공고, 이력서` |
| `agent_step` action=`use_tool` (tool, arg, observation) | `AGENT_<NAME>/RUNNING` | **`도구 <tool> 호출 — <observation 80자>`** |
| `agent_step` action=`reply` | `AGENT_<NAME>/RUNNING` | `스텝 N · 답변 작성` |
| `agent_step` action=`limit`/`unavailable` | `AGENT_<NAME>/RUNNING` | `도구 사용 상한 도달` / `중단(판단 불가)` |
| `delegate` (from,target,dataKeys) | `AGENT_<NAME>/RUNNING` | `<from> → <target> · 받은 데이터: …` |
| `delegate_refused` (target,reason) | `AGENT_<NAME>/RUNNING` | `위임 거부: <target> — <reason>` |
| `node` (node, toolLog 마지막 message) | `AGENT_<NODE>/RUNNING` | 노드가 toolLog 에 쓴 문구 **그대로** |
| `observe` (rule≠none) | `AGENT_<NAME>/RUNNING` | `실행 후 재점검: <reason>` |
| `agent_end` (warnings, sessionUpdates) | `AGENT_<NAME>/COMPLETED` | `완료 · 경고 2건 · 3.1초 · 넘김: analysis` |
| `agent_crashed` | `AGENT_<NAME>/FAILED` | 예외 요약 |
| 되묻기 결정(NEEDS_INPUT) | `CLARIFICATION/WAITING` → `RESULT` | 질문 대기 |
| 계약 검증 통과 | `CONTRACT_VALIDATION/COMPLETED` | `스키마·참조 무결성 확인` |
| 응답 조립 완료 | `RESULT_ASSEMBLY/COMPLETED` → `RESULT` | — |
| `EngineNotConfigured`/`EngineFailed`/기타 예외 | `ERROR` (마지막 줄) | 코드 유지: `AI_PROVIDER_NOT_CONFIGURED` / `AI_PROVIDER_UNAVAILABLE` / `INVALID_AI_RESPONSE` |
| `llm_usage` | 싣지 않음 | 사용자 화면에 뜻이 없다 |

`AGENT_<NAME>` 은 에이전트 키를 대문자·`_` 로 정규화한 값(`fit_analysis` → `AGENT_FIT_ANALYSIS`).
id 패턴을 만족하고 백엔드 워커가 쓰는 stage 값(`CONTEXT`·`AI_ANALYSIS`·`VALIDATING`·`SHARED_REUSE`)과도 겹치지 않는다.

## 5. 구현 위치 (AI/ 안에서만)

1. **`v2bridge/app.py`** — `@app.post("/v1/analyses/stream")` 추가.
   `StreamingResponse(media_type="application/x-ndjson")`, 인증 의존성 동일.
   이미 있는 `/v1/chat/stream` 과 **같은 패턴**이라 새 구조가 필요 없다.
2. **`v2bridge/service.py`** — `analyze_events(request)` 제너레이터 신설.
   `chat_events` 와 같은 구조: 워커 스레드에서 `analyze()` 를 돌리고 그 **스레드 안에서**
   `trace.recording(sink=...)` 을 열어 `queue.Queue` 로 넘긴다(trace 는 contextvars 라
   반드시 실행 스레드에서 열어야 한다). 마지막에 `{"type":"result", ...}`.
3. **`v2bridge/stream.py`(신규)** — trace 이벤트 → `AnalysisStreamEvent` 매퍼 + sequence 카운터.
   `mapping.ProgressMapper` 의 라벨 사전·`agent_label` 을 재사용한다(문구를 두 곳에서 정의하지 않는다).
   여기서 길이 제한(80/120/500/1000)과 stages ≤12 를 잘라 지킨다.
4. **`v2bridge/models.py`** — `AnalysisStageDefinition` / `AnalysisStageUpdate` /
   `AnalysisStreamEvent` 를 `ai-server/app/models.py` 와 **같은 제약으로** 추가(검증을 우리 쪽에서 먼저 건다).

불변식(코드로 지킬 것):
- `runId == request.analysis_job_id`, `sequence` 는 단일 카운터로만 증가
- 첫 줄은 항상 `RUN_STARTED`, 마지막 줄은 항상 `RESULT` **또는** `ERROR` (둘 다 아니면 백엔드가 `EMPTY_AI_RESPONSE`)
- `RESULT` 는 **정확히 1건**
- 스트림이 시작된 뒤의 실패는 HTTP 상태로 알릴 수 없다 → 반드시 `ERROR` 이벤트로

## 7. 하지 말 것
- 허위 지연·가짜 단계로 화면을 채우는 것(백엔드 문서 명시)
- 이벤트로 판정을 바꾸는 것 — 스트림은 **창문**이고, 결정은 `RESULT` 안에만 있다
- `RESULT` 를 여러 번 보내거나 sequence 를 재사용하는 것(뒤 이벤트가 앞을 덮어쓴다)
- 에이전트가 부르지 않은 툴 이름을 문구로 만드는 것(근거 없는 관측)
