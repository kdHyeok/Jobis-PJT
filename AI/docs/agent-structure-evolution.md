## ① 2026-07-15 — LLM 파이프라인 첫 구동

**만든 것**: LangGraph 기반 6노드 파이프라인이 껍데기(가짜 응답)에서 벗어나 처음으로 전 구간 동작.

```text
parse_job_posting → build_user_profile → analyze_gap → plan_roadmap
→ (find_alternatives) → verify_result
```

- 공통 인프라: 설정(config), LLM 팩토리, 문서 추출(extract), 구조화 출력(structured),
  RAG 어댑터 **자리(계약)만** 마련 — "콘센트를 미리 설치".
- verify_result 의 재시도 신호가 실제로는 한 번도 되돌리지 못하던 이중 검사 버그를 발견·수정.
- 평가 하네스(성적표) 신설 — 로드맵 예산 준수율 0.5→1.0 개선을 숫자로 증명. 테스트 41개, 76초→1초.

**그리고 곧바로 내린 진단 (0715개선사항)**: 아키텍처는 RAG-ready 인데 실행은 LLM-first.

| 노드 | 당시 상태 |
|---|---|
| parse / profile | 완전 LLM 의존 (스킬 표준화·taxonomy 없음) |
| analyze_gap | **LLM이 해석+비교+판정 전부** — 핵심 판단이 비결정적 |
| plan_roadmap | 100% LLM 생성 ("invented roadmap") |
| find_alternatives | LLM 추측 생성 — 허구 직무 위험 |
| verify_result | LLM이 LLM 결과를 검증 — 신뢰도 문제 |

> 여기서 프로젝트를 관통하는 한 줄이 나왔다: **"판단은 데이터가 하고, LLM은 말만 하게 만들어야 한다."**

## ② 2026-07-16~20 — 판정의 결정론화

①의 진단을 설계로 확정한 단계. 모든 노드를 **3계층** 중 하나로 분류했다.

| 계층 | 하는 일 | LLM |
|---|---|---|
| **읽기(Read)** | 비정형 텍스트 → 정형 필드 추출 | ✅ 읽기 용도만 (없는 사실 생성 금지) |
| **판단(Decide)** | 매칭·계산·검색·검증 | ❌ 금지 — 결정론이어야 신뢰성이 나온다 |
| **말하기(Speak)** | 정형 결정 → 자연어 서술 | ✅ 표현 용도만 |

**바뀐 것 (노드별 변화점)**:

- `parse_job_posting`: 순수 LLM → **하이브리드**(정규식 `rule_extractor` 1차 → 잔여 비정형만 LLM).
  직무 카테고리·연차 "판단"은 `role_taxonomy` 룰로 이관. LLM 읽기 스키마에서 해당 필드를
  **아예 제거** — "판단하지 마라"를 프롬프트가 아니라 스키마에서 강제하는 전략의 시작.
- `analyze_gap`: LLM 통째 판단 → **`gap_matcher`(신규 판정 엔진)**. 동의어 사전(`skill_taxonomy`)
  정확 매칭 + 유사도 매칭 + severity 룰 + 가중 집계.
- `plan_roadmap`: LLM 생성 → **자격증 정형 DB**(`cert_db` + `skill_to_cert`) + 프로젝트 과제
  템플릿(`project_template_db`) + 주차 배치 결정론 계산(`roadmap_scheduler`). RAG로 학습자료를
  검색하려던 안(hook ③)은 **폐기** — 강의는 무한·휘발성이라 벡터 DB와 상충, IT 자격증은
  유한·안정·정형이라 DB 조회 한 방.
- `find_alternatives`: LLM 추측 → **`career_graph`**(직군 전이 그래프)로 징검다리 직군 도출
  + RAG `search`로 실존 공고만 + `gap_matcher` 재사용. 공고를 지어내지 않는다.
- `verify_result`: LLM 검증 → **룰 4종**(스키마·금지표현·근거 참조 무결성·정합성 교차검증).
- 신규 노드 `check_profile_completeness` 추가(총 10노드) — 결측 enum 필드를 비블로킹으로 되묻기.
- **RAG(벡터 검색)는 딱 2 hook**으로 확정: 기업 맥락(`fetch_company_context`)·공고 코퍼스(`search`).
  데이터 조회 사다리: 내부 정형 DB → RAG → 웹검색 → 외부 LLM.

**이 단계에서 확립된 핵심 원칙들**:

1. **'모른다'와 '아니다'의 구분** — 판정 못 하면 `not_met`이 아니라 `uncertain`. uncertain 은
   gap(확인된 부족)에 넣지 않고 되묻기로 돌린다. 모르는 걸 부족으로 세면 근거 없이 사람의 결함을
   단정하고, 그 위에 로드맵까지 쌓여 오류가 증폭된다. (`embed.similarity()`가 미연결 시 0.0이
   아니라 None 을 반환하는 것도 같은 원칙.)
2. **주장 vs 증명 분리** — 이력서 스킬 나열은 주장. `evidenceMap`(원문 근거 문장 저장소)이 증명을
   담고, LLM이 생성한 근거 문장은 **원문 대조로 환각 제거**(`_filter_grounded_evidence`), id는 룰로
   재부여, 스킬↔근거 매핑(`skillEvidence`)은 룰로만 구축 — 지어낼 기회를 구조적으로 차단.
3. **함의 관계 `implies`** — MySQL→(RDBMS, SQL). "MySQL 인덱스 튜닝" 근거가 RDBMS·SQL 요구의
   근거로도 인정된다. 단 엄격히 수반되는 것만(Spring Boot→Java는 넣지 않음 — Kotlin 가능).
4. **"분석할 정보가 충분한가" ≠ "이 사람이 충분한가"** — 섞으면 역량 부족한 사용자에게 질문을
   퍼붓는 무례한 제품이 된다. 차단하는 결핍(blocking)만 분석을 멈춘다.
5. **테스트로 결정을 못 박기** — 133건(당시), LLM 없이 1초 미만. uncertain→not_met 으로 되돌리면
   테스트가 깨진다(변이 주입으로 확인).

결과: **LLM 호출이 입구(파싱·프로필 추출 2곳)와 출구(최종 요약 1곳)에만 남았다.**

## ③ 2026-07-20~21 — 실데이터 기반 보정

실제 페르소나 문서(user1·user2)로 돌려보며 내린 결정들.

- **임베딩 → LLM 의미판정 교체 (07-20)**: 서술형 요구사항("이벤트 드리븐 아키텍처 설계 경험")의
  2차 매칭을 원래 임베딩 cosine 유사도로 설계했으나, 실측에서 `text-embedding-3-small/-large`
  둘 다 짧은 텍스트 간 주제 관련성 판정이 신뢰 불가("React"가 "Kafka"보다 "이벤트 드리븐"과
  더 유사하다고 판정). → `semantic_judge`(LLM 구조화 출력, **이진 판정만**)로 교체. 판단 계층
  "LLM 금지" 원칙의 **유일한 의도적 예외**가 됐다.
- **기재 스킬 met 인정 (07-20)**: 이력서에 스킬로 기재만 돼 있어도(근거 문장 없이) met 판정에
  포함 — 사용자가 직접 적은 스킬은 인정하되, confidence 는 근거 있는 쪽에 높게 줘 신뢰도 차이는
  남긴다. reason 문장에는 "근거로 확인됨 / 기재만 됨"을 반드시 구분해 적는다.
- **종합 적합도 점수·등급 확정 (07-21)**: 카테고리 가중치(techSkill 0.35, projectExperience 0.25,
  roleRelevance 0.15, domainFit 0.15, certLanguage 0.10) 가중 평균 → 등급 경계 상 ≥0.7 / 중 ≥0.4.
  계산된 카테고리만 분모에 넣고, 하나도 없으면 (None, "판정불가")로 정직하게 남긴다.
- `experiences` vs `projects` 경계 확정(고용관계 유무), 프로필 스키마 pydantic 하위 모델로 타입
  강제, `role_taxonomy`를 직무 어휘의 단일 소유자로 정리.

## ④ 2026-07-21~22 — 행동 계층·오케스트레이터 설계 (방향 확정)

판정 엔진을 굳히고 나서의 자기의심 — "판정을 결정론으로 뺀 게 에이전트답지 못한 과소설계 아닌가?"
— 에 대한 답: **그 의심은 틀렸다. 판정 결정론화는 정답이고 되돌리지 않는다.** 문제는 판정이 아니라,
제품의 차별점인 "판정 뒤의 행동"과 "사용자 의도를 해석하는 정문"을 짓지 않은 것이었다.

> **"에이전트냐 워크플로우냐"는 잘못된 질문이었다. 정답은 3계층 분업 —
> 위는 에이전트(조합), 가운데는 결정론(판정), 아래는 인간게이트(행동).**

| 계층 | 신뢰성을 무엇으로 버나 | LLM/에이전트 |
|---|---|---|
| 오케스트레이터 | 확인 가능한 라우팅(오라우팅은 사용자가 잡음) | ✅ 얇은 플래너. dispatch만, judge 금지 |
| 판정 엔진 | 틀리지 않음(결정론·테스트) | ❌ 입출구만 |
| 행동 계층 | 제출 전 사람이 본다(인간게이트) | ✅ 환경 대면 루프 + 근거제한 생성 |

이 단계에서 확정한 설계 자산:

- **행동 에이전트 6단계 골격**: P0 PLAN(룰) → P1 GATHER(★에이전트, 환경 대면만) → P2 MAP(룰) →
  P3 DRAFT(LLM·근거제한) → P4 VERIFY(룰) → **P5 GATE(중단·사용자 검토)** → P6 COMMIT(사용자).
  예측 불가능한 외부 환경을 상대하는 P1 한 단계에만 자율 루프를 가둔다.
- **P6 안전 경계 — 툴 미보유로 강제**: "제출·결제·전송을 하지 않는다"를 프롬프트로 부탁하지 않고
  해당 툴을 아예 주지 않아 구조적으로 차단. (스키마에서 필드를 빼던 전략의 행동판.)
- **자소서 두 절대 규칙**: 문항 답을 지어내지 않는다(프로필에 없으면 묻는다) /
  `evidenceMap` 밖 성과를 서술하지 않는다(사용자 이름으로 나가는 거짓말 방지).
- **세 갈래 순환**: 하(대체추천) → 사용자 공고 선택 → 재판정 → 상이면 즉시지원(apply).
- **가장 중요한 경고 — 자율성은 창발하지 않는다**: 입력만 느슨하게 열면 생기는 건 자율성이 아니라
  고장이다. 자율성은 명시적으로 만드는 계층이다. 순서도 확정: 명시적 진입점(a) 먼저,
  LLM 오케스트레이터(b)는 도구가 안정된 뒤.

## ⑤ 2026-07-23~ — 대화형 멀티에이전트 전환 (구현)

④의 방향을 현재 코드 기준의 실행 계획으로 구체화하고 착수한 단계
(브랜치 `feature/multi-agent-orchestrator`).

**확정 결정 (2026-07-23)**:

- 서비스 진입은 **자연어 대화** (`POST /api/v1/chat`).
- 오케스트레이터 첫 구현은 **LLM 의도분류 + 결정론 dispatch** — LLM은 발화를 의도 라벨로만
  분류(`{intent, slots, confidence}` — 판단 필드가 스키마에 없음), 어떤 에이전트를 부를지는
  결정론 라우팅 테이블이 정한다. 저신뢰·복수 의도면 실행 대신 되묻고, dispatch 전에
  "~로 이해했어요"를 보여줘 오라우팅을 사용자가 즉시 잡는다.
- **전담 에이전트 로스터 6종**: 적합도 분석 · 공고 추천 · 이력서 진단 · 자소서 초안 ·
  로드맵 관리 · 면접 준비. 생성 에이전트들은 전부 판정 결과의 **소비자** — 판정을 다시 하지
  않고, 분석 결과가 없으면 라우터가 적합도 분석을 먼저 끼워 넣는다(⊕ 전제조건 자동 합성).
- 진행 순서(Phase): ① 에이전트 분해 → ② 대화 오케스트레이터 → ③ 생성 에이전트(면접→자소서)
  → ④ checkpointer + 로드맵 지속성 → ⑤ 추천 검색 루프 → ⑥ (수요 확인 후) tool-calling 플래너.

**성능 병목 해소 (2026-07-23 실측, user2 실문서)**:

| 개선 | 효과 |
|---|---|
| 의미판정 배치화(`judge_topics_relevance` N건→LLM 1콜) + 캐시 | check_sufficiency 144초→0초, analyze_gap 142초→0초 |
| `skill_taxonomy` 임베딩 폴백 메모 캐시 | 재임베딩 중복 차단 |
| langchain-openai 0.3 structured output 버그(`method="function_calling"` 명시) | GMS 실호출 전멸 → 복구 |
| 모델 교체 실측 `gpt-5-nano`→`gpt-5.4` (`.env` 한 줄) | 파이프라인 240초 → **81초 (66%↓)**, 판정 결과 동일(fitGrade "중") — 판정 계층은 결정론이라 모델 교체 무영향 |

구조적 특성: 비용 대부분이 세션당 1회인 원문 추출(이력서·공고)에 있어, **첫 분석 턴만 느리고
이후 추천·진단·면접·자소서 턴은 세션 캐시로 수 초~수십 초**. 남은 여지: parse ∥ profile
병렬화(~50초선), 이력서 추출의 백엔드 사전 계산화, nl_render 실측.

## 관통하는 원칙 (시기 불문 유지)

1. **판단은 데이터가 하고, LLM은 말만 한다** — LLM은 입구(읽기)와 출구(말하기), 그리고 의도적
   예외인 의미판정(이진)에만.
2. **모른다 ≠ 아니다** — uncertain 은 gap 도 0점도 아니다. 분모에서 빼고 되묻는다.
3. **금지는 프롬프트가 아니라 구조로** — 줄 수 없는 답은 스키마에서 빼고, 하면 안 되는 행동은
   툴을 주지 않는다.
4. **자율성은 창발하지 않는다** — 명시적으로 짓는다. 오케스트레이터는 dispatch만, judge 금지.
5. **행동의 최종 확정은 사람** — 에이전트는 솔루션(초안)을 제공하고, 제출은 사용자가 한다.
6. **결정은 테스트로 못 박는다** — 계층별 신뢰성 계약이 다르므로 테스트 스위트도 분리한다.
