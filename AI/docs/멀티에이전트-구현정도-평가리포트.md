### 1-1. 협업 정확도 (Hand-off) — ○ 통로는 견고, **성공률은 미측정**

### 1-3. 역할 준수도 (Role Adherence) — ◎ 구조로 강제하고 테스트가 지킨다

"검수 에이전트가 코드를 직접 수정해버리는" 류의 이탈이 이 시스템에서는 **구조적으로 불가능**하게
설계되어 있고, 그 방식이 AGENTS.md §2-2("금지는 프롬프트가 아니라 구조로")와 일치한다:

| 이탈 시나리오 | 차단 장치 |
|---|---|
| 도구가 사용자에게 직접 말함 | `kind="tool"`은 reply를 비움 — **테스트가 강제** (§2-10) |
| 에이전트가 세션을 직접 수정 | 상태 전이는 `sessionUpdates` + 턴 끝 write-back 1회만. 위임은 읽기 전용 |
| 플래너가 판정을 내림 | 플래너 출력 스키마에 **판단 필드 자체가 없다** (`planner.py:22-33`) |
| 없는 에이전트/인자 호출 | `Literal` 이름 제한 + `validate_agent_args` 결정론 대조 |
| 위임으로 동의 게이트 우회 | `heavy` 에이전트 위임 금지 |
| 제출·결제·전송 | 툴 미보유 (D18) |

실측 사례 1건이 규약의 실효를 보여준다: 관찰 문구에 "안내하세요"라는 지시가 섞이자 답변이
도구 동작을 서술하는 위반이 발생 → 지시를 `goal_system`으로 이동해 수정(비교분석 §2-1).
즉 위반이 생기면 **검출되고 규약 위치가 교정되는** 사이클이 돈다.

### 1-4. 갈등 해결 (Conflict Resolution) — ○ 재작성 루프는 실증, "중재"는 설계상 없음

이 시스템의 refinement loop는 세 겹이고, 둘은 발동이 실측됐다:

- **자기비판 재작성**: `coverletter_draft`의 `check_draft`→`save_draft`(보완 재작성)가
  5회 중 **2회** 실제 발동 (eval-record 후속5). 궤적 최대 4스텝 — `max_steps` 3→5 상향이
  사후 정당화된 근거.
- **검증 실패 → 재시도**: `verify_result`가 근거 전멸·구조 결함 시 생성 재시도
  (`MAX_GEN_RETRY=1`, `MAX_VERIFY_RETRY=1`), 금지표현은 1회만 재작성 후 폴백.
- **판정과 생성의 충돌 중재**: 등급 `하/판정불가`인데 자소서가 예정돼 있으면
  `weak_grade_transition`이 큐를 결정론으로 교체 (`chat.py`, 테스트 18건, 실사용 발동 1건 계측).
  중재자가 LLM이 아니라 규칙이라는 점이 프레임워크의 "적절히 중재되는가"에 대한 이 코드베이스의
  답이다.

**냉정한 판정**: "에이전트 간 의견 충돌"(두 에이전트가 다른 결론을 내고 수렴하는 debate 류)은
**존재하지 않는다** — 판정은 `gap_matcher` 단일 출처(D52)라 충돌할 두 번째 의견 자체가 없다.
이건 결함이 아니라 §1 3계층 설계의 귀결이지만, 이 지표를 "중재 프로토콜 보유"로 읽으면 없는 것이
맞다. 또한 검증 재시도의 실제 발동률은 집계되지 않았다.

### 2-4. 병렬 처리율 (Parallelism Rate) — ◎ vs ✕

본체는 두 계층에서 병렬을 돌리고, **한 번 "투기적"이라 의심받은 뒤 재측정으로 수치를 박았다**(D54):

  계산, 상한 3, 세션 사본·큐 순서 병합. **재측정: 순차 47.8·48.0초 vs 병렬 13.3·37.6초
  = 10~35초 단축** (`chat.py:376-381` docstring). 1차 측정(gpt-4.1-mini)은 21.3→15.6초.
- 판정 그래프: `parse_job_posting ∥ build_user_profile` 팬아웃 + `defer` 합류.

프로토타입: `async`/`await`/`ThreadPool` 그렙 **0건**. tool_calls를 for 루프로 순차 처리하며,
LLM이 병렬 툴 호출을 요청했을 때 순서가 뒤바뀌면 `posting=None`이 되는 위험을 스스로
백로그로 적어 두고 멈췄다.

본체 감점: "병렬 처리**율**"(독립 작업 중 실제 병렬화된 비율)은 집계되지 않는다. 그리고
병렬 구간의 토큰 스트리밍 뮤트가 UX 부채로 남아 있다(`다음작업.md`).

### 3-3. 예외 처리 및 폴백 (Fault Tolerance) — ◎ vs ✕ 격차가 가장 큰 지표

**프로토타입은 이 축에서 자기 계약을 어긴다.** `run_agent` docstring이 "raise 안 함"을
선언하지만, LLM 호출 5곳 전부 **try/except 0, 재시도 0, 타임아웃 0** — 일시적 네트워크 오류
한 번이 전체를 예외로 죽인다. `ToolError` 봉투 설계(툴 내 raise 0건)는 훌륭했으나 정작 가장
잘 터지는 곳(LLM)이 봉투 밖이다.

본체:

- 재시도 단일 계층: `_MAX_ATTEMPTS=3` 백오프, 클라이언트 `max_retries=0`으로 중첩 차단.
- **정직한 폴백 구분**: `llm_not_configured`(mock 허용) vs `llm_call_failed`(가짜 샘플 금지,
  빈 결과 + 경고) — 폴백이 이유를 삼키지 않는다(경고 코드 **60종**).
- 실패 격리: 도구 예외 → 관찰 문자열로 루프 계속 / 생산자 실패 → `drop_unrunnable`이 후속
  단계 제외(실측 결함 — `analysis=None` 위에서 자소서가 돌던 것 — 을 이 규칙이 닫았다) /
  미등록 에이전트 → 크래시 없이 안내 + 경고 / trace sink 예외 무시.
- 실측: 138콜 중 `llm_failed` 1건(재시도로 흡수), 루프 3×5 경고 0건.

**본체의 가장 무서운 실측 사고**도 여기 있다: Claude CLI에서 `--tools ""` 누락으로 **자기 루프
층이 통째로 꺼진 채 결정론 폴백이 "정상처럼" 답하고 있었다**(eval-record 후속5). 폴백이
그럴듯하면 결함이 안 보인다 — AGENTS §3-7("실 모델로 한 번 돌린다")이 규약이 된 이유이며,
"폴백 작동이 원활한가"라는 이 지표가 **원활해서 오히려 위험할 수 있음**을 보여준 사례다.

**07-29 후속 조치 — 조용한 폴백을 시끄럽게 만들었다**(D56). 사고의 원인은 신호가 없었던 게
아니라 **신호가 아무 데도 안 남았던 것**이다: `llm_call_failed` 는 경고 객체(응답에 실려 아무도
읽지 않음)와 trace(턴 끝에 소멸)로만 존재했고, `src/` 전체의 `log.warning`/`log.error` 는 **2줄**
뿐이었다. 두 곳을 박았다 — ① `structured.py` 재시도 소진 시 WARNING(호출 지점 16개가 전부 이
파일을 지난다), ② `chat.py` 턴 끝에 `llm_call_failed` 가 있으면 ERROR 로 *"LLM 이 죽은 채 답변이
나갔다 — 이 응답은 결정론 폴백이다"*. 답변이 나간 사실과 LLM 이 죽은 사실이 **같은 줄에** 있어야
로그를 훑는 사람이 알아본다. 회귀 테스트 1건.

**`llm_call_failed` 간헐 발생 자체는 고치지 않는다**(D57) — 배포·실서비스는 LLM API 고정이고
`claude_code` CLI 는 **에이전트 궤적·E2E 확인용 하네스**다. CLI 고유 실패는 제품 결함이 아니다.
그런데 이 조치의 값은 그래서 **더 크다**: CLI 가 조용히 폴백하면 *E2E 결과 자체가 거짓말*이 된다.
07-29 사고가 정확히 그것이었다 — "3케이스 × 5회 정상"으로 보였는데 루프 층이 죽어 있었다.
이 로그는 제품 장애 알림이 아니라 **하네스 신뢰성 가드**다.

### 3-4. 상태/메모리 일관성 (State & Memory Consistency) — ◎ vs —

프로토타입은 싱글턴(D12 재확정, checkpointer 미사용)이라 지킬 상태가 없다. 해당 없음.

본체: `SqliteSessionStore`(WAL) + 자산 18키 화이트리스트 + **write-back 규약**(턴 시작 1회
읽기 / 턴 끝 1회 쓰기 — 병렬 중 오염 차단은 세션 사본 + 큐 순서 병합) + 상태 전이
오케스트레이터 독점(`sessionUpdates`) + 자산 무효화(이력서 갱신 시 profile·analysis 폐기) +
히스토리 30항. `produces ⊆ ASSET_KEYS`를 테스트가 강제 — 이 테스트가 없던 시절 `interview`
키 누락으로 면접 턴이 실서버에서 매번 KeyError였던 실사고가 근거다.

감점: 오케스트레이터 층에 interrupt/resume(checkpointer)이 없어 `ask_user`가 일회성 —
중단·재개 왕복은 Phase 4 미착수.

### 4-1. 목표 달성률 (Overall Task Success Rate) — ○ vs ✕

### 4-2. 일관성 (Coherence & Consistency) — ◎ vs ○

- **재현성**: 본체 mean_stability **1.0000**(46×3, 최종 baseline), unstable 0. 정확도와
  안정성을 갈라 세는 지표(stable-wrong vs unstable)가 있어 처방을 구분할 수 있다 — 이 관점
  자체는 프로토타입(eval.py N회 실행)에서 이식해 와서 한 칸 발전시킨 것.
  프로토타입은 궤적은 3/3 일관이지만 **판정값(level)이 중/중/하로 흔들렸고**(온도 미설정,
  D16의 temp=0 계획 미반영), W3(agent 상/직접 중)을 자체 로그가 "결정론이 허상"이라 결론냈다.
- **톤앤매너 통일**: 본체는 여러 에이전트 출력의 병합 지점을 `compose_reply` 한 함수로
  모았다(D51 — 같은 자리 실측 결함 3회 재발 후 구조로 해결). 도구는 말하지 않고 표현은
  `render`가 만들므로(§2-10) 문체의 출처가 단일하다. 프로토타입은 판정 노드 안 f-string이
  곧 표현 재료라 분리 자체가 없다.
- 잔여 감점: 시퀀스 지표가 "순서 무관 집합"을 표현하지 못해 내용이 맞고 순서만 다른 케이스
  1건이 오답으로 세어진다(일부러 실패 유지). 문장 수준 coherence(어색함)는 사람 눈 확인만
  있고 지표가 없다.

### 4-3. 제약조건 준수 (Constraint Satisfaction) — ○ vs ✕

프로토타입: 출력 제약 검증 코드 0 — URL 병기·형식은 프롬프트 문장으로만 요구되고 사후 검사가

### 4-4. 공통 공백 — "좋은 답인가"는 아무도 재지 않았다

양쪽 모두에 없는 것: 추천 적합도 정답셋, 생성물(자소서·면접 질문) 품질의 LLM-judge 또는

부르는가'와 '같은 답을 내는가'이지 '좋은 답인가'가 아니다."* 벤치마크 점수라는 프레임워크
항목에 대응하는 것이 본체에는 아직 없다.

## 5. 종합

### 구현정도를 한 문장씩으로

- **협업**: 통로(위임·자동 삽입·병렬)와 가드는 상용 수준으로 촘촘하고 역할 준수는 구조로
  강제되며, **측정 층도 07-29 밤에 채워졌다** — hand-off 집계 첫 실측(시도 0건/mini —
  발동이 모델 의존임을 발견), 턴당 콜 수 평균 2.8 실측. 남은 공백은 위임을 실제로 쓰는
  모델 조합에서의 성공률 표본이다.
- **비용/속도**: 지연은 실측과 회수 이력(58% 낭비 제거, 병렬 10~35초 단축)이 있고,
  **토큰도 07-29 밤부터 실측**(턴당 4,347→301) — 남은 것은 단가 곱한 비용 환산뿐이다.
- **안정성**: 4영역 중 가장 성숙. 상한 12종, 폴백-경고 60종 계약, fail-closed 동의 게이트,
  uncertain 집행까지 규약이 코드와 테스트로 내려와 있다. 단 "그럴듯한 폴백이 결함을 가린"
  실사고가 있었고, 발동률 통계가 없어 견고성이 **입증**이 아니라 **설계+일화**로 서 있다.
- **품질**: 궤적·재현성·제약은 수치가 강하다(0.978/1.0/준수 1.0). 그러나 판정 baseline 2케이스,
  산출물 품질 미측정, baseline 파일의 모델 오귀속 — **품질 주장의 절반은 아직 표본과 지표가
  못 받친다.**

### 프로토타입과의 관계에 대한 최종 문장

프로토타입은 멀티에이전트 평가의 비교군이 아니다. 단일 에이전트 하한선으로서 가치 있었던 것은
루프 상한·툴 에러 봉투·N회 일관성 관점·조건엣지 직검사였고 — 전부 본체가 이식을 끝냈다.
하한선 자체는 갭분석 1/6, LLM 호출 무방비, 계측 0으로 서비스 투입 불가 상태에서 멈췄다.
남은 유일한 비교 가치는 **비용 구조(3~4콜)** 인데, 본체에 콜 수 집계가 생기기 전까지는 그
비교조차 성립하지 않는다.
