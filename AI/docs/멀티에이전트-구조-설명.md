# 이 서비스의 AI는 어떻게 만들어져 있나

> **비개발자를 위한 설명서.** 코드를 몰라도 "이게 멀티에이전트고, 툴 콜링은 이렇게 하는구나"를
> 이해할 수 있게 썼다. 2026-07-30 기준 (공고 URL·캡쳐 인입, 서비스 v2 연결까지 반영).
>
> 여기 나오는 모든 수치·목록은 코드에서 뽑은 것이다. 직접 확인하려면 §8 을 보면 된다.

---

## 1. 한 줄로 말하면

**하나의 거대한 AI가 아니라, 역할이 다른 여러 담당자가 나눠 일하고, 그중 "정확해야 하는 일"은
AI가 아니라 계산기가 한다.**

비유하자면 **종합병원**이다.

| 병원 | 이 서비스 |
|---|---|
| 접수 창구 — 무슨 과로 보낼지 정한다 | **플래너** (AI가 판단) |
| 검사실 — 피를 뽑아 수치를 낸다. 기분에 따라 값이 달라지지 않는다 | **판정 엔진** (계산만, AI 없음) |
| 진료과 — 검사 수치를 보고 환자와 이야기한다 | **전담 에이전트 11종** |
| 처방전은 주지만 약을 대신 먹여 주진 않는다 | **초안까지만.** 지원·제출은 사용자가 한다 |

핵심은 **검사실에 AI를 쓰지 않는다**는 것이다. "당신은 이 공고에 몇 점입니다"는 계산으로
나오고, AI는 그 결과를 사람 말로 옮기거나 사용자와 대화하는 데만 쓴다.

## 2. "멀티에이전트"가 무슨 뜻인가

### 하나의 AI에게 다 맡기면 생기는 문제

"이 공고에 지원할 만한지 봐줘"를 AI 하나에게 통째로 맡기면, 그 AI는 한 번에 이걸 다 한다:
공고 읽기 → 이력서 읽기 → 비교 → 점수 매기기 → 로드맵 짜기 → 답변 쓰기.

문제는 **어디서 틀렸는지 알 수 없다**는 것이다. 점수가 이상해도 공고를 잘못 읽은 건지, 비교를
잘못한 건지, 말만 그렇게 한 건지 구분이 안 된다. 그리고 같은 질문을 두 번 하면 답이 다르다.

### 그래서 쪼갰다

일을 **담당자(에이전트) 11명**으로 나누고, 각자 이것만 정했다:

- **무엇이 있어야 일을 시작할 수 있나** (전제조건)
- **일을 끝내면 무엇이 남나** (산출물)

예를 들어 "자소서 초안" 담당은 *이력서*와 *적합도 분석 결과*가 있어야 시작할 수 있고, 끝나면
*자소서 초안*을 남긴다. 그래서 사용자가 "자소서 써줘"라고 했는데 분석 결과가 없으면,
**시스템이 알아서 "먼저 적합도 분석이 필요합니다"를 알아낸다.** 순서를 사람이 코드에 적어 둔 게
아니라, 담당자들의 전제조건에서 저절로 나온다.

## 3. 담당자 10명 — 누가 무엇을 하나

**두 종류**로 나뉜다. 기준은 딱 하나 — **말을 하는가.**

- **도구형(6명)**: 계산만 한다. 사용자에게 직접 말하지 않는다. 결과를 사람 말로 옮기는 건
  별도의 "표현 담당"이 한다. → 계산이 정확해야 하는 일
- **대화형(5명)**: 사용자와 이야기한다. 스스로 도구를 골라 쓰며 여러 번 오간다.
  → 융통성이 필요한 일

| 담당자 | 종류 | 하는 일 | 시작 조건 | 남기는 것 |
|---|---|---|---|---|
| **공고 수집** | 도구 | 공고 URL·캡쳐 이미지에서 원문 텍스트를 받아 온다 | 공고(주소/파일) | 공고 원문 |
| **적합도 분석** | 도구 | 공고와 이력서를 대조해 등급(상/중/하)과 근거를 낸다 | 이력서 **+** 공고 | 분석 결과, 준비 로드맵 |
| **공고 분석** | 도구 | 공고만 읽어 요구 연차·필수/우대·기술을 정리한다 | 공고 | — |
| **이력서 진단** | 도구 | 이력서에서 읽어낸 항목·근거 있는 스킬·빈 섹션을 정리한다 | 이력서 | — |
| **공고 추천** | 도구 | 실제 공고 DB에서 맞는 공고를 찾아 준다 | 이력서 **또는** 선호 | 추천 목록 |
| **로드맵 조회** | 도구 | 저장된 준비 로드맵을 보여준다 | 로드맵 | — |
| **진로 대화** | 대화형 | 고민·하소연·일반 질문을 받아준다 | (없음) | — |
| **선호 파악** | 대화형 | 이력서 없이 대화로 원하는 직군·지역 등을 모은다 | (없음) | 공고 선호 |
| **면접 준비** | 대화형 | 한 번에 한 질문씩 묻고 답을 점검해 꼬리 질문으로 파고든다 | 분석 결과 | 면접 진행 상태 |
| **자소서 초안** | 대화형 | 초안을 쓰고 스스로 점검해 고친다 | 이력서 **+** 분석 결과 | 자소서 초안 |
| **지원 경로 설계** | 대화형 | "지금 목표로 둘지"와 지원 경로 2~3개를 세운다 | 분석 결과 | 지원 경로 |

> **왜 "적합도 분석"이 도구인가?** 등급은 계산 결과이지 의견이 아니어야 하기 때문이다.
> 실제로 AI 모델을 바꿔도 등급이 똑같이 나오는 것을 확인했다 — 계산이라서 그렇다.

> **"공고 수집"은 특별한 담당이다.** 플래너(AI)의 선택지에도 안 보인다 — 공고가 주소인데
> 아직 원문이 없으면 시스템이 **계산으로** 맨 앞에 끼운다. "수집할지 말지"는 AI가 고를
> 판단이 아니라 자산 상태에서 저절로 나오는 필연이기 때문이다. 수집은 3단 사다리를 탄다:
> 본문 리더(jina) → 상세요강 프레임 추출 → 그래도 안 되면 **캡쳐 이미지를 비전 AI(Clova)로
> 텍스트화**. 크롤링을 막아 둔 채용 사이트도 캡쳐만 있으면 분석할 수 있다.

## 4. 툴 콜링 — AI가 도구를 골라 쓴다는 게 뭔가

여기가 "에이전트답다"고 하는 부분이다.

### 보통의 AI 사용법

질문을 주면 답을 준다. 끝. AI가 아는 것(또는 아는 척하는 것)만 나온다.

### 툴 콜링

AI에게 **쓸 수 있는 도구 목록**을 주고, AI가 **직접 골라 쓴다.** 도구는 사실을 돌려주고,
AI는 그 사실을 보고 다음에 무엇을 할지 다시 정한다. 이 왕복이 몇 번 반복된다.

### 실제로 일어난 일 (자소서 담당, 실측 기록)

```
1단계  find_evidence("Java, Spring")   →  도구: "이력서에서 확인된 사실 3건"
2단계  save_draft("동기: … 강점: …")     →  도구: "기록했습니다. 동기 189자, 강점 173자"
3단계  check_draft()                   →  도구: "공고 요건 3/3 다룸. 단, 보완 문단이 2문장(기준 3~5)"
4단계  save_draft("보완: …")            →  도구: "기록했습니다(작성 2회)"      ← 스스로 고쳤다
5단계  답변 작성
```

**3단계에서 지적을 받고 4단계에서 고쳤다.** 이걸 사람이 코드로 "점검하고 고쳐라"라고 적어 둔 게
아니다. AI가 점검 도구를 부르기로 정하고, 결과를 보고 다시 쓰기로 정했다.

### 여기서 중요한 규칙 — **근거는 도구만 준다**

AI는 **도구가 주지 않은 사실을 쓸 수 없다.** 자소서에 들어갈 경험·수치는 `find_evidence`가
이력서에서 찾아준 것만 쓴다. 그래서 "없는 경력을 지어내는" 일이 구조적으로 막힌다 —
AI에게 "지어내지 마세요"라고 부탁하는 게 아니라, **지어낼 재료를 안 준다.**

### 담당자별 도구 목록

| 담당자 | 쓸 수 있는 도구 |
|---|---|
| **면접 준비** | `pick_material` 질문 소재 고르기 · `find_evidence` 이력서 근거 찾기 · `check_answer` 사용자 답변 점검 · `record_question` 질문 기록 |
| **자소서 초안** | `find_evidence` 근거 찾기 · `save_draft` 문단 기록 · `check_draft` 스스로 점검 · **`ask_agent`** 이력서 진단 담당에게 물어보기 |
| **선호 파악** | `record_preference` 선호 기록 · `request_material` 자료 요청 · **`preview_postings`** 공고 추천 담당에게 "지금 조건으로 공고가 있나" 물어보기 |

> **담당자끼리 물어볼 수도 있다.** 자소서 담당이 "쓸 근거가 왜 빈약한지"를 이력서 진단 담당에게
> 직접 물어본다. 같은 계산을 두 번 만들지 않기 위해서다. 단 **읽기만** 가능하다 —
> 남의 답을 참고할 수는 있지만 그 결과로 시스템 상태를 바꾸지는 못한다.

## 5. 검사실 — 판정 엔진 (AI를 쓰지 않는 곳)

"적합도 분석"이 실제로 하는 일은 **10단계 공정**이다. 대부분 AI가 아니라 계산이다.

| 단계 | 하는 일 | AI를 쓰나 |
|---|---|---|
| 1. 공고 읽기 | 정규식으로 먼저 뽑고, 남은 서술만 AI가 읽는다 | 일부 (읽기만) |
| 2. 이력서 읽기 | AI가 항목을 뽑고, **원문에 없는 문장은 지운다** | 일부 (읽기만) |
| 3. 빈 항목 확인 | 규칙 | ❌ |
| 4. 판정 가능한지 확인 | 규칙 — 근거가 부족하면 **되묻는다** | ❌ |
| 5. **갭 분석** | 계산 (아래 참고) | ❌ |
| 6. 로드맵 짜기 | 자격증 DB + 프로젝트 과제 DB + 일정 계산 | ❌ |
| 7. 대안 공고 찾기 | 직군 전이 지도 + 실제 공고 검색 | ❌ |
| 8. 결과 검증 | 규칙 4종 (형식·금지표현·근거 실존·앞뒤 정합) | ❌ |
| 9. 요약 문장 | AI가 쓰되, 검증을 통과해야 나간다 | 표현만 |
| 10. 조립 | 계산 | ❌ |

> **1~2단계(읽기)와 3~10단계(판정)는 코드 파일도 갈라 뒀다.**
> 전에는 한 파일(1,500줄)에 둘이 섞여 있어서, 새 판정을 넣을 자리를 물으면 답이 항상
> "여기"였다. 파일 경계를 계층에 맞추면 그 질문의 답이 자명해진다.

### 갭 분석은 이렇게 계산한다 (5단계)

1. **표기 통일** — "ReactJS"·"리액트"·"React"를 같은 것으로. "MySQL을 안다"면 "SQL도 안다"로 인정.
2. **이력서 근거와 대조** — 요구 기술의 80% 이상이 확인되면 충족.
3. **기술명이 없는 서술형 요건**("이벤트 드리븐 설계 경험")만 AI가 **"관련 있다/없다" 두 값으로만**
   판정. 점수는 못 매긴다.
4. **연차 비교** — 관련 직군 경력만 개월로 합산해 사다리(인턴~리드) 위치를 비교.
5. **점수 → 등급** — 항목별 가중 평균 후 상 0.7 / 중 0.4 기준으로 나눈다.

### 이 서비스에서 가장 중요한 규칙 — **"모른다"와 "아니다"는 다르다**

판정할 수 없는 항목은 **"부족"으로 세지 않는다.** 점수 계산에서 아예 빼고, 대신 사용자에게
되묻는다.

왜냐하면 "모르는 것"을 "없는 것"으로 세면, **근거 없이 사람의 결함을 단정**하고 그 위에
로드맵까지 쌓여서 틀린 게 두 배로 커진다.

### 쓰이는 내부 지식·계산 도구 (17종)

기술 용어 사전 · 직무 분류 · **갭 계산기** · 의미 판정(이진) · 정보 충분성 규칙 ·
결과 검증 규칙 4종 · 자격증 DB · 스킬↔자격증 연결 · 프로젝트 과제 템플릿 · 주차 배치 계산 ·
직군 전이 지도 · 경력 개월 추정 · 프로필 완결성 검사 · 공고 DB(실제 공고 **2,053건**) ·
공고 원문 규칙 추출 · 공고 URL·캡쳐 수집기(jina+프레임+비전 AI) · 표현 생성

## 6. 한 번의 대화가 흐르는 순서

사용자가 한마디 할 때마다 **여섯 관문**을 지난다.

```
사용자: "이 공고 자소서 써줘"   (+ 이력서·공고 첨부)
   │
① 첨부 저장     붙여넣은 게 이력서인지 공고인지 내용을 보고 바로잡는다.
   │            공고 주소(URL)만 붙여넣어도 알아본다 — http 가 없어도, 주소에 한글이
   │            섞여 있어도 된다. 이력서가 새로 오면 그걸로 만든 옛 분석은 버린다.
   │
② 플래너(AI)    누가 이 일을 해야 하나? → "자소서 초안"
   │            확신이 낮으면 → 대화 담당이 받아서 사람처럼 되묻는다.
   │            단, **방금 자료를 제출한 턴은 예외** — 공고를 막 냈는데 계획이 공고를
   │            쓰는 일이라면, 말이 짧아 확신이 낮아도 그대로 진행한다
   │            (첨부 제출은 말보다 강한 의도 표시니까).
   │
③ 검증기(계산)  자소서는 분석 결과가 필요하다 → "적합도 분석"을 앞에 끼운다.
   │            공고가 아직 주소뿐이면 → "공고 수집"을 맨 앞에 끼운다.
   │            근데 적합도 분석은 수십 초 걸리는 무거운 일이다
   │            → 말없이 시작하지 않고 **먼저 묻는다**: "먼저 적합도 분석이 필요해요. 진행할까요?"
   │            물을지 말지는 계산이 정한다 — 사용자가 직접 청했거나 직전 턴에 동의했을
   │            때만 그냥 돈다. **애매하면 묻는 쪽으로 기운다.**
   │
④ 실행          순서대로. 서로 상관없는 일은 **동시에** 돌린다(최대 3개)
   │
⑤ 관찰(계산)    방금 결과를 보고 남은 계획을 다시 정한다
   │            예1: 적합도가 '하'로 나왔다 → 자소서 대신 **지원 경로 설계**로 바꾼다
   │            예2: 공고 수집이 실패했다 → 공고를 쓰는 뒷일은 접고 본문 붙여넣기를 청한다
   │
⑥ 저장          이번 턴에 생긴 것만 한 번에 저장
```

### 예: 공고 URL 하나만 붙여넣으면 (2026-07-30 실측)

```
사용자  : saramin.co.kr/…rec_idx=54347596…   (주소만, 다른 말 없음)
① 감지  : 주소 → 공고 자산으로 등록
② 플래너: "공고 분석"    ③ 검증기: 원문이 없네 → "공고 수집"을 앞에 끼움
④ 실행  : 수집(16초, 원문 4,850자) → 공고 분석
답변    : "공고를 받았어요. 에이펙스이에스씨 · AI/NLP 엔지니어 공고를 정리했어요.
          필수 요건 12건 — … / 우대 사항 12건 — … 이력서를 주시면 대조해 드릴게요."
```

### ⑤가 오늘 개선된 부분이다 (실측 기록)

```
플래너 계획 :  적합도 분석 → 자소서 초안
적합도 분석 완료 → 등급 '하' (100점 만점에 30점)
강제 교체   :  자소서 초안을 빼고 → 지원 경로 설계
사용자에게  :  "적합도가 '하'로 나와서 자소서 초안은 잠시 미뤘어요.
               먼저 이 공고를 지금 목표로 둘지와 지원 경로부터 정리할게요.
               판정을 보고도 그대로 진행하고 싶으시면 다시 말씀해 주세요."
```

**"근거가 약한데 자소서를 쓰는 것"을 코드가 막는다.** 전에는 이 판단을 AI에게 맡겨 뒀는데,
실제로 한 번도 발동하지 않았다. 그래서 규칙으로 내렸다.

단 **사용자를 가두지 않는다.** 등급을 보고 "알아, 그래도 써줘"라고 하면 그때는 바로 써 준다.

## 7. 왜 이렇게 만들었나 — 안전장치 8개

| 위험 | 어떻게 막았나 |
|---|---|
| AI가 즉석에서 판단해 버린다 | 판정 계층에 AI를 쓰지 않는다. AI 출력 형식에 **"판단" 칸을 아예 안 만든다** |
| 없는 경험을 지어낸다 | 근거는 도구만 준다. 이력서 원문에 없는 문장은 **지운다** |
| 모르는 걸 부족으로 센다 | "판정 불가"는 점수에서 빼고 되묻는다 |
| 공고를 지어낸다 | 추천은 실제 공고 DB에서만. 없으면 **빈 결과 + 솔직한 안내** |
| 무거운 작업을 말없이 시작한다 | 사용자가 청하지 않은 수십 초짜리 작업은 **먼저 묻는다.** 전에는 AI가 "이건 제가 끼운 겁니다"라고 **신고해야** 물었는데, 신고 칸을 비우면 그냥 돌았다 — 이제 **모르면 묻는다**(안전한 쪽이 기본값) |
| 엉뚱한 담당자를 부른다 | AI가 고를 수 있는 이름을 목록으로 **제한**한다(없는 이름은 애초에 못 낸다) |
| AI가 실패했는데 그럴듯한 답이 나간다 | 실패하면 **이유를 반드시 기록**한다. 조용히 넘어가지 않는다 |
| 사용자 대신 지원·제출을 해 버린다 | **그런 기능을 아예 만들지 않았다.** 최종 결정은 사람 |

> 공통 원칙: **"하지 마세요"라고 부탁하지 않고, 할 수 없게 만든다.**
> AI에게 부탁한 금지는 실제 테스트에서 지켜지지 않았다.

## 7.5 웹 서비스와는 어떻게 연결되나 — 브릿지 2종

이 AI 는 웹 코드에 섞여 있지 않다. **브릿지**라는 얇은 번역층 하나를 사이에 두고 HTTP 로만
만난다. 브릿지는 "웹이 쓰는 말"과 "AI 가 쓰는 말"을 번역할 뿐, **흐름을 정하지 않는다** —
무엇을 할지는 항상 위의 여섯 관문(플래너·검증기)이 정한다.

| 브릿지 | 상대 | 계약 |
|---|---|---|
| `webbridge` | 기존 백엔드 | WebSocket 분석 대화 + 단발 HTTP (자료 파편화·로드맵 등) |
| `v2bridge` | 서비스 v2 백엔드 | HTTP 4종 — 대화 / 공고 분석 / 커리어 조각 추출 / 증빙 검증 |

v2 백엔드는 환경변수(`AI_SERVER_URL`) 하나로 AI 서버를 고르므로, **주소만 바꾸면** 임시
어댑터 대신 이 에이전트가 대화·분석을 전부 받는다. 상세: `docs/v2bridge.md`.

## 8. 직접 확인하는 법 (개발자용)

이 문서를 믿지 말고 코드에 물어볼 수 있다.

```bash
# 담당자 목록·시작 조건·산출물·한 턴의 관문·규칙을 전부 출력
uv run --extra prototype python -m jobis_ai.explain

# "이력서와 공고가 있는데 자소서를 요청하면 무슨 일이 일어나나"
uv run --extra prototype python -m jobis_ai.explain --assets resume,job_posting --plan coverletter_draft

# 회귀 테스트 (AI 호출 없이 1초대, 비용 0)
uv run --extra dev --extra prototype pytest -q
```

`explain`은 **문서가 아니라 코드에서 값을 읽어** 출력한다. 문서는 낡을 수 있지만 이건 안 낡는다.

## 9. 지금 이 시스템이 얼마나 믿을 만한가 (측정치)

| 무엇을 쟀나 | 결과 |
|---|---|
| **누구를 부를지 제대로 고르나** (46가지 상황 × 3회) | 정확도 **0.978** |
| **물어야 할 때 묻나** (실행 대신 되묻기) | **1.000** |
| **같은 말에 같은 답을 하나** (재현성) | **1.000** ← 0.986 에서 개선 |
| 상황에 따라 답이 흔들리는 경우 | **0건** ← 2건에서 개선 |
| 일관되게 틀리는 상황 | **1건** (아래 참고) |
| 판정·규칙 회귀 테스트 | **506건 통과** (2초 안팎, AI 호출 없음) |

> 위 표의 라우팅·재현성 수치는 2026-07-29 측정값이다. 이후(07-30) 바뀐 것은 플래너
> 프롬프트가 아니라 그 **뒤의 계산 규칙**(수집 삽입·확신 예외)이라 재측정 없이 유효하다.

측정 방법과 남은 문제는 `docs/eval-records/` 에 날짜별로 기록돼 있다.
숫자만 적지 않고 **무엇을 왜 쟀고 무엇이 아직 안 됐는지**까지 함께 적어 두었다.

### 아직 안 되는 것 (솔직하게)

- **자료가 하나도 없는데 "내 이력서 진단해줘" 라고 하면** 엉뚱한 담당(선호 파악)이 받는다.
  전에는 상황에 따라 흔들렸고 지금은 **일관되게** 그쪽으로 간다 — 흔들리는 것보다 낫다
  (원인을 짚을 수 있으므로). 고치는 방향은 담당자 설명을 좁히는 것이고, 규칙을 더 넣는
  방향은 이미 한 번 시도해 실패했다(다른 상황 4건이 같이 깨졌다).
- 추천 품질(사용자가 실제로 만족하는가)은 **아직 측정하지 않았다.** 지금 측정한 것은
  "누구를 부르는가"와 "같은 답을 내는가"이지 "좋은 답인가"가 아니다.
- 실제 의미 검색(RAG)이 아직 연결되지 않아, 공고 추천은 키워드 기반이다.
- 공고 페이지에 회사 전체 기술스택 블록이 있으면 "요구 기술" 목록이 그만큼 부풀 수 있다
  (요건 섹션 밖의 기술까지 센다). 요건 판정(필수/우대)은 섹션 기준이라 영향이 없다.
