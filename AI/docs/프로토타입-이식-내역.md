## 1. 가장 크게 도움이 된 두 가지 (효과가 측정된 것)

### ① 조건엣지 — "판정이 나쁘면 코드가 끊는다"

`agent/graph.py::_route_after_tools` 가 `analyze_gap` 직후 level 을 읽어 중/하면 대체직군 검색을
**강제**하고 상이면 그냥 끝내는 구조요. LLM 재량이 아니라 엣지라는 점이 핵심이었습니다.

저희는 **같은 성격의 규칙을 LLM 관찰에 맡겨 뒀고, 실측에서 한 번도 발동하지 않았습니다.**
가장 중요한 제품 규칙을 부탁으로 두고 있던 셈이었고, 그걸 이 구조를 보고 알았습니다.

- **지금 위치**: `src/jobis_ai/orchestrator/observe_rules.py::weak_grade_transition`
  (주석에 `_route_after_tools` 를 원형으로 명시해 뒀습니다)
- **동작**: 적합도 등급 `하`·`판정불가` + 자소서·면접이 예정돼 있으면 → 빼고 `application_plan`
  (목표 상태·지원 경로)로 교체하고, 왜 바꿨는지 사용자에게 말합니다.
- **실측 발동 기록**:
  ```
  planner:  원안=['fit_analysis','coverletter_draft']
  agent:    fit_analysis 완료 → 등급 '하' (0.30)
  forced:   등급=하 → 큐 교체 ['application_plan']
  ```
  풀턴 일관성 평가에서도 같은 전이가 잡혔습니다.

### ② N회 일관성 평가 — "1회 측정으로는 정확도를 말할 수 없다"

`tests/eval.py` 가 케이스당 3회 돌려 **궤적 불변식**(`search ⟺ level ∈ {중,하}`)을 보고,
*"level 값은 중/중/하로 흔들렸으나 궤적은 동일"* 까지 기록해 둔 부분이요.

이 관점이 저희 쪽에서 **바로 값을 했습니다.** 저희는 플래너 정확도를 "46케이스 100%"로 적어
두고 있었는데, 그게 **1회 측정치**였고 재측정해 보니:

| | |
|---|---|
| baseline 저장 | 2026-07-27 **16:24** (46/46, 1회) |
| 프롬프트 규칙 추가 | 같은 날 **21:42** (`fbc876d`) — 5시간 뒤 |
| 그 뒤 프롬프트 변경 | 07-28 에 3회 더 |
| 재측정 | **없었음** |

즉 **그 100% 는 이미 죽은 숫자**였고, 3회로 재니 0.67 이었습니다. 이걸 못 찾았으면 오늘 개선을
"기존 100% 에서 떨어졌다"로 오독했을 겁니다.

- **지금 위치**: `src/jobis_ai/eval/consistency.py`(풀턴, docstring 에 출처 명시) ·
  `src/jobis_ai/eval/loop_consistency.py`(자기 루프 궤적, 오늘 신설)

**그리고 지표를 한 칸 발전시켰습니다.** "일관성 k/N" 하나는 *정확도*와 *안정성*을 섞어서, 0/3 을
볼 때 **일관되게 틀린 것**(명세·프롬프트 결함 — 재실행해도 안 나음)인지 **무작위로 틀린 것**
(flaky — 온도·경계 애매)인지 구분이 안 됩니다. 처방이 다르므로 갈라 셌습니다:

```
accuracy   기대와 일치한 run 비율
stability  최빈 결과가 차지한 비율 (정답 여부와 무관)
verdict    stable-correct / stable-wrong / unstable
```

이 구분이 실패 17건을 **세 원인으로 갈랐습니다** — 데이터셋 낡음 8건 / 프롬프트 과잉 적용 5건 /
진짜 flaky 4건. 섞어 봤다면 전부 "불일치"로 뭉쳐서 온도·프롬프트 경화를 헛되게 뒤졌을 겁니다.
최종적으로 정확도 **0.9783** · 되묻기 **1.0000** · 안정성 **0.9855** 까지 갔고,
그 여정의 출발점이 이 관점이었습니다.

## 4. 뺀 것 하나 — 먼저 밝힙니다

`agent⇄tools` 루프를 저희 오케스트레이터 계약으로 이식한 `ObserveDecision`(에이전트 실행마다
경량 LLM 이 `continue/finish/call` 을 내는 것)을 **오늘 제거하고 결정론 규칙으로 교체했습니다.**

**왜**: 그건 프로토타입 루프의 **열화 모방**이었습니다. 세 성질을 비교하면 —

| | 프로토타입 `agent⇄tools` | 저희 `observe_after` |
|---|---|---|
| LLM 이 보는 것 | **전체 메시지 히스토리** | 요약(reply 300자·dataKeys·경고코드…) |
| LLM 이 고르는 것 | **실제로 할 행동**(툴 호출) | `continue/finish/call` — **제어 신호** |
| 최종 답변 | **LLM 이 직접 씀** | 쓰지 않음 |

정보는 요약으로 잘리고 권한은 제어 신호로 좁혀져 있었습니다. 실측에서 `call` 0건이었고,
**자기 자리의 실제 위험도 못 막았습니다** — 판정이 실패해 `analysis` 가 없는데 자소서가
`analysis=None` 위에서 돌고 있었습니다(재현 확인). 그래서 그 자리는 규칙으로 내렸습니다.

**루프 자체는 살아 있고, 오늘 오히려 넓혔습니다.** 도구를 골라 쓰며 스스로 도는 구조는
`agents/agent_loop.py` 에 있고 — 채택 2 → **3**(`preference_intake` 추가), 스텝 상한 3 → **5**,
**대화 이력을 매 스텝 입력에 추가**(프로토타입의 "전체 히스토리"에 해당). 궤적도 처음 측정했습니다:

```
coverletter_draft   2/5  find_evidence>save_draft>check_draft
                    2/5  find_evidence>save_draft>check_draft>save_draft   ← 자기비판 재작성
                    1/5  find_evidence>ask_agent>save_draft>check_draft    ← 옆 담당에게 물어봄
```

최대 4스텝이라 **상한을 3에서 올린 것이 사후 정당화**됐습니다(3이면 재작성·위임 궤적이 잘립니다).
D11 의 "툴 선택은 LLM, 분기는 조건엣지"를 오늘 저희가 관찰 층에 그대로 적용한 셈입니다.

## 7. 그 뒤 바뀐 것 (07-29 밤 추가) — 가져온 것들의 후속

이 내역서를 쓴 뒤 본체를 다시 냉정하게 훑어 다섯 군데를 지적했고, **셋을 고치고 둘은 제가
틀렸습니다.** 그쪽에서 가져온 아이디어와 직접 닿는 부분만 적습니다. 결정 기록은
`docs/decisions.md` D50~D54 입니다.

### ① 조건엣지(→ `weak_grade_transition`) 의 부수 효과가 하나 더 나왔습니다

규칙이 계획을 바꾸면 **답변 첫 문장이 하지 않은 일을 하겠다고 말하는** 문제가 있었습니다
(자소서를 미뤄 놓고 "자기소개서 초안을 작성하겠습니다"로 시작). 플래그를 하나 더 걸어 막았다가
**같은 자리에서 세 번째로 재발**해서, 조건이 아니라 구조를 바꿨습니다 — 턴의 문장을 조립하는
자리를 함수 하나(`compose_reply`)로 모으고 규칙을 한 문장으로 못 박았습니다:
*"계획 설명은 다른 화자가 대신할 수 없을 때만 실린다."* 불리언 세 개가 사라졌습니다(D51).

> 그쪽 구조에서 이 문제가 안 보이는 이유는 **화자가 하나**여서입니다(`reply` = LLM 최종 답변
> 한 줄). 저희는 첨부 확인·계획 설명·에이전트 발화·규칙 설명 네 화자가 한 문장을 공유합니다.
> 멀티턴·다중 에이전트로 가면 생기는 비용이고, 미리 알고 계시면 좋을 것 같습니다.

### ② `MAX_STEPS` 가드에서 배운 것 — 동의 게이트를 **fail-closed** 로 바꿨습니다

"무거운 작업(수십 초)은 사용자가 청하지 않았으면 먼저 묻는다"는 게이트가 있는데, 그 입력이
**LLM 자기신고**였습니다("이건 제가 전제로 끼웠습니다"). 모델이 그 칸을 비우면 게이트가
**통과**였고, 실제로 새서 파이프라인이 말없이 돌았습니다. 스키마를 긍정형(*사용자가 직접 청한 것만
적어라*)으로 뒤집어 **모르면 묻게** 했고, 동의는 세션에 기록해 코드가 확인합니다.
46케이스×3회 재측정에서 정확도는 그대로(0.9783)인데 재현성이 0.9855 → **1.0000** 이 됐습니다(D50).

### ③ 지연 비교 — 그쪽에 자료가 없다고 적었던 그 자리, 저희 수치를 갱신했습니다

독립 3개 동시 실행: **순차 47.8·48.0초 vs 병렬 13.3·37.6초**(claude_code/sonnet).
비교하실 때 쓰시라고 남깁니다. 참고로 저는 이 병렬 구조를 "복잡도만 크고 이득은 몇 초"라고
지적했다가 **재측정에서 틀렸음이 드러났습니다**(D54) — 규모만 보고 판단하면 이렇게 됩니다.

### ④ `analyze_gap` 는 여전히 §5 그대로입니다

돌려드린다고 적은 두 가지(`try/except` 부재 · 룰 매칭의 거짓 양성)는 아직 그쪽 코드에
남아 있는 것으로 보입니다. 특히 후자는 **"Java 3년 이상" × 프로필의 "Java" = 충족**으로
연차·수준을 무시하기 때문에 등급이 상 쪽으로 부풀 수 있습니다. 그쪽 `decisions.md` D16
(LLM-as-judge 전환)이 같은 문제를 이미 짚고 있으니, 그 결정을 실행하시는 게 맞아 보입니다.
