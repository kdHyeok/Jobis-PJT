# AI 파트 중간 회고 (2026-07-24)

> 중간발표 시점 기준. 무엇을 만들었고, 왜 그렇게 설계했으며, 어디까지 검증됐고, 무엇을 개선할지.
> 구조 상세는 [`agent-structure-current.md`](./agent-structure-current.md),
> 발전 과정은 [`agent-structure-evolution.md`](./agent-structure-evolution.md) 참조.

## 1. 한 줄 정의

**사용자의 상태를 진단하고 솔루션을 제공하는 취업 준비 멀티에이전트 서비스** —
판정은 데이터가 하고, 행동은 사람이 확정하고, 조합은 에이전트가 정한다.

이 프로젝트의 핵심은 무언가를 자율적으로 창조하는 AI가 아니라, **진단·처방 서비스에
에이전틱 요소를 녹여내는 것**이었다. 자율성에 매몰되지 않고 솔루션의 퀄리티를 기준으로,
하네스 엔지니어링을 통해 **에이전트에게 자율성을 부여할 부분과 차단할 부분을 구분해 설계**했다.

## 2. 만든 것 (구조 요약)

```
사용자 ↔ 자연어 대화
   │
① 오케스트레이터 — 의도분류[LLM, 라벨만] → 라우팅 대응표[순수 파이썬] → 세션
   │  판단하지 않는다. 해석·검사·조립·중계·중단만 한다.
   ▼
② 전담 에이전트 6종 — 적합도 분석 · 공고 추천 · 이력서 진단
   · 자소서 초안 · 로드맵 관리 · 면접 준비
   │  서로의 존재를 모른다. 호출은 전부 오케스트레이터가 한다.
   │  판정이 상류, 생성이 하류 — 생성 에이전트는 판정 결과의 소비자.
   ▼
③ 판정 엔진 (적합도 분석의 본체, 10노드 결정론)
   │  4단 매칭 캐스케이드 → 가중 평균 → 임계값 등급(상0.7/중0.4)
   ▼
④ 인간 게이트 — 초안까지만. 제출 툴 미보유로 최종 행동은 사람만 가능.
```

- **LLM이 하는 일은 3종뿐**: 비정형 읽기(공고·이력서 추출), 서술형 요구 의미판정(이진, 센서 역할),
  자연어 표현(요약·자소서 초안). 판정·비교·집계·라우팅은 전부 코드.
- 6종 중 LLM을 쓰는 생성 에이전트는 자소서 초안 하나. 이력서 진단·로드맵 관리·면접 준비는
  판정 산출물을 조립하는 순수 룰이다.

## 3. 핵심 설계 결정과 근거 (Q&A 정리)

### 3.1 판정을 LLM이 아니라 코드로

- **근거(실측)**: 첫 버전(7/15)이 LLM 판정이었고 실패를 직접 겪었다 — 같은 입력에 흔들리는
  판정, 근거 없는 결론, 지어낸 로드맵. LLM이 원문에 없는 근거 문장을 창작하는 것도 로그로
  잡았다(hallucinated_evidence). 코드 전환 후 모델을 교체해도 판정 불변(fitGrade "중") —
  신뢰성이 모델이 아니라 코드에 있다는 실증.
- **근거(원리)**: LLM은 확률적 토큰 생성기라 "비교"라는 연산 자체를 하지 않는다 — 비교 결과처럼
  보이는 텍스트를 생성할 뿐이며, 요구사항을 빠뜨려도 없는 강점을 만들어도 스스로 모른다.
  우리는 비교를 실제 자료구조(사전 조회·집합 연산·반복문)로 구현해 전수성·재현성·근거를 보장한다.
- LLM이 개입하는 서술형 의미판정도 LLM은 "관련 문장 번호"만 내는 센서이고, 그 신호를
  충족/미충족/판정불가로 해석하고 집계하는 것은 코드 규칙이다.

### 3.2 되묻기·분기를 룰로

- "판정 불가 50% 초과면 되묻기"는 파이썬 if(임계값 상수)다. 어려운 판단은 상류 매칭 엔진이
  이미 끝냈고 게이트에 남은 건 산수라, LLM을 쓰면 정확성은 안 오르고 비일관성만 산다.
- "분석할 정보가 충분한가 ≠ 이 사람이 충분한가" 경계를 blocking 플래그로 코드에 못 박았다 —
  프롬프트 부탁으로는 보장 불가능한 제품 철학.

### 3.3 오케스트레이터 — dispatch만, judge 금지

- LLM은 발화→의도 라벨 번역만(7개 라벨, 판단 필드 없는 스키마). 어떤 에이전트를 어떤 순서로
  부를지는 (의도 × 세션 보유 자산) 대응표가 확정 — 전수 테스트 가능.
- 시퀀스는 실행 전에 확정되고, 실행 중에는 산출물을 세션에 실어 중계 + "추가 정보 필요" 신호 시
  중단만 한다. 결과 내용 기반 분기(등급별 처방·재시도)는 에이전트 내부 결정론 라우터의 일 —
  판단의 위치를 계층별로 갈랐다.
- ⊕ 전제조건 자동 합성: 분석 없이 자소서를 요청하면 표에 적힌 2단 시퀀스대로 분석을 먼저 실행.

> **[07-24 갱신]** 팀 결정으로 라우팅을 **LLM 플래너 + 결정론 검증기**로 전환했다
> ([`llm-planner-design.md`](./llm-planner-design.md)). LLM이 capability manifest(레지스트리)에서
> 호출할 에이전트를 직접 고르되, 선택지는 스키마(Literal)로 제한하고 전제조건 검사·전제 자동
> 삽입·되묻기는 순수 코드(`validate_plan`)가 확정한다 — "LLM은 여전히 판정하지 않는다.
> 선택하되, 실행 가능 여부는 코드가 확정한다." 위 대응표는 LLM 미설정·실패 시 폴백으로 유지.
> 평가셋 41케이스 실측: 플래너 정확도 **100%** (폴백 78.0%).

### 3.4 자율성의 지도 — 있는 곳 7, 없는 곳 2

- **자율성 있음**: ①의도 해석 ②실행 계획 조립(⊕) ③멈추고 되묻기(충분성 게이트)
  ④판정 불가 자기 인식(uncertain) ⑤등급별 처방 분기 ⑥자기 검증·재시도 루프
  ⑦도구 캐스케이드(룰→LLM 선택)
- **자율성 차단(의도적)**: 판정(결정론)·최종 제출(툴 미보유). 차단은 부탁이 아니라 구조다.

### 3.5 하네스 엔지니어링 7겹

① 출력 스키마 제약(줄 수 없는 답은 스키마에서 뺀다) ② 도구 통제(제출 툴 미보유)
③ 재료 통제(자소서는 룰이 조립한 facts 안에서만) ④ 출력 검증(원문 대조·verify 룰 4종)
⑤ 제어 흐름 코드화(라우팅 표·조건부 엣지·재시도 예산) ⑥ 실패의 정직한 처리(가짜 결과 대신
빈 결과+경고, None≠0.0) ⑦ 인간 게이트+라우팅 가시화. — 모델은 소모품, 자산은 하네스.

### 3.6 왜 멀티에이전트인가

기능마다 신뢰를 버는 방식이 다르다(판정=틀리지 않음 / 생성=사람이 검토 / 대화=확인 가능).
단일 에이전트로 뭉치면 가장 불안정한 부분이 전체 신뢰를 오염시키고, 역할이 좁아야 가능한
스키마 제약도 사라진다. 분리 덕에 계층별 검증·기능별 모델 최적화·산출물 재사용(세션 캐시)·
새 기능의 저비용 추가(면접 준비 = 판정 소비자 하나)가 성립했다.

## 4. 검증 현황

| 계층 | 방법 | 상태 |
|---|---|---|
| 판정 | 결정론 회귀 테스트(LLM 없이 1~2초, 0원) + 평가 하네스(F1·근거성·정책·로드맵 준수) | ✅ 144건 |
| 생성물 | 매 요청 런타임 검증 — 원문 대조 + verify 룰 4종, 실패 시 재분석 | ✅ 작동 |
| 대화 | 의도분류 평가셋(정확도·되묻기 비율) + 라우터 전수 테스트 | ⬜ 구축 예정 |
| 성능 | 노드별 실측 — 첫 분석 턴 ~81초(gpt-5.4), 판정 계층 0초대, 이후 턴 수 초 | ✅ 실측 완료 |

**외적 타당성의 한계(정직하게)**: 지금 검증은 "판정이 규칙대로, 근거 있게 내려졌는가"(내적
타당성)까지다. 등급 경계(0.7/0.4)·카테고리 가중치는 도메인 휴리스틱이지 실제 합격 데이터로
보정된 값이 아니다. 다만 판정이 파라미터화된 결정론이라 **데이터가 쌓이면 보정 가능한
구조**라는 점이 핵심 — LLM 판정이면 보정이라는 행위 자체가 성립하지 않는다.

## 5. 잘한 것

1. **실패를 겪고 방향을 바꾼 기록이 있다** — LLM 파이프라인(7/15) → 진단 → 결정론 전환.
   "판단은 데이터가, LLM은 말만"이 경험에서 나온 원칙이라 방어가 된다.
2. **금지를 프롬프트가 아니라 구조로** — 스키마 필드 제거·툴 미보유·룰 게이트. 일관된 전략.
3. **모른다≠아니다** — uncertain 개념이 판정·임베딩 폴백·RAG 미연결 폴백까지 관통한다.
4. **계층별 신뢰성 계약 분리** — 테스트·배포·모델 선택이 전부 계층 단위로 독립.
5. **실측 기반 의사결정** — 임베딩 폐기, 의미판정 배치화, 모델 교체 전부 측정하고 결정했다.

    운영 후 실제 지원 결과 추적(예측 등급 vs 서류 통과 일치율), 전문가 벤치마크.

12. **tool-calling 플래너(Phase 6)** — 표로 커버 안 되는 자유 조합 수요가 실제로 쌓이면
    capability manifest 위에 얹는다. 수요 확인 전에 미리 짓지 않는다.
13. **행동 계층 P1(환경 대면)** — 지원 폼 자동 읽기·채우기(브라우저). 인간 게이트(P5)와
    제출 차단(P6 툴 미보유)이 전제.

## 7. 마무리 — 이 프로젝트가 증명하려는 것

에이전트 제품의 경쟁력은 어떤 모델을 쓰느냐가 아니라 **모델을 어떤 구조로 묶느냐(하네스)**에서
나온다. 우리는 자율성을 목표가 아니라 도구로 다뤘고, 솔루션 퀄리티를 기준으로 자율성의 자리를
설계했다. 그 결과 — 워크플로우처럼 믿을 수 있고, 에이전트처럼 알아서 움직이는 서비스.

**판정은 데이터가, 행동은 사람이, 조합은 에이전트가 한다.**
