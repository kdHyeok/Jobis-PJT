# 전체 구조 — 에이전트는 이 서비스 어디에 꽂혀 있는가

> **읽는 사람**: 프론트·백엔드·RAG 어느 파트든, "AI 에이전트가 도대체 시스템 어디에 붙어 있고
> 무엇을 주고받는가"를 한 번에 알고 싶은 사람.
> **쓰는 기준**: 문서가 아니라 **코드를 읽어서** 적었다. 파일 경로가 함께 적힌 문장은 그 파일이 근거다.
> 코드와 이 문서가 어긋나면 코드가 맞다(`AGENTS.md` §0).

**한 문장으로**: 프론트는 AI 를 모르고, 백엔드만 AI 를 안다. 백엔드는 AI 를 **HTTP 5개 문**으로만
부르고, AI 는 그 문 안에서 "누가 이 턴을 맡을지"를 매번 새로 정해 에이전트를 돌린다.
그리고 AI 는 자기 DB 를 진실로 삼지 않는다 — **매 요청에 실려 온 것이 문맥의 전부**다.

## 1. 경계와 계약 — AI 로 들어가는 문은 5개뿐

`AI/src/jobis_ai/v2bridge/app.py` 가 전부다. 이 파일에 없는 경로는 백엔드가 부를 수 없다.

| 문 (엔드포인트) | 부르는 쪽 | 언제 | 무엇이 오고 | 무엇이 나가나 |
|---|---|---|---|---|
| `POST /v1/analyses` | `AnalysisWorker` | 공고 분석 잡을 집었을 때 | 공고 원문/URL + 사용자 커리어 스냅샷 + 이전 되물음 답변 | `COMPLETED` + 공고맥락·평가·역량제안, 또는 `NEEDS_INPUT` + 객관식 질문 1개 |
| `POST /v1/analyses/stream` | 같음(먼저 시도) | 위와 동일 | 같음 | **NDJSON** 진행 이벤트 → 마지막 줄이 결과 |
| `POST /v1/chat` | `ChatReplyWorker` | 대화 답변 잡 | 대화 이력 + 커리어 요약 + **세션 블롭** | 답변 문장 + 화자별 문장 + 진행단계 + `collected`(이번 턴 산출물) |
| `POST /v1/chat/stream` | 같음(먼저 시도) | 같음 | 같음 | NDJSON `progress`×N → `result` 1건 |
| `POST /v1/career-extractions` | `CareerExtractionWorker` | 이력서·포트폴리오 업로드 | 원문 텍스트 | 커리어 조각(경력·프로젝트·자격…) 목록 |
| `POST /v1/evidence-verifications` | `EvidenceVerificationWorker` | 증거 제출 | 증거 + 대상 역량 노드 | 판정·신뢰도·강점·격차·다음행동 |
| `POST /v1/competency-assessments` | `CompetencyAssessmentService` | 역량 검증 문답 한 턴 | 역량 정의 + 지금까지의 문답 | 직전 답 채점 + 다음 문제 |
| `GET /health`, `GET /v1/sessions/{id}` | 사람·모니터 | 아무 때나 | — | 상태·세션 요약(읽기 전용) |

**인증**: 모든 `/v1/**` 은 헤더 `X-JOBISS-AI-SECRET` 을 `compare_digest` 로 검사한다
(`app.verify_internal_secret`). 백엔드 쪽 값은 `jobiss.ai.shared-secret`
(`backend/src/main/resources/application.yml`). 사용자 토큰은 AI 까지 오지 않는다 — AI 는 사용자를
모르고, 서버 대 서버 신뢰만 쓴다.

**주소 한 줄로 갈아끼운다**: 백엔드는 `AI_SERVER_URL`(기본 `http://localhost:8000`) 하나로 AI 를 고른다.
그래서 가짜 AI ↔ 진짜 에이전트 교체가 환경변수 한 줄이다.

### 오류 코드가 곧 계약이다

AI 는 "그럴듯한 결과"를 만들지 않고 **실패를 실패로** 낸다(`AGENTS.md` §2-6). 백엔드 워커는 이 코드로
재시도 여부를 판단한다.

| 코드 | HTTP | 뜻 | 백엔드 행동 |
|---|---|---|---|
| `AI_PROVIDER_NOT_CONFIGURED` | 503 | LLM 미설정 — 가짜 성공을 만들지 않는다 | FAILED 기록 |
| `AI_PROVIDER_UNAVAILABLE` | 503 | 엔진이 결과에 못 이름 (재시도 가능) | 재시도/백오프 |
| `INVALID_AI_RESPONSE` | 502 | 산출물이 pydantic 계약 검증 탈락 | FAILED + 안내 문구 |
| `POSTING_TEXT_INSUFFICIENT` | 503 | 공고 원문이 부족 — **재시도해도 같다** | 사유 문장을 그대로 사용자에게 |
| `CAREER_DATA_REQUIRED` | 503 | 이력서가 없다 — 사용자가 할 일이 있다 | 사유 문장을 그대로 사용자에게 |

> 뒤의 두 코드가 왜 따로 있나: 백엔드 `AnalysisWorker.safeMessage` 가 `AI_PROVIDER_UNAVAILABLE` 을
> "AI 서비스 응답이 지연되었습니다"로 **덮어쓴다.** 실측(08-03)에서 "이력서를 등록해 주세요"라는 진짜
> 사유가 그 문구에 지워져, 화면에는 있지도 않은 장애만 남고 사용자가 할 일은 사라졌다.
> 코드를 갈라 내면 그 함수가 우리 문장을 그대로 저장한다. (`v2bridge/service.py` `EngineFailed`)

## 2. 경로 A — 공고 분석 (버튼 → 진행 휠 → 커리어 지도)

가장 무거운 경로. **끝에서 끝까지** 무엇이 지나가는지.

```
[프론트] 공고 붙여넣기/URL
   │ POST /api/job-postings  또는  POST /api/conversations/{id}/messages (posting 첨부)
   ▼
[백엔드] job_postings 행 생성 + analysis_jobs 행 생성(QUEUED) → 즉시 202 응답
   │                                   ↑ 프론트는 여기서 잡 id 를 받고 폴링 시작(2.5초)
   │ @Scheduled 3초마다 claim_analysis_job(worker) 로 한 건 집기
   ▼
[AnalysisWorker.loadRequest]  ── PostgreSQL 에서 문맥을 **긁어모은다**
   · job_postings              → posting{ id, sourceType, sourceUrl, rawText }
   · user_competencies         → career.nodes[]      (보유 역량 + 검증 레벨)
   · career_fragments(CONFIRMED) → career.fragments[] (경력·프로젝트·자격 조각)
   · user_goal_profiles        → career.goals        (현재 목표 공고 / 최종 목표)
   · analysis_questions(ANSWERED) → answers[]        (되물음에 사용자가 고른 답)
   · posting_analysis_cache    → sharedAnalysis      (같은 공고를 남이 이미 분석했으면 재사용)
   ▼ POST /v1/analyses/stream  (404/405 면 자동으로 /v1/analyses 단건 폴백)
[AI v2bridge.service.analyze]
   · 세션 id = "v2-analysis-{analysisJobId}"  → **매번 clear 하고 새로 세운다**
     (재시도가 와도 같은 자리에서 다시 시작 = 요청이 곧 문맥 전부)
   · sourceType 보다 **본문 내용이 사실이다**: TEXT 인데 내용이 주소 한 줄이면 URL 자산으로 취급
   · career 조각들을 텍스트로 합쳐 resume 자산으로
   · handle_chat 을 최대 4턴 돌린다 (되물음이 오면 규칙대로 답하고 재개)
        - confirm_* (동의 게이트)  → "네" (분석 요청 자체가 사용자의 실행 지시니까)
        - resume/job_posting 요청 → **대신 대답하지 않고** 사유 코드로 끝낸다
        - 그 밖의 질문           → 선택지 있으면 NEEDS_INPUT 으로 사용자에게 올림
   ▼ NDJSON 한 줄 = 한 이벤트
[AnalysisWorker.recordProgress] → analysis_agent_events 테이블 + analysis_jobs.stage 갱신
   ▼ 마지막 줄 RESULT
[AnalysisWorker.complete]  ── **여기가 유일한 writer**
   · job_postings          갱신(회사·직무·마감·parsed_data, URL 공고면 수집 원문 되메움)
   · posting_path_profiles (트랙·요구 경력 관문)
   · user_competencies     upsert  ← AI 가 낸 competencies[]
   · posting_competency_requirements ← requirements[] (REQUIRED/PREFERRED + 신뢰도)
   · posting_target_projects ← targetProject (목표 프로젝트 브리프)
   · posting_catalog / observations / duplicate_candidates (공용 카탈로그 승격)
   · posting_analysis_cache 적재 → 다음 사람은 같은 공고를 다시 분석하지 않는다
   · analysis_jobs.result_data = 정규화된 응답,  status=SUCCEEDED
   · notifications + conversation_messages(ANALYSIS_STATUS 카드)
   · RoadmapService.autoGenerateAfterAnalysis → 지도 자동 생성
   ▼ 폴링
[프론트] AnalysisProgressWheel 이 progressEvents 로 진행 휠을 그리고, 완료되면 커리어 지도로
```

### 여기서 꼭 알아야 할 세 가지

**① 등급(verdict)은 AI 가 정하지 않는다.**
AI 는 "무엇이 요구되는가"(역량·요건·경력 관문)를 낸다. `APPLY_NOW` / `STRENGTHEN_THEN_APPLY` /
`ALTERNATIVE_FIRST` 판정은 백엔드 `AnalysisWorker.evaluateReadiness` 가 **SQL 로** 센다
(검증된 필수 역량 n/m, 요구 경력 개월 대비 확인된 경력). 판단은 결정론, 표현은 LLM 이라는
원칙(`AGENTS.md` §1)이 서비스 경계 너머까지 이어진 자리다.

**② 같은 공고는 한 번만 분석한다.**
`content_fingerprint`(원문 정규화 SHA-256) + `clarification_fingerprint`(되물음 답변)를 키로
`posting_analysis_leases` 로 임대(lease)를 잡는다. 두 사람이 같은 공고를 동시에 넣으면 한쪽만
AI 를 부르고, 다른 쪽은 `WAITING_FOR_SHARED_ANALYSIS` 로 기다렸다가 캐시를 재사용한다.

**③ 진행 휠의 이벤트는 우리가 만든다.**
`v2bridge/stream.py` 가 지켜야 하는 불변식 — 어기면 그 잡이 FAILED 로 끝난다:
`runId == analysisJobId` / `sequence` 1부터 엄격 증가 / 첫 줄 `RUN_STARTED` / 마지막 줄 `RESULT` 또는
`ERROR` / `RESULT` 정확히 1건. 이벤트 1건 = 백엔드 DB 쓰기 1건이므로 한 분석당 예산 60건이고,
넘치면 진행 갱신만 멈추고(계획·결과·오류는 계속) 못 보낸 건수를 로그로 남긴다.

## 3. 경로 B — 대화 (채팅 한 줄 → 담당 에이전트들이 답)

```
[프론트 ChatView] POST /api/conversations/{id}/messages { content, posting? }
   ▼
[ConversationService] conversation_messages(USER) 저장
   · 공고가 첨부돼 있으면 job_postings + analysis_jobs 도 함께 생성(경로 A 동시 착수)
   · chat_reply_jobs 큐에 넣고 즉시 { chatReplyJobId, analysisJobId? } 반환
   ▼
[ChatReplyWorker.loadRequest] ── 대화 문맥을 **전부 실어 보낸다** (AI 는 저장소를 안 갖는다)
   messages[]      최근 대화 이력
   career.completedNodes / activeGoals / recentPostings / savedEvidence
   career.resumes[]      career_sources 원문 (최신 5)
   career.postings[]     이 대화에서 다룬 공고 + parsed_data (재파싱 방지)
   career.preferences    user_goal_profiles.chat_preferences
   career.facts[]        user_goal_profiles.chat_facts
   career.interview      interview_sessions.state
   career.sessionState   agent_session_state.state  ← **세션 블롭 전체**
   ▼ POST /v1/chat/stream
[AI] _seed_session_state 로 sessionState 를 **번역 없이 그대로** 복원 → handle_chat 1턴
   ▼ progress 줄이 생기는 즉시 흘러나온다
[ChatReplyWorker.recordChatProgress] → chat_reply_agent_events + chat_reply_jobs.stage
   ▼ result 줄
[ChatReplyWorker] · conversation_messages(ASSISTANT) 저장 (progress·replySources 포함)
                  · ingestCollected / ingestOutputs 로 collected 를 테이블에 투영(§5)
   ▼ 폴링(2.5초)
[프론트] 담당별 말풍선(agents.ts 의 색·아이콘) + 진행 단계 + 제안 액션
```

**왜 매 턴 이렇게 많이 실어 보내나**: AI 를 무상태로 두기 위해서다. AI 가 자기 SQLite 를 진실로
삼던 시절엔 그 파일이 없으면 사용자가 올린 이력서가 대화에서 사라졌다. 지금은 **PostgreSQL 이 진실**,
AI 세션은 캐시다.

## 4. AI 안쪽 — 한 턴에 무슨 일이 일어나나

`AI/src/jobis_ai/orchestrator/chat.py` `handle_chat` 이 본체다. 흐름이 **고정돼 있지 않다** —
매 턴 새로 정한다.

```
 발화 + 첨부
   │
 ① 인테이크 (결정론, LLM 없음)
   ·첨부의 종류를 내용으로 바로잡는다(공고라고 준 게 이력서면 이력서로)
   ·발화 속 URL 을 공고 자산으로 승격 (URL 은 공고 전용)
     단, 이미 저장된 분석이 있으면 채용사이트로 알아볼 수 있는 주소만 — 깃허브 링크가
     수십 초짜리 판정을 말없이 지우지 않게
   ·발화에 통째로 붙여넣은 이력서 원문 감지
   │
 ② 플래너 (LLM — 이 턴의 유일한 "무엇을 할까" 판단)
   ·입력: 발화 + 세션 자산 상태 + 최근 이력 + **에이전트 manifest**
   ·출력: 고른 에이전트 이름들 + 확신도 + 인자 + 이해확인 문장(ack)
   ·낼 수 있는 값은 레지스트리에 등록된 이름뿐 (스키마 Literal 로 강제 = 환각 차단)
   ·확신 < 0.6 이면 실행하지 않고 확인 버튼으로 남긴다(버리되 잃지 않는다)
   │
 ③ 검증기 (순수 코드 — router.validate_plan)
   ·전제 자산이 없는 에이전트는 제거하거나, 그 자산의 **생산자를 앞에 끼운다**
   ·예: 자소서를 청했는데 분석이 없다 → fit_analysis 를 앞에 삽입
   │
 ④ 게이트
   ·이력서 확인(공고당 1회): "어느 이력서로 볼까요?"
   ·동의 게이트: 사용자가 청하지 않은 **무거운(heavy)** 작업은 먼저 묻는다
     단, 묻는 동안에도 가벼운 담당(공고 정리 등)은 실행해 답한다
   │
 ⑤ 실행 (최대 5스텝, 서로 독립인 것은 최대 3개 병렬)
   ·에이전트는 세션을 직접 못 고친다 — AgentResult.sessionUpdates 로만 상태가 바뀐다
   │
 ⑥ 관찰 → 재선택 (결정론 규칙 — observe_rules)
   ·방금 결과를 보고 남은 큐를 다시 정한다. 판정이 실패했으면 그 산출물에 기대던 뒤 단계를 뺀다
   ·"뺐다" 다음의 "대신 뭘 할까"만 LLM 에게 턴당 1회 물어본다
   │
 ⑦ 조립 — 문장별 화자(replySources) + 되묻기 카드 + 경고를 붙여 응답
```

### 담당(에이전트) 로스터 — `agents/__init__.py`

**도구(tool)와 에이전트(agent)를 가르는 기준은 하나다: 말을 하는가.**
도구는 결정론 계산만 하고 문장을 만들지 않는다(문장은 `render` 가 만든다). 에이전트는 LLM 으로
자유도를 갖고 자기 루프(`agent_loop.py`)를 돈다.

| 이름 | 종류 | 전제 자산 | 하는 일 |
|---|---|---|---|
| `posting_fetch` | tool(내부) | job_posting | URL → 원문 승격. 플래너가 아니라 오케스트레이터가 결정론으로 끼운다 |
| `posting_analysis` | agent | job_posting | 공고 담당 대화 — 요건 정리·풀이, 이 공고 기준 학습 방향 |
| `resume_diagnosis` | agent | resume | 이력서 담당 대화 — 항목 정리·강점·보강 방향 |
| `fit_analysis` | **tool** | resume + job_posting | **판정 엔진 전체**(§6). heavy. `analysis`·`roadmap` 생산 |
| `job_recommend` | tool | resume **또는** preferences | RAG 로 실공고 추천 |
| `preference_intake` | agent | — | 공고 추천용 선호 수집 |
| `application_plan` | agent | analysis | 지원 경로 2~3개 + 목표 상태 |
| `coverletter_draft` | agent | resume + analysis | 자소서 초안 (쓰고 스스로 점검해 고친다) |
| `interview_prep` | agent | analysis | 면접 문답 (여러 턴 이어짐) |
| `roadmap_manager` | tool | roadmap | 저장된 로드맵 조회 |
| `career_chat` | agent | — | 기능 요청이 아닌 발화 + 자료 요청 폴백 |

`heavy=True`(지금은 `fit_analysis`)만 동의 게이트에 걸린다. `internal=True`(`posting_fetch`)는
플래너 눈에 안 보인다 — 필연적 단계를 LLM 이 고를 판단으로 만들지 않는다.

프론트 `frontend/src/agents.ts` 의 키가 **이 이름들과 같은 이름공간**이다. AI 는 화자 키만 보내고
색·아이콘은 프론트 한 곳에만 둔다(세 곳에 두면 갈린다).

## 5. 상태는 어디에 사는가 — "블롭 하나가 진실, 테이블은 투영"

AI 는 SQLite 세션(`AI/sessions.sqlite3`)을 쓰지만 그건 **캐시**다. 진짜 규약은 이렇다:

```
매 턴 응답  collected.outputs.sessionState  = 세션 자산 **전체**
              ▼ 백엔드가 agent_session_state.state 에 저장 (V23)
다음 요청   career.sessionState             = 그대로 되돌아옴
              ▼ AI 가 번역 없이 복원
```

번역 층을 없앤 이유: 예전엔 `resumes/postings/preferences` 를 세션 어휘로 번역하는 층이 셋 있었고,
그 번역이 에이전트의 "방금 받았나" 판단을 덮어써 단계별 행동이 무너졌다(D151·D152).

그 위에 **읽기 전용 투영**이 얹힌다 — 화면·조회·통계가 읽을 수 있게. writer 는 백엔드 하나다.
선언 표는 `v2bridge/persistence_map.py` 에 있고, 여기 없는 세션 키가 생기면 테스트가 깨진다
(= 조용한 유실 방지 장치).

| 세션 자산 | 투영되는 곳 |
|---|---|
| `resume` / `resume_library` | `career_sources` |
| `job_posting` / `posting_summary` / `posting_library` | `job_postings`(raw_text·parsed_data) |
| `preferences` / `user_facts` | `user_goal_profiles.chat_preferences` / `.chat_facts` |
| `analysis` / `roadmap` / `judgment_summary` | `analysis_jobs.engine_result` |
| `profile` | `ai_user_profiles` |
| `recommendations` | `posting_recommendations` |
| `coverletter` | `coverletter_drafts` |
| `interview` | `interview_sessions.state` |
| `application_plan` | `application_plans` |
| `pendingConsent` / `pendingRequest` / `resumeAskedFor` | 블롭에만 (대화 이력으로 복원 불가한 약속들) |

대화가 만든 지도 재료(`competencyProposal` + `jobContext`)는 특별하다: 채팅으로 공고를 다룬 턴에도
`collected.outputs` 로 나가고, 백엔드가 그걸 `posting_analysis_cache` 에 넣으면 **경로 A 의 기존
재사용 코드**가 집어서 적재한다 — 적재 코드를 복제하지 않는다(writer 는 하나여야 한다).

## 6. 판정 엔진 — `fit_analysis` 안에 있는 또 하나의 그래프

`fit_analysis` 는 에이전트가 아니라 **도구**이고, 그 안은 LangGraph다(`AI/src/jobis_ai/graph/`).

```
START ─┬→ parse_job_posting ──┐   (공고 파싱과 프로필 빌드는 병렬)
       └→ build_user_profile ─┘
                 ▼ (둘 다 끝난 뒤 합류: defer=True)
        check_profile_completeness → check_sufficiency
              ├ 부족 → ask_user → assemble_output      (모른다 ≠ 아니다: 되묻는다)
              └ 충분 → analyze_gap → plan_roadmap
                            └→ (필요시) find_alternatives  ← 여기서 RAG
                                     ▼
                              verify_result ─(재시도 or 통과)→ assemble_output → END
```

각 노드 뒤에 **산출물 검증 라우터**가 붙는다: 생성이 실패하면 다음으로 넘어가지 않고 같은 노드에
다시 지시하고, 재시도 예산을 다 쓴 뒤에만 진행한다. 상태는 `GraphState` 하나이고
`warnings`·`sources`·`toolLog` 는 누적 리듀서로 병합된다 — **왜 이 결과가 나왔는지**가 항상 따라붙는다.

## 7. RAG 는 어떻게 붙어 있나

에이전트는 **RAG 내부 구현을 모른다.** 아는 것은 `AI/src/jobis_ai/rag.py` 의 인터페이스 둘뿐이다.

```python
class RagAdapter(Protocol):
    def fetch_company_context(company_name, requirements) -> RagResult   # 기업 맥락
    def search(query, *, top_k=5) -> RagResult                            # 범용 검색
```

`RagResult = { items[], sources[], warnings[] }`. **실패해도 예외를 던지지 않는다** — 경고를 달고 빈
결과를 돌려준다. RAG 가 죽어도 그래프는 계속 돌고, 왜 결과가 얇은지는 warnings 에 남는다.

### provider 분기 (`RAG_PROVIDER`)

| 값 | 구현 | 동작 |
|---|---|---|
| `http` | `HttpRagAdapter` | 실 RAG 서버 호출. 실패하면 경고 달고 키워드 검색으로 강등 |
| `local_postings` | `LocalPostingsRagAdapter` | 크롤 공고 JSON(`sample_data/`)에 대한 키워드 검색 |
| `null`/미지정 | 공고 파일 있으면 local, 없으면 `NullRagAdapter` | 미연결 — 빈 결과 + 안내 |

### 실 RAG 와의 계약 (`RAG/RAG_입출력_명세서.md`)

```
POST {RAG_SEARCH_URL:-http://127.0.0.1:8765}/search
  { "input": "데이터 엔지니어" | {profile JSON}, "top_k": 5, "evaluate": false }
→ { "postings": [ 원본 공고 JSON + score + match_reason, ... ] }   0건이면 빈 배열
```

RAG 쪽(`RAG/jobrag/`)은 **PostgreSQL + pgvector** 위에서 하이브리드 검색(BM25 + 벡터, RRF 병합)
후 리랭커를 태운다. `evaluate=false` 로 CRAG 평가자(LLM 채점)는 끈다 — AI 저장소의 LLM 호출 규약을
지키기 위해서다.

### 어댑터가 추가로 하는 일

- **중복 제거**: 같은 공고가 work24·saramin 에 각각 크롤돼 있다. 회사명(법인격 표기 제거) + 제목
  (상태 표기 제거)으로 정규화해 지운다. 후보를 만드는 자리가 여기 하나뿐이라 중복 제거도 여기서 한 번만.
- **`company_context_unsupported`**: 검색은 붙어 있는데 *기업 맥락*을 낼 소스가 없는 경우를
  "미연결"과 구별한다. 붙어 있는데 미연결로 적으면 다음 사람이 없는 장애를 좇는다.
- **예열(`warm_search_async`)**: 공고·이력서가 채워진 시점에 그 자산 기반 쿼리를 한 번 쏘아 버린다.
  콜드 첫 쿼리가 30초를 넘긴 실측이 있어서, 그 대가를 사용자가 기다리기 전에 미리 지불한다.

**호출 지점**: `job_recommend`(추천), `graph/nodes.find_alternatives`(대안 공고),
`graph/nodes.analyze_gap`(기업 맥락), `agents/_common`(공용 검색).

## 8. 실패하면 어떻게 되나 (계층별)

| 어디가 죽나 | 무슨 일이 일어나나 | 사용자에게 보이는 것 |
|---|---|---|
| RAG 서버 | 키워드 검색으로 강등 + `rag_http_failed` 경고 | 결과는 나온다 (추천 근거가 얇아짐) |
| LLM(플래너) | 플래너 None → `career_chat` 이 턴을 받는다 | 대화는 이어진다. 대응표로 흐름을 대신 정하지 않는다 |
| LLM 전체 미설정 | `AI_PROVIDER_NOT_CONFIGURED` 503 | 잡 FAILED — **그럴듯한 폴백을 만들지 않는다** |
| 스트림 엔드포인트 없음/죽음 | 백엔드가 404/405·비-NDJSON 을 보고 단건 경로로 폴백 | 실시간이 아닐 뿐, 진행 단계는 최종 응답에 담겨 온다 |
| 스트림 중간 실패 | 이미 200 이 나갔으므로 본문에 `ERROR`/`error` 한 줄 | 워커가 그 코드로 잡을 실패 처리 |
| 계약 검증 탈락 | 502 `INVALID_AI_RESPONSE` + 무엇이 어긋났는지 로그 | "다시 분석" 안내 |
| 자료가 없음 | 사유별 코드로 즉시 종료 | 에이전트가 청한 그 문장이 화면까지 그대로 간다 |

관통하는 원칙 하나: **폴백은 이유를 삼키지 않는다.** 문장만 돌려주는 계약은 "왜 기본 문구가
나왔는지"를 지운다 — 이 저장소가 세 번 대가를 치른 실수다(`AGENTS.md` §2-6).

## 11. 마지막으로 — 이 구조가 지키려는 것 세 줄

1. **판단은 데이터가 하고, LLM 은 말만 한다.** 매칭·계산·검증·분기에 LLM 을 쓰지 않는다.
   등급 판정이 백엔드 SQL 에 있는 것도, 관찰-재선택이 규칙인 것도 같은 이유다.
2. **금지는 프롬프트가 아니라 구조로.** 플래너가 낼 수 있는 값은 스키마 Literal 로 제한하고,
   하면 안 되는 행동은 도구를 주지 않는다. "하지 마라"는 실측에서 지켜지지 않았다.
3. **모른다 ≠ 아니다, 그리고 폴백은 이유를 삼키지 않는다.** 판정 못 하면 되묻고, 강등되면
   왜 강등됐는지가 경고로 남아 화면·로그까지 간다.
