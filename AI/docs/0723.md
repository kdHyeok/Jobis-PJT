2. 그 에이전트의 **판단은 LLM이 아니라 파이썬**이 한다 — 재현되고 설명되는 진단을 위해.

## 슬라이드 1 — 우리 시스템은 챗봇이 아니라 에이전트다

**제목**: 한 번 답하고 끝나는 챗봇이 아니다 — 스스로 도는 AI 에이전트
**부제**: 입력 1회 → 10단계 자율 실행 → 스스로 검증하고, 모르면 되묻는다

### 레이아웃
좌 45% 흐름도 캡처(노드 10개 · **되돌아가는 순환 엣지가 보이게** 자를 것) · 우 55% 아래 표.

### ① LLM 챗봇과 무엇이 다른가

| | LLM 챗봇 | 우리 시스템 |
|---|---|---|
| 실행 | 질문 1회 → 답변 1회 | **입력 1회 → 10단계 자율 실행** |
| 도구 | 없음 (모델 안의 지식) | **17종 도구·내부 DB를 상황에 따라 선택** |
| 오류 | 사용자가 발견 | **스스로 검수하고 재분석** (검증 루프) |
| 정보 부족 | 그럴듯하게 지어냄 | **판정을 멈추고 되묻는다** |
| 산출물 | 텍스트 한 덩어리 | **구조화된 진단 + 로드맵 + 대안** (그대로 서비스에 연결) |

### ② 에이전트 구성 — 3계층 10개

| 계층 | 에이전트 | 구현 |
|---|---|---|
| **읽기** 2 | 공고 파싱 · 프로필 구축 | LLM (추출 전용) |
| **판단** 6 | **갭 판정 ★** · 충분성 게이트 · 로드맵 · 대체경로 · 검수 · 결측보완 | **순수 파이썬** (룰·DB·계산) |(정량적인 항목에서는 점수로직 기반으로 산출/정성적인 항목은 llm을 활용해서 알고리즘과 llm을 혼용하여 판정)
| **말하기** 2 | 최종 응답 조립 · 되묻기 | LLM (표현 전용) |

**데이터는 공유 상태(GraphState) 하나로만 오간다** — 에이전트끼리 직접 호출하지 않는다.

```
공고  ─▶ 정형 요구사항 ─┐
                       ├─▶ 갭 판정 ─▶ 로드맵 ─▶ 검수 ─▶ 최종 응답
이력서 ─▶ 프로필+근거 ─┘              └── 실패 시 재분석 ◀┘
```

> **말할 것(슬라이드엔 안 씀)**: 위에서 아래로 한 번 흐르는 파이프라인이 아니라 **되돌아가는
> 엣지가 있는 순환 구조**다. 그래서 "에이전트"다.

## 슬라이드 2 — 왜 판단을 LLM에 안 맡겼나

**제목**: 에이전트의 판단을 파이썬으로 구현한 이유
**부제**: "합격 가능성"은 재현되고 설명돼야 한다

### ① LLM에 맡겼다면 vs 파이썬으로 얻은 것

| LLM에 맡겼다면 | 파이썬으로 구현해서 얻은 것 |
|---|---|
| 같은 이력서에 매번 다른 진단 | **재현성** — 같은 입력이면 항상 같은 결과·같은 경로 |
| "왜 그렇게 봤는지" 설명 불가 | **근거 추적** — 판정마다 이력서 원문 문장 ID가 붙는다 |
| 없는 자격증·회사를 지어냄 | **환각 차단** — 자격증은 내부 DB, 대안은 실존 공고에서만 |
| 결과 검증 불가 | **자동 검증** — 산출물을 룰로 4단 검사, 실패 시 재분석 |
| 틀리면 프롬프트를 달램 | **수정 가능** — 룰 한 줄 고치면 끝, 회귀는 테스트가 잡는다 |

### ② 측정된 효과

| 지표 | 값 |
|---|---|
| 전체 회귀 테스트 | **144개 통과 / 1.8초 / API 비용 0원** |
| 요청당 LLM 호출 | **3회 고정** (재시도 포함 최대 5회) |
| 판정 로직의 결정론 비율 | **100%** — 점수·등급·갭 판정에 LLM 미개입 |
| 판정 근거 | 요구사항마다 **원문 근거 ID 연결** |

### ③ 정리 — LLM을 안 쓴 게 아니라, 쓸 자리를 골랐다
비정형 문서를 읽는 일과 결과를 사람 말로 옮기는 일은 룰로 안 된다 → **거기만 LLM**.
매칭·점수·기간 계산은 파이썬이 더 정확하고 빠르고 싸다 → **거기는 전부 코드**.

> **말할 것(슬라이드엔 안 씀)**: 테스트 1.8초의 의미 — 판정이 결정론이라 **LLM 없이 전 구간을
> 검증**할 수 있다. 고칠 때마다 즉시 회귀 확인 → 개발 속도가 붙는다.

## 부록 A — 예상 질문 대응 (발표자만 숙지)

**Q. 결국 GPT에 이력서 붙여넣고 물어보는 거랑 뭐가 다른가?**
챗봇은 한 번 답하고 끝이고 근거가 없다. 이건 10단계를 스스로 돌며 도구를 고르고, 산출물을
스스로 검수하고, 정보가 부족하면 되묻고, 모든 판정에 이력서 원문 근거를 붙인다.

**Q. (심화) 이력서+목표공고를 똑같이 GPT에 주고 분석시키면 차이 없지 않나?**
"내부 DB를 상황에 따라 고른다"만 내세우면 이 반박에 진다. 요즘 LLM은 웹검색·파일업로드로
외부 정보를 끌어오니 **"정보 소스를 고른다"는 더 이상 차별점이 아니다.** 진짜 차이는
소스가 아니라 **판정의 성질**에 있다 — GPT 붙여넣기가 구조적으로 못 하는 것들이다.

1. **재현성** — GPT는 같은 이력서를 두 번 물으면 "합격 65%→72%"로 흔들린다. 우리는
   점수·등급·갭 판정이 100% 파이썬이라 같은 입력이면 항상 같은 결과다. 서비스에서
   "어제와 오늘 진단이 다름"은 치명적인데 GPT 붙여넣기는 이걸 원천적으로 못 막는다.
2. **근거 추적(환각 차단)** — GPT는 "프로젝트 경험이 좋다"고 하지만 *어느 문장* 때문인지
   못 짚고, 없는 자격증·회사를 지어낸다. 우리는 판정마다 이력서 원문 문장 ID가 붙고,
   대안 공고는 실존 DB에서만 나온다.
3. **멈추고 되묻기** — 정보가 부족하면 GPT는 그냥 지어내 답을 채운다. 우리는 충분성
   게이트에서 판정을 멈추고 되묻는다.
4. **자기검증 루프** — GPT는 한 번 뱉으면 끝, 틀려도 사용자가 발견해야 한다. 우리는
   산출물을 룰로 4단 검사하고 실패하면 스스로 재분석한다.

> **답변 프레임**: "GPT에 붙여넣어도 *답은* 나온다. 하지만 그 답은 매번 다르고, 근거가
> 없고, 검증이 안 되고, 모르면 지어낸다. 서비스는 '답이 나오느냐'가 아니라 '같은 답이
> 재현되고 근거로 방어되느냐'로 판가름난다."
>
> **주의**: 슬라이드 1 ①표의 "도구: 내부 DB를 상황에 따라 선택" 행이 제일 약한 프레임이라
> 공격받기 쉽다. 차별점을 "정보 소스 선택" → "판정의 결정론성·근거성·검증가능성"으로
> 옮겨야 이 질문에 안 흔들린다.

**Q. 에이전트라면서 LLM을 왜 3곳만 쓰나?**
**에이전트는 LLM이 아니다.** 판단을 안 하는 게 아니라, 판단을 LLM이 아니라 알고리즘으로 한다.
자율성은 LLM 호출 횟수가 아니라 **스스로 도구를 고르고 검증하고 되묻는 능력**에 있다.

**Q. 다음 단계를 LLM이 정하는 구조(supervisor)인가?**
의도적으로 안 썼다. 실행 경로가 매번 달라지면 진단을 재현할 수 없다. 분기 조건을 전부 코드에
명시한 상태 머신이다.

**Q. 룰이 많아지면 유지보수가 어렵지 않나?**
그래서 판정을 한 곳(갭 판정)에 몰았고, 지식은 룰이 아니라 **데이터(자격증 DB·스킬 사전·커리어
그래프)** 로 뺐다. 새 스킬 추가는 코드가 아니라 사전 한 줄이다.
