# 자비스 프로젝트에서 멀티에이전트 구조의 당위성

자비스 프로젝트에서 멀티에이전트 구조를 선택해야 하는 이유는, 이 서비스가 단순 질의응답형 챗봇이 아니라 공고 분석, 사용자 이력 구조화, 갭 진단, 준비 로드맵 설계, 대체 경로 탐색, 결과 검증까지 이어지는 복합 업무 시스템이기 때문이다.[cite:21][cite:27] 자비스는 사용자가 채용공고와 자신의 자료를 입력하면 부족 역량을 분석하고 실행 가능한 준비 계획과 대체 취업 경로를 제안하는 개인화 취업 준비 AI 에이전트로 정의되어 있으며, 문서상 핵심 흐름도 여러 단계의 구조적 처리로 설계되어 있다.[cite:21]

## 자비스의 문제 구조와 멀티에이전트 적합성

자비스의 핵심 흐름은 목표 채용공고 입력, 사용자 이력 및 경험 선택, 공고 요구사항 구조화, 사용자 경험과 비교, 부족 역량 및 강점 분석, 준비 우선순위 결정, 기간별 준비 로드맵 생성, 유사 직무·대체 공고 제안으로 정리되어 있다.[cite:21] 이는 하나의 프롬프트로 답을 생성하는 단일 에이전트보다, 역할을 나눈 여러 에이전트가 순차적으로 협력하는 구조에 더 잘 맞는 업무 형태다.[cite:21][cite:27] 멀티에이전트 시스템은 공유된 목표 아래 여러 자율적 컴퓨팅 개체가 협력하는 구조로 정의되며, 복합적이고 상태 의존적인 문제에 특히 적합하다고 설명된다.[cite:27]

## 역할 분리가 필요한 이유

자비스는 적어도 공고 구조화, 사용자 프로필 구조화, 갭 분석, 로드맵 설계, 대체 경로 추천, 결과 검증이라는 성격이 다른 판단들을 수행해야 한다.[cite:21] 이 역할들을 하나의 거대한 에이전트에 몰아넣으면 어떤 판단이 어느 근거에서 나왔는지 추적하기 어려워지고, 디버깅과 품질 개선도 힘들어진다.[cite:18][cite:21] 반대로 역할 기반 멀티에이전트 구조를 쓰면 각 에이전트가 자신이 소유한 입력과 출력에만 집중할 수 있어 설명 가능성과 책임 경계가 선명해진다.[cite:13][cite:25]

예를 들어 공고 분석 에이전트는 “이 공고가 무엇을 요구하는가”만 구조화하고, 사용자 이력 에이전트는 “사용자가 실제로 무엇을 해봤는가”를 정리하며, 갭 분석 에이전트는 둘의 차이를 판정하는 식으로 나눌 수 있다.[cite:13][cite:21] 이렇게 분리하면 사용자가 결과에 의문을 제기했을 때, 어떤 단계에서 어떤 기준으로 해당 판단이 나왔는지 추적 가능한 구조를 만들 수 있다.[cite:18][cite:21]

## 사람과 에이전트의 협업 구조에 유리함

자비스는 완전 자율형 시스템보다 human-in-the-loop, 즉 사람의 수정과 승인을 중간 단계에 포함하는 구조가 더 적합하다.[cite:12][cite:21] 문서에서도 공고 구조화 결과 확인, 사용자 이력 구조화 수정, 갭 분석 이후 추가 질문, 로드맵 수정 기능 같은 확인 지점이 자연스럽게 전제되어 있다.[cite:21] 이런 서비스에서는 각 단계별 결과를 사용자에게 보여주고 수정받아야 하므로, 단계별 책임이 분리된 멀티에이전트 구조가 UX와 신뢰 형성에 더 유리하다.[cite:12][cite:18]

단일 에이전트 구조에서는 내부 판단 과정을 사용자에게 끊어서 보여주기 어렵고, 사용자는 단순히 “폼을 넣고 LLM 결과를 받는 서비스”로 인식하기 쉽다.[cite:18] 반면 멀티에이전트 구조는 오케스트레이터가 현재 어느 단계가 진행 중인지 제어하고, 각 에이전트의 결과를 검토·승인 포인트로 연결할 수 있어 에이전트 팀이 협업하는 느낌을 만들기 쉽다.[cite:21][cite:28]

## 신뢰성과 검증 측면의 이점

자비스는 취업 준비라는 민감한 영역을 다루기 때문에, “합격 가능”이나 “지원 불가” 같은 과도한 표현을 피하고 근거 중심의 조언을 제공해야 한다.[cite:21] 문서에서도 피해야 할 표현과 권장 표현이 별도로 정리되어 있고, 점수 역시 보조적으로만 사용해야 한다고 명시되어 있다.[cite:21] 이런 제약은 생성 에이전트와 별도로 검증 에이전트 또는 검증 레이어를 두는 구조와 잘 맞는다.[cite:18]

멀티에이전트 구조에서는 결과 검증 에이전트를 통해 필수 필드 누락, 근거 없는 강한 주장, 금지 표현 사용 여부, 로드맵과 갭 분석의 연결성 등을 다시 확인할 수 있다.[cite:18][cite:21] 이는 단일 에이전트가 한 번에 생성한 결과를 그대로 노출하는 방식보다 훨씬 안정적이며, 실서비스에서 요구되는 품질 관리 체계를 만들기에도 유리하다.[cite:18][cite:27]

## 확장성과 유지보수 측면의 장점

자비스는 초기에는 IT 직군, 특히 웹 백엔드 중심의 취업 준비 사용자를 겨냥하지만, 이후 직무 확장과 데이터 소스 확장이 충분히 예상되는 프로젝트다.[cite:21] 멀티에이전트 구조를 채택하면 새로운 직무를 추가할 때 전체 시스템을 바꾸기보다 공고 파서나 로드맵 플래너 같은 일부 에이전트만 교체·확장할 수 있다.[cite:23][cite:25] 또한 기업 정보 조회, 후기 정형화, 자격증 추천 근거, 대체 공고 탐색 같은 기능도 독립 모듈처럼 붙이기 쉬워 장기 운영에 유리하다.[cite:21][cite:23]

실무 가이드들은 멀티에이전트 구조가 역할 기반 재사용과 계층형 오케스트레이션에 강점을 가지며, 새로운 도메인 요구가 생겼을 때 플러그형으로 확장하기 좋다고 설명한다.[cite:23][cite:28] 자비스 역시 이 구조를 택하면 초기 MVP에 필요한 에이전트만 얇게 구현한 뒤, 후속 기능을 단계적으로 붙이는 전략이 가능하다.[cite:21][cite:28]

## 비용과 성능 최적화에도 유리함

자비스가 처리하는 작업들은 난이도와 컨텍스트 길이가 서로 다르다.[cite:21] 예를 들어 공고 파싱, 이력 구조화, 간단한 필드 검증은 비교적 작은 모델이나 룰 기반 처리로도 충분할 수 있지만, 갭 분석이나 장기 로드맵 생성은 더 강한 추론이 필요할 수 있다.[cite:21][cite:28] 멀티에이전트 구조에서는 각 단계마다 적절한 모델과 도구를 배정할 수 있어, 전체를 하나의 비싼 모델 호출로 처리하는 방식보다 비용과 응답 시간 최적화가 쉽다.[cite:21][cite:28]

또한 자비스 문서에는 데이터 조회 우선순위가 내부 정형 DB, 벡터 DB 또는 RAG, 자체 웹 검색 툴, 외부 LLM 검색 기능 순으로 제시되어 있다.[cite:21] 이는 각 에이전트가 자신의 목적에 맞는 도구를 우선적으로 사용하고, 필요할 때만 더 비싼 외부 자원으로 넘어가는 계층형 실행 전략과 잘 맞는다.[cite:18][cite:28]

## 결론

자비스에서 멀티에이전트 구조는 단순히 기술적으로 멋있어 보이기 위한 선택이 아니라, 서비스의 문제 구조와 요구 품질을 고려했을 때 가장 합리적인 설계 선택이다.[cite:21][cite:27] 자비스는 여러 판단 단계를 분업해야 하고, 사람의 확인을 중간에 반영해야 하며, 결과의 근거와 표현을 검증해야 하고, 이후 확장까지 견뎌야 한다.[cite:18][cite:21] 따라서 오케스트레이터 아래에 공고 분석, 사용자 프로필 구조화, 갭 분석, 로드맵 설계, 대체 경로 탐색, 결과 검증 역할을 둔 멀티에이전트 구조가 자비스의 목적에 가장 잘 맞는다.[cite:21][cite:23]
