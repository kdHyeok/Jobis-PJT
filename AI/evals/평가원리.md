# 평가 원리 — 무엇을 어떻게 재고, 그 수치가 무엇을 바꿨나

> **이 문서는 "왜 이렇게 재는가"를 설명한다.** 측정 이력과 원본 수치는
> `docs/eval-records/2026-07-29_planner-reproducibility.md` 와 `evals/*.json` 이 정본이다.
> 코드는 `src/jobis_ai/eval/` 세 파일이고, 지표 로직 검증은 `tests/test_planner_eval.py` 가 맡는다.

---

## 0. 전제 — LLM 시스템의 정확도는 1회로 말할 수 없다

이 평가 체계가 생긴 계기가 그것이다. 기록돼 있던 플래너 정확도 **100%** 는 **1회 측정치**였고,
그 후 프롬프트가 세 번 바뀌는 동안 재측정이 없었다. 재측정해 보니 0.67 이었다 — 코드 회귀가
아니라 **프롬프트가 바뀐 순간 이미 죽은 숫자**였는데 아무도 몰랐던 것이다.

여기서 나온 두 가지 규약이 이 체계의 뼈대다.

1. **같은 입력을 N회 돌려 결과 분포를 본다.** 단일 실행은 결과가 아니라 표본 하나다.
2. **프롬프트 변경과 평가셋 재측정은 같은 커밋에.** 떨어지면 baseline 은 조용히 죽는다.

---

## 1. 세 층을 따로 잰다

에이전트 시스템은 한 덩어리가 아니라 층이다. 층마다 "잘한다"의 정의가 달라서 하나의 하네스로
뭉갤 수 없다.

| 층 | 코드 | 재는 것 | 정답이 있나 |
|---|---|---|---|
| **① 계획** | `eval/planner_harness.py` | 발화 → 어떤 에이전트를 어떤 순서로 돌릴지 | **있다** (기대 시퀀스 완전 일치) |
| **② 풀턴** | `eval/consistency.py` | `handle_chat` 한 턴 전체의 디스패치 궤적 + 답변 문구 | **느슨하게 있다** (불변식 술어) |
| **③ 자기 루프** | `eval/loop_consistency.py` | `agent_loop` 에이전트가 도구를 고르는 궤적 | **없다** (안정성 + 불변식만) |

세 층 모두 **답변 품질(글이 좋은가)은 판정하지 않는다.** 구조·경로·재현성만 본다. 품질은 사람이
읽어야 하는 것이고, 그것을 LLM 심판으로 대체하면 측정 대상보다 심판이 더 흔들린다.

## 2. 공통 지표 원리 — 정확도와 안정성을 갈라 센다

프로토타입(`Agent_Test/tests/eval.py`)에서 이식해 온 지표는 **"일관성 k/N" 하나**였다. 그런데
`0/3` 을 볼 때 이 하나로는 두 가지가 구분되지 않는다.

- *일관되게 틀린 것* → 명세·프롬프트 결함. **재실행해도 안 낫는다.** 프롬프트를 고쳐야 한다.
- *무작위로 틀린 것* → flaky. 온도·프롬프트 경화 대상.

**원인이 다르고 처방이 다르다.** 그런데 같은 run 데이터에서 공짜로 갈라낼 수 있다.

| 지표 | 정의 | 무엇을 말해주나 |
|---|---|---|
| `accuracy` | 기대와 일치한 run 비율 | 맞추는가 |
| `stability` | **최빈 결과**가 차지한 비율 (정답 여부와 무관) | 흔들리는가 |
| `verdict` | `stable-correct` / `stable-wrong` / `unstable` | 위 둘의 교차 판정 |

`stability = 1.0` 이면 모든 run 이 같은 결과이므로 `accuracy` 는 0 또는 1 뿐이다. 그래서 두 축의
교차가 실패를 자동 분류한다.

```
              accuracy=1        accuracy=0        그 사이
stability=1   stable-correct    stable-wrong      (불가능)
stability<1        —                 —            unstable
```

- `stable-wrong` → **결함 티켓.** 프롬프트·명세를 고칠 대상.
- `unstable` → **경화 대상.** 발화 자체가 애매한지, 규칙이 서로를 흐리는지 본다.

`tests/test_planner_eval.py::test_stable_wrong_is_not_flaky` 가 바로 이 구분을 못 박은 테스트다.

### 왜 이 구분이 실제로 값을 했나

실패 17건을 이 축으로 갈랐더니 성격이 셋으로 나뉘었고, 처방이 전부 달랐다.

| 버킷 | 성격 | 처방 |
|---|---|---|
| A. 데이터셋 낡음 (8건) | 지금 동작이 **의도한 것** — 정책이 바뀐 뒤 기대값이 안 따라왔다 | 기대값 갱신 |
| B. 프롬프트 결함 (5건) | `stable-wrong` — 명시적 요청에도 `fit_analysis` 가 안 불렸다 | 프롬프트 수정 |
| C. 잔여 flaky (4건) | `unstable` — 발화가 진짜 애매하거나 순서만 다르다 | 개별 판단 |

지표가 하나였다면 17건이 그냥 "17건 실패"였고, A(고칠 것이 없음)와 B(실사용 손해)가 같은
줄에 섞여 있었을 것이다.

## 3. ① 계획 층 — `planner_harness.py`

### 무엇을 입력하나

`evals/planner_dataset.json` 의 46케이스. 케이스 하나는 **발화 + 세션 자산 목록**이다.

```json
{
  "caseId": "fit-basic",
  "message": "이 공고 나 되나?",
  "assets": ["resume", "job_posting"],
  "expectedAgents": ["fit_analysis"],
  "expectAsk": false
}
```

`assets` 는 이름만 적고 `build_session()` 이 더미로 확장한다. 자산은 **존재 여부만** 판정에
쓰이므로 내용은 최소로 둔다 — 재려는 것은 라우팅이지 내용 이해가 아니다.

### 무엇을 기대값으로 두나 — "최종 실행 시퀀스"

플래너의 원 선택(`plan.agents`)이 아니라 **검증기를 통과한 뒤의 최종 시퀀스**를 기대값으로 둔다.
플래너의 선택 실수가 `validate_plan` 보정으로 살아나는 것까지 포함해 재려는 것이고, 그것이
**사용자에게 실제로 일어나는 일**이기 때문이다.

### 프로덕션 흐름을 그대로 따라간다 (오늘 고친 것)

`dispatch_case` 가 `chat.handle_chat` 의 분기를 그대로 밟게 고쳤다. 그러지 않으면 프로덕션이
아닌 흐름을 재게 되는데, **실제로 그랬다.** 07-28 에 들어온 두 경로를 하네스가 모르고 있었다.

| 경로 | 프로덕션(`handle_chat`) | 수정 전 하네스 |
|---|---|---|
| 확신 < 0.6 | **`career_chat` 이 턴을 받아 대화한다** | `asked=True`("ASK")로 뭉갬 |
| 무거운 생산자 자동 삽입 | **동의 게이트** — 실행 없이 한 턴 묻는다 | `agents=()`+`asked=False` → 빈 키 |

여기서 `asked=True` 의 정의를 확정했다: **"실행 없이 사용자에게 되묻는다"**.
동의 게이트는 해당하고, 저신뢰 폴백은 **해당하지 않는다**(에이전트가 실제로 돌아 말을 한다).
이 수정만으로 `thanks-chat`·`vent-chat` 이 오답에서 정답으로 돌아왔다 — **코드는 처음부터
맞았고 하네스가 틀렸던 것이다.**

### 어떻게 채점하나

결과를 비교 가능한 한 문자열로 접는다.

```
outcome_key = "ASK"            (되묻기)
              "a>b>c"          (실행 — 순서 포함 완전 일치)
```

정답 = (되묻기 일치) AND (실행이면 시퀀스 완전 일치). 이 문자열 비교가 그것과 동치다.

### 부가 지표 — **모델을 갈아 끼울 때 원인을 가른다**

정확도만 남기면 모델 교체 시 오진한다. 약한 모델의 알려진 실패 모드는
**"에이전트는 맞게 고르면서 `confidence` 를 0.00 으로 채우는"** 것이다(07-28 `gpt-4.1-nano` 실측).
그러면 임계값(0.6)에 걸려 전부 `career_chat` 으로 후퇴하는데, 결과만 보면 "라우팅을 못 한다"로
읽힌다. 그래서 함께 남긴다.

| 지표 | 용도 |
|---|---|
| `ask_accuracy` | "묻느냐 실행하느냐"만 맞았는지 — 시퀀스보다 거친 축 |
| `paths` 분포 | `planner` / `fallback` / `gate` / `llm_failed` 중 어디로 갔나 |
| `mean_confidence` | 확신 자체가 죽었는지 |
| `fallback_rate` | **모델 교체 시 가장 먼저 보는 값** |
| `llm_failed` | 환경 문제 — 정확도와 섞지 않고 따로 센다 |
| `observed` | 관측된 모든 결과와 횟수 — **이탈을 덮지 않는다** |

`fallback_rate` 는 이후 실제로 프롬프트 개선의 신호가 됐다 (§6-③).

### 실행

```bash
python -m jobis_ai.eval.planner_harness evals/planner_dataset.json --runs 3 --save evals/planner_baseline.json
```

- `--runs 1` 이면 예전 baseline 과 **같은 값**이 나온다 — 축을 바꾸지 않고 늘렸다.
- 오프라인 평가라 순서가 결과에 영향을 주지 않으므로 4워커 병렬(`_EVAL_WORKERS`).
  무한정 넓히지 않는 이유는 `chat._MAX_PARALLEL` 과 같다 — 동시 과금·레이트리밋.
- `--save` 는 `summary` + 케이스별 결과를 JSON 으로 남긴다. 이게 baseline 파일이 된다.

## 4. ② 풀턴 층 — `consistency.py`

`handle_chat` 을 실제로 호출해 `dispatched` 순서와 `reply` 를 받고, 케이스마다 **술어(람다)** 로
판정한다.

```python
("S6 슬롯 오배정 교정", "", [("job_posting", RESUME)],   # 이력서를 공고 슬롯에
 lambda d, r: "이력서로 등록했어요" in r),
```

계획 층과 다른 점:

- **시퀀스 완전 일치가 아니라 느슨한 불변식.** `"posting_analysis" in d` 처럼 필요한 것만 본다.
  첨부 처리·슬롯 교정처럼 **답변 문구까지 봐야** 하는 케이스를 커버하기 위해서다.
- 첨부(`attachments`)를 실제로 넣는다 — 계획 층의 더미 자산으로는 재현되지 않는 경로다.
- `SESSION_STORE=memory` 강제 — 평가가 `sessions.sqlite3` 를 오염시키지 않게.
- 예외를 잡아 `CRASH` 로 기록한다. **평가에서는 크래시 자체가 결과다.**

7케이스 × 3회로 돌리며, 계획 층이 잡지 못하는 것을 잡는다. 실제로 계획 층은 46케이스가
초록이던 시점에도 풀턴 S5 가 갈렸다.

### 기대값을 고쳐 초록으로 만들지 않는다

S5("자소서 써줘" + 이력서·공고 동시 제출)는 결과가 갈렸고, 그 원인이 **동의 게이트의 구멍**이었다.
이 케이스는 기대값을 고치지 않고 코드에 `KNOWN FAILURE` 주석으로 박아 뒀다 —
**구멍이 닫히기 전에 초록으로 만들면 그 사실이 사라진다.** (구멍은 §6-④ 에서 닫혔다.)

## 5. ③ 자기 루프 층 — `loop_consistency.py` (신설)

`agent_loop` 를 도는 세 에이전트(`preference_intake`·`interview_prep`·`coverletter_draft`)는
매 턴 **도구를 스스로 골라** 여러 스텝을 돈다. 계획 층은 "어떤 에이전트"까지만 재고, 풀턴 층은
에이전트 내부를 보지 않아서 **이 궤적은 아무도 재지 않고 있었다.**

### 여기서는 정답을 두지 않는다 — 이게 핵심 차이다

도구를 몇 개 쓸지는 발화·근거에 따라 달라지는 것이 **정상**이다(쓸 도구가 적으면 적게 돈다).
그래서 궤적에 기대값을 두지 않고, `stability`(같은 입력에 같은 길을 가는지)만 본다.

대신 **불변식**은 검사한다 — 어겼으면 그건 취향이 아니라 결함이다.

| 에이전트 | 불변식 | 왜 |
|---|---|---|
| `coverletter_draft` | `save_draft` 를 반드시 부른다 | 저장 없이 답하면 화면에 나갈 본문이 없다 |
| `interview_prep` | 도구를 최소 하나 쓴다 | 도구 없이 질문을 지어내면 근거 제한 위반 |
| `preference_intake` | `record_preference` 를 부른다 | 기록 없이 답하면 다음 턴이 아무것도 물려받지 못한다 |

### `warnings` 를 지표로 둔 이유 — **폴백이 그럴듯하면 결함이 안 보인다**

첫 실행에서 두 에이전트가 **도구 0개**로 답했다. "도구를 안 썼다"로 읽을 수 있었지만
`loopSteps` 가 빈 것과 **루프가 아예 안 돈 것**은 다르므로 파고들었더니:

```
llm_call_failed :: claude CLI 종료 코드 1: {"is_error":true,"stop_reason":"tool_use", ...}
```

`agent_loop` 프롬프트가 *"쓸 수 있는 도구:"* 로 목록을 늘어놓는 순간 Claude 가 **자기 내장
도구(Read/Bash…)** 를 쓰려 들고 `--max-turns 1` 에 걸려 실패했다. 3회 재시도 끝에 전부
**결정론 폴백**으로 나갔는데 — **답변이 그럴듯해서 겉으로는 정상처럼 보였다.**
(플래너 프롬프트는 "에이전트 목록"이라 이 함정을 안 밟았다. 그래서 계획 층 측정은 정상이었다.)

→ `claude_code_llm._COMMON_ARGS` 에 `--tools ""` 추가(내장 도구 전부 끄기).
회귀 방어는 `tests/test_claude_cli_args.py` — CLI 를 부르지 않고 **인자만 검사**한다.
조용히 사라지는 종류의 결함이라 못을 박았다.

**그래서 경고 코드 분포를 지표로 넣었다.** `llm_call_failed` 가 보이면 궤적이 빈 것이 아니라
루프가 죽은 것이고, `coverletter_check_unresolved` 는 점검 지적을 남긴 채 답했다는 뜻이다.
**폴백 이유를 삼키지 않는다.**

| 지표 | 정의 |
|---|---|
| `trajectory` | 도구 호출 순서 한 문자열 (`find_evidence>save_draft>check_draft`) |
| `stability` | 최빈 궤적 비율 |
| `replied` | 검증 통과 문장을 만든 비율 (0 이면 결정론 폴백으로 나갔다는 뜻) |
| `steps` | 평균·최대 — 상한(`DEFAULT_MAX_STEPS`)에 닿는지 |
| `warnings` | 경고 코드 분포 |

### 낮은 안정성이 여기서는 나쁜 것이 아니다

```
coverletter_draft   2/5  find_evidence>save_draft>check_draft
                    2/5  find_evidence>save_draft>check_draft>save_draft   ← 자기비판 재작성
                    1/5  find_evidence>ask_agent>save_draft>check_draft    ← 에이전트 간 위임
```

안정성 **0.40** 인데 세 궤적이 **전부 정당하다** — 점검 통과 / 점검 후 재작성 / 옆 담당에게
물어보기. 초안 품질에 따라 갈리는 것이 이 에이전트의 설계 의도다.
**플래너 안정성과 같은 잣대로 읽으면 오독이다** — 플래너는 같은 입력에 같은 계획이 나와야 하고,
자기 루프는 근거에 따라 다르게 도는 것이 정상이다. 불변식 위반은 0건이었다.

### 덤 — 구조만 있던 것이 계측으로 확인됐다

평가 문서가 "구조는 있으나 증명 못 했다"로 남겼던 것 셋이 이 측정에서 처음 잡혔다.

1. **자기비판 재작성이 실제로 발동한다** (`check_draft` → `save_draft`, 2/5)
2. **에이전트 간 위임이 실사용에서 발동한다** (`ask_agent` → `resume_diagnosis`, 1/5)
3. **`max_steps` 3 → 5 상향이 값을 했다** — 최대 궤적이 4스텝이다. 상한이 3이었다면 재작성과
   위임 궤적이 **잘렸다.** 근거 없이 올린 값이 사후에 실측으로 정당화됐다.

## 6. 이 수치가 에이전트를 어떻게 개선시켰나

측정은 숫자를 남기는 일이 아니라 **다음에 무엇을 고칠지 고르는 일**이다. 실제 궤적이 그렇다.
**한 번에 두 축을 고치지 않고, 고칠 때마다 다시 쟀다** — 그래야 어느 변경이 무엇을 움직였는지
말할 수 있다.

| 단계 | 무엇을 했나 | 정확도 | 안정성 | correct / wrong / unstable |
|---|---|---|---|---|
| ① | 하네스를 프로덕션 흐름에 맞춤 (재측정 기준선) | 0.6739 | 0.9420 | 29 / 9 / 8 |
| ② | 프롬프트 결함 B 수정 | 0.7826 | 0.9565 | 32 / 8 / 6 |
| ③ | ②가 같이 넣은 과잉 조항 축소 | 0.8188 | **0.9855** | 37 / 7 / 2 |
| ④ | 데이터셋 낡은 기대값 A 갱신 | 0.9275 | 0.9783 | 41 / 2 / 3 |
| ⑤ | 규칙 5개 → 우선순위 사다리 1개 + Claude CLI 전환 | 0.8406¹ | 0.9493 | 36 / 4 / 6 |
| ⑥ | 동의 게이트 구멍을 **스키마**로 닫음 | 0.8478 | 0.9565 | 37 / 3 / 6 |
| ⑦ | 평가셋 재캘리브레이션 (범위를 먼저 갈랐다) | 0.8985 | 0.9493 | 40 / 1 / 5 |

¹ ⑤의 하락은 프롬프트가 아니라 **모델 교체분**이다 — 아래 대조군 참고.
`ask_accuracy` 는 ⑥에서 **1.0** 이 되어 유지된다.

현재 저장된 baseline(`evals/planner_baseline_claude.json`)은 **정확도 0.9783 / 안정성 0.9855 /
stable-wrong 0** 이고, 남은 실패는 `unstable` 2건(`fit-missing-posting-degrade`·`resume-missing`)
뿐이다. **`stable-wrong` 이 0 이라는 것이 이 축의 의미다** — 재실행해도 안 낫는 결함이 없다.

### ② → ③ — 총계는 올랐는데 깨진 것이 있었다

②에서 `fit_analysis` 결함을 고치면서 *"인사·감사·하소연·잡담이면 `career_chat`"* 조항을 함께
넣었다. 총계는 0.67 → 0.78 로 올랐으니 **총계만 보면 통과시켰을 것이다.**

케이스별 판정을 보고서야 드러났다: **고친 것 8건 / 깨뜨린 것 6건.**
조항의 후반부 문구가 기능 요청까지 끌어가서 `interview-with-analysis`("면접 예상 질문 뽑아줘",
analysis 보유)가 `career_chat` ×3 이 됐다. 조항을 좁히고 반례를 명시하니 ③에서 불안정이
6 → **2** 로 떨어졌다.

> **교훈: 프롬프트 규칙은 좁히는 문장과 넓히는 문장을 같은 커밋에 넣지 않는다.**
> 총계만 보면 서로를 가린다. 그래서 하네스가 케이스별 `verdict` 를 반드시 출력한다.

### 규칙을 더 넣어서 고칠 수 없다 (같은 날 세 번 배웠다)

"전제가 반만 있을 때" 를 고치려고 여섯 번째 규칙을 넣었더니 **총계까지 내려갔다**
(0.9275 → 0.9058). 목표 2건은 고쳤지만 **무관한 케이스 4건이 깨졌다** — 로드맵·면접처럼
새 규칙이 **언급조차 하지 않는** 케이스가 흔들린 것이 규칙 간 간섭의 증거다.

되돌렸고, 다음 시도를 **추가가 아니라 합침**으로 바꿨다. ⑤에서 규칙 5개를 **우선순위 사다리
6단 하나**로 합쳤고, 문제의 ①은 병렬 규칙이 아니라 **사다리 4단의 종속절**로 들어갔다.

### ⑤ — 변수 두 개를 동시에 움직였으므로 대조군을 돌렸다

프롬프트(사다리)와 모델(GMS `gpt-4.1-mini` → Claude `sonnet` CLI)이 같이 바뀌어서 귀속이
불가능했다. 대조군 C(옛 프롬프트 + 새 모델)를 하나 더 돌려 갈랐다.

| | 프롬프트 | 모델 | 정확도 | 폴백률 | 파일 |
|---|---|---|---|---|---|
| A | 옛 규칙 5개 | `gpt-4.1-mini` | 0.9275 | 0.029 | `planner_baseline.json` |
| C | 옛 규칙 5개 | Claude `sonnet` | 0.8188 | 0.109 | `planner_control_old-prompt_claude.json` |
| B | **사다리** | Claude `sonnet` | 0.8406 | **0.065** | `planner_baseline_claude.json` |

- **모델 효과 (A→C, 프롬프트 고정): −0.109.** 정확도 하락은 **전부 모델 교체**다.
- **프롬프트 효과 (C→B, 모델 고정): +0.022, 폴백률 −40%.** → 사다리는 개선이다. 유지.

**`fallback_rate` 가 여기서 값을 했다.** 규칙이 서로를 흐리면 모델이 확신을 잃고 대화로
후퇴하는데, 합치니 그 비율이 40% 줄었다. 정확도 +0.022 만으로는 "노이즈"라고 했을 것이다.

### ⑥ — 측정이 **결정론 결함**을 찾아냈다 (프롬프트로는 못 막혔다)

풀턴 S5 의 불안정을 파고들자 표면이 아니라 코드 결함이 나왔다.

```python
# router.validate_plan (수정 전)
requested = set(agents)                  # ← 플래너의 선택을 "사용자가 청한 것"의 대용품으로 씀
inserted_heavy = [n for n in plan if n not in requested and registry[n].heavy]
```

게이트가 막으려는 것은 **"사용자가 청하지 않은 무거운 작업"** 인데 *"플래너가 고르지 않았다"* 를
대용품으로 쓴다. **플래너도 전제를 추론해 넣으므로 대용품이 샌다** — 실측 S5 에서 플래너가
스스로 `[fit_analysis, coverletter_draft]` 를 골라 `fit_analysis` 가 `requested` 에 들어가고
**수십 초 파이프라인이 말없이 돌았다.**

먼저 프롬프트로 금지해 봤고(*"무거운 판정을 전제로 스스로 끼워 넣지 마라"*), **안 먹혔다** —
`coverletter-motivation` 이 `fit_analysis>coverletter_draft` ×2 로 나왔다. 그래서 스키마로 갔다.

```python
inferredPrerequisites: list[AgentName]   # agents 에 넣었지만 사용자가 청하지는 않은 것
requested = set(agents) - set(inferred)  # 대용품을 실제 값으로 교체
```

프롬프트 가드도 **금지 → 신고**로 바꿨다(금지는 실측에서 안 먹었으므로 남겨 둘 이유가 없다).
**판단은 LLM, 행동은 코드.** 산문이 아니라 필드라 규칙 간섭 실패 모드를 피한다.

실측(`evals/planner_claude_inferred.json`)에서 플래너가 실제로 갈라 채운다:

| 발화 (이력서+공고) | 신고 | 결과 |
|---|---|---|
| "분석 후에 면접 질문도 준비해줘" | `[]` — 둘 다 사용자가 청했다 | `fit_analysis>interview_prep` (게이트 없음) |
| "자소서 초안 부탁해" | `[fit_analysis]` | **ASK** (게이트) |

구조가 같은 계획(`[fit_analysis, 소비자]`)이 발화에 따라 갈린다 — **계획만 보고는 불가능했던
구분이다.** `ask_accuracy` 가 1.0 이 된 것이 이 작업의 성과고, 닫은 것은 정확도 +0.007 이 아니라
**말없이 수십 초를 쓰는 결함**이다.

부작용 1건도 실측이 잡았다: `analysis` 를 **이미 가진** 세션의 "자소서 다시 써줘"에 게이트가
걸렸다. 게이트는 "필요한데 무거운 것"에만 의미가 있으므로 **신고된 전제 중 이미 있는 자산을
만드는 것은 묻지 않고 뺀다**(`validate_plan` 의 `redundant`).

### ⑦ — 재캘리브레이션의 범위를 먼저 갈랐다

기대값 갱신은 위험한 작업이다. 관측에 맞춰 고치면 **평가셋이 구현을 따라가는 거울**이 되어
측정이 의미를 잃는다. 그래서 기준을 하나로 못 박았다: **현재 동작이 의도인 경우만 갱신.**

| 가족 | 판단 | 근거 |
|---|---|---|
| 상위집합 2건 (`preference_intake>job_recommend`) | **갱신** | `job_recommend` 의 `preconditions_any` 가 생산자를 앞에 끼우는 것은 **설계이고 테스트로 못 박혀 있다** |
| "전제가 반만 있을 때" 4건 | **갱신 안 함** | 사다리 4단이 *"대화로 넘기지 않는다"* 를 명시한다 — 낡은 기대값이 아니라 **모델이 프롬프트를 안 따르는 것** |

데이터셋 `description` 에 `note` 규약을 박았다:
**`갱신`** = 정책 변경으로 고친 것(근거 필수) / **`OPEN`·`KNOWN FAILURE`** = 관측과 다르지만
**일부러 고치지 않은 것**. 이 규약이 없으면 6개월 뒤에 "왜 이 기대값이 이런가"를 아무도 모른다.

## 7. 이 체계가 실제로 잡아낸 것들 (요약)

측정이 만든 차이는 정확도 숫자가 아니라 **찾아낸 결함의 목록**이다.

| 잡아낸 것 | 어떤 지표가 잡았나 | 성격 |
|---|---|---|
| 하네스가 프로덕션 아닌 흐름을 재고 있었다 | `paths` 분포 | **측정 자체의 결함** |
| `fit_analysis` 가 명시적 요청에도 안 불린다 | `stable-wrong` 5건 | 프롬프트 결함 (실사용 손해) |
| 인사 조항이 기능 요청까지 끌어갔다 | 케이스별 `verdict` (총계는 올랐다) | 프롬프트 과잉 |
| 규칙 6개째가 무관한 케이스를 흐린다 | 총계 하락 + 무관 케이스 이탈 | 규칙 간섭 |
| 동의 게이트를 플래너가 우회한다 | 풀턴 `unstable` → 코드 추적 | **결정론 결함** |
| 자기 루프 층이 Claude CLI 에서 통째로 꺼져 있었다 | `warnings` 경고 코드 | **폴백이 가린 결함** |
| `max_steps` 3 은 부족했다 | `steps` 최대값 | 상수 근거 |
| 온도 0.3 → 0 은 값이 없다 | `mean_stability` (0.942 → 0.949) | **하지 않기로 한 결정** |

마지막 줄이 중요하다. 측정 전에는 티어별 온도 분리가 유력한 손잡이로 보였는데, 재고 나니
값이 없어서 **하지 않았다.** 남은 흔들림은 온도가 아니라 발화 자체의 애매함에서 왔다.

## 8. 한계 — 지금 못 재는 것

정직하게 남긴다. 초록 숫자를 과대 해석하지 않기 위해서다.

1. **답변 품질은 평가하지 않는다.** 세 층 모두 구조·경로만 본다.
2. **지표가 "순서 무관"을 표현하지 못한다.** `multi-coverletter-and-interview` 는 내용이 맞고
   순서만 반대인데 오답으로 찍힌다 — 둘은 서로의 산출을 쓰지 않아 `chat.parallel_group` 이
   실제로는 **동시 실행**한다. 즉 순서가 결과를 바꾸지 않는데 데이터셋이 순서를 강제한다.
3. **데이터셋이 특정 모델 성향으로 캘리브레이션돼 있다.** 모델을 바꾸면 "상위집합"(기대
   에이전트를 **포함해** 한 단계 더 함) 같은 실패가 생긴다. 이걸 "모델이 못하다"로 읽으면 안 된다.
4. **`--save` 시 기록되는 모델명이 provider 를 따라가지 않는다.** `settings.llm_model` 을 그대로
   싣기 때문에 `LLM_PROVIDER=claude_code` 로 돌린 baseline 에도 GMS 모델명이 남는다.
   파일 이름과 `docs/eval-records/` 로 구분해야 한다.
5. **루프 궤적 안정성은 baseline 파일이 없다.** `planner_harness` 처럼 `--save` 가 없어서
   비교 기준선이 문서에만 있다.
6. **비용 때문에 자주 못 돈다.** 46케이스 × 3회 = 138콜, Claude CLI 로 1콜 ≈ 5.2초 → 4워커에
   약 6분. **큰 분기마다 한 번**만 측정한다는 방침이라, 프롬프트를 반복 조율하며 매번 재는
   방식은 쓰지 않는다.
