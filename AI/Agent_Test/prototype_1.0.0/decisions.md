## 2026-07-26 — 개발 방법론·아키텍처 결정

### D1. 바이브코딩 플레이북을 우리 프로젝트용으로 재단
- **결정:** 개발자 참고용 `VIBE-CODING-PLAYBOOK.md`(웹/Spring·Vue 브라운필드 전제)를 그린필드 Python+LLM Agent용으로 취사선택 → `agent_ver_VIBE-CODING-PLAYBOOK.md` 작성.

### D2. 실행 형태 = 서버 없는 파이썬 core (FastAPI 후순위)
- **결정:** 프로토타입은 `python run.py`로 도는 순수 파이썬 core. **FastAPI는 마지막 태스크**로 미룸.
- **왜:** Agent 로직 돌리는 데 서버 불필요 — LLM은 우리가 **클라이언트로 외부 호출**. 서버는 Java 백엔드(타 부서)가 우리를 부를 때만 필요. core를 먼저 완성하면 서버·HTTP 변수가 안 껴서 버그 출처가 깨끗함.
- **연결고리:** `run_agent()`가 처음부터 `{reply, meta:{scenario, tools_called[], level}}`를 반환 → 나중 FastAPI는 이걸 봉투에 감싸기만 하면 됨(공짜) + 성공판정도 이 meta로 검증.

### D3. 기능 모듈화 = 장애 격리선
- **결정:** `agent/ · tools/(파일1개=툴1개) · preprocess/ · llm/ · schemas/ · api/(후순위)`. 에러 봉투에 `source` 필드 추가.
- **왜:** 문제 터졌을 때 어느 모듈인지 즉시 갈리게. ReAct 구조와 자연스럽게 맞음.
- **주의:** 과분할 금지(~6~7 모듈). 장애 격리선을 넘는 분할은 오히려 추적을 어렵게 함.

### D4. 정적 모델 티어 매핑 (런타임 동적선택 ❌)

### D9. 라우팅 = LLM 동적 계획으로 확정 (AGENTS §5.2 교정, 2026-07-27)
- **결정:** 입구 라우팅은 **LLM이 자연어 쿼리를 읽고 툴을 동적으로 계획**(ReAct, 정본 §4). 고정 시나리오 규칙 분류 아님. 6 시나리오는 **행동 지침 + 테스트 케이스**로 존속(하드코딩 분기 아님).
- **하이브리드:** **입구 라우팅 = 동적(LLM)** / **level 상·중·하 분기(§5.3) = 결정적 규칙(워크플로우) 유지.** → D7의 "level 분기=결정적 edge"는 그대로 유효(정정 아님).
- **경위(교훈):** AGENTS §5.2가 소스 모순(정본 §4 ReAct ↔ §6.4 "라우팅=워크플로우")을 규칙 쪽으로 **조용히 봉합**해 "명시적 감지(플래그+정규식)"로 서술 → 실제 의도(동적)와 충돌해 교정. 재발방지 feedback 메모리화([[surface-ambiguity-not-silent-resolve]]).
- **⟨task 07 게이트⟩:** 동적 계획 ↔ 결정적 level 분기의 그래프 결합 방식. 성공기준 1·4(호출 여부)는 LLM 의존이 되므로 문구 다듬기.

### D10. load_posting 반환 = Posting(타입 객체) + URL 정확 일치 (task 04, 2026-07-27)
- **결정:** `load_posting(url)` 성공 시 **`Posting`(Pydantic)** 반환, 실패 시 `ToolError(NOT_FOUND)`. URL은 **정확 일치**.
- **경위(교훈 적용):** 설계(정본 §4.3 / AGENTS §4.1)는 "공고 JSON 1건(원본), 구조화 안 함"으로 **dict에 가깝게** 서술 → 반환 타입은 설계에 **미결정**이었음("기존에 Posting으로 정함"은 사실 아님, 문서 재확인으로 밝힘). 이번에 **새로 Posting 채택**: 파이프라인 전부 Pydantic이라 타입 안전 + `search_postings`도 `ScoredPosting(Posting)`이라 일관. 내용 동일·`.model_dump()`로 dict 복원 가능 → "구조화 안 함" 취지 위배 아님.
- **범위 밖:** URL 정규화(슬래시·http/https), 데이터팀 실제 DB 연동 → 백로그/외부.

### D11. task 07 아키텍처 = B (tool-calling ReAct + 결정적 level 엣지) — D9 게이트 해소 (2026-07-27)
- **결정:** LangGraph 아키텍처를 **A(순수 ReAct) / B(tool-calling + 결정적 edge) / C(LLM 라우터 + 결정적 edge)** 중 **B** 채택.
- **B 구조:** `agent`(LLM bind_tools — 툴 동적 선택) ↔ `tools` 루프 + **analyze_gap 직후 조건 엣지**(코드가 level 관찰 → 중/하면 `auto_search`로 search 강제, 상이면 종료로). = **동적 라우팅 + 결정적 level 분기.**
- **왜 B (A/C 아님):**
  - **agent다움**: LLM이 툴을 동적으로 운전(A와 동급) → D9 "동적 계획"에 최상 충실. C는 입구만 LLM이라 워크플로우처럼 보임.
  - **결정적 level 분기**: 성공기준 2·3(중/하→search)이 안정(A는 게이트도 LLM이라 search 건너뛸 위험).
  - **design.md agent 기준 충족**(§1 "관찰에 따라 결정" / §4 "Thought로 대체직군"): B에서 관찰-의존 흐름·Thought(대체직군 LLM 생성) 온전. 코드로 굳힌 건 "중/하→search" **이진 스위치뿐** — design도 이를 "(나뉘어진 워크플로우 툴)"로 인정한 부분.
  - **반전**: A의 "게이트까지 LLM 자유"는 agent다움이 아니라 **설계 의도(중/하→검색) 위반 리스크**. B가 그 의도를 결정적으로 보장 = 더 충실.
- **비용(감수):** 툴을 LLM이 부르므로 `@tool`/스키마 래핑 + 결과(Pydantic)→문자열 직렬화 필요(구조화 결과는 State에 별도 보관해 조건엣지·meta에 사용).
- **해소:** D9의 ⟨task 07 게이트⟩(동적↔결정적 결합 방식) = 이 D11로 확정. (D7의 "level 분기=결정적 edge"와도 정합)

### D15. 버전 브랜치 전략 — 선형 순차(분화 아님) (2026-07-27)
- **결정:** 버전 간 **분화(fork) 안 함. 선형 순차** 진행. 각 버전 = main에서 딴 작업 브랜치 → merge → 태그.
  - `v1.0.0` 태그(= `d183b76`, 완결본 복구 지점) 찍음.
  - `dev/1.0.1` 브랜치 생성 → 강건화 진행 → merge/`v1.0.1` 태그.
  - **`dev/1.1.0`은 1.0.0이 아니라 1.0.1(merge 지점)에서 분기** — 강건화·`analyze_gap` 정교화 이득을 물려받기 위해.
- **핵심 구분:** *브랜치(작업 격리, 나중에 합류=선형)* ≠ *분화(두 라인 영구 병행+backport)*. 1.1.0에 브랜치를 따로 두는 건 위험(멀티턴=구조 변경)이 커 **오래 격리**하려는 것이지 fork가 아니다.
- **순서 근거(계층):** 1.0.1 스코프(다중 이력서·mock검색·analyze_gap)는 **모듈 국소 → 단위테스트로 격리**되어 싱글턴 위에서 안전·저비용. 멀티턴은 `agent/graph.py` 오케스트레이션+State 계약을 바꾸는 **통합 계층 변경 → 단위테스트 밖**. 그래서 **강건화(안정 기반) 먼저 → 멀티턴 나중.** 뒤섞으면 버그 시 "라우팅 강건성이냐 상태관리냐" 분리 불가.
- **fork를 쓸 유일한 경우(해당 없음):** 1.0.x를 출시본으로 유지보수하며 1.1.0을 병행·backport 할 때. 솔로 학습 프로토타입엔 오버킬 + analyze_gap 공통이라 충돌·중복.
- **문서:** `decisions.md`는 분기 없이 D15~로 **연속 append**(폴더/로그 복제 금지). 1.0.1 tasks/checkpoints는 기존 폴더에 추가.
