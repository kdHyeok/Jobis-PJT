## 1. 프로젝트 개요

- **무엇을 만드나**: 사용자의 이력서 또는 채용 공고를 입력받아, 적합한 공고를 추천하거나 특정 공고에 대한 **지원 가능성(갭)을 분석**해주는 커리어 코치 AI Agent.
- **타깃 사용자**: 이직·취업 준비자.
- **대표 가치**: "이 공고에 지원할 수 있을까?", "나에게 맞는 공고는?", "부족한 부분은 무엇이고 어떻게 채우나?"에 답한다.

### 왜 Agent인가 (Workflow가 아닌 이유)

- 사용자 요청에 따라 **실행 경로가 달라진다** (이력서·공고 유무, 요청 의도).
- 특히 **관찰 결과가 다음 행동을 결정한다**: 갭 분석(`analyze_gap`) 결과의 `level`(상/중/하)에 따라 이후에 대체 직군을 찾을지, 로드맵을 줄지, 추가 검색을 할지가 갈린다.
- 즉 입력만 보고 경로를 확정할 수 없고 `decide → observe → decide` 루프가 필요하다 → **Agent**.
- (상세 근거는 §6 시나리오 3)

## 2. 시스템 구성도 & 개발 범위

```
                 ┌──────────────────────────────────────────┐
   사용자 입력 ──▶│              AI Agent (본체)               │──▶ 사용자 응답
 (자연어/이력서/  │  라우팅 + 관찰 기반 분기(agent loop)        │
   공고 URL)      │  ├─ Thought: 대체직군 생성 / 공고 정리      │
                 │  └─ Tool 호출                              │
                 └───┬───────────────┬───────────────┬───────┘
                     │               │               │
              ┌──────▼─────┐  ┌──────▼──────┐  ┌─────▼──────┐
              │ analyze_gap│  │search_postings│ │load_posting│
              │  (툴)      │  │  (툴, RAG)    │ │  (툴)      │
              └──────┬─────┘  └──────┬──────┘  └─────┬──────┘
                     │               │               │
      이력서 파서 ───┘        RAG 검색 엔진        공고 DB
   (docx→profile)           (별도 담당)         (데이터팀)
```

### AI Agent 파트가 **직접 개발**하는 부분 (우리 담당)

| 구성요소 | 설명 |
|----------|------|
| **Agent Loop** | 요청을 시나리오로 라우팅하고, 관찰 결과에 따라 다음 행동을 분기 |
| **`analyze_gap` 툴** | 이력서↔공고 갭 분석 (LLM 추출·매칭 + 알고리즘 채점) |
| **`load_posting` 툴** | 공고 URL로 DB에서 공고 JSON 조회 |
| **이력서 파싱 (전처리)** | `docx → text → profile JSON` (§3) |
| **Thought 로직** | 대체 직군 생성, 공고 정리(사용자 친화 출력) |
| **`search_postings` 인터페이스** | 계약(입출력)만 정의. 실제 검색 로직은 RAG 담당. 데모에서는 **mock(깡통)** 으로 대체 |

### 다른 파트 / 외부 담당

| 구성요소 | 담당 | Agent와의 관계 |
|----------|------|----------------|
| **RAG 검색 엔진** | 별도 담당 인원 | `search_postings` 계약대로 구현. 완성 시 mock을 실제 구현으로 교체 |
| **공고 DB** | 데이터팀 | URL로 조회 가능한 공고 JSON 저장소 |

## 3. 이력서 파싱 파이프라인

Agent 실행 **이전 전처리** 단계로, 이력서 파일을 구조화 JSON(`profile`)으로 변환한다.

```
docx 파일
  → [docx_to_text]  python-docx로 문단 텍스트 추출 (표 없는 텍스트 이력서 가정)
  → resume_text
  → [LLM structured output]  with_structured_output(Pydantic 스키마 강제)
  → profile JSON
```

- 구현: `python-docx`(docx→text) + LLM 구조화 추출.
- **structured output(스키마 강제)은 필수** — free-form "JSON 뽑아줘"는 구조가 흔들려 다운스트림이 깨진다.

### profile JSON 스키마 (`_UserProfileRead`, 10필드)

| 필드 | 설명 | 구조 |
|------|------|------|
| `skills` | 기술 | `[{ name, level }]` |
| `experiences` | 재직이력 | `[{ id, company, role, employmentType, period, summary }]` |
| `projects` | 프로젝트 | `[{ id, title, projectType, period, teamSize, role, summary, techStack[], achievements[] }]` |
| `education` | 학력 | `[{ id, school, major, degree, status, period }]` |
| `certifications` | 자격증 | `[{ id, name, status, acquiredDate }]` |
| `languages` | 어학 | `[{ id, name, testName, score, testDate, proficiency }]` |
| `bootcamp` | 부트캠프 | `[{ id, name, organization, track, period, summary }]` |
| `awards` | 수상 | `[{ id, title, organization, date, description }]` |
| `evidenceMap` | 근거문장(메타) | `[{ evidenceId, source, text }]` |
| `uncertainties` | 불확실사항(메타) | `[string]` |

**규칙**
- 없는 섹션 → 빈 배열 `[]`
- 값 없는 스칼라 → `null`
- **로드베어링 필드**(검색·갭분석 실사용): `skills`, `projects.techStack`, `experiences`
- `profile`은 `search_postings`와 `analyze_gap`이 **공유하는 중심 계약**이다.

## 4. 툴 명세 (3개)

> 본 §4가 툴 정의의 **단일 출처(single source)** 이다. §6의 시나리오는 아래 툴을 참조한다.

### 4.1 `analyze_gap` — 갭 분석 (툴4)

이력서와 특정 공고를 비교해 지원 가능성을 정량 점수로 산출한다.

| 항목 | 내용 |
|------|------|
| 입력 | `profile`(JSON) + 공고(JSON, `detail_text` 포함) |
| 처리 | 1) [LLM] `detail_text` → 필수/우대 항목 리스트 추출 2) [LLM] 각 항목을 `profile`이 커버하는지 매칭(matched/partial/missing) 3) [알고리즘] 가중치 합산 → 점수·등급 |
| 출력 | `{ score, level, matched_required[], missing_required[], matched_preferred[], rationale }` |
| 사용 조건 | 이력서와 공고가 **둘 다** 있을 때 |
| 비고 | `level`(상/중/하)이 시나리오 3의 분기 트리거. `missing_required`가 대체직군·로드맵의 재료 |

### 4.2 `search_postings` — 유사 공고 검색 / RAG (툴8)

쿼리(직업명 또는 이력서)로 관련 공고를 검색한다. **실제 검색은 RAG 담당, 데모는 mock.** (기존 툴5+툴8 통합)

| 항목 | 내용 |
|------|------|
| 입력 | 직업명(`string`) **또는** `profile`(JSON) 중 하나 |
| 출력 | 공고 JSON 배열 (각 공고 = 원본 필드 + `score` + `match_reason`), `postings` 배열로 반환 |
| 사용 조건 | 이력서 기반 추천(시나리오 1), 직업군 검색(시나리오 4), 대체직군 검색(시나리오 3 중·하) |
| 메커니즘 | 임베딩 유사도 검색 (RAG 재량) |
| 상세 계약 | → `../rag_입출력 관련 명세서/RAG_입출력_명세서.md` |

### 4.3 `load_posting` — 공고 조회 (툴6)

공고 URL로 DB에서 저장된 공고 JSON을 조회한다. (조회만, 가공·구조화 안 함)

| 항목 | 내용 |
|------|------|
| 입력 | 공고 URL(`string`) |
| 출력 | 공고 JSON 1건 (원본 그대로) |
| 사용 조건 | 사용자가 특정 공고 URL을 제시할 때(시나리오 2) |
| 메커니즘 | DB 키 기반 조회 |

## 5. Thought (툴이 아닌 LLM 추론 단계)

아래는 외부 능력이 아니라 **LLM이 스스로 수행**하는 단계이므로 툴로 만들지 않는다.

| Thought | 역할 | 툴이 아닌 이유 |
|---------|------|----------------|
| **대체 직군 생성** | 갭이 큰 경우(중/하) 전직 가능한 대체 직군을 생각해냄 (예: 백엔드→데브옵스) | LLM 내부 지식으로 추론. 외부 조회·계산 아님 |
| **공고 정리** | `load_posting` 결과를 사용자 친화적으로 요약·정리해 출력 | 이미 확보된 JSON을 요약하는 것 = LLM 응답 생성 |

## 6. 시나리오 & 작동 흐름

자연어 입력을 받아 아래 6개 시나리오로 라우팅한다.

> **툴 범례**: 툴4 = `analyze_gap` / 툴8 = `search_postings` / 툴6 = `load_posting` · 정식 명세는 §4. "입력3" = 시나리오 3(갭분석)으로의 유도를 의미.

### 6.1 시나리오 요약

| # | 입력 조건 | 작동 흐름 (툴/Thought 순서) | 성격 |
|---|-----------|------------------------------|------|
| 1 | 이력서 O / 공고 X | 이력서 파싱 → **`search_postings`**(추천) → (공고 선택) → 갭분석 유도 → (수락 시) **`analyze_gap`** | 라우팅 |
| 2 | 이력서 X / 공고 O | **`load_posting`** → LLM 공고 정리 출력 → 이력서 입력 유도 | 최소 (1툴+정리) |
| 3 | 이력서 O / 공고 O | **`analyze_gap`** → **[관찰: `level`]** → · 상: 근거 출력 · 중/하: 근거 + Thought(대체직군) + 로드맵 + **`search_postings`**(대체직군 공고) | **핵심 Agent** |
| 4 | 직업군명 입력 | **`search_postings`** | 라우팅 |
| 5 | 일상 대화 (번외) | 툴 없음 → 시나리오 1·2·3 가능함을 안내·유도 | Guardrail |
| 6 | 취업 무관 질의 | 툴 없음 → "취업 관련 외 질의는 받지 않습니다" 거절 | Guardrail |

> **정합성 메모**: 시나리오 1·2는 모두 **시나리오 3(갭분석)으로 수렴**하도록 유도한다(대화 상태 연결). 시나리오 1의 `search_postings` → `analyze_gap` 사이에는 **"검색 결과 중 특정 공고 선택"** 단계가 존재한다(검색은 여러 건, 갭분석은 1건 대상).

### 6.2 입력 예시별 상세 흐름 (원본 설계 메모)

0. 자연어 입력 받기

1. **"내 이력서 기반으로 갈 수 있는 공고 추천해줘"** (이력서 O / 공고 X)
   → 이력서 파싱 기반 유사 공고 RAG 검색(툴8) → 이후 관련 공고 기반으로 시나리오 3(공고+이력서 갭 분석) 유도 → 유도 성공 시 툴4 진행

2. **"나 해당 공고로 지원하고 싶은데 공고 분석 좀 해줘"** (이력서 X / 공고 O)
   → 해당 공고 내용을 JSON으로 받기(툴6) → 그 JSON을 가공해 사용자 친화적 형태로 정리·출력 → 이후 이력서까지 입력하면 시나리오 3(갭 분석) 가능함을 알려주고 유도

3. **"내 이력서 기반으로 해당 공고에 지원할 수 있는지 알고 싶어"** (이력서 O / 공고 O)
   → 갭분석(툴4) 후
   · 상(上)인 경우: 근거 출력
   · 중·하인 경우: 근거 + 대체 직업군 + 로드맵 출력 (대체 직군을 **Thought**로 생성 → 그 직군 기반으로 관련 공고 검색(툴8))

4. **"해당 직업군 관련 공고 찾아줘"** (직업군명 함께 입력)
   → 툴8

5. (번외) **일상 대화** — 예: "나 너무 힘들어"
   → 공감 후 시나리오 1·2·3 중 하나가 가능함을 안내·유도
   → 예: "힘들겠다. 관심 있는 채용 공고나 이력서를 주면 네게 맞는 공고를 찾거나 비교해줄 수 있어!"

6. **취업 무관 질의** → "취업 관련 외 질의는 받지 않습니다" 거절

### 6.3 시나리오 내 사용 tool 관련 내용 (원본 설계 메모)

<툴 정리 VER_2> 

4. [툴] 갭분석 
[analyze_gap] (수정안)
  1. [LLM] detail_text → 필수/우대 항목 리스트 추출
  2. [LLM] 각 항목을 이력서(profile)가 커버하는지 매칭 (matched/partial/missing)
  3. [알고리즘] 가중치 합산 → score + level(상/중/하)
  출력예시: {score, level, matched_required[], missing_required[], matched_preferred[], rationale}


8. [툴] 유사 공고 찾기 - RAG (이력서, 혹은 대체 직군 기반 유사도 높은 공고 찾기)
- 기존 툴 5, 8을 합침
- 인풋은 이력서(json형태) 혹은 직업 명(문자열 타입) 일 수 있으며 rag쪽에 전달. rag로부터 받는 것은 관련 공고 파일 json형태(이것이 
아웃풋, 정확히는 공고 JSON들의 배열(postings))

6. [툴] 공고 URL로 DB 내 공고 JSON 파일 출력 -> URL 입력 시 , 해당 URL에 해당하는 공고 JSON 파일을 DB에서 찾아서 해당 JSON 반환

### 6.4 Agent성의 근거 (시나리오 3)

```
analyze_gap  →  level 관찰  →  (중/하이면) Thought(대체직군)  →  search_postings
    │              │                                                   │
    └── 실행하기 전엔 level을 알 수 없음 → 관찰 후에야 다음 툴이 결정됨 ──┘
        = decide → observe → decide (Agent의 정의)
```

- 시나리오 1·2·4의 상위 분기(입력 유무 기반)는 Routing(Workflow성)이므로 **Agent 정당화의 근거로 삼지 않는다.**
- Agent성은 오직 **시나리오 3의 관찰 기반 tool 체인**에서 나온다.

## 7. RAG 입출력 계약 (요약)

`search_postings`가 호출하는 RAG의 입출력. **상세·정식 계약은 별도 문서를 단일 출처로 삼는다.**

- **입력**: 직업명(`string`) 또는 `profile`(JSON) 중 하나
- **출력**: 원본 공고 필드를 그대로 두고 `score`·`match_reason`만 얹은 공고들을 `postings` 배열로 반환

```jsonc
{
  "postings": [
    { /* 원본 공고 JSON + score + match_reason */ },
    { /* ... */ }
  ]
}
```

- 정렬: `score` 내림차순 / 기본 `top_k = 3` / 결과 0건 시 `{ "postings": [] }`
- 📄 상세: `../rag_입출력 관련 명세서/RAG_입출력_명세서.md`

## 8. 고도화 백로그 (현재 프로토타입 개발 대상 아님)

> ⚠️ 아래 항목들은 **본 프로토타입(1.0.0)에서는 개발하지 않는다.** 추후 고도화 단계에서 반영을 염두에 둔 후보이며, 유사한 개선 아이디어가 나올 때마다 이 섹션에 **지속적으로 추가·정리**한다.

### 8.1 다음 설계 단계 (프로토타입 이후 곧 진행)
- Agent 패턴 선택 정리 (ReAct 유력)
- 동작 명세: 시나리오 3의 Thought/Action/Observation trace 예시
- 성공 판정 기준 체크리스트 (3~5개)

### 8.2 관측성 / 신뢰도
- **파싱 신뢰도 플래그** `meta.sectionStatus`(섹션별 `extracted`/`empty`/`uncertain`) + `warnings`. 검색 결과가 이상할 때 원인(파싱 vs 검색)을 추적하는 관측 장치. LLM 자기보고 또는 룰 대조(원문 키워드 유무로 "없음 vs 파싱 miss" 구분)로 채움. 단, 파일 추출 단계 실패는 LLM이 원리적으로 감지 불가(코드 레벨 필요).

### 8.3 안정성
- **종료 조건** (max_steps, done signal, 반복 감지 등)
- **Tool 실패 처리** (각 툴 `{ ok: false, error }` 반환 + Agent 대응), RAG 출력의 `ok`/`error` 봉투

### 8.4 정확도
- `analyze_gap` 매칭·가중치 알고리즘 정교화 (스킬 동의어 정규화, 경력 연차 매칭 등)
- 이력서 표(table) 파싱 지원 (`docx` 표 셀 처리)
- OCR 필요 공고(`need_ocr:"O"`) 처리

## 9. 예상 설계 우려사항

멀티턴 대화 상태 — 문서에 안 드러난 숨은 난이도 ⭐ 제일 중요

시나리오 1·2가 "이력서/공고 더 주면 갭분석 가능" 유도를 하잖아요? 이건 여러 턴에 걸쳐 이력서·공고를 누적한다는 뜻입니다. → 대화 상태(메모리) 관리가 필요해요.
근데 문서엔 "상태를 어떻게 들고 있는지"가 없습니다. 이게 프로토타입에서 은근히 어려운 부분이에요.
결정 필요: 프로토타입을 (A) 싱글턴(이력서+공고를 한 번에 다 받음)으로 할지, (B) 멀티턴(턴 넘어가며 누적)으로 할지.
A면 훨씬 쉬움 (유도 로직 최소화)
B면 agent다움↑ but 상태관리 복잡도↑
추천: 프로토타입은 A(싱글턴)로 시작 → 동작 확인 후 B로 확장. 문서에 이 결정을 명시하면 좋습니다.
