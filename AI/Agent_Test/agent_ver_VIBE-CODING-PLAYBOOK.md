# 바이브코딩 운영 플레이북 — 커리어 코치 Agent 버전

> **원본:** `VIBE-CODING-PLAYBOOK.md` (웹/Spring·Vue 브라운필드 전제)
> **이 버전:** 그린필드 **Python + LLM Agent** 프로토타입(`agent_prototype_1.0.0`)에 맞게 재단.
> **근거 문서(단일 출처):**
> - 설계 명세: [`agent 설계 명세서/agent_prototype_1.0.0.md`](./agent%20설계%20명세서/agent_prototype_1.0.0.md)
> - week-6 설계서: [`../ai-agent-repo/week-6/design.md`](../ai-agent-repo/week-6/design.md)
> - RAG 계약: [`rag_입출력 관련 명세서/RAG_입출력_명세서.md`](./rag_입출력%20관련%20명세서/RAG_입출력_명세서.md)

> **이 문서의 용도:** 새 세션에서 LLM에게 이 파일을 제공하면, LLM이 아래 규약대로
> `AGENTS.md`와 `tasks/`를 생성하고 그 위에서 개발을 진행한다.
>
> **첫 지시 예시:**
> "이 플레이북대로 작업한다. 먼저 §1에 따라 `AGENTS.md` 초안을 작성하고 내 컨펌을 받아라.
> 근거는 `agent_prototype_1.0.0.md`다. 컨펌 전에는 코드를 작성하지 마라."

## 0. 원칙 (LLM은 이 4줄을 항상 지킨다)

1. **컨펌 없이 코드를 쓰지 않는다.** 모든 구현은 `tasks/NN-*.md` 명세를 먼저 만들고 사람의 승인을 받은 뒤 시작한다.
2. **설계 명세에 없는 것은 만들지 않는다.** 특히 **툴은 3개(`analyze_gap`·`search_postings`·`load_posting`)로 고정**이다. 4번째 툴이 필요해 보이면 먼저 `Thought`로 풀 수 있는지 검토하고(§5), 그래도 필요하면 명세를 고쳐 다시 컨펌받는다.
3. **기존 자산을 재사용한다.** `profile` 스키마·공고 JSON·툴 계약은 이미 정의돼 있다. 새 스키마/유틸을 만들기 전에 명세서에 있는지 먼저 찾는다.
4. **실행 결과를 명세 파일에 되돌려 쓴다.** 구현이 끝나면 태스크 파일 하단에 검증 결과(§7 성공 판정 로그)를 기록한다.

## 2. `AGENTS.md` 템플릿 (Agent 프로토타입용)

목적은 하나다 — **LLM이 지어내거나 새로 만들 여지를 사전에 없애는 것.**
아래 섹션 중 **§0·§2·§5·§7이 핵심**이다(스키마·로직·에러코드를 비우면 LLM이 그럴듯하게 발명한다).

```markdown
# 커리어 코치 Agent — 이력서·공고 갭분석 Agent (Prototype 1.0.0)

> 기술 스택: Python 3.x / <LLM 프레임워크: LangChain 등 — §0에서 확정> / Pydantic / python-docx
> 근거 설계: agent 설계 명세서/agent_prototype_1.0.0.md
> 최종 갱신일: YYYY-MM-DD

## 0. 확정 전제·제약 (그린필드 — As-Is 대체)
> ★ 원본의 "현재 상태(As-Is)"는 코드가 이미 있는 프로젝트용. 우리는 코드가 없으므로
>   "반드시 이렇게 / 절대 이건 안 함"을 못박는다.
| 항목 | 확정 사항 |
|---|---|
| 언어/런타임 | Python 3.x |
| 실행 형태 | **서버 없는 파이썬 core.** `python run.py`로 함수 직접 실행·검증 |
| LLM 프레임워크 | <확정 필요: structured output 강제 가능해야 함 — with_structured_output/Pydantic> |
| LLM 프로바이더 | Claude 계열(예시) — 정확한 모델 ID는 구현 태스크에서 확정 |
| 구조화 추출 | Pydantic 스키마 강제 (free-form "JSON 뽑아줘" 금지) |
| 이력서 파싱 | python-docx (표 없는 텍스트 이력서 가정) |
| 대화 방식 | **싱글턴** (이력서+공고를 한 번에 받음). 멀티턴 누적은 범위 밖 |
| RAG(`search_postings`) | **Mock**. 계약대로 동작한다고 가정, 함수 몸통만 나중에 교체 |
| **FastAPI 서버화** | **후순위 — 마지막 태스크.** core 완성 후 얇게 씌움. Java 백엔드 연결용 |
| 모듈 모델 배치 | **정적 매핑.** 모듈(단계)별로 필요 성능에 맞는 모델을 구현 시 고정 배치. 런타임 동적 전환 아님 |
| 절대 안 할 것 | 4번째 툴 신설 / 멀티턴 상태관리 / core 없이 서버부터 짓기 / 런타임 모델 자동선택 |

| 항목 | 결정 | 유지/변경 | 우선순위 |
|---|---|:---:|:---:|
| 툴 개수 | 3개로 고정 | **유지(불변)** | ★ |
| Agent 패턴 | ReAct | 유지 | ★ |
| max_steps | 10 | 유지 | ★ |
| 대화 | 싱글턴 | 유지 | ★ |
| profile 스키마 | _UserProfileRead 10필드 | **유지(불변)** | ★ |
| 실행 층 | 파이썬 core (서버X) | 유지 | ★ |
| FastAPI/Java 연결 | 마지막 태스크 | 후순위 | ○ |

> ★ "유지(불변)"로 못박은 항목은 LLM이 개선/변경 제안해도 기각한다.

## 2. 데이터 모델 (스키마 — ERD 아님)
> ★ 원본 §2는 관계형 ERD용. 우리는 **JSON 스키마**가 데이터 모델이다. 요약하지 말고 전부 적는다.
> 원칙 한 줄: "설계서에 정의된 필드명·타입·구조는 그대로 유지한다. 임의 추가·개명 금지."
### 2.1 profile JSON (`_UserProfileRead`, 10필드) — **중심 계약**
>  search_postings와 analyze_gap이 공유. skills / experiences / projects / education /
>  certifications / languages / bootcamp / awards / evidenceMap / uncertainties
>  (각 필드 구조는 설계서 §3 표를 그대로 옮긴다)
>  규칙: 없는 섹션 → [] · 값 없는 스칼라 → null · 로드베어링 = skills·projects.techStack·experiences
### 2.2 공고 JSON (load_posting/DB 원본, 약 15필드)
>  source·posting_id·company·title·url·detail_text·need_ocr·collected_at 등 (설계서 §7.2 ① 샘플 그대로)
>  need_ocr:"X"(본문 채워진 것)만 사용
### 2.3 search_postings 출력
>  { "postings": [ 원본 공고 JSON + score + match_reason ] } · score 내림차순 · top_k=3 · 0건 → {"postings":[]}
### 2.4 run_agent 반환 계약 (core 출력) — ★ FastAPI를 나중에 공짜로 씌우기 위한 못박기
>  { "reply": "<자연어 응답>",
>    "meta": { "scenario": <1~6>, "tools_called": ["load_posting","analyze_gap", ...], "level": "상|중|하|null" } }
>  → 성공 판정(§7)이 이 반환값만으로 검증되고, FastAPI는 이걸 success/data로 감싸기만 하면 됨.

## 3. 목표 디렉토리 구조 (모듈 = 장애 격리선)
> ★ 트리로 못박는다. 모듈 경계는 "문제 터졌을 때 어디인지 즉시 갈리는 선"으로만 나눈다. 과분할 금지.
> api/         FastAPI 라우터 (얇게) — **후순위, 마지막 태스크**
> agent/       ReAct 루프·라우팅·run_agent() 진입점
> tools/       analyze_gap.py · search_postings.py(mock) · load_posting.py   ← 파일 1개 = 툴 1개
> preprocess/  resume_parser (docx→text→profile)
> llm/         llm_client — **모델 선택·호출의 단일 창구** (정적 티어 매핑이 여기 산다)
> schemas/     Pydantic 모델 (profile / 공고 / 툴 I·O / run_agent 반환)
> sample_data/ (기존) 공고 JSON·이력서 docx  ← 재사용, 이동 금지

## 4. 계약 규격 — 2층 (원본의 "인터페이스 공통 규격" 재해석)
> ★ 원본은 HTTP 규격 한 층. 우리는 두 층인데 우선순위가 다르다.
### 4.1 내부 툴 I/O 계약  ← **프로토타입의 주 계약**
>  - 툴은 예외를 throw하지 않고 **결과 객체**로 실패를 돌려준다:
>    `{"error": "<CODE>", "source": "<모듈명>", "detail": "..."}`
>    (LLM이 읽고 다음 행동을 고를 수 있게. source로 어느 모듈이 던졌는지 즉시 특정 — §7 참조)
>  - 파괴적 동작 없음(조회·분석만) → confirm 파라미터 불필요
>  - 툴 3종의 정식 입출력 스키마는 설계서 §4가 단일 출처. 여기서 재정의 말고 링크.
### 4.2 외부 API 계약 (FastAPI ↔ Java)  ← **후순위, 마지막 태스크에서 확정**
>  - core 완성 후 얇게. `run_agent()` 반환(§2.4)을 { "success": bool, "data": {...}, "error": null } 봉투로 감쌈.
>  - 엔드포인트 표면(단일 POST vs 시나리오별)은 이 태스크에서 결정. 지금 확정하지 않는다.

## 5. 핵심 비즈니스 로직 (여기가 비면 LLM이 지어낸다)
> ★ 의사코드로 확정한다.
### 5.1 analyze_gap 채점
>  1) [LLM] detail_text → 필수/우대 항목 리스트 추출
>  2) [LLM] 각 항목을 profile이 커버하는지 매칭 (matched / partial / missing)
>  3) [알고리즘] 가중치 합산 → score → level(상/중/하)
>  ※ 가중치·score→level 경계값(임계치)은 **구현 전 확정 필요** → §7 상수에 못박는다.
### 5.2 라우팅 (6 시나리오)
>  설계서 §6.1 표를 판정 규칙으로 옮긴다. 입력(이력서 유무/공고 유무/직군명/일상/무관)으로 분기.
### 5.3 관찰 기반 분기 (Agent 핵심)
>  analyze_gap.level == "상"  → rationale만 출력, search_postings 호출 안 함
>  analyze_gap.level in ("중","하") → rationale + Thought(대체직군) + 로드맵 + search_postings(대체직군)
### 5.4 Thought(툴 아님) — 대체직군 생성 / 공고 정리. LLM 내부 추론이므로 툴로 만들지 않는다.
### 5.5 단계별 모델 티어 매핑 (정적 — llm/ 단일 창구에서 관리)
> ★ 모듈(단계)별로 필요 성능에 맞는 모델을 **구현 시 고정 배치.** 런타임 자동선택 아님.
> ★ 정확한 모델 ID·프로바이더는 구현 태스크에서 확정. 아래는 난이도 티어 배치안.
| 단계(모듈) | 하는 일 | 티어 |
|---|---|:---:|
| 라우팅 (agent) | 6 시나리오 의도 분기 | cheap |
| 공고 정리 / 최종 응답 생성 (agent) | JSON→자연어 요약 | cheap~mid |
| docx→profile 구조화 추출 (preprocess) | 스키마 강제 추출 | mid |
| detail_text→필수/우대 추출 (analyze_gap) | 텍스트→항목 | mid |
| 항목 매칭 matched/partial/missing (analyze_gap) | 추론 필요 | strong |
| 대체직군 Thought (agent) | 지식 기반 추론 | strong |
> 주의: cheap 티어라도 structured output(Pydantic 강제) 지원 모델이어야 함 → 태스크 선행 검증 게이트로 확인.

## 6. 코딩 컨벤션 (금지형으로 쓴다)
| 항목 | 규칙 |
|---|---|
| 구조화 출력 | free-form 프롬프트로 JSON 파싱 **금지**. Pydantic 강제만 사용 |
| 스키마 | schemas/ 밖에서 dict 임의 조립 **금지**. 정의된 모델 사용 |
| 모델 선택 | 모듈이 직접 모델 지정 **금지**. `llm/` 창구를 통해서만 호출 (티어는 §5.5) |
| 모듈 경계 | 층 건너뛴 직접 import **금지** (예: api가 tools를 직접 X → agent 경유) |
| 툴 실패 | raise로 흐름 중단 **금지**. `{"error","source","detail"}` 반환 |
| 시크릿 | API 키 소스 하드코딩 **금지**. 환경변수 주입 |
| 툴 신설 | 3툴 외 새 툴 추가 **금지** (§0 원칙 2) |
| 멀티턴 | 대화 상태 누적 로직 추가 **금지** (싱글턴 고정) |
| 서버 선행 | core 전에 FastAPI부터 짓기 **금지** (후순위) |

## 7. 에러코드 / 공통 상수 (미리 전부 정의 — 도메인마다 새로 발명 방지)
| 이름 | 발생 지점(source) | 의미 / 메시지 |
|---|---|---|
| `NOT_FOUND` | load_posting | 해당 URL 공고가 DB에 없음 |
| `INSUFFICIENT_INPUT` | analyze_gap | 이력서/공고 정보 부족 |
| `SEARCH_FAILED` | search_postings | 검색 오류 (0건은 에러 아님 → `{"postings":[]}`) |
| 상수 `MAX_STEPS` | agent loop | 10 |
| 상수 `LEVEL 임계치` | analyze_gap | <구현 전 확정 — 예: score≥0.7 상, 0.4~0.7 중, <0.4 하> |
| 상수 `TOP_K` | search_postings | 3 |
| 상수 `MODEL_TIER[단계]` | llm/ | §5.5 매핑을 코드 상수로 (cheap/mid/strong → 실제 모델 ID) |

> ※ FastAPI 태스크 완료 후엔 `uvicorn ...` 기동 + 엔드포인트 호출도 DoD에 추가.
```

## 3. `tasks/NN-기능명.md` 템플릿

**1 태스크 = 1 세션 = 1 커밋.** 번호는 구현 순서.

## 4. 세션 진행 프로토콜

LLM은 태스크 하나를 이 순서로 처리한다.

```
[1] 명세 생성
    사람: "N번 태스크로 <기능>을 하고 싶다"
    LLM : 설계서 + AGENTS.md를 근거로 tasks/NN-*.md 초안 작성.
          → 재사용 자산 표를 채우기 위해 기존 스키마·샘플·계약·llm 창구를 먼저 확인.
          → 이 단계에서 코드는 쓰지 않는다.

[2] 컨펌  ★ 게이트
    사람이 작업 항목·DoD를 검토·수정 → 승인.

[3] 구현
    승인된 항목만 구현. 항목 밖(특히 새 툴·서버 선행)이 필요해지면 [1]로 돌아간다.

[4] 검증
    DoD를 실제로 실행한다. `python run.py` 스모크 + 해당 성공 판정 케이스.
    ★ LLM 출력은 비결정적 → "정확한 문자열"이 아니라 "구조적 동작(tool 호출 순서·에러 반환·종료)"을 판정.
      → run_agent().meta 로 검증하면 로그를 안 뒤져도 된다.
    통과할 때까지 [3]↔[4] 반복.

[5] 문서 되돌려쓰기  ★ 생략 금지
    - 작업 항목 체크박스 [x] 처리
    - "## 검증 메모" 추가 — 실행 명령·meta.tools_called·발견한 버그
    - 상태 ⬜ → ✅
    - 계획과 다르게 갔으면 §5 규약대로 취소선 처리

[6] 커밋
    코드 + 갱신된 태스크 문서를 함께 커밋.
    메시지는 태스크 단위로. 예: "feat: analyze_gap 채점 로직 (task 06)"
```

## 5. LLM 제안을 기각했을 때 (중요)

명세와 다른 방향으로 가기로 결정하면, **항목을 지우지 말고 취소선으로 남긴다.**

```markdown
- [x] ~~search_postings를 실제 임베딩 검색으로 구현~~ → **대체 채택**: mock 유지. 사유는 아래 구현 메모.
- [x] ~~프로토타입에 FastAPI 먼저 붙이기~~ → **대체**: core 함수 우선, 서버는 마지막 태스크(AGENTS §0).
- [x] ~~런타임에 난이도 감지해 모델 자동선택~~ → **대체**: 정적 티어 매핑(§5.5). 감지 로직 자체가 테스트 불가.

## 구현 메모 — 채택 방식 결정
- search_postings는 계약(입출력 스키마)만 지키는 mock으로 둔다.
  - 사유 1) 실제 RAG는 별도 담당 범위 → 계약 불변, 함수 몸통만 나중 교체
  - 사유 2) 프로토타입 성공 판정은 "구조적 동작"만 대상 → 검색 품질 불필요
```

**왜 지우면 안 되는가:** 이 태스크 파일은 다음 세션의 LLM이 다시 읽는 입력이다.
항목을 삭제하면 나중 세션이 "왜 이렇게 안 했지?" 하고 되돌린다.
취소선 + 사유가 있으면 그 되돌림이 차단된다. **거부 기록 자체가 컨텍스트다.**

## 6. 안티패턴

| 하지 말 것 | 이유 |
|---|---|
| 컨펌 없이 바로 구현 | 되돌리는 비용이 명세 쓰는 비용보다 크다 |
| **4번째 툴 신설 / Thought를 툴로 만듦** | 툴 3개 고정 원칙이 깨진다. Thought는 LLM 추론이지 외부 능력이 아니다 |
| **core 전에 FastAPI부터 짓기** | 서버·HTTP 변수가 껴서 버그 출처가 흐려진다. core는 서버 없이 돈다 |
| **런타임 모델 자동선택 로직** | 또 하나의 불확실한 LLM 호출이 되고 테스트 불가. 정적 매핑으로 |
| **멀티턴 상태관리 추가** | 싱글턴 고정 결정을 어긴다. 복잡도 폭증 |
| **모듈 과분할** (20개 파일) | 장애 격리선을 넘어선 분할은 오히려 추적을 어렵게 한다 |
| DoD를 "동작 확인"으로 뭉뚱그림 | 검증 불가·완료 판정이 주관적이 된다 |
| **LLM 출력 문자열을 그대로 assert** | 비결정성 때문에 재현 불가. 구조적 동작(meta)으로 판정할 것 |
| **갭분석·추천 "품질"을 성공 기준에 넣음** | 프로토타입 판정 대상은 구조뿐. 품질은 LLM 의존 → 범위 밖 |
| 검증 메모(tool 호출 로그)를 안 남김 | 다음 세션이 같은 함정을 다시 밟는다 |
| 태스크 하나에 기능 3개 | 세션 컨텍스트가 넘치고 커밋 추적이 깨진다 |
| AGENTS.md §2(스키마)·§5(로직)·§7(에러코드)를 비워둠 | LLM이 그럴듯하게 지어낸다 |
| 기각 항목을 삭제 | 다음 세션이 되돌린다 |

## 7. 검증 체크리스트 (태스크 종료 전 매번)

- [ ] 스모크 실행 통과 — `python run.py` 크래시 없이 완료
- [ ] DoD 항목 전부 **실제 실행**으로 확인 (읽어보고 판단 X)
- [ ] 해당 태스크가 걸린 **성공 판정 기준**(아래) 충족 — `run_agent().meta`로 확인
- [ ] 컨벤션 정합 — AGENTS §6 위반 없음, 스키마·샘플·계약·llm창구 재사용했는가 (중복 구현 X)
- [ ] 모듈 경계 준수 — 층 건너뛴 직접 import 없는가, 에러에 `source` 있는가
- [ ] API 키가 소스에 평문으로 없는가 (환경변수 주입)
- [ ] LLM이 문서/주석에 쓴 사실이 실제 코드·설계서와 일치하는가 (환각 교차검증)

### 성공 판정 기준 (설계서 §8 — 구조적 동작만, 품질 아님)

| # | 기준 | 판정 방법 (meta 기반) |
|---|---|---|
| 1 | 이력서+공고 요청(시나리오 3)에서 `analyze_gap`이 호출된다 | `meta.tools_called`에 포함 |
| 2 | level '중/하' → 이어서 `search_postings`(대체직군) 호출 **★핵심** | `meta.tools_called`에서 `analyze_gap → search_postings` 순서 |
| 3 | level '상' → 추가 검색 없이 rationale만 | '상' 케이스에서 search_postings **미포함** |
| 4 | 없는 URL → `load_posting`이 `NOT_FOUND` 반환, 크래시 없이 안내 응답 | 없는 URL 입력 → 크래시 없음, error.source 확인 |
| 5 | 모든 요청이 `max_steps`(10) 이내 종료 | step 카운트 ≤ 10 |

> **기준 2가 이 Agent의 핵심** — "관찰(level)이 다음 tool 호출을 결정한다"는 Agent 정당화가 실제로 동작하는지 판정.

## 8. 알려진 한계 — 사람이 반드시 볼 것

- **LLM 비결정성**: 같은 입력에도 출력 문구가 달라진다. 판정은 문자열이 아니라 **구조(meta: tool 호출 순서·에러 source·종료)**로만 한다.
- **사실 환각**: 문서·주석·README에 실제와 다른 내용을 쓴다. 설계서와 교차 검증 필수.
- **맥락 무시**: 컨텍스트가 부족하면 정의된 스키마·mock·llm창구를 무시하고 새로 만들려 한다. → §3 "재사용 자산" 표 + AGENTS §0·§2로 방어.
- **버전 호환**: LLM 프레임워크(structured output 지원 여부)·모델 티어별 지원·Python 버전 충돌은 사람이 검증한다. → 태스크 "선행 검증 게이트"로 조기 확인.
- **보안**: API 키 관리는 산출물을 그대로 두지 말고 사람이 최종 점검한다.
- **범위 밖(설계서 §8 백로그)**: 멀티턴, 관측성 플래그, 툴 실패 재시도, 채점 알고리즘 정교화, 표 파싱, OCR — **프로토타입에서 건드리지 않는다.**
