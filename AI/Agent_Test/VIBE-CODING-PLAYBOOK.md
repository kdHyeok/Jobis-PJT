# 바이브코딩 운영 플레이북

> **이 문서의 용도:** 새 프로젝트 세션에서 LLM에게 이 파일을 제공하면, LLM이 아래 규약대로
> `AGENTS.md`와 `tasks/`를 생성하고 그 위에서 개발을 진행한다.
>
> **첫 지시 예시:**
> "이 플레이북대로 작업한다. 먼저 §1에 따라 `AGENTS.md` 초안을 작성하고 내 컨펌을 받아라.
> 컨펌 전에는 코드를 작성하지 마라."

---

## 0. 원칙 (LLM은 이 4줄을 항상 지킨다)

1. **컨펌 없이 코드를 쓰지 않는다.** 모든 구현은 `tasks/NN-*.md` 명세를 먼저 만들고 사람의 승인을 받은 뒤 시작한다.
2. **명세에 없는 것은 만들지 않는다.** 범위를 넓히고 싶으면 명세를 고치고 다시 컨펌받는다.
3. **기존 자산을 재사용한다.** 새 클래스/유틸을 만들기 전에 같은 역할의 기존 코드가 있는지 먼저 찾는다.
4. **실행 결과를 명세 파일에 되돌려 쓴다.** 구현이 끝나면 태스크 파일 하단에 검증 결과를 기록한다.

---

## 1. 층 구조 — 파일 2종

| 파일 | 역할 | 갱신 시점 |
|---|---|---|
| `AGENTS.md` (레포 루트) | 프로젝트 불변 규칙. **매 세션 자동 로드됨** | 거의 안 바뀜 |
| `tasks/NN-기능명.md` | 태스크 계약 **+ 실행 결과 기록** | 실행 전 / 실행 후 양쪽 |

> `AGENTS.md`는 Claude Code·Codex 등이 자동으로 읽는 표준 파일명이다. 파일명을 바꾸지 말 것.
> 매번 붙여넣을 필요 없이 항상 컨텍스트에 들어간다.

**작업 순서: `AGENTS.md` 작성 → 커밋 → 그 다음에 첫 코드.**
컨텍스트 문서가 코드보다 먼저 커밋되어야 한다.

## 2. `AGENTS.md` 템플릿

목적은 하나다 — **LLM이 지어내거나 새로 만들 여지를 사전에 없애는 것.**
아래 섹션 중 §0·§3·§6·§7이 핵심이다. 나머지는 프로젝트 성격에 따라 조절한다.

```markdown
# <프로젝트명> — <한 줄 설명>

> 기술 스택: <스택 나열>
> 최종 갱신일: YYYY-MM-DD

## 0. 현재 상태 (As-Is) — 출발점
> "지금 레포에 실제로 있는 것"만 적는다. 계획이 아니라 사실.
| 영역 | 현재 상태 |
|---|---|
| 언어/런타임 | |
| 구현된 기능 | |
| 구현된 데이터 | |
| 미사용/레거시 | |

<기존 소스 구조 트리>

※ 신규(그린필드) 프로젝트라면 이 절을 **"확정 전제·제약"**으로 대체:
   반드시 써야 하는 라이브러리·버전, 절대 안 쓸 것, 배포 환경 등.

## 1. 결정 사항 (As-Is → To-Be)
| 항목 | 현재 | 목표 | 우선순위 |
|---|---|---|:---:|
> ★ **바꾸지 말 것**을 반드시 "유지"로 명시한다.
>   예: "회원 식별자 = 유지(INT)", "기존 4개 테이블 스키마 = 그대로 유지하고 확장"
> ★ 범위 밖 항목은 "후순위"로 따로 묶는다. LLM이 손대는 것을 막는다.

## 2. 데이터 모델 (ERD / 스키마)
> 테이블·컬럼·타입을 전부 적는다. 요약하지 않는다.
> 앞머리에 원칙 한 줄: "기존 테이블의 컬럼명·타입·PK는 그대로 유지하고 확장한다."

## 3. 목표 디렉토리 구조
> 트리로 못 박는다. 파일 위치 논쟁이 사라진다.
> 하단에 "정리 대상(삭제할 레거시)"도 명시.

## 4. 인터페이스 공통 규격
> - 공통 응답/에러 포맷을 **JSON 실예시**로
> - 전체 엔드포인트(또는 공개 API) 목록 표
> - 인증/권한 규칙

## 5. 핵심 비즈니스 로직
> 계산식·판정 규칙을 **의사코드로 확정**한다. 반올림 규칙과 예시 결과값까지.
> 여기가 비면 LLM이 그럴듯하게 지어낸다.

## 6. 코딩 컨벤션
| 항목 | 규칙 |
|---|---|
> ★ **금지형으로 쓴다.** "~를 권장" (X) → "~ 금지" (O)
>   예: "Options API 금지", "세션 사용 중단", "중복 구현 금지"
> 포함: 패키지/모듈 경로 규칙, 네이밍 접미사, 계층별 책임, 상태관리 방식, 환경변수 접근법

## 7. 에러 코드 / 공통 상수
| 이름 | HTTP | 메시지 |
|---|:---:|---|
> ★ 미리 전부 정의한다. 안 그러면 도메인마다 LLM이 새 코드를 발명한다.

## 8. 빌드 및 실행
> 사전 조건 + 실제 실행 명령. DoD 검증에 그대로 쓰인다.
```

## 재사용 자산 (신규 작성 금지)
| 용도 | 재사용 대상 |
|---|---|
| | <기존 파일 경로 링크> |

## ⚠️ 선행 검증 게이트  (불확실 요소가 있을 때만)

## 4. 세션 진행 프로토콜

LLM은 태스크 하나를 이 순서로 처리한다.

```
[1] 명세 생성
    사람: "N번 태스크로 <기능>을 하고 싶다"
    LLM : AGENTS.md를 근거로 tasks/NN-*.md 초안 작성.
          → 재사용 자산 표를 채우기 위해 기존 코드를 먼저 검색할 것.
          → 이 단계에서 코드는 쓰지 않는다.

[2] 컨펌  ★ 게이트
    사람이 작업 항목·DoD를 검토·수정 → 승인.

[3] 구현
    승인된 항목만 구현. 항목 밖의 것이 필요해지면 [1]로 돌아간다.

[4] 검증
    DoD를 실제로 실행한다. 빌드/테스트/엔드포인트 호출.
    통과할 때까지 [3]↔[4] 반복.

[5] 문서 되돌려쓰기  ★ 생략 금지
    - 작업 항목 체크박스 [x] 처리
    - "## 검증 메모" 추가 — 실행 명령·결과·발견한 버그
    - 상태 ⬜ → ✅
    - 계획과 다르게 갔으면 §5 규약대로 취소선 처리

[6] 커밋
    코드 + 갱신된 태스크 문서를 함께 커밋.
    메시지는 태스크 단위로. 예: "feat: 인증 JWT 전환 (task 03)"
```

## 5. LLM 제안을 기각했을 때 (중요)

명세와 다른 방향으로 가기로 결정하면, **항목을 지우지 말고 취소선으로 남긴다.**

```markdown
- [x] ~~pom.xml에 Spring AI 의존성 추가~~ → **대체 채택**: 의존성 무추가, HTTP 직접 호출. 사유는 아래 구현 메모.
- [x] ~~config.ChatClientConfig~~ → **대체**: domain.coach.llm.CoachLlmClient

## 구현 메모 — 채택 방식 결정
- Spring AI starter 대신 OpenAI 호환 API 직접 호출을 채택.
  - 사유 1) Boot 3.3.4 + Spring AI 1.0 GA(Boot 3.4+ 요구) 호환 충돌 회피
  - 사유 2) 의존성 무추가로 빌드 리스크 최소화
```

**왜 지우면 안 되는가:** 이 태스크 파일은 다음 세션의 LLM이 다시 읽는 입력이다.
항목을 삭제하면 나중 세션이 "왜 이렇게 안 했지?" 하고 되돌린다.
취소선 + 사유가 있으면 그 되돌림이 차단된다. **거부 기록 자체가 컨텍스트다.**

외부 예제를 참고했을 때도 같은 방식으로 차이를 명시한다:
> "참고한 예제는 JSP 기반이나, 본 프로젝트는 Vue 3 SPA이므로 적용 대상이 다름."

## 6. 안티패턴

| 하지 말 것 | 이유 |
|---|---|
| 컨펌 없이 바로 구현 | 되돌리는 비용이 명세 쓰는 비용보다 크다 |
| DoD를 "동작 확인"으로 뭉뚱그림 | 검증이 불가능해지고 완료 판정이 주관적이 된다 |
| 검증 메모를 안 남김 | 이 방법론의 이점 절반이 날아간다. 다음 세션이 같은 함정을 다시 밟는다 |
| 태스크 하나에 기능 3개 | 세션 컨텍스트가 넘치고 커밋 추적이 깨진다 |
| `AGENTS.md`의 §5(로직)·§7(에러코드)를 비워둠 | LLM이 그럴듯하게 지어낸다 |
| 기각 항목을 삭제 | 다음 세션이 되돌린다 |
| 완료된 태스크 상태 표를 방치 | 진행 상황이 실제와 어긋나 신뢰를 잃는다 |

## 7. 검증 체크리스트 (태스크 종료 전 매번)

- [ ] 빌드 통과 — `<빌드 명령>`
- [ ] DoD 항목 전부 실제 실행으로 확인 (읽어보고 판단 X)
- [ ] 컨벤션 정합 — AGENTS §6 위반 없음, 기존 코드 재사용했는가 (중복 구현 X)
- [ ] 기존 기능 회귀 없음
- [ ] 시크릿·키가 소스에 평문으로 없는가 (환경변수 주입)
- [ ] LLM이 문서/주석에 쓴 사실이 실제 코드와 일치하는가 (환각 교차검증)

## 8. 알려진 한계 — 사람이 반드시 볼 것

- **버전 호환**: LLM은 최신 라이브러리를 전제로 제안한다. 실제 런타임/프레임워크 버전과의 충돌은 사람이 검증한다.
- **사실 환각**: 문서·주석·README에 실제와 다른 내용을 쓴다. 교차 검증 필수.
- **맥락 무시**: 컨텍스트가 부족하면 기존 코드를 무시하고 새로 만들려 한다. → §3 "재사용 자산" 표로 방어.
- **보안**: 키 관리, 권한·소유권 검증은 산출물을 그대로 두지 말고 사람이 최종 점검한다.
