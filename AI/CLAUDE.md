# CLAUDE.md

이 문서는 프로젝트의 **Git 협업 규칙**을 정의한다. 팀원과 협업 에이전트(Claude Code 포함)는 이 규칙을 기준으로 브랜치, 커밋, PR을 관리한다. 규칙은 업계에서 가장 널리 쓰이는 **GitHub Flow 브랜치 전략 + Conventional Commits + PR 리뷰 기반 병합**을 따른다.

---

## 1. 브랜치 전략 (GitHub Flow)

### 1.1 기본 브랜치

| 브랜치 | 용도 | 규칙 |
|---|---|---|
| `main` | 항상 배포 가능한 안정 버전 | 직접 push 금지. PR을 통해서만 병합. |

`main` 하나만 상시 유지하고, 모든 작업은 `main`에서 분기한 짧은 수명의 작업 브랜치에서 진행한 뒤 PR로 다시 `main`에 병합한다.

### 1.2 작업 브랜치

작업은 항상 `main`에서 브랜치를 새로 파서 진행하며, 절대 `main`에서 직접 작업하지 않는다. 작업 브랜치는 오래 유지하지 않고, 병합되면 바로 삭제한다.

| 접두사 | 용도 | 분기 기준 | 병합 대상 |
|---|---|---|---|
| `feature/` | 신규 기능 개발 | `main` | `main` |
| `fix/` | 버그 수정 | `main` | `main` |
| `refactor/` | 기능 변경 없는 리팩터링 | `main` | `main` |
| `docs/` | 문서 작업 | `main` | `main` |
| `chore/` | 설정·빌드·의존성 등 잡무 | `main` | `main` |

### 1.3 브랜치 이름 규칙

```
<타입>/<이슈번호>-<간단한-설명>
```

- 소문자와 하이픈(`-`)만 사용한다. (kebab-case)
- 이슈 번호가 있으면 포함한다.

**예시**
```
feature/12-job-posting-parser
fix/34-resume-pdf-extract-error
docs/5-git-convention
```

## 2. 커밋 메시지 규칙 (Conventional Commits)

### 2.1 형식

```
<타입>(<범위>): <제목>

<본문 (선택)>

<푸터 (선택)>
```

- **제목**은 50자 이내, 명령형 현재 시제로 작성한다. (예: "추가한다" / "add", "고친다" / "fix")
- 제목 끝에 마침표를 붙이지 않는다.
- 본문은 "무엇을, 왜" 변경했는지 설명한다. (어떻게는 코드가 설명한다)
- 하나의 커밋은 하나의 논리적 변경만 담는다.

### 2.2 타입

| 타입 | 의미 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 |
| `style` | 코드 포맷팅, 세미콜론 등 로직 변화 없는 수정 |
| `refactor` | 기능 변화 없는 코드 구조 개선 |
| `test` | 테스트 코드 추가·수정 |
| `chore` | 빌드, 패키지 매니저, 설정 등 기타 잡무 |
| `perf` | 성능 개선 |
| `ci` | CI/CD 설정 변경 |

### 2.3 범위(scope)

변경이 속한 모듈·영역을 괄호에 명시한다. (선택이지만 권장)

**예시**
```
feat(agent): Gap Analyzer 갭 판정 체인 추가
fix(backend): 이력서 PDF 추출 시 인코딩 오류 수정
docs(readme): 실행 방법 안내 보강
```

## 3. Pull Request (PR) 규칙

### 3.1 기본 원칙

- 모든 병합은 PR을 통해서만 이루어진다. `main`에 직접 push하지 않는다.
- PR은 **작게, 자주** 올린다. 리뷰 가능한 단위(대략 400줄 이하 변경 권장)로 나눈다.
- PR 제목은 커밋 규칙과 동일한 형식을 따른다. (예: `feat(agent): Roadmap Planner 체인 구현`)

### 3.2 PR 본문 템플릿

```markdown
## 작업 내용
- 무엇을 했는지 요약

## 변경 이유
- 왜 이 변경이 필요한지

## 확인 방법
- 리뷰어가 어떻게 검증하면 되는지 (실행/테스트 방법)

## 관련 이슈
- Closes #12
```

### 3.3 리뷰·병합 규칙

- PR은 **최소 1명 이상의 승인(approve)** 을 받아야 병합할 수 있다.
- 리뷰어는 24시간 이내 확인을 권장한다.
- CI가 있으면 **모든 체크가 통과**해야 병합한다.
- 병합 방식은 **Squash and merge**를 기본으로 한다. (커밋 히스토리를 깔끔하게 유지)
- 병합 후 작업 브랜치는 삭제한다.
- 리뷰 코멘트는 존중하는 태도로 작성하고, 반영/미반영 사유를 남긴다.

## 4. 이슈(Issue) 규칙

- 모든 작업은 이슈로 등록한 뒤 브랜치를 만든다.
- 이슈 제목은 명확한 한 문장으로 작성한다.
- 라벨로 유형을 구분한다. (`feature`, `bug`, `docs`, `question` 등)
- 이슈 본문에는 배경, 목표, 완료 조건(Definition of Done)을 적는다.
- 완료된 이슈는 PR에서 `Closes #번호`로 자동 종료되게 연결한다.

---

## 5. 협업 워크플로 요약

```text
1. 이슈 생성
2. main에서 최신 상태로 pull
3. feature/<이슈번호>-<설명> 브랜치 생성
4. 작업 + Conventional Commits 규칙에 맞게 커밋
5. 원격 push 후 PR 생성 (대상: main)
6. 코드 리뷰 → 승인 → Squash and merge
7. 브랜치 삭제
8. main 병합 시점이 곧 배포 시점 (항상 배포 가능한 상태 유지)
```

---

## 6. 지켜야 할 기본 수칙

- 작업 시작 전 항상 `git pull`로 최신 상태를 반영한다.
- 커밋 전 변경 내용을 `git diff`로 확인한다.
- `.env`, 비밀 키, 개인 자격증명, 대용량 산출물은 절대 커밋하지 않는다. (`.gitignore`로 관리)
- `force push`(`git push -f`)는 공용 브랜치에서 금지한다. 개인 작업 브랜치에서만 신중히 사용한다.
- 커밋과 PR은 자주, 작게. 큰 덩어리로 몰아서 올리지 않는다.
- 충돌(conflict)은 발생 즉시 본인 브랜치에서 해결하고 리뷰어에게 넘기지 않는다.
