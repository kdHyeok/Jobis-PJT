## 두 개의 축

이 폴더를 읽을 때 헷갈리는 지점은 **"도구/에이전트"와 "단발/자기 루프"가 다른 축**이라는 것이다.

**축 1 — 말을 하는가 (`AgentSpec.kind`)**

- **도구(`kind="tool"`)**: 계산만 하고 `reply` 를 비운다. 문장은 `tool_render` 가 만든다.
  그래서 문구를 고칠 때 계산 코드를 건드리지 않는다.
- **에이전트(`kind="agent"`)**: 스스로 말한다.

**축 2 — 몇 번 도는가**

- **단발**: `session dict → AgentResult` 한 번.
- **자기 루프**: `agent_loop` 하네스를 타고 도구를 골라 쓰며 여러 스텝을 돈다.

두 축이 겹친 예가 `fit_analysis`(도구인데 무겁다)와 `posting_analysis`(에이전트이면서 루프다).

**모든 파일이 지키는 규율 하나**: 자율성은 표현에, **근거는 도구에.** LLM 은 판단하되
없는 근거를 만들 수 없다 — 근거는 결정론 파이썬 함수만 준다.

# 기반 3개

## `__init__.py` — 레지스트리

`AgentSpec` 자료형과 `get_agent_registry()` 하나. **"무엇이 존재하는가"의 단일 출처**이고,
오케스트레이터는 여기 등록된 이름만 호출할 수 있다(플래너 환각의 화이트리스트 방어).

`AgentSpec` 의 필드가 곧 오케스트레이션의 어휘다:

| 필드 | 뜻 |
|---|---|
| `description` | 플래너 manifest 에 실리는 카탈로그 문구. **에이전트 실행 시에는 안 읽힌다** |
| `preconditions` | AND — 전부 있어야 실행 |
| `preconditions_any` | OR — 하나라도 있으면 충족 |
| `produces` | 실행 성공 시 생기는 자산. 검증기가 선행 삽입을 추론하는 근거 |
| `entry` | 실제 호출되는 함수 |
| `kind` / `render` | 도구인가 · 도구면 문장을 누가 만드나 |
| `params` / `params_satisfy` | 플래너가 넘길 수 있는 인자 · 그 인자가 전제를 대신하나 |
| `heavy` | 자동 삽입 시 사용자 동의를 먼저 받나 |
| `internal` | 플래너에게 숨기고 오케스트레이터가 결정론으로 부르나 |

`preconditions`(필요) ↔ `produces`(생산) 짝이 의존 그래프를 만들고, 검증기가 빠진 전제를
`produces` 하는 에이전트를 앞에 자동으로 끼운다.

## `_common.py` — 공용 헬퍼

들어오는 기준은 자산 종류가 아니라 **"둘 이상이 같은 계산을 따로 구현했나"** 다.
헬퍼 7개 중 6개의 docstring 이 `실측: ~했다` 로 시작한다 — 미리 설계한 추상화가 아니라
실제로 깨진 다음에 모은 것이다.

**자산 확보** (없으면 만들어 캐시)
- `ensure_posting_text` — URL 자산 → 원문 텍스트 승격. 공고가 아닌 페이지는 거부한다(D102)
- `ensure_profile` — 이력서 → 정규화 프로필 (LLM 호출이라 캐시가 중요)

둘 다 같은 함정을 공유한다: **세션 dict 는 복사본**이라 직접 고쳐도 안 남는다. 턴 안이면
`_stagedUpdates` 에 스테이징하고, 턴 밖이면 저장소에 직접 쓴다. 턴 안에서 직접 쓰면 턴 끝의
write-back 이 방금 만든 캐시를 덮는다.

**세션 읽기**
- `posting_identity` — (회사명, 직무). 자소서는 회사명을 안 읽었고 `application_plan` 은
  없는 칸에서 읽어 늘 빈 값이었다. 두 곳이 같은 것을 다르게 틀려서 모았다
- `agent_arg` — 플래너가 넘긴 인자. 없으면 빈 문자열(에이전트는 기존대로 동작)
- `upsert_posting_library` — 정리했던 공고를 최대 5개 기억(D86). 항목은 원문(`_sourceText`)도
  들고 있어 그 공고를 활성으로 되돌릴 수 있다(D111). 밑줄 키는 소비자가 필드를 골라 써서
  화면·프롬프트로 나가지 않는다

**루프에 줄 재료**
- `grep_source_lines` — 원문에서 키워드 든 줄. **못 찾으면 못 찾았다고 돌려준다**
  (빈 관찰을 주면 LLM 이 사전지식으로 채운다)
- `others_this_turn` — 이번 턴에 나 말고 실행될 담당들. 없는 사실은 지시로 못 메우므로
  **구조로 준다**

## `agent_loop.py` — 자기 루프 하네스

`session → AgentResult` 순수 함수로는 표현할 수 없던 일(면접 꼬리 질문, 자소서 자기비판)을
가능하게 하는 틀.

```
매 스텝: {facts, recentHistory, userFacts, observations} → LLM
  use_tool → 도구 실행 → 관찰 문자열 → observations 에 누적 → 다음 스텝
  reply    → 금지표현 검증 → 통과하면 종료
  상한(기본 5) 도달 → 도구 없이 답만 만들게 함
```

**가두는 장치**

- 도구 이름을 Pydantic `Literal` 로 제한 — 프롬프트 부탁이 아니라 **스키마로** 환각 차단.
  단, `action` 자리에 도구 이름을 바로 쓰는 것도 받는다(모델이 자연스럽게 하는 표기를
  막을 이유가 없다 — 막을 것은 없는 도구지 표기가 아니다)
- 스텝 상한 — **"몇 번 고쳐 쓸 수 있나"를 정하는 값**이다. 자소서는 7
- 금지표현이 걸리면 **한 번은 다시 쓰게 한다** — 바로 폴백하면 맥락 있는 답변을 통째로 잃는다
- 도구 실패는 예외가 아니라 관찰로 알린다(루프가 안 죽는다)

**`delegate_tool`** — 에이전트가 다른 에이전트를 부르는 통로. 지금 쓰는 곳은
`coverletter_draft`(→`resume_diagnosis`)와 `preference_intake`(→`job_recommend`) 둘뿐이다.
가드: 읽기 전용 · 세션 사본 전달 · 화이트리스트 · `heavy` 금지 · 깊이 1 · 거부도 trace.

**폴백이 이유를 삼키지 않는다** — 이 파일을 관통하는 규율. 실패해도 `LoopOutcome` 자체는
돌려준다(`None` 이면 호출부가 폴백하며 warnings 를 잃는다). 도구가 낸 경고도
`__warnings__` 키로 끌어올린다.

## `tool_render.py` — 표현 계층

도구는 말하지 않으므로 문장은 전부 여기서 만든다. 함수는 모두 `(문장, 경고들)` 을 낸다 —
경고를 못 돌려주면 폴백 이유가 조용히 사라진다.

대부분 결정론 문자열 조립이고, LLM 을 쓰는 자리가 몇 군데 있다(적합도 판정 뒤의 다음 행동
제안, 공고·이력서 정리의 마무리 문장). LLM 표현은 **금지표현 검증 통과 + 실패 시 결정론
폴백**을 지킨다.

주요 함수: `render_fit_analysis` · `render_job_recommend` · `render_posting_analysis` ·
`render_resume_diagnosis` · `render_roadmap_manager` · `render_posting_fetch`.
`posting_facts` 는 렌더 전용이 아니라 루프의 facts 조립에도 쓰인다.

# 도구 4개

## `posting_fetch.py` — URL 수집 (49줄, internal)

**URL 자산 → 원문 텍스트 자산 승격, 그 하나만 한다.** 발화에서 URL 을 뽑는 것은
`chat.detect_posting_urls`(정규식), 내용 파싱은 `posting_analysis` 다.

왜 수집을 따로 뗐나(D64): 수집(I/O, 느리고 실패함)과 읽기(파싱)는 실패 양상이 다르다.
제 단계를 가지면 진행 UI 에 보이고, 실패 시 "본문 붙여넣어 주세요" 카드가 이 도구 하나에서
떨어진다.

`internal=True` — URL 이 미수집이면 다음 단계는 필연이라 LLM 이 고를 판단이 아니다.
`chat.py` 가 큐 맨 앞에 결정론으로 꽂는다. manifest 를 안 건드리므로 플래너 재측정도 없다.

## `fit_analysis.py` — 적합도 판정 (heavy)

**판정 로직이 한 줄도 없다.** 세션 자산을 `AnalyzeRequest`/`GraphState` 로 바꿔 판정
파이프라인(`build_graph`)을 부르고 결과를 전달하는 래퍼다.

- **화이트보드 ↔ 그래프 양방향**(D84): 이미 있는 파싱·프로필을 그래프에 시드해 재계산을
  막고, 그래프가 새로 만든 지식은 자산으로 승격한다
- **완료된 분석만 승격한다** — `need_more_info` 상태를 저장하면 다음 턴 라우터가
  "분석 있음"으로 오판해 자소서·면접이 빈 근거 위에서 돈다
- **지목 개수가 뜻을 가른다**(플래너 인자 `targets`): **둘 이상 = 비교**(D88) — 라이브러리
  파싱본을 대상별로 시드해 반복하고, `analysis` 자산은 **활성 공고일 때만** 승격한다
  (근거-대상 불일치 방지). **하나 = 전환**(D111) — `_switch_active` 가 활성 공고 자체를
  갈아 끼우고 평소 단일 경로로 판정한다. 하류(자소서·면접)는 활성 하나만 보기 때문이다
- 뒤 단계의 타당성 변경(등급이 낮으면 자소서 대신 지원 경로 설계로)은 여기서 판단하지
  않는다 — `observe_rules` 가 결정론으로 한다

## `job_recommend.py` — 공고 추천

`find_alternatives` 의 프로필-단독 판. **LLM 호출이 없다.**

```
프로필 스킬 + 직군 + 선호 → 검색 쿼리 → RAG(30건) → 연차 필터 → gap_matcher 매칭 → 상위 5
```

- **연차 필터** — "신입"이라 말한 사용자에게 8년 요구 공고가 가던 문제. 신입에게는
  연차 미표기 '경력' 공고도 제외한다(데이터의 최다 유형이라 이게 원인이었다).
  경력자에게는 +1년까지 허용(도전 가능)
- **이력서 없이 선호만으로도 동작한다** — 그때는 역량 일치를 계산하지 않는다.
  빈 프로필로 매칭하면 전 후보가 "일치 0" 으로 탈락해 추천이 통째로 사라진다.
  근거를 없는 것처럼 말하지 않고 "이력서를 올리면 일치까지 계산해 드려요"로 답한다
- **실공고가 없으면 지어내지 않는다** — 빈 결과 + 정직한 경고

# 자기 루프 5개

## `posting_analysis.py` — 공고 담당

**도구에서 대화형 에이전트로 승격됐다(D97).** 계기는 실측 — 공고를 정리한 뒤 "이 공고 기준으로
뭘 공부할까"를 물었는데 어휘에 그 담당이 없어 플래너가 이력서를 요구하는 쪽으로 갔다.
공고만으로 답할 수 있는 질문에 사용자 정보를 요구한 것이다.

```
_parse (결정론)                    루프 (LLM)
  URL 수집 → 파싱 → 캐시      →     read_posting / save_plan → 답변
  같은 원문은 재파싱 안 함(D79)      못 만들면 tool_render 폴백
```

- **`save_plan` 이 이 파일의 핵심 설계다.** 프로젝트 제안은 **커버하는 요구사항 ID 를 대야**
  기록된다. 외부 리뷰가 "제안이 아무 공고에나 나올 답"이라 지적했고, 처방은 "프롬프트로
  근거를 강제하라"였지만 그건 실측이 부정한 방식이다 — 대신 근거 필드를 **필수로** 만들고
  도구가 검증한다. 공고에 없는 ID 를 대면 기록되지 않고 이유가 관찰로 돌아간다
- `requirement_index` 에서 **연차 요건은 빠진다** — 프로젝트로 연차를 채울 수는 없다.
  하면 안 되는 것은 선택지에서 뺀다
- **루프가 답하면 그 답이 전부다.** 결정론 요약 표를 앞에 붙였더니 루프가 같은 요건을
  611자로 다시 정리해 사용자가 같은 목록을 두 번 봤다. **한 문장의 생산자가 둘이면
  프롬프트로는 못 막는다.** 표는 폴백 경로에만 남는다
- 한 턴에 URL 이 여러 개면 나머지를 **병렬로** 수집·파싱해 라이브러리로 승격(D94)

## `resume_diagnosis.py` — 이력서 담당

`posting_analysis` 의 짝이고 승격 이유도 같다(D97). 항목화 사실만 내던 시절에는
"내 강점이 뭐야"의 담당이 없었다 — `evidencedSkills` 는 있었지만 그걸 **강점으로 서술**하는
층이 없었다.

- 결정론 부분: `ensure_profile` → 섹션 항목화 → 근거 있는 스킬 vs 이름만 적힌 스킬 →
  빈 섹션 → 보완 질문
- 루프 도구는 `read_resume` 하나. 프로필은 정형 추출이라 자기소개·성과 서술이 통째로 빠진다
- **이름만 적힌 스킬은 결함이 아니라 보강 지점**으로 말한다. 빈 섹션은 "부족"이 아니라
  "아직 안 적힌 것" — 적지 않은 경험이 없는 경험은 아니다
- 승격하면서 "대신 할 수 있는 일"이라는 **역할 문장을 지웠더니** 평가셋 케이스가
  1.00 → 0.67 로 깨졌다. 능력과 역할은 다른 정보이고 둘 다 있어야 한다

## `preference_intake.py` — 선호 수집

"이력서 없는데 공고 추천받고 싶어"를 "이력서 주세요"로 닫지 않는다.

- **분기점은 순수 파이썬**(`_sufficient`) — 선호 차원 2개 이상, 또는 1개 + 되묻기 2턴 소진.
  LLM 이 바꿀 수 없고, 무한 되묻기로 사용자를 가두지 않는다
- 직군 1차 탐지는 `role_taxonomy` 별칭 매칭(LLM 없이도 동작)
- 도구 인자는 문자열 하나뿐이라 **라벨 줄 미니포맷**(`직군: 백엔드`)을 쓰고 도구가 파싱한다
- **`preview_postings`(= `job_recommend` 위임)가 대화를 바꾼다**: 0건이면 조건이 좁다는
  뜻이니 넓히자고 묻고, 여러 건이면 이력서를 받아 정교화하자고 넘어간다
- 표현 검증이 2종이다 — 금지표현 + **질문으로 끝나는지**. 이 에이전트의 응답은 항상 다음
  정보를 물어야 하므로, 확인만 하고 끝난 문장은 버리고 폴백(항상 질문형)을 쓴다

## `interview_prep.py` — 면접 연습 (첫 자기 루프)

질문 → 답변 → 평가 → **꼬리 질문**이 여러 턴 이어진다. 상태는 세션 자산 `interview`
(`asked`/`answers`/`usedTopics`)에 남아 다음 턴이 이어받는다.

- **소재 선택이 결정론 가중치 계산이다** — LLM 이 순위를 바꿀 수 없다:
  사용자 프로젝트에 실제 등장(3) > 공고 필수 요건(2) > 격차 심각도(0~2) >
  기재만 되고 근거 없음(2). 마지막 항목이 "면접관이 반드시 파고드는 지점"이다
- `check_answer` 도 인상이 아니라 **세는 것으로** 판정한다: 기술 용어 개수 + 숫자 유무 +
  역할 서술어(담당·구현·주도…)
- 한 번에 **질문 하나만**. 여러 개를 나열하면 연습이 안 된다
- 폴백해도 **이번 턴에 도구가 쌓은 진행분은 보존한다** — LLM 이 한 번 실패했다고 사용자의
  답변 기록이 사라지면 안 된다

## `coverletter_draft.py` — 자소서 초안 (581줄, 가장 큼)

쓰고 → 점검하고 → 고치는 루프. 상한이 7인 이유는 그 한 바퀴를 돌 수 있는 최소치이기 때문이다.

- **근거의 출처를 갈랐다**: 공고 쪽(요건·부족 역량)은 *과제*라 프롬프트에 싣고,
  이력서 쪽은 *근거*라 도구(`find_evidence`)만 준다. 없는 경험을 쓰는 길을 구조로 막는다
- **`check_draft` 가 세는 것들**: 빈 문단 · 금지표현 · 근거 없는 스킬 언급 · 문단별 문장 수
  (3~5) · 공고 요건 커버리지 · 부족 역량 언급 여부. 전부 값으로 판정한다
- 커버리지는 **기술 용어 대조**로 재고, 기술 용어가 없는 서술형 요건은 분모에서 뺀다 —
  셀 수 없는 것을 센 척하지 않는다
- **본문은 검증 통과 문단으로 결정론 조립한다.** LLM 이 본문을 `reply` 에 다시 옮겨 적으면
  검증 전 문장이 사용자에게 가고, 화면과 저장본이 갈린다. LLM 은 마무리 안내만 쓴다
- `_verify_draft` 가 마지막 방어선 — 점검을 건너뛰었어도 **근거 없는 주장은 사용자에게
  가지 않는다.** 남은 지적은 warnings 로 올려 묻히지 않게 한다
- 두 절대 규칙: 문항 답을 지어내지 않는다 · 이력서에 없는 성과를 서술하지 않는다.
  후자는 **사용자 이름으로 나가는 거짓말**이다
- 산출물은 항상 "초안" — 사용자 검토 없이 완성본이 되지 않는다(P5 GATE)

## `career_chat.py` — 진로 대화 · 최종 폴백

`FALLBACK_AGENT` 다. 플래너가 못 골랐을 때 · 확신 < 0.6 일 때 · 검증기가 다 걷어냈을 때 ·
LLM 자체가 죽었을 때 — 네 경로 전부 여기로 온다. **기능 목록만 읽어주고 끝내지 않고**
사용자 말에 답하면서 필요한 자료를 청한다.

  받는다 — 조회성 질문에 **재분석 없이** 답한다(D79)
- **입력 상한 1000자**: 자산으로 승격되지 못한 긴 원문(문서 붙여넣기)이 통째로 대화 근거가
  되는 것을 구조로 막는다. 프롬프트 금지는 실측에서 안 지켜졌다
- 취업·커리어와 무관한 요청은 내용을 답하지 않고 서비스 범위를 안내한다

## `application_plan.py` — 목표 상태 + 지원 경로

**판정은 룰, 문구는 LLM** 이 가장 선명한 파일이다.

- `_decide_status` 는 순수 룰 — 점수 구간과 요건 판정만 본다. 경계값은 리터럴로 다시 적지
  않고 `gap_matcher` 에서 가져온다(한쪽만 고쳐도 테스트가 통과하는 형태를 피한다)
- **구조적 제약**(`is_hard_constraint`) — 경력 N년·학위·필수 자격처럼 프로젝트·학습으로
  대체할 수 없는 조건. 이게 미충족이면 점수와 무관하게 중기 목표다. 로드맵을 다 해도
  그 조건 자체는 채워지지 않으니까
- LLM 은 `status`·`effort`·`hardRisk` 를 **바꾸지 않는다** — 확정된 판정을 사람 말로 옮길 뿐
- `_related_postings` 가 특이하다: `job_recommend` 를 부르고 싶은데 이 에이전트는 단발
  호출이라 `delegate_tool` 을 못 쓴다. 그래서 가드를 **수동 재현**한다(거부도 trace ·
  읽기 전용 · 실패해도 폴백 유지)

# 이 폴더를 읽을 때 알아둘 것

**1. 대부분의 주석이 사고 기록이다.** `실측(2026-07-31)`, `외부 리뷰가 지적한` 으로 시작하는
주석은 장식이 아니라 **그 코드가 왜 그 모양인지의 유일한 기록**이다. 지우면 다음 사람이
같은 것을 다시 시도한다.

**2. 폴백은 항상 이유를 남긴다.** `warnings` 를 버리는 경로가 있으면 그건 버그다 —
"왜 폴백됐는지 로그에 아무것도 없었다"를 여러 번 겪고 만든 규율이다.

**3. 하면 안 되는 것은 프롬프트로 금지하지 않고 선택지에서 뺀다.**
`requirement_index` 가 연차 요건을 빼는 것, `Literal` 로 도구 이름을 제한하는 것,
`save_plan` 이 근거 ID 를 필수로 만드는 것 — 전부 같은 원리다.

**4. `description` 을 고치면 평가셋 재측정 대상이다.** 그게 플래너의 유일한 어휘이고,
한 문장이 라우팅을 바꾼다(D97 에서 1.00 → 0.67 로 깨진 전례). 에이전트 안의 `_GOAL_SYSTEM`
을 고치는 것은 답변 품질을 바꾸는 것이라 성격이 다르다.
