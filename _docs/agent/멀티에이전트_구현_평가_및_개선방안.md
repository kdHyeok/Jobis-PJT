# 멀티에이전트 구현 평가 및 개선방안

> 2026-07-28 검토. 대상 소스: `feat/ai/web-bridge` 브랜치 `AI/src/jobis_ai/`
> (orchestrator / agents / graph / webbridge / structured.py / llm.py / session.py)

## 총평

**"LLM 플래너 + 순수 코드 검증기 + 함수형 에이전트 디스패치" 구조로, 설계 규율은 상위권이지만
엄밀히는 멀티에이전트가 아니라 '지능형 라우터 + 파이프라인'이다.**
흔한 실패작(if-else 의도 분기, 하드코딩 흐름표)은 잘 피했고, 검증 계층·평가 하네스·실측 근거가
코드에 남아 있는 점은 이 규모에서 드물게 잘한 부분. 다만 "오케스트라 기반 에이전트"라고
부르기엔 구조적 한계가 명확하다.

한 줄 요약: **하네스 설계는 A급, 오케스트레이션 동역학은 C급.**
정형 워크플로우를 피하는 뼈대(플래너 자율 + capability manifest 유도)는 이미 맞게 놓여 있으므로,
"결과를 보고 다시 정하는 루프"와 스트리밍·병렬화만 얹으면 구조를 갈아엎지 않고 목표에 도달한다.

---

## 1. 잘 구현된 것 (유지할 자산)

- **플래너/검증기 분리** (`orchestrator/planner.py` + `orchestrator/router.py`)
  판단은 LLM, 실행 가능성 확정은 순수 코드. 액션 스페이스를 Pydantic `Literal` 스키마로 제한해
  미등록 에이전트 환각을 구조적으로 차단 — 정석적인 하네스.
- **capability manifest** (`agents/__init__.py` — `AgentSpec.preconditions/produces`)
  전제 자산 생산자 자동 삽입(`router.py::_plan_agent`)으로 흐름표 없이 에이전트 추가 가능.
  "정형 워크플로우 느낌 안 나게"의 핵심 자산.
- **검증 계층 일관성**
  사용자향 LLM 문장 전부에 금지표현 검증(`safe_ack`, career_chat 등),
  `llm_not_configured` vs `llm_call_failed` 구분 후 정직한 폴백.
  표현 계층도 검증을 면제받지 않는 원칙이 전반에 지켜짐.
- **자산 무효화 규율** (`orchestrator/chat.py::_store_attachments`)
  이력서 갱신 시 파생 자산(profile/analysis) 폐기, `resume_extra`는 교체가 아닌 덧붙임.
- **평가 하네스 존재** (`eval/planner_harness.py`, `tests/test_planner_eval.py`)
  "플래너를 gpt-5-nano로 바꾸면 정확도 100%→48.8% 붕괴" 같은 실측 근거가 주석으로 남아 있음.

## 2. 구조적 한계 — "오케스트라"가 되려면 여기가 관건

### 2-1. 턴당 1회 계획, 재계획 없음 (`chat.py` 실행 루프)

플래너가 턴 시작에 시퀀스를 확정하면 에이전트 결과가 이후 선택에 반영되지 않는다.
유일한 피드백은 `followUpQuestions` 발생 시 중단뿐. 예: `posting_analysis`가
"공고 본문이 사실상 비었다"를 발견해도 뒤 에이전트는 그대로 돈다.
**오케스트레이터 느낌의 본질은 "결과를 보고 다음을 다시 정하는 루프"인데 그게 없다.**

→ **개선**: 에이전트 실행 후 `outcome` 요약을 플래너에게 주고 "계속/수정/중단"을 묻는
경량 재계획 단계 추가. 재계획 상한 1~2회로 제한(기존 하네스 철학 그대로).
다중 에이전트 시퀀스일 때만 돌리면 단일 에이전트 턴 지연은 늘지 않는다.

### 2-2. 에이전트가 에이전트가 아님

각 에이전트는 `session dict → AgentResult` 순수 함수. 도구도, 자율 루프도, 상호 통신도 없다.
세션 자산을 통한 blackboard 패턴 자체는 건전하지만, 에이전트가 실행 중 다른 에이전트나
플래너에게 무언가를 요청할 방법이 전무하다. 현 로스터에선 문제가 안 되지만
"멀티에이전트 구현"으로 소개하려면 이 격차를 인지해야 한다.

### 2-3. 무거운 파이프라인 자동 삽입에 동의 게이트 없음 (`router.py` 생산자 삽입)

분석 없이 "자소서 써줘" 하면 검증기가 `fit_analysis`(LangGraph 전체 파이프라인,
LLM 5~6회, 수십 초)를 말없이 앞에 끼운다. note로 알려주긴 하나 실행은 이미 시작된 뒤.

→ **개선**: `AgentSpec`에 `heavy: bool` 플래그를 추가하고, 무거운 생산자가 자동 삽입될 때는
"먼저 적합도 분석이 필요해요, 진행할까요?"로 한 턴 묻는다. UX·비용 모두 개선.

## 3. 성능·속도 — 효과 큰 순서

### 3-1. 전부 동기·순차 LLM 호출

`structured.py`의 `invoke()` 블로킹 호출이 워커 스레드에서 직렬로 이어진다.
fit_analysis 턴 기준: 플래너 → 공고 파싱 → 프로필 빌드 → 시맨틱 판정 → nl_render →
next_steps ≈ **직렬 LLM 6회**.

→ **개선**: 공고 파싱(`parse_job_posting`)과 프로필 빌드(`build_user_profile`)는 상호 독립 —
`graph/builder.py`에서 LangGraph 팬아웃 엣지로 병렬화하면 2~4초 즉시 단축.

### 3-2. 토큰 스트리밍 없음

SSE(`/chat/stream`)는 PROGRESS 이벤트만 중계하고 최종 답변은 통짜로 도착한다.

→ **개선**: `career_chat`·`fit_analysis_next`처럼 스키마가 `reply` 문자열 하나뿐인 표현 계층은
구조화 출력 대신 일반 스트리밍 + 사후 금지표현 검증으로 전환. 하네스가 깨지지 않으면서
체감 지연 개선폭이 가장 크다.

### 3-3. 잡담 턴이 LLM 2회 + 플래너 프롬프트 캐싱 미활용

플래너(고급 모델) → 저확신 → `career_chat`(고급 모델). 매 턴 고급 모델 플래너 호출은
nano 실측 붕괴 근거가 있으니 유지하되, 플래너 시스템 프롬프트는 매 턴 거의 동일하다.

→ **개선**: manifest(정적)와 feasibility(동적)를 분리해 정적 부분을 프롬프트 앞으로 몰고,
provider 프롬프트 캐싱(Anthropic `cache_control` / OpenAI 호환 prefix cache)이 걸리게 한다.
지연·비용 동시 절감.

### 3-4. 재시도 중첩

`structured.py` 3회 × `ChatOpenAI(max_retries=2)` = 최악 9회 네트워크 시도.
여기에 그래프 노드 재실행 루프(`route_after_*`)까지 곱해진다.
실패 시 지연 폭주가 현 구조의 숨은 리스크.

→ **개선**: 재시도는 `structured.py` 한 계층만 남기고 클라이언트 `max_retries=0`.

### 3-5. 세션 저장소 왕복 과다

한 턴에 get/update 6~8회(첨부 저장, last_message, 에이전트별 sessionUpdates,
history 기록 2회 — `append_history`가 각각 get+update). SQLite라 지금은 버티지만,

→ **개선**: 턴 시작에 한 번 읽고 턴 끝에 한 번 쓰는 write-back으로 묶으면 코드도 단순해진다.

## 4. 자잘한 결함

| 위치 | 내용 |
|---|---|
| `chat.py` (label 결정) | intent 라벨이 플래너 원안 첫 에이전트라, 검증기가 생산자를 삽입하면 실제 `dispatched`와 어긋난 라벨이 프론트로 감 |
| `structured.py` (`_MAX_INPUT_CHARS=16000`) | 뒤쪽 절단인데 한국 채용공고는 자격요건·우대사항이 후반부에 몰림 — 조용한 품질 저하. 자격/우대 키워드 이후를 보존하는 휴리스틱 필요 |
| `session.py` (`MemorySessionStore.get`) | 얕은 복사라 중첩 dict 공유 — "복사본 규약"이 사실상 깨짐. SQLite 구현과 동작 상이 |
| `router.py` (생산자 탐색) | `next(첫 번째)`라 같은 자산의 생산자가 둘 생기면 등록 순서가 곧 정책이 됨. 현재는 유일하나 주석으로 명시 필요 |

## 5. 우선순위 제안

| 순위 | 항목 | 효과 |
|---|---|---|
| 1 | 표현 계층 토큰 스트리밍 | 체감 속도 (가장 큼) |
| 2 | 그래프 독립 노드 병렬화 (파싱 ∥ 프로필 빌드) | fit_analysis 2~4초 단축 |
| 3 | 에이전트 실행 후 경량 재계획 루프 | "오케스트라 느낌"의 본질 |
| 4 | 무거운 생산자 자동 삽입에 동의 게이트 | UX·비용 |
| 5 | 플래너 프롬프트 정적/동적 분리 + 캐싱 | 매 턴 지연·비용 |
| 6 | 재시도 중첩 제거 | 실패 시 지연 폭주 방어 |
