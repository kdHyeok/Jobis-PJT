## 총평 (2026-07-29 갱신)

**"LLM 플래너 + 순수 코드 검증기 + 재계획 루프 + 도구를 쓰는 에이전트" 구조.
1차 검토의 판정("엄밀히는 멀티에이전트가 아니라 지능형 라우터 + 파이프라인")은 더 이상
정확하지 않다** — 그때 근거로 든 세 가지(재계획 없음 / 에이전트가 도구도 자율 루프도 없음 /
LLM 이 다중 시퀀스를 계획한 사례 0건)가 모두 코드와 실측에서 바뀌었다.

**남은 격차 하나**: 관찰(재계획)이 실행을 실제로 바꾼 실측 사례가 아직 없다. 루프는 돌고
결정을 기록하지만, 관측된 결정은 전부 `continue`·`finish` 였다. 통신·병렬은 07-29 오후에
메웠다(§0 표) — 다만 둘 다 **좁게** 열었다: 위임은 읽기 전용·화이트리스트, 병렬은 서로의
산출을 기다리지 않는 구간만.

한 줄 요약: **하네스 설계 A급, 오케스트레이션 동역학 C급 → B+급.**
"에이전트가 도구를 쓰며 스스로 돌고, 필요하면 옆 담당에게 묻고, 독립인 일은 동시에 한다"
까지는 실물로 확인됐다. 남은 것은 *재계획이 값을 하는지* 증명 하나다.

### 1차 검토의 핵심 근거가 뒤집힌 지점

07-28 계측의 결정적 근거는 **"LLM 이 다중 에이전트 시퀀스를 계획한 경우는 8턴 중 0건"**
(한 턴에 둘 이상 돈 것은 전부 검증기의 생산자 자동 삽입)이었다. 그것이 "라우터일 뿐"
판정의 뼈대였다.

2026-07-29 실측(이력서+공고 첨부, "이 공고에 내가 얼마나 맞는지 분석해줘"):

```
planner: 원안=['posting_analysis','resume_diagnosis','fit_analysis'] 확신=0.90
dispatch: 확정=['posting_analysis','resume_diagnosis','fit_analysis']   ← 삽입 0건
observe: continue after=posting_analysis   남은예정=['resume_diagnosis','fit_analysis']
observe: continue after=resume_diagnosis   남은예정=['fit_analysis']
observe: skipped (남은 예정 없음) after=fit_analysis
```

원안과 확정이 같다 — **검증기가 끼운 것이 아니라 플래너가 3단 시퀀스를 직접 계획했다.**
"공고를 정리하고 → 이력서를 진단하고 → 둘을 대조한다"는 순서는 코드 어디에도 없다.

### 아직 증명하지 못한 것 (정직하게)

- **관찰이 실행을 바꾼 사례 0건.** 위 궤적도 `continue` 두 번이다. 관찰의 값을 주장하려면
  `finish`(뒤 단계가 무의미해져 중단)나 `call`(새 단계 추가)이 실제로 일어난 궤적이 필요하다.
  당장 노려볼 자리는 `fit_analysis` 뒤다 — 등급이 낮은데 자소서가 예정돼 있으면 중단·교체가
  타당하다(그래서 이 도구만 `observe=True` 예외로 관찰을 건다).
- **위임 소비자 1건.** 통로(§2-2)는 열었지만 실제로 쓰는 곳이 하나뿐이다. 하나로는
  "통로가 있다"까지만 말할 수 있고 "에이전트들이 협업한다"고는 아직 못 한다.
- **병렬은 관찰 지점을 대가로 샀다.** 구간 안에서 앞 결과를 보고 뒤를 취소할 기회는 없다
  (§3). 그래서 위 첫 항목(관찰 계측)이 더 급해졌다.

## 1. 잘 구현된 것 (유지할 자산)

- **플래너/검증기 분리** (`orchestrator/planner.py` + `orchestrator/router.py`)
  판단은 LLM, 실행 가능성 확정은 순수 코드. 액션 스페이스를 Pydantic `Literal` 스키마로 제한해
  미등록 에이전트 환각을 구조적으로 차단 — 정석적인 하네스.
- **capability manifest** (`agents/__init__.py` — `AgentSpec.preconditions/produces`)
  전제 자산 생산자 자동 삽입(`router.py::_plan_agent`)으로 흐름표 없이 에이전트 추가 가능.
- **Tool / Agent 구분** (2026-07-28~29 추가). 기준은 하나 — *말을 하는가.*
  도구(`job_recommend`·`roadmap_manager`·`fit_analysis`)는 계산만 하고 `entry` 에서 reply 를
  비우며, 문장은 표현 계층(`agents/tool_render.py`)이 만든다. 구분에서 규칙이 따라 나온다:
  **도구 뒤에는 관찰을 걸지 않는다**(결정론이라 재선택 여지가 없다). 근거가 성립하지 않는
  도구는 `observe=True` 로 예외 선언한다 — 규칙의 근거는 "도구라서"가 아니라 "바꿀 게 없어서"다.
- **자기 루프 하네스** (`agents/agent_loop.py`)
  도구 이름 Literal 제한, 스텝 상한, 사용자향 문장 금지표현 검증 + **1회 재작성 기회**,
  스텝마다 trace + 로그. 실패해도 outcome 을 돌려줘 폴백이 이유를 삼키지 않는다.
- **검증 계층 일관성** — 사용자향 LLM 문장 전부에 금지표현 검증,
  `llm_not_configured` vs `llm_call_failed` 구분 후 정직한 폴백. 표현 계층도 면제받지 않는다.
- **자산 무효화 규율** (`chat.py::_apply_attachments`) — 이력서 갱신 시 파생 자산 폐기.
- **평가 하네스** (`eval/planner_harness.py`, `tests/test_planner_eval.py`) — 실측 근거가
  주석으로 남아 있다("플래너를 nano 로 바꾸면 정확도 붕괴").
- **규약을 테스트가 강제한다** — 도구는 reply 를 만들지 않는다 / 도구는 render 를 갖는다 /
  에이전트는 render 를 갖지 않는다 / 도구 뒤에 관찰이 걸리지 않는다 / **에이전트가 만든다고
  선언한 자산(`produces`)은 세션이 저장할 수 있는 키다**(마지막 항목은 07-29 에 실제로
  어긋나 면접 턴이 매번 실패하던 것을 잡고 추가).

## 2. 구조적 한계 — 지금 남은 것

### 2-1. 재계획 루프는 있으나 값을 증명하지 못했다 ✅구조 / ⚠️증명

에이전트마다 결과 요약을 경량 플래너에 되물어 계속/중단/수정을 정한다(`chat.py`).
낭비도 정리했다 — 도구 뒤·남은 예정이 없을 때는 아예 걸지 않는다(07-28 계측: 관찰 두 번이
26.2초를 쓰고 아무것도 바꾸지 않았다).

→ **다음**: `finish`·`call` 이 실제로 발생하는 시나리오를 계측한다(등급 하 + 자소서 예정).
발생하지 않는다면 관찰의 존재 이유를 다시 따져야 한다 — 지금은 "돌긴 도는" 상태다.

### 2-2. 에이전트 간 통신 ✅해결(좁게) / ⚠️소비자 1건

`agent_loop.delegate_tool` 로 통로를 열었다. 자기 루프 에이전트가 루프 안에서 다른 담당을
직접 부르고, 그 답을 관찰로 받는다. **좁게 연 것이 설계의 핵심이다** — 통로가 넓으면
오케스트레이터의 상태 전이 독점과 동의 게이트가 동시에 무너진다:

| 가드 | 이유 |
|---|---|
| 읽기 전용(상대의 `sessionUpdates` 미적용) | 턴의 상태 전이는 오케스트레이터만 한다 |
| 화이트리스트로 선언한 상대만 | 등록돼 있다고 아무나 부르면 액션 스페이스 제한이 무의미 |
| `heavy` 금지 | 에이전트가 말없이 수십 초 파이프라인을 시작하면 동의 게이트 우회 |
| 전제 미충족이면 실행 안 함 | 빈 근거 위에서 돌지 않는다 |
| 중첩 금지(깊이 1) | 재귀 폭주 방어 |
| 상대의 경고를 그대로 올림 | 폴백 이유를 삼키지 않는다(이 코드베이스의 반복된 실수) |

지금 소비자는 하나다(`coverletter_draft` → `resume_diagnosis`: 근거가 빈약한 이유는
이력서 진단이 이미 세고 있으므로 같은 계산을 두 번 구현하지 않는다). **소비자가 하나뿐인
동안은 "통로가 있다"까지가 정직한 주장이다.**

### 2-3. 나머지 에이전트의 표현 분리 미완 ⚠️남음

`posting_analysis`·`resume_diagnosis` 는 추출(도구)과 표현이 한 몸이다. `fit_analysis` 를
도구로 내린 방식(계산은 `entry`, 문장은 `tool_render`)을 그대로 적용하면 된다.

## 3. 성능·속도 — 1차 지적은 모두 반영됨

§3-1~§3-5 는 §0 표 참고(팬아웃 병렬화, 표현 계층 토큰 스트리밍, 플래너 프롬프트 정적화,
재시도 단일화, 세션 write-back). **에이전트 시퀀스 병렬화도 07-29 에 반영했다.**

실측(같은 입력, GMS `gpt-4.1-mini`): 순차 24.5·20.7·21.5·18.4초 → 병렬 12.1·22.4·12.5·15.2초.
평균 21.3 → 15.6초. 편차가 큰 것은 병렬 구간의 길이가 **가장 느린 멤버 하나**(fit_analysis)로
정해지고 그 자체가 흔들리기 때문이다 — 구조적 이득은 "합계 대신 최댓값"이고, 덤으로 구간
중간의 관찰 호출 2회가 사라진다.

**대가도 적는다.** 병렬 구간 안에서는 (ㄱ) 중간 재선택 지점이 사라지고 — 앞 결과를 보고
뒤를 취소할 기회를 포기한다 — (ㄴ) 토큰 스트리밍을 끈다(프론트가 델타를 한 버퍼에 이어
붙여서 두 에이전트 토큰이 섞인다). 진행 이벤트는 그대로 흐른다.

한편 "여러 멤버가 각자 프로필을 짓는 중복"을 막으려 선빌드를 넣었다가 **뺐다**: 임계 경로에
8.3초를 얹는데, 전제에 resume 이 있다고 프로필을 쓰는 것이 아니어서(fit_analysis 는 그래프
안에서 따로 짓는다) 대부분 헛돈이었다. 확실한 손해로 드문 손해를 막지 않는다.

한편 LLM 공급자를 GMS(`gpt-4.1-mini`)로 옮기면서 턴당 30~70초 → **4~7초**가 됐다
(2026-07-28). 속도 논의의 상당 부분은 이 전환이 흡수했다.

| `RAG/` | 산출물 `.py` 0개. 우리 훅(`rag.py` provider 분기)은 준비됐고 그 자리는 `local_postings`(실공고 2053건)가 채우고 있다. 계약 형태 확정이 코드보다 급하다 |
