# RAG 성능 평가 계획 v5 — 재수립 및 재테스트

> v4 실행([APPLIED.md](APPLIED.md))은 **게이트 3 FAIL(κ=0.263)이 확인된 파일럿**이다.
> 인프라(풀링·지표·게이트·CI)는 유효하므로 유지하고, **실패 원인인 judge 라벨 품질만 고쳐서 전량 재테스트**한다.
> v4 리포트의 수치는 이후 인용하지 않는다.

---

## 0. v4에서 확정된 사실 (재테스트의 근거)

| 발견 | 증거 |
|---|---|
| judge(gemini, PROMPT_V1)가 양성을 체계적으로 부풀림 | McNemar b=1, c=32 (교차모델 앵커 112쌍) |
| 부풀림의 구체 패턴 = **직군 무시** (기술 키워드 겹침만으로 Correct) | "Python QA" ↔ "AI 서비스 개발자" → Correct 등 32건 중 다수 |
| 경력 요건 무시도 관찰 (10년↑ 공고를 3년차 질의에 Correct) | 앵커 불일치 목록 |
| Correct 이진 기준으로는 Ambiguous 계층 잡음이 전이되지 않음 | ambiguous 세션 이진 일치 20/20 |

→ 수정은 **확인된 결함(직군 판정 우선)을 반영한 PROMPT_V2** 하나만. 앵커에 과적합하지 않도록 결함 1건 단위로 고치고 매번 검증한다.

## 1. 평가 방향성 3원칙 (사용자 요구, 사전 등록)

1. **객관적 지표** — 정규화 nDCG@3 헤드라인 유지. 객관성은 지표가 아니라 **라벨 신뢰성 게이트(κ)** 가 만든다
2. **과정·결과의 합리성** — 사전 등록(이 문서) → 실행 → 게이트 → 리포트. 게이트 FAIL이면 헤드라인 인용 금지. 평가셋 버전 스탬프(프롬프트 버전·코퍼스 상태·일시)를 리포트에 박아 회귀 비교 가능하게 한다
3. **산업 표준 정합** — TREC pooling / BEIR-style qrels / graded relevance / LLM-judge + 앵커 κ 검증 / 쌍대 부트스트랩. v4와 동일 계보 유지

## 2. 실행 단계 (사전 등록)

### Phase 0 — 프롬프트 A/B (전량 재판정 전 관문)

- 대상: 앵커 112쌍 (v4 Claude 라벨 보유분) — 추가 비용 약 15 API 호출
- PROMPT_V2로 112쌍만 판정 → Claude 앵커 대비 v1/v2 비교
- **채택 기준 (측정 전 등록):**
  - 이진 일치율 ≥ 0.75 (v1: 0.64)
  - 이진 κ ≥ v1 + 0.15 (v1: 0.263)
  - McNemar 부풀림 방향(c≫b) 완화
- 미달 시: 전량 재판정 하지 않고 결함 패턴을 다시 분석해 프롬프트 재수정

> **Phase 0 실행 결과 (2026-07-28):**
> | 프롬프트 | 3분류 | 이진 | κ | McNemar (b, c) | 판정 |
> |---|---|---|---|---|---|
> | v1 (기준) | 53.6% | 70.5% | 0.263 | (1, 32) | — |
> | v2 (직군 규칙) | 67.9% | 79.5% | 0.313 | (3, 20) | **기각** (κ 미달) |
> | v3 (직군+경력+지역 규칙) | 74.1% | 87.5% | **0.525** | (1, 13) | **채택** (두 기준 통과) |
>
> v2 기각 후 잔여 불일치 20건 분석 → 전부 경력 요건·지역 무시 패턴 → 해당 규칙만 추가한 v3 재검증.
> "확인된 결함 1건 단위 수정" 원칙이 두 사이클 작동함.

### Phase 1 — 전량 재판정

- `judgments.json` → `_archive/judgments_v1_prompt_v1.json` 백업 후 초기화
- `python -m eval.run --judge` (PROMPT_V2, 재개형, 약 3,300건)
- 풀은 **v4와 동일**(pool.json 유지) — arm 결과·코퍼스가 불변이므로 재판정만으로 충분하고, v4와의 차이가 순수하게 라벨 효과로 해석된다

### Phase 2 — 앵커 재구성 + 검증

- 새 judgments 기준으로 층화추출 재실행 (`--sheets`) — 라벨이 바뀌면 계층 소속이 바뀌므로 필수
- Claude 앵커 재라벨: 기존 112쌍 라벨은 (qid, uid) 키로 재사용, 신규 쌍만 추가 판정 (기준은 v4와 동일하게 고정: 지역·직무/기술·경력 3조건)
- **사람 채점은 여전히 별도 트랙** — 원본 시트 label 열은 비워 두고, 사람이 채점하면 gemini/Claude/사람 3자 비교로 승격
- `python -m eval.anchor --score` → 게이트 3 재판정

### Phase 3 — 측정 + 리포트 v2

- `python -m eval.run --measure` (게이트 통과 시 --force 없이)
- 리포트에 버전 블록 추가: `{prompt_version, n_corpus, judged_at}`
- v4 대비 변화 요약을 별도 섹션으로 기록 (라벨 분포 변화, arm 순위 유지 여부)

## 4. 성공 판정 (사전 등록)

- **1차 목표**: 게이트 3 PASS (κ ≥ 0.60, Claude 앵커 기준) 상태의 report.json — "배너 없는 첫 리포트"
- **2차 목표**: v4 대비 arm 순위 결론(rrf_ce best, bm25 열세)이 유지되는지 확인 — 유지되면 순위 결론의 라벨-강건성 입증, 뒤집히면 v4 순위 결론도 철회
- 절대 수치는 사람 채점 전까지 계속 "교차모델 합의 기준"으로만 인용

**게이트 3 재실패의 분해** (judge=Correct 50쌍 중 앵커 동의 12):
- 앵커 Ambiguous 17건 — 재택 미확인·경력무관↔시니어 요구 등 진짜 경계 사례 (기준 정의 차이)
- 앵커 Incorrect 21건 — **규칙이 프롬프트에 있는데도 모델이 적용 실패** (직군 구분·신입↔N년↑·기술 부재)
- judge=Incorrect 동의율 100%, Ambiguous 95% — **judge의 음성 판정은 신뢰 가능, 양성 판정만 불신**

**결론**: 프롬프트 반복 수정의 한계 도달. 남은 선택지는 (a) judge 모델 상향(gemini-2.5-flash 비-lite A/B), (b) 사람 채점으로 어느 쪽 기준이 옳은지 확정, (c) 양성 판정만 2차 검증(judge=Correct 쌍 한정 Claude 재판정 — 약 970건).

## 6. 입출력 명세서 반영 — 입력 계약 트랙 (2026-07-28 추가)

명세서(`RAG_입출력_명세서.md`)가 규정하는 실제 입력은 이번 Tier 1이 잰 자연어 질의와 다르다:

| | 명세서 입력 A | 명세서 입력 B | 기존 Tier 1 질의 |
|---|---|---|---|
| 형태 | **직업명 문자열** ("백엔드 개발자") | **profile JSON** (_UserProfileRead) | 자연어 (지역·경력 조건 포함) |
| 정규화 | parse_query (텍스트 파싱) | **파싱 없음 — 필드 직접 매핑** | parse_query |
| 지역/경력 조건 | 없음 | 지역 없음 / 연차는 experiences에서 합산 | 질의에 명시 |

**구현 완료**: [jobrag/spec_adapter.py](../jobrag/spec_adapter.py) — 명세서 계약 진입점 `search(conn, 입력A|입력B)`
- 입력 B 매핑: `skills[].name`+`projects[].techStack`→tech(화이트리스트 정규화), `experiences[].role`→role_category(룰 분류)+질의 텍스트, `period` 합산→exp_years. `evidenceMap`/`uncertainties`는 명세대로 미사용
- 출력 계약: 원본 공고(raw JSONB) 무변경 + `score`(단조 내림차순)·`match_reason`(본문 근거 있는 skills만 — 환각 0) 추가, 0건 시 `{"postings": []}`, 예외 전파 금지
- 무의미 질의 가드: 기술·직군 신호 0 + BM25 매치 0이면 dense 최근접으로 채우지 않고 0건 반환

**Tier 0 결과 (2026-07-28)**: 31 passed / 0 failed — `accepts_string`·`accepts_profile`·`empty_ok`·`fields_intact`·`sorted`·`topk`·`skills_grounded`·`fields_grounded` 전부 PASS ([contract_report.json](contract_report.json))

**남은 것 — 입력 계약 Tier 1 (별도 트랙)**:
- 입력 A 트랙: 직업명 질의셋(직군 12종 기준)으로 풀링·판정 재사용 — 지역·경력 축이 없으므로 기존 30질의 결과를 대체하지 않고 병행 보고
- 입력 B 트랙: golden profile 약 8건 제작 → 동일 기계 재사용 (판정 약 440건). "이 profile에 이 공고가 적합한가"는 판정 기준 자체가 질의형과 다르므로 앵커도 별도 표본 필요
- 기존 자연어 30질의 트랙은 **파서 강건성 스트레스 테스트**로 재해석해 유지 (실입력 경로는 아님을 리포트에 명시)

## 6.5 앵커셋 재구축 — 명세서 정규화 질의 기반 (2026-07-28)

기존 앵커(자유 자연어 질의 표본)는 실입력 분포와 달라 폐기(`_archive/anchor_freeform_v5/`)하고,
명세서 키워드(**직군+기술+연차**)가 항상 전부 포함된 정규화 질의 15종([spec_anchor.py](spec_anchor.py) SPEC_QUERIES,
직군 12종 전부 + 연차대 분산)으로 재구축했다. 풀 439쌍(5 arms × depth 10) → gemini v3 전량 판정
(`judgments_spec.json`, 기존 자연어 트랙 judgments.json과 분리) → 층화추출 120쌍 + recheck 20.

| 지표 | 구 앵커 (자유 질의, v3) | **신 앵커 (정규화 질의, v3)** |
|---|---|---|
| 이진 κ | 0.252 | **0.445** |
| 이진 일치율 | — | 0.742 |
| 사후가중 정확도 | 0.766 | **0.822** |
| judge=Correct 일치 | 24% (12/50) | **54% (27/50)** |
| judge=Ambiguous 일치 | 95% | 75% |
| judge=Incorrect 일치 | 100% | 94% |
| McNemar | (1, 32) | (8, 23) — 양성 부풀림 잔존·완화 |
| 게이트 3 (κ≥0.60) | FAIL | **FAIL** |

해석: 질의를 정규화 고정형으로 바꾸자 judge 신뢰도가 전 지표에서 개선됐다(경계 조건이 명시돼
판정이 쉬워진 효과). 그러나 양성 부풀림은 구조적으로 잔존 — 불일치 23건의 패턴은 여전히
직군 혼동(풀스택↔백엔드, AI 개발자↔DS)과 신입·인턴 전용 공고 vs 경력 질의. 게이트 3 통과에는
여전히 (a) judge 모델 상향 또는 (b) 사람 채점이 필요하다(§5 결론과 동일).

주의: 이 앵커의 κ는 정규화 질의 분포 기준이다. 기존 report.json(자연어 30질의)의 게이트 3에
그대로 대입할 수 없으며, 본평가를 정규화 질의로 옮기는 입력 계약 Tier 1(§6)과 짝을 이룬다.
사람 채점용 시트는 `anchor/session_easy.csv` 등 label 열 공란으로 유지, Claude 라벨은 `*_claude.csv`.

## 6.6 judge 모델 상향 A/B — flash-lite vs flash (2026-07-29 실행, 사전 등록)

§6.5가 남긴 두 갈래 중 **(a) judge 모델 상향**을 먼저 검증했다(사람 채점 전에 끝내야
시트 재생성이 불필요해지므로 순서상 우선). 실행: [judge_ab.py](judge_ab.py),
리포트 `anchor/ab_report_flash.json`.

- **단일 변수**: judge 모델만 교체. 프롬프트 v3·풀(pool_spec.json 439쌍)·앵커(Claude 120쌍) 동일
- **사전 등록 채택 기준** (측정 전 고정, HANDOFF §3-B): κ ≥ 0.60 **또는** 기준선(0.4448) 대비 +0.10 이상
- 앵커 120쌍만 뽑아 재판정하지 않고 **풀 439쌍 전량**을 재판정했다 — 앵커만 재판정하면 한 프롬프트에
  함께 들어가는 공고 20건의 배치 구성이 기준선과 달라져 모델 외 변수가 섞인다. 기준선 κ를
  0.4448로 재현해 대조 코드가 `anchor_report.json`과 같은 양을 재는지 먼저 확인했다.

| 지표 | gemini-2.5-flash-lite (기준선) | **gemini-2.5-flash (실험군)** |
|---|---|---|
| 이진 κ | 0.4448 | **0.5000** (Δ +0.055) |
| 이진 일치율 | 0.7417 | **0.7917** |
| judge=Correct 일치 | 54% (27/50) | **63.9% (23/36)** |
| judge=Ambiguous 일치 | 75% (15/20) | 70% (14/20) |
| judge=Incorrect 일치 | 94% (47/50) | 90.6% (58/64) |
| McNemar (b, c) | (8, 23), 통계량 6.32 | **(12, 13), 통계량 0.00** |
| 판정 뒤집힘 | — | 56/439쌍 (12.8%) |
| 게이트 3 (κ≥0.60) | FAIL | FAIL |

**판정: REJECT** — κ 0.500은 절대 기준(0.60)에도, 증분 기준(+0.10)에도 미달한다. 사전 등록한
기준선이므로 사후에 기준을 낮추지 않는다. **본판정 judge는 flash-lite(v3) 유지**,
`judgments_spec.json`·`report.json`은 그대로 두고 `judgments_spec_flash.json`은 실험 기록으로만 보존한다.

해석 — 채택은 못 했지만 결과가 무의미하지는 않다. flash는 **양성 부풀림의 방향성을 사실상 제거**했다:
McNemar가 (8, 23)/6.32 → (12, 13)/0.00으로, "LLM이 체계적으로 Correct를 남발한다"는 v4 이래의
편향이 대칭 잡음으로 바뀌었다. Correct 판정 수 자체도 50 → 36으로 줄고 그 정밀도는 54% → 64%로 올랐다.
즉 **남은 불일치는 방향성 편향이 아니라 경계 사례에서의 산발적 불일치**다. 이는 §6.5가 지목한
경계 기준 2건(① 신입·인턴 전용 공고 vs 경력 질의, ② 풀스택 공고 vs 백엔드 질의)이
모델 용량이 아니라 **기준 미정의** 문제임을 시사한다 — 사람 채점 전 이 2건을 확정하는 절차

### 6.7.1 절단 k=3 해석 유효성 진단 (2026-07-29 추가)

"k=3에서 본 수치를 지표로 해석하는 것이 유효한가"에 답하기 위해 진단값을 산출했다

**결론: 절단 자체는 타당하다.** 생성부가 상위 3건을 컨텍스트로 쓰므로(`ragas_prep.TOP_K=3`)
지표 k가 시스템의 실제 결정 크기와 일치한다. 임의로 고른 숫자가 아니다.
**문제는 타당성이 아니라 해상도**이고, 셋 중 둘이 절대 수치를 낙관 쪽으로 민다.

| 문제 | 실측 | 방향 |
|---|---|---|
| ① 천장 포화 | rrf_ce가 **6/15 질의(40%) 만점**, 서로 다른 값 7종 | 낙관 + 검정력 소실 |
| ② Ambiguous 반값 | nDCG@3 0.7521 → 애매=0이면 **0.6450** (−0.107) | 낙관 |
| ③ 기준선 이원화 | 정규화 분모=풀 내부 무작위 0.3482, random arm=코퍼스 무작위 0.0626 | **보수적** (부풀리지 않음) |

**①이 중요한 재해석을 낳는다.** 그간 "질의 15종이라 검정력 부족"으로 설명했는데,
절반은 **지표 포화** 때문이었다. 질의당 후보 29건에 적합 평균 6.6건(23%)이면 상위 3건에
적합을 넣는 건 어려운 과제가 아니고, 만점이 40%면 개선을 측정할 여지 자체가 없다.
→ 질의 수만 늘려도 arm 구분이 안 될 수 있다. **풀 depth를 늘려 천장을 올리는 게 병행돼야 한다.**

**②의 극단 사례**: SA11(데이터 사이언티스트)은 사람 라벨에서 **적합 0건**인데 nDCG@3 = 0.70이다

정상 동작이지만, **"적합한 게 없는 질의"에서 0.70이 나오는 수치를 성능으로 인용하면 오독**이다.
라벨 구성이 Correct 99 / Ambiguous 88 / Incorrect 252로 애매가 적합과 거의 맞먹어 영향이 크다.

### 지표 설계 보완 (사전 등록)

1. **k=3 유지 + P@3·애매=0 nDCG@3 헤드라인 병기** — 애매 인정분을 숨기지 않는다. (반영 완료)
2. ~~풀 depth 상향 후 nDCG@10 · Recall@10 추가~~ → **정정: 풀 재구성이 불필요했다.**
   풀이 5 arm × top-10의 **합집합**이므로 각 arm의 상위 10건은 전부 판정돼 있다
   (arm 결과 750건 중 미판정 0건). 따라서 **k≤10은 기존 라벨로 즉시 계산되고 앵커셋과 무관하다**
   — 앵커는 라벨 신뢰도(κ)를 재는 별도 표본이라 절단 k와 상관이 없다. §6.7.2에서 실행함.
   k>10 또는 풀을 더 깊게 파는 것만 재판정·재채점이 필요하다
3. **적합 0건 질의는 "결과 없음이 정답" 케이스로 분리 채점**

### 6.7.2 절단 k 확대 재측정 (2026-07-29, 추가 라벨링 0건)

§6.7.1의 "풀 재구성 필요" 판단이 틀렸음을 확인하고 k = 1 · 3 · 5 · 10으로 재측정했다
(`report_spec.json` → `multi_k`). 사람 라벨·앵커셋 불변.

| 절단 | 만점 질의 | 값 종류 | 구분된 비교 | recall 천장 | rrf_ce nDCG | rrf_ce recall |
|---|---|---|---|---|---|---|
| k=1 | 11/15 | 3/15 | 4/10 | 0.210 | 0.8000 | 0.1286 |
| k=3 | 6/15 | 7/15 | 6/10 | 0.553 | 0.7521 | 0.3030 |
| k=5 | 2/15 | 13/15 | 6/10 | 0.717 | 0.7228 | 0.4093 |
| **k=10** | **1/15** | **15/15** | **7/10** | **0.935** | 0.7166 | 0.6033 |

**진단·개발용 절단은 k=10이 옳다.** 천장 포화가 사실상 해소되고(1/15) 질의별 값이 전부
달라져(15/15) 해상도가 최대가 된다. 운영 주장용 k=3은 제품 정합성 때문에 유지한다.

#### 결론이 바뀐 것 두 가지

1. **교차인코더 기여 부정이 강화됐다.** `rrf_vs_rrf_ce`가 k=1·3·5·10 **전부** 0선을 걸친다
   (k=10 CI [−0.055, +0.132]). §6.7.1에서 "k=3 천장 포화 탓일 수 있다"고 유보했으나
   **포화가 해소된 k=10에서도 동일** → 절단 탓이 아니라 실재하지 않는 차이로 판단한다.
   질의당 0.836초(다른 arm의 20배)를 쓸 근거가 없다. **rrf를 기본값으로 권고.**
2. **하이브리드 자체의 가치는 확인됐다.** `bm25_vs_rrf_ce`는 k=3에서 구분 불가였으나
   k=5·k=10에서 유의해진다(k=10 CI [+0.005, +0.164]). `bm25_vs_rrf`도 k=10에서 유의.
   즉 **융합 단계의 가치는 실재하고 재순위 단계의 가치만 미확인**이다.

| rrf | 0.5333 | 0.4000 | 0.2526 | 0.5662 |
| bm25 | 0.4444 | 0.3400 | 0.2258 | **0.4527 (최하)** |

## 6.8 판정 기준 성문화 + 연차 추출 결함 발견 (2026-07-29)

게이트 3 해소의 최우선 수단으로 경계 기준을 문서화하려 했고
([JUDGING_CRITERIA.md](JUDGING_CRITERIA.md) v1 작성), 그 과정에서
**기준 문제가 아닌 파이프라인 데이터 결함**을 발견했다.

### 발견 — 연차 필터가 코퍼스 79%에서 무력화돼 있다

| 실태 | 수치 |
|---|---|
| active 공고 | 1,172건 |
| `exp_min` NULL (판정자에게 "경력 무관/미상"으로 표시) | **930건 (79.4%)** |
| 그중 본문에 "경력 N년" 명시 | **476건 (전체의 40.6%)** |
| 원인: `raw.experience`에 값 없이 라벨만 수집 (`'경력'`) | **785건 (67.0%)** |

`sources.py::parse_exp_range('경력')` → 숫자 없음 → `(None, None, False)`.
의심 플래그도 서지 않는다(`"경력" not in raw`가 False). 그리고
`search.py:96` `(p.exp_min IS NULL OR p.exp_min <= %s)`가 NULL을 **항상 포함**시킨다.
→ **명세서 입력 3요소(직군·기술·연차) 중 연차가 사실상 작동하지 않는다.**

이것이 SA01(3년차 질의)의 상위 3건이 5년+/6년+/7년+ 공고로 채워진 이유이고,
경력 질의 불일치율 22.1%의 직접 원인이다. **기준 미정의가 아니라 데이터 부재였다.**

### 사람 라벨로 검증

| 본문 기준 연차 양립성 | n | Correct | Ambiguous | Incorrect | Incorrect율 |
|---|---|---|---|---|---|
| 요구 > 질의 연차 (초과) | 29 | 7 | 3 | 19 | **65.5%** |
| 요구 ≤ 질의 연차 (양립) | 34 | 17 | 6 | 11 | 32.4% |

기준서는 "초과 시 기본 Incorrect, 단 초과폭 1년 이내 + 직군·기술 정확 일치일 때만 Ambiguous"로 성문화했다.

## 6.9 명세서 실입력 경로 평가 — 입력 A / B 트랙 (2026-07-29)

기존 15종 트랙이 명세서 입력 A도 B도 아닌 **합성 중간형**임을 확인하고, 실제 진입점으로
재측정했다. 실행: [io_tracks.py](io_tracks.py), [golden_profiles.py](golden_profiles.py),
리포트 `report_io_tracks.json`.

| 트랙 | 진입점 | 질의 |
|---|---|---|
| 입력 A | `query_parser.parse_query(직업명)` | 직업명 문자열 12종 |
| 입력 B | `spec_adapter._spec_from_profile(profile)` | 합성 골든 profile 12건 |
| (상한) 15종 | `_run_arm_*` 직접 호출 | 직군+기술+연차 합성 문자열 |

골든 profile은 **저자 작성 합성 표본**이다(실제 이력서 아님). 명세서 `_UserProfileRead`
스키마·예시를 따르고, 12건 전부 어댑터가 의도한 연차·직군으로 매핑되는지 검증했다(불일치 0).

### 결과 — 예측이 틀렸다

사전에 "입력 A는 기술 신호가 0이라 가장 나쁠 것"이라 예상했으나 **반대였다.**

| 트랙 | best arm | 정규화 nDCG@3 | P@3 |
|---|---|---|---|
| **입력 A (직업명만)** | rrf_ce | **0.7669** | **0.7500** |
| 입력 B (profile) | rrf_ce | 0.5936 | 0.5000 |
| (상한) 15종 | rrf_ce | 0.6853 | 0.6222 |

쌍대 부트스트랩(같은 12직군, 짝지어 비교):

| arm | B − A | 95% CI | 판정 |
|---|---|---|---|
| rrf_ce | −0.1633 | [−0.319, −0.011] | **유의** |
| **dense** | **−0.3030** | **[−0.492, −0.133]** | **유의** |
| rrf | −0.0829 | [−0.259, +0.099] | 구분 불가 |
| bm25 | −0.0430 | [−0.236, +0.159] | 구분 불가 |

### 원인 — 질의 텍스트에 기술을 이어붙이면 dense가 망가진다

`_spec_from_profile`은 `text = roles[:1] + tech[:8]`로 질의 텍스트를 만든다
([spec_adapter.py:73](../jobrag/spec_adapter.py)). 여기에 **일반적인 기술명**이 붙으면
임베딩 벡터가 직군 개념에서 밀려나 off-role 공고를 끌어온다.

증거: **dense만 −0.303으로 무너지고 bm25는 −0.043으로 사실상 불변**이다.
BM25는 항별로 점수를 매기니 희석에 둔감하고, dense는 문장 전체를 한 벡터로 만들므로 직격탄이다.

직군별로 보면 기술의 **판별력**이 부호를 정한다:

| 손실 큰 직군 | 기술 | Δ |
|---|---|---|
| qa | Python, Git | **−0.671** |
| mobile | Kotlin, Android | −0.669 |
| security | Linux | −0.591 |
| frontend | React, TypeScript, Next.js, JavaScript | −0.331 |

| 이득 본 직군 | 기술 | Δ |
|---|---|---|
| fullstack | React, Node.js, JavaScript, MySQL | **+0.361** |
| sre | Kubernetes, Linux, Terraform | +0.331 |

`Python`·`Git`·`Linux`처럼 직군을 가리지 못하는 기술이 붙으면 직군 신호를 삼킨다.
반대로 `Kubernetes+Terraform`처럼 조합 자체가 직군을 특정하면 도움이 된다.

### 함의 (사전 등록 없이 채택하지 말 것)

개선 후보는 **질의 텍스트 구성 변경**이다 — 직군 term에 가중치를 주거나, 직군과 기술을
따로 임베딩해 결합하거나, 기술을 dense 질의에서 빼고 BM25·필터에만 쓰는 방안.
단 **이건 사후 관찰에서 나온 가설이므로 사전 등록 후 A/B로 검증해야 한다**(PLAN_v5 §2 원칙).

### 비교의 한계 (반드시 병기)

1. **트랙마다 풀이 다르므로 정규화 분모가 다르다.** A·B는 같은 코퍼스·깊이·판정 프롬프트이고
   12직군으로 짝지어 부트스트랩했으므로 A vs B 비교는 성립하지만, 절대 수치를 트랙 간
   직접 대입할 수는 없다.
2. **15종 트랙 수치는 `exp_min` 백필 이전 코퍼스 기준**이다(§6.8). A·B는 백필 이후다.
   "상한선"으로 인용할 때 이 confound를 함께 적어야 한다.
3. 골든 profile 12건은 합성이며 실사용 이력서 분포를 대표하지 않는다.
4. 게이트 3(판정 신뢰도)은 15종 트랙 앵커에서만 측정됐다. A·B 트랙에는 **사람 라벨이 없다** —
   두 트랙 수치는 judge 라벨 단독 기준이므로 "LLM 교차검증 기준" 꼬리표가 필요하다.
