# 📝 AI AGENT 설계서 템플릿 및 작성 가이드

> **참고**: 이 설계서 템플릿은 *Agent Engineering* 도서를 참고하여 작성 
> Agent 개발 프로세스에서 시행착오를 줄이고, 에이전트를 체계적으로 설계하기 위해 활용 목적으로 작성

---

## 🛠️ 설계서 템플릿 (9개 섹션)
아래 9개 섹션을 순서대로 모두 작성합니다. 각 섹션 하단의 **💡 작성 요령**을 참고하여 구체적으로 작성하세요.

### 1. 개요·목적
*   **해결하려는 문제**: (1~2문장으로 명확하게 서술)
*   **타깃 사용자**: (한 줄 요약)
*   **왜 Agent여야 하는가**: 단일 LLM 호출, 단순 RAG, 또는 고정된 Workflow 패턴으로 해결할 수 없는 이유를 1~2문단으로 서술합니다.

> **💡 작성 요령**
> "Agent가 필요한 이유"를 설명할 때는 "요청마다 동적으로 처리 경로가 달라지는 구체적인 예시"를 제시해야 합니다. 추상적으로 "더 지능적인 처리가 필요해서"와 같은 설명은 피하세요.

---

### 2. 사용자 시나리오
*   **페르소나 (1명)**: 이름, 역할, 최종 목적 정의
*   **대표 요청 (2~3개)**: 사용자가 실제로 입력할 법한 자연어 원문 예시
*   **단일 Tool로 끝나지 않는 이유**: 각 요청이 왜 한 번의 단순 도구 호출로 해결되지 않는지 분석 (요청별로 한 줄씩 작성)

> **💡 작성 요령**
> 준비한 2~3개의 요청 시나리오는 서로 완전히 다른 처리 경로를 타도록 설계해야 합니다. 만약 모든 요청이 동일한 도구 호출 순서로 해결된다면, 그것은 Agent가 아니라 일반적인 Workflow(시나리오 기반 개발)에 가깝습니니다.

---

### 3. 기능 요구사항
*   **Must-have (필수 요구사항)**: 3~5개
*   **Nice-to-have (선택 요구사항)**: 2~3개

> **💡 작성 요령**
> 각 항목은 "어떤 입력을 받아 어떤 출력을 내는지" 동작(Behavior) 위주로 작성합니다. 내부 구현 기술이나 방법론 대신 시스템이 외부에 보여줄 구체적인 행동을 명시하세요.

---

### 4. Agent 패턴 선택과 근거
*   **선택한 패턴**: ReAct / Reflection·Reflexion / Plan-and-Execute / Multi-Agent 중 택일 (혹은 혼합형)
*   **선택 근거 (2~3줄)**: 왜 이 문제와 도메인에 해당 패턴이 가장 적절한지 서술
*   **루프 구조도**: 의사코드(Pseudocode) 또는 5~10줄 내외의 순서 설명

> **💡 작성 요령**
> 단순히 "가장 널리 쓰여서" 혹은 "유명해서" 같은 근거는 피해야 합니다. "요청당 필요한 단계(Step) 수 예측이 가능한가", "스스로 검증(Self-Correction)을 해야 하는가", "역할 분담이 필요한가" 등의 명확한 기준으로 선택 이유를 따질 것.

---

### 5. 동작 명세
전통적인 소프트웨어 요구사항 명세서(SRS)의 입출력 정의에 Agent 고유의 특성(종료 조건, 실패 흐름 등)을 더해 구체화합니다.

*   **입력 스키마**: 사용자 입력의 형태 (단순 자연어 문자열인지, 구조화된 필드를 포함하는지 정의)
*   **출력 스키마**: 최종 응답 포맷 (자연어 답변, 구조화된 JSON, 혹은 둘 다인지 정의)
*   **정상 흐름 (Trajectory 예시)**: 특정 시나리오 하나를 선정하여 LLM이 겪는 생각(Thought), 행동(Action), 관찰(Observation) 과정을 5~10단계의 트레이스 샘플로 작성
*   **예외 흐름**: 도구(Tool) 호출 실패, 처리 불가 응답, 권한 부족 상황에서의 시스템 대처 방식
*   **종료 조건**: 최대 허용 단계 수(Max steps), 정지 신호(Stop signal), 무한 루프 반복 탐지 기준

> **💡 작성 요령**
> 정상 흐름 예시는 시스템 개발 및 검증의 기준이 되는 '모범 답안 경로(Trajectory)' 역할을 합니다. 이 흐름을 바탕으로 추후 성공 판정 체크리스트를 구축합니다.

---

### 6. Tool 명세
제공할 도구는 2~5개 사이로 구성하는 것을 권장합니다. 도구가 너무 많으면 LLM이 도구 선택 과정에서 혼란을 느껴 성능이 저하될 수 있습니다.

| Tool 이름 | 목적 (1줄 요약) | 입력 스키마 | 출력 스키마 | 실패 시 반환 포맷 | 사용 조건 (조건부) | -> 작성 예시 목록


> **💡 작성 요령**
> *   **설명의 구체성**: 각 도구의 설명은 LLM이 이를 언제 호출해야 하는지 스스로 정확하게 판단할 수 있도록 자연어로 아주 세세하게 작성해야 합니다.
> *   **예외 반환 규칙**: 에러 발생 시 시스템 예외(Throw Exception)를 던지기보다, `{ error: "...", detail: "..." }` 형태의 결과 객체를 반환하도록 설계해야 LLM이 에러 메시지를 학습해 다음 행동을 조율할 수 있습니다.
> *   **파괴적 동작 예방**: 데이터 삭제, 결제 등 위험한 동작을 수행하는 도구는 반드시 사용자 동의를 확인하는 안전 장치(`confirm=True`) 파라미터를 명시하세요.

---

### 7. 데이터셋
각 도구가 실제로 주고받는 데이터의 구체적인 명세를 정립합니다.

*   **도구별 데이터 출처**: API 엔드포인트 URL, 데이터셋 이름, 혹은 실제 파일 경로
*   **응답 샘플**: 실제 데이터 값 기반의 샘플 데이터 1~2건 (JSON, CSV 등)
*   **데이터 특성 요약**: 데이터 필드 수, 업데이트 주기, 접근 권한/인증 요구 여부
*   **Mock 여부**: 실제 데이터 환경이 구축되지 않았다면 Mock 데이터임을 명시 (단, 스키마는 동일하게 유지)

> **💡 작성 요령**
> 대상 API를 실제로 한 번 호출해본 뒤 반환되는 실제 JSON 응답을 그대로 붙여넣는 것이 가장 확실하고 빠릅니다.

---

### 8. 성공 판정 기준
개발한 Agent의 동작 성공 여부를 객관적이고 정량적으로 평가하기 위해 3~5개의 체크리스트를 정립합니다.

*   [ ] **경로 검증**: "요청 X에 대해 Tool A → Tool B 순서로 정상 호출하는가?"
*   [ ] **예외 처리**: "특정 Tool 호출 실패 시, 재시도하거나 대체 도구(Fallback)로 전환하는가?"
*   [ ] **결과 검증**: "최종 답변 내에 Tool을 통해 조회한 특정 핵심 데이터 필드가 온전히 포함되어 있는가?"
*   [ ] **효율성**: "모든 태스크가 제한된 스텝 수(예: 6 step) 이내에 스스로 도구 사용을 멈추고 종료되는가?"
*   [ ] **일관성**: "동일한 요청을 여러 번 주입했을 때 비정상적으로 실행 경로가 바뀌지 않는가?"

> **💡 작성 요령**
> 각 검증 항목은 주관성을 배제하고 **예/아니오(Yes/No)로 명확히 판정할 수 있어야** 합니다. "자연스럽게 대답한다", "지능적으로 판단한다"처럼 모호한 정성 평가 방식은 지양할 것. -> 추후 agent 판단 평가를 위한
