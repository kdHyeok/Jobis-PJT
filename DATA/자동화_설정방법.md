# 매일 자동 수집 설정 방법 (Windows + WSL)

`run_daily_update.py` 를 매일 정해진 시각에 자동 실행하도록 등록하는 방법입니다.

## 왜 WSL의 cron을 쓰지 않는가

WSL2 안의 `cron` 은 **우분투가 실행 중일 때만** 동작합니다. PC를 켜두더라도 WSL 창을
열지 않으면 우분투가 잠들어 있어서 cron이 돌지 않습니다. 그래서 **Windows 작업
스케줄러가 WSL을 깨워서 실행**하는 방식이 확실합니다.

## 1. 실행 확인 (먼저 손으로 한 번)

**Windows의 PowerShell**에서 실행합니다(WSL 우분투 터미널이 아님). `wsl.exe` 는 Windows
프로그램이고, 작업 스케줄러도 Windows에서 도니까 같은 경로를 미리 확인하는 것입니다.

```
wsl.exe -d Ubuntu-24.04 -- bash -lc "cd ~/projects/Jobis && .venv/bin/python run_daily_update.py --max-new 5"
```

`status=completed 모든 단계 성공` 이 나오면 준비 완료입니다.

> **배포판 이름 주의**: 이 PC에 등록된 이름은 `Ubuntu`가 아니라 **`Ubuntu-24.04`** 입니다.
> `-d Ubuntu` 로 쓰면 "지정한 이름의 배포가 없습니다" 오류가 납니다. 이름을 다시 확인하려면
> PowerShell에서 `wsl.exe -l -v` 를 실행하세요.

## 2. 작업 스케줄러 등록

1. 시작 메뉴에서 **작업 스케줄러**(Task Scheduler) 실행
2. 오른쪽 **작업 만들기**(Create Task) 클릭 — "기본 작업 만들기"가 아니라 "작업 만들기"
3. **일반** 탭
   - 이름: `Jobis 채용공고 일일 수집`
   - **사용자가 로그온했는지 여부에 관계없이 실행** 선택
   - **가장 높은 수준의 권한으로 실행** 체크 해제(불필요)
4. **트리거** 탭 → 새로 만들기
   - 매일, 시작 시각 예: `오전 6:00`
   - 하단 **작업을 놓친 경우 가능한 즉시 작업 시작** 체크
     (PC가 꺼져 있어 놓친 날은 다음 부팅 직후 실행됨)
5. **동작** 탭 → 새로 만들기
   - 동작: 프로그램 시작
   - 프로그램/스크립트: `wsl.exe`
   - 인수 추가:
     ```
     -d Ubuntu-24.04 -- bash -lc "cd ~/projects/Jobis && .venv/bin/python run_daily_update.py"
     ```
6. **조건** 탭
   - **컴퓨터를 AC 전원으로 사용할 때만 작업 시작** — 노트북이면 체크 해제 권장
   - **작업을 실행하기 위해 절전 모드 해제** 체크(선택)
7. **설정** 탭
   - **작업이 이미 실행 중이면 다음 규칙 적용**: `새 인스턴스 시작 안 함`
     (스크립트에도 잠금 장치가 있지만 스케줄러 쪽에서도 막아두면 안전합니다)

## 3. 결과 확인

실행마다 로그가 남습니다(14일 후 자동 삭제).

```bash
ls -lt ~/projects/Jobis/logs/ | head
tail -40 ~/projects/Jobis/logs/daily_update_*.log | tail -40
```

정상 실행이면 마지막 줄이 이렇습니다.

```
status=completed 모든 단계 성공
```

일부 단계가 실패하면 이렇게 남고, 어떤 단계인지 알려줍니다.

```
status=completed_with_failures steps=ocr:work24
```

## 4. 만들어지는 결과물

| 파일 | 용도 |
|---|---|
| `exports/all_job_postings.json` | RAG 파이프라인 입력 |
| `exports/all_job_postings_postgres.sql` | 백엔드 PostgreSQL 적재용 |
| `data/all_job_postings/all_job_postings.db` | 로컬 확인용 SQLite |

SQL은 `ON CONFLICT DO UPDATE`라 **같은 파일을 여러 번 넣어도 안전**합니다. 동일 PK의
공고에 새 OCR 본문이 생기면 본문·출처·OCR 상태를 함께 갱신하고, 새 본문이 비어 있으면
기존 본문을 보존합니다. 테이블 스키마는 `infra/airflow/migrations/jobrag`의 Flyway
마이그레이션을 먼저 적용해야 합니다.
운영 DB 반영은 서버 담당자에게 SQL 파일을 전달하거나, 직접 접속 권한이 있으면
아래처럼 적용합니다.

```bash
psql -h <서버주소> -U <사용자> -d jobiss -f exports/all_job_postings_postgres.sql
```

## 참고: 옵션

```bash
.venv/bin/python run_daily_update.py --max-new 100   # 사이트당 상한 변경(기본 50)
.venv/bin/python run_daily_update.py --skip-crawl    # 수집 없이 OCR~SQL만 다시
.venv/bin/python run_daily_update.py --skip-ocr      # OCR 없이 수집~SQL만
```

## 주의

- **수집 중에는 같은 사이트 크롤러를 따로 실행하지 마세요.** 같은 JSON·DB 파일을
  동시에 쓰면 내용이 깨집니다. 스크립트에 잠금 장치가 있지만, 개별 크롤러를 직접
  실행하는 경우는 막지 못합니다.
- 첫 실행이 아니라면 이미 수집한 공고는 자동으로 건너뛰므로, 매일 실행해도
  중복이 쌓이지 않습니다.
