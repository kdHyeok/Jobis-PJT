# 채용공고 데이터 수집 방법론 (5개 사이트)

> 팀 공유·발표용 문서. "이 데이터 어떻게 모았어요?"에 대한 답.
> 방법론은 크롤러 코드(`crawl_*_it.py`) 기준이며, 수집 건수만 진행에 따라 갱신하면 됨.
> 작성: 2026-07-27

## 🎤 30초 요약

> 잡코리아·사람인·원티드·인크루트·고용24 5개 사이트에서 **'개발자' 관련 검색어 29개**로,
> **모두 최신 등록순 정렬**로 검색 결과를 조회해 공고 상세를 수집했습니다.
> 제목 키워드로 개발 직무만 남기고, 상세 본문에 **담당업무·자격요건이 텍스트로 있는 공고**와
> **본문이 이미지뿐이라 OCR이 필요한 공고**(이미지 URL만 보관)를 분리 저장했습니다.
> 사이트별 텍스트 2,000건 + 이미지형 500건이 목표이고, 요청 간격 1.2초를 지켰으며,
> 공고 ID로 사이트 내 중복을, 회사명+공고명으로 사이트 간 중복을 제거해 통합합니다.

## 1. 공통 설계 (5개 사이트 동일)

### 검색 조건
- **검색어 29개** (전 사이트 공유): 개발자, 백엔드/프론트엔드/풀스택/웹/앱/모바일/안드로이드/iOS/서버 개발자,
  소프트웨어 엔지니어·개발자, 시스템 엔지니어, 데이터 엔지니어, 데이터 사이언티스트, 머신러닝 엔지니어,
  AI 개발자, DevOps 엔지니어, 클라우드 엔지니어, Java/Python/자바/Node/React 개발자,
  게임/임베디드 개발자, 보안/QA 엔지니어, 프로그래머
- **정렬: 전 사이트 최신 등록순** (정확도순 아님 → "수집 시점의 최근 공고 스냅샷")

### 필터 3단계 (공고 1건마다)
| 단계 | 기준 | 목적 |
|---|---|---|
| ① 직무 필터 | 제목에 개발 직군 단어(개발/엔지니어/프로그래머/developer/devops/아키텍트 등) 포함 **AND** 비개발 단어(사업개발·기획·디자이너·마케터·영업·헬프데스크 등) 미포함 | 비개발 공고 제거 |
| ② 본문 품질 | 본문이 일정 길이 이상 **AND** '담당업무'류 라벨 **AND** '자격요건'류 라벨 존재 → **텍스트 공고** (`need_ocr="X"`) | 부실 공고 제거 (우대사항은 선택) |
| ③ 이미지형 분류 | 본문 길이 미달 + 이미지 존재 → 본문 대신 **이미지 URL만 저장** (`need_ocr="O"`) | 버리지 않고 OCR 대기로 보존 |

- 본문 길이 기준: **300자**(잡코리아·사람인·인크루트·고용24 공통) / **원티드 100자**
  - 처음에는 350~400자로 두었는데, **담당업무·자격요건 라벨을 모두 갖춘 온전한 공고가
    글자수 몇 자 차이로 탈락하는 일이 반복**됐다(실측: 393자/400자, 341자/350자,
    291자/300자 — 모두 라벨과 기술스택이 명확한 실제 공고).
  - 반대로 실제로 걸러내야 했던 공고(회사소개만 있는 556자 이미지)는 글자수가 아니라
    **라벨·신호어 조건**에서 걸렸다. 즉 완결성을 판별하는 건 라벨이고 글자수는 정상
    공고만 떨어뜨리고 있어서, 라벨 조건을 유지한 채 글자수 문턱만 낮췄다.
  - 원티드가 100자인 이유: 본문이 짧아도 라벨 구조가 뚜렷한 사이트라 라벨 존재를
    더 신뢰한다(라벨 없이 짧은 경우는 여전히 걸러진다).
- `detail_text`에는 **요약이 아니라 실제 모집요강 원문만** 저장 (사이트별 원문 위치는 2절)

### 수집량·중복·저장
- 상한: 사이트별 **텍스트 2,000건 + 이미지형 500건** (별도 상한, 둘 다 차면 자동 종료)
- 사이트 내 중복: **공고 ID 기준** 1회만 수집 (여러 검색어에 걸려도 중복 없음)
- 저장: SQLite + JSON 이중 저장, **15개 필드 공통 스키마**
  (`source, posting_id, company, title, url, employment_type, experience, education, location,
  posted_date, deadline, detail_text, image_urls, need_ocr, collected_at`)
- 각 레코드에 수집 시각(`collected_at`, UTC) 기록

### 수집 윤리·안정성
- **요청 간격 1.2초** (사이트 부하 방지 · 이용정책 고려), 수집 봇을 밝히는 User-Agent
- 25건마다 중간 저장(checkpoint), 중단 시 이어받기(resume) → 불필요한 재요청 최소화
- 한 공고 실패가 전체를 멈추지 않음 (건별 예외 처리 후 계속)

## 2. 사이트별 수집 방식 (다른 부분만)

### ① 잡코리아 (jobkorea.co.kr)
- **목록**: 검색 페이지 `/Search/?stext=검색어&ord=RegDtDesc&Page_No=N` — `ord=RegDtDesc` = 등록일 내림차순
- **메타데이터**: 상세 페이지에 심긴 **구조화 데이터(JSON-LD, schema.org JobPosting 표준)** 파싱
  → 회사명·제목·고용형태·경력·학력·근무지·등록일·마감일
- **본문**: 상세 페이지 요약이 아닌, 모집요강 **iframe**(`GI_Read_Comt_Ifrm`) 원문

### ② 사람인 (saramin.co.kr)
- **목록**: **채용정보 전용 검색** `/zf_user/search/recruit?searchword=검색어&recruitSort=reg_dt&recruitPage=N` — `reg_dt` = 등록일순, 페이지당 40건
  - 🔍 **디버깅 사례**: 처음엔 통합검색(`/zf_user/search`)의 `page` 파라미터를 썼으나, 수집이 ~500건에서
    멈춰 조사 → **깊은 페이지 응답이 바이트 크기까지 동일**한 것을 발견 (`page`가 무시되어 항상 첫 페이지 반환).
    채용 전용 검색의 `recruitPage`가 실제 페이지 파라미터임을 실측(페이지 간 겹침 0)으로 확인 후 교체.
- **본문**: **모바일 페이지**(`m.saramin.co.kr`)가 본문을 **base64 인코딩**으로 담고 있어 이를 디코드해 원문 확보
  (PC 페이지는 동적 렌더링이라 정적 수집이 어려움 → 모바일 우회가 핵심 아이디어)
- **메타데이터**: PC 상세의 og:title 메타태그(회사명·제목) + 본문의 라벨(`고용형태:`, `근무지`, `접수기간` 등) 정규식 추출
- 본문 끝의 사람인 유의사항·저작권 고지는 제거 후 저장

### ③ 원티드 (wanted.co.kr)
- **목록**: **공식 검색 API** (`/api/v4/jobs?...&job_sort=job.latest_order`) — 최신순, JSON 응답 (파싱 안정성 최고)
- **메타데이터**: API JSON에서 직접 (id, 포지션명, 회사명, 주소, 마감)
- **본문**: 상세 웹페이지에서 "포지션 상세" ~ "유의사항" 사이 구간만 잘라 저장
- **한계**: 검색 API가 검색어당 약 700건까지만 반환 → 검색어 수를 늘리는 방식으로 보완

### ④ 인크루트 (incruit.com)
- **목록**: 통합검색 `search.incruit.com/list/search.asp?col=job&kw=검색어&SortCd=reg` — `SortCd=reg` = 최근 등록순, 페이지당 30건
- **메타데이터**: 상세 페이지 텍스트의 라벨(고용형태/경력/학력/근무지역/마감) 다음 줄 추출
- **본문**: 모집요강 **iframe**(`jobpostcont.asp`) 원문
- 특이사항: 응답 인코딩이 cp949(한국어 레거시) → 인코딩 처리, 일시 오류 3회 재시도
- 본문 품질에 개발 용어(Python, 백엔드, AI 등) 포함 조건 추가 (비개발 도배 공고 방지)

### ⑤ 고용24 (work24.go.kr — 고용노동부 공공 채용정보)
- **목록**: 검색 폼 **POST 요청** (`sortField=DATE&sortOrderBy=DESC` = 최근 등록일순), 페이지당 10건
  - 검색어를 번갈아 순회해 최신 공고를 검색어 간 고르게 수집
- **메타데이터**: 상세 페이지의 표(th/td 라벨: 고용형태/경력/학력/근무 예정지), 접수기간에서 마감일 추출
- **본문**: '상세모집요강' **iframe** — 고용24가 연결한 외부 채용사이트의 원문
- 특이사항: 공공 사이트라 응답이 느려 타임아웃 45초 + 3회 재시도

## 3. 사이트 간 통합 (merge_job_postings.py)

- 5개 사이트 JSON을 하나로 병합, **사이트 간 중복 제거**
- 중복 판정: **회사명 + 공고명**을 정규화(소문자화, 특수문자 제거)한 키가 같으면 동일 공고
- 중복 시 남기는 기준(품질 우선순위): 텍스트 본문 있는 것(`need_ocr=X`) > 본문 긴 것 > 메타데이터 많은 것 > 최근 수집
- 일부 사이트 미수집 상태여도 있는 사이트만으로 병합 가능
- 결과: `exports/all_job_postings.json` + `data/all_job_postings/all_job_postings.db`

## 4. 이미지형 공고 OCR 보강 (enrich_ocr.py)

- 대상: `need_ocr="O"` 공고의 이미지 → 본문 텍스트로 변환해 `need_ocr="X"`로 전환
- 엔진: **PaddleOCR** (로컬·무료, 한국어 검출+인식 모델 명시) — 외부 API·LLM 호출 없음(비용 0원)
- 파이프라인: 이미지 다운로드 → 작은 이미지 2배 확대 → **세로로 긴 이미지 슬라이싱**(2000px, 겹침 150px)
  → OCR → 겹침 구간 **유사 줄 중복 제거(fuzzy dedup)** → 오탈자 보수 교정 → 품질 판정(길이+채용 신호어) 통과 시 채택
- **정확도 검증**: 실제 공고를 사람 수준 판독(비전 모델)으로 전사해 준정답을 만들고 CER(글자 오류율) 측정
  - 개선 과정(표본 1건 기준): EasyOCR 18.1% → PaddleOCR(엔진 교체) 17.8% → **+중복 제거 개선 9.4%**
  - **다중 표본 검증(4개 사이트 공고 4건, 총 7,206자)**: 표본별 CER 7.9%~19.1%,
    **평균 CER 11.4% (정확도 88.6%)**
  - 오류 성질: 순수 오독(치환)은 극소수(표본당 4~25자). CER의 대부분은 차트 라벨·장식 텍스트
    누락과 다단 레이아웃의 읽기 순서 차이로, 채용 정보 이해에는 영향 적음
  - **채용 핵심 정보(담당업무·자격요건·우대사항 섹션, 기술 키워드) 보존율: 4개 표본 모두 100%**
- 채택 기준: 공백 제외 **250자 이상 + 채용 신호어 3개 이상**. 로고·장식 이미지처럼 글자가
  거의 없는 결과는 자동으로 걸러진다.
- 실패한 공고는 사이트별 사이드카(`*_ocr_failed.json`)에 **건별로** 기록해 다음 실행에서
  건너뛴다(중단돼도 같은 실패를 반복 시도하지 않음). `--retry-failed` 로 재시도한다.

### 이미지 수집·판독에서 실제로 겪은 문제 (해결 완료)

사이트마다 이미지를 올리는 방식이 달라서, "OCR 정확도"와 무관한 **수집 단계 문제**가
상당수였다. 모두 실제 공고 페이지를 직접 열어 데이터와 대조하다가 발견했다.

| 문제 | 원인 | 해결 |
|---|---|---|
| 본문 이미지가 통째로 누락 | 이미지가 URL이 아니라 HTML에 **base64 인라인**으로 박혀 있어, `http/https`로 시작하는 것만 받는 필터에서 전부 탈락 (공고 전문 1,047자 손실) | 상세 페이지 주소만 저장하고(base64 원문은 1건에 1.7MB라 저장 불가) OCR 시점에 그 페이지를 받아 안의 이미지를 꺼내 읽음 |
| 이미지 요청 403 | 공백·한글 URL 대응으로 넣은 URL 인코딩이, 파일명에 구분자로 쓰인 `+`(`EV+Charger`)까지 `%2B`로 바꿔 경로가 달라짐 | `+`를 안전 문자에 추가 |
| 예외 없이 빈 응답 | 인크루트 이미지 변환 프록시가 같은 URL에 0바이트를 간헐적으로 반환(3회 연속 요청으로 재현 확인) | 빈 응답이면 대기 후 최대 2회 재시도 |
| 이미지 없는데 OCR 대기로 분류 | 사람인이 이미지가 없을 때도 `blank.png` placeholder를 `<img>`로 넣어둠 | 파일명 패턴으로 제외 |
| HTTPS 인증서 오류 | 오래된 회사 자체 호스팅 서버가 인증서만 깨져 있고 HTTP는 정상 | 인증서 오류 시 HTTP로 1회 재시도 |

**"OCR이 안 된다"의 대부분은 OCR 성능 문제가 아니었다.** 잡코리아 잔여 13건을 파보니
이미지 9~10장이 전부 사이트 템플릿의 UI 장식(섹션 제목 그래픽·화살표)이라 읽을 글자가
없고, 실제 내용은 HTML 텍스트로 온전히 있는데 글자수 문턱에서 탈락한 경우였다.

## 4-1. 자동 실행 (run_daily_update.py)

크롤링 → OCR → 통합 → SQL 4단계를 한 번에 실행한다. **OCR이 통합보다 먼저** 돌아야
하므로(사이트별 파일의 본문을 채운 뒤 합쳐야 함) 순서를 고정했다.

- 사이트당 새 공고를 `--max-new`(기본 50)만큼만 추가 → 매일 돌려도 부담 없음
- **중복 실행 방지**: 잠금 파일로 막는다. 같은 JSON·DB를 동시에 쓰면 파일이 깨지기 때문
  (비정상 종료로 남은 잠금은 6시간 뒤 자동 무시)
- **실행별 로그**: 자식 프로세스 출력을 받는 즉시 기록 → 몇 분 걸리는 단계도 진행 상황
  확인 가능. 14일 후 자동 삭제
- **부분 실패 허용**: 한 사이트가 실패해도 나머지로 계속 진행

### 재수집 제외 목록 (excluded_postings.json)

사람이 확인해 "본문을 채울 방법이 없다"고 판정한 공고를 데이터에서 지워도, **그 공고는
사이트에 그대로 살아 있어서 다음 수집에 새 공고로 다시 들어온다.** 자동화로 매일 돌리면
정리한 결과가 매일 되돌려지므로, 제외 판정을 파일에 남겨 크롤러가 건너뛰게 했다.

제외 사유 예시 — 사이트 자동 삽입 장식 이미지뿐(카테고리 아이콘·`blank.png`),
마케팅 배너만 있음, 채용공고가 아닌 교육과정 모집, 본문 텍스트 0자, 직무 오탐(제목의
"엔지니어"만으로 통과한 기계 엔지니어 공고).

## 5. 한계 (질문 대비 — 먼저 밝히면 신뢰도가 올라감)

1. **전수조사 아님**: 검색어 기반이라 검색어에 안 걸리는 공고는 누락 (예: 제목이 "테크리드 모집"뿐인 공고)
2. **시점 스냅샷**: 최신순 수집 → 마감되면 사라지는 데이터. 수집분의 상당수가 D-30 이내 마감
3. **메타데이터 결측**: 경력 등 일부 필드는 사이트 구조화 데이터의 한계로 미표기 비율 높음 (본문 추출로 보강 여지)
4. **동일 업체 도배** 가능 (한 업체가 지역별 수십 건) → 분석 시 별도 필터 필요
5. **이미지형 공고**는 OCR 정확도(≈90%)만큼의 오탈자 존재 — 단, 오독은 조사(을/를) 위주로 내용 이해에 지장 없음
6. **원티드**는 API 반환 한계(검색어당 ~700건)로 타 사이트 대비 수집량이 적을 수 있음
7. **페이지네이션 파라미터는 사이트마다 검증 필요**: 파라미터를 받아도 무시하고 같은 페이지를
   돌려주는 경우가 있음(사람인 통합검색의 `page`) → 페이지 간 응답 크기·결과 겹침 비교로 검증함
