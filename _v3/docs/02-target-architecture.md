# 02. 목표 아키텍처

- 이름: JOBIS AI v3 semantic core
- 목표: 임의의 URL·이미지·텍스트 공고를 근거 보존형 구조로 해석하고, 사용자의
  확인을 거쳐 적합도와 로드맵 초안을 생성한다.
- 비목표: AI가 DB를 직접 변경하거나, 사용자 승인 없이 공고·커리어·로드맵을 공개 적용하는 것

## 1. 핵심 원칙

### 1.1 원문과 해석을 분리한다

수집기가 만든 텍스트는 원본이 아니라 `추출 결과`다. 원본 URL·이미지, 추출 세그먼트,
사용자 정정본과 AI 해석을 서로 다른 객체로 보존한다.

### 1.2 AI는 후보와 근거를 만들고 규칙은 무결성을 검증한다

AI가 담당한다.

- 문맥에 따른 모집 직무 후보
- 포지션별 경력 조건
- 필수·우대·업무 문장의 원자적 분해
- 공고 문장과 기술·업무·도메인의 의미 연결 후보
- 사용자 경험과 요건의 근거 기반 관련성

결정론적 코드가 담당한다.

- JSON Schema와 enum 검증
- evidence ID 참조 무결성
- min/max 경력 범위와 날짜 형식 검증
- 필수·우대 충족률 계산
- 공고 해시·중복·캐시 키
- 권한, RLS, 저장, 큐, 재시도, 버전
- 사용자 승인 여부
- 로드맵 그래프의 간선·좌표·버전 무결성

### 1.3 taxonomy는 열린 사전이다

taxonomy는 알려진 별칭과 기존 기술 ID를 찾는 데 사용한다. 사전에 없는 기술은 버리지 않고
`NEW_CANDIDATE`로 남긴다. taxonomy 일치 여부는 공고의 직무나 기술 존재 여부를 최종 확정하지
않는다.

### 1.4 공고 분석과 커리큘럼 설계를 분리한다

공고가 요구하는 사실과 사용자가 무엇을 어떤 순서로 배워야 하는지는 다른 문제다. 공고
분석이 먼저 검증된 구조를 만들고, 로드맵 에이전트는 그 구조만 사용해 학습 후보를 제안한다.

### 1.5 불확실성을 보존한다

하나로 확정할 근거가 부족하면 후보, 신뢰도, 충돌 근거를 저장한다. 사용자에게 결과를 크게
바꾸는 질문만 한 번에 하나씩 묻는다. 질문 상한에 도달해도 임의로 미충족 처리하지 않는다.

### 1.6 외부 효과는 사람이 승인한다

AI 결과는 항상 초안이다. 사용자 확인 전에는 공고 해석, 커리어 조각, 로드맵 공개 버전을
변경하지 않는다. 공용 카탈로그 병합과 신규 기술 승인은 운영자 권한이다.

## 2. 목표 구성 요소

```text
1. Intake Orchestrator
   └─ 대화 의도·입력 종류·필요한 다음 단계를 선택

2. Source Acquisition
   ├─ URL/HTML 수집
   ├─ 이미지 VLM/OCR
   ├─ 붙여넣기 원문
   └─ source segments + warnings

3. Source Verification
   ├─ 추출 원문 표시
   ├─ 사용자 수정
   └─ VerifiedPostingSnapshot 생성

4. Posting Interpreter
   ├─ 회사·제목
   ├─ positions[]
   ├─ 포지션별 경력·업무
   ├─ 필수·우대요건
   └─ evidence references

5. Ambiguity Resolver
   ├─ 실제 복수 모집 직무 선택
   ├─ 경력 조건 충돌 확인
   └─ 결과를 크게 바꾸는 질문만 생성

6. Fit Analyzer
   ├─ confirmed career evidence
   ├─ claimed/evidenced/verified 분리
   ├─ requirement status
   └─ verdict proposal + gaps

7. Capability Normalizer
   ├─ 기존 canonical skill 연결
   ├─ 신규 기술 후보
   ├─ 업무·도메인·자격·정성요건 분리
   └─ 운영자 검토 후보

7.5 Capability Knowledge Graph
   ├─ 공용 역량·개념·기술 노드
   ├─ 필수·권장·조건부 선행관계
   ├─ 구성·선택·대체·직무 관련 관계
   ├─ 출처·신뢰도·검토 상태·버전
   └─ 목표 역량의 역방향 선행경로 조회

8. Curriculum Proposer
   ├─ 학습 가능한 역량만 선택
   ├─ 수준·범위·선행관계 제안
   ├─ 회사 맞춤 프로젝트 제안
   └─ RoadmapProposal 생성

9. Deterministic Service Core
   ├─ 저장·RLS·큐·캐시·중복
   ├─ 계산·그래프 무결성
   └─ 승인·버전·감사·롤백

10. Renderer
    └─ 검증된 정형 결과를 사용자 문장과 카드로 표현
```

각 항목을 반드시 독립 LLM 에이전트로 구현할 필요는 없다. `Source Acquisition`, 저장,
계산, 검증은 도구나 결정론적 서비스가 적합하다. 에이전트라는 이름보다 책임과 계약 분리가
우선이다.

Capability Knowledge Graph는 별도 `C:\jobiss-capability-graph-lab` 작업에서 구축한다.
v3 AI는 그래프 데이터를 직접 소유하거나 임의 수정하지 않고, 승인된 그래프 버전을 조회하는
소비자다. 그래프가 준비되기 전에도 Source Verification부터 Fit Analyzer까지는 독립적으로
구현할 수 있다.

| 결정 | AI | 규칙/서버 | 사용자 | 운영자 |

| 모집 포지션 후보 | 근거와 함께 제안 | 계약·모순 검증 | 분석할 포지션 선택 | taxonomy 개선 |
| 경력 조건 | 근거와 함께 제안 | 범위·단위 검증 | 애매할 때 확인 | 이상 사례 검토 |
| 필수·우대요건 | 원자적으로 제안 | evidence 참조 검증 | 원문 확인 | 필요 시 교정 |

| 로드맵 학습 후보 | 제안 | 그래프·중복·잠금 계산 | 초안 적용·취소 | 정책 검토 |
| 공고 중복 | 유사 후보 설명 | 정확 중복 판정 | 영향 없음 | 최종 병합·분리 |
| DB 변경 | 권한 없음 | 트랜잭션 수행 | 승인 버튼 | 관리자 작업 |

## 4. 사용자 진입점별 흐름

### 4.1 채팅에서 URL과 “분석해줘” 입력

```text
사용자 메시지 즉시 저장
→ 의도: 공고 분석
→ URL 수집·원문 추출
→ 추출 결과 확인 카드 표시
→ 사용자 확인 또는 수정
→ positions[] 구조화
→ 복수 직무/중대한 모호함이 있으면 질문
→ 선택 포지션 기준 공통 공고 분석
→ 사용자별 적합도 분석
→ 결과 카드와 로드맵 초안 생성 제안
```

“분석해줘”는 수집과 구조화 시작에 대한 동의다. 추출 결과의 정확성까지 자동 승인한 것으로
해석하지 않는다.

### 4.2 채용공고 페이지에서 URL·이미지 등록

채팅과 같은 Source Acquisition 및 Verification API를 사용한다. 별도 HTML 파서나 별도
직무 판정 흐름을 만들지 않는다. 화면만 다르고 계약과 상태 전이는 동일하다.

### 4.3 붙여넣기 원문

붙여넣기 텍스트는 OCR 오류 위험이 낮지만 여전히 복수 직무와 경력 문맥 오류가 가능하다.
긴 원문을 접어서 보여주되 회사·제목·직무·경력·요건 구조를 사용자가 확인한다.

### 4.4 이미지 공고

이미지 원본과 추출 텍스트를 나란히 확인할 수 있어야 한다. 경력, 직무, 마감일처럼 결과를
크게 바꾸는 필드는 원본 영역을 바로 열 수 있어야 한다. 신뢰도가 낮거나 서로 충돌하는
세그먼트는 확인 전 분석을 차단한다.

## 5. 공용 데이터와 사용자 데이터

### 공용으로 재사용할 수 있는 것

- 검증된 공고 원문 지문과 출처 식별자
- 사용자 개인정보를 제거한 구조화 공고
- 포지션별 직무·경력·필수·우대요건
- 정규화된 공용 기술 연결
- 분석기·계약 버전
- 운영자가 승인한 공고 중복·기술 병합 정보

### 사용자별로만 저장할 것

- 사용자가 제공한 원문과 정정 내역
- 대화와 질문 답변
- 이력서·커리어 조각
- claimed/evidenced/verified 상태
- 적합도, 공백, 지원 판정
- 개인 로드맵 버전과 진행 상태
- 현재 목표와 최종 목표

공통 분석 캐시는 공고 구조까지만 재사용한다. 사용자별 적합도는 항상 현재 사용자의 최신
근거와 검증 상태로 다시 계산한다.

## 6. 진행 상태 공개

내부 추론이나 chain-of-thought는 노출하지 않는다. 사용자가 기다려야 하는 실제 작업 경계만
이벤트로 공개한다.

```text
SOURCE_FETCH
SOURCE_EXTRACT
AWAITING_SOURCE_VERIFICATION
POSTING_STRUCTURE
AWAITING_POSITION_SELECTION
PROFILE_ASSEMBLY
FIT_ANALYSIS
CAPABILITY_NORMALIZATION
ROADMAP_PROPOSAL
CONTRACT_VALIDATION
RESULT_ASSEMBLY
```

- 빠른 단계도 이벤트 이력에는 남긴다.
- 화면 표시를 위해 인위적으로 지연하지 않는다.
- 10~15초 동안 새 이벤트가 없으면 heartbeat와 현재 단계의 경과 시간을 표시한다.
- 내부에서 LLM 재작성이나 tool loop가 실행되면 같은 단계의 `detail`을 갱신한다.
- 새로고침해도 서버 상태를 다시 조회해 동일한 진행 상태를 복원한다.

## 7. 오류와 fallback 원칙

- 수집 실패와 분석 실패를 구분한다.
- OCR 신뢰도 부족은 분석 실패가 아니라 사용자 확인 필요 상태다.
- 계약 검증 실패 시 잘못된 일부 결과를 저장하지 않는다.
- 근거가 없으면 `null` 또는 `UNKNOWN`을 반환한다.
- fallback을 사용하면 사용자와 로그에 이유를 남긴다.
- 분석 실패 후 사용자 원문, 정정, 질문 답변, 작업 ID는 보존한다.
- 재시도는 같은 idempotency key를 사용하고 중복 결과를 만들지 않는다.
- 서버 재시작 후 오래된 `RUNNING` 작업은 lease 만료로 복구한다.

## 8. v3의 성공 기준

- 임의 공고의 직무와 경력을 단어 하나로 확정하지 않는다.
- 여러 모집 포지션을 손실 없이 저장한다.
- 사용자 확인 전 잘못된 OCR이 적합도와 로드맵에 들어가지 않는다.
- 공고의 정성적 문장이 기술 노드로 표시되지 않는다.
- 사전에 없는 기술을 누락하지 않고 후보로 보존한다.
- 같은 공고의 공통 구조는 재사용하되 사용자 평가는 섞이지 않는다.
- 기존 에이전트의 추적·동의·상태·RAG 장점을 유지한다.
- 기존 버전과 병행 실행 및 즉시 롤백할 수 있다.
